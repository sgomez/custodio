# F154 — Packages: the .deb depends on libtss2-rc0t64 and every package requires systemd 257

## Scope
Design 4 and Design 5, packages. Built here:
- `packaging/nfpm.yaml`: the `.deb` Depends gain `libtss2-rc0t64` beside the other libtss2 packages, with a comment that systemd loads
  `libtss2-rc` by `dlopen` and Ubuntu only recommends it. The `.rpm` and Arch package keep `tpm2-tss` (it ships every libtss2 library), unchanged.
  The `.deb` Pre-Depends rises to `systemd (>= 257)`; the comment citing ubuntu2404 as the reason for 255 is replaced. The `.rpm` and Arch keep `systemd >= 257`.
- The reference lists in `scripts/package_expected.py` (the `.deb` dlopen list, `SYSTEMD`, the comments citing 255) follow the new values.
- Dependency gate (`scripts/check-tss-deps.sh` / `check_tss_deps.py`, run by `just package`): requires `libtss2-rc0t64` in the `.deb`'s Depends; a `.deb`
  without it, or with it only in Recommends (or only in Pre-Depends), fails with a message naming `libtss2-rc0t64`. The gate may take it from the same table as the
  `dlopen` TCTI, since the binary does not link `libtss2-rc` (no NEEDED soname).
- Package gate (`scripts/check-packages.sh` / `check_packages.py`, run by `just package`): for each of the three formats it requires systemd 257 or later and fails
  with a message naming the format and `systemd` when there is no systemd requirement or the bound is below 257 (or unversioned). The gate's exact-string table
  already meets "257 or later, fails on less"; it is not turned into a version comparison and no 258 case is added.
- Self-tests: all new systemd negative controls go in `scripts/test-check-packages-deps.sh`, beside the existing cases (not in `test-check-packages.sh`, which keeps
  only what it has; the `verify` runs both). The existing cases that write `systemd (>= 255)` as the good value are updated to 257.
- `scripts/test-deb-lifecycle-real.sh` gets a case where real dpkg refuses the `.deb` on a root whose installed systemd is 255. Like every lifecycle test it runs at the
  checkpoint, not in this `verify`; the builder only runs it if it fits in a command (see Cost) and otherwise states that in PROGRESS.md.
- Left for other features: the e2e targets and VM harness (ubuntu2404 no longer being installable is theirs), and any other doc that says 255 outside the files above
  (a step greps for leftovers and fixes the ones in packaging/scripts comments; anything in SPEC.md is not edited).

Environment: all tests use nfpm fixtures and `dpkg-deb`/`rpm`/`bsdtar` already used by the current suites; no new tool. The lifecycle case uses the real
`dpkg` in a user namespace like the existing cases (`bf_in_root`).

Cost (estimates from the existing suites; neither script is separately listed as new in `budgets.tsv`, the loop measures them):
- Systemd cases already existing and only edited: `rpm-`/`arch-systemd-too-old`, `rpm-`/`arch-systemd-unversioned`, `rpm-`/`arch-no-systemd`, `deb-no-systemd`
  (255→257 strings). New fixture cases (each builds three packages with nfpm, ~1–2 s, own output dir, parallel-safe): `deb-systemd-too-old` at 255 (replaces the 254 one)
  and `deb-systemd-unversioned`, so +1 case net, about +2 s.
- The three `check_tss_deps.py` cases run `$TSS` directly on edited copies of `nfpm.yaml`: no nfpm build, milliseconds each. They need one new test-helper op in
  `scripts/lib/nfpm_edit.py` to put a dependency under `deb.recommends`.
- Lifecycle case: one dpkg run (~2 s) added to `test-deb-lifecycle-real.sh`. That suite has no measured time in `budgets.tsv` or PROGRESS.md that I could find; the
  73 s / 100 s figures belong to `test-deb-lifecycle.sh`. Step 5 runs the real suite once and records its measured time in PROGRESS.md; if it exceeds a command, the builder says so.
No e2e case.
