# F164 — CI runs the VM target for the release only

## Scope
Built:
- A new workflow file `.github/workflows/e2e-vm.yml` (its own file, so `e2e.yml` and its test stay as they are). Trigger: `pull_request`
  only, with no `push`, `schedule`, `workflow_dispatch`, `pull_request_target` or `merge_group`. The VM jobs carry a job-level condition
  that holds only when the head branch starts with `milestone/` **and** the head repository is this repository (a fork cannot name a branch
  `milestone/x` and get a KVM runner). The head ref reaches the condition only through the expression, never through a `run` script
  (zizmor would flag it).
- Two VM jobs, one per mode, running at once (a matrix or two jobs, the builder's choice): `just e2e-vm full` and `just e2e-vm lacking`.
  Each job: checks out with `persist-credentials: false`; enables KVM for user `runner` by the udev step of `docs/findings/F150.md`; first
  runs `ls -l /dev/kvm` and `just vm-host-check`, which fail the job naming what is missing (no software-emulation fallback anywhere);
  installs what the VM and the package build need (qemu, ovmf, cloud-image-utils, ubuntu-keyring, gpgv, swtpm, nfpm, just, Rust cache as
  `e2e.yml` does). The `lacking` mode needs swtpm 0.10 or newer (`vm-host-check` prints `swtpm-profile`); if `ubuntu-26.04` ships an older
  one, the job installs the pinned 0.10.2 `.deb`s by checksum as `harness/Containerfile` does. A step looks this up (package version on
  26.04, from packages.ubuntu.com or the runner image notes) and records it in `docs/findings/F164.md` as **inferred**: this session
  cannot run a GitHub runner. Every action is pinned by commit SHA with a version comment; every download by SHA-256. The run steps have
  no `continue-on-error`, no `|| true`, no `exit 0`, no echo-only step. `timeout-minutes` is set from the measured VM run times in
  `.harness/logs/` and PROGRESS.md (F160, F163 runs) with room for a slower runner; the number and its source go in the finding.
- One closing job, the status check a person makes required. It runs on every pull request (a required check that is never reported
  would block ordinary pull requests), `if: always()`, `needs` both VM jobs: on a release head it fails unless both VM jobs are `success`
  (skipped or cancelled is a failure); on any other head it passes without a VM having run. Its `name:` is a fixed string distinct from the
  `e2e` check (for example `e2e-vm`); PROGRESS.md names it for the person who approves it. Making it required is a person's step and
  stays outside the repository.
- `scripts/test-ci-e2e-vm.sh`, added to `test-scripts` in the justfile. It parses the workflow with the same Python/yaml approach as
  `scripts/test-ci-e2e.sh` and reports each problem; controls are generated copies of the workflow.
- `docs/findings/F164.md` (heading `## F164`, rules of `docs/findings.md`) with the runner facts above and the timeout source.
Left to other features: the VM cases themselves (F160–F163), KVM in the dev container (F150), the required-check setting and the
observation on the real release (acceptance 15 says "observed on the milestone's release": a person's check at the release, not
provable here), the release recipe, and any change to `e2e.yml` (unchanged; this feature only asserts it still triggers on every
pull request and on push to main and mentions no VM).
Costs: `scripts/test-ci-e2e-vm.sh` is one script test, about 2 s (YAML parse plus about 12 generated copies, like `test-ci-e2e.sh`, which
takes a few seconds); it runs in parallel with the other script tests under the default `*` budget (120 s), no new `budgets.tsv` line.
No e2e case, no VM run, no container in any step: `just e2e-vm` is not run by this feature, and the workflow itself runs only on the
release. Each step below is a single short command; the longest is `just quick` (about 3 min in the recent attempts).

## Evidence
- Trigger is `pull_request` only; never a push, schedule, dispatch, `pull_request_target` or merge queue → `scripts/test-ci-e2e-vm.sh`
  → passes on the workflow; control copies with a `push` trigger, and with `pull_request_target`, are refused.
- The VM jobs run only when the head branch starts with `milestone/` in this repository → `scripts/test-ci-e2e-vm.sh` evaluates the
  condition text (a small expression check on `startsWith(github.head_ref, 'milestone/')` and the same-repository test) → passes; control
  copies with no condition, with a condition on another prefix, on the base branch, or without the same-repository test are refused.
- Both modes run, as `just e2e-vm full` and `just e2e-vm lacking`, each in its own job → `scripts/test-ci-e2e-vm.sh` → passes; a
  control copy with one mode, one without a mode (`just e2e-vm`), and one with an unknown mode are refused.
- KVM for the runner user as F150 says, `/dev/kvm` and `just vm-host-check` before the run, no software emulation → `scripts/test-ci-e2e-vm.sh`
  checks the udev rule and the two reloads in order before the run step, the host check, and that no step mentions `-accel tcg`/`TCG`
  or a variable that turns KVM off → passes; a control copy without the udev step, and one with `tcg`, are refused.
- Installs what the VM needs → `scripts/test-ci-e2e-vm.sh` checks that each package `vm-host-check` names is installed by an apt step
  before the run → passes; a copy without one of them is refused. That the packages work on the runner is proven only by the release run
  (a person's observation, acceptance 15).
- Actions pinned by commit, tools by checksum → `zizmor --offline .github/workflows` (unpinned-uses) and `scripts/test-ci-e2e-vm.sh`
  (every `uses:` is a 40-hex SHA, every `curl` download is followed by `sha256sum -c`) → pass; a copy with a tag-pinned action and one
  with an unchecked download are refused.
- Cannot pass without the run → `scripts/test-ci-e2e-vm.sh`: no `continue-on-error` on a job or step, no `|| true`/`|| :`/`exit 0`/echo-only
  run step, and the run step is `just e2e-vm <mode>` → passes; control copies with `continue-on-error`, with `|| true` and with an
  echo-only fallback are refused.
- The closing job is the single named status check, needs both VM jobs, runs always, and fails on a release head when a VM job is
  skipped, cancelled or failed → `scripts/test-ci-e2e-vm.sh` (name, `needs`, `if: always()`, and the shell condition run against
  `success/success`, `failure`, `skipped`, `cancelled` on a release head and `skipped` on another head) → expected outcomes: pass
  only for `success/success` on a release head, and for skipped on another head; controls: a copy that does not need one mode, and one
  that passes on `skipped` for a release head, are refused.
- The container E2E workflow is unchanged for ordinary pull requests and pushes → `scripts/test-ci-e2e-vm.sh` asserts `e2e.yml` still
  triggers on `pull_request` (no branch filter) and `push` to `main`, has no VM step, and the VM workflow has no job named like its
  `result`/`e2e` check; `scripts/test-ci-e2e.sh` (verify) → both pass; `git diff` of `e2e.yml` in the commit range is empty.
- `actionlint` and `zizmor` pass → `actionlint && zizmor --offline .github/workflows` → exit 0.
- Whole verify → `just quick && actionlint && zizmor --offline .github/workflows && scripts/test-ci-e2e-vm.sh && scripts/test-ci-e2e.sh`
  → exit 0.
