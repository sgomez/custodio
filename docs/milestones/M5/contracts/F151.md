# F151 — Research: booting the Ubuntu 26.04 minimal cloud image with swtpm, tpm-crb and OVMF

## Scope
Built: `docs/findings/F151.md` (headed `## F151`) and its index line `(findings/F151.md)` in `docs/findings.md`.
It records a boot done by hand in this dev container with KVM, with every command that was run. No product code,
no test, no recipe and no harness script: the VM harness is built by later features, which read this finding.
The finding gives what the description lists, each fact marked **verified** (a command run here, with the
lines that show it) or **inferred** (a source named): the image and signed checksum locations, the serial and
how it is read, how long old serials stay on the mirror; the QEMU command line; the guest kernel's
`CONFIG_TCG_CRB` and `/dev/tpmrm0`; `systemd-analyze has-tpm2` before and after `libtss2-rc0t64`; guest systemd and kernel
versions; the channel and its setup; apt reaching the archive; the TPM persistent state across a guest power cycle;
and a last line `Decision: ` naming the channel and the seed tool.

Not built (other features): the harness download and verification code, the seed generator, the VM case list,
the credential reader, the mode that makes the TPM lack RSA, and the CI job. The finding only informs them.
The KVM question is F150's; this feature cites it and does not redo it.

Environment, measured in this session (`ls -l /dev/kvm; command -v qemu-system-x86_64 swtpm cloud-localds genisoimage ssh ssh-keygen; curl -sI https://cloud-images.ubuntu.com/minimal/releases/`):
`/dev/kvm` exists, `qemu-system-x86_64`, `swtpm`, `cloud-localds` and `genisoimage` are installed, and the cloud-images
mirror answers `HTTP/1.1 200`. `ssh` and `ssh-keygen` are **not** on the PATH of this container. So the SSH channel
is possible only if the finding shows a way that needs no change to the dev container; otherwise the finding
chooses the serial (or virtio) console, whose setup it records, and says so in `Decision: `. It must not
install a package on the container by hand and call that a setup. If it concludes SSH is the better channel, it
states that `openssh-client` would have to be added to `harness/Containerfile` (a person's rebuild, via `BLOCKED.md`
by the builder of the feature that needs it), and still names a channel that works today. Seed tool: `cloud-localds`
is installed; `genisoimage` is the fallback; the finding names the one the harness will use and shows it produces a seed the guest read.
Working files (image, seed, vars copy, swtpm state, keys, logs) live in a new empty directory under `/tmp`, are
untrusted data, are not committed, and are removed at the end. The image is verified (GPG with
`/usr/share/keyrings/ubuntu-cloudimage-keyring.gpg`, then `sha256sum -c`) before it is booted; the finding shows both outputs.
No VM is left running at the end. Nothing is pushed to any service.

Test cost: no new test or suite. The `verify` is a few `grep`s, under 1 s. The hand work is a one-off: image download
(a few hundred MB; time recorded), and each boot with KVM is expected in 30–120 s; each boot or wait is bounded by `timeout` and
waits on a condition (a marker line on the serial console or the SSH/console prompt), never a fixed `sleep`. Each
command stays well under 30 minutes; the whole research fits in one session; installing a package in the guest and the
power cycle are separate commands.

## Steps
- [x] Find and download (outside-material research by subagent where it is only reading): where the minimal image
      (`ubuntu-26.04-minimal-cloudimg-amd64.img` or the name actually published) and `SHA256SUMS`/`SHA256SUMS.gpg` are, how
      the serial is read (the `release-<serial>` directory and/or the manifest or `.json`/`current` links; the command that
      prints it), and how long old serials stay (the directory listing of the mirror now; the Ubuntu documentation or a
      statement by the publisher if one exists, else **inferred** and called a guess about retention). Verify signature and
      checksum here with the dev container's tools and record both results. Write the finding's first sections (conclusion first).
- [x] Prepare the boot: the seed (NoCloud `user-data` with a key or console login, `meta-data`) built with the chosen tool, a
      writable copy of the OVMF vars, a `swtpm` socket with its state directory, and the channel's setup. Write the exact
      QEMU command line (KVM, OVMF code and vars from the files F150 names, `-chardev socket`, `-tpmdev emulator`, `-device tpm-crb`,
      the user-networking and channel options) into the finding.
- [x] Boot with KVM and read the guest: kernel and systemd versions; `CONFIG_TCG_CRB=y` (from `/boot/config-*` or
      `/proc/config.gz`; say which and the line); `ls -l /dev/tpmrm0`; `systemd-analyze has-tpm2` output **before**;
      `apt-get update` reaching the archive (the image's lists are empty: show the count of lists before and the success
      after); then `apt-get install --no-install-recommends libtss2-rc0t64` and `systemd-analyze has-tpm2` **after**
      (record the exact outputs, whatever they are, even if full support does not appear: the finding reports it and
      what else is needed, found by reading the output, not guessed).
- [x] Power cycle: shut the guest down, keep the `swtpm` state directory, restart `swtpm` and the guest, and show the
      TPM's persistent state survived (for example a persistent handle or NV index created before, read after, with the tool
      the guest has; the finding names it and its output). Include a negative control: the same read with a fresh, empty
      state directory finds nothing. Clean up the working directory and any process left running.
- [x] Finish `docs/findings/F151.md` (conclusion first, marks, commands and key lines only, under 5000 tokens, headed `## F151`,
      ending with `Decision: <channel>, <seed tool>`), add its line to `docs/findings.md`, run the `verify` and `just quick`.
