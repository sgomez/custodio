# F153 — Research: systemd 259 credential header and key identifiers

## Scope
Built: `docs/findings/F153.md` (headed `## F153`) and its index line `(findings/F153.md)` in `docs/findings.md`. It settles SPEC's
open question "The credential identifiers for systemd 259". No product code, no test, no recipe, no harness script. The later
feature that writes `e2e/vm/credread.py` reads this finding and builds from it, not from `crates/`; nothing is copied from the
service's code (the finding does not read `crates/` for the layout or the ids).

Source: the exact systemd the Ubuntu 26.04 guest installs, `259.9-0ubuntu0.1` (F151). The step fetches that source package
(Ubuntu's `.orig` tarball and `.debian.tar` or the Launchpad tag, found by the builder) into a new empty `/tmp` directory
(untrusted data; `-I` for any Python reading it). It says whether Ubuntu's patches touch `creds-util.c`, `creds.c`,
`tpm2-util.c` or `credential` files; if the source of exactly that version cannot be fetched, the finding says which upstream tag it
read instead and marks every line number **inferred**. Line numbers are file:line of that tree, as F110 cites them.

Environment, checked in this session: the dev container has `systemd-creds` **257.13** (not 259), `swtpm` 0.7.1, `tpm2_startup` and
the other `tpm2-tools`; network to `raw.githubusercontent.com` and `git.launchpad.net` answers (HTTP 200). So credentials made in
the dev container are 257 only. 259 credentials are made in the **F151 guest** (Ubuntu 26.04, systemd 259.9, `libtss2-rc0t64`,
`-esys`, `-mu` installed, `swtpm` from the dev container as the guest TPM, serial-console channel, `cloud-localds` seed, QEMU
line from `docs/findings/F151.md`), and carried out as base64 text over the console. Each credential row states the version that made it
(259.9 from the guest, 257.13 from the dev container with `swtpm` as in F110). If the guest cannot be booted, the finding says so with the
error, makes only the 257 ones, marks every 259 value **inferred** from source, and the contract's 259 evidence rows are then
met by that statement; no `BLOCKED.md` for that alone.

Credentials to make (each read back for identifier and PCR mask; the reader used for read-back is a few shell/`od`/Python `-I`
lines in the finding, not a harness file): TPM-bound (`host+tpm2`, user-scoped as the Varlink `Encrypt` of the daemon yields, and
`--user` CLI where it works), host-only and its user-scoped form, TPM-only (`tpm2`), bound to PCR 7, null key. Forms that need a
TPM public key (`tpm2_pubkey`/signed-PCR forms) are given by source with **inferred** unless cheap to make with `systemd-creds
--tpm2-public-key`; the finding says which.

Not built (other features): `credread.py`, any fixture generator, the VM harness, any end-to-end case.

Test cost: no new test or suite. `verify` is a few `grep`s, under 1 s, in the script group (`script *` budget 120 s) unchanged.
Hand work is one-off: one guest boot 30–120 s with KVM, waiting on the login prompt/sentinel never a fixed `sleep`, each command under
`timeout`; the source download is a few MB. Working files are in new empty `/tmp` directories, never committed, removed at the end
with no process left from this session (the two idle `swtpm` pids of F150–F152 are known leftovers).

## Steps
- [x] Fetch the source of systemd `259.9-0ubuntu0.1` into a new `/tmp` directory; note Ubuntu patches on the credential, TPM and
      Varlink files. Read (subagent for the broad reading, then check the lines yourself): the header struct of an encrypted credential
      (every field, size, byte offset: magic/key id, the TPM fields, PCR mask, bank, blob sizes, IV/seal, signature fields in the
      TPM-with-public-key form), and where the id of each key is defined and chosen: user-scoped host+TPM, host, user-scoped host,
      TPM-only, the forms with a TPM public key, null. Record each as file:line, **inferred** until step 3.
- [x] Source for the daemon path: which identifier the Varlink `Encrypt` with `scope=user` and no `withKey` picks when a usable TPM is found
      (and when not), and the default PCR mask in 259 (empty or 7). Compare with the 257 and 262 values of `docs/findings/F110.md`
      (also its byte-48 mask claim) from the same files at those versions where F110 does not already give lines.
- [x] Boot the F151 guest with a fresh `swtpm` state; make there, with `systemd-creds`, the credentials listed in Scope (Varlink `Encrypt`
      with `scope=user` too if `varlinkctl` is in the guest, else the `--user` CLI, which is the same call per F110); extract each as base64
      to a new `/tmp` directory; read back the identifier and PCR mask at the offsets from step 1 for each; also decrypt each to show
      it is the real thing (exit 0, plaintext equal), and one negative control: the mask or the id read at a wrong offset or from a
      credential of another kind does not match. Make the 257 set in the dev container the way F110 did (`just with-swtpm`, or
      `scripts/with-swtpm.sh`) for the comparison.
- [x] Write `docs/findings/F153.md`: conclusion first (header layout table with offsets; identifier table with kind, id, scoped or not,
      source file:line, made by version, **verified** or **inferred**), then evidence (commands and key lines only), a list of
      differences from the 257 and 262 values of F110, the leftovers (processes, `/tmp` removal). Under 5000 tokens. Ends with a line
      `Decision: ` naming how the harness reader makes its fixtures (for example: live `systemd-creds` in the guest, or committed
      byte strings, or generated from the layout with a stated tool) and what it must reject. Add its line to `docs/findings.md`.
- [x] Run the `verify` and `just quick`; fix; remove `/tmp` working directories; append to `PROGRESS.md` and commit.

## Evidence
- Header layout with file and line, at 259.9 → the finding's table: every field with size and offset, key id, PCR mask, TPM fields, each cited `file:line` of the fetched tree → **verified** by the read-back below (offsets recovered from real credentials); a wrong offset in the table makes the read-back row disagree. `verify` greps `header`, `PCR`, `259`.
- Identifier of each key a credential can carry (user-scoped host+TPM, host, user-scoped host, TPM-only, forms with a TPM public key, null) → one table row each with id, source `file:line` and **verified**/**inferred** mark → each row is checked against a made credential (rows with a TPM public key may stay **inferred** with the stated reason). `verify` greps `scoped`, `host`, `tpm2`, `null`.
- Real credentials in 259.9 (TPM-bound, host-only, PCR 7, null) → in the guest: `systemd-creds --version` line, the `systemd-creds encrypt` command, the base64 read back, the id (16 bytes) and PCR mask (`le64`) per credential, decrypt exit 0 with plaintext equal → ids equal the table; PCR-7 credential has mask `0x80` and the others mask 0 (or whatever 259.9 gives, stated); the null one carries the null id. `verify` greps `swtpm`, `systemd-creds`, `PCR`.
- The id the daemon's Varlink `Encrypt` gets with a usable TPM → source lines plus the user-scoped host+TPM credential made with `--user`/`varlinkctl` in the guest → its id equals the table's user-scoped host+TPM row; the case with no TPM yields the host-user id (as F110 saw in a container).
- States which systemd version made each credential → a column in the evidence table → every row names 259.9 (guest) or 257.13 (dev container).
- Differences from F110's 257 and 262 values → a list in the finding, from the dev container 257.13 credentials made here, F110's table, and source at 262 where F110 gives none → each difference named, or "none" with the comparison shown.
- Negative control → the read-back at a wrong offset, or the reader applied to a credential of another kind, does not give the expected id/mask → the finding quotes it.
- The `Decision: ` line, the index line, and the `verify` → `f=docs/findings/F153.md`; the `verify` command of features.json → exit 0; `just quick` → green.
