# F152 — Research: making the virtual TPM lack a capability RSA 2048 needs

## Scope
Built: `docs/findings/F152.md` (headed `## F152`) and its index line `(findings/F152.md)` in `docs/findings.md`. It settles
SPEC's open question "How to make the virtual TPM lack an RSA capability". No product code, no test, no recipe, no harness
script: the VM harness and the `lacking` mode are built by later features, which read this finding. Hand work in the VM of F151
(`docs/findings/F151.md`: serial-console channel, `cloud-localds` seed, the recorded QEMU command line, `libtss2-rc0t64`,
`libtss2-esys-3.0.2-0t64` and `libtss2-mu-4.0.1-0t64` needed for `has-tpm2` = `yes`), with every command recorded.
The product is **not** installed in these boots; "the service's capability query" and "the service's ECC P-256 parent" are
shown by the same TPM commands the service sends (see Evidence), taken from `docs/api.md` (F107/F111, "TPM capabilities") and `docs/decisions.md`
(parent), and by building and running `custodio-it`'s own capability code natively on the host against the same
filtered TPM only if that is cheaper than a guest binary; the finding says which. The end-to-end run with the real `.deb` is a later feature's.
Routes tried (each works, fails, or is ruled out by a named source, **verified** or **inferred**):
1. `tpm-filter` (`crates/custodio-it/examples/tpm-filter.rs`) between QEMU's emulator backend and `swtpm`. QEMU's backend uses the
   control channel (and passes the data channel as a file descriptor/another way) where the filter was built for the data socket
   (TCTI); the route shows what QEMU actually sends on each channel and whether the filter can proxy both (control and data).
2. An `swtpm`/`libtpms` profile that disables an algorithm: the `swtpm` and `libtpms` versions that support it (source or
   `swtpm_setup --help`/man page of a version, named), whether the dev container's 0.7.1 does (it is expected not to), and how the
   dev container (`harness/Containerfile`) and CI would get a newer one (package, backport or build; the cheapest that is pinned).
   The finding does not install anything on the container by hand and call it a setup: a newer `swtpm` is tried in a new empty
   `/tmp` directory (a build or an unpacked package, untrusted data), and what the container or CI must add is stated, not done.
3. Any other route found (for example filtering at the CRB/data level in a QEMU-side proxy, or `libtpms` build options); ruled out or shown.
Whether P-256 can also be made to lack a capability without breaking the kernel's TPM, `systemd-creds` or the ECC parent is
tried for each route that works for RSA.
If no route gives RSA `encrypted-tpm` without breaking the TPM for the kernel or systemd, the builder follows CLAUDE.md and the feature
description: `BLOCKED.md` with the question and the options, work committed, stop.
Not built (other features): the VM harness, the lacking mode, the CI change, the container change (a person's rebuild, via
`BLOCKED.md` of the feature that needs it), the credential reader, any end-to-end case.
Environment known from F150/F151: `/dev/kvm`, `qemu-system-x86_64` 10.0.13, `swtpm` 0.7.1, `cloud-localds`, `tpm2-tools`
(host) are present; `ssh` is not. The smallest check that the guest can run the tools is the F151 boot; step 1 repeats it.
Test cost: no new test or suite. The `verify` is a few `grep`s, under 1 s. Hand work is one-off: each boot with KVM
30–120 s (F151: login prompt under 30 s), each bounded by `timeout` and waiting on a condition (the login prompt, the
sentinel line), never a fixed `sleep`; independent routes use separate working directories and may boot at once. A `swtpm` build
(route 2) is the only long command; it is bounded by `timeout` well under 30 minutes, or replaced by reading the source if it cannot fit. Working
files live in new empty directories under `/tmp`, are untrusted, never committed, and are removed at the end with no process left.

## Steps
- [x] Read-only research (subagent for outside material): the `swtpm` and `libtpms` versions with profile support and the profile syntax that
      removes an algorithm or curve (source or release notes, with versions); what the Ubuntu 26.04 guest does with the TPM at boot (the kernel
      creating a primary for bus encryption, `systemd-creds`'s SRK choice) from the tools' source or from commands in the guest. Record
      what is read as **inferred** until a command proves it.
- [x] Boot the F151 VM (full TPM, tools installed) and record the baseline: the capability answers
      (`tpm2_getcap algorithms`, `ecc-curves`, `commands`), `systemd-analyze has-tpm2`, `systemd-creds --with-key=host+tpm2 encrypt` then `decrypt`
      round-trip, `tpm2_createprimary` with ECC P-256 and with RSA 2048, and the kernel's own primary. This is the control every route is compared with.
- [x] Route 1: run `tpm-filter` (built on the host) between `swtpm` and QEMU for the capability RSA lacks; boot and repeat the baseline
      commands; record what QEMU sends on the control and data channels and what the filter does to each, or why it cannot be placed.
- [x] Route 2 and route 3: try the profile route with a `swtpm` that supports it (named, how obtained) and any other route found; boot and repeat the baseline commands for each that starts.
      Then, for each route that works for RSA, try also removing P-256 (curve or algorithm) and record what breaks.
- [x] Finish `docs/findings/F152.md` (conclusion first, **verified**/**inferred** marks, commands and key lines only, under 5000 tokens, headed `## F152`,
      ending with `Decision: <route>; <what the dev container or CI must add>; P-256 <gets|does not get> encrypted-tpm`), add its line to
      `docs/findings.md`, run the `verify` and `just quick`. If RSA cannot get `encrypted-tpm` without breaking the kernel's TPM or systemd, write `BLOCKED.md` and commit.

## Evidence
- Route 1 (`tpm-filter`, control and data channel) → the QEMU command line, the filter's command line and what each channel carried, as run → either the guest boots with the filtered TPM and the checks below pass, or the finding quotes the failure (QEMU's or the filter's message) that rules it out; `verify` greps `tpm-filter`.
- Route 2 (profile), the `swtpm` version that supports it, and how the dev container and CI get it → version output of the `swtpm` tried and the profile used, or the source/man page naming the first supporting version; the Containerfile line or CI step needed, stated → `verify` greps `profile`; marked **verified** if run, else **inferred** with the source.
- Any other route → each one tried or ruled out with the reason → quoted.
- The capability is missing as every guest process sees it → in the guest, one block per working route: `tpm2_getcap algorithms` (RSA absent), `systemd-analyze has-tpm2` output, `systemd-creds has-tpm2`, kernel view (`dmesg | grep -i tpm`, `/sys/class/tpm/tpm0`), and the exact capability queries of `docs/api.md` (`GetCapability(ALGS)` for RSA, `TestParms`) issued with `tpm2-tools` → RSA reported absent by all, versus present in the baseline control; `verify` greps `RSA`, `tpm2-tools`, `systemd-creds`. A negative control: the same commands on the unfiltered TPM show RSA present.
- RSA creation is refused or reported absent, not only hidden from one query → `tpm2_createprimary -C o -G rsa2048` (or `TestParms`) result under the route → recorded as is, so the finding says whether "lacking" is real or only the capability list.
- The kernel's TPM and `systemd-creds` sealing with "host plus TPM" still work → `ls -l /dev/tpmrm0` (character device), `dmesg` without a TPM error, `systemd-creds encrypt --with-key=host+tpm2` and `decrypt` round trip back to the plaintext, each with exit code, under the route → `verify` greps `/dev/tpmrm0`, `systemd-creds`.
- The service's ECC P-256 parent can still be created → the parent's template from `docs/decisions.md` (named; ECC P-256 primary) created with `tpm2_createprimary` and used (create/load a child under it) under the route → exit 0 with the handle; `verify` greps `parent`.
- Whether P-256 can also lack a capability → for each working route, the same removal for P-256 and the outcome of the kernel, `systemd-creds` and parent checks → the finding says which of them break (quoted), or that none does; `verify` greps `P-256`.
- Finding shape → `docs/findings/F152.md` headed `## F152`, with `**verified**`/`**inferred**` marks, a line `Decision: ` that names the route, what the dev container or CI must add (or "nothing") and whether P-256 gets `encrypted-tpm`, indexed as `(findings/F152.md)` in `docs/findings.md`, `just quick` green (5000-token limit) → the `verify` exits 0.
- RSA that cannot get `encrypted-tpm` without breaking the TPM → `BLOCKED.md` exists with the options, only in that outcome; otherwise absent → checked by the builder.
- No leftovers → `pgrep -a 'qemu|swtpm|tpm-filter'` prints nothing and the `/tmp` working directories are gone, stated in the finding's last lines.
