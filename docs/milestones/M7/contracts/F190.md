# F190 — Research: reading journald's effective storage without root

## Scope
Research only. Output: `docs/findings/F190.md` (headed `## F190`, within the 5000-token limit, rules at
the top of `docs/findings.md`: conclusion first, **verified**/**inferred**, evidence as commands and the
lines that prove them) and one index line in `docs/findings.md`
(`- [F190](findings/F190.md) — topic: the conclusion`). No product code, no test, nothing in `e2e/`, no
change to other contracts. F203 implements the `Decision: ` line (check 5 of `custodio doctor`, its
parser and fuzz target); this feature does not. Acceptance of check 5 is proven by F203's tests.

What the finding must settle (SPEC Design 2 check 5, open question 3):
- Which files journald reads and in what precedence: `journald.conf`, and `journald.conf.d` in `/etc`,
  `/run`, `/usr/lib` (and `/usr/local/lib` if systemd reads it), the override rule (same file name masks
  the lower directory; lexical order; last value wins), the `[Journal]` section, a repeated key, an
  empty value, case and whitespace, invalid values. Read from systemd source and `man journald.conf`,
  cross-checked with `systemd-analyze cat-config systemd/journald.conf` (runs as an ordinary user here)
  and by a fixture-tree run of the real tool where it can take a root directory.
- `Storage=` for each value (`auto`, `persistent`, `volatile`, `none`): what ends up on disk across a
  reboot, including `auto` with and without `/var/log/journal` (and whether journald creates it, and
  when), `persistent` creating it, and a volatile state kept under `/run/log/journal` (and what its
  presence says by itself). Whether the persistent directory alone, or a drop-in alone, is enough to
  decide, and which combinations contradict each other.
- What an ordinary user can read: file modes of the configuration, `/var/log/journal` (its existence,
  the `stat` of the directory, whether `read_dir` is needed and allowed) and `/run/log/journal`; which
  of these fail with permission denied and so are "could not check".
- systemd 257 and later: what changed or may change (Debian 13 ships 257; for each later release the
  finding checks the NEWS between 257 and the newest release it can read, for `Storage=`, the
  config-file search path, `/var/log/journal` creation, and tmpfiles `var.conf`/`journal-nocow.conf`).
- The default install of each supported target: `debian13`, `ubuntu2604`, `fedora44`, `alma10`,
  `arch`: systemd version, the packaged `journald.conf` value of `Storage=`, whether `/var/log/journal`
  exists after install (package ships it, tmpfiles, or `systemd-journald` creating it), and any
  distribution drop-in. The first step finds the smallest command that shows whether the dev container
  can pull and run the target images (`podman` exists, no image is present); if it can, each target's
  default is **verified** by running it. If it cannot, the finding reads package file lists and
  sources (distribution package pages or archives) and marks the default **inferred**, with the
  source named. A container is not a booted system, so what `auto` makes of `/var/log/journal` on a
  real boot is taken from the source and marked accordingly.
- The documented fix for each non-persistent case (a drop-in `Storage=persistent` under
  `/etc/systemd/journald.conf.d/`, `mkdir /var/log/journal` plus `systemd-tmpfiles --create --prefix
  /var/log/journal` and a restart or flush, `journalctl --flush`; and for `none` and a volatile
  override the file to change). Each fix is quoted from `man journald.conf`/`man systemd-journald` or
  the systemd docs, and says whether it needs root (`doctor` only prints it).
- The table of states: for each state (config value × directory present/absent × volatile directory ×
  readable/unreadable) the answer `persistent`, `not persistent` (with its fix) or `could not check`
  (with the reason), and why a state is "could not check" rather than guessed. The conservative
  choice applies when the source leaves a case open (SPEC: choose the conservative option).
- The finding ends with one line `Decision: ` that F203 can implement without further research: the
  exact files and order read, the rule for each state, and the states reported as could not check.
  Choices a later session could undo without knowing why also go in `docs/decisions.md`, by its rules.

Outside material is read by subagents that return conclusions, not dumps (systemd source and NEWS,
`man journald.conf`, distribution packages).

Cost: no test or suite is added; `just quick` (runs `scripts/check-files.sh`) is the only run, at its
usual cost, and the feature's `verify` (a grep script, under a second). If the container runs are
possible, each is one short command per target, run at once and not in a loop one after another, each
with `timeout`.
