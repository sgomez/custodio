# F213 — Checkpoint and last automated feature: the whole milestone after `custodio setup`

## Scope
Almost nothing is built. This feature runs every suite of its `verify` on the finished milestone (F189–F209, F212's rename and F214's swap and core-dump settings) and fixes
whatever fails, at its cause, under the earlier checkpoints' rules: no `#[ignore]`, no lowered threshold, no `#[allow]` without a
justification, no recipe turned into a no-op, no guard loosened, no case changed except where the case is wrong, no skip added without a
stated and evidenced reason, no edit of `budgets.tsv`. The `verify` is
`just check && just api-contract && just fuzz-smoke && just memory-safety && just e2e && just package-gates && just coverage-gate && just e2e-vm full && just e2e-vm lacking`;
the loop runs it whole, a builder session never does. No new test, script, case or e2e target is added (no new cost). A fix may add a
regression test at the cheapest level that catches its cause and `PROGRESS.md` says what it costs.

**What this checkpoint adds over F209:** F209's runs proved the tree before F212 renamed `register` and `fingerprint` to `setup browsers`
and `setup fingerprint`. F212 changed the parser, the messages, the man page, the completions, the systemd user unit, the install notices,
the container and VM e2e scripts, the documents and their runners; its own `verify` ran only the fast tests. This feature re-proves the
whole tree with the same suites and evidence as `contracts/F209.md`, on the new argv: every `fingerprint-*`, `doctor-*`, snap and
`vm-fingerprint-*` case drives `custodio setup …`, the real packages' install notice names `sudo custodio setup fingerprint enable`, and
`just check` runs the document runners (the 0.8.0 notes no longer, as F212 decided).

**What F214 adds to the runs (proven here, built there):** the container target `debian13` owes four more cases, `memory-unit-settings`,
`memory-core-limit`, `memory-not-dumpable`, `memory-service-answers` (`e2e/targets/debian13/cases.list`; F214 measured them alone, and they
run inside debian13's record, the slowest of the six at once). The VM mode `full` runs nine `vm-memory-*` cases (`swap-max`, `default-stage`,
`default-crash`, `default-crash-override`, `default-control`, `coredump-stage`, `coredump-crash`, `coredump-crash-override`,
`coredump-control`; SPEC acceptance 24) and `lacking` skips the same nine with the reason in `e2e/vm/skip.list`. They must be `run` in
`full`: `check-cases.sh` refuses `vm-memory-*` reported skipped in a full run. A `*-stage` case that cannot stage the core handler (apport,
`systemd-coredump`) fails and is reported, never skipped. F214's `vm/memory.sh` leaves apport stopped and `systemd-coredump` installed for
the rest of the full run; if a later group (cycle, snap, sign, ...) fails on that, the fix is here, in the order or the cleanup of the
group, not a skip.

**Environment:** as F209 measured (dev container, 2026-11-16): `/dev/kvm`, `qemu-system-x86_64`, `swtpm`, podman; checked again on the
host on 2026-11-21 (`/dev/kvm`, podman, qemu-system-x86_64, swtpm present). Step 1 reruns `bash e2e/vm/run.sh --check full` in the
container. If KVM, QEMU, swtpm, the network or the guest image are gone, that is `BLOCKED.md`, not a reason to skip a group or case. VM
runs use the whole machine's memory budget: they run one after the other and never alongside `just e2e` or the coverage run.

**Time and budgets** (`budgets.tsv`, set by a person; the builder compares and never edits), measured at F209: `just check` ~2 min warm
(`CHECK_FORCE=1`), `just e2e` 172–219 s wall (six records at once, every target under its row; debian13 row 800 s), VM `full` 372 s
at F209 before F214 (row now 700 s, raised by a person on 2026-11-21 for F214's core-dump cases, estimated at 70–100 s), `lacking` 97 s
(row 500 s). The `vm-memory-*` group is the new cost; the VM rows are not read by the loop yet, so an overrun is reported in `PROGRESS.md`
and does not by itself fail the gate. Limits: a command runs at most 30 min, a session 45 min. `just e2e`, `just memory-safety`, `just package-gates`, each
coverage half, and each VM mode get a command of their own with `timeout 1700`. No step runs the whole `verify`. A mode over its row is a
request for a bigger row in `BLOCKED.md` with the measured times, written after every other step is done.

## Steps
- [x] 1. Host side: `CHECK_FORCE=1 timeout 1700 just check` (a red script or test is run alone first), then `just api-contract`, then
      `just fuzz-smoke` (its default list equals the fuzz targets `cargo fuzz list` shows); then `timeout 1700 just memory-safety`. Fix
      each failure at its cause, one commit per fix.
- [x] 2. Container end-to-end: remove old `target/e2e/*` records; `timeout 1700 just e2e` once (six records at once); fix every failing
      case at its cause; note the six wall times against `budgets.tsv` in `PROGRESS.md`.
- [x] 3. `timeout 1700 just package-gates`; then `timeout 1700 just coverage` and `timeout 1700 just crap`, each its own command. Fix
      every finding with a test of the behaviour, never by lowering a threshold.
- [x] 4. VM: remove old `target/e2e/vm.*`; `bash e2e/vm/run.sh --check full`; `timeout 1700 just e2e-vm full`; after it ends,
      `timeout 1700 just e2e-vm lacking`. Fix every failing case at its cause (debug with `just e2e-vm-cases <mode> '<glob>'`). Note
      per-phase times.
- [x] 5. Final: after the last fix, rerun every suite that ran before it, one per command (the VM modes again after any change to the
      package, `e2e/` or guest scripts); recount the Evidence records; `just quick` once. `BLOCKED.md` for a budget row only after every
      other step is ticked, with the measured times.
