# F143 — End-to-end cases: more calls than TPM object slots

## Scope
New cases `tpm-slots-*` for SPEC acceptance 10, against the real packaged service, module, CLI, polkit and journal in the debian13 container. The guest's `swtpm` is reached
through its unix socket (F108), without a kernel resource manager, so an object the service leaves loaded stays loaded: a leak per call is visible, as in F130. Alice imports an
RSA 2048 and a P-256 key (kind `tpm` in `swtpm` and in `lacking`). The number of TPM object slots is **read in the guest from the TPM's own capability** (`tpm2_getcap` on the
service's socket, `$TPM_SOCK`, the filter's in `lacking`; the property for the transient objects the TPM can hold at once; the builder picks the exact property in step 1 and
names it in `docs/findings/F143.md`; F130's `parse_slots`/`slot_count` in `tpm_resources.rs` already read it, so reuse that property and confirm it in the guest and behind the filter). Then, judged from real outputs:
- **more signatures than slots** — for each key, N signatures in a row through the real path (`pkcs11-tool --sign` with the packaged module, polkit approved each time), with
  N = slots + 3 at least (so a service that leaked one object per call would fail at call slots+1 and the run goes past it). Every call succeeds, and every signature verifies
  with `openssl` against the served certificate. Two cases: `tpm-slots-sign-rsa` (RSA-PKCS and one RSA-PSS mechanism in the mix) and `tpm-slots-sign-ec` (ECDSA).
- **more imports than slots** — M = slots + 3 imports in a row as alice (distinct ids, same `.p12`), each succeeds with kind `tpm`, `ListKeys` shows all M (+ the earlier ones),
  and the last one signs and verifies. Case `tpm-slots-import`. The keys are deleted at the end in one polkit session (a polkit-authorised call costs ~5 s; one session for all).
- **nothing is left loaded** — after the signing and import runs, `tpm2_getcap handles-transient` (on the service's socket) lists no handle (and `handles-loaded-session` no session) that was not there before the case
  (the service holds none between calls), and a signature still succeeds after it. Case `tpm-slots-no-leak`. Negative control in the guest: root loads one object with
  `tpm2_createprimary` without flushing, the same judgement reports it as a handle that was not there before, and it is flushed again.
- **Not repeated:** calls that fail midway, the per-call flush at library level, (F130 `tpm_resources`, `tpm_sign`, `tpm_import`); concurrent calls are not claimed; the kinds and
  mechanisms (F133/F134); `encrypted-tpm` keys use no TPM object per call (and cannot be made in the container, `SPEC_DEVIATIONS.md` F134), so no claim is made for them here.
  Package gates and `just e2e` as a whole are proven at the checkpoint.

**Modes.** `swtpm` and `lacking`: all cases run, kind `tpm` judged for every key (a wrong kind fails the case, so the run is not vacuous). `none`: no TPM, so no slots; the keys are
`encrypted-host`, and the cases are reported skipped (`skip.list`, reason). Ids in `e2e/targets/debian13/cases.list` (outcome depends on the TPM, SPEC end-to-end scope), not in
`e2e/cases.list`; `check-cases.sh` refuses a `tpm-slots-*` skip in `swtpm` and `lacking`, like `pcr-*`. Group `tpmslots` in `select.sh` (pattern `tpm-slots-*` captured before
`tpm-*`, which no other group may capture; the host select test checks it), step in `guest.sh` after `tpmclear` and before the upgrade, leaving the service active and the state
and counts as found (all its keys deleted).

**Cases** (each reported exactly once): `tpm-slots-sign-rsa`, `tpm-slots-sign-ec`, `tpm-slots-import`, `tpm-slots-no-leak`.

**Negative controls.** Guest: the leaked-handle control above (the judgement can fail); the slot count is shown to be what the TPM reports (it is printed in the case detail and must
be at least 1, so N is never zero). Host (`scripts/test-e2e-tpmslots.sh`, no container, added to the justfile script-test list): the judgement functions (python3 `-I`, functions of
files, in `e2e/tpmslots.py`) accept a good record and reject: fewer calls than slots+3, a failed call, a signature that does not verify, a wrong kind, a missing key from `ListKeys`
after the imports, a transient handle left after the run, a slot count of zero or unparsable capability output; and `check-cases.sh` accepts the `none` skip and refuses one in
`swtpm` and `lacking`; the ids are in the debian13 list and not in `e2e/cases.list`.

**Cost.** Host test: under 5 s, parallel with the other script tests (budget 60 s). Guest, per mode (`swtpm`, `lacking`; swtpm reports 3 slots, so N = M = 6 or so): two signing
runs of ~6 calls each, run as parallel background jobs joined with `wait` (if a run fails with a TPM out-of-memory error, run them in series; do not loosen the check) (a polkit-approved sign is ~1–5 s, the signs of one key stay in series, since "in a row" is the point),
6 imports (2–4 s each, in series; they are the costly part, ~15–25 s), one delete session (~5–8 s), the capability reads (<1 s). Estimated 30–40 s of the phase, no new container;
`just e2e-cases debian13 'tpm-slots-*'` about 60–80 s per mode (F140: 55–57 s whole run, phase 31 s), ~20 s in `none` (skips only). The full debian13 `swtpm` run grows by ~35 s on top
of F135–F140 and F142's m3 phase, against 430 s in `budgets.tsv` (measured 360 s before those): **this may not fit**. The builder sums it in `PROGRESS.md` and asks for more
in `BLOCKED.md` if a measured run passes the budget (that run is the checkpoint's). M stays slots+3; lowering it needs an amendment the evaluator approves. No `budgets.tsv` change is requested now.

**Environment.** `tpm2_getcap`, `tpm2_createprimary`, `tpm2_flushcontext`, `openssl`, `pkcs11-tool` are in the debian13 guest (F137/F140 used them); `swtpm` does not run in the dev
container (F136), so the probe of step 1 is the guest run itself. If the capability cannot be read through the `lacking` filter, the builder records it in the finding and takes the
count from the unfiltered `swtpm` state (same TPM underneath) before building more.

Size: five steps, one session each at most.

## Evidence
- More signatures than slots all succeed → `tpm-slots-sign-rsa` and `tpm-slots-sign-ec` (`just e2e-cases debian13 'tpm-slots-*'` in `swtpm` and `E2E_TPM=lacking`) → for each key at least
  slots+3 consecutive signatures succeed and verify with `openssl`; the slot count printed is the TPM's reported one (≥ 1); kind `tpm` for the key.
- More imports than slots all succeed → `tpm-slots-import` (same runs) → slots+3 imports in a row, each with kind `tpm`, all listed by `ListKeys`, the last signs and verifies; deleted after.
- No object is left behind → `tpm-slots-no-leak` (same runs) → no new transient handle on the service's TPM after the runs, a signature still works; the control (a handle root
  loads and leaves) is reported by the same judgement as a leak.
- The judgements can fail, accounting is right → `scripts/test-e2e-tpmslots.sh` (in the justfile script-test list, like the sibling `test-e2e-tpmclear.sh`; run by the builder directly, it is not in `just quick`) → good record
  accepted; every bad record listed above rejected; `none` skip accepted, `swtpm`/`lacking` skip refused; ids placed in the debian13 list only.
- Skipped where it does not apply → `E2E_TPM=none just e2e-cases debian13 'tpm-slots-*'` → exit 0, "4 cases accounted for", 4 skipped with the reason from `skip.list`.
