# F106 — Research: which parent key in the owner hierarchy

## Scope
Built:
- A section `## F106` in `docs/findings.md` that settles the SPEC open question "Which parent"
  for the two candidates: (A) a persistent SRK at 0x81000001, (B) a primary recreated on each use
  from a fixed template (the finding chooses RSA 2048 or ECC P-256 and says why). Every claim is
  backed by a command and its output on `swtpm`, or by a source or document read (marked
  verified or inferred, as the rest of the file does). The section covers, for each candidate:
  NV write or secret needed; survival of reboot, `TPM2_Clear` and package upgrade; behaviour with
  a password on the owner hierarchy; behaviour when 0x81000001 holds a key with another template;
  how a stored blob records its parent name and how the service detects a mismatch before use;
  what package removal must clean; and the cost per call of (B).
- The probe `crates/custodio-it/examples/tpm-probe.rs`, subcommand `parent [--tcti <tcti>]`
  (`tss-esapi` is already a dev-dependency of `custodio-it` from F105, so an example can use it).
  Without `--tcti` it uses the environment TCTI that `just with-swtpm` sets. It prints the facts
  the finding relies on, one `key: value` line each, so a person can repeat it on a hardware TPM
  in F111. It is read-only with respect to persistent state: it never calls `EvictControl`, never
  sets an auth value and never clears, so running it on a hardware TPM writes no NV storage. It
  creates only transient objects and flushes them. The parts of the finding that need a write
  (persisting an SRK, changing the owner auth, a foreign key at 0x81000001) are run on `swtpm`
  with `tpm2-tools` through the F105 fixture or `just with-swtpm`, and are shown in the finding
  as commands with output, not in the probe.
- The finding ends with a line `Decision: <parent>`. Per SPEC the default is: no NV write, no
  secret in the service, an unusable owner hierarchy fails the import and never falls back. If
  the finding departs from that default, it says why and flags it for the person in F111.

Left to other features: the import and the TPM module (F108 onward); the hardware-TPM run and
approval (F111); the mechanism questions (F107, which adds `tpm-probe mechanisms`); recording the
approved parent in `docs/decisions.md` (F111). Nothing here changes `SPEC.md`.

Environment (checked this session, dev container): `just with-swtpm bash -c '...'` runs
`tpm2_createprimary -C o -G ecc256` (0.012 s real), `tpm2_evictcontrol -C o -c ... 0x81000001`
(prints `action: persisted`), `tpm2_changeauth -c o secret`, after which `tpm2_createprimary -C o`
without the password fails with `0x9A2 ... authorization failure without DA implications`, and
`tpm2_getcap handles-persistent` lists `0x81000001`. So every scenario in the finding can be run
here. Not yet shown: the same through `tss-esapi` 8.0.0-alpha.4 (primary creation, `ReadPublic`
name, `GetCapability` of persistent handles); step 1 checks it. swtpm serves one client at a time:
the probe must be run alone, not while a `tpm2-tools` command holds the connection.

## Evidence
- Persistent SRK and recreated primary both examined, with cost per call → `## F106` has a
  subsection per candidate; the cost is a measured number from `tpm-probe parent` (mean over
  N calls) pasted with the output → section contains both candidates' `0x81000001` / `template`
  text and a time per creation.
- NV write and secret, per candidate → `tpm2_evictcontrol` output and the NV listing before/after
  on `swtpm` are in the finding → the finding states "NV write: yes" for A (persist) and "no" for
  B, and "secret: none" for both with the reason, matching the commands shown.
- Survival of reboot, upgrade, clear → restart of `swtpm` on the same state and a `tpm2_clear`,
  each followed by `tpm2_getcap handles-persistent` and the probe's primary names → output shows
  A present after restart and gone after clear; B's name is the same after restart and changes
  after clear; text says what a package upgrade does to each (the template is the only thing a
  package carries) and why; upgrade survival is argued, so it is marked inferred.
- Owner hierarchy with a password → `tpm2_changeauth -c o` then create primary and the probe →
  the response code (`0x9A2` authorization failure) is quoted for B, and for A the load of the
  already persistent key (works without the owner auth) versus its first provisioning (fails);
  the finding states the import fails with a named error and never falls back, and the probe
  exits non-zero with that code in its output.
- Persistent handle with another template → persist a key of a different template at
  0x81000001 and run the probe → the probe prints its template attributes and a name different
  from the expected SRK name; the finding states the service must treat it as unusable
  (error, no overwrite, no eviction) and that this negative control differs from the expected
  case in the printed name.
- Parent name recorded in the blob → the experiment child created under A, loaded under a parent
  with another name or after clear, shows the TPM error → the finding names where the parent
  name is stored and why (as the experiment shows it), the comparison done before `Load`, and
  quotes the error that the TPM gives when the check is skipped.
- Package removal → the finding lists exactly what removal must clean for the chosen parent
  (for A: whether the persistent handle may be evicted and why a package must not, since the
  handle is shared with other tools; for B: nothing in the TPM, only the service's state) →
  present as a subsection and consistent with the Decision.
- Default applied → the Decision line is consistent with SPEC "Open questions" default (no NV
  write, no secret, fail never fall back), or the finding states the departure and its reason →
  read by the evaluator; the verify's `Decision: ` regex passes.
- Probe works and is read-only → `just with-swtpm cargo run -q --locked -p custodio-it --example
  tpm-probe -- parent` → exit 0 and the facts above printed; run again with a hardware-free bad
  TCTI (`--tcti swtpm:path=/nonexistent`) → non-zero exit with a message (negative control: the
  probe can fail); `tpm2_getcap handles-persistent` and NV listing taken before and after a probe
  run on a fresh `swtpm` are identical (no persistent or NV change); those listings go into the finding with their output.
  The probe also prints an explicit line `persistent_0x81000001_matches_srk: yes|no|empty`.
- Probe on an owner password and on a foreign key at 0x81000001 → the probe is run on `swtpm`
  prepared both ways and its output is pasted into the finding → owner password: non-zero exit
  naming the response code; foreign key: exit 0 with the occupant's template shown as differing.
- Whole feature → `just quick` and the `verify` command of F106 from features.json → exit 0.
