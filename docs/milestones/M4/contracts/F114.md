# F114 — Sign inside the TPM with every mechanism

## Scope
Built in `custodiod`, in the `tpm` module (small files under `crates/custodiod/src/tpm/`, none over 5000 tokens; every new
non-`tests.rs` file joins the `mutants` recipe's `--file` list). Follows `docs/decisions.md` 2026-11-03 "TPM RSA keys: the
service pads, the TPM does the raw operation" and "TPM parent":
- **Request**: a stored blob (`Blob`/`Imported` of F113), the key type, a `sign::Mechanism` (the existing type) and the caller's
  data. Result: the signature bytes in the same format as `sign::sign` (RSA: 256 bytes; P-256: raw `r || s`, 64 bytes).
- **RSA** (`CKM_RSA_PKCS`, `CKM_RSA_PKCS_PSS` with SHA-256/384/512 and the requested salt length): the service builds the
  PKCS#1 v1.5 type 1 block or the EMSA-PSS block, the TPM does the raw private operation (`TPM2_RSA_Decrypt`, null scheme), and the
  service checks the result with the public key of the blob before returning it. The service does not hash the message and does
  not parse the `DigestInfo`: `CKM_RSA_PKCS` signs any payload up to `k - 11` bytes, as `sign::sign` does. So no new parsing of
  signing input exists; the only inputs are lengths, and they are bounded (below).
- **P-256** (`CKM_ECDSA`): the service truncates the digest to the leftmost 32 bytes as the existing signer does
  (`docs/decisions.md` 2026-10-28) and the TPM runs `TPM2_Sign` (ECDSA, SHA-256 scheme).
- **Bounds and errors**: the same as `sign::sign` for the same inputs (`BadData` for a wrong length, an oversized payload or salt, an
  empty ECDSA digest; `MechanismMismatch` for a mechanism that does not fit the key type). The builder may add TPM-specific
  error variants but must not change what `sign::sign` returns.
- **Missing capability**: if the TPM cannot serve a mechanism (a command refused, an algorithm absent), the result is a typed
  "lacks" error naming the missing item; the call never drops the request, never falls back to another mechanism, hash, salt or
  key kind, and never changes the data. A TPM error that is not a lack stays a TPM error with its response code.
- **Load**: `TPM2_Load` of the blob under the parent (recreated per call, F113's template), after F113's parent-name check. A
  blob recorded for another parent returns `ParentMismatch` (F113) with no `TPM2_Load`; a blob that passes the check but is
  refused by `TPM2_Load` (corrupted or truncated private area) returns a different typed error, distinct from `ParentMismatch`,
  from "lacks" and from other TPM errors. Messages contain no names and no key bytes.
- **No key in service memory**: the private key never exists in the service in this feature; the only secret-bearing data is the
  data to sign, which is not secret. Nothing here parses or holds a sensitive area.
- **Flushes**: the parent, the loaded key and every session are flushed by the end of the call, whatever the outcome.

Left to other features: choosing the storage kind and reading blobs from disk (F117), D-Bus wiring, polkit, journal and error
mapping (F119, F120), the end-to-end "no PCR dependency" and "resource test" and the package gates (checkpoints F90/F100),
and the hardware TPM (F111, already done). "Independent implementation" for verification means `openssl` run by the test; the
`rsa`/`p256` crates the service itself uses do not count.

Environment check (dev container): F112/F113 already run `swtpm`, `tpm2-tools`, `openssl` and the `custodio-it` filter (`Lacks`,
fault rules by command, recording, `Swtpm::{clear, restart}`) in `tpm_access` and `tpm_import`. `swtpm` has no resource manager
and 3 transient slots, which the many-signatures test depends on; the builder confirms the slot count with `tpm2_getcap
properties-fixed` in the test.

## Evidence
- Every mechanism, both key types, verified independently → `tpm_sign::every_mechanism_verifies_with_the_certificate` → for an
  RSA 2048 key (`CKM_RSA_PKCS` with a `DigestInfo` per SHA-256/384/512 and with a non-`DigestInfo` payload; `CKM_RSA_PKCS_PSS` per
  hash with salt 0, `hLen` and the largest salt) and a P-256 key (`CKM_ECDSA` with 32-, 48- and 64-byte digests), the test imports
  a key generated by the test with a self-signed certificate, signs through the TPM and verifies with `openssl` using the
  certificate (`openssl pkeyutl -verify -pkeyopt ...` / `openssl dgst -verify`, ECDSA signature converted to DER by the test);
  every case exits 0. Controls: one flipped bit of the signature, and a signature verified against the wrong hash, salt length or
  another certificate, each fail in `openssl`.
- Truncation as the service does it → same test, ECDSA with 48- and 64-byte digests → `openssl` verifies the signature over
  the first 32 bytes of the digest as a prehash; control: the same signature does not verify as a 48-byte prehash of a different
  digest. `tpm_sign::ecdsa_truncation_matches_the_software_signer` → for each digest length the TPM and `sign::sign` agree on
  which lengths are accepted or refused.
- Same bounds and errors as the existing signer → `tpm::tests::sign::bounds_parity` (unit, front end, table above) and
  `tpm_sign::errors_match_the_software_signer` (integration, each error class: oversized payload, wrong digest length for PSS,
  oversized salt, empty ECDSA digest, RSA mechanism on a P-256 key and the reverse) → the error equals `sign::sign`'s class
  for the same input, and the filter records zero commands for a refused request (control: a valid request records commands).
- No parsing of signing input beyond lengths → `tpm::tests::sign::payload_is_opaque` (unit) → a `CKM_RSA_PKCS` payload that is not a
  valid `DigestInfo` (random bytes, a `DigestInfo` with trailing bytes, a truncated one, a length-field claiming more than the input)
  is signed byte for byte as given (the verified-by-`openssl` raw recovery of the block shows the payload unchanged), and none
  panics; oversized payloads are refused before allocation beyond the input.
- A mechanism the TPM cannot serve is a missing capability → `tpm_sign::missing_capability_is_reported` → with the filter's
  `Lacks`/fault rule making `TPM2_RSA_Decrypt` (RSA) and `TPM2_Sign` (P-256) unavailable, each mechanism returns the typed lacks
  error naming the item; the recording shows no other signing command was tried (no fallback); a TPM error that is not a lack
  (injected response code on the same command) returns the TPM error, not "lacks". Control: with no rule, the same call signs.
- The private key is never in the service's memory → `tpm_sign::private_key_not_on_the_wire_or_in_the_result` → through the
  recording `TpmFilter`, the bytes sent for an RSA and a P-256 signature (load plus sign) contain no encoding of the private
  key the test generated (raw scalar, `p`, `q`, private exponent, PKCS#1, PKCS#8, SEC1), and the signature call's type signatures
  take no key type: `tpm::tests::sign::no_secret_in_the_api` (unit, the request type holds the blob, the data and the
  mechanism only, checked by exhaustive destructuring). Control: the search finds a key the test plants in the recording.
- Everything flushed → `tpm_sign::nothing_left_loaded` → after a successful RSA and P-256 signature, after a refused request,
  after a parent mismatch, after a failed load and after an injected error response on each command before the last flush
  (create primary, load, sign, read public if used), `tpm2_getcap handles-transient`, `handles-loaded-session` and
  `handles-saved-session` on the same `swtpm` list nothing; where the flush itself is faulted or the connection is dropped,
  the call reports the error, a later signature on the same `swtpm` succeeds, and after `Swtpm::restart` nothing is loaded.
  Control: a recording without the flush rule of the filter shows the handle that stays.
- More signatures than the TPM has slots → `tpm_sign::many_signatures_in_a_row` → 30 signatures per key type (more than the 3
  transient slots, read from `tpm2_getcap properties-fixed`) on one `swtpm`, alternating mechanisms, all verify with `openssl`, and
  `handles-transient` is empty afterwards.
- A blob that does not load gives a distinct error → `tpm_sign::unloadable_blobs_are_distinct` → (a) blob imported, then
  `Swtpm::clear` (TPM cleared): `ParentMismatch`; (b) a second, independent `swtpm`: `ParentMismatch`; in both the filter records
  no `TPM2_Load`; (c) a blob whose private area has one byte changed, on the right TPM: the load error, not `ParentMismatch` and
  not "lacks"; (d) a blob with a truncated or oversized private area: a typed parse error, no TPM command; (e) the four variants'
  `Display` strings differ from each other and contain no names or key bytes (`tpm::tests::sign::error_messages`, unit). Control:
  after `Swtpm::restart` without a clear, the same blob signs and verifies.
- Every call checks the parent before loading → part of the case above (a)/(b) plus `tpm_sign::no_load_before_the_check` → the
  recording shows `CreatePrimary` precedes `TPM2_Load` on a good blob; for a bad blob only `CreatePrimary` and `FlushContext`.
- Files join `mutants` → for each file under `crates/custodiod/src/tpm*` that is not a `tests.rs` or under a `tests/` directory:
  `grep -c -- "--file crates/custodiod/src/<path>" justfile` → 1; after `just mutants-diff F114`, `missed.txt` is empty and each new
  file with mutants has at least one caught.
- Whole feature → the `verify` of F114 in features.json (`just quick && cargo test -p custodiod --test tpm_sign --locked && just
  mutants-diff F114`) → exit 0.

## Amendments
- When the flush itself is faulted or the connection is dropped, the later signature on the same `swtpm` follows `tpm2_flushcontext -t`
  (the cleanup the kernel resource manager does when a connection closes) instead of following the failed call directly. Finding: `swtpm`
  has no resource manager and 3 transient slots (read with `tpm2_getcap properties-fixed` in the test); with `TPM2_FlushContext` faulted
  both the parent and the key stay loaded, and a faulting filter applies to every occurrence, so a direct retry cannot fit. The test still
  checks that the faulted flush leaves handles, that the call reports the error, that a signature succeeds after the cleanup, and that
  nothing is loaded after `Swtpm::restart`.
