# F112 — TPM access point and capability query in custodiod

## Scope
Built, in `custodiod`, a new `tpm` module (several small files; `just quick` rejects files over 5000 tokens, and
every new `.rs` file under `crates/custodiod/src/tpm*` joins the `mutants` recipe's `--file` list; test modules in
`tests.rs` files do not):
- the **access point**: a trait over "open the TPM and answer capability queries", with two kinds of implementation:
  the **production** one, which opens only the kernel resource manager `/dev/tpmrm0` through `tss-esapi` (a
  dependency of `custodiod` from now on, pinned like the one in `custodio-it`; `cargo deny` and `cargo machete` stay green
  under the unchanged `deny.toml`), and **test** ones that take a TCTI string (an `swtpm` instance, the F107 `TpmFilter`, a
  faulty one) or a directory root standing in for `/dev`;
- the **classification** of a TPM for one key type (RSA 2048, ECC P-256) as `Absent`, `Lacks` (naming every
  absent item of the list), `Ready`, or `Error` (device present but not openable, a TPM error with its response code, an
  owner hierarchy the service cannot use). An `Error` is never turned into `Absent` or `Lacks`. When the owner hierarchy
  is unusable *and* a capability is absent, the result is `Error` (conservative: `Lacks` selects a weaker kind, `Error`
  stores nothing);
- the **capability list per key type**, from `## F107` of `docs/findings.md` as `docs/decisions.md` (2026-11-03,
  "the service pads", approved in F111) narrows it, documented once in `docs/api.md` (or a page it links), and a
  test that ties the code's list to that document;
- an `swtpm`-backed fault mode in `custodio-it` (see Steps) so integration tests can inject a TPM error response.

The list is way (b), fixed now from `## F107` ("The TPM capabilities each key type needs"), `docs/decisions.md`
(2026-11-03 "the service pads", and 2026-11-03 "TPM parent": ECC P-256 primary, AES-128-CFB, SHA-256 name) and what F113/F114
call. Both key types need the parent, so the parent's items are on both lists. SHA-384 and SHA-512 are queried for neither
(F111: the STM hardware TPM lacks SHA-512 and must be `Ready`).

| Item | Query | RSA 2048 | ECC P-256 |
|---|---|---|---|
| algorithm ECC (`0x0023`; the parent) | `GetCapability(ALGS)` | yes | yes |
| curve NIST P-256 (`0x0003`) | `GetCapability(ECC_CURVES)` | yes (parent) | yes |
| name algorithm SHA-256 (`0x000b`) | `GetCapability(ALGS)` | yes | yes |
| algorithm AES (`0x0006`; the parent's symmetric) | `GetCapability(ALGS)` | yes | yes |
| parent template: ECC P-256, AES-128-CFB, null scheme | `TestParms` | yes | yes |
| command `TPM2_CC_CreatePrimary` | `GetCapability(COMMANDS)` | yes | yes |
| command `TPM2_CC_Import` | `GetCapability(COMMANDS)` | yes | yes |
| command `TPM2_CC_Load` | `GetCapability(COMMANDS)` | yes | yes |
| algorithm RSA (`0x0001`) | `GetCapability(ALGS)` | yes | no |
| rsa2048, null scheme | `TestParms` | yes | no |
| command `TPM2_CC_RSA_Decrypt` | `GetCapability(COMMANDS)` | yes | no |
| ECDSA with SHA-256 on P-256 | `TestParms` | no | yes |
| command `TPM2_CC_Sign` | `GetCapability(COMMANDS)` | no | yes |

A `TestParms` item whose algorithm item is already absent is not queried and not named a second time (the algorithm is
named). `Lacks` names every other absent item. The table above is the contract's copy; `docs/api.md` carries the one
documented copy. If the builder finds an item missing while building, an amendment adds it to the table, the document and
the code, with the reason in the commit.

Environment decisions the builder must apply (conservative, SPEC section 2): `Absent` only when the platform exposes no
TPM device, i.e. `/dev/tpmrm0` does not exist. `/dev/tpmrm0` missing while the raw `/dev/tpm0` exists is `Error` (the
platform has a TPM, the resource manager is missing), found by `stat`, never by opening the raw node. Any other
failure to open (permission, `ENXIO`, `ENODEV`, a TCTI that fails) is `Error`. Under the dedicated variable below (the test-only
TCTI), a missing socket is `Absent`, as F108's "No TPM" e2e case builds it (the drop-in's TCTI stays set, `swtpm` is not
started); a path that exists but is not a socket, and a refused or broken connection, are `Error`. The choice is recorded in
`docs/decisions.md` with the variable.

How the test-only TCTI reaches the access point (F108, route 2, which the e2e containers use on the real shipped
package): the shipped binary reads **one dedicated variable** (a name of its own, not `TPM2TOOLS_TCTI`, `TSS2_TCTI`,
`TPM20TEST_TCTI` or `TCTI`) that accepts only an `swtpm:path=<absolute unix socket>` TCTI. The shipped unit and packages never
set it (F131 and the e2e cases check that no drop-in ships). Unset, the production constructor opens `/dev/tpmrm0`
and nothing else; set to anything that is not a well-formed `swtpm:path=` value, or to an existing path that is not a
socket, it is refused as `Error`, never a fallback to `/dev/tpmrm0` and never `Absent`. The generic TCTI variables and
every other form (`device:`, `mssim:`, `tabrmd:`) are ignored or refused. The choice is recorded in `docs/decisions.md`.
If the builder judges even this too permissive for the SPEC ("no configuration of the shipped unit can do so"), it writes
`BLOCKED.md` instead of choosing a route that rules out F108's. The e2e wiring (drop-in, bind of the socket directory) is F131; here only the variable and its refusals.

Left to other features: importing and signing (F113, F114), choosing the kind and the import flow (F117), the journal
(F120) and D-Bus error names (F119), polkit, packaging and unit directives (F109's decision is applied later), the e2e
cases, and any run on a hardware TPM. A real `/dev/tpmrm0` does not exist in the dev container (`ls /dev/tpm*` →
`No such file or directory`, checked), so the production `Ready` path on a real node is proven at the checkpoint/e2e
level (F131 onward) and by the person's hardware run in F111, not here; the dev container proves the same query code through the
test TCTI and the production path's `Absent`.

Environment check (dev container): `pkg-config --modversion tss2-esys tss2-tctildr` → `4.1.3` / `4.1.3`;
`custodio-it` already builds `tss-esapi` 8.0.0-alpha.4 against it (F105 passes); `swtpm` is installed and
`custodio_it::swtpm::Swtpm` starts one per test; `swtpm`, `tpm2_changeauth`, `tpm2_hierarchycontrol`, `tpm2_getcap` and
`tpm2_createprimary` are all in `/usr/bin` (checked with `ls /usr/bin`). The F107 `TpmFilter` today cannot remove commands from
`TPM_CAP_COMMANDS` (it rewrites `ALGS` and `ECC_CURVES` only, `crates/custodio-it/src/tpm_filter.rs`): the `custodio-it` step
extends `Lacks` with a command list and rewrites that answer.

## Steps
- [x] Tests first: the classification as a pure function over an answer type (the capability answers, the owner-hierarchy
      state, the open outcome), unit tests for `Absent`, `Lacks` (named items), `Ready`, each `Error` kind, the
      precedence rule (`Error` over `Lacks`), and `Display`/`Debug` of the result naming the cause and carrying nothing else.
- [x] Add `tss-esapi` to `custodiod`, the `tpm` module, the access-point trait, the capability list (one constant per
      key type) and the classification; `docs/api.md` (or a linked page) gets the list; the doc-versus-code test.
- [x] The production implementation (`/dev/tpmrm0` only, through a root-directory seam for tests) and the test-only
      implementation taking a TCTI, with the route settled above; owner-hierarchy usability check (the builder picks
      the TPM properties or a create-and-flush of a primary, within: nothing it creates survives the call, and it fails on
      an owner auth that is set and on a disabled owner hierarchy).
- [x] `custodio-it`: extend `Lacks` with commands removed from the `TPM_CAP_COMMANDS` answer (so `TPM2_RSA_Decrypt`,
      `TPM2_CC_Import` and `TPM2_CC_Load` can be made absent), and a fault mode that makes a chosen TPM command answer a chosen
      response code or drop the connection (in the filter or a sibling); each with its own test in the existing filter test target.
- [x] Integration test target `tpm_access` in `crates/custodiod/tests/` (`tpm_access.rs`): `swtpm` ready for both key
      types, lacking `swtpm` per item, absent, injected faults, no TPM objects left behind.
- [x] New `tpm` source files in the `mutants` recipe; `just quick`, `cargo test -p custodiod --test tpm_access`, then
      `just mutants-diff F112`; kill survivors with tests, not exclusions.

## Evidence
- Production opens only the resource manager, never the raw device →
  `tpm::production_opens_only_tpmrm0` (unit) → the production conf string / path is exactly `/dev/tpmrm0`; the
  module never calls `File::open` or `OpenOptions`; and an `tpm_access` case on a temp root with a
  regular file `tpm0` and no `tpmrm0` is `Error`, (the raw node is mode `000`, so an open would fail as a different, open-failure `Error`: control — the same root with `tpmrm0` mode `000` gives the open-failure kind, so the two kinds are told apart).
- Nothing but the one variable can substitute a TPM → `tpm_access::production_ignores_environment` → a child process (re-exec
  of the test binary; no `set_var` in a threaded test) with `TPM2TOOLS_TCTI`, `TSS2_TCTI`, `TPM20TEST_TCTI` and `TCTI`
  pointing at a live `swtpm` classifies as `Absent` through the real production constructor. It asserts first that
  `/dev/tpmrm0` does not exist (true in the dev container and CI; on a host with a TPM it fails loudly rather than passes);
  control: the dedicated variable with the same swtpm socket is `Ready`. `tpm_access::dedicated_variable_refusals` → a
  malformed value, a `device:` or `mssim:` TCTI, a relative path, and a path that is a regular file each give `Error`, never
  `Absent`/`Ready`/`Lacks`. `grep -rc` of the variable name in `data/`, `packaging/` and the shipped unit → 0.
- `Absent`: the platform exposes no TPM device → `tpm_access::absent_when_no_device` → empty temp root gives
  `Absent`; the real production constructor in the dev container gives `Absent`; a missing swtpm socket gives `Absent` through the dedicated-variable constructor
  (the e2e "no TPM" shape of F108), while a path that is a regular file under the same constructor is `Error`
  (`dedicated_variable_refusals`).
- `Ready` → `tpm_access::ready_both_key_types` → a fresh `Swtpm` is `Ready` for RSA 2048 and for ECC P-256.
- `Lacks`, named, per the table → `tpm_access::lacks_each_item` → through `TpmFilter`, one case per queryable item:
  RSA algorithm; ECC algorithm; curve P-256; SHA-256; AES; and, through the extended `Lacks`, each of `CreatePrimary`,
  `Import`, `Load`, `RSA_Decrypt`, `Sign`. Each gives `Lacks` naming exactly that item for the key types that list it and
  `Ready` for the others (RSA algorithm missing → ECC `Ready`, RSA `Lacks`; `RSA_Decrypt` missing → ECC `Ready`; `Sign` missing →
  RSA `Ready`). ECC algorithm missing → `Lacks` for **both** key types, naming the ECC algorithm once (the parent). AES
  missing → `Lacks` naming AES for both. `Import` or `Load` missing → `Lacks` for both. `TestParms` refusals
  (`TPM_RC_SCHEME` / `TPM_RC_HASH` / `TPM_RC_CURVE` / `TPM_RC_TYPE`) for the three `TestParms` items are `Lacks` naming that
  item (a unit case on the classification for the codes the filter cannot reach, e.g. a refusal of ECDSA/SHA-256 alone).
  `tpm::tests::dependent_items_named_once` (unit) → the rule of the table's note.
- SHA-384 and SHA-512 are not part of the list → `tpm_access::sha512_absent_is_ready` → the filter lacks SHA-384 and
  SHA-512 (the F111 hardware case): both key types are `Ready`; control: lacking SHA-256 is `Lacks` (the filter does remove hashes).
- `Error` is never `Absent` or `Lacks` → `tpm_access::faults_are_errors` → (a) device node present, mode `000`: open
  failure `Error` (not `Absent`); (b) `ENXIO`-style node (a directory or a socket where the node should be): `Error`;
  (c) the fault TCTI answers `TPM_RC_FAILURE` to `GetCapability`, to `TestParms` (the same code that a lacking
  capability does *not* use), and drops the connection mid-reply: each `Error` carrying the response code, none `Lacks`; (d)
  `swtpm` with the owner auth set (`tpm2_changeauth -c o`) and with the owner hierarchy disabled
  (`tpm2_hierarchycontrol -C p shEnable clear`): `Error` of the owner-hierarchy kind; controls: the same two states
  restored (or a fresh instance) give `Ready`; (e) owner auth set on a filter-lacking `swtpm` is `Error`, not `Lacks`.
  Mutation testing of the classification (`just mutants-diff F112`) kills a mutant that maps an error to `Absent`/`Lacks`.
- Response codes as a real TPM returns them → `tpm::tests::parameter_qualified_codes` and a `tpm_access` case → the
  classifier masks the parameter and format bits: `0x1C3` (SHA-512 `TestParms`, F111), `0x1D2` and the filter's `0x0A6|0x40|1<<8` forms are `Lacks` where they mean an unsupported item, any other code is `Error`.
- No TPM object or session is left behind → `tpm_access::nothing_left_loaded` → after a `Ready` classification, a
  `Lacks` one and an owner-check run, `tpm2_getcap handles-transient` and `handles-loaded-session` on the same swtpm list
  nothing (control: after `tpm2_createprimary` without flush the same command lists one handle, so the check can fail).
- The list is documented once, from the finding → `tpm::list_matches_document` → the table in `docs/api.md` (or the
  page it links) is parsed and equals the code's list per key type, item for item; no SHA-384/512 in either. `just api-contract` stays green with the added section.
- Filter extension can fail → its filter-target tests → with `RSA_Decrypt`, `Import` and `Load` in the command list, `tpm2_getcap
  commands` through the filter omits exactly those and plain `swtpm` lists them; a command given a fault rule is answered with the
  chosen code (or the dropped connection) and the client sees it; without the rule the same command succeeds.
- Decisions recorded → `grep -c` in `docs/decisions.md` for the dedicated variable's name → at least 1; the entry states that a missing
  socket under it is `Absent` (F108) and everything else malformed is `Error`.
- `Display`/`Debug` of each result are distinct, contain the response code or the item name, and nothing else: asserted inside the
  unit cases of the first Step (no separate test).
- New files join `mutants` → for each file under `crates/custodiod/src/tpm*` that is not a `tests.rs`:
  `grep -c -- "--file crates/custodiod/src/<path>" justfile` → 1; after `just mutants-diff F112`, `missed.txt` is empty and
  each of those files that has mutants has at least one caught.
- Whole feature → the `verify` of F112 in features.json (`just quick && cargo test -p custodiod --test tpm_access --locked
  && just mutants-diff F112`; `cargo deny check` and `cargo machete` also pass as `just quick` already runs them or
  the builder runs them once at the end) → exit 0.
