# F140 — End-to-end cases: signing after the TPM is cleared

## Scope
New cases `tpm-clear-*` for SPEC acceptance 8, against the real packaged service, module, CLI, polkit and journal in the debian13 container. Alice imports an RSA 2048 and a
P-256 key (kind `tpm` in `swtpm` and in `lacking`), both sign (guest control), then root clears the TPM the service uses with `tpm2_clear` on its socket (lockout
hierarchy, empty auth, as `swtpm.rs` `clear()` of F129 does; the owner seed changes). Then, judged from real outputs:
- **sign fails, documented** — each key signs through `pkcs11-tool` and the D-Bus `Sign` (`owner-call.py`): the module reports `CKR_DEVICE_ERROR` (the module maps every
  service error but the polkit and invalid-argument ones to it, `backend.rs` `error_for_name`) and the D-Bus error is `com.rfirma.Custodio1.Error.KeyLost` with the
  text `docs/api.md` documents; the attempt is repeated once more (the key is not deleted and nothing is cached by a first failure).
  One journal entry per attempt: operation `sign`, outcome `signing_failed`, `CUSTODIO_CAUSE=key_lost`, the key id, the stored kind `tpm`, the caller's uid, and no secret
  (password, key bytes) in it; no fall-through entry of another kind or operation.
- **keys still listed** — `ListKeys` and `custodio list` show the same ids with kind `tpm` as before the clear, and the state directory (as root) is byte-identical to
  before the clear (the service did not delete or rewrite a record).
- **can be deleted** — `custodio delete` (polkit, as alice) of both keys succeeds after the clear; the records are gone from the state directory and from `ListKeys`; one
  `delete` journal entry per key. As a recovery check, importing one of the same ids again succeeds with kind `tpm` and signs (the service works with the new owner seed),
  and is deleted.
- **TPM-bound (`encrypted-tpm`) keys** — cannot be made in the container (`SPEC_DEVIATIONS.md` F134, `docs/findings/F134.md` last section). This feature extends that
  entry to F140 for the `encrypted-tpm` half only, in its own commit with this contract's amendment; the coverage statement is F129 (`tpm_lifecycle`
  `cleared_*`: four keys incl. `encrypted-tpm` through a credential double, sign fails `KeyLost` with an entry, keys listed, deletable) and `creds.rs`
  `cleared_tpm_cannot_decrypt`; the real `systemd-creds` is not run for it. No `encrypted-tpm` claim is made by these cases. The deviation needs an evaluator's approval and a
  person's review; the builder does not claim the TPM-bound half proven end to end.
- **Not repeated:** the same property on the bus with a fake polkit, all four kinds, PCR changes and restarts (F129); the cause names (F120); the kinds and mechanisms (F133/F134).
  Package gates and `just e2e` as a whole are proven at the checkpoint.

**Isolation (the design constraint that matters).** Clearing the shared TPM would make every key of the earlier steps (`rsa1`, `ec1`, …) unusable for the later steps
(upgrade, lifecycle, refusal). The step therefore must leave the main TPM and those keys as found. The builder chooses how: the preferred route is the one `tpm-dup-other-tpm`
(F136) and `tpmfail-*` (F139) use — a second, independent `swtpm` on its own socket and state directory, the e2e drop-in rewritten to it, the service restarted, the keys
imported there, cleared there, and everything restored by a trap (drop-in back to the mode's TPM, service restarted, second swtpm stopped) even if a case fails. In `lacking`,
the second `swtpm` goes behind the same filter (`/e2e-bin/tpm-filter`, `alg=0x16`) so the `lacking` leg is really a lacking TPM. If the builder instead clears the main TPM, it
must delete or re-import every key of the earlier steps that later steps use, and name them in the finding; the evidence "state left as found" below must hold either way.

**Modes.** `swtpm` and `lacking`: all cases run, kind `tpm` judged before and after (a wrong kind fails the case, so the run is not vacuous). `none`: no TPM to clear, keys are
`encrypted-host`, which a TPM clear does not touch; the cases are reported skipped (`skip.list`, reason). Ids in `e2e/targets/debian13/cases.list` (outcome depends on the TPM,
SPEC end-to-end scope), not in `e2e/cases.list`; `check-cases.sh` refuses a `tpm-clear-*` skip in `swtpm` and `lacking`. Group `tpmclear` in `select.sh` (the pattern `tpm-clear-*`
is captured by no other group: the existing `tpm-dup-*`/`tpm-kind-*`/`tpmfail-*` patterns are checked by the host test), step in `guest.sh` after `tpmfail` and before the upgrade.

**Cases** (each reported exactly once; every id matches `tpm-clear-*`): `tpm-clear-sign-fails` (control signs before; the clear really happened — see the negative control; both keys
fail on both paths with `KeyLost`/`CKR_DEVICE_ERROR`, twice; one `key_lost` entry per attempt, no secret), `tpm-clear-keys-listed` (same ids and kind after, in `ListKeys` and in
`custodio list`; state directory unchanged), `tpm-clear-delete` (both deleted, records gone, entries, re-import works). The builder may add one.

**Negative controls.** Guest: the clear is shown to have changed the owner hierarchy (the public name of a primary created under the owner hierarchy with a fixed template differs
before and after, or the owner seed's effect is shown otherwise), so failing signatures follow from a real clear and not from a service that merely broke; and a key imported again after the clear (the re-import of `tpm-clear-delete`) signs on the same, now cleared TPM, so a failure is not the rig (it shows the rig and the new seed work; it is not an "uncleared position"). Host (`scripts/test-e2e-tpmclear.sh`, no container,
in the justfile script-test list): the judgement functions (python3 `-I`, functions of files, in `e2e/tpmclear.py`) accept a good record and reject: a signature that succeeded after the
clear, a different error name, a wrong CKR, zero or two entries per attempt, a wrong cause, a missing key id or wrong kind in the entry, a secret in the entry, a key missing from
`ListKeys` or the CLI list, a changed kind, a changed state directory, a delete that failed or left a record, an unchanged owner-hierarchy name, a missing re-import; and `check-cases.sh`
accepts the `none` skip and refuses one in `swtpm` and `lacking`; the ids are in the debian13 list and not in `e2e/cases.list`.

**Cost.** Host test: under 5 s, parallel with the other script tests (budget 60 s). Guest, per mode (`swtpm`, `lacking`): a second `swtpm` start (~1–2 s), drop-in rewrite and
service restart waited on a new MainPID + `is-active` + bus `Ping`, never a fixed sleep (~3 s, twice: in and out), two imports as alice (2–4 s each, run as parallel background
jobs joined with `wait`), signing rounds over both paths (~1 s each; the failing ones are quick), `tpm2_clear` (<1 s), two deletes and one re-import + sign + delete (~10 s, a
polkit-authorised call is ~5 s, so the deletes of both keys run in one session). Estimated 25–35 s of the phase, no new container; `just e2e-cases debian13 'tpm-clear-*'` about 55–75 s
per mode (F137: 46–48 s whole run with a 23–25 s phase), ~20 s in `none` (skips only). The full debian13 `swtpm` run grows by ~30 s on top of F135 (~20 s), F136 (~22 s), F137 (~23 s) and
F139 (~30 s) against the budget in `budgets.tsv`: **this may not fit**. The builder sums it in `PROGRESS.md` and asks for more in `BLOCKED.md` if a measured run passes the budget
(that run is the checkpoint's). No `budgets.tsv` change is requested now.

**Environment.** `tpm2_clear`, `swtpm`/`swtpm_setup`, `swtpm_ioctl`, `systemctl` are in the debian13 guest (F136/F137/F139 used them); `swtpm` does not run in the dev container (F136), so
step 1's probe is the guest run itself. The filter program is mounted only in mode `lacking`. If `tpm2_clear` through the filter or on the second swtpm cannot be driven, the
builder rewrites the affected case with the command and result in the finding before building more (a person's run or a deviation).

Size: five steps, one session each at most.

## Evidence
- Signing fails after a clear, documented error → `tpm-clear-sign-fails` (`just e2e-cases debian13 'tpm-clear-*'` in `swtpm` and `E2E_TPM=lacking`) → for the RSA and the P-256 key,
  twice each: `Sign` gives `KeyLost` with the documented text, `pkcs11-tool` gets `CKR_DEVICE_ERROR`; both signed before the clear.
- A journal entry → same case → exactly one `sign` / `signing_failed` / `key_lost` entry per attempt with key id, kind `tpm` and uid, no other entry for it, no secret.
- The clear is real, not a broken rig → guest control in `tpm-clear-sign-fails` → the owner-hierarchy primary's name (fixed template, no unique data) differs before and after; a key re-imported after the clear signs on the cleared TPM.
- Keys still listed → `tpm-clear-keys-listed` (same runs) → same ids and kind `tpm` in `ListKeys` and `custodio list`; state directory byte-identical to before the clear.
- Can be deleted → `tpm-clear-delete` (same runs) → both deletes succeed, records and `ListKeys` entries gone, one `delete` entry per key; a re-import of the same id succeeds with kind `tpm`, signs, and is deleted.
- TPM-bound keys → not run in the container: `SPEC_DEVIATIONS.md` F140 extension, covered by F129 `tpm_lifecycle` `cleared_*` and `creds.rs` `cleared_tpm_cannot_decrypt` (part of `just quick`) →
  the deviation is reviewed by a person; these cases make no `encrypted-tpm` claim.
- Skipped where they do not apply → `E2E_TPM=none just e2e-cases debian13 'tpm-clear-*'` → 3 skipped, "accounted for"; host test: `check-cases.sh` accepts the `none` skip and refuses one in `swtpm`
  and `lacking`; ids in the debian13 list, not in `e2e/cases.list`.
- Each judgement can fail → `scripts/test-e2e-tpmclear.sh` → rejects each bad record listed, accepts the good ones.
- State left as found → end of the step → main TPM and the earlier steps' keys unchanged, the unit's TPM equals the mode's per `tpm_observe`, service active and answering `Ping`, no extra `swtpm`/filter
  process, both keys absent from `ListKeys` (full run at the checkpoint).
- Same property on the bus with a fake polkit, all four kinds → F129, not repeated.
- `just quick` green and the `verify` command → exit 0.
