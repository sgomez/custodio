# F105 — tss-esapi under the supply-chain policy and an swtpm fixture for Rust tests

## Scope
Built:
- `tss-esapi` (and what it pulls in) enters the workspace as a dependency of `custodio-it`,
  pinned in `Cargo.lock`; `cargo deny check` and `cargo machete` pass. `deny.toml` is not
  loosened: no entry is removed or relaxed, and any new licence, advisory or `skip` entry carries
  a comment saying why. Which `tss-esapi` version to take (stable or the pre-release that
  `cargo info` currently shows as latest) is the builder's call; a pre-release needs one line in
  the commit saying why the stable one does not do.
- An `swtpm` fixture in `custodio-it` (library code, not under `tests/`), used by the integration
  target `crates/custodio-it/tests/swtpm_fixture.rs`. Each instance: its own `swtpm` on a private
  socket, fresh state directory, `TPM2_Startup` done; it gives its TCTI string (for `tss-esapi`
  and for `tpm2-tools`) and can run a `tpm2-tools` command against itself without touching the
  process environment (tests run in parallel); extend a PCR; restart on the same state; clear the
  TPM with `tpm2_clear`; start a second independent instance. Drop kills `swtpm` and removes the
  state, also while panicking.

Left to other features: any Custodio TPM code (import, signing, parent keys), and the `with-swtpm`
recipe (F104, done). CI green with the new crates is proven at the checkpoint.

Environment (checked in this session, dev container): `swtpm`, `tpm2_clear`, `tpm2_pcrextend`
are on PATH; `pkg-config --modversion tss2-esys tss2-tctildr` prints 4.1.3 for both; `clang` and
`libclang-cpp19` are present; crates.io is reachable (`cargo info tss-esapi` works). Not yet
shown: that `tss-esapi-sys` builds here (bindgen needs libclang headers). Step 1 runs that. If the
build needs a distribution package the container and CI do not install, that is a change to the
dev container: the builder writes `BLOCKED.md` (and updates the package list, sync check and CI in
the same commit). F104 found that in this container `swtpm` cannot be signalled (EPERM, even
SIGKILL); the fixture must stop it the way `scripts/with-swtpm.sh` does (control socket,
`swtpm_ioctl -s`, signal as fallback, bounded wait), not rely on `Child::kill`.

## Evidence
- `tss-esapi` in the workspace and pinned → `cargo build -p custodio-it --tests --locked` and
  `grep -c 'name = "tss-esapi"' Cargo.lock` → builds, count 1.
- Accepted by `cargo deny check` without loosening → `cargo deny check`, plus
  `git diff main -- deny.toml` read by the builder → exit 0; the diff has no removed or widened
  `allow`/`ignore`/`skip` line, and every added line has a comment.
- Used, so machete passes → `cargo machete` → exit 0 with `tss-esapi` listed in `custodio-it`
  (it is used by the fixture tests, not an `ignored` entry).
- Context through the fixture reads a TPM property → test `swtpm_fixture` (open `tss-esapi`
  context from the fixture's TCTI string, `get_capability` / `TPM2_PT_MANUFACTURER` or similar) →
  a plausible swtpm value (non-zero, the manufacturer of swtpm), not just `Ok`.
- TCTI works for `tpm2-tools` too, private socket → test runs `tpm2_getcap properties-fixed`
  through the fixture's runner → exit 0; and the socket path lies inside the instance's own state
  directory, different from the other instance's.
- Extend a PCR → test extends PCR 16 (or another resettable one) with known data, reads it back
  with `tss-esapi` or `tpm2_pcrread` → equals the SHA-256 of 32 zero bytes followed by the digest
  of the data; before the extend it was all zero (fails if extend were a no-op).
- Restart on the same state → test creates a persistent object (`tpm2_createprimary` +
  `tpm2_evictcontrol`) or reads a value that only survives with state, restarts the instance,
  and finds the same persistent handle and the same public key; also the TPM property read still
  works after the restart through a new context (old TCTI string either still valid or the new one
  is returned, as documented in the fixture) ; the PCR extended before the restart is back to zero
  (TPM2_Startup CLEAR semantics), proving a restart really happened.
- Clear → test after the restart runs the fixture's clear (`tpm2_clear`) → persistent handle
  list is empty and the same createprimary now gives a different public key than before the clear.
- Two independent instances → test starts two, runs `tpm2_createprimary -C e` (or `-C o`) with
  one template on each → public keys differ; a persistent object made in one is absent in the
  other; clearing or dropping one leaves the other working.
- Cleanup on drop, panics included → test records swtpm pid, socket and state directory; after a
  normal drop, and after a drop during a panic (`std::panic::catch_unwind`, or a panicking
  thread, with the fixture alive) checks the process no longer exists (or is a zombie-free gone
  pid) and the directory is gone. Negative control: the same check run against an instance that
  was `mem::forget`ed or not dropped yet shows the process alive and directory present, so the
  assertion can fail.
- Fresh state per instance → test: two consecutive instances, a persistent object made in the
  first is not in the second (`handles-persistent` empty).
- Tests fail, not skip, when `swtpm`/`tpm2-tools` are absent → the fixture's start returns a
  clear error naming the tool and the test panics on it; checked by running the target with a
  `PATH` that hides `swtpm` once → fails with that message.
- Whole feature → `just quick && cargo deny check && cargo machete && cargo test -p custodio-it
  --test swtpm_fixture --locked` → exit 0.
