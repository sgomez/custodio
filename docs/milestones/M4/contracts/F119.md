# F119 — The storage kind in the API and the client documentation

## Scope
`custodiod` reports the storage kind chosen by F117 and stored by F116; `custodio-client` exposes it; `docs/api.md` documents
it; `just api-contract` checks it. After F117 and F118 the kinds exist, are chosen and are used to sign, but nothing on the
bus carries them yet, and the TPM and credential failure names (`TpmFailed`, `CredentialsUnavailable`, `KeyLost`,
`TemporarilyUnavailable`) were added by F117/F118 and are documented there.

- **Import result and list.** `ImportP12` returns the kind next to the key type; `ListKeys` returns the kind of every key,
  read from the stored record (listing never opens the TPM or the credential service, as today). The wire strings are the
  ones `store::Kind::wire` already fixes (`tpm`, `encrypted-tpm`, `encrypted-host`); they are not changed here.
- **The D-Bus signatures change** (`ImportP12` out, `ListKeys` out). That breaks a client written for M3, so the first step
  decides the shapes (the kind goes next to the key type) and records the decision in `docs/decisions.md` (a later session
  could undo it without knowing why). Every consumer in this repository is updated in the same feature so that it keeps
  working with the same visible behaviour: the `custodio` CLI's `bus.rs` and the PKCS#11 backend read the new shape and
  ignore the kind (the PKCS#11 module has no visible change); `custodio-it` rigs and the daemon's own tests follow.
- **`custodio-client`** gets the kind as a type with the three wire strings, parsing from the wire string, and a value for a
  string it does not know (a kind added later must not make a client fail). It adds no D-Bus calling code. What the CLI
  prints about the kind is F123; the journal's kind is F120.
- **`docs/api.md`**: the kind values (one line per value in a format `just api-contract` reads), the changed `out` lines, and
  a section that explains each kind and what it protects against and from whom, in the words of the SPEC threat model and
  the table of SPEC section 1 (TPM: nobody can copy it; encrypted TPM-bound: root while the machine runs; encrypted
  host-bound: root and anyone with a backup or copy of `/var/lib`), and when each is chosen (SPEC section 2). The errors
  section already names the TPM and credential failures; this feature only keeps them in step with the check.
- **`just api-contract`** (the `api_contract` target) learns the kinds: the document's kind lines against the kinds the live
  service returns and against the client's list; and the error names against the client's constants as well as the
  document and `ServiceError::ALL`.
- **Left to other features.** Kind text in the CLI (F123); kind in the journal and `docs/audit.md` (F120); purge (F121);
  the errors' behaviour (proven in F117 `storage_choice` and F118 `sign_kinds`, not repeated here: this feature proves only
  that they are documented and consistent); e2e cases and the install/lifecycle tests at the checkpoints (F132/F146).
- **Size.** About five steps; no split proposed.

Environment: needs nothing beyond what `storage_choice` and `sign_kinds` already use (`swtpm`, `systemd-creds`, the private
bus). `api_kind` reuses their rig (`storage_choice/rig.rs`); no new tool.

## Evidence
`api_kind` runs the real service on the private bus with fake polkit, the in-memory sink, `swtpm` and, where a row needs it,
the real `systemd-creds` (as `storage_choice` does); the result is read from the raw D-Bus reply (signature and value), not
through service code. Each kind row runs for RSA 2048 and P-256.

- Import returns the kind next to the key type, for each kind → `api_kind::import_returns_kind` → TPM ready gives
  (`rsa2048`|`ecdsa-p256`, `tpm`); TPM lacking a capability gives `encrypted-tpm`; no TPM gives `encrypted-host`; the
  reply signature is the documented one; the kind equals the one in the stored record (read from the store files) and is
  one of the client's three values.
- List returns the kind of each key → `api_kind::list_returns_kind` → with one key of each kind of the same owner in the
  store, `ListKeys` returns for each id its own kind and key type and certificate (a constant kind, or the kind of the
  first key, fails); another owner's keys are not listed; the TPM `open` and the credentials `decrypt` counts do not move
  during the list.
- The kind survives what makes a key unusable → `api_kind::list_after_loss` → after the `swtpm` is cleared and for a
  credential that cannot be decrypted, the list still gives the stored kind (the kind is read, not probed).
- The wire strings are stable and the client copes with an unknown one → unit tests in `custodio-client`
  (`kind::tests`) → the three strings round-trip exactly as `tpm`, `encrypted-tpm`, `encrypted-host`; an unknown string
  parses to the unknown value and keeps its text; the client's list of kinds equals the service's
  (`store::Kind`) wire strings (checked in `api_contract`, which can see both).
- Existing consumers still work → the unchanged behaviour tests of the CLI (`custodio-cli` list and import tests),
  the PKCS#11 backend tests and `custodio-it` list/cryptoki targets, run by `just quick` → green with the new shape (a
  consumer left on the old shape fails to deserialize and fails these).
- Error names documented for the TPM and credential failures → `just api-contract` (`api_contract::api_document_matches_its_sources`)
  → green; it now also compares the client's `ERROR_*` constants with `ServiceError::ALL` and the document, so a name added
  to one and not the others fails. Negative controls in `edited_copies_of_the_document_fail`: a name removed from the
  document fails `source item missing`; a name only in the document fails `document item missing`. That the service
  emits `TpmFailed`/`CredentialsUnavailable` at import and `KeyLost`/`TemporarilyUnavailable` at sign is F117's
  `storage_choice` and F118's `sign_kinds` (not repeated).
- Kinds documented and consistent with the live service → `api_contract::api_document_matches_its_sources` → the kind lines
  of `docs/api.md` equal the set of kinds the live service returned for an import and a list of each kind (the same rig as
  `api_kind`) and the client's list. Negative controls (in `edited_copies_of_the_document_fail`): a kind line removed fails
  `source item missing`; a kind line for a kind that does not exist fails `document item missing`; a service double that
  returns a string that is not documented fails.
- The `out` signatures of `ImportP12` and `ListKeys` in the document are the live ones → the existing introspection
  comparison in `api_contract` → green; a wrong signature in a copy fails (the existing control for `Sign` covers the
  mechanism; one more control edits the `ListKeys` out line).
- Each kind and what it protects against explained, in the words of the SPEC threat model → read by the evaluator against
  SPEC section 1 and the threat model (a document is not tested by its wording); the kind values themselves are held by the
  `api_contract` rows above.
- No kind or key material in the new replies beyond the kind string → `api_kind::import_returns_kind` also asserts that the
  reply holds no more than the key type and the kind.
- The kind plumbing is tight → `just mutants-diff F119` → 0 missed (a mutant that returns the wrong or a constant kind in
  the import reply or the list is killed by the rows above). New non-test files join the `mutants` list.
