# F187 — Checkpoint and last automated feature: the whole milestone

## Scope
Almost nothing is built. This feature runs every suite of M6 on the work of F170–F186 and fixes whatever fails, at its cause,
under the M4/M5 rules: no `#[ignore]`, no lowered threshold, no `#[allow]` without a justification, no recipe turned into a
no-op, no guard loosened, no case changed except where the case is wrong, no skip added without a stated and evidenced reason,
no `budgets.tsv` edit. The `verify` is
`just check && just api-contract && just fuzz-smoke && just memory-safety && just e2e && just package-gates && just coverage-gate && just e2e-vm full && just e2e-vm lacking`;
the loop runs it whole, a builder session never does. No new test, script, case or e2e target is added (no new cost); a fix
may add a regression test at the cheapest level that catches its cause, and says what it costs.

**Claims earlier features left to this checkpoint** (each is proven by a suite below, not by a new test; a builder who finds one
unproven writes the proof as a fix):
- Real polkit, journald, AppArmor and the Firefox snap on the socket: `snap-*` cases in `just e2e-vm full` (F179; SPEC
  acceptance 17, 18). Fail closed: `check-cases.sh` refuses a `snap-*` case reported skipped in a `full` VM run. In `lacking`
  every `snap-*` case is skipped with a reason (`e2e/vm/skip.list`; the route does not depend on the TPM kind, SPEC Design 6).
- The units inside the built `.deb`, `.rpm` and Arch package (tmpfiles entry, socket unit, user refresh units, `modutil`
  dependency, module ELF requirements against the snap base): `just package-gates` (acceptance 1, 12's units, 13).
- Package lifecycle scripts with the socket calls (F173/F174 notes: Arch upgrade leaves a running service stopped until the next
  connection; the container e2e on Arch may expect it running — fix at its cause if so): `just package-gates` and `just e2e`.
- Bus entries unchanged except for the transport field, and the bus half of the flood test (F175): the bus cases of `just e2e`
  on the real service and `just api-contract`.
- `PathChanged=` firing on a rename-replaced module (F184, inferred from systemd's inotify watch): **not** proven by an existing VM
  case. The builder checks whether a `snap-*` or registration case exercises it. If none does, it is written in `PROGRESS.md` as
  unverified and left for a person; no case is added for it here (a case would be a new VM test costing a full run).
- Acceptance 19 and 20 are a person's (`docs/manual-acceptance.md` section 25; the prose of the README, threat model,
  `SECURITY.md` and release notes). Not proven here and not claimed.

**What the checkpoint proves, and where**
- `just check`: lint, every unit and integration test, system gates and all script tests (acceptance 1–16 at their cheap levels:
  the label-source peer tests, unknown methods, polkit subject, overflow uid, journal fields, bounds, directory ownership,
  `SNAP_INSTANCE_NAME` in the module, the registration command on fixture homes, NSS tools on a registered profile, stale copy
  refresh, state-directory classification, exposure score, docs commands run as written). A red test is run alone first to see its cause.
- `just api-contract`; `just fuzz-smoke`. Its default list must equal the fuzz targets that exist: today 14 (`custodio-cli` 2:
  `nss_modules`, `profile_index`; `custodio-pkcs11` 1: `pkcs11_args`; `custodiod` 11). A target the list lacks is added to it.
- `just memory-safety` (Miri, ASan, fuzz build and its lints) on the M6 code (`register_*`, `browser_files`, the socket code,
  `snap_label`/handshake, the module's transport choice).
- `just e2e` with `E2E_TPM` unset: five targets (alma10, arch, debian13, fedora44, ubuntu2604) with `swtpm`, and debian13 also
  with `none`: six records. Every case id owed is accounted for exactly once per record. M6 added no container case, so the
  cases are those of M5; they must still pass with the socket unit, the tmpfiles entry and the user units installed. Old
  `target/e2e/` records of other targets (for example `ubuntu2404.*`) are removed before counting.
- `just package-gates` (package, parity, glibc ceiling, snap base fit, package lint). A lint list entry only with a reason and
  only for a finding that is not a defect.
- `just coverage-gate`: coverage and CRAP at unchanged thresholds over the code of F170–F186.
- `just e2e-vm full` and `just e2e-vm lacking` on the verified Ubuntu 26.04 minimal image: `full` runs the M5 cases and the 12
  `snap-*` cases; `lacking` runs the M5 cases and reports the 12 `snap-*` cases skipped. Records at
  `target/e2e/vm.<mode>.record`.

**Environment, checked while writing this contract** (results go in `PROGRESS.md` again at build time): `just vm-host-check`
reports OK for kvm-device, qemu, ovmf, swtpm, seed-tool, gpgv, keyring; `podman info` exit 0; `swtpm --version` 0.7.1 in the dev
container (the VM uses its own under `/opt/swtpm`); a previous `vm.full` run on this host recorded the snap step at 91 s. The
snap group needs network for the store (Firefox snap and content snaps); if KVM, podman, the network or the store is gone, or an
image cannot be pulled, that is `BLOCKED.md`, not a reason to skip a target, mode or case. Software emulation is never used. If
podman lost its pause process, `timeout 120 podman system migrate` is the known remedy. **A change in snapd's rules** (the observed
label is not `snap.firefox.*` in enforce mode, the socket unreachable from the confinement, the bus not denied) is never worked
around or skipped: the builder records what changed in `docs/findings/F187.md` and writes `BLOCKED.md` for a person.

**Time and budgets** (`budgets.tsv`, set by a person; the builder compares and never edits):
- `just check`: ~10–15 min cold; skipped on an unchanged tree through `target/check-ok` (`CHECK_FORCE=1` forces it).
- `just e2e`: six records at once, wall = the slowest. The last recorded debian13 swtpm run is 626 s against row 800 (none: no row
  of its own; alma10 540, fedora44 570, arch 480, ubuntu2604 530). No growth is expected. A target over its row is a `BLOCKED.md`
  request after the other steps are done; no case is removed or skipped to fit.
- `just package-gates`: the lifecycle scripts have their own rows (`script *` 120 s, others up to 250 s); a script over its row is
  reported the same way.
- `just coverage-gate`: run as `just coverage` then `just crap`, one per command, `timeout 1700`. M5's checkpoint did not
  record a time; the builder records both here. If `coverage` alone passes 25 min, say so in `PROGRESS.md` and ask in `BLOCKED.md`.
- `just e2e-vm full`: M5 measured 503 s against row 580; the snap step adds about 65–90 s (the install wait hides behind the other
  groups), so **570–590 s, at or over the row**. `just e2e-vm lacking`: 430 s measured against row 500; the snap cases are skipped
  there, so it fits. If `full` measures over 580, the builder finishes every other step and asks for roughly 1.2× the measured time in
  `BLOCKED.md`; the snaps are not removed, trimmed or cached unverified to fit. (SPEC allows caching snaps by revision only verified as
  snapd verifies them; not a first move.) The rows are "not read by the loop yet".
- Limits: a command runs at most 30 min and a session 45 min. Each step below is one command or a few short ones; the container
  `just e2e`, each coverage half and each VM mode get a command of their own with `timeout 1700`. No step runs the whole `verify`.
  A failure fixed here may take more than one session; a step stays ticked only if its evidence passed on the final tree.
