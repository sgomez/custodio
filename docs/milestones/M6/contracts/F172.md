# F172 — Research: native browser profiles and NSS registration with modutil

## Scope
Research only. It writes `docs/findings/F172.md` (headed `## F172`, under 5000 tokens, conclusion
first, each claim marked **verified** or **inferred**, ends with `Decision: ` lines), and its index
line in `docs/findings.md`. No product code, no change to `SPEC.md`, `docs/decisions.md` or
`e2e/`; the registration features read the `Decision:` lines. Probes are scratch scripts outside
the repository, not committed; the finding quotes commands and the lines of output. It settles
SPEC's open question "Profile locations" for native browsers (the snap's part is F171's) and
prepares the registration command (F1xx features that parse `profiles.ini`/`pkcs11.txt` and run
`modutil` read the list as data, so the finding ends with it as a table: browser, channel/package
variants, profile root(s), index files, lock files, NSS library the browser uses).

Environment, checked in this session:
- The dev container has `/usr/bin/modutil` and `/usr/bin/certutil`; `podman` 5.4.2 works and
  `docker.io/library/fedora:44` is pulled from the registry (the fedora44 target is built on it;
  `e2e/targets/fedora44/Containerfile` installs `nss-tools`). `curl` reaches github.com,
  ftp.mozilla.org and registry.fedoraproject.org, so Mozilla's and the derivatives' sources and
  docs can be read through subagents. No browser is installed and none is needed: the finding
  builds fixture profile directories by hand and runs `modutil` on them.
- Not shown yet: whether a real Firefox 147+ can be run here. If not, the XDG layout is taken from
  Mozilla's source/release notes and marked **inferred**, with the file and line read.

Cost: no new test, suite, e2e case or script in the repository, nothing in `e2e/*/cases.list`,
nothing touches `budgets.tsv`. Each probe is a few seconds (modutil on a temp dir); the fedora44
container run is about a minute (image already local or one pull). All commands run in the
foreground with `timeout`; outside material (Mozilla source, packaging of the derivatives,
distro package file lists) is read by subagents that return conclusions. The loop's `verify` is a
few greps, under a second. Package gates, install and lifecycle tests, `just e2e`: not run, and
nothing here is proven only by them.

The feature fits in five steps; no split.

## Steps
- [x] Native Firefox and Thunderbird layouts. From Mozilla's source or docs (file and line, or URL
      and version, quoted): the profile root of Firefox in the legacy `~/.mozilla/firefox` and the
      XDG location used since Firefox 147 (what is the exact path, what happens to an existing
      legacy profile, which is read when both exist, whether the Release/ESR/Beta/Developer/Nightly
      channels share a root or use `installs.ini` hashes and their own profiles), how `profiles.ini`
      (`[ProfileN]`, `Path`, `IsRelative`, `Default`, `[InstallHASH]`, `[General]`, `StartWithLastProfile`)
      and `installs.ini` list profiles including relative and absolute paths, and the same for
      Thunderbird (`~/.thunderbird`, its XDG analogue if any). Include the Debian/Fedora/Arch/Ubuntu
      packages' own choices (Debian `firefox-esr`, Fedora `firefox`, Flatpak and snap are out
      of scope: only a stated one-line reason each).
- [x] The derivatives. For LibreWolf, Floorp and Waterfox (and any other the step finds used on the
      five targets): profile root(s) (e.g. `~/.librewolf`, `~/.floorp`, `~/.waterfox`, XDG or
      not), the index files, whether they bundle their own NSS or use the system one, and how each
      is distributed (native, Flatpak, AppImage, snap) so the list says which are native and
      registrable. Each is included in the data list only if its path and index format are
      **verified** from a source read or **inferred** with a reason; one that cannot be established
      is listed as excluded with why.
- [x] `modutil` and `pkcs11.txt`, measured with the dev container's NSS tools (record the NSS
      version) on a fixture directory: creating an empty database (`certutil -N --empty-password -d sql:DIR`),
      `modutil -dbdir sql:DIR -add NAME -libfile PATH -force`, `-list`, `-delete NAME -force`, and what
      each leaves in `pkcs11.txt` (the `library=` key, `name=`, `NSS=` flags line, the exact bytes
      before and after); behaviour on a library path that does not exist, on a missing or read-only
      directory, on a name already present, on a second add of the same library under another name,
      and on a profile with no `pkcs11.txt` yet; whether `modutil` loads the library when adding
      (and so needs a working module or only a path); its exit codes; whether it rewrites the file
      atomically (rename or in place: strace or inode before/after) and what it locks while writing
      (`.lock`/`cert9.db` locks, the sqlite lock), so the contract of "an interruption leaves the
      old state or the new one" is known to hold or not; and whether the legacy `dbm:` database
      matters (Firefox has used `sql:` for years; state the version). Then the package that ships
      `modutil` per format: Debian/Ubuntu `libnss3-tools`, Fedora/RHEL/Alma `nss-tools`, Arch `nss`,
      each from the target's package manager or file list (**verified** in the fedora44 container
      with `rpm -qf $(command -v modutil)`, and in the dev container with `dpkg -S`; the Alma and
      Arch names by their file lists or package pages, **inferred** if not run).
- [x] Running browsers and the p11-kit test. (a) The profile lock a running Firefox/Thunderbird
      holds: on Linux the `lock` symlink (`hostname:+PID`) and `.parentlock`; from Mozilla's source
      how each is created and how a stale one is told from a live one (a symlink to a dead PID,
      `fcntl` lock on `.parentlock`); a fixture reproduction of each state (absent, stale symlink,
      live symlink to a running process, `.parentlock` flock-held by a second process) and the
      detection rule that classifies all of them correctly, with the command and result. (b) How the
      command recognises a system whose NSS loads p11-kit-proxy: in the fedora44 container (and,
      if the image can be pulled, alma10), the exact file or setting that makes it so
      (`/etc/pki/nssdb/pkcs11.txt`, the `p11-kit-proxy.so` entry in the system NSS database, or
      `nss-p11-kit-config`/`/usr/share/p11-kit/modules`), `modutil -list -dbdir sql:/etc/pki/nssdb`
      output there, and the same on the Debian, Ubuntu and Arch targets (where it must be absent),
      so the finding names one rule that is true on fedora44/alma10 and false on the others, and
      says what it reads (a path and a string) and from which database. State what Mozilla's own
      Firefox tarball does on those systems (bundled NSS, no system database read).
- [x] Write the finding: the conclusion first; a versions table (NSS, Firefox, Thunderbird, derivatives
      where read); the data list as a table the registration command reads; the `Decision: ` lines
      (profile roots in lookup order, index parsing rules, derivatives included/excluded, the `modutil`
      invocation and package per format, the lock-detection rule, the p11-kit rule); add its line to
      `docs/findings.md`; where a Decision conflicts with SPEC's Design 3 text, say so in the
      finding (and the evaluator decides whether a deviation is needed; do not edit SPEC); append
      `PROGRESS.md`; run `just quick`; commit `docs(F172): ...`.

## Evidence
- Firefox legacy and XDG roots (since 147), channels, `profiles.ini`/`installs.ini` format incl.
  relative/absolute paths → the quoted source lines or release-note URL with version, and a fixture
  `profiles.ini` + `installs.ini` parsed by hand in the finding showing the profile list the rule
  yields → a stated path list in lookup order, marked **verified** or **inferred** with reason; it
  would fail if the fixture rule yields a different list from the stated one.
- Thunderbird roots and index → same method → a table row, **verified** or **inferred**.
- LibreWolf, Floorp, Waterfox → source/packaging read per derivative → each a row with root, index,
  NSS source, distribution, included or excluded with reason.
- `modutil` add/delete/list and `pkcs11.txt` format → commands run on a fixture directory in the dev
  container, with NSS version and the `pkcs11.txt` lines before and after → the `library=` key
  shown, add idempotence behaviour, delete result, error cases and exit codes stated, **verified**.
  Negative control: a second `-add` of the same library under a different name, and an add of a
  nonexistent path, shown to behave as stated (so "recognised by the library path" in SPEC is
  necessary, not decoration).
- `modutil` locking and atomicity → inode/strace (or file listing) before and after a write, and a
  run against a database a second process holds locked → stated: atomic or not, and what blocks →
  **verified**; if not atomic, the Decision says the command must copy and swap the profile's
  `pkcs11.txt` itself or accept the stated risk.
- Packages per format → `dpkg -S`/`apt-file`-style output in the dev container, `rpm -qf` in the
  fedora44 container; Alma and Arch names with their source → `libnss3-tools`, `nss-tools`, `nss` each
  marked **verified** or **inferred**.
- Running-browser lock detection (`lock`, `.parentlock`) → fixture states (absent, stale, live,
  flock-held) and the rule's classification of each, with the command run → every state classified as
  stated; a wrong rule (checking only that the symlink exists) is shown misclassifying the stale one.
- p11-kit-proxy recognition → fedora44 (and alma10 if pulled) `modutil -list` / file content, and the
  same check on the dev container (Debian/Ubuntu family) → one rule, true on fedora44/alma10, false on
  the others; Arch and Mozilla-tarball behaviour **verified** or **inferred**, stated.
- Verify keywords and structure (`## F172`, the fifteen words, a **verified**/**inferred** mark, a
  `Decision: ` line, the index line) → the loop's `verify` command → exit 0.
- Index line in `docs/findings.md` and the file under 5000 tokens → `just quick`
  (`scripts/check-files.sh`) → green.
