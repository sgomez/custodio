# F50 — End-to-end refusal on Ubuntu 24.04 with dbus-daemon

## Scope
Built here (SPEC acceptance item 8; section 4 "Lifecycle cases", the refusal on a bus without `ProcessFD`):
- A target `ubuntu2404` (`e2e/targets/ubuntu2404/`: `Containerfile` from `ubuntu:24.04`, `install.sh`, `probe.sh`, `package.pattern`, `skip.list`) that boots
  Ubuntu 24.04 with systemd, real polkit and its **default** bus daemon, `dbus-daemon`. The image never installs `dbus-broker` and never contains the package.
- The harness learns a target that runs **only** the refusal case: the cases common to the other targets (`e2e/cases.list`) do not apply to it, its own case ids are
  the only ones accounted for, and the steps that need an installed service (service start, key import, `user.sh`, upgrade, lifecycle) do not run. How the target says so
  (a marker file, a mode) is the builder's choice, but it is a committed, tested property of the target directory and not an ad-hoc `if` on the target name in `guest.sh`.
  A target without the marker is unchanged. The refusal target needs no package N+1 and no old package; `run.sh` must not demand one for it.
- The refusal case (ids chosen by the builder, one per Evidence line below, registered in the target's own `cases.list`; a run that skips one or reports an unknown one fails
  by the existing accounting; no `skip.list` entry).
- `just e2e all` includes the target because it is a directory under `e2e/targets/`; the host test proves `all` runs it, and the real run below proves it passes.

Left for other features: the package's own bus check and its messages (F42 deb `preinst`/`bus-check.sh`, F43; this feature proves them on the real 24.04, it does not change them
unless the real run shows a defect, which is fixed with its own test), the runtime refusal in `custodiod` (acceptance 9, an integration test), `dbus-broker` on 24.04 as an
installable configuration (SPEC says it is not supported by this milestone's e2e; not run here), the polkit 124 source reading (F41, verdict A: 24.04 stays in the set).

Environment (run in the dev container, 2026-10-31): `podman pull docker.io/library/ubuntu:24.04` succeeds; in a container of it, `apt-get install systemd dbus polkitd` installs
`dbus 1.14.10-4ubuntu4.1` and `polkitd 124-2ubuntu1.24.04.4` (so the package's `polkitd (>= 124)` and `dbus-system-bus` dependencies are met by the image and the refusal cannot be an
unmet-dependency failure), `dbus-broker` is not installed, and `/usr/bin/busctl` exists. Rootless podman already boots systemd containers for the other five targets (F45-F49).
Nothing new is needed from the host. The builder confirms, in the booted image, which bus daemon the bus is (asked of the bus, as the other `probe.sh` do).

Size: about five steps; no split.

## Steps
- [x] Tests first, red: host tests (stub engine, like `scripts/test-e2e-host.sh` / `test-e2e-targets.sh`) for the target directory, the refusal-only marker, the case accounting
      (only the target's ids; the common ids are not required of it; an omitted id fails; other targets still require the common ids) and `all` including the target; a self-test of the
      refusal checks with fixtures, one control per rejection (see Evidence).
- [x] The refusal checks as a library with that self-test (run by the guest before it relies on it and by `just test-scripts`): functions that print one message per problem; the list
      of packaged files taken from the package file (`dpkg-deb -c`), not from the installed system.
- [x] The target directory and the refusal-only run: Containerfile (default `dbus-daemon`, polkit, `busctl`, no package), `install.sh` (the same `apt-get install -y` on the mounted file as
      ubuntu2604, but the tool's exit status and its stdout+stderr are returned to the guest, not discarded), `probe.sh`, and the guest's refusal section.
- [x] Run `just e2e ubuntu2404` until green. A failure is a defect of the case, or a real defect of the package (fix it with its own test; BLOCKED.md if it is a decision). Never weaken a check.
- [x] Update the docs that list the e2e targets/cases; a `docs/findings.md` entry only if the run showed something non-obvious. Real run, required: `just e2e all` (all six targets); paste the exit
      status, the new `E2E-CASE` lines and the observed values below into `PROGRESS.md`; run `verify`.

## Evidence
- Target boots 24.04 on its default `dbus-daemon` → real run → the target's record (`E2E-RECORD`, saved under `target/e2e/ubuntu2404.record`) has `bus-daemon=dbus-daemon`, a 1.14 version
  and a polkit 124 version; the Containerfile starts `FROM` `ubuntu:24.04` (verify's grep) and neither installs `dbus-broker` nor copies a package (host test, as for the other targets).
- The bus is up and really lacks `ProcessFD` before the install, so the refusal is for the right reason → real run → before installing, the case asks the running system bus for the credentials of
  the bus itself (the same query the package uses, but written separately in the test, not by sourcing `bus-check.sh`) and asserts the reply is a success and has no `ProcessFD` entry; `systemctl
  is-system-running` is running/degraded and `dbus.service` is active. Control: a fixture reply containing a `ProcessFD` entry, and one that is an error or empty (bus not up, which would
  make the package install with a "no bus" notice), are each rejected by the precondition check.
- Installing the `.deb` with apt fails, with a message naming `ProcessFD` → real run → `install.sh` on the mounted package exits non-zero; the captured stdout+stderr contains `ProcessFD`
  and the package script's own prefix (`custodio:`) and apt/dpkg's report that the pre-installation script failed (so the failure comes from the package's check, not from a dependency or
  network error: the output must not be an `E: Unable to locate`/`unmet dependencies` failure). The capture is non-empty. Controls: a fixture where the install exits 0, one where it exits
  non-zero with output not naming `ProcessFD`, and an empty output, are each rejected.
- No Custodio file is installed → real run → the non-directory entries of the package file are listed with `dpkg-deb -c` (count asserted > 0 and including `/usr/lib/custodio/custodiod`, the PKCS#11
  module, the unit and the D-Bus policy/service files); after the failed install none exists (`test -e` and `-L`), and neither does `/usr/lib/custodio` nor `/var/lib/custodio` (the
  directories the package owns; checked as paths, no shared system directory is judged). Control: a fixture tree with one packaged file left, and one with only `/usr/lib/custodio` left, are rejected.
  The builder records in `PROGRESS.md`, as a value observed in the run, whether the `custodio` account exists afterwards and whether `preinst` creates it only after the check passes; SPEC says
  no Custodio *file*, so an account would need a decision recorded, not a silent pass: if the check runs after account creation, it is a package defect to fix (the check comes first), unless the
  builder shows it cannot and writes BLOCKED.md.
- dpkg does not list the package as configured → real run → `dpkg-query -W -f '${db:Status-Status}' custodio` reports `not-installed` or fails with no such package, and `dpkg -s custodio` does not
  report `Status: install ok installed`; also not `half-configured`, `unpacked` or `half-installed` (the builder records the observed status in `PROGRESS.md`). `dpkg --audit` prints nothing for it.
  Control: fixtures with status `installed`, `half-configured`, `unpacked` and `half-installed` are each rejected, and `not-installed` passes.
- Nothing listens on `com.rfirma.Custodio1` → real run → after the failed install the name is not owned (`busctl --system list` lacks it), not activatable (`busctl --system list --activatable`
  lacks it), a call to it fails with a not-activatable / ServiceUnknown error, `systemctl cat custodio` fails (no unit), `systemctl is-active custodio` is not `active`, and no `custodiod` process
  exists (`pgrep -x custodiod` finds none). The case never starts, stops or reloads anything of Custodio (static check below). Controls: a fixture listing that contains the name (owned, and
  activatable), and a fixture with a live `custodiod` pid, are each rejected.
- The refusal is the package's doing, not the test's → static check → the refusal section and every file it calls (`install.sh`, the library) contain no `systemctl start|restart|stop|reload|daemon-reload`
  of the service, no `kill`/`pkill`, no `rm`/`dpkg --remove|--purge` of Custodio paths, no `dbus-broker` and no `ProcessFD`-providing change to the bus (no replacement of the bus daemon, no edit of bus
  configuration); the check fails if the section's markers are missing or the section is empty. Self-test fixtures: a section that runs `systemctl stop custodio`, one that runs `pkill custodiod`,
  one that removes `/usr/lib/custodio`, and one that installs `dbus-broker` each fail.
- The target runs only the refusal case → real run + host test → `target/e2e/ubuntu2404.log` has an `E2E-CASE` line "run" for every id of the target's `cases.list` and for no id of `e2e/cases.list`
  (host test: the accounting of a refusal-only target fails if it is given a common id, or lacks one of its own; the other targets still fail without the common ids). The guest's cases that need
  a service (key import, `user.sh`, upgrade, lifecycle) do not run on it (no `import.py` or `upgrade.sh` call in the refusal path; host test on the guest's structure).
- `just e2e all` includes it → host test (stub engine) + REQUIRED real `just e2e all` → the stub run with `all` execs the guest for `ubuntu2404` too; the real run exits 0 and prints
  "e2e: passed: " followed by all six targets (alma10 arch debian13 fedora44 ubuntu2404 ubuntu2604). The record of every target still shows its bus daemon and polkit version.
- Shellcheck and syntax → `just check`, `bash -n e2e/*.sh`; verify's greps (`ubuntu:24.04|noble` in the Containerfile, `ProcessFD` under `e2e`) hold but are not the proof: the real run is.
