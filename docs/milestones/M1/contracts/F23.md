# F23 — Miri, AddressSanitizer and fuzzing for the new FFI entry points

## Scope
Proves, with the tools the repository already has, that the FFI entry points added or changed by
F19–F22 are free of undefined behaviour and cannot be crashed by arbitrary arguments or call
orders. Production code changes only if a tool finds a bug, apart from these planned exceptions:
the `unsafe_code` lint attributes (below), a sign-call counter in `fake.rs`, widening the
visibility of the `SERIAL` lock in `ffi/tests.rs`, and one added line in the justfile `test` recipe (exact command under "Justfile").

- **Miri / ASan (unit tests).** `just miri` and `just asan` already run all `--lib` tests of
  `custodio-pkcs11`, which use the fake service. Nothing in them is gated off (no `cfg(miri)`, no
  `#[ignore]`; the builder confirms this and may not add either). What is added: tests in a new
  file `src/ffi/tests/sanitizers.rs` (a `mod sanitizers;` line in `ffi/tests.rs`; a new file keeps the
  existing ones under the 5000-token file gate), for the gaps in the Evidence table. Every new test
  below has the path `ffi::tests::sanitizers::<name>`. Tests that already
  cover a row are cited, not copied.
- **Fuzz target.** `ffi/fuzzing.rs` (`step`, `% 17` ops) gains: `C_SignUpdate`, `C_SignFinal`,
  `C_Login`, `C_Logout`; the composed mechanism types in the `C_SignInit` mechanism choice and in `C_GetMechanismInfo`:
  the three ECDSA ones (`CKM_ECDSA_SHA{256,384,512}`), which the fake supports, and the three RSA
  ones (`CKM_SHA{256,384,512}_RSA_PKCS`), which it must refuse;
  and the `C_Sign` op keeps its sizes. The `C_Sign` and `C_SignFinal` ops pass an output buffer that
  is either NULL or a `Vec<u8>` of exactly the length passed (never `storage()`, which rounds up to
  8 bytes, and never a larger allocation), so ASan sees a write one byte past `*len`. Any order, any sizes: every op is chosen from the script
  bytes with no state kept by the harness. If the file would exceed the token gate, the new ops go
  in `src/ffi/fuzzing/` submodule(s); the `--exclude` of `just crap` is then extended to those
  files only (the same harness-only exclusion that exists for `fuzzing.rs`) and `docs/decisions.md`
  is not touched. `fuzz/Cargo.toml` and `fuzz_targets/pkcs11_args.rs` stay as they are unless a
  second target is wanted (not planned).
- **`forbid(unsafe_code)` outside FFI.** Today the crate has no such attribute (only the doc
  comment in `lib.rs`; `ffi`, `unsupported` hold the `unsafe extern "C"` functions). Add
  `#![deny(unsafe_code)]` to `lib.rs`, `#![allow(unsafe_code)]` (with the comment justifying it) in
  `ffi.rs` and `unsupported.rs` only, and `#![forbid(unsafe_code)]` in `module.rs`, `composed.rs`,
  `token.rs`, `backend.rs` and `fake.rs`, and in `src/tests.rs` (a crate-root test module outside FFI,
  which would otherwise get only the `deny` from `lib.rs`; it holds no `unsafe` today). Test modules under
  `ffi/` inherit the FFI allowance. `module/` (including `module/tests/`) and `composed/` inherit
  `forbid` from their parent files `module.rs` and `composed.rs`, so they need no attribute of their own.
- **The fake has no RSA key.** `fake.rs` holds one P-256 key; the existing tests assert that
  `C_GetMechanismInfo` refuses `CKM_SHA{256,384,512}_RSA_PKCS` and that the list has 4 entries
  (`CKM_ECDSA` plus the 3 composed ECDSA types). Those assertions stay as they are. The FFI-level
  "composed" rows below therefore cover the 3 ECDSA composed types, and the RSA composed types are
  checked only as refused. This is enough for the sanitizers: the RSA-specific code (`DigestInfo`
  construction) lives in `composed.rs` and `module/signing.rs`, which are `forbid(unsafe_code)`, and
  it receives the same FFI buffers and lengths as the ECDSA path, already converted to safe slices
  before it runs. It is covered by the `module` tests that use their own RSA backend.
- **Sign-call counter.** `fake.rs` gains `pub static SIGN_CALLS: AtomicUsize` (`cfg(test)`, like `LAST_INPUT`), incremented by
  `FakeBackend::sign`. Tests read it as a before/after difference under the `SERIAL` lock.
- **Serialising the fuzzing tests.** `fuzzing::run` calls `C_Finalize` at its start and end, so
  `ffi::fuzzing::tests` must not overlap with `ffi::tests`, which holds `SERIAL` (private to
  `ffi::tests` today). `SERIAL` becomes `pub(in crate::ffi)`; every `fuzzing::tests` test takes it
  first (`super::super::tests::SERIAL`), poison-tolerant like `Session::new`, and holds it for the
  whole test, including its reads of `SIGN_CALLS` and `LAST_INPUT`. The pass is checked by running
  the whole lib suite with `--features fuzzing` and default threads, repeated 5 times.
- **Justfile.** One line is added to the `test` recipe, after `cargo test --workspace --locked`, which
  stays unchanged: `cargo test -p custodio-pkcs11 --features fuzzing --lib --locked`.
- **Environment.** The pinned nightly `nightly-2026-10-26` with `miri`, `rust-src` and
  `llvm-tools-preview` must be installed (`just setup` does it); earlier sessions could not run
  `just miri` for lack of it. If it cannot be installed (no network), write `BLOCKED.md`.

Left for other features: running the fuzzer for long (CI/nightly campaigns), the audit journal,
e2e. No change to `features.json`, `SPEC.md` or the justfile recipes `miri`, `asan`, `fuzz-build`,
`lint-fuzz`. The feature fits in six steps; no split.

- Arbitrary multi-part sequences in any order and with any sizes → **new** `ffi::fuzzing::tests::sequences_in_any_order`: every script uses `CKM_ECDSA_SHA256`, opens a session first, passes sign output buffers of 64 bytes, and the `sign` op passes a zero-length message, so a well-ordered operation succeeds. For every permutation of {init, update, final, sign} (24) and update sizes 0, 1, 129, 4096, plus a NULL part with length 0 and a NULL part with a non-zero length, the test runs the script through `fuzzing::run` and compares the final differences of `SIGN_CALLS` and `LAST_INPUT` with a reference model written in the test, following F21 (`contracts/F21.md`, `multipart_sign_after_update_is_rejected`, `sign_update_and_final_arguments`):
  - State: none, or active with a flag `updated`. `init` with none active starts an operation with `updated = false`; `init` while one is active is refused (`CKR_OPERATION_ACTIVE`) and changes nothing.
  - `update` needs an active operation, else refused. A part that reaches the module (valid pointer of any size, including size 0, or NULL with length 0) is appended and sets `updated = true`: an empty update counts as an update, so it forbids `C_Sign` afterwards. A NULL part with a non-zero length is `CKR_ARGUMENTS_BAD` raised by `ffi.rs` before the module; per F21 it leaves the operation exactly as it was, does not append and does not set `updated`. It does not end the operation (the buffer-too-small rule of PKCS#11 does not apply; F21's argument-error rule does).
  - `final` needs an active operation: it calls the service exactly once with the digest of the bytes appended so far (the empty digest if none) and ends the operation. Its failures other than a small buffer end the operation; none arises in these scripts.
  - `sign` needs an active operation. If `updated` is false it calls the service exactly once with the digest of its (empty) message and ends the operation. If `updated` is true it returns `CKR_OPERATION_ACTIVE`, makes no service call and ends the operation (so a later `final` is refused). A `sign` length query (NULL buffer) behaves the same as the full call after an update (ends the operation, no call); without an update it returns the length and leaves the operation active.
  - Every other call (no active operation) is refused and moves nothing.

  The model's count is asserted with `assert_eq!` for each permutation. Worked examples (update of 1 byte unless noted): init-update-final gives 1 (digest of the part); init-update-sign gives **0** (sign after update is refused); init-sign-update-final gives 1 (sign signs the empty message and ends the operation, update and final are refused; `LAST_INPUT` the empty digest); init-final-update-sign gives 1 (final over empty data, the rest refused); update-final-init-sign gives 1 (`LAST_INPUT` the empty digest); final-sign-update-init gives 0. Longer hand-listed scripts in the same test, with the model's answer asserted: init, update, sign, final gives 0 (sign after update ends the operation, final is refused); init, update, sign, init, final gives 1 with the empty digest (the new operation starts clean, which fails if the refused sign left the operation open: the second init would be refused and the final would sign the part); init, update with size 0, sign gives 0 (an empty update counts); init, update with a NULL part and length 0, sign gives 0; init, update with a NULL part and non-zero length, sign gives 1 (the failed update neither appended nor ended); init, update NULL/non-zero, update 1 byte, final gives 1 with the digest of that byte only; init, update, sign with a NULL buffer, final gives 0 (the query ended the operation); init, sign with a NULL buffer, update, final gives 1 (no update before the query, so it kept the operation and the final signs the part). `LAST_INPUT` is asserted equal to the model's digest whenever the count is 1, so an unwired update (digest of the empty string instead of the parts) fails. The test also ends with the module finalized (`C_Initialize` returns `CKR_OK`, then `C_Finalize`). If the module's real behaviour differs from the model, the builder decides which is right from SPEC.md and F20/F21, not by copying the observed number. Plus a deterministic xorshift set of 2000 random scripts of length ≤ 512 → no panic, no abort. Under Miri the counts shrink via `cfg!(miri)` to 24 permutations x sizes {0, 129} and 20 random scripts (a reduced loop count, not a skipped test; the hand-listed scripts always run). Per-op failure: init unwired → every count is 0, so init-update-final fails; update unwired → `LAST_INPUT` is the empty digest, fails; final unwired → init-update-final stays 0, fails; sign unwired → init-sign-update-final stays 0, fails. Mutation note (not committed, see the mutation list): if `Module::sign` accepts a sign after an update (the `updated` check removed), init-update-sign goes from 0 to 1 and init, update, sign, final from 0 to 1, and the test fails.
