# F96 — End-to-end upgrade keeps keys, owners and certificates

## Scope
Built: the existing `upgrade-*` cases (N to N+1, run in the main guest run, and `upgrade-oldpath-*`, run in the
old-path guest run; `e2e/upgrade.sh` serves both) are extended so that, before the package is replaced, the guest
holds keys for **two real accounts** and one certificate has been replaced; after the upgrade each account is checked.
Acceptance 10 of SPEC.md, end to end, for both builds (both built from this tree: F71).

Parts:
- A seed phase in the upgrade case, before `install.sh` of N+1: besides the two keys that already exist (alice's
  `rsa1`, `ec1`), a second ordinary account (bob, created with the same guarded `useradd` as `owner-run.sh`, after checking that no key is left under his uid by earlier steps (the old-path run has no bob), with its own logind session and test
  agent) imports a key of his own (at least one id that alice also has, to prove owners and not only ids), and one
  certificate is replaced with `ReplaceCertificate` on the package being upgraded from (so it must work on the
  old-path build too; if the old-path build cannot be called the same way, that is a finding for the builder, not a
  skip). Calls the CLI lacks are made with `e2e/owner-call.py`.
- A check phase after the upgrade, as each user, in his or her own session: `custodio list`, the PKCS#11 listing,
  the replaced certificate, and a signature with polkit.
- New cases are not added: the check phase is judged under the six existing ids of each prefix (`keys-listed`,
  `signs-with-polkit`, `state-unchanged`; the others as they are). Ids in `e2e/cases.list` stay; the builder may add
  ids only if the self-test and the catalog (`e2e/catalog-text.txt`) are updated with them.
- Every shell helper has a container-free test (`scripts/test-e2e-upgrade.sh`, in `just quick`) with bad-evidence
  cases, as the existing upgrade self-test.
- Placement: the lifecycle cases start from the state the upgrade leaves. Either the lifecycle's judgement is
  unchanged by bob's key (it compares listings and state before/after its own steps, so extra keys are neutral) or
  the seed keys are deleted by their owners at the end of the upgrade case; the builder picks and shows it. `'upgrade-*'` does not run the lifecycle cases; that choice is checked by one run of `just e2e-cases debian13 'lifecycle-*'` after the upgrade ones, or else at F100 (the builder says which in PROGRESS.md). The
  `journal` counts and `TOTAL` are not touched (the upgrade runs after them).

Not built: new service, CLI or module behaviour (F72, F78, F87 and their tests). Version, binary, service restart and
no-manual-step checks stay as F48/F61 built them (F71 owns the M3-only starting point). Package gates and `just e2e`
on all targets run at F90/F100.

Environment (run in this session): `podman run --rm --privileged --cgroupns=host alpine echo ok` → `ok`; the
`custodio-e2e-*` images exist, F91's `owner-*` cases already run two accounts with sessions and agents on debian13, so
the dev container can do it. The feature is about five steps; no split.

## Steps
- [x] Failing container-free tests first: the self-test and `scripts/test-e2e-upgrade.sh` judge the new evidence
      (per-account listing is exactly the expected ids, owners compared, the replaced certificate is the new one,
      one agent request per signature) with bad-evidence cases (a key of the other account in a list, an extra or
      missing key, the old certificate, a missing request); a mutant of each judgement goes red.
- [x] Seed phase (root orchestration, `upgrade.sh` and a user script): create bob, sessions and agents for alice and
      bob, import bob's key(s), replace one certificate on the old package with a new certificate for the same
      key, and record a snapshot per account before the install (ids from `custodio list`, certificate DER
      sha256 read through the module and through the service, state directory owner and mode of each file).
- [x] Check phase after the upgrade, for each account in its own session: its `custodio list` shows exactly
      its own ids (none of the other's), the replaced certificate is the new one and the others are unchanged
      (compared with the snapshot and with the DER that was replaced in), bob's state entries sit under `./<bob-uid>/` and alice's
      under `./<alice-uid>/` as before, with sha256, owner `custodio` and mode as before (the store keeps every file as the service
      account; the owner is the uid directory, SPEC section 2), and each signs through the PKCS#11 module with one request in that account's agent and the signature
      verifies against that account's public key and fails against the other's (the shared id included; with a denied signature still failing).
- [x] Run for both prefixes (`upgrade-*` and `upgrade-oldpath-*`, the second through the old-path guest run), update
      `e2e/catalog-text.txt` and the e2e docs if they describe what the cases prove; settle placement for the lifecycle.
- [x] Negative controls, wiring checks only (one run each, reverted; the judgement itself is covered by the self-test): (a) the replaced certificate is replaced back to the old one
      after the upgrade → the certificate check goes red; (b) bob's list is taken as alice → the
      "exactly its own keys" check goes red.
- [x] Run `just quick`, then `just e2e-cases debian13 'upgrade-*'` until it passes.

## Evidence
- Two accounts' keys exist and one certificate was replaced before the upgrade → seed output and the snapshot judged in
  `upgrade-keys-listed` (and `upgrade-oldpath-keys-listed`) → the snapshot holds alice's and bob's ids, a shared
  id for both, and the replaced certificate's hash differs from its original; fails if the seed was skipped.
- Each account lists exactly its own keys after the upgrade → `upgrade-keys-listed`, `upgrade-oldpath-keys-listed`
  → bob's shared-id key has its own key pair and subject; alice's `custodio list` (id plus subject) equals her set, bob's
  equals his, from his own session, and the certificate DER sha256 of the shared id (read through the module, per
  account) differs between them and equals the one recorded before the upgrade, so a service giving bob alice's key
  goes red; the listings equal those before;
  an extra, missing or foreign id fails (self-test bad-evidence cases; negative control b).
- Owners kept → `upgrade-state-unchanged`, `upgrade-oldpath-state-unchanged` → the state directory snapshot (path,
  sha256, owner, mode) is identical, including bob's entries under `./<bob-uid>/` (owner `custodio`, 0600); self-test
  bad-evidence case: a file that moved from `./<bob-uid>/` to `./<alice-uid>/` goes red. The behavioural proof of owners is
  the per-account listings and signatures below.
- The replaced certificate is the new one → `upgrade-keys-listed` / `upgrade-oldpath-keys-listed` → after the upgrade the
  certificate of that key, read through the module and through a DER-returning call of `owner-call.py` (the builder names the method, or adds a `cert ID` subcommand), equals the replacement and differs
  from the original; the others are unchanged (negative control a).
- Each account signs with polkit → `upgrade-signs-with-polkit`, `upgrade-oldpath-signs-with-polkit` → for alice and for
  bob, one signature makes exactly one request in that account's own agent log, verifies against that account's
  certificate (the new one for the replaced key) and fails against the other account's (the shared id included), a denied signature fails and is asked again.
- The rest of the upgrade is unchanged → `upgrade-version-greater`, `-service-new-binary`, `-no-manual-step` and the
  oldpath versions → still pass in the same run (F48/F61/F71 own their proofs).
- Judgements and mutants → `scripts/test-e2e-upgrade.sh` via `just quick` → exit 0.
- Whole feature → `just quick && just e2e-cases debian13 'upgrade-*'` → exit 0, all upgrade cases accounted for
  (the six of each prefix) and no other.
