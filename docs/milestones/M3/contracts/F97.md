# F97 — End-to-end CLI cases

## Scope
Built: the `cli-*` cases of `e2e/cases.list`, run by the e2e guest against the shipped package (service, `custodio` CLI, PKCS#11 module, real polkit and
logind, `pkttyagent` from the polkit package). They prove acceptance 11 of SPEC.md end to end. Placement follows the F93–F95 groups: a new step group `cli`
(`case_group` / `phase_runs` in `e2e/select.sh`, a step in `e2e/guest.sh` after `appid` and before `upgrade`), so that `just e2e-cases debian13 'cli-*'`
runs the setup and this step only. Every key the group makes is deleted by its owner at the end; root compares the state directory with the one at the start
(as `rd-run.sh` does), so TOTAL, the journal counts and the state the upgrade and lifecycle cases start from are as before.

Case ids (the builder may rename or split them, if `e2e/cases.list`, the self-tests and `scripts/test-e2e-select.sh` follow):
`cli-list-keys`, `cli-list-none`, `cli-delete-confirms`, `cli-delete-declined-confirmation`, `cli-delete-declined-polkit`, `cli-no-agent-precondition`,
`cli-import-pkttyagent`, `cli-import-pkttyagent-wrong-password`, `cli-delete-pkttyagent`.

Not built here, proven by the features that own them: the CLI's behaviour with a private bus, the error texts, the man page and "no terminal refuses"
(F87, F88), the arguments of `pkttyagent`, that it is stopped on interruption, and that it is not started without a terminal (F89, fake `pkttyagent`).
The F89 deviation (`--fallback`, `SPEC_DEVIATIONS.md`) is taken as it is: this feature only shows the real `pkttyagent` working when no agent is
registered. Package gates and `just e2e` on every target run at F90/F100; this feature runs on debian13 only, as its `verify` says.

Environment (run in this session): `podman run --rm --privileged --cgroupns=host alpine echo ok` → `ok`; the debian13 image has polkitd, `libpam-systemd`
and python3 (so a pty driver as `e2e/import.py` and `delete.py` is possible), `/usr/bin/pkttyagent` comes with polkit, and F91–F95 already run several
accounts with their own sessions on it. Not yet shown, and a step decides within these limits: the debian13 image answers every polkit authentication
with `pam_permit` (`e2e/targets/debian13/Containerfile`), so a typed password proves nothing there. The pkttyagent cases therefore give the account a known
password (`chpasswd`) and make PAM service `polkit-1` check it (`pam_unix`) for the duration of the step only, restoring the original file (judged
identical, also on failure, by an EXIT trap). If this cannot work in the guest, the step records why in `docs/findings.md` and the contract is amended
before going on; falling back to `pam_permit` is allowed only for the success cases and then the wrong-password case is dropped by a deviation, not silently.
The feature is about five steps; no split.

## Steps
- [x] Failing container-free tests first: a self-test of the judgements (`cli-lib.sh` or similar, with `scripts/test-e2e-cli.sh` in `test-scripts`, run by
      `just quick`) with bad-evidence cases for each judgement below (a list that lacks the type, the subject or the end date; a list of another account's
      key; "none" said while keys exist; a delete that left the key in the list, the module or the state; a decline with a request logged or a changed state;
      a pkttyagent case with an agent request, with a leftover `pkttyagent`, or with the PAM file changed), a mutant of each judgement that goes red, and the
      placement (order in `guest.sh`, `select.sh` group, ids in `cases.list`); `scripts/test-e2e-select.sh` knows the `cli-*` group.
- [x] Fixtures and the list cases: alice (her own session and test agent, as `rd-user.sh`) imports two keys of different types with certificates of known
      subject and end of validity; a fresh account with a session and no keys is the "none" case. Root judges the output against what OpenSSL says about
      the certificates.
- [x] The delete cases on a pty (agent approving, then agent denying, and the confirmation answered "no"), with snapshots of `custodio list`, the module and
      the state directory before and after, and the agent's request count.
- [x] The pkttyagent cases: a session of class user with **no** test agent, the PAM and password set-up with its EXIT-trap restore, a pty driver that answers
      the `.p12` prompt and the account-password prompt of `pkttyagent` separately (and "yes" at the delete confirmation), import and delete with the right
      password, import with a wrong one; leftover processes and the journal checked. Add the ids to `e2e/cases.list`, the group to `guest.sh` and `select.sh`.
- [x] Negative controls, wiring checks only (one run each, reverted; the judgements themselves are covered by the self-test): (a) the declined-confirmation
      case answered "yes" → red; (b) the test agent of the polkit-denied case left approving → red; (c) PAM left on `pam_permit` in the wrong-password case
      → red. Then `just quick`, and `just e2e-cases debian13 'cli-*'` until it passes; record the run in `PROGRESS.md`.

## Evidence
- `custodio list` prints each key with id, key type, subject and end of validity → `cli-list-keys` → for two keys of different types (RSA and EC) the output
  holds, per key, its id, its type, the subject and the end date that `openssl x509 -subject -enddate` gives for the certificate imported with it, and
  no other account's key; the self-test fails on output missing any one of the four, or showing another key's subject with this id.
- With no keys it says there are none and exits 0 → `cli-list-none` → for an account with no keys, while alice's list at the same time is non-empty: exit
  0 and the "none" message and no key block; the self-test fails on "none" with keys listed, or a non-zero exit.
- `delete` asks for confirmation, then polkit, and deletes → `cli-delete-confirms` → on a pty with an approving agent, the confirmation prompt (saying the
  key cannot be recovered) appears in the output before the answer is typed, the agent logs exactly one `delete` request after it, exit 0, and afterwards
  the id is gone from `custodio list`, from the module's tokens, and from the state directory (the other key's files unchanged); the self-test fails if
  any of the three still shows the key or the request count is not 1.
- Declining the confirmation deletes nothing and exits non-zero → `cli-delete-declined-confirmation` → answer "no": non-zero exit, zero requests in the
  agent's log (polkit was not asked), and list, module and state directory equal to the snapshots before.
- Declining polkit deletes nothing and exits non-zero → `cli-delete-declined-polkit` → confirmation answered, agent denying: non-zero exit, exactly one
  `delete` request, and list, module and state directory equal to the snapshots before. Control (b) shows this fails when the agent approves.
- No polkit agent is registered in the pkttyagent cases → `cli-no-agent-precondition` → in the session used by those cases the same import made over D-Bus
  without a terminal (`owner-call.py import`) is refused with an authorization error and creates no key, and no test-agent process runs as that user; so
  what the next cases pass through is `pkttyagent`, not a session agent.
- On a pty with no agent, `custodio import` asks for the account password through pkttyagent and succeeds when it is typed → `cli-import-pkttyagent` →
  the driver types the `.p12` password, sees the polkit prompt of `pkttyagent` (authentication for the import action, naming the account), types the
  account's real password; exit 0, the key is in `custodio list` and the module shows its token, and no `pkttyagent` process of the account remains after
  the CLI returned.
- The password is really checked → `cli-import-pkttyagent-wrong-password` → with PAM checking the password, a wrong account password gives non-zero
  exit, no key imported (list, module and state directory equal to before), and no leftover `pkttyagent`; the same call with the right password
  (`cli-import-pkttyagent`) succeeds, so it was the password. Control (c) shows this fails under `pam_permit`.
- `custodio delete` asks for the password through pkttyagent and succeeds when it is typed → `cli-delete-pkttyagent` → on a pty with no agent: the
  confirmation is answered "yes", the polkit prompt is answered with the account password; exit 0, the key is gone from list, module and state
  directory, no leftover `pkttyagent`.
- The step leaves the guest as it found it, and no secret leaks → the group's end checks in `cli-run.sh` (judged as `end:` problems under the last case
  that ran) → the state directory equals its start snapshot, `/etc/pam.d/polkit-1` is byte-identical to the original, and neither the `.p12` password
  nor the account password appears in the journal since the step started.
