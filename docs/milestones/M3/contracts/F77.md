# F77 — Delete leaves one journal entry and fails closed

## Scope
`DeleteKey` (`Custodio::delete_call`, F76 order: id bound → credentials → lookup → polkit → removal) gains the
journal entry. F74 already defines `OperationEntry::delete`, `DeleteOutcome`, the message id, the catalog entry and
`docs/audit.md`; this feature emits them and adds the "unusable" state.

- **When.** Once polkit has been asked, exactly one delete entry is submitted through the existing sink before the
  reply (on a worker thread like `sign_call`/`import_call`), with operation, the caller's uid and pid, the key id and
  the outcome: `deleted` (approved), `denied`, `authorization_unavailable` (polkit `Unavailable`/`BadSender`).
  Delete never emits `storage_failure`: marking the key unusable is in memory and cannot fail, and a removal
  failing after the entry went out cannot change the entry. `docs/audit.md` says so, the F74 doc comment on
  `DeleteOutcome::StorageFailure` (`operation.rs`) is corrected to match ("reserved; delete never emits it"), and
  the documentation test checks the statement.
  As for sign and import (`docs/decisions.md`, `docs/audit.md`): a missing sender or failed credentials lookup, once
  the id is valid, leaves one `authorization_unavailable` entry without uid and pid and returns
  `AuthorizationUnavailable` (no polkit). No entry and no sink call for `InvalidArgs` and `NoSuchKey` (M1/F76
  behaviour: refusals before authorization).
- **Order after approval (the fail-closed rule).** (1) The key is made unusable: from then on `Sign` for that
  owner and id fails `NoSuchKey` (no polkit asked), and a second `DeleteKey` fails `NoSuchKey`; (2) the entry is
  submitted; (3) only then the files are removed (F76 removal, key first). The mechanism is the builder's, but it
  must be in memory only (no file change), so that marking and restoring cannot fail. A sign already past its lookup completes with the key it holds (F76 rule,
  unchanged). While the key is unusable `ImportP12` of the same id still fails `KeyIdTaken` (the id is not free until
  the files are gone) and `ListKeys` does not show it (conservative: it is not usable).
- **Sink failure.** If the entry cannot be submitted, for any outcome, the call returns `AuditUnavailable`. For an
  approved delete the key is restored: it is listed, signs again (valid signature) and both files are
  byte-identical; nothing was removed. For `denied`/`unavailable` the key was never touched.
- **A deleted key never lacks an entry.** The files are removed only after a successful submission, so every
  removal is preceded by a `deleted` entry. If the removal then fails (`Internal`, F76 partial rules), the entry
  already says `deleted`; the key stays unusable for the life of the process (conservative: it is never usable
  again after an entry said it was deleted) and `docs/audit.md`/`docs/api.md` state this. A crash between the
  entry and the removal leaves the key present with a `deleted` entry; this is recorded as the accepted residual
  case in `docs/audit.md` ("Not guaranteed" or the delete section).
- **Concurrency.** Deletes of one owner+id are serialized from the lookup through the removal (or restore), so a
  second delete looks the key up only after the first has finished: if the first removed it, the second fails
  `NoSuchKey` without asking polkit and leaves no entry; if the first was denied, unavailable or failed on the sink,
  the key is still there and the second runs normally with its own one entry. Deletes of other ids or owners are
  not blocked by it. Sign and ListKeys are not serialized with it. Consequence: entries equal polkit asks.
- **Content.** Never certificate bytes, key bytes, data or signature: the entry model cannot hold them (F74); this
  feature proves it end to end.
- **Docs.** `docs/audit.md` delete section (outcomes as built, the unusable-then-submit-then-remove order, the
  residual cases) and `docs/api.md` `DeleteKey` (`AuditUnavailable` applies; order; remove the F76 wording that no
  entry is written). Documentation tests extended for any statement added.
- Left for other features: replace certificate entries (F78+); the entry model, catalog and docs table (F74);
  `DeleteKey` ordering, polkit and removal themselves (F76); e2e journal cases with a real agent and the packaged
  catalog (F90/F100). Size: about five steps; no split.

Environment: nothing beyond the dev container. Tests use the private `dbus-daemon`, the async polkit double with
`hold`/`on_request` of `tests/audit/bus.rs`, and `MemorySink`/`FailingSink`/the gate sink of `tests/audit/timing.rs`.
No new tool, network or privilege. Tests needing an unwritable store skip as root.

## Evidence
All rows in `tests/delete_audit.rs` unless stated; "entry" is what `MemorySink` recorded, decoded to its wire fields.
- Exactly one entry per outcome → `delete_entry_per_outcome`: approved → one entry operation `delete`, outcome
  `deleted`, the caller's uid and pid, the key id; Deny → `denied`; Unavailable and `BadSender` →
  `authorization_unavailable`. Each: `len() == 1`, literal field values, and the reply error as in F76. This is the single proof of
  polkit result → outcome and reply; a counting authorizer and sink show refusals give 0 asks and 0 entries.
- Missing sender / failed credentials → `delete_without_caller_leaves_unavailable_entry`: one
  `authorization_unavailable` entry with no uid/pid, `AuthorizationUnavailable`, polkit not asked, key kept.
- Refusals leave no entry → `delete_refusals_leave_no_entry`: bad ids, a missing id, another uid's id: sink count 0
  (also with the failing sink, which must not turn them into `AuditUnavailable`); the error is the F76 one.
- Order unusable → submit → remove → `delete_sign_during_entry_fails_no_such_key`: a gate sink holds the submission
  of an approved delete; while held, `Sign` for that id gives `NoSuchKey` with no polkit ask, a second `DeleteKey`
  gives `NoSuchKey`, `ListKeys` omits the id, `ImportP12` of the id gives `KeyIdTaken`, and both files are still on
  disk (checked while held, which also proves removal comes after the submission); the sink counts are `Delete` 1
  (held) and `Sign` 0 (refusal before authorization, no extra entry); when released the delete succeeds and the files are gone. Fails if the files are removed first or the key
  stays usable while the entry is pending.
- Failing sink restores → `delete_failing_sink_restores_key`: an approved delete with the failing sink replies
  `AuditUnavailable`; `<id>` and `<id>-cert` byte-identical; listed; `Sign` gives a valid signature (verified with
  the public key); a later delete with a working sink succeeds and leaves its one entry. Also for the sink failing
  on `denied` and `authorization_unavailable` (reply `AuditUnavailable`, key untouched, signs).
- A sign in progress → `sign_in_progress_survives_delete_audit`: a sign held in polkit after its lookup, a delete
  approved and finished with entry; the released sign returns a valid signature or `NoSuchKey`, never another error;
  the same with the failing sink (the delete fails `AuditUnavailable`, the sign still succeeds).
- Removal fails after the entry → `delete_removal_failure_keeps_key_unusable`, two sub-cases (skipped as root):
  (i) only the certificate cannot be removed (key file removed first per F76, certificate kept; the builder picks
  the means that makes just that removal fail and names it in the test); (ii) neither can be removed (store
  directory read-only). Each: reply `Internal`; exactly one `deleted` entry (entries == polkit asks == 1); `Sign`
  gives `NoSuchKey`; `ListKeys` omits the id in both states (stated in `docs/api.md`). Fails if the key is usable
  after an entry said `deleted`.
- Concurrency → `concurrent_deletes_one_entry`, at least 20 rounds, two same-uid deletes of one id: the polkit
  double holds the first ask; the test asserts the second delete has not reached polkit (ask count stays 1) until
  the first is released; then one success and one `NoSuchKey`, files gone. In every round the number of entries
  equals the number of polkit asks (1) and exactly one `deleted` entry exists. With the failing sink: the first
  replies `AuditUnavailable` and the key is restored; the second then runs (second ask, second failed submission,
  `AuditUnavailable`); entries submitted equal asks, no `deleted` entry is recorded, files are byte-identical, the
  key signs. A variant with different ids (or owners) shows they do not block each other.
- Content → `delete_entries_hold_no_secrets`: the whole datagram/fields of every delete entry (success, denied,
  failing) contain no certificate bytes, key bytes, data or signature (raw, hex, base64), with a negative control
  that plants such a string and is caught (as in `import_audit.rs`).
- Journal path → `journal_sink_datagram_for_delete` (extends `tests/audit/leaks.rs` style): a delete over the
  private bus with the journal sink gives a datagram with `CUSTODIO_OPERATION=delete`, the catalog `MESSAGE_ID`,
  uid, pid, key id and outcome.
- Docs → `docs/audit.md` and `docs/api.md` statements checked by their documentation tests (`cargo test -p custodiod
  docs`) and `just api-contract`; fails if the delete order, outcomes, the "never emits `storage_failure`" statement or `AuditUnavailable` are missing.
- Existing behaviour intact (F76 delete rows, sign, import, owners) → adapted tests pass in `just quick`.
- Mutants → `just mutants-diff F77`: no surviving mutant in the changed code (order mark/submit/remove, restore,
  outcome mapping, unusable checks in sign/list/delete).
