# F95 — End-to-end app-id cases

## Scope
Built: the `appid-*` cases of `e2e/cases.list`, run by the e2e guest against the shipped `custodio.service` (unchanged unit: ProtectProc=invisible,
PrivateUsers=yes, no capabilities) and the real journal. They prove acceptance 9 of SPEC.md with the source F67 decided on.

F67 decided **(c)**: the source is the caller's cgroup scope `app-flatpak-<escaped id>-<n>.scope` in `user@<uid>.service/app.slice`
(`docs/findings.md` `## F67`, `Decision: (c)`). The branch of this feature's description for decision (d) ("always could not be determined") does not
apply; the first step checks the `Decision:` line and marks nothing else conditional. `/.flatpak-info` is not used, so there is no file for a caller
to make a symlink or FIFO of.

Parts:
- A step group `appid` in `e2e/select.sh` (`case_group`, `phase_runs`), run by `guest.sh` after `journal-ops` and before `upgrade`, like F91-F94;
  `just e2e-cases debian13 'appid-*'` runs the setup and this step only, `just e2e` runs it too. It deletes every key it imports, so the state
  directory and `TOTAL` after the step are as before (shown, as F91-F94 do).
- The fake flatpak caller: a process of alice that is in a scope of her own user manager, named as flatpak names it (F67 did this with
  `systemd-run --user --scope`; how the builder starts it is its choice). The caller is the process that makes the bus call itself (no proxy), so
  the entry's `CUSTODIO_PID` is its pid, known to the harness (the F94 pattern: wrapper or client printing its pid). Callers, each with its scope:
  - a valid id with `.`, `_` and `-` (the `-` is `\x2d` in the scope name) → `read`;
  - not in a flatpak scope: an ordinary session process, and a process in `app-gnome-<x>-<n>.scope` → `none`;
  - hostile sources, all `undetermined`: names that fail the rules of the F67 reader format (not exactly one `-` before the instance, an instance not
    1-10 digits, an escape other than `\x2d`, an id that fails flatpak's id rules, a 255-byte name that is also invalid), and an over-the-cap caller
    (below). At least one invalid-id caller must remain whatever else is dropped; with none, the builder writes `BLOCKED.md` (acceptance 9's hostile
    part would have no real-source evidence).
  - the edge of the bound: a name of exactly 255 bytes that is otherwise valid (id built to fit, checked against the reader's own rules) → `read`
    with the id. Linux accepts a cgroup name of 256 bytes (probe in the guest, see Amendments), so the 256-byte caller (name over the bound, otherwise
    valid) is a hostile `undetermined` caller, and "oversized" is covered for real by the 255/256 pair; the rest by F81.
  - over the cap: the root-side script creates `app.slice` children until their count exceeds the cap (`MAX_CHILDREN` of `app_id_source`, read from the
    code, not retyped), then picks the caller's scope name (varying the instance digits, removing candidates that do not qualify) so that its position
    in `os.listdir` of `app.slice` (kernfs order, the order the scan walks) is after the cap-th child; it then gets `undetermined`. The same script
    asserts the position before the call, so the expectation derives from the order, not from creation order. A second variant (a valid caller
    listed within the first cap children while the count is over the cap) → `read`, showing the cap bounds the walk and not the count. The extra
    children are removed after these cases, their absence is asserted, and every other case runs only while they are gone.
  - hostile scopes are made without systemd: alice's `mkdir` in `app.slice` plus writing the pid to `cgroup.procs`, by a caller that writes nothing
    to the journal, so the user manager logs no unit name for them.
- Operations: the full matrix of states is run with **sign** (cheapest, approved and denied). Import, replace certificate and delete are run once each
  as the valid-id flatpak caller (entry `read` with the id) and once as a non-sandboxed caller is not repeated: F82's audit tests own "every
  operation × three states" with the fake source; here only the real unit and the real cgroup source matter, which the one call per operation
  shows reaches the shared lookup.
- Container-free tests of every new shell/Python helper and judgement, with bad-evidence cases that must fail (`scripts/test-e2e-*.sh`, run by
  `just quick`), as F91-F94 do. The judgement reuses `e2e/jo.py` (ledger, window by marker cursors, `docs/audit.md` query extraction, `journal.py sweep`)
  rather than copying it; extending them is allowed.

Not built, owned elsewhere:
- The reader's parsing, validation, bounds and deadline at unit level, including symlink, FIFO, oversized `cgroup.procs`, too many children and a
  stuck read: F81 (`app_id_source` tests). A cgroup filesystem cannot hold a symlink, a FIFO or a file of other size as `cgroup.procs`; the first
  builder step records the command that tries to make a symlink and a FIFO in the caller's `app.slice` in the guest and its refusal. The cases
  here cover what that tree can hold: hostile names and a hostile count. The deadline itself cannot be made to fire from a real tree (a read of
  `cgroup.procs` does not block), so "within the bound" is proven here as an upper limit of the call's wall time, and the deadline by F81.
- The entries' fields, outcomes, forbidden content and the other queries of `docs/audit.md`: F94 (`journal-ops-*`), which does not use app-id callers.
- Outcome and polkit subject unaffected by the app-id at unit level: F82 (the fake source). Here the same is shown against the real source.
- Package gates, other targets (F90, F100).
The feature is about five steps; no split.

Environment (run in this session): `podman run --rm --privileged --cgroupns=host alpine echo ok` → `ok`; six local `custodio-e2e-*` images exist.
The dev container has no journal and no systemd user manager, so what needs them is the first guest-side step: (1) alice's user manager lets her
start a scope named `app-flatpak-…` (F67 did) and she can also create a child directory of her `app.slice` herself (needed for the over-the-cap
caller; if she cannot, the over-cap case is dropped and the cap is left to F81, with a note in PROGRESS.md); (2) the direct path
`/sys/fs/cgroup/<prefix>/user.slice/user-<uid>.slice/user@<uid>.service/app.slice` is what F81's `tree_root` finds in the guest — shown by a
`read` entry. If (1) fails for a hostile name, that name is dropped with a note; if no scope can be made at all, the step cannot be built and the
builder writes `BLOCKED.md`.

## Steps
- [x] Failing container-free tests first: `select.sh` maps `appid-*` to the group `appid` (other groups unchanged), `phase_runs` is true only when a
      case of the group is selected, the accounting reports each case exactly once, `guest.sh` runs the step after `journal-ops` and before
      `upgrade`. Add the ids to `e2e/cases.list`. Check `docs/findings.md` `## F67` ends in `Decision: (c)`.
- [x] First, in the guest: record in PROGRESS.md the results of the environment checks above (scope by alice with a flatpak-style name; her
      attempt to make a symlink and a FIFO in `app.slice`; her mkdir of a child of `app.slice`; the app-id entry of one real call).
- [x] Judgement library and self-test as functions of files (ledger with the expected app-id state and id per call, `journalctl -o json` / export,
      call durations), each with bad-evidence cases that must fail: wrong state; `CUSTODIO_APP_ID` present with `none`/`undetermined` or absent with
      `read`; wrong id; a hostile-name marker found anywhere in the full export (any field, any unit) of the window; outcome differing from the
      ledger's; wall time above the limit; entry count not equal to ledger lines; the documented app-id queries (by id, `read`, `none`, `undetermined`,
      extracted from `docs/audit.md`, placeholders replaced, window bound added) returning anything but exactly the ledger's prediction.
- [x] Guest side: alice's session and test agent, the callers above, marker entries before and after, one ledger of calls (caller kind, operation,
      approve/deny, expected state, id, outcome), every key deleted at the end; the root-side script that makes fixtures and judges, wired into
      `guest.sh`.
- [x] Negative controls (run, shown red, reverted): (a) the valid caller run outside its scope (state `none`, the case expecting `read` fails);
      (b) one hostile name made valid (state `read`, expecting `undetermined` fails); (c) the sweep fed a copy of the export with the hostile name
      appended to a MESSAGE (fails, kind and field only); (d) the limit on wall time lowered to zero (fails). Then `just quick` and
      `just e2e-cases debian13 'appid-*'` until both pass.

## Evidence
- The cases are in `e2e/cases.list`, reported exactly once each, and the selection reaches only their step → `scripts/test-e2e-select.sh` and
  the accounting tests (via `just quick`) → pass; a case missing from the guest output fails.
- Each judgement fails on bad evidence → the new `scripts/test-e2e-*.sh` self-test (via `just quick`) → passes; its mutants are caught: state
  compared loosely, id not compared, "no app-id field with `none`/`undetermined`" dropped, sweep of the full export reduced to some fields,
  duration check dropped, an unknown documented app-id query ignored instead of failing.
- A fake flatpak caller gets an entry naming its app-id → case `appid-flatpak` → alice's sign call from a process in
  `app-flatpak-<escaped>-<n>.scope` (id with `.`, `_`, `-`) leaves exactly one entry with `CUSTODIO_APP_ID_STATE=read`, `CUSTODIO_APP_ID` equal
  to the unescaped id, `CUSTODIO_UID` alice's, `CUSTODIO_PID` the caller's pid, outcome `signed`; the same with the agent denying gives `denied`
  with the same app-id. Control (a) fails it.
- The edge of the name bound → case `appid-flatpak-max` → the valid 255-byte scope gives `read` with its id; the 256-byte caller (same id rules, one byte longer) gives `undetermined` (in `appid-hostile`); the `mkdir` of 256 bytes is recorded as accepted.
- The cap bounds the walk → case `appid-cap` → the caller listed within the first cap children while the count is over the cap gives `read`, the one
  listed after gives `undetermined`; the positions asserted from `os.listdir`.
- The app-id on every operation → case `appid-operations` → as the same caller: import (stored), replace certificate (replaced) and delete
  (deleted) each leave one entry with state `read` and the id.
- A non-sandboxed caller gets `none` → case `appid-none` → an ordinary session process, and a process in `app-gnome-…scope` of the same
  `app.slice`, each leave an entry with `CUSTODIO_APP_ID_STATE=none` and no `CUSTODIO_APP_ID` field, outcome as expected.
- A hostile source gives `undetermined`, copies no invalid text → case `appid-hostile` → for each hostile caller of Scope (names failing the
  format rules, the invalid 255-byte name, the over-cap caller listed after the cap) the entry has `CUSTODIO_APP_ID_STATE=undetermined` and no `CUSTODIO_APP_ID`; a marker
  string unique to each hostile name (and its escaped and unescaped forms) is found nowhere in the full journal export of the window: no
  field of any entry, no `MESSAGE`, no unit, with no exclusion: the hostile scopes are made without systemd, so a correct build gives a clean
  sweep (shown first, before any control). If that shows records of alice's user manager naming the scope, the builder instead excludes exactly
  records of that manager (its `_PID`, `_COMM=systemd`), says so in the judgement and its self-test, and every other record is judged. The 255-byte
  valid name is not a hostile marker (it is `read`; its id appears in the entry only). Control (b) and (c) fail it; (c) must go red whichever
  variant is used. Symlink, FIFO and oversized file: not possible in the cgroup
  tree (command and refusal recorded in PROGRESS.md); proven at unit level by F81, listed in Scope.
- The outcome is unaffected → case `appid-outcome` → for the valid, the `none` and every hostile caller, a sign approved gives a signature that
  verifies against the key's certificate and a sign denied gives the denial; the number of agent requests per call is one and equals what the
  non-sandboxed caller's calls get; the polkit subject in the agent's log (pid and uid of the caller) equals the entry's `CUSTODIO_PID` and
  `CUSTODIO_UID`, whatever the state.
- The call returns within the documented bound → case `appid-bound` → the wall time of every call of the step, hostile ones included (the over-cap
  caller is the heaviest), is at most the documented lookup bound (1 s, `LOOKUP_DEADLINE` of `docs/audit.md`, read from the document) plus a
  slack that is a per-call maximum, not a margin over a median: the largest wall time among the non-sandboxed caller's calls measured in the same
  step (not assumed), checked to be below a stated absolute figure so it cannot grow the limit unnoticed. Only control (d) (the limit set to zero)
  turns it red. That the
  deadline itself fires: F81, in Scope.
- Entries are queryable by app-id → case `appid-queries` → the queries of `docs/audit.md` for a given app-id and for `read`, `none` and
  `undetermined`, with placeholders replaced and the window bound added, return exactly the entries the ledger predicts (set equality; empty for
  an id no call used); the step fails if `docs/audit.md` holds an app-id query it does not judge.
- Whole feature → `just quick && just e2e-cases debian13 'appid-*'` → exit 0, accounting lists the `appid-*` cases and no other, and the state
  directory and `TOTAL` after the step equal those before.

## Amendments
- Facts from the guest (debian13, run as `podman run … custodio-e2e-debian13`, probes in PROGRESS.md), none weakens a gate: (1) alice's `mkdir` of a 256-byte
  child of her `app.slice` succeeds (the contract assumed a refusal), so the oversized name is tested for real: the 256-byte caller expects `undetermined` and
  the `appid-flatpak-max` evidence changes as above (stricter, not weaker); (2) alice can write a pid to `cgroup.procs` of her own child only from a process
  inside her user manager's subtree, so every hostile caller starts as `systemd-run --user --scope` and moves itself, with the hostile name read from a file
  (`systemd-run` logs its command line, so a name on it would reach the journal); (3) a process in a user-manager scope belongs to no logind session, and polkit
  finds the agent only through the user's display session, which exists only for a session of class `user`: the step opens alice's sessions with
  `XDG_SESSION_CLASS=user` (`su -l` keeps it), otherwise every approved call from a scope is `PolkitDenied`; (4) the agent logs the polkit subject (`polkit.subject-pid`) in a
  new file beside `requests`, so `appid-outcome` compares it with the ledger's pid.
