## F172

Native browser profiles and NSS registration with `modutil` (SPEC Design 3 "Native browsers"; open question "Profile
locations"). Probes were scratch scripts run 2026-11-12 in the dev container (Debian 13, NSS 3.110, `libnss3-tools
2:3.110-1+deb13u5`) and in podman containers `fedora:44`, `almalinux:10`, `archlinux:latest`, `ubuntu:26.04`. Mozilla's
source was read at `mozilla-firefox/firefox` `main` (and tag `FIREFOX_147_0_RELEASE`) by a subagent; no browser was run.

### Conclusion

1. **Firefox root.** Since 147 the root is `${XDG_CONFIG_HOME:-$HOME/.config}/mozilla/firefox`, but the legacy
   `~/.mozilla/firefox` is used when it exists (nothing migrates; both present: legacy wins). Both hold `profiles.ini` and
   `installs.ini` (**verified**, source: `GetLegacyOrXDGHomePath`: `if (exists || IsForceLegacyHome() || aForceLegacy)`
   returns the legacy dir; release notes 147.0: "Firefox now supports the Freedesktop.org XDG Base Directory
   Specification"). All channels share one root; they differ by `[InstallHASH]` and profile name
   (`default-release`, `default-esr`, `dev-edition-default`; the first two **inferred** from `default-%s`).
2. **Thunderbird**: `~/.thunderbird` if it exists, else `$XDG_CONFIG_HOME/thunderbird` (bug 2081031 shows a 157.0.1 profile
   there) (**inferred**: toolkit code is shared, comm-central not read). Same index format.
3. **Derivatives.** Include LibreWolf (`~/.librewolf` only if it has `profiles.ini`, else `~/.config/librewolf/librewolf`,
   **verified** from its `xdg-dir.patch`), Floorp (`~/.floorp`, **inferred** from its Flatpak manifest) and Waterfox
   (`~/.waterfox`, **verified**: `MOZ_APP_PROFILE` disables XDG). Only LibreWolf is in a distribution (Arch `extra`); all
   three are otherwise tarball/PPA/Flatpak, so they matter only when a person unpacked or installed them natively.
4. **`modutil`** (measured on NSS 3.110) **writes `pkcs11.txt` by itself and does not
   reliably dedupe by library.** A second `-add` of an already registered library under another name *renames* the entry
   for `p11-kit-proxy.so` but fails with rc 22 for Custodio's own module and `libnssckbi.so` (entry unchanged); adding an
   existing *name* with a different library fails (rc 22, misleading text); delete + add moves the entry to the end. The write is not atomic
   (below), so the command runs `modutil` on a scratch copy of the profile's three database files and renames the
   result over `pkcs11.txt`. A stale Custodio entry is updated by `-delete NAME` then `-add NAME` on that copy: "updated in
   place" is read as "not duplicated", the position is not kept (**SPEC conflict**, see below).
5. **Lock.** A profile is held if the `lock` symlink points to `IP:+PID` of a live local process, or any other host's
   address, or is unparseable, or if an `fcntl` write lock on `.parentlock` cannot be taken. The mere presence of `lock`
   or `.parentlock` proves nothing (both are left behind) (**verified** by fixtures).
6. **p11-kit.** The rule is: `modutil -list` of a new database (`modutil -create`) lists `p11-kit-proxy`. True on fedora44
   (**verified** with the command's two calls, NSS 3.133, `fedora:44` container, issue #32) and alma10 (**verified** only
   on a `certutil -N` database), false on Debian, Ubuntu, Arch (**verified**). That `/etc/crypto-policies/back-ends/nss.config` holds
   `library=p11-kit-proxy.so` does not prove NSS reads it: Ubuntu's `crypto-policies` ships the file and its NSS ignores it
   (**verified**, Ubuntu 26.04.1; corrected by issue #32, which replaced a rule based on the file).

### Evidence: Mozilla source (subagent; **verified** unless marked)

- `profiles.ini`: `[General]` `StartWithLastProfile`, `Version=2`; `[ProfileN]` needs `Name` and `Path`, read until
  `IsRelative` is missing; `IsRelative=1` resolves against the directory of `profiles.ini`, else `Path` is absolute;
  `[InstallHASH]` has `Default=<path>` (relative to the same directory) and `Locked=1`. `installs.ini` is read back only
  for an old profiles.ini; with `Version=2` the install sections live in `profiles.ini`.
- Fixture (`profiles.ini` in `/tmp/w/pi`: `[Profile1] IsRelative=0 Path=/tmp/w/pi-abs`, `[Profile0] IsRelative=1
  Path=abc.default-release`, `[Install4F96D1932A9F858E] Default=abc.default-release`), rule applied:
  `['/tmp/w/pi-abs', '/tmp/w/pi/abc.default-release']`: two profiles, the install default not repeated.
- `MOZ_LEGACY_HOME=1` forces legacy; `XDG_CONFIG_HOME` is honoured when set and non-empty.
- Lock source (`nsProfileLock.cpp`): `.parentlock` is taken with `fcntl(F_SETLK)`; the legacy symlink is
  `inet_ntoa(PR_GetHostByName(hostname))` + `":+"` + pid (127.0.0.1 if the lookup fails). Stale: same address and
  `kill(pid,0)` fails with `ESRCH`; "Remote lock: give up even if stuck" when the address differs; unparseable counts
  as stale in Firefox (the command is stricter: held).
- Packaging: Debian `firefox-esr` 153.7.0esr-1, Fedora `firefox` 160.0 and Arch `firefox` 160.0 have no profile-dir
  patch (Arch: **inferred**). Debian trixie builds with bundled NSS (`DIST` filter), Fedora and Arch with
  `--with-system-nss` (Fedora spec `%global system_nss 1`). Snap: `MOZ_LEGACY_HOME: 1`, `HOME=$SNAP_USER_COMMON` (F171).
  Flatpak (`~/.var/app/...`) is out of scope: the sandbox cannot load a host module path.

### Evidence: `modutil` (dev container, NSS 3.110, fixture `certutil -N --empty-password -d sql:DIR`)

| Case | Result |
|---|---|
| `-add x -libfile L -force` | rc 0; appends `library=L`, `name=x`, blank line to `pkcs11.txt`; bytes before: the internal module 4 lines |
| `-add` nonexistent path | rc 22 `cannot open shared object file`; file unchanged (negative control) |
| `-add` junk file | rc 22 `file too short`; unchanged |
| second `-add two -libfile L` after `one`, L = `p11-kit-proxy.so` | rc 0; `one` is replaced by `two` |

| entry whose library file was deleted: `-list` / `-delete cust -force` / `-add cust -libfile NEW` | all rc 0 (no load on delete); `cust` ends last, after the other entries (**verified**) |
| `-add one -libfile L2`, `one` exists | rc 22 `Failure to load dynamic library`; unchanged |
| a,b,c with 3 names of the same `p11-kit-proxy.so` | after each add only the last name remains |
| `-delete b` + `-add b` of a middle entry `b` among `Internal,b,c` | `Internal,c,b`: the entry moves last |
| `-delete nope` | rc 26 |
| no `pkcs11.txt` in an existing dir | rc 0; creates `cert9.db`, `key4.db`, `pkcs11.txt` |
| dir missing | rc 46 `SEC_ERROR_BAD_DATABASE`; nothing created |
| dir read-only (0500) | rc 22 `File not found` |
| `-dbdir dbm:DIR` on an sql dir | rc 46 `SEC_ERROR_LEGACY_DATABASE`; Firefox uses `sql:` (`cert9.db`) since 58, so `dbm:` is ignored |
| relative `-libfile p11-kit-proxy.so` | accepted, stored as written (loaded by the search path) |
| hand-added entry with `parameters=` and `NSS=` lines | kept verbatim after another add |

- `modutil` **dlopens the library** when adding (a path that does not load fails), so Custodio must be installed
  and loadable. It prints a confirmation prompt when the library is `p11-kit-proxy.so` (and on Fedora/Alma for any add, as
  p11-kit is then enabled): the command runs it with stdin from `/dev/null` (EOF continues, **verified**: rc 0 and the entry written).
- **No `pkcs11.txt` yet: the swap is wrong.** With `cert9.db`/`key4.db` but no `pkcs11.txt`, `modutil` run on a scratch copy writes
  `configdir='sql:SCRATCH'` into the internal module line; after `mv -T` and `rm -rf SCRATCH` the profile's `-list` prints
  nothing useful (bad database), so the command runs `modutil -dbdir sql:PROFILE` directly there (rc 0, `-list` shows
  `NSS Internal` and `cust`, `configdir='sql:PROFILE'`); an empty directory too creates all three files, rc 0. There is no old
  module state to lose, so atomicity is not needed (**verified**).
- **Atomicity: no.** An inotify watch on the directory during `-delete x`: `CREATE pkcs11.txu`, `MODIFY`, `CLOSE_WRITE
  pkcs11.txu`, `DELETE pkcs11.txt`, `MOVED_FROM pkcs11.txu`, `MOVED_TO pkcs11.txt`. The inode changes (6529 to 6536). There is
  a window where `pkcs11.txt` does not exist and `-add` also rewrites it in place once; an interruption in that window loses
  every other module of the profile. Locking: `modutil` takes no lock file of its own; with an exclusive sqlite lock on
  `cert9.db` held by another process, `-add` failed after 2 s, rc 46 `CKR_GENERAL_ERROR`, file unchanged.
- Packages: `dpkg -S` here: `libnss3-tools: /usr/bin/modutil`; Ubuntu 26.04 (3.120-1ubuntu2.2) same; `rpm -qf` in fedora44:
  `nss-tools-3.133.0-1.fc44`; almalinux:10: `nss-tools-3.124.0-5.el10_0`; archlinux: `pacman -Qo`: `nss 3.133-1` (all **verified**).

- **Scratch copy and swap (fixture, **verified**), only for a profile that has `cert9.db`, `key4.db` and `pkcs11.txt`.**
  `cp -p` of exactly those three files into SCRATCH (the profile also held `prefs.js`; same filesystem, so `rename` is atomic),
  `modutil -dbdir sql:SCRATCH -add ...` rc 0, then `mv -T SCRATCH/pkcs11.txt PROFILE/pkcs11.txt` (a `rename(2)`); `-list`
  on the profile then shows `1. NSS Internal`, `2. base`, `3. pk`. `-add` changes only `pkcs11.txt`: `sha256` of `cert9.db`
  and `key4.db` are identical before and after (so only that one file is swapped). The internal module's
  `configdir='sql:/original/path'` is kept verbatim, not rewritten to the scratch path. `modutil` killed (SIGKILL) while
  working on the scratch copy leaves the profile's `pkcs11.txt` untouched (3 `name=` entries as before). Residual risk: the
  swap needs the profile free (lock rule) because a browser writing `pkcs11.txt` between the copy and the rename would be
  overwritten; the scratch directory left by an interruption is deleted by the next run.

### Evidence: p11-kit

- fedora44 (nss 3.133) and alma10 (nss 3.124): `strings libnss3.so` contains `/etc/crypto-policies/back-ends/nss.config`
  inside a built-in `name="Policy File" ... NSS="flags=internal,moduleDB,skipFirst,moduleDBOnly,critical"` module line, and
  that file (crypto-policies) holds `library=p11-kit-proxy.so`, `name=p11-kit-proxy`. A fresh profile database
  (`certutil -N`, no p11-kit entry in it) lists `2. p11-kit-proxy`. So it is the NSS library, not the database
  `/etc/pki/nssdb` (whose `pkcs11.txt` only names `libnsssysinit.so`), that loads the proxy into every database, including a
  native Firefox's profile: Fedora's firefox links the system `nss` (`--with-system-nss`).
- Debian 13, Ubuntu 26.04, Arch: no `/etc/crypto-policies`; a fresh database lists only the internal module; the Debian
  `libnss3` has no such string (all **verified**). Mozilla's tarball bundles NSS: **inferred** that it does not read the file.
- Ubuntu 26.04.1 with `crypto-policies 20251128.git19878fe-0ubuntu4` (issue #32): `nss.config` is a symlink to
  `/usr/share/crypto-policies/DEFAULT/nss.txt` with `library=p11-kit-proxy.so`, yet `strings -a` over every `.so` of
  `libnss3` 3.120-1ubuntu2.2 finds no `crypto-policies`, `back-ends` or `nss.config` (only `/etc/nss/params.config`), nor
  does Firefox's bundled `/usr/lib/firefox/libnss3.so`; a fresh database lists only `NSS Internal PKCS #11 Module`;
  Firefox 160 (deb), headless on a scratch profile, maps only its bundled `libnss3.so`/`libsoftokn3.so`, no
  `p11-kit-proxy` (all **verified**). Debian's `crypto-policies` was not checked; Ubuntu's derives from it.
- Debian trixie `firefox-esr` bundles NSS but the registration still works: the entry goes in the profile.

Conflicts with SPEC Design 3: (1) "Safety": an interruption must leave the old state or the new one. `modutil` alone does not
(unlink then rename), but the scratch-copy swap does, so it is met by the Decision below, not by `modutil`. (2) A stale entry is
"updated in place": `modutil` cannot keep the position (delete + add moves it last), so the Decision keeps the entry once, not
in place; the evaluator decides if that needs a deviation. SPEC lists both roots; Firefox itself reads only the legacy one when it exists, the command scans
both so no profile is missed (a profile in the unused root is merely inert).

Decision: roots are scanned in the order of the table, every root that exists, all of them (not only the one Firefox would pick); for each `profiles.ini` the profiles are every `[ProfileN]` with `Name` and `Path` (`IsRelative=1` against the file's directory, else absolute) plus every `[InstallHASH]` `Default=`, deduplicated by real path, and a profile directory is registered even without `cert9.db` (`modutil` creates it, rc 0; a profile never opened has none), by the direct route of the swap Decision.
Decision: the list in "Data the command reads" is shipped as data: Firefox, Thunderbird, LibreWolf, Floorp and Waterfox included; Zen, Mullvad, Tor, Flatpak and AppImage excluded (the snap is F171's).
Decision: register with `modutil -dbdir sql:PROFILE -add NAME -libfile PATH -force` and stdin from `/dev/null`; before `-add`, read `pkcs11.txt` and recognise an existing entry by its `library=` value (any name; `modutil` does not rename it for Custodio's module, it fails rc 22, so never rely on its dedupe); an entry whose library file is gone is still deleted by name; a stale Custodio entry is updated by `-delete` of its name then `-add`; remove with `-delete NAME`; `modutil` is the only writer of module entries.
Decision: because `modutil` rewrites `pkcs11.txt` non-atomically (unlink, then rename), when the profile has `cert9.db`, `key4.db` and `pkcs11.txt` the command, with the profile free, copies those three files to a scratch directory beside the profile (same filesystem), runs `modutil -dbdir sql:SCRATCH` there, and `rename(2)`s `SCRATCH/pkcs11.txt` over the profile's (only that file changes; an interruption leaves the old file or the new one); it deletes a leftover scratch directory at the start of each run and on failure. If `pkcs11.txt` or either database file is missing it runs `modutil -dbdir sql:PROFILE` directly (the swap would write the scratch path into `configdir`).
Decision: packages: `libnss3-tools` (Debian, Ubuntu), `nss-tools` (Fedora, RHEL, Alma), `nss` (Arch); all verified.
Decision: a profile is held (skipped, exit non-zero) unless `lock` is absent or points to `IP:+PID` of a local address with a dead PID, and an `fcntl` write lock on `.parentlock` can be taken (then released); a foreign address, an unparseable target or a PID owned by another user counts as held.
Decision: the system loads the p11-kit proxy when `modutil -list` of a new database in a private scratch directory lists `p11-kit-proxy`; there the command does not register native profiles and says why; if that `modutil` fails, the native profiles fail (issue #32).
