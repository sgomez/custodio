### Conclusion
- **Header layout** (all little endian; `creds-util.c` in `src/shared`, 259.9). **verified** by read-back from real credentials (below):

| offset | field | size | source | present |
|---|---|---|---|---|
| 0 | key id | 16 | `:661` | always |
| 16 / 20 / 24 / 28 | `key_size` (32), `block_size` (1), `iv_size` (12), `tag_size` (16) | 4 each | `:662-665` | always |
| 32 | `iv` (12 bytes), zero padded to an 8 boundary → section ends at **48** | 12+4 | `:666`, `ALIGN8` `:1086` | always |
| 48 | `pcr_mask` | 8 (le64) | `:671` | id needs TPM (host+tpm2, tpm2, and `+pk` ids) |
| 56 / 58 | `pcr_bank` (0x000b = SHA256), `primary_alg` (0x0023 = ECC; RSA 0x0001) | 2 each | `:672-673` | same |
| 60 / 64 | `blob_size` (240), `policy_hash_size` (32) | 4 each | `:674-675` | same |
| 68 | TPM blob, then policy hash; section = `ALIGN8(20+blob+policy)` (296 here → ends **344**) | var | `:676`, `:1101` | same |
| 344 | public-key section: `pcr_mask` le64 (0x800 = PCR 11), `size` le32 (451), DER key; `ALIGN8(12+size)` | var | `:681-685`, `:1105-1112` | `+pk` ids only |
| after TPM and pk sections (344 here; 48 for scoped host-only) | **scoped header**: `flags` le64 = `0x7` (uid, machine, user name) and nothing else | 8 | `:688-690`, `:715`, `:1114-1121` | scoped ids only |
| after that | AES-256-GCM ciphertext of the metadata header (timestamp, not_after, name) and data, then the 16-byte tag; everything above is the AAD | | `:1126-1141` | always |

  The scoped header holds **no uid**: the uid, user name and machine id are hashed into the key (`mangle_uid_into_key` `:759-800`, struct `:700-705`), so a reader cannot recover the uid from the file.
  A reader must not assume the scoped header sits at 48+8: for TPM ids it is at 344 (+ the pk size). The decrypt side computes the same offsets (`:1302-1360`).
  For ids without TPM (host, null) bytes 48.. are metadata ciphertext, so the mask may be read **only after** the id says TPM (negative control below).

  Automatic choice (`creds-util.c:997-1013`): host key and TPM key both usable → host+tpm2 (`_SCOPED` when `_CRED_AUTO_SCOPED`, `_WITH_PK` when a public key loaded); TPM only and not scoped → tpm2;
  host only → host or host scoped; else `ENOTRECOVERABLE` (`:1012`), null only for `_CRED_AUTO_INITRD`. **Scoped never gives TPM only.** An explicit key id is used as is (`:1015`).
- **What the service's Varlink `Encrypt` gets** (`scope=user`, no `withKey`): `vl_method_encrypt` passes `_CRED_AUTO_SCOPED` (`creds.c:1367`) → host+tpm2 scoped `ef4ac136...` when the root daemon sees a usable TPM,
  host scoped `55b9ed1d...` when not (the second case is F110's; the code path `:1007-1008` is unchanged since 257). **verified** (259.9: `varlinkctl call ... Encrypt` blob → `ef4ac136...`, mask 0, decrypts with Varlink `Decrypt scope=user`: `plain= hello-f153`, rc 0).
- **The CLI `--user` never sends the key**: `ipc_encrypt_credential` builds the call without `withKey` (`creds-util.c:1601-1611`), so `--user encrypt --with-key=host` in the guest gave `ef4ac136...` (host+tpm2 scoped) too,
  not `55b9ed1d...` (F110 saw `55b9ed1d` only because no TPM reached the daemon). `--user --with-key=null|tpm2` is refused client side: `Selected key not available in --uid= scoped mode, refusing.` (`creds.c:1110`). **verified**
- **Default PCR mask**: 259.9 `0` (`creds-util.c:887-888`, `creds.c:1113-1114`); 257.13 `0x80` (PCR 7). **verified** both (table below). The mask is `le64` at **byte 48**: `--tpm2-pcrs=7` gives `0x80` on both. **verified**
- **null**: Varlink `withKey=null` (259 only) and root `--with-key=null` both succeed and carry the null id; the user CLI refuses it. In the guest I made the null credential with the root CLI and with Varlink. **verified**
