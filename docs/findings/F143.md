## F143

More signatures and imports than TPM object slots, in the debian13 guest (2026-11-06, packaged service, swtpm through its socket with no resource manager, modes swtpm and lacking).

- **Property (verified).** `TPM2TOOLS_TCTI=swtpm:path=$TPM_SOCK tpm2_getcap properties-fixed` prints `TPM2_PT_HR_TRANSIENT_MIN:` and, on the next line, `raw: 0x3` (also `raw: 0x3` behind the `lacking` filter,
  where `$TPM_SOCK` is the filter's socket). It is the property F130's `parse_slots` reads. The cases run N = 3 + 3 = 6 signatures per key and 6 imports.
- **Minimum, not capacity (inferred from the TPM 2.0 Part 2 definition of `TPM_PT_HR_TRANSIENT_MIN`, the minimum number of transient objects the TPM can hold; not measured here).**
  swtpm may hold more than it reports. Then a service that leaks one object per call would still pass `tpm-slots-sign-*` and `tpm-slots-import` and be caught only by
  `tpm-slots-no-leak`, which compares the handle lists before and after and does not depend on the capacity. The sign and import cases are therefore not the leak proof.
- **How a leaked handle shows (verified).** `tpm2_getcap handles-transient` prints one `- 0x80000000` line per loaded object and nothing when none is loaded (the lists before and
  after the step are empty, `handles-loaded-session` as well). `tpm2_createprimary -C o -c ctx` run directly on the socket leaves its primary loaded: the list then holds one handle,
  and `tpm2_flushcontext -t` empties it (control in the step: 1 handle, then 0).
- **Cost (measured).** Series imports ~5 s each (6 = ~31 s). Deleting the 8 keys one after another took ~42 s (one polkit-approved call each); the same deletes as parallel jobs in the
  one session took ~7 s, so `tpmslots-user.sh delete` runs them in parallel. Signing 2 x 6 calls takes ~2 s.
