## F152

Making the virtual TPM lack an RSA capability, tried by hand in the F151 VM (Ubuntu 26.04.1, kernel 7.0.0-42, `systemd 259.9`, `tpm2-tools` 5.7 from apt, QEMU 10.0.13, OVMF, `tpm-crb`), 2026-11-08, user `dev`, KVM.
The product is not installed. Every boot used a fresh qcow2 overlay of one prepared disk, a fresh OVMF vars copy and an **empty `swtpm` state directory**. Network from the container: the F151 probe (`curl -sI` → `200`) held; this session downloaded the image (SHA256SUMS signature and checksum checked as in F151) and four `.deb` files.

Conclusion:
- **Route 2, an `swtpm` 0.10.2 custom profile, works and is the one to use.** **verified**. `swtpm` 0.7.1 (the dev container, `libtpms` 0.9.2) has no `--profile`; 0.10.2 with `libtpms` 0.10.2 does. Unpacked from Debian forky `.deb` files in a new `/tmp` directory and run with `LD_LIBRARY_PATH`, it started on the trixie container and drove the VM.
- RSA lacks with `"Commands"` that leave out `0x159` (`TPM2_RSA_Decrypt`): the capability list drops the command and the TPM answers `command code not supported`. Or with `rsa-min-size=3072`: RSA 2048 is refused by `TestParms` and `CreatePrimary`. `rsa` itself cannot be removed from a profile (rejected at `PTM_INIT`, below). **verified**
- The kernel's TPM, `systemd-creds` ("host plus TPM", root and `--user`) and the ECC P-256 parent work under both. **verified**
- P-256 can lack in two ways. (a) `ecc-min-size=384` removes the curve (`ecc-nist-p256` cannot be named away: accepted, no effect), but the parent of every TPM key (the "TPM parent" decision, `docs/decisions.md:241`: a transient ECC P-256 primary, AES-128-CFB, SHA-256 name) is refused (`curve not supported`) and systemd's SRK flips to RSA 2048: that breaks the parent, so it is **not** acceptable, and the service would call RSA *lacks* too (the `curve NIST P-256` and parent rows are "yes" for RSA 2048 in `docs/api.md`). (b) `Commands` without `0x15d` (`TPM2_Sign`), the `command Sign` row that only P-256 needs (r2h): `tpm2_sign` → `command code not supported`, and the kernel's TPM, `systemd-creds` (root, `--user`, SRK stays ECC) and the parent plus a child (`tpm2_create`/`tpm2_load`) all still work. So **P-256 gets `encrypted-tpm`** by removing `Sign`. **verified**
- One combination breaks systemd: RSA 2048 refused (`rsa-min-size=3072`) **and** P-256 removed: `systemd-creds encrypt --with-key=host+tpm2` → `Failed to seal to TPM2: Operation not supported`, and `--user` silently seals with the host key only. With `RSA_Decrypt` removed instead of the key size, systemd keeps its RSA SRK and nothing breaks. **verified**
- Route 1, `tpm-filter` as built, cannot be placed under QEMU: **verified**. With a small adapter it works for RSA and P-256 but only hides capabilities (below). It stays for host tests with `swtpm` 0.7.1.
- The kernel has no bus-encryption primary here: `CONFIG_TCG_TPM2_HMAC is not set`, no `/sys/class/tpm/tpm0/null_name`. **verified** (so "any primary it makes" is none on 26.04's kernel).

Decision: route 2, an `swtpm` 0.10.2 custom profile (`Commands` without `0x159` `TPM2_RSA_Decrypt` makes RSA lack; `Commands` without `0x15d` `TPM2_Sign` makes P-256 lack); the dev container and CI must add `swtpm`/`swtpm-libs`/`swtpm-tools` 0.10.2-2 and `libtpms0` 0.10.2-5 (Debian forky `.deb`, sha256 below, installed over 0.7.1); never use `ecc-min-size=384` (breaks the ECC parent) nor `rsa-min-size=3072` together with it (breaks systemd); P-256 gets encrypted-tpm.

### Systemd's SRK
Image facts: `systemd-tpm2-setup-early.service` is skipped (`ConditionSecurity=measured-uki`) and `systemd-tpm2-setup.service` is `inactive`, so at boot there is no persistent SRK (`getcap handles-persistent` empty, `readpublic -c 0x81000001` → `the handle is not correct for the use`). `systemd-creds` then makes a transient primary (`SYSTEMD_LOG_LEVEL=debug`: `Creating primary key on TPM.`, after `Getting TPM2 capability 0x0000` and `0x0008`, i.e. algorithms and ECC curves), and writes its type in the credential header: `base64 -d cred.enc | xxd -s 56 -l 4 -p` → `0b002300` (SHA-256 bank, ECC) or `0b000100` (RSA). Running `/usr/lib/systemd/systemd-tpm2-setup` by hand persists the SRK: `0x81000001`, `readpublic` type `ecc` in r0/r1/r2a/r2b, `rsa` in r1b/r2e/r2g. So removing RSA does not change systemd's choice (it takes ECC P-256); removing P-256 (curve or ECC) makes it take RSA 2048. **verified**

### Route 1: `tpm-filter` between QEMU and `swtpm`
- The example (`crates/custodio-it/examples/tpm-filter.rs`, built with `cargo build -p custodio-it --example tpm-filter`) wants the `swtpm` TCTI data socket; `swtpm socket --server type=unixio,path=up --ctrl type=unixio,path=up.ctrl` plus `tpm-filter up flt alg=1` gave `ready swtpm:path=…/flt`, and `flt.ctrl` is a plain byte pump. QEMU pointed at `flt.ctrl` stops: `qemu-system-x86_64: -tpmdev emulator,id=tpm0,chardev=chrtpm: tpm-emulator: Failed to send CMD_SET_DATAFD: Success`. QEMU's emulator backend sends the data channel as a file descriptor (`SCM_RIGHTS`) on the control channel, which a byte pump drops. **verified**
- With a ~60-line throwaway adapter (Python, not committed): it listens where QEMU connects, forwards control bytes to `up.ctrl`, takes the fd of the message `00000010` (`CMD_SET_DATAFD`), answers it with `00000000` itself and pumps that fd (raw TPM commands, no framing) to `flt`. The log shows the control channel (`00000001`, `0000000e`, `00000011…`, `00000002`, `00000004`, `00000005`, …, `00000003` at shutdown) and over a thousand log lines of data commands for one boot and probe (`0x144` Startup, `0x17a` GetCapability, …); the guest booted and all probes ran. **verified**
- What the filter does: `GetCapability(ALGS/ECC_CURVES)` lose the entry, `TestParms` gets `0x1ca` (`TPM_RC_TYPE`, parameter 1; `tpm2_testparms` prints `Unsupported algorithm specification`), `Sign`/`RSA_Decrypt` schemes are refused. It does **not** refuse `CreatePrimary`/`Create`: `tpm2_createprimary -G rsa2048` and an RSA child succeed in r1, and the ECC parent succeeds in r1b/r1c. The service's query alone (`algorithm RSA` absent in `GetCapability(ALGS)`) sorts r1 as *lacks*, with P-256 *ready*. So "lacking" is real for the capability list, not for key creation. **verified**
- Cost: the adapter and a pump in `custodio-it`, `tpm-filter` built in the VM harness, and `swtpm` run with `--server` and `--ctrl`. It needs nothing new in the container, but the TPM is not really lacking. Not chosen.

### Route 2: `swtpm` profile
- Where: `man swtpm` (0.10.2, `--profile`): only the `custom` profile (or `custom:<name>`) may list `Algorithms`, `Commands`, `Attributes`; the profile is set once, at the first start with no state file; `swtpm socket --tpmstate dir=D --tpm2 --print-info 0x08` lists `Implemented`/`CanBeDisabled`. `CanBeDisabled` does not hold `rsa`, `ecc`, `ecc-nist-p256`, `aes`, `sha256`, `oaep`. **verified** (read and run)
- Run: `swtpm socket --tpm2 --profile file=prof.json --tpmstate dir=$STATE --ctrl type=unixio,path=$PWD/swtpm.sock --daemon …` (QEMU command line of F151 otherwise). `prof.json` is `{"Name":"custom","Algorithms":"<enabled list from --print-info 0x08, edited>","Commands":"<edited>"}`; with `--profile '{…}'` inline the commas break the option parser (`Unknown option '{"Name": "custom"'`): use `file=`. The error for a bad profile comes at `swtpm_ioctl -i` (`PTM_INIT` result `0x9`, `Error: Could not set profile for TPM2`), not at the start (process keeps running):
  - no `rsa,rsa-min-size=1024,rsassa,rsaes,rsapss,oaep` → rejected; no `ecc-nist`/`ecc-nist-p*` → rejected; no `ecc-nist-p256` alone, `rsa-min-size=3072`, no `rsassa,rsapss,rsaes` → accepted.
- Profiles tried: r2a `rsa-min-size=3072`; r2b `Commands` = the active list with `0x142-0x159` cut to `0x142-0x158` (default `0x11f-0x122,0x124-0x12e,0x130-0x140,0x142-0x159,0x15b-0x15e,0x160-0x165,0x167-0x174,0x176-0x178,0x17a-0x193,0x197,0x199-0x19c`); r2e `ecc-min-size=192` → `384`; r2d without `ecc-nist-p256,`; r2g = r2b + r2e; r2f = r2a + r2e.
- `tpm2_rsadecrypt` on an RSA 2048 primary: r2b and r2g → `Esys_RSA_Decrypt(0xB0143) - rmt:error(2.0): command code not supported`; control r2d → reaches the command (`0x182 inconsistent attributes`, the primary is restricted). `getcap commands | grep -c TPM2_CC_` → 108 (r2b) against 109. **verified**
- `tpm2_createprimary -G rsa2048` under r2a: `Esys_CreatePrimary(0x2C4) - tpm:parameter(2):value is out of range or is not correct for the context`; the ECC parent under r2e/r2g: `Esys_CreatePrimary(0x2E6) - tpm:parameter(2):curve not supported`. **verified**

### Route 3: others
- `libtpms` build options: no switch for RSA exists in the 0.9.2 package; 0.10's profile is the supported form of it. Ruled out. **inferred** (no source built).
- A QEMU-side proxy that edits the data channel is route 1 with the adapter above.

### Notes for the VM harness
- Per route a fresh `swtpm` state: a leftover persistent SRK from `systemd-tpm2-setup` would hide systemd's choice.
- A `--user` credential is sealed by the system service over Varlink (`io.systemd.Credentials.Encrypt`); when TPM sealing is impossible it does not fail, it uses the host key only (r2f). The harness reads the header (`xxd -s 56 -l 4`) to know whether the TPM took part.
- Seven boots ran in parallel on 12 cores without trouble. The tool sandbox cannot kill a started `swtpm`: two idle ones remain (pid 32088 from F151, 96049 from a mistaken start of mine); start `swtpm` only together with QEMU.
