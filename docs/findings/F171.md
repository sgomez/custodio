## F171

The Firefox snap in the M5 VM image (SPEC Design 6 "Check first", open questions on labels, profiles, base).
Run 2026-11-12 with `e2e/vm/vm.sh start full` on `ubuntu-26.04-minimal-cloudimg-amd64.img` (release-20261105),
guest Ubuntu 26.04.1, kernel 7.0.0-42-generic, 2 vCPU, 1.9 GB RAM, 8.6 GB disk. Probe scripts were scratch, not committed.

### Conclusion

1. The minimal image **ships snapd** (deb 2.77.1+ubuntu26.04.2, `snapd.socket` and `snapd.service` active) and
   **boots with AppArmor enabled** (`/sys/module/apparmor/parameters/enabled` = `Y`, 174 profiles loaded, 98 enforce,
   `apparmor` 5.0.2). Nothing to install from the archive (**verified**). The guest reaches the store (HTTP 200 from
   `api.snapcraft.io` through user networking).
2. `snap install firefox` (stable) took **50 s** and pulled 6 snaps, **1.22 GB** in `/var/lib/snapd/snaps`, disk 709 MB to 1.9 GB used
   (**verified**). The store query then matches: rev **9181**, 160.0-1, base **core26** (the SPEC's 154 / core24 is old;
   the run installs 9181 / core26). snapd re-executes from the snapd snap 2.78 after install.
3. Caching works but saves little: `snap download` of all 7 snaps took 57 s, and `snap ack` + `snap install ./file` of the
   six with the store unreachable took 19 s (**verified**). snapd rejects a tampered file. Installed from files the
   snaps have no channel (`Tracking -`), so nothing refreshes them. The cache would save about 31 s of 50 s on this host.
4. Accept **only `snap.firefox.firefox`**. The label observed from the app is `snap.firefox.firefox (enforce)`. Hooks do not
   load the module and have no home plug. `/proc/self/attr/current` is unreadable inside the snap: use `SO_PEERSEC`.
5. Base core26 has glibc **2.43**, above the ceiling 2.39 (`packaging/glibc-ceiling.txt`): the base supports the module.
   No `BLOCKED.md`.

### Evidence

**Image (step 1).** `snap --version` gives `snapd 2.77.1+ubuntu26.04.2`; `systemctl is-active snapd.socket snapd.service`
gives `active active`; `cat /proc/self/attr/current` outside gives `unconfined`; `sudo aa-status` gives
`174 profiles are loaded.` `98 profiles are in enforce mode.`; after the install `188` and `112`. Reading
`/sys/kernel/security/apparmor/profiles` needs root.

**Install and size.** `sudo snap install firefox` printed `firefox 160.0-1 from Mozilla** installed`, `elapsed=50`.
`snap info firefox` says `tracking: latest/stable`, `installed: 160.0-1 (9181) 312MB`, `latest/stable: 160.0-1 2026-11-12 (9181)`.
`snap list --all`: bare 5, core26 750, firefox 9181, gnome-core26 33, gtk-common-themes 1535, mesa-2604 123, snapd 28332.
`ls -l /var/lib/snapd/snaps` (bytes): firefox 312287232, gnome-core26 498053120, mesa-2604 215195648,
gtk-common-themes 96141312, core26 63639552, snapd 34091008, bare 4096; total `du -sb` 1219411968.
Bases: `gnome-core26` and `mesa-2604` are `base: core26`, `gtk-common-themes` is `base: bare`.
Assertions stay in `/var/lib/snapd/assertions/asserts-v0` (account, account-key, snap-declaration, snap-revision, model, serial).

**Cache by revision, verified, no silent refresh.**
- `snap download NAME --revision=R --basename=NAME_R` writes `NAME_R.snap` and `NAME_R.assert` (4.5 to 8 KB each).
  The assertions are tiny; the snaps are the 1.22 GB.
- With `snap set system proxy.https=http://127.0.0.1:9` (store unreachable: `error: no snap found for "hello-world"`),
  after `snap remove --purge` of all but snapd: `snap ack core26_750.assert && snap install ./core26_750.snap` printed
  `core26 20261023 from Canonical** installed`; the same for bare, gnome-core26, mesa-2604, gtk-common-themes, firefox,
  in that order (bases and content snaps first). `install_s=19`. `snap list` shows `Tracking -`.
- A copy of `bare_5.snap` with one byte changed: `snap install /tmp/t.snap` gave
  `error: cannot find signatures with metadata for snap/component "/tmp/t.snap"` (**verified**: the hash must match a
  signed `snap-revision`). Removing a snap keeps its assertions, so the "install without ack" case does not prove the ack
  is required; `snap ack` is the offline way to get the assertions.
- Hold: `sudo snap refresh --hold firefox` gives `General refreshes of "firefox" held indefinitely`; `sudo snap refresh --hold`
  gives `Auto-refresh of all snaps held indefinitely`; `snap refresh --time` then shows `hold: forever`, `next: ... (but held)`.
  `sudo snap set system refresh.hold=<now+89d>` works (`sudo snap get system refresh.hold` gives `2027-02-09T18:31:38Z`);
  the system hold is capped at 90 days. The run uses `--hold` (no end date).
- Fresh guest (**verified**): `bare_5.snap` (4096 B) and `bare_5.assert` (4521 B) were taken from a first guest and put on
  the payload drive (`VM_PAYLOAD` tar); a second, new boot read them with `sudo tar -xf /dev/disk/by-id/virtio-custodio-payload`
  (root needed), store blocked by proxy. `snap install ./bare_5.snap` before ack: `error: cannot find signatures with metadata
  for snap/component "./bare_5.snap"`; after `sudo snap ack bare_5.assert` (rc 0) the same install printed `bare 1.0 from
  Canonical** installed`, `snap list` `bare 1.0 5`. So ack is required and enough on a guest that never saw the snap.
  Only bare was carried: the 1.22 GB cannot leave a guest at 15 KB/s (F160), so the host would fetch the big snaps from the
  store itself; installing them the same way is **inferred** from bare and the same-guest run above.

**Apps, hooks, labels.** `meta/snap.yaml`: `name: firefox`, `version: 160.0-1`, `base: core26`, `confinement: strict`.
Apps: `firefox` (`command: firefox.launcher`) and `geckodriver` (`usr/lib/firefox/geckodriver`), neither a daemon.
Hooks (`meta/hooks/`, same names in `snap.yaml`): `configure`, `install`, `post-refresh`, `disconnect-plug-host-hunspell`.
Profiles in `/var/lib/snapd/apparmor/profiles/`: `snap.firefox.firefox`, `snap.firefox.geckodriver`,
`snap.firefox.hook.configure`, `.hook.install`, `.hook.post-refresh`, `.hook.disconnect-plug-host-hunspell`, and
`snap-update-ns.firefox`; `aa-status` lists the first six as enforce.

| Context | `SO_PEERSEC` seen by an unconfined listener | Source |
|---|---|---|
| plain shell | `b'unconfined'` | **verified** |
| `snap run --shell firefox` | `b'snap.firefox.firefox (enforce)'` | **verified** |
| `snap run --shell firefox.geckodriver` | `b'snap.firefox.geckodriver (enforce)'` | **verified** |
| hooks (4) | `snap.firefox.hook.<name> (enforce)` | **inferred** from profile names |

Both app probes ran `python3 -I` found in the base (`gnome-platform/usr/bin/python3`; `socat` is absent) and connected to a
Unix socket in the home. Hooks cannot be started that way: as a user, `snap run --shell --hook=configure firefox` gives
`cannot create transient scope ... AccessDenied`; as root with `-c`, `cannot use --hook and --command together`. `aa-exec -p`
of a profile from outside the mount namespace fails to read files, so it proves nothing. The hook profiles hold no home
rule beyond `~/snap/firefox/**` and no `/run/snap.firefox` rule (`grep -c` is 0 for both the hook and the app profile: the socket
directory rule is what the package adds). `cat /proc/self/attr/current` in the app gives `Permission denied`.

**Base and glibc.** Inside `snap run --shell firefox`, `ldd --version` prints `Ubuntu GLIBC 2.43-2ubuntu2.4`,
`/proc/self/maps` shows `libc.so.6` from `/usr/lib/x86_64-linux-gnu`, and `/etc/os-release` says `Ubuntu Core 26`.
`packaging/glibc-ceiling.txt` has `ceiling = 2.39`: the module copy needs no GLIBC symbol above it, so core26 (2.43) is enough.

**Profile location.** `HOME` and `SNAP_USER_COMMON` are `/home/ubuntu/snap/firefox/common` (`MOZ_LEGACY_HOME: '1'` in the yaml).
`snap run firefox --headless --screenshot /home/ubuntu/shot.png about:blank` (rc 0) created
`~/snap/firefox/common/.mozilla/firefox/{profiles.ini,t0wy5glf.default,"Crash Reports","Pending Pings"}`;
`profiles.ini` has `Path=t0wy5glf.default`, `IsRelative=1`, `Default=1`. `~/.mozilla` does not exist. Not XDG.
The `firefox` plug `dot-mozilla-firefox` and `etc-firefox` exist in the yaml (not exercised).

Decision: snapd comes from the image (deb 2.77.1); the run installs nothing from the archive and asserts AppArmor `Y` and a `snapd.socket` that is active.
Decision: the run installs `firefox` from `stable` from the store and records revision 9181-or-later, base, snapd (deb and snap), AppArmor and dbus-daemon versions; it does not cache snaps by default (50 s of a run of about 500 s; that is snapd behaviour, not the transfer limit). If the store is slow or unavailable, the cache route (tested with bare on a fresh guest; big snaps inferred) is `snap download` + `snap ack` + `snap install ./file`, bases and content snaps first, then `snap refresh --hold`.
Decision: the socket accepts only the exact label `snap.firefox.firefox`; the geckodriver app, the hooks and every other snap are refused. Read the label with `SO_PEERSEC`, not `/proc/self/attr/current`.
Decision: the base core26 (glibc 2.43) is not older than the module supports; no `BLOCKED.md`.
Decision: the profile directory for the snap is `~/snap/firefox/common/.mozilla/firefox/` (`profiles.ini` there).
