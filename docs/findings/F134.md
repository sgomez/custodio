## F134

Question: what do the PSS salt lengths, the over-maximum refusal and the key kinds look like through the PKCS#11 module, in the debian13 container under `swtpm`, `none` and
`lacking`, and what can `pkcs11-tool` pass? Run on 2026-11-05 with `just e2e-cases debian13 'sign-*'` in each mode (OpenSC `pkcs11-tool`, OpenSSL 3, swtpm 0.7.1). All **verified**.

- **`pkcs11-tool` cannot do RSA-PKCS-PSS with this module.** `--mechanism RSA-PKCS-PSS --hash-algorithm SHA256 --mgf MGF1-SHA256 --salt-len 32` prints `couldn't find the corresponding
  pubkey` then `error: Incorrect length of private key`, in all three modes, before any request: it needs a public key object to learn the key size, and the module serves only the
  private key and the certificate (`crates/custodio-pkcs11/src/token.rs`). So the PSS signatures go through `e2e/p11-pss.py`, a `ctypes` client of the module: `C_SignInit` with
  `CK_RSA_PKCS_PSS_PARAMS` (hash, MGF1 of the same hash, salt) and one `C_Sign`. The other mechanisms use `pkcs11-tool`.
- **PSS salts.** For each of SHA-256/384/512: salt 0, the hash length (32/48/64) and the maximum 222/206/190 sign (256 bytes) and `openssl pkeyutl -verify` with `rsa_padding_mode:pss`,
  `rsa_mgf1_md` of the same hash and that exact `rsa_pss_saltlen` accepts them; the same signature fails with another salt, hash or digest. The maximum plus one fails with
  `C_Sign ... rv = CKR_DATA_INVALID (0x20)`, no output, in all three modes.
- **Over-long RSA-PKCS payload.** 246 bytes: `pkcs11-tool` shows `C_SignUpdate failed: CKR_OPERATION_NOT_INITIALIZED` (it retries a failed one-shot `C_Sign` with the multi-part calls, which hides
  the first error); one `C_Sign` through `p11-pss.py ... pkcs` gives `CKR_DATA_INVALID (0x20)`, the same as the salt, in all three modes. The 36-byte MD5||SHA-1 payload, a 100-byte payload
  and the three `DigestInfo` forms sign (256 bytes); `openssl pkeyutl -verifyrecover` returns the payload exactly.
- **The agent is asked for a refused signature too.** The request counts of the agent are 6 for `rsa-pkcs` (5 signatures + the over-long payload), 4 for each PSS hash (3 + the over-maximum salt),
  3 for each composed or ECDSA group; identical in the three modes. The signatures of a group run at once, so only the total per group is checked, not a request per signature.
- **EC.** `ECDSA` over a SHA-256/384/512 digest gives 64 bytes r||s; converted to DER, `openssl pkeyutl -verify` with the raw digest accepts it (it truncates the longer digests as the service does).
  `ECDSA-SHA256/384/512` with `--signature-format openssl` gives DER (70-72 bytes), verified by `openssl dgst`. `SHAn-RSA-PKCS` gives 256 bytes.
- **Kinds per mode** (`ListKeys` of the test's own keys): `swtpm` RSA `tpm`, EC `tpm`; `none` `encrypted-host` for both; `lacking` (the F131 filter removes RSAPSS `0x16`) RSA `tpm`, EC `tpm`.
  The contract expected RSA `encrypted-tpm`, but RSAPSS is not a capability any key needs (`docs/decisions.md`, "the service pads"; `docs/api.md`, TPM capabilities), so nothing is lacking.
  Removing RSA (`alg=0x1`) does make RSA lack, and the import of the first RSA key then fails with `CredentialsUnavailable`: `encrypted-tpm` needs `systemd-creds` sealed to a TPM, which the
  container does not have. The fallback kinds in the container are for a later feature (F138); here `lacking` signs under `tpm`, and `sign-kind-matches-mode` fixes that by a run.
- Times: each `just e2e-cases debian13 'sign-*'` takes 46-47 s in the three modes (the signatures of a group run at once).

## Why `encrypted-tpm` cannot be produced in the debian13 container (checked 2026-11-05, systemd 257, **verified** unless marked)

- The F131 filter with `alg=0x1` (no RSA) makes the import fail with `CredentialsUnavailable` (`E2E_TPM=lacking`, filter edited and the observe check adapted for the run; reverted).
- Not the filter: `systemd-creds encrypt --with-key=tpm2 --tpm2-pcrs= --tpm2-device=swtpm:path=<filtered socket>` run as root against the filtered TPM (dev container, `just with-swtpm`) works.
- The service runs `SystemdCreds::system(None)` (`crates/custodiod/src/main.rs:29`): Varlink, scope `user`, the TPM is whatever the root `systemd-creds@.service` daemon finds. As a non-root user the CLI
  with `--tpm2-device` is the system scope: `Failed to encrypt: io.systemd.InteractiveAuthenticationRequired`; with `--user` the key is `auto` (99 bytes in the container = host key only).
- The daemon in the container logs `System lacks TPM2 support or running in a container, not attempting to use TPM2.` even with `ExecStart=-systemd-creds --tpm2-device=swtpm:path=... --tpm2-pcrs=` in a
  drop-in; `systemd-analyze has-tpm2` there prints `partial -firmware -driver +system -subsystem +libraries`. A bind mount of a fake `/sys/firmware/acpi/tables/TPM2` did not change `-firmware`. No `SYSTEMD_*` variable
  in `libsystemd-shared` overrides this (`grep` of the library: only `SYSTEMD_TPM2_DEVICE`).
- Not a missing device: no container gets past it (2026-11-05, debian13 image under rootful docker `--privileged`, host EFI-booted with a real TPM and
  `tpm_vtpm_proxy` loaded). The container sees the host's `/dev/tpmrm0` and `/sys/class/tpmrm/tpmrm0`, and `has-tpm2` is still `-firmware -driver -subsystem`.
  `systemd-detect-virt -c` gives `container-other` even with `/.dockerenv` removed (`Running in a pid namespace, assuming unknown container manager.`),
  which systemd as PID 1 of a container cannot avoid. `libsystemd-shared` 257 has no variable that overrides the detection (its `SYSTEMD_*` names: only
  `SYSTEMD_TPM2_DEVICE` for the TPM). `varlinkctl introspect` of `io.systemd.Credentials.Encrypt`: `name`, `text`, `data`, `timestamp`, `notAfter`, `scope`,
  `uid`, `allowInteractiveAuthentication`, no key choice, so the daemon always takes the automatic key, which skips the TPM in a container. A fake sysfs
  or securityfs, a vTPM (`swtpm chardev --vtpm-proxy`) or a drop-in on the daemon cannot change that; only a VM could.
- On the 257 targets `encrypted-tpm` cannot exist outside a container either: there the daemon's TPM credential is bound to PCR 7 and the service refuses it
  (`SPEC_DEVIATIONS.md`, F110). Signing under `encrypted-tpm` is proven by `crates/custodiod/tests/sign_kinds` (F118: the real service and the real
  `systemd-creds` bound to `swtpm` through `--tpm2-device`, RSA-PKCS, RSA-PSS and ECDSA, each verified with the stored key).
