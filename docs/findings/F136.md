## F136

**Verified** (debian13 container, `E2E_TPM=swtpm` and `lacking`, `just e2e-cases debian13 'tpm-dup-*'`; swtpm 0.7.1, tpm2-tools 5.7). Not run in the dev container:
`swtpm_setup`+`swtpm socket` as `tpm_swtpm_start` starts them fail there (`TPM failure` on the first command), so the probe is the guest run itself.

- **The records.** Root reads `/var/lib/private/custodio/<uid>/<id>` (the state directory of F135); layout as `crates/custodiod/src/store/record.rs`: header, id, certificate, then
  parent name (`u16` + bytes) and the blob, which is `TPM2B_PUBLIC` and `TPM2B_PRIVATE` with their size fields (the files `tpm2_load -u` and `-r` read). `e2e/tpmdup.py scan` takes them out;
  `checks_every_stored_key` (`cargo test -p custodiod --test tpm_duplicate`) runs it on records of the real `Record::encode` and compares the areas and names.
- **Records judged.** Every record of kind `tpm` in the directory, not two chosen ones: the selected run had `rsa1` and `ec1` there from an earlier step, so it judged four keys (`td-rsa`, `td-ec` among
  them, required by `tpmdup.py inventory`). All four store the same parent name.
- **The service's swtpm.** Root opens `swtpm:path=/tmp/custodio-e2e-tpm/swtpm.sock` (also in `lacking`: the filter's socket) with tpm2-tools. The parent is made with
  `tpm2_createprimary -C o -G ecc256:aes128cfb -a 'fixedtpm|fixedparent|sensitivedataorigin|userwithauth|noda|restricted|decrypt'` (F113): its name is equal to the stored one for each key.
- **The second swtpm** starts and stops in the container: `swtpm_setup --tpm2 --tpmstate /var/tmp/custodio-e2e-tpmdup-state --createek --not-overwrite`, then `swtpm socket --tpm2
  --tpmstate dir=… --server type=unixio,path=/tmp/custodio-e2e-tpmdup/swtpm.sock,mode=0666 --ctrl …sock.ctrl --flags not-need-init,startup-clear --daemon` (`tpm_swtpm_start SOCK STATE`);
  stopped with `swtpm_ioctl --unix …sock.ctrl -s` and a wait for no process with that state dir. Both parents come from one helper (`mk_parent`), and their public areas are equal but
  for the name and `x`/`y` (`tpmdup.py samepub`). Names: `000b6191…6b51` (service) and `000b188e…f582` (second).
- **Outputs** (same for all four keys, both modes):
  - `tpm2_readpublic`: `name:`, `attributes: userwithauth|adminwithpolicy|sign` (RSA: `…|decrypt|sign`), `type: ecc|rsa`, and **no** `authorization policy:` line. The line exists in 5.7
    when the policy is not empty: the control key made with a policy prints `authorization policy: bef56b8c…e8a2` (64 hex), and the guest requires the judgement to see it.
  - `tpm2_duplicate` under a policy session on `TPM2_CC_Duplicate`: exit 1, `ERROR: Esys_Duplicate(0x99D) - tpm:session(1):a policy check failed`, no `dup.priv`. The same invocation on a
    key made without `fixedtpm|fixedparent` and with the policy exits 0 and writes `dup.priv`.
  - `tpm2_load` under the second parent: exit 1, `ERROR: Esys_Load(0x1DF) - tpm:parameter(1):integrity check failed`. On the first swtpm under its own parent the same load succeeds.
- Objects: `tt` flushes (`tpm2_flushcontext -t`) after each command, as F128's `Rig::tool` does; the two TPMs are driven by two background jobs, one TPM never by two.
