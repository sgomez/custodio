## F131

Question: does the F108 route (swtpm on a unix socket, test drop-in) work in the final e2e harness, and what differs per target?
Run on 2026-11-05 in the dev container (rootless podman, debian13 target built from `e2e/targets/debian13/Containerfile`).
All **verified** unless marked *inferred*.

### The environment probe (debian13)
- `podman build` of the Containerfile with `swtpm swtpm-tools tpm2-tools` added: exit 0. In the container: `swtpm 0.7.1`, `tpm2_getcap 5.7`, glibc `2.41-12+deb13u4`
  (the dev container has the same glibc 2.41).
- `just e2e-cases debian13 pkcs11-tool-approve-rsa` with `E2E_TPM` unset/`swtpm` and `none`: the guest starts the real `custodio.service` of the installed package
  with the drop-in (`e2e/tpm-lib.sh`) and prints `e2e: the unit sees the TPM of the mode swtpm` / `... none`; the record has `tpm=swtpm` / `tpm=none`.
- `swtpm_setup --tpm2 --tpmstate /var/tmp/custodio-e2e-tpm-state --createek --not-overwrite` and `swtpm socket ... path=/tmp/custodio-e2e-tpm/swtpm.sock,mode=0666 ...
  --daemon` work as in F108 (state under `/var/tmp`, socket under `/tmp`; the host profile that confines `swtpm` lets only those through).

### How "inside the unit" is done
`ExecStart` stays as shipped. `tpm_in_unit` builds a transient unit with `systemd-run --pipe --wait` from what the installed unit reports (`systemctl show --value` of
`PrivateTmp`, `DynamicUser`, `ProtectSystem`, `PrivateDevices`, `PrivateUsers`, `RestrictAddressFamilies`, `NoNewPrivileges`, `BindReadOnlyPaths`) and takes the TCTI from
`systemctl show -p Environment` (`CUSTODIOD_TEST_SWTPM_TCTI`). A misspelt variable fails the check ("has no CUSTODIOD_TEST_SWTPM_TCTI"); a wrong bind path leaves
the socket out of the sandbox, so `tpm2_getcap algorithms` fails. In mode `none` the same command fails with `Cannot connect to swtpm TPM socket`. That the
daemon itself sees the TPM is shown by F133 (`tpm-kind-*`), not here.

### Per target (each run on 2026-11-05 as `E2E_TPM=<mode> just e2e-cases <target> pkcs11-tool-approve-rsa tpm-installed-unit-clean`)
| target | swtpm | none | notes |
|---|---|---|---|
| debian13 | pass | pass | also `lacking`: pass |
| ubuntu2604 | pass | pass | swtpm from the distribution, no change |
| fedora44 | pass | pass | needed the type-level drop-in exemption below |
| alma10 | pass | pass | `swtpm`, `swtpm-tools`, `tpm2-tools` from the standard repositories |
| arch | pass | pass | `swtpm` carries `swtpm_setup`; no `swtpm-tools` package |
| ubuntu2404 | pass | pass | refusal-only: nothing installs, so no TPM is set up; the guest only reports `tpm=<mode>` |
- **AppArmor** is enabled on this host (`/sys/module/apparmor/parameters/enabled` is `Y`) and confines `swtpm` in every container (F108), so the paths `/tmp` and
  `/var/tmp` were used on all targets and none needed a change. **SELinux** cannot be exercised here: `/sys/fs/selinux/enforce` does not exist in the dev container,
  so fedora44 and alma10 ran with no enforcing policy. *Inferred*, not run: a `--privileged` container runs unconfined (`spc_t`), so `swtpm` and the socket in `/tmp`
  are not denied on an SELinux host either; a CI runner (Ubuntu, AppArmor) is the same case as this host. No deviation is needed.
- **Fedora ships a type-level drop-in** for every service: `systemctl show -p DropInPaths custodio.service` lists
  `/usr/lib/systemd/system/service.d/10-timeout-abort.conf` on fedora44 with no TPM setup. `tpm_unit_problems` ignores that directory (and only that) in
  `DropInPaths` and in `systemctl cat`; anything under `custodio.service.d`, `/run` or `/etc` still counts.
- `lacking` has been run on debian13 only. The filter is built in the dev container (glibc 2.41, as debian13 and ubuntu2604); `ubuntu:24.04` ships glibc 2.39, so a
  dev-built filter may not run on ubuntu2404. That matters only once a `lacking` run reaches ubuntu2404 (M4 cases); not solved here.
