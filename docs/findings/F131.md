## F131

Question: does the F108 route (swtpm on a unix socket, test drop-in) work in the final e2e harness, and what differs per target?
Run on 2026-11-05 in the dev container (rootless podman, debian13 target built from `e2e/targets/debian13/Containerfile`).
All **verified** unless marked *inferred*.

### The environment probe (debian13)
- `podman build` of the Containerfile with `swtpm swtpm-tools tpm2-tools` added: exit 0. In the container: `swtpm 0.7.1`, `tpm2_getcap 5.7`, glibc `2.41-12+deb13u4`
  (the dev container has the same glibc 2.41).
- `just e2e-cases debian13 pkcs11-tool-approve-rsa` with `E2E_TPM` unset/`swtpm` and `none`: the guest starts the real `custodio.service` of the installed package
  with the drop-in (`e2e/tpm-lib.sh`) and prints `e2e: the unit sees the TPM of the mode swtpm` / `... none`; the record has `tpm=swtpm` / `tpm=none`.
- `swtpm_setup --tpm2 --tpmstate /var/tmp/custodio-e2e-tpm-state --createek --not-overwrite` and `swtpm socket ... path=/tmp/custodio-e2e-tpm/swtpm.sock,mode=0666 ...
  --daemon` work as in F108 (state under `/var/tmp`, socket under `/tmp`; the host profile that confines `swtpm` lets only those through).

### How "inside the unit" is done
`ExecStart` stays as shipped. `tpm_in_unit` builds a transient unit with `systemd-run --pipe --wait` from what the installed unit reports (`systemctl show --value` of
`PrivateTmp`, `DynamicUser`, `ProtectSystem`, `PrivateDevices`, `PrivateUsers`, `RestrictAddressFamilies`, `NoNewPrivileges`, `BindReadOnlyPaths`) and takes the TCTI from
`systemctl show -p Environment` (`CUSTODIOD_TEST_SWTPM_TCTI`). A misspelt variable fails the check ("has no CUSTODIOD_TEST_SWTPM_TCTI"); a wrong bind path leaves
the socket out of the sandbox, so `tpm2_getcap algorithms` fails. In mode `none` the same command fails with `Cannot connect to swtpm TPM socket`. That the
daemon itself sees the TPM is shown by F133 (`tpm-kind-*`), not here.

### Per target (*inferred* until each is run; step 3b of the contract)
- `ubuntu2404` is a refusal-only target (the package never installs), so there is no service to give a TPM: its guest reports `tpm=<mode>` and nothing else.
- `lacking` needs a filter binary built in the dev container (glibc 2.41); `ubuntu:24.04` ships glibc 2.39, so a dev-built binary may not run there. It only matters
  when a `lacking` run reaches ubuntu2404, which M4 cases would do; not solved here.
