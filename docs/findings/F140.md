## F140

Signing after the TPM is cleared, in the debian13 guest (2026-11-06, systemd 257, packaged service, modes swtpm and lacking). All **verified** by `just e2e-cases debian13 'tpm-clear-*'`.

- **Isolation.** A second `swtpm` (socket `$TPM_DIR/clear.sock`, state `/var/tmp/custodio-e2e-tpmclear-state`; in `lacking` the real swtpm is on `clear-up.sock` and `/e2e-bin/tpm-filter ... alg=0x16`
  on `clear.sock`) is the TPM of the service while the step runs (drop-in rewritten by `tf_point`, wait for a new MainPID + active + Ping). The main TPM is never cleared; a trap points the drop-in back,
  restarts the service and stops the second swtpm. At the end `tpm_observe <mode>` passes and no `swtpm` holds the second state directory.
- **`lacking` leg.** `tpm2_clear` (TPM2_Clear 0x126) goes through the filter (`alg=0x16` only drops RSAPSS from the algorithm list and `TestParms`): exit 0 on the filter's socket, empty output.
  Before the keys are imported the step checks the second TPM like `tpm_observe` does the first: `getcap algorithms` lacks `rsapss`, `testparms rsa2048:rsapss:null` fails with TPM_RC_SCHEME (0x1D2),
  `rsa2048:rsassa:null` passes, and the real swtpm behind the filter accepts the lacking parameters. Both keys are kind `tpm` in both modes.
- **`tpm2_clear`** with the lockout hierarchy and its empty auth works on swtpm as is (exit 0, no output). The owner seed changes: a primary under the owner hierarchy with the fixed template
  `ecc256:aes128cfb`, `fixedtpm|fixedparent|sensitivedataorigin|userwithauth|noda|restricted|decrypt` and no unique data has a different name before and after (`000b0eb0...` -> `000bdb6e...`).
- **Sign after the clear.** D-Bus `Sign` gives `com.rfirma.Custodio1.Error.KeyLost` with the message `the stored key can no longer be used`, for the RSA and the P-256 key; `pkcs11-tool --sign` exits
  non-zero with `CKR_DEVICE_ERROR`. The journal entries are `sign` / `signing_failed` / `key_lost` with the key id, `CUSTODIO_STORAGE_KIND=tpm` and alice's uid. GLib puts the error name in
  front of the message (`GDBus.Error:<name>: <message>`); `e2e/tpmclear-sign.py` removes that prefix.
- **Count of `Sign` calls.** One `pkcs11-tool --sign` run makes **two** service `Sign` calls (measured: a round of 2 D-Bus calls + 2 tool runs = 6 approvals and 6 journal entries, in both rounds and both
  modes). The cases therefore compare the entries with the agent's approvals (polkit is asked for every Sign, also one that then fails), not with the number of tool runs, and require at least 2 per key.
- **State.** A successful `Sign` leaves the state directory (`find` + `sha256sum`) unchanged: the listing after import equals the listing after the signing round `pre` (a control in
  `tpm-clear-sign-fails`). After the clear the failing signatures leave it identical to the one before them, and the records are still there with kind `tpm` (`tpmdup.py scan`).
- **Delete.** `custodio delete` (polkit, alice) of both keys succeeds after the clear; records and `ListKeys` entries are gone; one `delete` / `deleted` entry per key, which carries no
  `CUSTODIO_STORAGE_KIND` (docs/audit.md lists the kind for import and sign entries only). Importing `tc-rsa` again gives kind `tpm` and signs on the cleared TPM (shows the rig and the new seed work; not an "uncleared position").
- **`encrypted-tpm`.** Not run (SPEC_DEVIATIONS.md, F134 entry extended to F140; the credential kind cannot be made in the container, docs/findings/F134.md).
