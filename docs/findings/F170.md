## F170

Who the socket peer is, as the service sees it (SPEC Design 1 open questions: real uid under `PrivateUsers=`,
the D-Bus handshake, polkit's `unix-process` pidfd subject). Run 2026-11-12.

### Conclusion

1. Under the shipped `PrivateUsers=yes`, `SO_PEERCRED` of a peer that is neither root nor the service's uid reports
   **65534**, not the real uid (**verified**, systemd 259.9, twice). `PrivateUsers=identity` (systemd 257 floor)
   reports the real uid for uids 0..65535 and 65534 above that, and keeps the exposure score 0.7. It is the route.
   Dropping the namespace (`PrivateUsers=no`) gives 0.8 and breaks the rule.
2. Identity must come from the kernel, never from what the peer says. A zbus peer-to-peer server accepts one
   mechanism. `ANONYMOUS` takes no claim from the peer; `EXTERNAL` takes a claimed uid and compares it with the
   kernel's. Choose `ANONYMOUS` on the server and read `SO_PEERCRED`/`SO_PEERPIDFD`.
3. polkit 124 to 127 accept a `unix-process` `{pidfd, uid}` subject from a trusted caller (the action's `owner`
   annotation) for another uid. polkit 123 and earlier have no pidfd. polkit does not check the claimed uid against
   the pidfd's process for a trusted caller, so the service alone guarantees the uid it passes: it must refuse an
   unmapped uid (65534) **before** calling polkit.

### Q1: the real uid

Probe output (`PEERCRED` line, service side; `PIDFD_GET_INFO` with `PIDFD_INFO_CREDS` on `SO_PEERPIDFD`):

| Unit mode | Peer uid | `SO_PEERCRED` | `PIDFD_GET_INFO` | Unit starts | Score (offline) | Column from |
|---|---|---|---|---|---|---|
| `yes` (shipped) | 1234 | **65534** | ruid 65534 | yes | 0.7 | VM and container (same) |
| `yes` | 0 (root) | 0 | 0 | yes | 0.7 | VM, container |
| `yes`, service's own uid (63319, socketpair) | 63319 | 63319 | | yes | 0.7 | VM, container |
| `identity` | 1234 | 1234 | 1234 | yes (uid_map `0 0 65536`) | **0.7** | VM; score dev container too |
| `identity` | 0 | 0 | 0 | yes | 0.7 | VM |
| `identity` | 70000 and 4000000 | **65534** | 65534 | yes | 0.7 | VM |
| `no` | 1234 | 1234 | | yes | **0.8** | VM; score dev container |

All **verified** (259.9). Peers were 1234, 0 and uids above 65535, so a coincidental match cannot read as "real uid seen";
only root and the service's own uid are mapped under `yes`. `systemd-analyze security` names `PrivateUsers=` as the
0.2 that `no` costs ("Service has access to other users"), **verified**.

Other kernel sources, all **verified**: `SO_PEERPIDFD` plus `PIDFD_GET_INFO` is translated the same way (65534 under
`yes`); `SCM_CREDENTIALS` is the same kernel translation (**inferred**); `/proc/<pid>/status` is invisible
(`ProtectProc=invisible`: `FileNotFoundError`), and `/proc` is read through the same namespace anyway. No source
inside the namespace gives a uid the namespace does not map. Asking a process outside it (the bus) is the M5 route and
is not available on a direct socket.

`identity` limit: uids above 65535 (some LDAP/AD setups) read as 65534; the service refuses them (fail closed). Inside
`identity` the service has full capabilities in its own namespace, which `CapabilityBoundingSet=` (empty) drops.

### Q2: handshake (zbus 6.1.0, `Cargo.lock`)

Source (`~/.cargo/registry/src/*/zbus-6.1.0/src/connection/`): `handshake/server.rs:135` rejects an `AUTH` whose
mechanism is not the server's one (`requested_mech != Some(mech)`), so a server cannot be forced to `EXTERNAL`
when it is set to `ANONYMOUS`, and the reverse. `server.rs:79` accepts `EXTERNAL` only if the claimed uid equals
`client_uid`; `builder.rs:739` sets `client_uid = self.user_id.or_else(|| creds.unix_user_id())`: the server must not call
`.user_id()`. Default mechanism is `EXTERNAL` (`server.rs:45`). **Verified** by reading and by this probe (VM, 259.9,
`Builder::unix_stream(..).server(..).p2p().auth_mechanism(..)`, client uid 1234):

| Server unit | Server mech | Client mech | Result |
|---|---|---|---|
| `yes` | ANONYMOUS | ANONYMOUS | OK, `peer_creds` uid 65534 |
| `yes` | ANONYMOUS | EXTERNAL | `EXTERNAL rejected ... Accepted mechanisms: [ANONYMOUS]` |
| `yes` | EXTERNAL | ANONYMOUS | rejected, accepted `[EXTERNAL]` |
| `yes` | EXTERNAL | EXTERNAL (own uid 1234) | rejected (kernel says 65534) |
| `yes` | EXTERNAL | EXTERNAL claiming **65534** | **OK**: the claim matched the overflow uid |
| `identity` | EXTERNAL | EXTERNAL (own uid) | OK, uid 1234 |

The `EXTERNAL` row claiming 65534 is the hazard: under `yes`, `EXTERNAL` succeeds for any peer that claims 65534, whatever its
real uid. `ANONYMOUS` has no claim, so the uid is only what the kernel says. Clients that offer only `EXTERNAL`
(libdbus, GDBus, sd-bus default) would not connect to an `ANONYMOUS`-only server; the Custodio clients are ours
(the PKCS#11 module), so this costs nothing (the client mechanism we choose is `ANONYMOUS`). Not run with other clients.

### Q3: polkit `unix-process` `{pidfd, uid}`

Source read (polkit tarballs 123, 124, 125, 126, 127): `src/polkit/polkitsubject.c` parses `pidfd` with `uid`
(124: line 458, 125/126: 454, 127: ~457 `polkit_unix_process_new_pidfd`) and fails with "'pidfd' specified withtout 'uid'"
without `uid`. 123 has no `pidfd` at all. The caller test is in `polkitbackendinteractiveauthority.c` ("Only trusted
callers (e.g. uid 0 or an action owner)", 127: ~1059 to 1085; `owner` annotation read at 907): a subject whose
`user_of_subject_matches` is false, or whose user differs from the caller's, is refused unless the caller is uid 0 or an
owner. `user_of_subject_matches` is `claimed uid == racy uid of the process`
(`polkitbackendsessionmonitor-systemd.c`, 127: 301; the function is byte-identical in 124 to 127).

| polkit | Ships in | pidfd + uid accepted for a trusted caller | Mark |
|---|---|---|---|
| 123 and older | Debian 12, Leap 16.0 (not targets) | no (no pidfd) | **verified** (source 123) |
| 124 | Ubuntu 24.04 (not a target) | yes | **verified** |
| 125 | alma10 | yes | **verified** |
| 126 | debian13 | yes | **verified** |
| 127 | ubuntu2604, fedora44 | yes | **verified** (source and run) |
| 128 | arch | yes | **inferred** (128 not read; no change expected) |

Versions per target: `docs/findings/F18-versions.md` and the fedora44 and Arch acceptance entries (package metadata
there); ubuntu2604 re-checked here: `polkitd 127-2ubuntu1.1`.

Measured on ubuntu2604 (container, polkit 127, 2026-11-12, **verified**). The caller is the probe running as the
service's uid (992, `DynamicUser` with `User=custodio`, `PrivateUsers=yes`, under the copied unit); it sends
`CheckAuthorization` for `com.rfirma.custodio.sign` with a `{pidfd, uid}` subject for a peer of real uid 1234
(`SO_PEERCRED` says 65534). "Accepted" = a reply that is not the "Only trusted callers" error.

| Policy file | Subject uid | Reply |
|---|---|---|
| shipped (`owner` = `unix-user:custodio`) | 1234 | accepted: `(False, True, {'polkit.result': 'auth_self'})` |
| shipped | 65534 | **accepted too**, `auth_self` (polkit trusts the claim) |
| shipped | 0 | accepted, `(True, False, {})` (root passes without a prompt) |
| shipped | omitted | `Error parsing unix-process subject: 'pidfd' specified withtout 'uid'` |
| `owner` annotation removed | 1234, 65534, 0 | `NotAuthorized: Only trusted callers (e.g. uid 0 or an action owner) can use CheckAuthorization() for subjects belonging to other identities` |

So the annotation is what makes it work, and polkit does not guard against a wrong claim: an unmapped uid sent to
polkit would be authorized as the user "nobody", and root's uid 0 would pass. Under `identity` the caller is mapped
to itself, so the annotation match is the same (**inferred**, not run: polkit is not in the VM).

### Decisions

Decision: the unit uses `PrivateUsers=identity` (systemd 257 is the floor); the exposure score stays 0.7, so no `BLOCKED.md`. The socket feature's test must assert that a peer whose uid reads as 65534 (an unmapped uid, e.g. 70000) is refused, with the real uid used for ownership and polkit for mapped uids, run under the shipped unit.
Decision: the service never uses a uid from the peer; it takes `SO_PEERCRED` (and the `SO_PEERPIDFD` it passes to polkit), and treats 65534 as "unknown" and refuses it before any polkit call.
Decision: the p2p zbus server is `ANONYMOUS` only (no `.user_id()`), the module's client uses `ANONYMOUS`; a test must show an `EXTERNAL` client is rejected.
Decision: polkit is asked with `{pidfd, uid}`, the uid from the kernel, under the `owner` annotation `unix-user:custodio`; where polkit is older than 124 or the call returns an error, the service fails closed (refuses the signature).
