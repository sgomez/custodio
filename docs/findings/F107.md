## F107

SPEC open questions "Mechanism parity on the TPM" and "A TPM that lacks a capability only for some mechanisms",
for a person to approve in F111. Ran on `swtpm` 0.7.1-1.5 with libtpms 0.9.2-3.2 (TPM 2.0 revision 1.64, firmware raw `0x20191023`,
manufacturer IBM `0x49424d00`), inside `just with-swtpm`, with the probe
`cargo run -q --locked -p custodio-it --example tpm-probe -- mechanisms [--tcti <tcti>]` and the tests
`cargo test -p custodio-it --test tpm_filter -- --nocapture`. Not run on a hardware TPM: that is F111, same
probe. Each claim is **verified** (a command run here) or **inferred**.

Scope: RSA 2048 and ECC P-256 only (what M4 ships). Import, the service's capability query and the parent (F106)
are other features; the probe uses transient owner-hierarchy primaries (mechanisms do not depend on the parent).

### Method

- **The two ways.** (a) `TPM2_Sign` only: the probe parses a `DigestInfo` for `CKM_RSA_PKCS`, serves
  `CKM_RSA_PKCS_PSS` only when the requested salt length is the one the TPM produces, and everything else is
  `lacks`. (b) Padding built in the probe (PKCS#1 v1.5 block type 1, EMSA-PSS with MGF1 and a random salt of the
  requested length); the TPM does only the raw RSA private operation, `TPM2_RSA_Decrypt` with the null scheme on
  a key with the `decrypt` attribute. (b) is RSA only: `CKM_ECDSA` has no raw private operation to replace
  `TPM2_Sign`: `way=b ... outcome=n/a`, not an unrun case.
- **The verifier is not the probe.** Every signature is checked by the `openssl` CLI (3.5.7): `pkeyutl
  -verifyrecover` for `CKM_RSA_PKCS` (must open to exactly the payload; `-verify` refuses inputs over 64 bytes, a
  SHA-512 `DigestInfo` is 83), `pkeyutl -verify` with `rsa_padding_mode:pss`, `rsa_pss_saltlen:<n>`, `rsa_mgf1_md`
  for PSS, `pkeyutl -verify` for ECDSA. It caught two probe bugs in the first run (that 64-byte limit;
  `TPM2_GetRandom` returning at most 64 bytes for a 222-byte salt), fixed. The probe exits 1 when a served
  signature does not verify.
- **Table rule for (a).** For `CKM_RSA_PKCS_PSS`, "served" means the requested salt equals the salt the TPM
  produces; any other length is `lacks` by policy (`rc=policy:`), not a TPM error.
- **Negative controls, all in the output:** right signature over a wrong payload rejected
  (`control: verifier right_payload=yes wrong_payload=no`); wrong expected salt (found + 1) does not verify
  (`wrong_salt_verifies=no`); the rightmost 32 bytes of a SHA-384/512 digest do not verify an ECDSA signature over
  the leftmost 32 (`verified_over_rightmost_32=no`); a sign-only key refuses the raw operation (`0x182`).

The probe (exit 0) prints one `case:` line per cell of the table below (`way= mechanism= ... outcome= rc=
verified=`), one `salt_found:` line per hash, the `capability:` and `decrypt_other_caller:` lines, and ends
`result: every case ran; every served signature verified`.

### Results per mechanism (verified)

Every "served" cell verified by `openssl`.

| Mechanism | Way (a) `TPM2_Sign` only | Way (b) padding in the service, raw private operation in the TPM |
|---|---|---|
| `CKM_RSA_PKCS`, `DigestInfo` SHA-1, SHA-256, SHA-384, SHA-512 | served (`DigestInfo` parsed, digest passed with `RSASSA`) | served, bytes equal to (a)'s on the same key |
| `CKM_RSA_PKCS`, payload not a `DigestInfo`: 36-byte TLS 1.0/1.1 MD5+SHA-1 stand-in, or an unknown hash OID | `lacks`: parser refuses; as a digest the TPM answers `0x1D5` (wrong size) | served |
| `CKM_RSA_PKCS_PSS`, SHA-256/384/512, salt = hash length (32/48/64) | served (what the TPM produces) | served |
| `CKM_RSA_PKCS_PSS`, largest salt that fits (222/206/190) | `lacks` (policy) | served at that salt |
| `CKM_RSA_PKCS_PSS`, salt 0 and salt 20 | `lacks` (policy) | served at that salt |
| `CKM_ECDSA`, P-256, SHA-256/384/512 digest, the service's truncation | served (see "Hashes a P-256 key needs") | n/a: RSA only |

Composed mechanisms (`CKM_SHA256_RSA_PKCS`, `CKM_SHA256_RSA_PKCS_PSS`, `CKM_ECDSA_SHA256` and the other hashes)
hash first and reduce to these rows.

`CKM_RSA_PKCS` with a non-`DigestInfo` payload is where the two ways differ in kind: (a) cannot serve it at all
(TLS 1.0/1.1 client auth signs the 36-byte MD5+SHA-1 concatenation, and any PKCS#11 client may hand
`CKM_RSA_PKCS` any payload that fits), (b) serves it. The SHA-1 `DigestInfo` is served by this `swtpm` under (a);
a TPM or firmware policy disabling SHA-1 would make it `lacks` (inferred; F111 repeats the probe).

|---|---|---|---|---|

`salt_found` lines on hardware. Under (b) the service picks the salt.
Answered by F111: the STM hardware TPM also uses the hash length; decided in `docs/decisions.md` (2026-11-03).

### Hashes a P-256 key needs from the TPM (verified)

`CKM_ECDSA` takes a digest. The service truncates a SHA-384/512 digest to its leftmost 32 bytes
(`docs/decisions.md`, 2026-10-28). Two hand-overs to `TPM2_Sign` were run:

- `truncated32+SHA-256`: the 32 bytes with scheme `ECDSA` and hash SHA-256. Served for all three digests;
  verifies over the leftmost 32 bytes, not the rightmost 32.
- `full+own-hash`: the whole 48/64-byte digest with scheme hash SHA-384/SHA-512. Also served, verifies over the
  leftmost 32 bytes, so this TPM truncates by itself. Needs SHA-384/SHA-512 from the TPM.

(OpenSSL also truncates, so `verified_over_full_digest=yes` is expected; the rightmost-32 control shows the
truncation is leftmost.) A P-256 key therefore needs **SHA-256 only**
from the TPM when the service hands over the 32 truncated bytes, which it already computes. That is the
recommended hand-over: truncation stays in one place and a TPM without SHA-384/512 does not lack `CKM_ECDSA`.

### The `decrypt` attribute against the threat model

Run (`decrypt_*` lines): a sign-only and a sign|decrypt RSA key created, blobs kept; **a second connection**
recreated the primary and loaded the blobs, as another holder of the TPM and the state directory could.

- The sign|decrypt key (the TPM accepts both on an unrestricted key with the null scheme; the spec rejects them
  together only on restricted keys, not run) decrypted a PKCS#1 v1.5 ciphertext `openssl` made to its public key:
  `plaintext recovered: "secret message"`. The sign-only key refused: `0x182`, attributes.
- Both keys signed a digest of the caller's choosing (`RSASSA`, SHA-256): any holder can sign with or without
  `decrypt`. That is the "Root can use a TPM key" row of the SPEC threat model, accepted by design.
- Neither key could be duplicated: `TPM2_Duplicate` answered `0x124` (the empty `authPolicy` needs a policy
  session that cannot be built). `decrypt` does not change that: the key stays `fixedTPM|fixedParent`. The
  in-scope threat "take a key out of the TPM" is not affected.

So the attribute adds **decryption of chosen ciphertexts** (S/MIME or CMS, a recorded TLS-RSA key exchange) and
**signing of arbitrary padding**. Both are *use* of the key by someone who controls the running machine, which SPEC
"Out of scope" lists ("root *using* a key while it controls the running machine"). The in-scope items (root
reading the state directory, a stolen disk, `TPM2_Duplicate`) are unchanged. "Root can use a TPM key" grows from
signing as the certificate to also reading past mail encrypted to it. For the encrypted kinds root can do both and
copy the key, so a TPM key with `decrypt` is still strictly stronger than the fallback. The service never exposes
decryption (no `C_Decrypt` path), and under (b) never passes a client-chosen block to the raw operation. SPEC
"Attributes of the imported key" asks for "no more usages than" the mechanisms need and calls `decrypt` "an open
question": under (b) it is needed.

### The TPM capabilities each key type needs (the list the service will query)

Calls: `GetCapability(ALGS)` / `(ECC_CURVES)` / `(COMMANDS)` (`TPM_CAP_ALGS`, `_ECC_CURVES`, `_COMMANDS`) and
`TestParms` (`TPM2_TestParms`, the exact check for a type, size,
scheme and hash). On `swtpm` every item of the tables below, and of way (a), answered `present` / `supported` (the
`capability:` lines); `tpm2_getcap commands` lists `TPM2_CC_Import`, `TPM2_CC_Load`, `TPM2_CC_Sign`,
`TPM2_CC_RSA_Decrypt`, `TPM2_CC_TestParms`, `TPM2_CC_GetCapability`.

**RSA 2048, way (b)** (recommended):

| Item | Answered by |
|---|---|
| algorithm RSA (`0x0001`) | `GetCapability(ALGS)` |
| key size 2048, exponent 65537, scheme null | `TestParms` rsa2048 null scheme |
| name algorithm SHA-256 (`0x000b`) | `GetCapability(ALGS)` |
| `decrypt` on a signing key: `TPM2_RSA_Decrypt` implemented | `GetCapability(COMMANDS)`; the attribute itself is not queryable, only proven by the import and `tpm2_readpublic` |
| no hash, no signature scheme: the service hashes and pads | nothing to query |

**RSA 2048, way (a)** (not recommended; for completeness): the rows above except `decrypt`, plus `RSASSA`
(`0x0014`) with each of SHA-1, SHA-256, SHA-384, SHA-512, `RSAPSS` (`0x0016`) with each of SHA-256, SHA-384,
SHA-512 (`TestParms` for each), and the salt the TPM produces (not queryable: found by signing).

**ECC P-256:**

| Item | Answered by |
|---|---|
| algorithm ECC (`0x0023`) | `GetCapability(ALGS)` |
| curve NIST P-256 (`0x0003`) | `GetCapability(ECC_CURVES)` |

and fails the import.

### Simulating a TPM that lacks one of them

- **A profile does not exist here (verified).** Not in `swtpm` 0.7.1 nor libtpms 0.9.2:
  `swtpm socket --tpm2 --print-capabilities` lists no profile feature; `swtpm_setup --help | grep -i -E
  "profile|algorithms"` prints nothing; `swtpm socket --help` mentions only the seccomp profile;
  `nm -D /usr/lib/x86_64-linux-gnu/libtpms.so.0 | grep -i profile` prints nothing (no `TPMLIB_SetProfile`).
  `swtpm` implements every scheme, hash and curve of the spec (curves `0001 0002 0003 0004 0005 0010 0011 0020`),
  so nothing real can be removed.
- **The replacement (built): `custodio_it::tpm_filter::TpmFilter`** (`crates/custodio-it/src/tpm_filter.rs`, std
  only, no `unsafe`; tests in the file and `tests/tpm_filter.rs`). A unix socket in front of the `swtpm` socket,
  bare `swtpm` TCTI framing both sides, `<path>.ctrl` passed through. `GetCapability` for algorithms and curves
  loses the lacking entries; `TestParms` with a lacking type, symmetric, scheme, hash or curve, and `Sign` /
  `RSA_Decrypt` with a lacking scheme or hash, get the spec's format-one code (`TPM_RC_TYPE`, `TPM_RC_SCHEME`,
  `TPM_RC_HASH`, `TPM_RC_CURVE`, parameter 1, or 2 for `Sign`). F108 onward reuse it:
  `TpmFilter::start(upstream_socket, filter_socket, Lacks { algorithms, curves })` and `filter.tcti()`.
- **It fails one capability while plain `swtpm` passes (verified, `3 passed`).** Plain `swtpm`: `TestParms`
  rsa2048 RSAPSS SHA-256 supported, `Sign` RSAPSS served. Filter lacking RSAPSS `0x0016`: RSAPSS absent from
  `GetCapability(ALGS)`, `TestParms` RSAPSS `0x1D2` (scheme, parameter 1), `Sign` RSAPSS `0x2D2` (parameter 2);
  RSASSA, RSASSA SHA-384 and ECDSA SHA-256 untouched. Filter lacking SHA-384 `0x000c` and P-256 `0x0003`: both
  absent from `GetCapability`, `TestParms` RSASSA SHA-384 `0x1C3` (hash), ECDSA P-256 `0x1E6` (curve), RSASSA
  SHA-256 supported. Plain `swtpm` answers `0x1C3` for SM3_256, which it does not implement, so the hash code is
  measured, not only specified. The RSAPSS case is a partial lack: only `CKM_RSA_PKCS_PSS` is lost under (a).
- **What it cannot simulate.** `Create`, `Load`, `Import`, `CreatePrimary` reach the real TPM, so "query
  accepted, import fails" (SPEC section 2 "TPM error during import", not "lacks") needs a different fault. The scheme and curve codes come from the TPM 2.0 Part 2 table and are **inferred** (only the hash code is
  measured). A hardware TPM may answer another code, or `TPM_RC_COMMAND_CODE`. No hardware timing, hardware salt,
  or `GetCapability` paging (`moreData` passed through).

### Partial lack: recommendation

SPEC section 4 sends a key type whose TPM cannot serve a mechanism to "lacks a capability" (encrypted, TPM-bound):
"A mechanism is never silently dropped or changed for a TPM key." The question: should it go to the TPM instead?

**Recommendation: keep the SPEC answer. The key type goes encrypted, TPM-bound, and `custodio import` says why.**
Reasons: (1) a TPM key refusing `CKM_RSA_PKCS_PSS` with salt 20 errors differently from the encrypted kind for the
same call, which is "dropped or changed for a TPM key"; (2) the importer cannot know which client needs which
mechanism, and a key that works in Firefox but fails in LibreOffice is the worse outcome; (3) with way (b) the
question mostly disappears for RSA: no per-mechanism item, so a TPM has all of it or lacks the key type, and a
missing `RSAPSS` or SHA-384 changes nothing (the RSAPSS filter case leaves the (b) items untouched; that the raw
operation then still works is **inferred**, the filter run did no null-scheme decrypt). TPM-with-loss would need
an explicit per-kind opt-in, the administrator override SPEC defers to M5; no departure from SPEC for M4.

### Departures and points for the person in F111

Answered in F111 and `docs/decisions.md` (2026-11-03).

- Way (b) puts the `decrypt` attribute on every TPM RSA key: SPEC's "no more usages than those" resolves to
  "includes `decrypt`". The threat model's "Not guaranteed" list should say root can also decrypt with a TPM RSA key.
- Under (b) the service must verify each signature with the public key before returning it (cheap): the TPM
  returns a bare private-key exponentiation, and a fault would otherwise leave the service as a signature.
- Under (b) the salt is drawn by the service (`TPM2_GetRandom` returns at most 64 bytes per call) or its own RNG;
  the service's `CKM_RSA_PKCS_PSS` bound checks (data length, salt length) stay as they are, which gives "the same
  bounds and the same errors".
- On hardware read the `salt_found` lines (only (a)), the `capability:` lines, and whether `decrypt` plus `sign`
  is accepted on an unrestricted RSA key.

### The probe is read-only, and its exit codes (verified)

```
$ just with-swtpm bash -c 'listings; tpm-probe mechanisms; listings'     # one TPM, before and after
probe exit=0, listings identical (no persistent handles, no NV index; HR_PERSISTENT 0x0, NV_COUNTERS 0x0)
$ tpm-probe bogus                                      ->  usage, exit 2
$ tpm-probe mechanisms --tcti swtpm:path=/nonexistent  ->  "tpm-probe: cannot connect to the TPM: ... IO failure.", exit 1
$ tpm-probe mechanisms --tcti notatcti                 ->  "tpm-probe: malformed --tcti", exit 1
```

Transient keys only, flushed; no `EvictControl`, no auth value set, no clear.

### Decision

Way (a) loses `CKM_RSA_PKCS` with a non-`DigestInfo` payload and every `CKM_RSA_PKCS_PSS` salt length but the hash
length, so every RSA key would "lack" by SPEC section 4 or be served with fewer mechanisms than the encrypted
kind. Way (b) serves every mechanism, bytes equal to (a) where (a) serves, for the cost of the `decrypt`
attribute, which adds use of the key that SPEC already leaves out of scope for root. ECC keys use `TPM2_Sign`
with the truncated digest and need SHA-256 only. Recommended for approval:

Decision: (b)
