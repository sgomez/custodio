## F106

Which parent key in the owner hierarchy wraps the imported keys (the SPEC "Which parent" open question). Ran on
`swtpm` (libtpms, IBM manufacturer id `0x49424d00`, TPM 2.0, dev container) through
`just with-swtpm bash -c '...'`, with `tpm2-tools` and the probe
`cargo run -p custodio-it --example tpm-probe -- parent [--tcti <tcti>]`. Restart and clear experiments also use
`just with-swtpm`: it exposes the control socket at `<TCTI path>.ctrl`, so `swtpm_ioctl --unix <sock>.ctrl -i`
(re-initialise, state kept) then `tpm2_startup -c` inside one `bash -c` is a TPM restart on the same state. Not run
on a hardware TPM: that is F111, same probe. Each claim is **verified** (a command run here, or a source read) or
**inferred**.

### The two candidates

- **A. Persistent SRK** at `0x81000001`, the handle the TCG provisioning guidance reserves for the SRK (what
  `systemd-cryptenroll` and `systemd-creds` use), created once from the TCG SRK template and made persistent with
  `TPM2_EvictControl`.
- **B. Primary recreated from a fixed template** on each use: `TPM2_CreatePrimary` in the owner hierarchy from a
  template the code carries. A primary is a function of the hierarchy seed and the template, so the same template
  gives the same key every time (the probe creates each template twice and compares). Transient, flushed after use.

The template compared is the TCG SRK template: restricted decryption key, `fixedTPM|fixedParent|
sensitiveDataOrigin|userWithAuth|noDA|restricted|decrypt`, name algorithm SHA-256, AES-128-CFB, null scheme, empty
unique field, in two variants: RSA 2048 and ECC P-256 (the probe's `srk_template`).

### The probe

`tpm-probe parent` prints one `key: value` line each. It never calls `EvictControl`, never sets an auth value and
never clears; it creates transient primaries and flushes them. Exit: 0 when the TPM answered and the owner hierarchy
accepts an empty auth; 1 when the TPM cannot be reached or the owner hierarchy is unusable (readable facts, the
persistent key among them, printed first); 2 on a usage error. So the exit is non-zero with an owner password even
when candidate A would still work: the probe reports "can the service provision or recreate", not "can it use an
existing key", and prints the second fact too (`persistent_0x81000001*`).

Read-only check (verified): persistent handles, NV indexes and the counters
(`tpm2_getcap handles-persistent`, `handles-nv-index`, `properties-variable | grep -E 'HR_PERSISTENT|HR_NV|NV_COUNTERS'`)
before and after a probe, in one `with-swtpm` call (each call starts a new TPM). Run on the fresh TPM (exit 0,
`HR_PERSISTENT: 0x0`, `HR_NV_INDEX: 0x0`, `HR_PERSISTENT_AVAIL: 0x41`) and with an SRK persisted: listings identical
both times.

Output on a fresh `swtpm` (`just with-swtpm cargo run -q --locked -p custodio-it --example tpm-probe -- parent`):

### Cost per call (candidate B)

Means over N=5 timed calls (after two untimed), each `CreatePrimary` + `ReadPublic` + `FlushContext`, on `swtpm`:
**ECC P-256 about 4.3 to 4.4 ms, RSA 2048 about 23 to 33 ms** (two runs: 32.8 and 23.1 ms). `swtpm` is software: hardware is
much slower for RSA (RSA 2048 key generation takes seconds on some parts); ECC P-256 is normally far cheaper there. N is kept small for that and printed next to each mean so F111
numbers compare. **Inferred** for hardware.
Superseded by F111 and `docs/decisions.md` (F114): the key is loaded per signature, so each signature recreates the
primary; on the STM hardware TPM that costs about 0.5 s (P-256) and RSA 2048 about 3.7 s.

### Candidate A: persistent SRK at `0x81000001`

NV write: **yes** (verified). `TPM2_EvictControl` stores the object in the TPM's NV storage and consumes a
persistent slot; it creates no NV index (`handles-nv-index` stays empty). After persisting an ECC P-256 SRK:
`handles-persistent` lists `0x81000001`, `HR_PERSISTENT: 0x1`, `HR_PERSISTENT_AVAIL: 0x40`, `HR_NV_INDEX: 0x0`. The
probe then prints:

```
persistent_0x81000001: occupied
persistent_0x81000001_template: ecc NistP256 fixedtpm=true fixedparent=true sensitivedataorigin=true userwithauth=true noda=true restricted=true decrypt=true sign=false
persistent_0x81000001_name: 000b59644dbdbedad559d8520067a3b2ce1c54dbcad446e6155dbe368eafb1f4c7cf
rsa2048_name: 000b589ff68f2c2c3807ef8d4db72516ccbced13b1791648ca7c0c4ed5b7b938bc50
ecc_p256_name: 000b59644dbdbedad559d8520067a3b2ce1c54dbcad446e6155dbe368eafb1f4c7cf
persistent_0x81000001_matches_srk: yes (ecc_p256)
```

Secret in the service: **none**. The TPM generates the key from its seed with an empty auth value (TCG template,
`userWithAuth` with empty auth, `noDA`). Provisioning needs the owner hierarchy authorisation, which the service would
have to hold when the owner has a password (below).

Reboot: **survives** (verified). After a restart on the same state (`swtpm_ioctl -i`, `tpm2_startup -c`, rc=0) the
handle, the template line, the name `000b5964...` and `matches_srk: yes (ecc_p256)` are unchanged.

`TPM2_Clear` (verified, `tpm2_clear`, lockout auth empty, rc=0): the owner seed changes and the persistent object is
removed with it. The next probe: `persistent_handles: none`, `persistent_0x81000001: empty`, new template names
`rsa2048_name: 000b69d5...`, `ecc_p256_name: 000be85b...`.

Package upgrade: **inferred**. An upgrade does not touch TPM state. A new version could carry a different template, leaving the old SRK at the handle with a name that no longer
matches (see "another template" below). Both candidates need the template frozen across versions.

### Candidate B: primary recreated on each use

NV write: **no**. `CreatePrimary` allocates only a transient object, flushed after use; the probe does it twice plus
N timed calls and the listings are identical before and after. Secret in the service: **none**. Empty auth value, no
`sensitive.data` input; it derives from the owner seed and the template only (`*_deterministic: yes`).

Reboot: **survives** (verified): the names after the restart equal those before (`rsa2048_name` `000b589f...`,
`ecc_p256_name` `000b5964...`). `TPM2_Clear`: **changes** (verified: `000b69d5...`, `000be85b...`), so every key
wrapped under the old primary is lost either way. Package upgrade: **inferred**: the package carries only the
template, so while the template bytes do not change the primary is the same; a changed template gives a different
name, which the stored-parent-name check (below) turns into an error instead of a failed load.

### Owner hierarchy with a password

`tpm2_changeauth -c o secret` (rc=0), then (verified):

| Action | Result |
|---|---|
| `tpm2_createprimary` without the password | `Esys_CreatePrimary(0x9A2) - tpm:session(1):authorization failure without DA implications`, rc=1 |
| probe | `owner_hierarchy: unusable (TSS Layer: TPM, Code: 0x000009A2, ...)`, `persistent_0x81000001: empty`, exit 1 |
| bad password | `0x9A2`, rc=1 |
| right password | rc=0 (B works; A persisted: `persistent-handle: 0x81000001`) |

`0x9A2` is `TPM_RC_AUTH_FAIL` seen through a session ("authorization failure without DA implications"; the owner
hierarchy is not subject to dictionary-attack lockout). The probe exits 1, quotes the code, and still prints the
occupant of `0x81000001`.

- **B** needs the owner authorisation on every use, so with a password it fails with `0x9A2` on every import *and*
  every later load: the service would have to keep the owner password, a secret in the service, which the SPEC
  default rules out. It fails; it does not fall back.
- **A** needs the owner authorisation only to provision, not to use (verified): with the SRK persisted before the
  password was set, the probe prints `occupied`, the template, `owner_hierarchy: unusable (... 0x000009A2 ...)`,
  `matches_srk: unknown (owner hierarchy unusable, no template name to compare)`, exit 1; yet
  `create under persisted SRK without owner password rc=0` and `load ... rc=0`, while `tpm2_evictcontrol` without
  the password fails with `Esys_EvictControl(0x9A2)`, rc=1.

If the owner has a password and the handle is empty, A cannot be provisioned either (`0x9A2`).

Service behaviour (both): an unusable owner hierarchy fails the import with a named error carrying the TPM code (`TPM_RC_AUTH_FAIL`, `0x9A2`); no fallback to the software key store, no retry with another
parent, and the service never asks for or stores the owner password.

### Another key at `0x81000001`

The occupant can be anything. "Use whatever is at the handle" would wrap keys under a key the service did not
create: a signing key cannot be a parent, and a storage key with another template or a known auth value could be
one the service cannot recreate or another program controls. Negative controls on `swtpm` (verified):

| Case | Probe output | Result |
|---|---|---|
| G1: a signing key at the handle | `template: ecc NistP256 ... noda=false restricted=false decrypt=false sign=true` | `matches_srk: no` |
| G2: SRK template with `noDA` cleared | `template: ... noda=false restricted=true decrypt=true sign=false`, name `000bbcdb...` | `matches_srk: no`, exit 0 |
| G3: `tpm2_evictcontrol` onto the occupied handle | `Esys_EvictControl(0x14C) - tpm:error(2.0): NV Index or persistent object already defined` | rc=1 |

The probe tells them apart by the `template` line and by the name (SHA-256 of the whole public area: any
difference gives `matches_srk: no`; the expected SRK gives `yes (ecc_p256)` or `yes (rsa2048)`). The service must treat `no` as unusable: error, no
overwrite, no eviction (it does not own the handle; `EvictControl` onto an occupied handle fails with `0x14C`
anyway). Candidate B has no such case: it never reads the handle.

### Where a stored blob records the parent name

A key created under a parent is stored as `TPM2B_PUBLIC` plus `TPM2B_PRIVATE`. Neither carries the parent name in
clear (verified: the digest of the parent's name occurs 0 times in `c.pub` (90 bytes), `c.priv` (128) and
`c.cdata` (34)). What the TPM enforces is cryptographic: the private part is an inner-wrapped sensitive area plus an
integrity HMAC keyed from the parent's seed and covering the child's name. Verified:

| `tpm2_load` of the blob under | Result |
|---|---|
| A, the same parent | rc=0 |
| B, the RSA SRK template, same hierarchy | `Esys_Load(0x1DF) - tpm:parameter(1):integrity check failed`, rc=1 |
| A', the same template after `tpm2_clear` | `0x1DF`, rc=1 |

`0x1DF` is `TPM_RC_INTEGRITY` on parameter 1. It does not say which parent was expected, and the same code appears
for a damaged blob. So the **service stores the parent name itself, next to the blob** (a `parent_name` field: the
34 bytes `000b || sha256` of the parent's public area), and before `Load` computes the name of the parent it is
about to use (B: `CreatePrimary` then `ReadPublic`; A: `ReadPublic` of `0x81000001`) and compares: a mismatch is the
named error "stored under a different parent" (clear, other template, other TPM, other template version) without
ever sending the blob to the TPM. The TPM check is the backstop; its `0x1DF` is the error the service reports if
the check was skipped or the stored name was edited.

### Package removal

For the chosen parent (B): **nothing in the TPM**. No persistent object, NV index or auth value was created, so
removal has nothing to evict. Only the service's own state (the stored wrapped keys and their `parent_name`) is
removed or kept, as the key store's removal policy dictates. For A, removal must not evict `0x81000001`: the handle
is shared with `systemd-cryptenroll`, `systemd-creds` and other tools whose credentials depend on it, so a package
that removes it can destroy data it did not create. Even "evict only if the name matches our template" would remove
keys of other tools using the same TCG template.

### Sources read

- **TCG TPM v2.0 Provisioning Guidance**, Version 1.0 Revision 1.0 (15 March 2017), Table 2: the SRK is
  `0x81000001` (EK `0x81010001`). **verified** (PDF read). Section 7.5.1 derives the shared SRK template from the EK
  Credential Profile 2.0 with four changes (set `userWithAuth`, clear `adminWithPolicy`, set `noDA`, empty
  `authPolicy`), and a shared SRK uses an all-zero well-known auth value. **verified**. The remaining template fields
  (AES-128-CFB, null scheme, SHA-256 name, RSA 2048 / exponent 0 / 256 zero bytes of unique, ECC P-256 / 32+32 zero
  bytes) come from the EK profile and were **inferred** from memory, not read. The "Persistent Handle Assignments"
  reference was not read.
- **systemd v257** (`src/shared/tpm2-util.c`, `tpm2-util.h`, `src/tpm2-setup/tpm2-setup.c`; about 200 of the 330 KB
  of `tpm2-util.c` read): `TPM2_SRK_HANDLE` is `0x81000001`; the template is ECC P-256 (preferred) or RSA 2048,
  SHA-256 name, AES-128-CFB, null scheme, empty authPolicy, `noDA`, `userWithAuth`, unique zeroed. **verified**.
  With the handle empty, `tpm2_get_or_create_srk` runs `CreatePrimary` in the owner hierarchy and
  `Esys_EvictControl` with the owner as authoriser, so it relies on an empty owner auth. **verified**. With the
  handle occupied it compares nothing and uses whatever is there (on `TPM2_RC_NV_DEFINED` it re-reads the handle).
  **verified**. `systemd-tpm2-setup` pins the SRK public key in `/run/systemd/tpm2-srk-public-key.pem` and under
  `/var/lib/systemd/`; a mismatch with the `/run` copy is fatal. **verified**. No evict, clear or flush of the SRK
  was found in the files read; the last 130 KB of `tpm2-util.c`, the package scripts, and the `cryptenroll` and
  `creds` sources were not read, so "never evicts on removal" is **inferred**. systemd's "use whatever is there" is
  exactly the behaviour Custodio must not copy.
- `tpm2_createprimary` (tpm2-tools 5.7): name hash SHA-256, RSA 2048 and ECC P-256 are the defaults, a restricted
  parent gets `aes128cfb`. **verified**. Its default attributes do not include `noDA` (**inferred**; the
  experiments pass the attributes explicitly).

### Decision

Applying the SPEC default (no NV write, no secret in the service, an unusable owner hierarchy fails the import and
never falls back): candidate B. A is rejected because it needs an NV write, a provisioning step that needs the
owner password when one is set, a shared handle with a foreign-key case, and an eviction rule on removal. B costs
4 ms per creation on ECC P-256 (RSA 2048 about 25 ms on `swtpm`, far more on hardware), fails with `0x9A2` when the
owner has a password, and loses every wrapped key at `TPM2_Clear`, as A does too. The template is the ECC P-256 TCG
SRK template above, frozen in code with its name checked in a test; F111 runs the probe on a hardware TPM and
confirms the cost and that ECC P-256 is available there before the choice is recorded in `docs/decisions.md`. The
service never writes persistent state to the TPM.

Decision: a primary recreated on each use from the fixed TCG SRK template, ECC P-256 (no persistent SRK at 0x81000001)
