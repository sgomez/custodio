## F189

Why the classifier answered `unknown`, then `not-encrypted`, for device `252:0` (SPEC Design 4, open question 1). Machine: the
dev container (Debian 13, systemd 257 text, kernel 7.0 sysfs, uid 1000), `crates/custodiod/src/storage.rs` at v0.8.0 = HEAD
(`git diff v0.8.0 HEAD -- crates/custodiod/src/storage.rs` is empty; `git merge-base --is-ancestor 751d7f7 v0.8.0` holds), so
two 0.8.0 starts ran the same LVM code. The F180 rules stand: nothing here showed one wrong.

**Conclusion.** The cause was **not reproduced** and no path of `storage.rs` flips for a mounted, complete `252:0`.
- **Verified:** a complete chain always gives `not-encrypted`; every incomplete read gives `unknown` (table below).
- **Verified** (Linux v6.12 `drivers/md/dm.c`, `dm_setup_md_queue`): the kernel does `add_disk()` (so `/sys/dev/block/252:0`
  exists), then `bd_link_disk_holder` for every table device (so `slaves/` is full), and only then `dm_sysfs_init` (so `dm/` and
  `dm/uuid` appear). A reader can see `unknown` only in that kernel-internal gap, before the device is resumed, so before any mount.
- **Verified** (systemd v257 `src/core/unit.c` `unit_add_exec_dependencies`, loop over `directories[dt]`): `StateDirectory=` adds
  `RequiresMountsFor=` on the state directory, so the unit waits for the mount of `/var/lib/custodio`, hence for the LV.
- **Inferred:** the two answers came from two different states of the machine that the report does not record (for example
  another mount under the state directory, a different filesystem, or a missing sysfs file), not from a race with udev or LVM
  activation. udev is not read by the classifier (no `/dev/mapper`, no udev database); only sysfs and mountinfo.
So the cause is **inferred**, and the answer is route 2 below.

**Code paths to `unknown`** (`storage.rs`; reproduced on a fixture copy of the real `252:0` chain, below):

| Path | Can differ between two starts? |
|---|---|
| `fs::canonicalize(state_dir)` fails (`STATE_DIRECTORY` unset uses `/var/lib/custodio`; several entries joined by `:`; directory not there) | no for the unit: systemd creates it before `exec` |
| `mounted_device`: no covering mount, fstype not on the block list, or device `0:N` | yes, if the mount at the longest prefix differs |
| `fs::canonicalize(/sys/dev/block/252:0)` fails | only in the kernel gap above |
| `walk_node` on the dm node: `dm/` absent, `dm/uuid` unreadable or empty, prefix not `LVM-`/`CRYPT-LUKS*`/`PLAIN` | only in the kernel gap (uuid is set at create, read under a lock) |
| `members`: `slaves/` unreadable or empty, members disagree | only in the kernel gap; mixed crypt/plain stays `unknown` by rule |
| partition → disk: no `dev`, `partition` on the disk, no `device` link, `slaves/` of the disk non-empty | no |
| `statx` fscrypt check fails or says encrypted | no (`statx` is in `@system-service`) |
| the default `StateStorage::Unknown` in `dbus.rs:276` | ruled out: `startup.rs:112` classifies and `.with_state_storage(storage)` (line 130) sets the real value |
| a different build at the two starts | ruled out for LVM: the LVM branch has been the same since 751d7f7, inside 0.8.0 |

Unit sandbox (`ProcSubset=pid`, `ProtectKernelTunables`, `PrivateDevices`, `PrivateUsers=identity`): the F180 text holds (reads
allowed); **inferred**, not run under the real unit (none can start here). It would give the same answer at every start anyway.

**Reproduction** (scratch, nothing committed; example target in `crates/custodiod/examples`, run with
`cargo run -p custodiod --example scratch_f189`, then deleted). It builds a fixture root: `proc/self/mountinfo` with
`1 0 252:0 / <state> rw - ext4 /dev/mapper/vg-root rw`; `sys/dev/block/{252:0,259:2,259:0}` → `dm-0` (`dm/uuid`, `slaves/nvme0n1p2`)
→ partition `nvme0n1p2` (`partition`) → disk `nvme0n1` (`dev`, `device`), the real shape of
`/sys/dev/block/252:0` here (`dm/uuid` is `LVM-Mc0k...`, `slaves` is `nvme0n1p2`, whose disk has `device`), and called
`classify_with(root, state, &|_| Ok(false))`. Lines printed:

```
A complete chain               -> NotEncrypted
B dm/uuid empty                -> Unknown
C dm/uuid missing              -> Unknown
D slaves/ empty                -> Unknown
E dm/ directory absent         -> Unknown
F disk without device link     -> Unknown
G disk with slaves             -> Unknown
```
The real sysfs under a fake mountinfo (`252:0` ext4, or `259:2`) gave `NotEncrypted`; no covering mount, and a tmpfs over the
state directory, gave `Unknown`. This container cannot create a dm device: no `dmsetup`, `sudo -n` fails, no `/dev/mapper`
(`losetup` exists, not used).

Decision: route 2. F196 keeps `unknown` and exposes a reason: a read-only, bus-only property with a short enumerated value per
cause (no covering mount or unreadable mount table; filesystem not on the block list or anonymous device; sysfs chain missing or
incomplete; layer not classified (md, other dm, no hardware link); members disagree; fscrypt not excluded), added under the
`docs/api.md` compatibility rule, so `doctor` can say what to do; no unit setting is needed and none is added (ordering is already
implied by `RequiresMountsFor=`, `systemd-udev-settle.service` is deprecated and would slow boot, and no sandbox directive changes);
`unknown` is never turned into `encrypted`.
