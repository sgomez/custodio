## F191

Shell completion locations per package format, and key ids for completion without polkit (SPEC Design 3 "Completions", open question 4,
acceptance 12). Run 2026-11-15 in the dev container (kernel 7.0.0-43, podman 5.4.2, nfpm 2.48.0 as pinned in `mise.toml`) and in the five
base images (`debian:13`, `ubuntu:26.04`, `fedora:44`, `almalinux:10`, `archlinux`, current at the run) with bash-completion, zsh and fish
installed from each distribution.

Decision: bash `/usr/share/bash-completion/completions/custodio` and fish `/usr/share/fish/vendor_completions.d/custodio.fish` in all three formats; zsh `_custodio` in `/usr/share/zsh/vendor-completions/` in the .deb (debian13, ubuntu2604) and in `/usr/share/zsh/site-functions/` in the .rpm and the Arch package (fedora44, alma10, arch), so `packaging/parity-exceptions.txt` gets `/usr/share/zsh/vendor-completions/_custodio | deb | presence | …` and `/usr/share/zsh/site-functions/_custodio | rpm,arch | presence | …` (the entry for `docs/decisions/packaging.md` is written by this feature, F205 writes none); key ids come from a hidden subcommand `custodio __key-ids` (calls `ListKeys` only, stdout one id per line sorted, nothing else; on any failure stdout empty, stderr empty, exit 1) with a 2 s call timeout inside `custodio` and none in the completion files; completion files call it as `custodio __key-ids 2>/dev/null` and treat each line as data; acceptance 12 bounds, for the whole completion from the real shell: service absent ≤ 1 s, service running with 200 keys ≤ 2 s, service hung or activation slow ≤ 4 s offering nothing; zsh users of debian13, fedora44 (new users only), alma10 and arch need `compinit` in their own `~/.zshrc` (only ubuntu2604 runs it globally), and F205's docs say so.

### Conclusions

1. **Locations (verified, 15 rows below).** bash and fish load from the same directory on all five targets. zsh differs: `vendor-completions`
   is in the default `fpath` on Debian and Ubuntu only (their zsh patch), `site-functions` on Fedora, Alma and Arch only; neither is in the
   other family's `fpath`. A stub `_custodio` was found by `compinit` only in the directory listed in the table (both stubs were present).
2. **Formats (verified).** One nfpm `contents` list gives identical paths for bash and fish; zsh needs `packager:`-filtered entries, as the
   file already does for the daemon and the unit. The forced difference is the zsh path of the .deb against the .rpm and Arch package: two
   presence exceptions (`scripts/check_parity.py` compares presence per path; a path in only some formats is a presence difference).
3. **Both zsh directories in every format (rejected).** Each file would lie in a directory the target's `fpath` never reads (a dead copy
   on every machine), and the .rpm and Arch package would have to own `/usr/share/zsh/vendor-completions`, which no package of fedora44 or
   alma10 owns (owner column below), so `dnf remove` would leave it (F49) unless an extra `type: dir` entry is added. The exception is the
   smaller change and each shipped file is in the loading path of every target its format serves.
4. **"No configuration" (verified).** bash: `bash -ic` of a new user has the default loader (`complete -F … -D`) on all five targets, which
   loads `completions/custodio` on first use (arch: `/etc/bash.bashrc:23` sources it; Fedora and Alma `/etc/profile.d/bash_completion.sh`).
   fish: nothing to configure; it autoloads `custodio.fish` once `custodio` is on `PATH` (without a `custodio` executable, fish 4.2 and 4.6 did not
   offer the stub: **verified**, `/usr/bin/custodio` is always installed). zsh: `compinit` is not run by default except on Ubuntu
   (`/etc/zsh/zshrc:108-112` runs it when `/etc/os-release` has `ID*=*ubuntu`); Debian's `/etc/zsh/zshrc` has the same block but skips on
   Debian (stub not registered: `comps=none`); Fedora's and Alma's `/etc/skel/.zshrc` has `compinit` (lines 7-8) so only users created
   from the skeleton have it, not `/etc/zshrc`; Arch has none. Docs must tell Debian, Arch and older Fedora/Alma users to add
   `autoload -U compinit; compinit`.
5. **Key ids (verified).** `custodio list` is not usable as is: it also calls `StateStorage` (`bus.rs:70-80`), parses every certificate, and
   writes a warning on stderr (`storage.rs:56-60`). `ListKeys` itself asks no polkit (`docs/api.md:96-104`, table `docs/api.md:306`) and the
   handler reads the store only (`crates/custodiod/src/dbus.rs:398-407`, `dbus/list.rs:22-49`: no `authorize`, no audit entry, no write).
   The client path `main.rs:55` (`DbusImporter::system`) → `bus.rs:56-70` (`call_method("ListKeys")`) opens no agent (`main.rs:56-58` starts
   one only through `with_agent` for import and delete) and writes nothing. Measured: a fake polkit in the rig logged 200 calls while the
   200 keys were imported and none during 12 `custodio list` runs.
6. **No client timeout today (verified).** A service that owns the name but is stopped (`SIGSTOP`) leaves `custodio list` blocked: it had
   not returned after 40 s (`timeout 40` killed it, rc 124). An activatable name whose `Exec` never claims it fails after the daemon's own 25 s
   (rc 1, "the system bus did not carry the call"). So a timeout must be added; it lives in `custodio` (the one place the three shells
   share, with no dependency on `timeout(1)` in a completion file, and unit-testable); 2 s is 45 times the 200-key maximum below.
7. **Ids are data (verified in the code, proven by F205's test).** An id is 1 to 59 bytes of `[A-Za-z0-9_-]` (`docs/api.md:9`), checked at
   import. `__key-ids` additionally drops any line outside that grammar, so a terminal or shell metacharacter never reaches the shell.
   bash: `while IFS= read -r id` into `COMPREPLY` filtered by `[[ $id == "$cur"* ]]` (never `compgen -W`, which expands its word list);
   zsh: `compadd -- ${(f)"$(custodio __key-ids 2>/dev/null)"}` (expansion results are not re-parsed); fish: `-a '(custodio __key-ids 2>/dev/null)'`
   (each output line is one literal candidate).

### Locations table (commands run in each container; `-` = not in the path)

| target | bash `pkg-config --variable=completionsdir bash-completion` | zsh `zsh -ic 'print -l $fpath'` (vendor / site) | fish `$__fish_vendor_completionsdirs` (`/usr/share/fish/vendor_completions.d`) |
|---|---|---|---|
| debian13 | `/usr/share/bash-completion/completions` | vendor yes / site - (`/etc/zsh/zshrc:108-112` ubuntu only) | listed |
| ubuntu2604 | same | vendor yes / site - (`compinit` run by `/etc/zsh/zshrc`: stub registered) | listed |
| fedora44 | same | vendor - / site yes (`/usr/share/zsh/site-functions`) | listed |
| alma10 | same | vendor - / site yes | listed (fish 4.2.0 from **EPEL**, `dnf info`: `From repo: epel`; not in BaseOS/AppStream: `Unable to find a match: fish`) |
| arch | same | vendor - / site yes | listed |

Directory owners (`dpkg -S`, `rpm -qf`, `pacman -Qo`): fedora44 and alma10: `filesystem` owns the bash, zsh `site-functions` and fish
directories, `/usr/share/zsh/vendor-completions` has no owner (does not exist); debian13: `bash-completion` (and others) own the bash
one, `fish-common` the fish one, `sqv` the zsh vendor one; arch: `bash-completion`/`audit`, `fish`/`curl`, `curl`/`kmod` (shared parents).
The alma10 fish directory is `filesystem`'s and the path comes from fish upstream; the package source (EPEL) is third party, so that row
is verified for fish 4.2.0 from EPEL only. Packages need not depend on any of the shells: no `type: dir` entry is needed for the
.rpm (every directory is `filesystem`'s on fedora44 and alma10, and the .rpm lists none); deb and Arch list their parents.

### nfpm reading (verified)

A scratch `nfpm.yaml` with the five entries (bash, fish unfiltered; zsh `packager: deb` to vendor-completions, `packager: rpm` and
`packager: archlinux` to site-functions) built three packages with nfpm 2.48.0; listings: .deb `./usr/share/zsh/vendor-completions/_custodio`,
.rpm and Arch `…/zsh/site-functions/_custodio`, the other two files identical in all three. `packaging/nfpm.yaml` already uses `packager:`
for the daemon, units and hooks, and `scripts/check_parity.py:7-9` ignores a directory listed in only some formats when it is 0755 root root.

### Cost and bound (verified, rig: the real service on a private `dbus-daemon`, release `custodio list`, `DBUS_SYSTEM_BUS_ADDRESS`)

Each row at least 10 runs (min / max, ms); the 200-key service held `key-000`…`key-199` (P-256). Hardware: the dev container.

| case | runs | min | max | result |
|---|---|---|---|---|
| running, 1 key | 12 | 3 | 8 | rc 0 |
| running, 200 keys | 12 | 34 | 43 | rc 0, 200 ids |
| bus socket missing | 12 | 2 | 2 | rc 1, stdout empty, stderr "cannot reach the system bus: …No such file" |
| bus there, name not owned or activatable | 12 | 2 | 3 | rc 1, stdout empty, stderr "not running on the system bus" |
| activatable, slow (`.service` `Exec` is a script that sleeps 3 s, then runs the service; fresh daemon per run) | 10 | 3009 | 3010 | rc 0, ids shown after the wait |
| activatable, never claims (`Exec` sleeps 100) | 1 | 25029 | 25029 | rc 1, stdout empty |
| name owned, process stopped | 1 | >40000 | | killed by `timeout` |

`custodio list` includes certificate parsing and the second call (`StateStorage`), so `__key-ids` is no slower. Bounds: absent ≤ 1 s is
about 300 times the measured maximum of 3 ms and leaves room for shell start-up and a loaded CI machine; running ≤ 2 s is 45 times 43 ms
(also the call timeout); hung or slow ≤ 4 s is the 2 s timeout plus the same 2 s margin. For the in-`custodio` timeout F205 tests the
stopped-process case (a rig that owns the name and never replies).

Limits: the `custodio` binary was the workspace's release build of the same day, not rebuilt after F190; `bash -ic` rows ran as a new user
with the skeleton files; Alma and Fedora shells ran as root with `HOME` of that new user.
