## F150

KVM for the VM target (SPEC "Open questions": KVM on the hosts). Written 2026-11-08 by a session inside the dev container as it was **before** the
rebuild this feature asks for; a later `ls -l /dev/kvm` in the rebuilt container rightly differs from the quotes below.

Conclusion:
- The dev container cannot open `/dev/kvm`: the device is not there. **verified** (below).
- The host's `/dev/kvm`, its permissions and whether the engine host offers it are not visible from the container: **inferred**. A person pastes
  `ls -l /dev/kvm; id` from the host (`BLOCKED.md`); on a Mac, `podman machine ssh ls -l /dev/kvm`. A missing device there is a host question for a person.
- Exposing it: `harness/run.sh` adds `--device /dev/kvm --group-add keep-groups` to the rootless podman run when the device exists on the host
  (**inferred**, podman-run(1) and containers/podman#29208). `--device` bind-mounts the host node for rootless podman; with mode 0660 `root:kvm`
  the user's group access is lost in the user namespace unless `keep-groups` (crun only) keeps it; with mode 0666 `--device` alone suffices.
- GitHub-hosted runner (`ubuntu-26.04` is a standard label, **inferred** from docs.github.com "GitHub-hosted runners"): a job must let user
  `runner` open `/dev/kvm` with a udev rule, then reload and trigger (**inferred**, github.blog changelog 2024-04-02, not run from here):
  `echo 'KERNEL=="kvm", GROUP="kvm", MODE="0666", OPTIONS+="static_node=kvm"' | sudo tee /etc/udev/rules.d/99-kvm4all.rules`,
  `sudo udevadm control --reload-rules`, `sudo udevadm trigger --name-match=kvm`. The docs do not say every standard runner has the device:
  the job starts with `ls -l /dev/kvm` and fails, naming it, if absent. Nothing here measured software emulation, and none is offered.
- Packages of `debian:trixie` (**inferred**, packages.debian.org file lists, 2026-11-08): `ubuntu-keyring` 2023.11.28.1-0.2 ships
  `/usr/share/keyrings/ubuntu-cloudimage-keyring.gpg`; `ovmf` 2025.02-8+deb13u1 ships `/usr/share/OVMF/OVMF_CODE_4M.fd` and `OVMF_VARS_4M.fd`
  (F151 boots with these); `cloud-image-utils` 0.33-1 ships `/usr/bin/cloud-localds`; `qemu-system-x86` 1:10.0.13. `gpgv` is not on this container's
  PATH (below), so the Containerfile installs it. Whether `-accel help` lists `kvm` is checked by `just vm-host-check` on the rebuilt container.

Evidence, this container (**verified**, 2026-11-08, user `dev`):
- `ls -l /dev/kvm` → `ls: cannot access '/dev/kvm': No such file or directory`; `ls /dev` lists console core fd full mqueue null ptmx pts random shm stderr stdin stdout tty urandom zero.
- `id` → `uid=1000(dev) gid=1000(dev) groups=1000(dev)`; `grep -c -E 'vmx|svm' /proc/cpuinfo` → 12 (the CPU has the flag; the node is what is missing).
- `command -v` finds only `swtpm`; no qemu, `/usr/share/OVMF`, `cloud-localds` or `gpgv`. `just vm-host-check` fails naming each.

Decision: dev container: install `qemu-system-x86`, `qemu-utils`, `ovmf`, `cloud-image-utils`, `ubuntu-keyring`, `gpgv`, and `harness/run.sh` passes `--device /dev/kvm --group-add keep-groups` to podman when `/dev/kvm` exists on the host (a person rebuilds, and fixes the host if it has none); CI: the VM job runs the udev step above on `ubuntu-26.04`, then `just vm-host-check`, with no fallback to software emulation.
