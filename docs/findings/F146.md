## F146

**Verified** (rootless podman 2026-11-06, kernel 7.0, dbus-broker 37 on arch and fedora44): the parallel `just e2e` failures of
attempts 1–3 came from the host's per-user inotify instance limit (`fs.inotify.max_user_instances`, 128 by default), not from
Custodio. Every container's systemd, journald, logind and dbus-broker take instances from that one limit; with 6 runs at once it
runs out. A bus reload then cannot open its directory watch, the bus keeps the old configuration and the removed name stays
activatable (`removal-not-activatable`); `systemctl` itself fails the same way, and logind lost a session once.
**Inferred**: the earlier `cli-import-pkttyagent-wrong-password` timeout (attempt 2, no transcript kept) had the same cause.

Evidence, `.harness/logs/*F146*verify.log`:

- s3 (arch): `remove output: Failed to allocate directory watch: Too many open files`.
- s4 (arch, alma10): `dbus-broker-launch: ERROR dirwatch_new @ ../src/util/dirwatch.c +39: Too many open files`, then
  `Job for dbus-broker.service failed` and `FAIL: com.rfirma.Custodio1 is still activatable after the remove`; alma10 also
  `FAIL: no logind session (XDG_SESSION_ID is empty)`.
- s5 (fedora44): the same `Job for dbus-broker.service failed`; no journal, because the diagnostic matched `^Job for` and dnf5
  prefixes scriptlet output with `>>> ` (fixed).
- One lone `just e2e-cases fedora44 'removal-*'`: ~12 instances in the container's user namespace at peak (18 with the host's 6).

Consequence: `e2e/run.sh` refuses to start when the limit is below 32 per run at once plus 64. With 6 at once that is 256, so a
host needs `sysctl fs.inotify.max_user_instances=1024` (or a lower `E2E_JOBS`). CI runs one target per job and fits in 128.
