# F49 — End-to-end removal, purge and reinstall cases on every target

## Scope
Built here (SPEC design section 2 "Removal", "Purge", "Reinstall after removal"; section 4 "Lifecycle cases"; acceptance item 7):
- A removal case run by the shared guest on debian13, ubuntu2604, fedora44, alma10 and arch, with each target's own removal tool
  (`apt-get remove`, `dnf remove`, `pacman -R`), in a `remove.sh` next to each target's `install.sh`. `rpm-ostree uninstall` has no target here and stays out.
- On debian13 and ubuntu2604 only, a purge case with `apt-get purge` (`purge.sh`), registered through the per-target `cases.list` that `run.sh` already appends
  (debian13 has one from F60; ubuntu2604 gets one). The other targets have no purge and no purge ids.
- After each removal (and each purge), a reinstall of the package with the target's `install.sh`, and the reinstall checks.
- The sequence runs inside the one guest run, after the upgrade case, from the state it leaves: N+1 installed, the keys imported by `import.py`, service running.
  On the deb targets: remove, check, reinstall, check, purge, check, reinstall, check. On the others: remove, check, reinstall, check.
- Ids registered in `e2e/cases.list` (all targets) and in the deb targets' `cases.list` (the purge and post-purge ones); a run that skips one without a `skip.list`
  entry fails, as for every case. No `skip.list` entry is added.
- Reuse, not copy, the helpers of F48 (`upgrade-lib.sh`: `snapshot_state`, `compare_state`, `compare_listing`, `upgrade-user.sh list|sign`); new checks go in a lifecycle
  library with a self-test run by the guest before it relies on it and by `just test-scripts`, like `upgrade-selftest.sh`.
- `scripts/test-e2e-host.sh` / `test-e2e-targets.sh` learn the new ids and files.

Left for other features: upgrade (F48), upgrade from cargo-deb (F60), the Ubuntu 24.04 refusal (F50), the removal notice under `rpm-ostree` (deviation in
`SPEC_DEVIATIONS.md`, F44), the package-level script tests (F43, F44, F58: they prove the scripts; this feature proves them on the real distributions with the real service).

Environment: F46-F48 ran `just e2e` on all five targets in this dev container with rootless podman, so the real runs are possible and required. Nothing new is needed
from the host. The builder confirms in each image that the removal tool runs non-interactively (`apt-get remove -y`, `dnf remove -y`, `pacman -R --noconfirm`).

Size: about six steps; no split.

## Steps
- [ ] Tests first, red: (a) the self-test of the lifecycle checks with fixtures, one control per rejection (see Evidence); (b) host tests: new ids in `cases.list`, the purge ids only in
      debian13 and ubuntu2604 `cases.list`, `remove.sh` on all five targets, `purge.sh` only on the two, an omitted id fails the accounting.
- [ ] Lifecycle library and self-test: the list of packaged files taken from the package file (not from the installed system), the checks of Evidence as functions that print one
      message per problem, a static check of the lifecycle section for forbidden commands.
- [ ] `remove.sh` for the five targets and `purge.sh` for the two deb targets; the removal output (stdout and stderr) is captured by the guest, not discarded.
- [ ] The guest section (between `# BEGIN lifecycle-case` / `# END lifecycle-case` markers, called from `guest.sh` after the upgrade case, main mode only): snapshot, removal, checks, reinstall, checks; purge cycle on the deb targets.
- [ ] Run `just e2e <t>` per target until green. A failure is a defect of the case, of a shared script wrong for one distribution (small fix, others stay green), or a real defect of the package (fix it with its own test; BLOCKED.md if it is a decision). Never weaken a check or skip.
- [ ] Update docs that list the e2e cases; a `docs/findings.md` entry only if the run showed something non-obvious. Real run, required: `just e2e` (all five); paste exit status, the new `E2E-CASE` lines per target and the evidence values below into `PROGRESS.md`; run `verify`.

## Evidence
- Service not running after removal and after purge → real run → `systemctl is-active custodio` is not `active` and `MainPID` is 0; the pid recorded before is gone (`/proc/<pid>` absent). Fixture control: an active unit, or a live old pid, is rejected. Before removing, the case asserts the service was active (so the check can fail).
- No packaged file remains → real run → the non-directory entries and the directories owned only by the package are listed from the package file with the target's tool (`dpkg-deb -c`, `rpm -qlp`, `pacman -Qlp`); count asserted > 0 and includes `/usr/lib/custodio/custodiod`, the PKCS#11 module, the unit and the D-Bus policy/service files; after removal (and after purge) none exists (`test -e` and `-L`). Control: a fixture tree where one file is left (and one where only a directory is left) is rejected. A file the tool keeps on deb `remove` (conffile) is not excused silently: the builder states which files, if any, remain after `remove` and that purge removes them; SPEC says removal removes every packaged file, so a surviving file is a defect or a recorded deviation, not a silent exception.
- `com.rfirma.Custodio1` cannot be activated → real run → before removal, as the user, the name is listed by `busctl --system list --activatable` (or the equivalent) and a call to it activates the service; after removal and purge the name is not activatable and a call fails with a not-activatable / ServiceUnknown error, and no `custodiod` process exists afterwards. Control: a fixture listing that still contains the name is rejected.
- State directory and key files present and unchanged → real run → `snapshot_state` of `/var/lib/custodio` (through the link to `/var/lib/private/custodio`) before the removal equals the one after it, and after the purge (sha256, uid, gid, mode, directories included; count asserted > 0 and includes the two keys' files); the link/directory itself still exists. Controls from F48's self-test (flipped byte, changed mode, owner, added, removed file, directory mode) are run against these calls too, and a fixture where the directory is gone fails.
- `custodio` account still exists → real run → `getent passwd custodio` succeeds after removal and purge, with the uid and gid recorded before. Control: a fixture lookup that fails, or another uid, is rejected.
- The removal output said where the keys are → real run → the captured output of the removal tool (stdout and stderr together, and for purge the output of `apt-get purge`) contains `/var/lib/custodio` and says the keys are still on disk; the case fails on an empty capture. Control: an output without the path, and an empty output, are rejected. Where a target's tool does not show scriptlet output on its terminal, the builder finds where it does appear (for example the tool's log) and says so; a notice that is not visible to the person running the command does not pass, and is a package defect.
- Reinstall lists the same keys → real run → after reinstalling with `install.sh`, the listing through the PKCS#11 module as the user (`upgrade-user.sh list`) is identical to the one taken before removal and names `rsa1` and `ec1`; the state snapshot is again equal. Control: a listing without a key, or empty, fails (F48's `compare_listing`).
- Reinstalled keys sign with polkit asked, without a new import → real run → `upgrade-user.sh sign`: one approved RSA and one approved ECDSA signature verify against the public keys; the agent's request counter rises by one per signature; with the agent set to deny a signature fails and the counter still rises by one. No import ran: a static check of the lifecycle section (between its markers; fails if a marker is missing or the section is empty; the self-test feeds it a section containing `import.py` and expects failure) finds no `import.py`, `pkcs11-tool` write/import option, `custodio import`, nor `systemctl start|restart|stop|daemon-reload|reload` / `kill` / `pkill` of the service in the section, so the stop of the service is the package's doing and not the test's.
- The same holds after purge on debian13 and ubuntu2604 → real run → every removal check above and every reinstall check above has an id for the purge cycle (`purge-*`, `reinstall-after-purge-*`), run through `apt-get purge`. Control: `purge.sh` is a different command from `remove.sh`, asserted by the host test (a `purge.sh` that only removes fails the host test), and the case checks that the dpkg status of the package after purge is not-installed with no residual config state (`dpkg-query -W` reports none / `dpkg -s` fails).
- The package is installed again by the target's tool → real run → after each reinstall the package database (`dpkg-query`, `rpm -q`, `pacman -Q`) reports N+1, and absent after each removal (`rpm -q` / `pacman -Q` / `dpkg -s` fail), so a no-op removal fails.
- The cases are accounted on every target → REQUIRED real `just e2e` → exit 0, "e2e: passed: alma10 arch debian13 fedora44 ubuntu2604"; every new id appears as run (not skipped) in `target/e2e/<t>.log`, purge ids on debian13 and ubuntu2604 only.
- Shellcheck and syntax → `just check`, `bash -n e2e/*.sh`; `verify`'s greps for `purge` and `reinstall` in `e2e` hold but are not the proof: the real run is.
