# F203 — `custodio doctor`: Firefox, the persistent journal, the state directory's storage, and the whole command

## Scope

Built here, on F202's `doctor_decide` (pure) and `doctor_cmd` (observes, prints):

- Check 4 (module registered in Firefox), read-only, per profile, with **the same discovery as `custodio register`** (`register_discover::discover`
  and `register_native::parse_entries`/`plan`, and the snap copy's comparison, the p11-kit decision `register` makes): native profiles, the
  Firefox snap's profiles and its copy of the module (a stale copy is `not ok`), and a p11-kit system, where Firefox sees the module without
  registration (`ok`, the line says why). Each profile gets its own line. No profile at all is `ok` with the text that there is none (not a failure,
  exit status unaffected). A malformed or unreadable `profiles.ini`/`pkcs11.txt` is `could not check` naming the file. The fix names `custodio register`
  (for a snap copy, also that Firefox must be restarted, as `register` says). Nothing is written, no `modutil` is run.
- Check 5 (persistent journal) as `docs/findings/F190.md` decided (its `Decision:` line is the specification; the builder does not re-research it): a
  new pure module `journald_conf` in custodio-cli (main file and drop-in precedence, `[Journal]`/`Storage=` parsing, last valid wins, the
  compiled-default comment, the table of S × `stat(/var/log/journal)`), and a thin reader in `doctor_cmd` that does file reads and `stat`s under the
  fixture root (never `journalctl`, D-Bus, `/run/log/journal`). Each non-persistent state prints the documented fix of the finding and the
  `file:line` that set it; every "could not check" case of the finding is `could not check` with its reason. Fuzz target `journald_conf`
  (`crates/custodio-cli/fuzz/fuzz_targets/journald_conf.rs`, a `[[bin]]` in that Cargo.toml, a `fuzz_journald_conf` entry point in the library like F197's
  `fuzz_pam_file`) and the name added to `fuzz-smoke`'s `expected` list in the justfile.
- Check 6 (state directory storage): asks the service `StateStorage` and, when it is `unknown`, `StateStorageReason` (`docs/api.md`, F196's route),
  both read-only, bounded wait (as F202's 1.5 s), no polkit. `encrypted` → ok; `not-encrypted` → `not ok` with the full-disk encryption advice (the
  README anchor `storage::README_ANCHOR`); `unknown` → `not ok` ("not known to be encrypted") with the reason's text and what to do for each reason value of
  `docs/api.md`; a value it does not know, an empty/absent reason (`UnknownMethod`: a service that predates it) → still `unknown`, never `encrypted`. The
  service unreachable (no bus, no owner, no answer in time, an error) → `could not check` with the reason and its fix (start/enable the service, install the package).
- The exit status: F202's `exit_status(broken_include, later)` now receives the real states of checks 4 to 6; `Report::exit_status` passes them. 0 only when
  no include is broken and checks 4, 5, 6 are all `ok` (so "could not check" counts there); checks 1 to 3 unsatisfied never count. The output lists all six checks
  in order (a broken include still first). Help text and `packaging/custodio.1` say six checks (the existing parity test in `tests/help.rs` covers them).
- Fixture seams: the existing `CUSTODIO_FIXTURE_ROOT`/`CUSTODIO_FIXTURE_EUID` and `HOME`/`DBUS_SYSTEM_BUS_ADDRESS`; no new variable expected (if one is needed, the
  three places of F202 are updated).

Left to other features: doctor on each target in containers and "leaves /etc and home unchanged" on real systems (F204); user docs (F207); a real Firefox, a real
journald and a real encrypted disk are not run here (fixtures and a fake service; F190 and F196 already settled the real behaviour). Check 3's per-state texts and checks 1 and 2 are
proven by F202; here `doctor_acceptance` only proves them again as part of the whole output (one fixture per run, several checks varied at once).

Environment: nothing new. Fake `net.reactivated.Fprint` and a fake `com.rfirma.custodio` service on a private `dbus-daemon` are already in
`tests/fprint_fixture` and `tests/fixture` (F202, F197, storage warning tests); `cargo fuzz` and the nightly toolchain are what `fuzz-smoke` already uses for
`pam_file`, the same recipe and crate. `modutil` is not needed (read-only).

Sizing: six steps, no split of the feature.

Costs (estimates from `doctor_reader` 1.5 s/17 cases and `doctor_polkit` 0.02 s):

| Test | Time | How it runs |
|---|---|---|
| `tests/doctor_firefox.rs` (about 15 cases, each runs the binary on a fixture home; no bus: `DBUS_SYSTEM_BUS_ADDRESS` points to a missing socket so check 1 fails at once) | 1 to 2 s | own binary, parallel tests, own fixture dirs |
| `tests/doctor_system.rs` (about 30 cases: the journald table on fixture roots with no bus, about 8 with a fake service on a private bus, 0.2 s each; one slow-answer case 1.5 s) | 2 to 3 s | own binary, parallel |
| `tests/doctor_acceptance.rs` (about 12 whole-command runs, each with its own bus and fixture; checks 1 to 6 varied together so every state of every check occurs) | 2 to 4 s | own binary, parallel |
| unit tests of `journald_conf` and the new `doctor_decide` parts, only where the files above do not reach | under 1 s | lib binary |
| new fuzz target `journald_conf` | build with `just fuzz-build`; one more target in `fuzz-smoke` (seconds, same -runs as the others) | in `verify` only |
| `just mutants-diff F203` | about 150 to 250 mutants (three new/extended modules), 3 jobs, 15 to 30 min | one command; if it would pass 30 min the builder splits it with `--file` per module and says so in PROGRESS.md |

No e2e case, no script. Nothing exceeds `budgets.tsv`.

## Amendments

- Check 4, p11-kit and "no `modutil` run" (found while reading `register_modutil.rs`): `register`'s p11-kit decision (`docs/findings/F172.md`, Decision) *is* a `modutil -create -force` plus `modutil -list` in a private scratch directory under the temporary directory, and a file-based rule was refuted there (Ubuntu ships `nss.config` and NSS ignores it). So doctor reuses that probe (`register_modutil::nss_loads_p11_kit`, not a second rule) and only when some native profile has no Custodio entry in `pkcs11.txt`; it never runs `modutil` on a profile directory. The "no `modutil` run" evidence becomes: the stub on `PATH` records its arguments, and every recorded run is a scratch-directory `-create`/`-list`, none names a fixture directory; with every native profile registered it is not run at all. A probe that fails leaves the profile `not ok` with the fix naming `custodio register` (which reports the `modutil` problem itself).
