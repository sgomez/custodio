# F29 — End-to-end: journal entries of custodio.service

## Scope
Extends the `just e2e` suite with the journal checks of SPEC acceptance 7 and 8. Nothing runs here
(the dev container has no systemd container engine; F31 runs `just e2e`), so the work is writing the
checks, running everything that can run locally, and recording in PROGRESS.md what only F31 can show.
No change to the service, the module or the M0/F28 assertions (`user.sh`, `composed.sh` stay as they are
except one added `source` line in `user.sh`, and added lines in `guest.sh`). Acceptance 9 (fail closed
when the entry cannot be written) is F25 and is not repeated here.

Design (the suite already splits root work in `guest.sh` and the user session in `user.sh`):
- **Cases** (`e2e/journal.sh`, sourced by `user.sh` after `composed.sh`, runs as alice with the agent
  registered). Every case is one signature by its own process, started through a wrapper
  `sh -c 'echo $$ > "$1"; shift; exec "$@"'` so the recorded pid is the pid that talks to the bus (a new
  pid per case, which also separates the cases in the journal). A case appends a line
  `<expected outcome> <key id> <pid> <uid>` to `$WORK/journal.cases` (uid from `id -u`). Cases:
  approve and deny on `rsa1` (`pkcs11-tool`, `SHA256-RSA-PKCS`), approve and deny on `ec1`
  (`ECDSA-SHA256`), and one through OpenSSL with pkcs11-provider (multi-part, approve). Each uses its own
  fresh input of known content kept in `$WORK/evidence/`, and every produced signature is kept there too.
  The agent counter must be `before + 1` per case, so the entry count is tied to a real polkit call.
- **Polkit unavailable** (`e2e/unavailable.sh`, run by `guest.sh` as alice with `su -l` after `user.sh`
  has finished, because root must stop polkit and the agent's registration dies with it): `guest.sh`
  stops polkit and masks it with `systemctl mask --runtime` (D-Bus activation would restart it), restores it
  with `unmask --runtime` and `start` in an `EXIT` trap, and runs one `rsa1` signature with the same
  wrapper. Expected: `pkcs11-tool` exits non-zero, no output file, no agent request, ledger line with outcome
  `authorization_unavailable`.
- **Checker** (`e2e/journal.sh`'s root half, called from `guest.sh`, with the byte-level work in
  `e2e/journal.py`, run as `python3 -I`). Runs `journalctl --sync`, then the documented query of
  `docs/audit.md` (`_SYSTEMD_UNIT=custodio.service _UID=$(id -u custodio) MESSAGE_ID=29c3d30e6c4242406c6db3f120d36401`,
  `-o json` for fields, `-o export` for bytes), `--since` the start of the run.

Left out: unattended-run details of `just e2e` (F31), rate-limit behaviour, entries of calls refused during
validation (open question in SPEC), manual acceptance.

## Evidence
- Acceptance 7, approved → `journal.sh`: `rsa1` and `ec1` approve cases and the provider case; the checker
  filters the documented query with `CUSTODIO_PID=<pid>` and `CUSTODIO_KEY_ID=<key>` → exactly one entry
  per ledger line (zero or two fail), `CUSTODIO_OUTCOME=signed`, `PRIORITY=6`.
- Acceptance 7, denied → deny cases on `rsa1` and `ec1` (agent in `deny` mode, `pkcs11-tool` exits non-zero,
  no output) → exactly one entry for that pid, `CUSTODIO_OUTCOME=denied`, `PRIORITY=5`. The deny cases sign an
  input over 1024 bytes so `pkcs11-tool` does not retry (see the F28 note on one-shot fallback); for the
  single-shot mechanisms of M0 the retry does not exist.
- Acceptance 7, polkit unavailable → `unavailable.sh` with polkit stopped and masked, agent counter
  unchanged, `pkcs11-tool` fails → exactly one entry, `CUSTODIO_OUTCOME=authorization_unavailable`,
  `PRIORITY=4`. A restore check in `guest.sh` (`systemctl is-active polkit` after the trap logic) shows
  polkit is back before the final health check.
- Acceptance 7, uid and pid of the signing process → every checked entry has `CUSTODIO_UID` equal to
  `id -u alice` (not the service uid, not 0) and `CUSTODIO_PID` equal to the pid the wrapper wrote; the five
  cases have five different pids, so an entry cannot match the wrong case. The `MESSAGE` text contains
  `uid <uid> pid <pid> key <key>` with the same values.
- Acceptance 7, the key → `CUSTODIO_KEY_ID` is `rsa1` or `ec1` as in the ledger; the `rsa1` cases never
  match an `ec1` query.
- Acceptance 7, documented query → the checker uses `_SYSTEMD_UNIT=custodio.service`, `_UID=$(id -u custodio)`
  and `MESSAGE_ID=…` exactly as in `docs/audit.md`; `grep -F` of the `docs/audit.md` query string in
  `journal.sh` (checked in the step run) shows they agree. A forged entry is not part of the e2e (that is
  F24/F26 territory), but a self-test case with an entry lacking `_SYSTEMD_UNIT`/`_UID` must be ignored by the
  checker.
- Acceptance 8, raw/hex/base64 → `journal.py` builds needles from the evidence files: each input, its
  SHA-256/384/512 digest, its RSA `DigestInfo` (fixed prefixes for the three hashes + digest), every
  signature kept, and the string `e2e-password`; it searches the `-o export` bytes of the whole service
  journal (all entries of `custodio.service` since the start, including M0 and F28 traffic) for each
  needle as raw bytes, lower/upper hex, standard and URL-safe base64 (with and without padding, and for needles
  of at least 16 bytes also at the three byte alignments, as a substring that is stable under alignment). Any hit
  fails and names the needle kind, not its value. → exit 0 on the clean journal.
- Acceptance 8, the check can fail → `journal-selftest.sh` plants each leak form into a synthetic export and
  requires failure; a checker that always passes fails the self-test. The self-test also requires that the
  failure message does not print the needle.
- Acceptance 8, M0 check unchanged → the existing `journalctl -u custodio | grep e2e-password` in `guest.sh`
  stays (git diff shows only added lines).
- Suite is well formed → `just lint` (shellcheck on the new `.sh`, typos, check-files; new files `git add`ed
  because shellcheck sees tracked files) and `bash -n e2e/*.sh` → exit 0.
- Suite contains the journal checks → the feature's `verify` command → exit 0. `journalctl` alone already
  matches `guest.sh`, so also `grep -q 'CUSTODIO_OUTCOME' e2e/journal.py`, `grep -q authorization_unavailable
  e2e/unavailable.sh e2e/journal.sh` and `grep -qF _SYSTEMD_UNIT=custodio.service e2e/journal.sh` must succeed
  (the real checks, not just the words in a comment); `base64` appears in `journal.py` code, not only in a
  comment (`grep -n 'b64' e2e/journal.py`).
- Caveat → the dev container cannot run `just e2e`. PROGRESS.md states: not run; F31 must confirm that masking
  and stopping polkit makes the service answer `authorization_unavailable` (and not hang), that
  `su -l` + `exec` gives the pid the bus reports, that `journalctl --sync` is available in the container, and
  that `-o export` of the whole service journal is a size the checker can read.
