# F29 — End-to-end: journal entries of custodio.service

## Scope
Extends the `just e2e` suite with the journal checks of SPEC acceptance 7 and 8. Nothing runs here
(the dev container cannot run `just e2e`; F31 does), so the work is writing the checks, running
everything that can run locally, and recording in PROGRESS.md what only F31 can show. No change to the
service, the module or the M0/F28 assertions: `user.sh` and `guest.sh` get added lines only. Acceptance 9
is F25 and not repeated.

Files (cases and checker are separate, because cases run as alice and the checker as root):
- `e2e/journal-cases.sh`: sourced by `user.sh` after `composed.sh` (one added `source` line), as alice with
  the agent running.
- `e2e/unavailable.sh`: run by `guest.sh` as alice (`su -l`) after `user.sh` has finished.
- `e2e/journal-check.sh` + `e2e/journal.py`: run by `guest.sh` as root; `journal.py` (`python3 -I`) does
  the byte-level work and is a pure function of its inputs (export/json streams, ledger, evidence dir,
  service uid, unit name) so it can be self-tested.
- `e2e/journal-selftest.sh`: feeds `journal.py` synthetic streams; `guest.sh` runs it first.

Design:
- **Cases.** Each case is one signature by its own process via
  `sh -c 'echo $$ > "$1"; shift; exec "$@"' wrapper "$pidfile" pkcs11-tool ...` (the explicit `wrapper`
  is `$0`), so the recorded pid is the one the bus reports, and every case has a different pid. A case
  appends `<expected outcome> <key id> <pid> <uid>` to `$WORK/journal.cases` (uid from `id -u`), and
  checks the agent counter is `before + 1`. Cases: approve and deny on `rsa1` (`SHA256-RSA-PKCS`), approve
  and deny on `ec1` (`ECDSA-SHA256`, raw r||s, no `--signature-format`), and an approve through OpenSSL with
  pkcs11-provider on `rsa1` (multi-part). Inputs are fresh `head -c N /dev/urandom` files in
  `$WORK/evidence/`; deny cases and the unavailable case use more than 1024 bytes so `pkcs11-tool` 0.26.1
  does not retry a failed one-shot `C_Sign` as a second multi-part signature (`docs/findings.md`).
  Every signature produced by F29 is kept in `evidence/`. Every case, deny cases included, runs under
  `timeout 60`; `timeout` forks, so the wrapper's `$$` is still the signing pid. Exit 124 fails the case with
  a message "signature hung", separate from the expected non-zero exit of a denied call. M0 `user.sh`
  cases overwrite `$WORK/sig.bin` and F28 outputs are not all kept, so the acceptance 8 sweep covers only what
  is on disk: F29's kept signatures, the last `sig.bin`, `issued.der` and any F28 file still present; earlier
  M0/F28 signatures are not swept (said plainly in PROGRESS.md).
- **Polkit unavailable.** `guest.sh` records `start=$(date +%s)` before `dpkg -i`; after `user.sh` it stops
  polkit and `systemctl mask --runtime` it, asserts `systemctl is-active polkit` is non-zero (else fails
  with "polkit still active"), runs `unavailable.sh` under `timeout 60` (one `rsa1` `SHA256-RSA-PKCS` signature of
  a >1024-byte file, same wrapper, ledger line `authorization_unavailable`), then explicitly runs
  `unmask --runtime` and `start polkit` and checks `systemctl is-active polkit`. An `EXIT` trap repeats the
  restore only as a fallback.
- **Checker queries.** Entry checks use the documented query of `docs/audit.md` (`_SYSTEMD_UNIT=custodio.service
  _UID=$(id -u custodio) MESSAGE_ID=29c3d30e6c4242406c6db3f120d36401`, `-o json`, `--since "@$start"`),
  `journalctl --sync` first. The acceptance 8 sweep uses a wider query,
  `journalctl -u custodio.service -o export --since "@$start"` (same as the M0 `-u custodio` check), with no
  `MESSAGE_ID` or `_UID` filter. `-u` also matches `UNIT=`/`OBJECT_SYSTEMD_UNIT=` entries that systemd,
  journald or coredump write about the unit, besides non-audit lines of the service itself.
- **Exactly one.** `journal.py` selects audit entries by `CUSTODIO_PID` alone (not by key), requires exactly
  one per ledger line, and only then compares key, uid, outcome and priority with the ledger. A whole-run
  count in `journal-check.sh` compares the audit entries since `@$start` (documented query, no pid filter)
  with the agent's request counter read just before `unavailable.sh` plus one for the unavailable signature;
  step 2 confirms the counter's semantics (one per signature call). If they cannot be made to match, the
  fallback is: zero audit entries without `CUSTODIO_PID` and no pid outside the ledger and M0/F28 pids.

Left out: `just e2e` itself and the real run (F31), rate limiting, entries for calls refused in validation,
manual acceptance.

## Evidence
- Acceptance 7, approved → three approve cases; `journal.py` selects entries by `_SYSTEMD_UNIT`,
  `_UID`, `MESSAGE_ID` and `CUSTODIO_PID` → exactly one per ledger line (zero or two fail), key matches the ledger,
  `CUSTODIO_OUTCOME=signed`, `PRIORITY=6`.
- Acceptance 7, exactly one, duplicates → self-test streams that must fail: a duplicate with the same pid and
  a different key; an extra audit entry with no `CUSTODIO_PID` (whole-run count too high, and fallback
  check); both otherwise perfect.
- Acceptance 7, no hang → every signature runs under `timeout 60`; exit 124 fails with "signature hung",
  distinct from the expected non-zero exit (a deny case that exits 124 fails the suite).
- Acceptance 7, denied → deny cases on `rsa1` and `ec1`, `pkcs11-tool` non-zero, no output, counter
  `before + 1` → exactly one entry, `denied`, `PRIORITY=5`.
- Acceptance 7, polkit unavailable → `unavailable.sh`: non-zero exit, no output file, exactly one entry,
  `authorization_unavailable`, `PRIORITY=4`; `systemctl is-active polkit` is non-zero before the case (a
  failed stop fails with its own message) and active again after the explicit restore.
- Acceptance 7, uid and pid of the signing process → `CUSTODIO_UID` equals `id -u alice` and `CUSTODIO_PID`
  the wrapper's pid, distinct per case; `MESSAGE` contains `uid <uid> pid <pid> key <key>` matching the fields.
- Acceptance 7, key → `CUSTODIO_KEY_ID` is `rsa1`/`ec1` as in the ledger.
- Acceptance 7, trusted fields → `journal.py` itself ignores entries whose `_SYSTEMD_UNIT` is not
  `custodio.service` or whose `_UID` is not the passed custodio uid; self-test: an otherwise perfect extra
  entry lacking those fields, and one with the right unit but wrong `_UID`, are ignored (a missing real entry
  still fails), and a forged duplicate does not count as a second entry.
- Self-test for acceptance 7 → synthetic streams that must fail: no entry, two entries, wrong uid, wrong pid,
  wrong key, wrong outcome, wrong `PRIORITY` (`signed` with 5), `MESSAGE` uid/pid/key differing from the fields;
  and one good stream that must pass.
- Acceptance 8 → `journal.py` builds needles from: every file in `evidence/`, plus `$WORK/data.bin`,
  `deny.bin` and the >1 MiB file of F28 where they exist; each file's SHA-256/384/512 digest; the RSA
  `DigestInfo` (fixed prefixes + digest); every kept signature (for `ec1` the raw r||s and, if the file is DER,
  also the r||s decoded from it; for the provider case the DER and its r||s equivalent where applicable);
  and `e2e-password`. The kept files are those listed under Scope (F29 evidence, last `sig.bin`,
  `issued.der`, F28 files still on disk). All case inputs are random bytes so a needle cannot match by chance. Each needle is
  searched in the whole `-o export` bytes of the wide query as raw bytes, lower and upper hex, standard and
  URL-safe base64 with and without padding, colon- and space-separated hex, the Rust `{:?}` byte-slice form
  (`[12, 34, …]`), and, for needles of at least 9 bytes, the base64 substrings that
  are stable at the three byte alignments. A hit fails and names the needle kind and the form, never its value.
- Acceptance 8, the check can fail → `journal-selftest.sh` plants each form (raw, lower hex, upper hex,
  base64 at alignments 0/1/2, URL-safe base64, colon-separated hex, space-separated hex, `[12, 34, …]` form, the password embedded at a non-zero offset in a longer base64
  blob, a DigestInfo, a signature) once in an audit entry and once in a non-audit entry without `MESSAGE_ID`, and once in an entry with only `UNIT=custodio.service` (caught
  only by the `-u` query form); each must fail the checker, the clean stream must pass, and the failure output must not contain the needle.
- Acceptance 8, M0 check unchanged → the `journalctl -u custodio | grep e2e-password` line stays (diff).
- Suite is well formed → `just lint` and `bash -n e2e/*.sh` → exit 0; `bash e2e/journal-selftest.sh` → exit 0
  locally, and `grep -n journal-selftest e2e/guest.sh` shows it is run and its failure aborts the suite.
- Suite contains the journal checks → the `verify` command → exit 0. Because `journalctl` already matches
  `guest.sh`, also `grep -qF '_SYSTEMD_UNIT=custodio.service' e2e/journal-check.sh`, `grep -q
  CUSTODIO_OUTCOME e2e/journal.py`, `grep -q authorization_unavailable e2e/unavailable.sh e2e/journal-cases.sh
  e2e/journal.py` (at least in the ledger line of `unavailable.sh`) and `grep -n b64 e2e/journal.py` find code,
  not just comments.
- Caveat → PROGRESS.md states: not run; F31 must confirm that stopping and masking polkit gives
  `authorization_unavailable` and no hang, that the wrapper's pid is what the bus reports, that
  `journalctl --sync` works in the container, that the export of the service journal is small enough to read,
  and what the provider and `pkcs11-tool` signatures look like on disk.
