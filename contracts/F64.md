# F64 — Client crate and the dependency check

## Scope
Built:
- A small client-side crate (name is the builder's; it is a workspace member) that both `custodio-cli` and
  `custodio-pkcs11` depend on. It holds only what the client documentation will describe: the bus name, the
  object path and the documented bounds (today `MAX_P12_LEN`; any other bound or constant the two clients
  take from `custodiod` today, such as the mechanism numbers in `custodiod::dbus`, only if a client uses it).
  `custodiod` re-uses or depends on that crate so each value is defined once. The client crate depends on
  nothing from the service.
- `custodio-cli` and `custodio-pkcs11` have no `custodiod` edge in any kind (normal, build, dev), directly or
  through another crate.
- Tests that need the real service code together with a client (today `custodio-cli/tests/cli.rs`,
  `custodio-pkcs11/tests/cryptoki/`, `tests/composed_openssl.rs`, and the unit tests in
  `custodio-pkcs11/src/composed/tests.rs`, which use `custodiod::sign` and `import`) move to a workspace crate
  of their own, or start the `custodiod` binary. Moving may split a test file; no test is deleted, weakened or
  `#[ignore]`d. Unit tests that only need the service's signing code to build an expected value may
  be moved to that crate too.
- `just deps-check`, added to `just lint` (and so reached by `test-changed` where it applies), reads
  `cargo metadata` (all dependency kinds, resolved graph, transitive) and fails naming the path from the client
  to the service crate. Its own test (a script run by the recipe or by `just test-scripts`) uses a fixture
  workspace with fake crates, one per kind (normal, build, dev, and a transitive one via a third crate), where a
  client reaches the service.
- `just test-integration` keeps running the same integration tests, now wherever they live (update the
  recipe and `scripts/changed_checks.py` mapping if needed).

Not built: documentation of the client contract (later features), new D-Bus error names (F65), any behaviour change.

Environment: `cargo metadata --format-version 1 --locked` works in the dev container, but needs the registry
(it downloaded crates here; with `--offline` it fails on uncached crates). deps-check therefore must not
require `--offline`; the builder decides how to avoid depending on non-Linux-only crates if that matters.
`python3` 3.13 and `jq` are present.

Size: about five steps; no split proposed.

## Steps
- [ ] Add the failing deps-check test on a fixture workspace (normal, build, dev and transitive edges to a
      fixture service crate, plus a clean fixture that must pass), then the `deps-check` recipe that makes it pass
      (it is expected to fail on the real workspace until the later steps).
- [ ] Create the client crate with the bus name, object path and documented bounds; make `custodiod` use it
      (single definition) and keep its tests green.
- [ ] Switch `custodio-cli` to the client crate, drop its `custodiod` dependency, and move its tests that need
      the service to a crate of their own (or to launching the binary).
- [ ] Do the same for `custodio-pkcs11`, including its dev-dependency, `tests/cryptoki`, `composed_openssl` and
      the `composed` unit tests; check the fuzz workspace of the module still builds.
- [ ] Wire `deps-check` into `just lint`; update `test-integration` and the changed-checks mapping for the
      moved tests; run `verify` and the evidence below.

## Evidence
- Neither client depends on `custodiod` in any kind at any depth → `just deps-check` on the real workspace →
  exit 0.
- `cargo metadata` independent check of the same → `cargo tree -p custodio-cli -e normal,build,dev -i custodiod`
  and the same for `custodio-pkcs11` → each fails with "did not match any packages"/empty (no path).
- Shared items are in a small client-side crate holding only bus name, object path and documented bounds →
  review of the crate's `Cargo.toml` (no `custodiod`, no service-side dependency such as polkit/store) and of
  its public items; `cargo tree -p <client crate>` shows no `custodiod` → only those items listed.
- Both clients and the service use the one definition → `grep` shows no second definition of `BUS_NAME`,
  `OBJECT_PATH`, `MAX_P12_LEN` outside the client crate; `cargo test -p custodiod` green (the service's
  constants test or existing dbus test compares against the client crate's values).
- Service-plus-client tests live outside the clients → `just test-integration` → green with the same set of
  integration tests as before (names of the CLI and cryptoki tests unchanged; count compared with
  `git stash`-free baseline from `cargo test -- --list` before and after, none missing or ignored).
- deps-check fails naming the path → fixture test: for each of normal, build, dev and transitive edge, the
  recipe exits non-zero and its output contains the full path (`client -> … -> service`) and the kind →
  asserted by the test.
- deps-check test can fail (negative control) → the clean fixture passes, and the same script run
  with the check's reading of `cargo metadata` broken (e.g. ignoring dev edges) makes the dev-fixture case
  report a failure of the test itself → test exits non-zero.
- `just lint` runs it → `just --dry-run lint` (or `just lint` output) contains `deps-check`; the test script
  asserts this by parsing the justfile.
- Behaviour of the CLI and module unchanged → the existing CLI tests (`cli.rs` cases) and the module's
  unit, `cryptoki` and `composed_openssl` tests pass unmodified in their assertions, via
  `just test-changed F64` and `cargo test -p custodio-pkcs11 --features fuzzing --lib`; the Miri/FFI tests are
  untouched (`git diff` shows no change in `src/ffi*`).
