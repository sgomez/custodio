# F179 — VM snap group: list and sign under the real Firefox snap, run early

## Scope
Builds the `snap-*` group of the VM target (SPEC Design 6, acceptances 17 and 18) and runs it alone once, to learn
early whether the route holds. Built:

1. **Case accounting.** The group's ids in `e2e/vm/cases.list` (the list below), `case_group` in `e2e/select.sh`
   (`snap-*` is its own group, a new step in `e2e/guest.sh` after `vm-silent` and before `sign`), `e2e/vm/run.sh`
   (step `snap` in the phases when a snap case is selected). Mode `full` runs the group. Mode `lacking` reports every
   `snap-*` case skipped, with a reason, in `e2e/vm/skip.list` (SPEC puts the group in `full`; the snap route does not
   depend on the TPM kind, so it is not repeated in `lacking`). `e2e/check-cases.sh` refuses a `snap-*` case reported
   skipped in a `full` VM run whatever the skip list says (fail closed: acceptance 18), as it does for `vm-silent-*`
   in `lacking`.
2. **The snap in the guest.** When a `snap-*` case is selected the run installs the Firefox snap from `stable`
   through snapd (so its signed assertions are checked by snapd itself). F171 decided: snapd and AppArmor come from
   the image (asserted, not installed), **no cache by revision** (it saved ~31 s of 50 s and is not built here), and
   `snap refresh --hold` after the install. The install does not wait behind the shared setup: it starts as soon as
   the guest can run it and overlaps with the setup (installing the key material), and the group waits for its end on
   a condition (`snap wait` / the change status), never a fixed sleep.
3. **The record.** `vm.full.record` gains the snap revision, base, snapd (deb and snap), AppArmor and dbus-daemon
   versions and the label the service observed (as the service journals it). A field that cannot be read is
   `unknown`, and `unknown` in any of them fails the run of a selection with snap cases.
4. **The cases**, one script on the guest side with the judging functions in a sourced file (like `judge.sh`) so that
   `scripts/test-e2e-vm-snap.sh` can run them on fixtures. The harness places the module copy (a byte copy of the
   installed module) and a small PKCS#11 client (Python `ctypes`, the style of `e2e/p11-pss.py`, run by the snap
   base's own `python3`; F171 found it there) in alice's `~/snap/firefox/common/`, by hand (`install`, no registration
   command: F183). The client lists the tokens/certificates and signs with a mechanism per key. The cases use alice's
   RSA 2048 and P-256 keys (the shared setup's, or imported and deleted by the group; the state and the audit counts
   other groups read are as before). The client runs under `snap run --shell firefox` as alice in her logind session
   with the test polkit agent (the agent of `e2e/agent.py`, approving), as the sign group does.
5. **The refusal label.** A process "under another snap's label" is obtained by a test AppArmor profile named
   `snap.e2e-other.app` loaded by the harness in the guest at run time with `apparmor_parser` (enforce, allowing at
   least `unix,` and file access, so AppArmor itself does not stop the connect), entered with `aa-exec -p`, and
   unloaded on every exit. The profile lives under `e2e/`, is not packaged and is not a label source of the service.
   The case first reads the label that process really has (the service's own refusal line, or `/proc/self/attr/current`
   of the child) and fails if it is not `snap.e2e-other.app (enforce)` or if the same process cannot reach the socket
   file (so a refusal can never be AppArmor's or a typo's). If `aa-exec` from an unconfined user gives a stacked label,
   the builder records it in `docs/findings/F179.md` and uses the plain-label route the finding supports
   (for example root loading the profile and `aa-exec` under it); the case still must see exactly that label.

Cases (ids; every one reported once, run in `full`, skipped in `lacking`):
`snap-record`, `snap-socket-dir`, `snap-list-keys`, `snap-sign-rsa`, `snap-sign-ec`, `snap-polkit-per-signature`,
`snap-journal-label`, `snap-bus-denied`, `snap-refused-unconfined`, `snap-refused-root`, `snap-refused-other-snap`,
`snap-unknown-methods`.

Not here: the registration command and the copy refresh (F183), Debian/Fedora/Arch (no snap route), the package
gates, the manual desktop acceptance 19, and the CI workflow (`e2e-vm.yml` already runs every case of `cases.list` in
`full`; `scripts/test-ci-e2e-vm.sh` must still pass unchanged). The register and snap sockets' lower-level behaviour
(label parser, bounds, polkit subject, unknown methods on the in-process service) is F174–F178's; here the same
properties are proven only where the real snap, the real AppArmor or the real systemd socket matter.

**Environment (run now).** `scripts/vm-host-check.sh` prints OK for kvm-accel, ovmf, swtpm, swtpm-profile, seed-tool,
gpgv and keyring in this container: the VM runs here (F168's full run: 503 s). F171 measured in this very image:
snapd 2.77.1 deb running, AppArmor `Y`, the store reachable from the guest, `snap install firefox` 50 s, 1.22 GB,
revision 9181, base core26 with glibc 2.43 (above the module's 2.39 ceiling's need), `snap run --shell firefox`
labelled `snap.firefox.firefox (enforce)`, `python3` present in the base, `/proc/self/attr/current` unreadable in
the snap (the label comes from the service's `SO_PEERSEC`, not from the client). Hooks cannot be started as a user
and are not tested.

**Costs and parallelism.**
- `scripts/test-e2e-vm-snap.sh`: fixtures and stubs only, no VM, an estimated 5 s; a script test, added to `test-scripts`
  in the `justfile` next to `test-e2e-vm-silent.sh`, runs in parallel with the others. Its controls run independent
  fixture copies; no fixed sleeps.
- `scripts/test-e2e-vm-cases.sh` gains a few controls on the accounting (about +1 s). `scripts/test-ci-e2e-vm.sh` unchanged.
- The VM group (the costliest level, and only here because snapd, the snap's AppArmor profile and systemd's socket
  exist only in a VM): estimated snap install 50 s (overlapped with the setup, so it adds ~0–30 s to the run) plus
  the cases, ~60–90 s. Alone (`just e2e-vm-cases full 'snap-*'`): image 17 + boot 14 + install/tools ~10 + setup ~11 +
  snap ~120–150 s, about 3–4 minutes, one command, far below the 30-minute limit and the session limit. It goes in
  `e2e/vm/cases.list` only (VM-only, Ubuntu 26.04), not in any container `cases.list`. The full run grows from the
  measured 503 s to an estimated 560–600 s against `budgets.tsv` `vm full 580`: the builder measures it and, if the
  group pushes the run over 580, asks for a bigger budget in `BLOCKED.md` (that file is a person's). No step runs the
  whole `verify`; each step runs one command.

## Steps
- [ ] Judging first: the sourced judge file (`e2e/vm/snap-lib.sh`; name the builder's) and `scripts/test-e2e-vm-snap.sh`
      with fixtures of the record, the client outputs, the journal and the refusals, and the negative controls of
      Evidence, written before the guest code; added to `test-scripts`.
- [ ] Accounting: the twelve ids in `e2e/vm/cases.list`, the `lacking` skips in `e2e/vm/skip.list`, `case_group`,
      the `check-cases.sh` rule (a `snap-*` case skipped in `full` is refused), controls in `scripts/test-e2e-vm-cases.sh`;
      `just e2e-vm-check full snap-sign-rsa` accepts and an unknown id is refused.
- [ ] The snap in the guest: the install overlapping with the setup, asserted preconditions (AppArmor `Y`, `snapd.socket`
      active), the hold, and the facts of the record (`run.sh` and the judge collect them; `unknown` fails).
- [ ] The positive path: module copy and client placed by hand, `snap-record`, `snap-socket-dir`, `snap-list-keys`,
      `snap-sign-rsa`, `snap-sign-ec`, `snap-polkit-per-signature`, `snap-journal-label`.
- [ ] The negative path: `snap-bus-denied`, `snap-refused-unconfined`, `snap-refused-root`, `snap-refused-other-snap`
      (the test profile, always unloaded), `snap-unknown-methods`.
- [ ] Run `just e2e-vm-cases full 'snap-*'` until it passes; write what the real snap showed that surprised the contract
      (label, pid, how the profile was entered, timings per phase, whether the full run still fits the budget) in
      `docs/findings/F179.md` (indexed in `docs/findings.md`) only if it is research a later session needs, otherwise in
      `PROGRESS.md`; `just quick`.

## Evidence
- Group runs in `full` and is accounted (every case once, an unknown or missing case fails) → `scripts/test-e2e-vm-cases.sh`
  → passes; controls: a `full` output with a `snap-*` case skipped, one missing, one reported twice, and an id not in the
  list are each refused; the same outputs in `lacking` with the group skipped are accepted.
- Group run alone → `just e2e-vm-cases full 'snap-*'` → exit 0; `target/e2e/vm.full.log` has one E2E-CASE line per case.
- Snap installed from the store, versions recorded (acceptance 17) → `snap-record` and `scripts/test-e2e-vm-snap.sh`
  → the record holds revision, base, snapd, AppArmor, dbus-daemon and the observed label; controls: each field removed or
  `unknown` fails the judge, and the live record of the VM run has none of them `unknown`.
- After the install `/run/snap.firefox/` is root 0755 and holds `custodio.sock` → `snap-socket-dir` → `stat` shows
  `root root 755` and a socket file named `custodio.sock`; controls on fixtures: mode 0775, owner alice, a regular file in
  place of the socket, and a missing socket each fail.
- Under `snap run --shell firefox` the client lists the user's keys → `snap-list-keys` → the ids/labels of alice's
  keys, only hers (no key of another user, which the shared setup may hold); controls: an empty list, a missing key and a
  foreign key each fail; if the socket is unreachable from the confinement the case **fails** with a message that names
  the socket (never skipped; acceptance 18).
- Signs with RSA 2048 and P-256, each verified with `openssl` → `snap-sign-rsa`, `snap-sign-ec` → `openssl` verifies
  every signature against the certificate the client read through the module; controls: a signature with one byte changed
  and one made over other data fail to verify.
- Polkit asked once per signature about the client's process → `snap-polkit-per-signature` → the test agent's request count
  grows by exactly the number of signatures (a second signature does not reuse the first approval), and the journal's
  `CUSTODIO_PID` of each entry is the pid of the client process the harness started (the builder checks the pid is not
  namespaced; if it is, the finding says what is used); controls: one request for two signatures and a pid of another
  process each fail. The `unix-process` subject and pidfd are proven in F176/F178.
- Each journal entry carries a `snap.firefox.*` label → `snap-journal-label` → every `sign` entry of the group has
  `CUSTODIO_TRANSPORT=socket` and `CUSTODIO_PEER_LABEL=snap.firefox.firefox (enforce)` (the exact string F171 observed);
  controls: label `unconfined`, `snap.firefox.firefox (complain)`, `snap.other.app (enforce)`, `transport=bus` and a
  missing label each fail. A label that is not `snap.firefox.*` in enforce mode fails the run (acceptance 18).
- From the same confinement a bus call is denied by AppArmor → `snap-bus-denied` → a method call to the service on the
  system bus (the same command, from inside `snap run --shell firefox`) fails with `AccessDenied`/permission denied, and the
  denial is an AppArmor one (an `apparmor="DENIED"` audit record naming the bus call, read from the journal/kernel log, or a
  finding that says why not available); control: the identical call outside the snap, as alice, succeeds, so the denial is the
  confinement's; if the call **succeeds** under the snap the run fails (acceptance 18). The judge's controls: a succeeded
  call, a denial without the AppArmor record, and a failing outside call each fail.
- Unconfined process and root refused at the socket → `snap-refused-unconfined`, `snap-refused-root` → the same client
  (module copy) run as alice outside the snap and as root outside the snap gets no slots / no signature, the service journal
  holds a refusal line with the fixed reason for that case, and no `sign` entry is added; positive control: in the same run,
  `snap-list-keys` succeeded through the same socket. Judge controls: a client that listed keys, a refusal line missing and a
  new `sign` entry each fail.
- A process under another snap's label is refused → `snap-refused-other-snap` → the child under `snap.e2e-other.app (enforce)`
  reaches the socket file, is closed before any method, the journal has the refusal for another snap, and no `sign` entry
  exists; the profile is unloaded after the case, also when it fails (checked in `scripts/test-e2e-vm-snap.sh` with a stub
  `apparmor_parser`, the unload runs on a failing judge and on a signal). Controls: a child whose label is not the test label
  (the case fails as vacuous) and one that cannot reach the socket (AppArmor, not the service, refused) each fail.
- `ImportP12`, `DeleteKey`, `ReplaceCertificate` fail as unknown methods → `snap-unknown-methods` → from the confinement each
  call returns the unknown-method error (not a polkit denial or a success), the key list and the state directory listing
  (names, modes, sizes) are unchanged, the audit log has no new entry and the agent got no request; controls on fixtures: a
  success, a polkit denial, a changed listing, a new entry and a new agent request each fail.
- Fail closed (acceptances 17, 18) → `scripts/test-e2e-vm-snap.sh` → the three preconditions (label not `snap.firefox.*` in
  enforce mode, socket unreachable, bus not denied) each give a failing judge with a message naming what moved ("snapd's rules
  changed; a person must look"), never a skip; and a selected group whose script is missing or whose cases did not report fails
  the accounting.
- Test script itself → `scripts/test-e2e-vm-snap.sh` → passes in the container without a VM, and fails when a judging function
  is replaced by `true` (one such negative control for the whole script).
- Existing gates still hold → `just quick`, `scripts/test-e2e-vm-cases.sh`, `scripts/test-ci-e2e-vm.sh` → pass.
- The snap route as a whole → `just e2e-vm-cases full 'snap-*'` (the loop's `verify`) → passes on a real Ubuntu 26.04 guest with
  the real Firefox snap.
