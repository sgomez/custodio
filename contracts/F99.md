# F99 — Written manual acceptance steps for M3

## Scope
Built: an M3 part of `docs/manual-acceptance.md` (a new heading for SPEC.md acceptance 14 to 16, one
section per acceptance), a test flatpak manifest the repository ships (the builder chooses the path and
format, JSON or YAML, and the app-id), and `scripts/test-docs-manual-m3.sh`, added to `test-scripts` in
the `justfile`. The existing M1/M2 parts and `scripts/test-docs-manual.sh` stay as they are and must still
pass; the page's title and intro line are updated to say it now covers M3 (the old test checks only the
machine parts, so this must not break it).

Left for other features: running the steps (a person does, at the milestone) and building or running the
flatpak (checkpoint F100 and the person). The service behaviour, the dialogs and the journal entries are
proved by F66-F98; this feature proves only that the written steps are complete and consistent with
`docs/api.md` and `docs/audit.md`. The detection steps are those of `docs/api.md` "Detection" (F98); the
steps point to them and do not restate other facts.

Decided already: `docs/findings.md` F67 ends `Decision: (c)` (app-id from the caller's cgroup scope), and
`SPEC_DEVIATIONS.md` has no F67 entry. So acceptance 15 asks for the real app-id in the journal entry, and
the deviation branch ("the F67 deviation") does not apply; the test checks that `SPEC_DEVIATIONS.md` has no
`## F67` entry, and fails if one appears while the page still demands the app-id (the page must then be
changed). The app-id field to look for is `CUSTODIO_APP_ID` with `CUSTODIO_APP_ID_STATE=read` and the
person's uid is `CUSTODIO_UID` (`docs/audit.md` "Flatpak app-id"); note the entry's `CUSTODIO_PID` is the
proxy's, and the page says so.

Environment probes (this session, dev container): `which flatpak flatpak-builder` → neither exists, and
`mise.toml` pins neither; `python3 -I -c "import yaml,json"` → works. So the test cannot build or run the
manifest; it parses it (and the proof that the flatpak runs is the person's run at the milestone and
`e2e-cases appid-*`, F82). The manifest is not built in any gate here.

Size: five steps; no split proposed.

## Steps
- [ ] Test first: write `scripts/test-docs-manual-m3.sh` with its check function, the section finder and the
      negative-control scaffolding (same pattern as `scripts/test-docs-manual.sh`: `DOC` override, a fixture
      copy must differ from the page and fail); red against today's page. Add it to `test-scripts`.
- [ ] The test flatpak manifest: a minimal app (the builder decides which runtime and what the app runs)
      whose `finish-args` / `finish_args` hold `--system-talk-name=com.rfirma.Custodio1`, and which can
      run the documented detection and a `Sign` (or `ImportP12`) call by `busctl`/`gdbus` or equivalent from
      inside the sandbox. A short README or comment in the page says how to build and run it
      (`flatpak-builder`, `flatpak run`); commands that were not run in this session are marked
      **unverified**, as the existing page does.
- [ ] Section for acceptance 14: detect the service following only `docs/api.md` "Detection", then import,
      list, replace the certificate, sign and delete with `busctl` (and `gdbus` as the alternative where the
      page offers it). Every command is one of the document's examples (same method, interface and path),
      says which polkit dialog shows (by action) and which error the person must see for a refused dialog,
      a wrong password, a certificate of another key and an id that does not exist. It tells the person to
      use only `docs/api.md`, and has a table to record each dialog and error seen.
- [ ] Section for acceptance 15: the manifest path and its build and run commands; run the detection steps
      from inside the flatpak; call `Sign` (or `ImportP12`) and answer the polkit dialog; then the journal
      query of `docs/audit.md` for the app-id and the uid (`CUSTODIO_APP_ID` equal to the manifest's app-id,
      `CUSTODIO_APP_ID_STATE=read`, `CUSTODIO_UID` equal to `id -u` of the person); the pid is the
      proxy's. A table row for each. The page also says what to record when the app-id is `undetermined`
      or `none` (a failure of acceptance 15, with the entry).
- [ ] Section for acceptance 16: Firefox and LibreOffice sign with a key the person imported (point to the
      existing M1/M2 sections by their headings, for the registration, the signing steps and the journal
      comparison, instead of copying them); a second account on the same machine lists tokens (the command
      of the existing sections, e.g. `pkcs11-tool --list-token-slots` or `modutil`) and sees no token for
      that key, and `ListKeys` of that account is empty. Add the M3 result form (one row per acceptance
      14, 15, 16, with the record of every dialog and error), update the page's title and intro. Run
      `just quick` and `scripts/test-docs-manual-m3.sh` (and `scripts/test-docs-manual.sh`) until they pass.

## Evidence
- Acceptance 14 part holds its items (detect, import, list, replace certificate, sign, delete, with
  busctl or gdbus, following only docs/api.md, each dialog and error) →
  `scripts/test-docs-manual-m3.sh`: in the acceptance 14 section, a command for each of the six
  operations, naming `ListKeys`, `ImportP12`, `ReplaceCertificate`, `Sign`, `DeleteKey` and the
  detection step, the text "only" + `docs/api.md`, a dialog/action line for each of import, replace, sign
  and delete, the four errors named above, and a table to record → exit 0; copies with one operation, the
  detection step, the `docs/api.md` sentence, or an error name removed → each reported, non-zero.
- Its commands match docs/api.md → the test extracts every `busctl`/`gdbus` command of the section and
  requires that its destination, path, interface, method and signature (and, for polkit prompts, the
  action id) equal those in an example block or method entry of `docs/api.md`, and that every action id
  and error name it mentions exists in `docs/api.md` → exit 0; a copy with a method name, a signature or
  an action id altered → non-zero.
- Acceptance 15 part: a flatpak manifest the repository ships, with the talk permission, detection by
  the documented steps, signing or importing after the dialog, the journal entry naming app-id and
  uid, or the F67 deviation →
  the test checks that the section names the manifest's path and that the file exists; that it parses
  (`python3 -I`, JSON or YAML according to the extension) and its finish arguments contain exactly
  `--system-talk-name=com.rfirma.Custodio1` (not a `--talk-name`, not `--socket=system-bus`, which would
  hide a missing filter); that the app-id in the manifest equals the one the section tells the person to
  look for in the journal; that the section references `docs/api.md` "Detection"; and that it has a
  `Sign`/`ImportP12` step followed by the journal step using `CUSTODIO_APP_ID`, `CUSTODIO_APP_ID_STATE`
  and `CUSTODIO_UID` → exit 0; copies with the manifest's permission removed or changed to `--talk-name`,
  an invalid manifest, a different app-id, the journal step removed → each non-zero.
- The journal commands match docs/audit.md → the test requires that each `CUSTODIO_*` field and value
  (`read`, `undetermined`, `none`) and the base journalctl query on the page are in `docs/audit.md` (the
  base query line is the one `scripts/test-docs-manual.sh` reads) → exit 0; an invented field or a
  changed query in a copy → non-zero.
- The F67 branch → the test reads `SPEC_DEVIATIONS.md`: with no `## F67` entry the page must demand the
  app-id (as above); if the entry exists the page must say the field is `undetermined` instead → exit 0
  now; a fixture deviation file with `## F67` and the unchanged page → non-zero.
- Acceptance 16 part: Firefox and LibreOffice still sign; a second account sees no token →
  the test checks the section names Firefox and LibreOffice, points to existing headings of the page
  (each referenced heading must exist, checked), has a second-account step with the token listing command
  and the empty `ListKeys`, and an expected result "no token" → exit 0; copies with Firefox, LibreOffice,
  the second-account step, or a referenced heading renamed → non-zero.
- Result form and old parts → the test checks the M3 form has a row for 14, 15 and 16; and
  `scripts/test-docs-manual.sh` still passes unchanged → exit 0; the form row removed in a copy →
  non-zero.
- Negative controls in general → each control builds a fixture copy of the page (or manifest, or
  deviation file) by `sed`/overrides, requires that it differs from the real file and that the check
  fails on it → every control gives non-zero, the real files give exit 0.
- Test is in `test-scripts` → `grep -F 'scripts/test-docs-manual-m3.sh' justfile` → match.
- Whole feature → `just quick && scripts/test-docs-manual-m3.sh` → exit 0.
