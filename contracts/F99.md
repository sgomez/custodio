# F99 — Written manual acceptance steps for M3

## Scope
Built: an M3 part of `docs/manual-acceptance.md` with four new headings that occur once on the page and
are fixed here: `## 16. M3 acceptance 14: ...`, `## 17. M3 acceptance 15: ...`, `## 18. M3 acceptance 16: ...`
and `## 19. M3 result form` (the old M2 sections `## 13. omarchy (acceptance 14)` and `## 14. ubuntu2404,
dbus-broker (acceptance 15)` mention Firefox, polkit and the journal, so the test must never search them), a
test flatpak manifest the repository ships in **JSON** (the builder chooses the path and the app-id; JSON so
the test needs only `python3 -I` with the standard library, also in CI), and `scripts/test-docs-manual-m3.sh`, added to `test-scripts` in
the `justfile`. The existing M1/M2 parts and `scripts/test-docs-manual.sh` stay as they are and must still
pass; the page's title and intro line are updated to say it now covers M3 (the old test checks only the
machine parts, so this must not break it).

Left for other features: running the steps (a person does, at the milestone) and building or running the
flatpak (checkpoint F100 and the person). The service behaviour, the dialogs and the journal entries are
proved by F66-F98; this feature proves only that the written steps are complete and consistent with
`docs/api.md` and `docs/audit.md`. The detection steps are those of `docs/api.md` "Detection" (F98); the
steps point to them and do not restate other facts.

Decided already: `docs/findings.md` F67 ends `Decision: (c)` (app-id from the caller's cgroup scope), and
`SPEC_DEVIATIONS.md` has no F67 entry. So acceptance 15 asks for the real app-id in the journal entry, and
the deviation branch ("the F67 deviation") does not apply; the test checks that `SPEC_DEVIATIONS.md` has no
`## F67` entry, and fails if one appears while the page still demands the app-id (the page must then be
changed). The app-id field to look for is `CUSTODIO_APP_ID` with `CUSTODIO_APP_ID_STATE=read` and the
person's uid is `CUSTODIO_UID` (`docs/audit.md` "Flatpak app-id"); note the entry's `CUSTODIO_PID` is the
proxy's, and the page says so.

Environment probes (this session, dev container): `which flatpak flatpak-builder` → neither exists, and
`mise.toml` pins neither; `python3 -I -c "import json"` → works (standard library; no PyYAML is needed). So the test cannot build or run the
manifest; it parses it (and the proof that the flatpak runs is the person's run at the milestone and
`e2e-cases appid-*`, F82). The manifest is not built in any gate here.

Size: five steps; no split proposed.

## Steps
- [ ] Test first: write `scripts/test-docs-manual-m3.sh` with its check function, the section finder (it takes the exact heading text of the four M3
      headings, asserts that each matches exactly one heading of the page, and prints only that section) and the
      negative-control scaffolding (same pattern as `scripts/test-docs-manual.sh`: `DOC` override, a fixture
      copy must differ from the page and fail); red against today's page. Add it to `test-scripts`.
- [ ] The test flatpak manifest: a minimal app (the builder decides which runtime and what the app runs)
      (JSON) whose `finish-args` hold `--system-talk-name=com.rfirma.Custodio1`, and which can
      run the documented detection and a `Sign` (or `ImportP12`) call by `busctl`/`gdbus` or equivalent from
      inside the sandbox (the app it runs includes `busctl` or `gdbus`). A short README or comment in the page says how to build and run it
      (`flatpak-builder`, `flatpak run`); commands that were not run in this session are marked
      **unverified**, as the existing page does.
- [ ] Section for acceptance 14: detect the service following only `docs/api.md` "Detection", then import,
      list, replace the certificate, sign and delete with `busctl` (and `gdbus` as the alternative where the
      page offers it). Every command is one of the document's examples (same method, interface and path),
      says which polkit dialog shows (by action) and, for every error that an `error=` annotation of a
      `docs/api.md` example fence names, how to trigger it and that the person must see it (refused dialog,
      wrong password, key id taken, invalid arguments, certificate of another key, no such key); an error a
      person cannot reasonably trigger (`AuthorizationUnavailable`) gets a line "not reproduced manually,
      because ...". It tells the person to
      use only `docs/api.md`, and has a table to record each dialog and error seen.
- [ ] Section for acceptance 15: the manifest path and its build and run commands; run the detection steps
      from inside the flatpak; call `Sign` (or `ImportP12`), naming the polkit action of the dialog, and
      answer it; only then the journal
      query of `docs/audit.md` for the app-id and the uid (`CUSTODIO_APP_ID` equal to the manifest's app-id,
      `CUSTODIO_APP_ID_STATE=read`, `CUSTODIO_UID` equal to `id -u` of the person); the pid is the
      proxy's. A table row for each. The page also says what to record when the app-id is `undetermined`
      or `none` (a failure of acceptance 15, with the entry).
- [ ] Section for acceptance 16: Firefox and LibreOffice sign with a key the person imported (point to the
      existing M1/M2 sections by their headings, for the registration, the signing steps and the journal
      comparison, instead of copying them); a second account on the same machine lists tokens with the command of an existing
      section (`modutil -dbdir ... -list` of section 6, or the token listing of another existing section; the
      test derives it from the page outside the M3 sections, so no invented command) and sees no token for
      that key, and `ListKeys` of that account is empty. Add the M3 result form (one row per acceptance
      14, 15, 16, with the record of every dialog and error), update the page's title and intro. Run
      `just quick` and `scripts/test-docs-manual-m3.sh` (and `scripts/test-docs-manual.sh`) until they pass.
