# F193 — Real help, colour rules and two-line errors, with the man page parity test and the parser's fuzz target

## Scope

Built here, for the commands the CLI has today (`import`, `list`, `delete`, `register`):

- Real help: `custodio --help`, `-h` and `custodio <command> --help` (standard output, status 0): what the command
  does, its arguments and options, and an example. Usage errors stay on standard error with status 2 and now say
  how to get help. Arguments stay parsed by hand.
- The commands and their options live in one table, and the parser dispatch, the help and the tests read it. A
  command added later (F197 `fingerprint`, F202 `doctor`, F194's `list <id>`) is then in the help test, and fails the
  man-page parity until its man page text exists. The parser moves out of `lib.rs` into its own module and the help
  is its own module, because `mutants` lists files.
- `packaging/custodio.1` is brought to the help's contents (every command and option, both ways).
- A colour module (a stream is coloured only if that stream and standard output are both terminals and `NO_COLOR` is unset or empty; with standard output not a terminal, neither stream has colour, as acceptance 10 says) and an error
  module. The error module is the one place that turns an error into text: line 1 says what went wrong, line 2 is
  the next step (a command, a documented section, or "report a bug" with where). Untrusted text in a message
  (key ids from the service, paths, browser names, the service's unknown error name) is escaped.
- `ServiceFailure` maps every error name of `docs/api.md`. Today it does not: `TpmFailed`, `CredentialsUnavailable`,
  `KeyLost` and `TemporarilyUnavailable` fall into `Unknown`. They get their own cases and messages.
- The fuzz target `cli_args` (in `crates/custodio-cli/fuzz`), added to `fuzz-smoke`'s default `expected` list.
  The `mutants` recipe's custodio-cli list gains the parser, help, colour and error modules.

Kept stable because scripts depend on it: the polkit-denial message still contains "not authorized"
(`e2e/ops-user.sh`, `e2e/jo-user.sh`, `e2e/ops-lib.sh`), and the absent-service message still contains "cannot talk to
the service" (`crates/custodio-it/tests/list.rs`). If a step changes either text, it updates those consumers in the
same commit.

Left to other features, not proven here: the `list` table and full view, certificate-text escaping (F194); the new
import errors and the restart note (F195); `fingerprint` (F197) and `doctor` (F202) commands, help and error
messages (they add their entries to the table and their messages to the error module; the tests here cover them
as they appear); completions (F205 and the others); the reading of help by a person (acceptance 21). Where colour is
actually used: this feature builds the rule and uses it for the help headings and the error prefix only; the
colour of the table is F194's.

Sizing: this is larger than five steps. If a session runs short, the natural split is (1) the table, parser module,
help, man page, fuzz target; (2) colour, errors, output_rules. The steps below are in that order, so the builder
can hand over between steps 6 and 7 without rework. I do not edit features.json.

Environment: no external tool or privilege is needed. A pseudo-terminal comes from `rustix` (feature `pty` is already
enabled in the crate) and the `custodio` binary is run with `CARGO_BIN_EXE_custodio`. The `fuzz-build`, `lint-fuzz` and `fuzz-smoke` recipes need the nightly
toolchain and cargo-fuzz, as the earlier fuzz features did.

Cost of the tests (estimates from similar tests in this crate; the builder reports measured times in PROGRESS.md):

| Test | Time | How it runs |
|---|---|---|
| unit tests in the new modules (table, parser, colour, error text, every variant, every API name) | under 1 s together | parallel, in `custodio-cli`'s lib test binary |
| `tests/help.rs` (runs the binary a few times, reads `custodio.1`, reads `Cargo.lock` for the dependency check) | about 1 s | its own test binary, tests parallel |
| `tests/output_rules.rs` (runs the binary with a pty, with a pipe, with `NO_COLOR`) | about 2 s | its own test binary, tests parallel |
| `cli_args` in `fuzz-smoke` | 2000 runs, about 1 s plus the build of one more target | the loop over targets in the recipe is the recipe's own |
| `just mutants-diff F193` | the moved parser is new code in the diff, so every mutant of it runs; expect 100 to 150 mutants, 3 jobs, about 10 to 15 minutes | one command; if it is going to exceed 30 minutes the builder splits the run with `--file` in the arguments and says so |

No e2e case: nothing here depends on the distribution, and the help and errors are proven by running the binary.
The man page already ships in every package; its packaging parity is checked at the checkpoints. No new test is
slower than the script budget (`budgets.tsv` does not list per-crate tests).

## Steps

- [ ] 1. Write the failing tests first for the command table and the help: every command has a section in the help,
      `--help` and `-h` print the global help and `<command> --help` the command's, on standard output with status 0 and
      nothing on standard error; each help has a description, arguments and options and an example; an option of the table that the
      parser accepts is in the help, and the help names no option that is not in the table. The parser and the help lookup take no writer (they return values), so they cannot print. Then build the table, the parser module (moved from `lib.rs`, same behaviour,
      existing parser tests still pass) and the help module.
- [ ] 2. Usage errors: a bad command line still writes to standard error, exits 2, writes nothing to standard output, and its
      text says how to get help (`custodio --help`, or `custodio <command> --help` when the command is known).
- [ ] 3. `crates/custodio-cli/tests/help.rs`: man-page parity driven by the table. Every command and option the help has is in
      `packaging/custodio.1`, and every command and option the man page has is in the help. Update the man page to fit. The commands and options of the help are read from the binary's actual
      output (not only from the table), so an option written by hand into the help text and missing from the table fails.
      Negative controls (two, on fixture text, not on the real page): a man page missing one option fails, a man page with
      an extra option fails.
- [ ] 4. Dependency test in `help.rs`: fails if any argument-parsing or completion-generating crate (at least `clap`,
      `clap_complete`, `clap_builder`, `structopt`, `argh`, `lexopt`, `pico-args`, `bpaf`, `gumdrop`, `argparse`, `getopts`,
      `docopt`, `clap_mangen`, `argp`) is in the resolved dependency graph of `custodio-cli` or `Cargo.lock`. The builder
      picks Cargo.lock or `cargo metadata`; it must see transitive dependencies. One negative control on a fixture lock file.
- [ ] 5. Fuzz target `cli_args` (any bytes turned into an argument list, run through the parser and the help lookup; must not
      panic; neither takes a writer, so printing is impossible by construction), in `crates/custodio-cli/fuzz` with its `[[bin]]` entry; add `cli_args` to the `expected`
      default of `fuzz-smoke` in the justfile. Run `just fuzz-build`, `just lint-fuzz`, `just fuzz-smoke`.
- [ ] 5b. Once `man_page_and_help_agree` passes, remove the two SYNOPSIS checks of `crates/custodio-cli/tests/man.rs` that it
      now proves, in a `test:` commit of their own that names the test that stays and says coverage of the product code did
      not drop (CLAUDE.md rule).
- [ ] 6. Add the parser and help modules to the custodio-cli list of the `mutants` recipe. Run `just quick`.
- [ ] 7. Colour module, tests first: colour on a stream only when that stream and standard output are both terminals and
      `NO_COLOR` is unset or empty (empty `NO_COLOR` does not disable colour; "0" does); when standard output is not a
      terminal, no colour on either stream. Record the rule in `docs/decisions.md` (a later session could go back to
      deciding each stream on its own; Design 3 alone would allow it, acceptance 10 does not); the coloured text, with its escape sequences removed,
      equals the plain text. Use it for the help headings and the error prefix.
- [ ] 8. Error module, tests first: one function from `CliError` to text; match without a wildcard so a new variant does
      not compile until it has text. The test's list of variants is also produced through a wildcard-free match (an exhaustive
      function that maps each variant to a sample), so a variant not listed in the test fails to compile. Every variant of every error enum the CLI prints (`CliError`, `ArgError`, `ImportFailure`,
      `ListFailure`, `DeleteFailure`, `ServiceFailure`, `RegisterError`, `Refusal`, `RunError`, `FileError`, `Refresh` and
      the others `custodio-cli` has) is built by a unit test, rendered, and checked: at least two lines, line 2 non-empty
      and not a repeat of line 1, no control character other than the line end, and no password, key bytes or the sentinel
      strings put into the inputs. Add the cases for `TpmFailed`, `CredentialsUnavailable`, `KeyLost`,
      `TemporarilyUnavailable` to `ServiceFailure`.
- [ ] 9. D-Bus names: a unit test reads the error names under "Errors" in `docs/api.md` and checks (one line; `custodio-client`'s own test already proves `ERROR_NAMES` against the document) that each is in
      `custodio_client::ERROR_NAMES`, that `ServiceFailure::from_name` maps it to a case that is not `Unknown` or `Transport`,
      and that the rendered message passes step 8's checks. Also `ServiceUnknown`, `NameHasNoOwner` (the service absent),
      a bus-daemon error (transport) and an undocumented name (rendered with the name escaped) pass the checks. Negative
      control: a fixture api.md text with one name the CLI does not map fails the checker.
- [ ] 10. Replace the places that print errors (`finish`, `main`, the register and list paths that write their own refusals)
      with the error module; update `exit.rs` and any other test of the old texts; keep the strings listed under Scope.
- [ ] 11. `crates/custodio-cli/tests/output_rules.rs`, see Evidence. Add the colour and error modules to the `mutants` recipe's
      custodio-cli list.
- [ ] 12. Run `just quick`, the `verify`'s tests, and `just mutants-diff F193` until they pass. Do not run the other gates.

## Evidence

- `--help`, `-h`, `<command> --help` print help on stdout, status 0, for every command → `help` unit tests and
  `help.rs::every_command_prints_its_help` (runs the binary for the global form and each command of the table, with both
  flags, asserts status 0, empty stderr) → passes; fails if one command lacks help or prints to stderr.
- Help says what the command does, arguments, options and an example → `help.rs` checks, for each command, the
  description, an arguments and options part (each option of the table is named) and an example line that starts with
  `custodio <command>` and that the parser accepts (the example is run through `parse_command`; an example that
  is a usage error fails) → passes.
- Usage error: standard error, status 2, says how to get help → `help.rs::usage_errors_go_to_stderr_and_say_how_to_get_help`
  (binary with no arguments, an unknown command, an unknown option, a missing argument for each command) → status 2,
  stdout empty, stderr names `--help`.
- Parsed by hand, no parser crate → `help.rs::no_argument_parser_crate_in_the_graph` → passes on the real tree; the
  negative control (fixture lock with `clap`) fails it.
- Commands and options in the help are in `packaging/custodio.1` and the other way → `help.rs::man_page_and_help_agree`,
  driven by the command table (a command with no man page text fails) → passes; the two fixture controls fail.
  Man page text is tested against the code (the table), not against its wording.
- Fuzz target `cli_args` in `fuzz-smoke`'s expected list → `just fuzz-smoke` runs it and passes; `just fuzz-smoke "cli_args x"`
  fails (`x` missing) is the existing negative control of the recipe, run once by the builder.
- The parser and help modules (and the colour and error modules) are in the custodio-cli `mutants` list → `just mutants-diff F193`
  passes with no surviving mutant in them. That the modules are in the recipe's list is a review point (the justfile line); if the run is split, PROGRESS.md says which `--file` arguments each part used.
- Colour only on a terminal, never with `NO_COLOR` non-empty, no escape sequence otherwise, same words → colour unit tests
  (the rule over terminal × `NO_COLOR` unset, empty, "1") and `output_rules.rs`, which runs the binary for
  `--help`, `list --help` and one failing command (a usage error) with: stdout and stderr as pipes (no byte 0x1b on either);
  a pty and `NO_COLOR=1` (none); a pty with `NO_COLOR` empty or unset (the escape sequence appears, on the streams that are ptys);
  stdout a pty and stderr a pipe (no 0x1b on stderr; colour allowed on stdout); stdout a pipe and stderr a pty (no
  byte 0x1b on either stream, acceptance 10); and compares the coloured output
  with the escape sequences removed to the plain output → passes; fails if colour is written to a pipe or the plain text
  differs.
- Every error is two lines on stderr, the second a next step → unit tests over every variant in step 8 and `output_rules.rs`
  (the binary run for a usage error, a bad `register` option, `delete` of a key with no terminal, and the service absent
  with an empty bus address, each checked for at least two lines, status, and an empty stdout) → passes; a variant with one line
  fails.
- Service absent, polkit denial and unavailability, `register`'s refusals → unit tests of step 8 for `ServiceAbsent`,
  `PolkitDenied`, `AuthorizationUnavailable` and every `Refusal`; the "not authorized" and "cannot talk to the service" strings
  are asserted by those tests because other scripts read them → passes.
- Every error of `docs/api.md` is mapped → step 9's test; the fixture control with an unmapped name fails; the four
  names that are `Unknown` today make it fail before step 8's change (written first).
- No password, key material or unescaped untrusted text in a message → in the variant tests, inputs carry a sentinel password,
  key bytes and control characters (escape sequences, newlines) in ids, paths and the unknown error name; the output has none
  of the sentinels and no control character but the line ends → passes; removing the escape in one message (a
  mutant, run by `mutants-diff`) is caught.
- Exit status unchanged (0, 1, 2) → the existing `exit.rs` tests, updated to the new texts → pass.
- Whole feature → `just quick` and the `verify` command of features.json. The packaged man page's presence in every package
  and the help of the later commands are proven at the checkpoint features and by F197 and F202.
