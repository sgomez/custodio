# F94 — End-to-end journal cases for every operation

## Scope
Built: the `journal-ops-*` cases of `e2e/cases.list`, run by the e2e guest against the shipped service and the real journal. Alice (an
ordinary account, her own session and test agent) makes a fixed set of calls of all four operations, each with a known outcome, and root
reads the journal of `custodio.service` afterwards. They prove acceptance 7 of SPEC.md for the whole M3 surface.

Parts:
- A step group `journal-ops` in `e2e/select.sh` (`case_group`, `phase_runs`), so `just e2e-cases debian13 'journal-ops-*'` runs the setup and
  this step only, and `just e2e` runs it too. It runs after `delete` and before `upgrade`, like F91-F93. Every key it imports it deletes, so
  the state, `TOTAL` and the starting state of upgrade/lifecycle are as before (the builder shows this, as F91-F93 did).
- Calls with their outcomes (the ledger: operation, outcome, key id, caller pid, uid), all by alice, all counted by marker entries in the
  journal (the F91 pattern, `owner-journal.py`) so entries of the other steps never count:
  sign approved and denied; import stored, denied, and wrong password (approved); delete denied and then deleted; replace denied,
  replaced, and certificate mismatch (a certificate of another key). Calls are made with the CLI, `pkcs11-tool` and `owner-call.py`
  (F91/F93 patterns); each is started so that its pid is known (wrapper writing `$$` before `exec`, or the Python client printing its
  own pid), because the pid the bus reports is that of the process that made the call.
- Container-free tests of every new shell/Python helper and judgement, with bad-evidence cases that must fail (`scripts/test-e2e-*.sh`,
  run by `just quick`), as F91-F93 do.

Not built, owned elsewhere:
- What each outcome means, the fail-closed ordering and the forbidden-content rule at unit level: F75, F77, F79 (audit integration tests).
- The three app-id cases against a real caller: F95. Here the `CUSTODIO_APP_ID_STATE` of alice's own entries is only judged to be
  one of the three documented values and to agree with the `app_id_state` queries; the `read` / given-app-id queries are run and
  their result must equal what the same filter gives over the window (empty for a non-flatpak caller), not forged by this feature.
- `authorization_unavailable` entries and polkit asked once per call: F92 (polkit stopped, calls counted by the agent) and F75/F77/F79. This
  feature does not stop polkit.
- M1 signing entries per mechanism and the catalog: `journal-signatures`, `journal-entries`, `journal-catalog` (they keep their checks;
  the sign calls here add what they do not check, `CUSTODIO_OPERATION=sign` and the shared queries).
- Fail closed when the sink fails (acceptance 8) and the checkpoint runs (F90, F100); the cases on the other five targets are proven at F100.
The feature is about five steps; no split.

Environment (run in this session): `podman run --rm --privileged --cgroupns=host alpine echo ok` → `ok`; the local `custodio-e2e-*`
images exist. `systemd-cat`, `openssl`, `pkcs11-tool`, the test agent and `owner-call.py` are already used by F91-F93 steps in the guest.
A forged entry with the service's field names (needed for the query control) is written by root with `systemd-cat`/`logger --journald`;
the builder confirms in the guest that it can set `CUSTODIO_*` fields, and if not, drops only that control and says so in PROGRESS.md.

## Steps
- [ ] Failing container-free tests first: `select.sh` maps `journal-ops-*` to the group `journal-ops` (and leaves `journal-signatures`,
      `journal-entries`, `journal-catalog` where they are); `phase_runs` is true only when a case of the group is selected; the accounting
      reports every case exactly once; `guest.sh` runs the step after `delete` and before `upgrade`. Add the ids to `e2e/cases.list`.
- [ ] Judgement library and its self-test, as functions of files (the ledger and `journalctl -o json` / `-o export` output), each with
      bad-evidence cases that must fail: exactly one entry per ledger line with the right `CUSTODIO_OPERATION`, `MESSAGE_ID` of that
      operation, `CUSTODIO_UID`, `CUSTODIO_PID`, `CUSTODIO_KEY_ID`, `CUSTODIO_OUTCOME` (and its priority); no entry of the window that no
      ledger line explains; the secrets sweep (reusing `journal.py sweep`, extended if needed to the `.p12`, both certificates DER, the
      other key's certificate, the signed data, signatures, the right and the wrong password, in raw, hex and base64); the extraction of
      the `journalctl` queries from the fenced blocks of `docs/audit.md` and their expected result computed from the ledger.
- [ ] Guest side, alice's session: the calls of the ledger above with their pids, the agent set to approve or deny per call, the marker
      entries before and after, every key deleted at the end; root-side script that serves what alice cannot do and keeps the fixtures
      (a `.p12`, two certificates of one key, a second key and certificate, the right and a wrong password), as `rd-run.sh` does.
- [ ] Root side, judgement: `journalctl --sync`, then the window between the markers; the cases below judge it. The queries are the ones
      found in `docs/audit.md` (not retyped), with the documented placeholders (`1000`, `my-key`, `org.example.App`) replaced by alice's
      uid, a key of the ledger and a value that no entry has; the step fails if the document holds a query the step does not know how to
      judge, so a new documented query forces a new check. Wire the step into `guest.sh`.
- [ ] Negative controls (run, shown red, reverted): (a) one ledger call not made (an entry without a call, and a call the journal lacks);
      (b) the secrets sweep fed the certificate in base64 added to a copy of the export; (c) a forged entry (other `_UID`, same `CUSTODIO_*`
      fields) shown to be excluded by the documented queries while a query without `_SYSTEMD_UNIT`/`_UID` would return it; (d) a ledger
      line with the wrong operation. Then `just quick` and `just e2e-cases debian13 'journal-ops-*'` until both pass.

## Evidence
- The cases are in `e2e/cases.list`, reported exactly once each, and the selection reaches only their step → `scripts/test-e2e-select.sh`
  and the accounting tests (via `just quick`) → pass; a case missing from the guest output fails.
- Each judgement fails on bad evidence → the new `scripts/test-e2e-*.sh` self-test (via `just quick`) → passes, and each of its
  mutants (judgement weakened) is caught.
- Sign, approved and denied, leaves one entry → case `journal-ops-sign` → for each of the two calls exactly one entry of
  `custodio.service` with `CUSTODIO_OPERATION=sign`, `MESSAGE_ID` of sign, alice's uid, the pid of the calling process, the key id, and
  outcome `signed` resp. `denied`.
- Import, approved, denied and wrong password → case `journal-ops-import` → one entry each with `CUSTODIO_OPERATION=import`, the import
  `MESSAGE_ID`, uid, pid, key id and outcome `stored`, `denied`, `wrong_password`; the stored one carries `CUSTODIO_KEY_TYPE=rsa_2048`.
- Delete, denied then approved → case `journal-ops-delete` → one entry each, `CUSTODIO_OPERATION=delete`, outcomes `denied`, `deleted`,
  uid, pid, key id; the denied call's key still signs afterwards (the entries describe what happened).
- Replace, denied, replaced and mismatch → case `journal-ops-replace` → one entry each, `CUSTODIO_OPERATION=replace_certificate`,
  outcomes `denied`, `replaced`, `certificate_mismatch`, uid, pid, key id.
- Exactly one entry per call and no more → case `journal-ops-exactly-one` → between the markers the entries of the audit `MESSAGE_ID`s
  from `custodio.service` are as many as the ledger lines (each ledger line matched by exactly one entry, no entry unmatched); the
  control (a) and (d) of the negative controls make it fail.
- No entry holds the `.p12`, the password, the certificate bytes, the data or the signature → case `journal-ops-no-secrets` → the sweep of
  the whole export of `custodio.service` for the window finds none of those files or passwords, raw, hex or base64; control (b) shows the
  sweep reports a planted certificate (by kind and form, not the bytes).
- Every query `docs/audit.md` documents returns the expected entries → case `journal-ops-queries` → each `journalctl` query extracted from
  the document (all operations by `MESSAGE_ID` and by `CUSTODIO_OPERATION`, by uid, by key, by app-id and app-id case, by outcome, the
  mismatch query) runs unchanged but for its placeholders, and returns exactly the set of entries the ledger predicts (compared by
  operation, outcome, key, pid); queries with no ledger entry return nothing; the step fails when the document holds a query it does not
  judge; control (c) shows the forged entry is not returned by the documented trusted-field queries.
- Whole feature → `just quick && just e2e-cases debian13 'journal-ops-*'` → exit 0, the accounting lists the `journal-ops-*` cases and no
  other, and the state directory after the step equals the one before.
