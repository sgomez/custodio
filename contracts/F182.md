# F182 — The registration subcommand for native profiles, and its removal

## Scope
Builds, in `custodio-cli`, the native half of SPEC Design 3: a new subcommand (name and options the builder's, in the
man page and the usage text) that registers the installed module in every native profile that
`register_discover::discover` (F181) returns, with `modutil`, and removes every registration it made. The rules are the
`Decision:` lines of `docs/findings/F172.md` (the `modutil -add NAME -libfile PATH -force` form with stdin from
`/dev/null`; scratch copy of `cert9.db`, `key4.db`, `pkcs11.txt` and `rename(2)` of `pkcs11.txt` when the three exist,
otherwise `modutil` directly on the profile; `-delete NAME` to remove; leftover scratch directory deleted at the start of
each run and on failure; `modutil` is the only writer of module entries). Where they leave a choice the more
conservative option holds. Behaviours:
- **Refuses root and sudo**: effective uid 0, or `SUDO_USER`/`SUDO_UID` in the environment, is a usage error before any
  file is read.
- **Per profile**: a *held* profile (F181's lock state) is skipped, named, with "close the browser"; a profile marked
  `Skipped::P11Kit` is skipped with its reason (not fixable by the person, so it does not make the exit non-zero); a
  profile it cannot write (unwritable directory or `modutil` failing) is skipped with the reason and does make the exit
  non-zero. The exit is non-zero for any fixable skip, zero otherwise (also when nothing is found).
- **Recognition**: an existing entry is recognised by its `library=` value (the installed module's path), whatever its
  `name=`, so a hand-registered entry is "already registered" and no second is ever added. An entry whose library is a
  Custodio module file (`libcustodio_pkcs11.so` by file name) at a path that no longer exists is updated in place
  (delete by its name, then add under the same name, as F172 decides: one entry afterwards). The builder pins in step 2
  what happens to a Custodio-named library at a different path that still exists, choosing the conservative option.
  Nothing else is touched: entries of other modules, including ones whose library is missing, stay byte for byte.
- **Report**: per browser and profile, what it found and did (registered, already registered, refreshed, skipped and
  why), on stdout; reasons for skips and the final failure on stderr.
- **Removal**: deletes every entry whose library is a Custodio module (by the same recognition, any name, including a
  hand-registered one), is idempotent, and skips held profiles like registration does.
- **Left for other features**: the Firefox snap copy, its registration and removal, stale-copy refresh and the
  refresh-only mode (F183, which also owns `register_snap.rs` and `register_acceptance.rs`, acceptance 10 as a whole);
  the `modutil` package dependency (F184); the README and `docs/install.md` (F185, F186). F182 leaves a snap profile in
  the fixture home untouched. The man page entry is written here, as prose a person checks (not tested by grepping).
- **Environment** (checked now): `modutil` and `certutil` are in the dev container (`/usr/bin`, NSS 3.110; F172 measured
  them); `target/debug/custodiod` and `libcustodio_pkcs11.so` exist after a build; the container user is uid 1000, so the
  root refusal is run under `unshare -Ur` (uid 0 in a user namespace, as F178's tests do) and by `SUDO_UID`.
  **Open and decided by step 1**: `cargo test -p custodio-cli --test register_native` must reach a real service and the
  built module. Facts checked now: `scripts/deps_check.py` (in `just quick`, via `just deps-check`) follows normal, build
  and dev edges and fails on any path from a client crate to `custodiod`, so neither `custodio-cli -[dev]-> custodiod` nor
  `custodio-cli -[dev]-> custodio-it -[dev]-> custodiod` is allowed, and the contract does not permit weakening it.
  `cargo test -p custodio-cli` builds neither `custodiod`, nor an example of `custodio-it`, nor `libcustodio_pkcs11.so`
  (they exist now only because earlier runs built the workspace), so the test must obtain them from the current tree
  itself (for example by running `cargo build --locked` for the named package/example, or a helper the test locates by
  path after building it) and must **fail, not skip**, when one is missing or older than the tree's sources it was built from.
  The real `custodiod` binary needs the system bus (`Connection::system()`, so a private `dbus-daemon` through its
  address variable), a polkit stand-in on that bus, a TPM (swtpm) or the software store, `systemd-creds` and
  `STATE_DIRECTORY`; the example `custodio-it/examples/docs_api_server.rs` already runs the real service code on a private
  bus with a scripted authorizer and is the nearest existing model. Probed now: `dbus-daemon`, `swtpm`, `systemd-creds`
  (`--help` rc 0), `unshare` are in `/usr/bin`; whether `systemd-creds` and an import work as uid 1000 is not measured, so
  step 1 measures it and chooses between the real binary and a `custodio-it` example running the service library.
  Builder notes from the review: prefer running `cargo build --locked` for the named targets over a timestamp check;
  record the chosen route and why in `docs/decisions.md` (so it is not "simplified" into a dev-dependency); the module
  runs inside `modutil` and `certutil`, so the bus address variable it reads must be in their environment too; step 5
  measures what the build adds to each mutant of `just mutants-diff F182`. `unshare -Ur` is available (F178 relies on it).
  If no route works without weakening a gate, the builder writes `BLOCKED.md`; it does not move the real-service case to
  another crate on its own, because `verify` names this file.
- **Costs.** `register_native` is an integration test with real `modutil`/`certutil` (about 30–60 ms per call; a case
  makes 3–15 calls) over fixture homes in temp dirs: about 15 cases, estimated 10–15 s of CPU, all in parallel with each
  other and with the other integration tests (similar: `register_discover`, plus the private `dbus-daemon` rigs of
  `custodio-it`). The real-service case starts a private bus and service (about 2–4 s, like `snap_transport`'s). No e2e
  case, no script test (the distribution-dependent parts, other NSS builds and packages, are F172's evidence and the
  checkpoint's). Waits for the held-profile child are on a pipe, never a `sleep`. The mutants diff covers the new
  non-trivial module(s) (the builder adds them to the `mutants` recipe's `custodio-cli` list in the justfile).
  `budgets.tsv` has no budget for cargo tests; nothing here needs one.
- Six steps; the rig is split in two so each fits a session.

## Evidence
- One entry per profile, legacy and XDG both present → `register_native::registers_every_native_profile_once` on a
  fixture home with a legacy Firefox profile, an XDG profile, a Thunderbird profile and a profile lacking `pkcs11.txt`
  → after the run `modutil -list` of each profile (the real tool) shows exactly one module with the installed
  library, and the pre-existing entries are still there; the report names each browser and profile as registered.
  A profile reached from both roots (symlink) is registered once.
- Second run changes nothing → `register_native::a_second_run_is_byte_identical` → a hash of every file of the fixture
  home (not only `pkcs11.txt`) is equal after run 2, and the report says "already registered" for each profile (a
  negative control: a run with an altered installed path is not byte-identical, so the comparison can fail).
- Hand-registered entry, any name → `register_native::an_entry_added_by_hand_under_another_name_is_not_duplicated`
  (`modutil -add "my token" -libfile INSTALLED` by hand before the run) → still one entry for the library, under its
  original name, `pkcs11.txt` unchanged, report "already registered"; and the case with a different `name=` on two
  profiles.
- Stale entry updated in place → `register_native::an_entry_for_a_vanished_custodio_path_is_updated` (entry named
  `Custodio` pointing to `/old/libcustodio_pkcs11.so`, absent) → one entry afterwards, same name, library the installed
  path, report "refreshed"; and `register_native::a_foreign_entry_with_a_missing_library_is_left_alone` (same shape,
  library `/old/libother.so`) → `pkcs11.txt` byte-identical; plus the pinned conservative case for a Custodio-named
  library at a different existing path, which asserts with `modutil -list` the count of Custodio modules (never two).
- Touches only Custodio entries → covered by the two cases above and
  `register_native::removal_keeps_every_other_entry_as_it_was`: a profile with the internal module, two foreign
  modules (one with `parameters=` and `NSS=` lines, one with a missing library) and a Custodio entry → after removal
  the foreign entries' lines are identical and `modutil -list` shows no Custodio entry.
- Removal → `register_native::removal_leaves_no_custodio_entry_and_is_idempotent` → after removal on the fixture home
  (including the hand-registered entry) no profile's `pkcs11.txt` has a Custodio library; a second removal is
  byte-identical; removal on a profile that never had an entry changes nothing; a held profile is skipped and named.
- Refuses root and sudo → `register_native::refuses_root_and_sudo`: the real binary under `unshare -Ur` (uid 0) and with
  `SUDO_UID=1000` set → non-zero, message names the reason, the fixture home byte-identical, `modutil` never run (a stub
  `modutil` on `PATH` writes a marker file when run; the marker is absent). Control: the same invocation as uid 1000
  without `SUDO_*` proceeds.
- Skips a held profile, names it, exits non-zero → `register_native::a_held_profile_is_skipped_named_and_fails_the_exit`
  with a live-pid `lock` symlink and, separately, a `.parentlock` held by a child process (released through a pipe) →
  that profile byte-identical, the others registered, report line naming browser, profile and "close", exit non-zero;
  after the lock is released a re-run registers it.
- Other skips → `register_native::skip_reasons_decide_the_exit_code`: p11-kit system (`nss.config` with the line) →
  every native profile skipped with the reason, exit zero, nothing changed; an unwritable profile directory → skipped,
  reason named, exit non-zero; no profiles at all → exit zero and a report that says so.
- Interruption leaves the old state or the new one → `register_native::a_failing_modutil_leaves_the_profile_untouched`
  (a stub `modutil` on the program path that exits non-zero after writing into its scratch copy, and one where the test kills the command with
  `SIGKILL` once the stub `modutil` has signalled through a FIFO that it is running, no `sleep`) → the profile's three files are byte-identical, the scratch directory is gone (failure) or is
  removed by the next run (kill); the report names the profile as failed and the exit is non-zero. Missing `modutil` →
  an error naming it, exit non-zero, nothing changed.
- Read-only discovery still holds, and the command never writes outside the profile directories it handles and their
  scratch siblings → `register_native::only_handled_profiles_change`: file lists and hashes of the snap profile, an
  excluded browser's directory (`~/.zen`) and the home's other files are equal before and after.
- Registration against real NSS with the real service (acceptances 10 and 11, native part) →
  `register_native::nss_sees_the_custodio_token_and_the_certificate` → with the real service (private bus, a key and
  certificate imported through the service, `libcustodio_pkcs11.so` from the same build) and a profile registered by the
  command, NSS's `modutil -list` shows the Custodio module and its token, and `certutil -L -h <token>` lists the
  imported certificate's nickname; NSS's `certutil -K -h <token>` lists its key. Control: the same query on an
  unregistered profile shows neither. The test asserts on `modutil -list` showing exactly one Custodio module.
- The subcommand's argument handling (unknown option, no arguments, the removal option) → unit tests in
  `custodio-cli` beside `parse_command`'s, and `tests/exit.rs`-style checks of the real binary's exit code for a usage
  error; the man page text is checked by a person, and the existing `man.rs` test still passes.
- Whole feature → `just quick`, `cargo test -p custodio-cli --test register_native --locked`, and
  `just mutants-diff F182` (every mutant of the new modules caught or unviable) → green.
