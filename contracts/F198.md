# F198 — The packages leave PAM alone and the install notice names the fingerprint command and doctor

## Scope

Built here:

- The install notice. Today no package script prints one. After a first install (not an upgrade, not removal) the deb
  `postinst`, the rpm `%post` and the Arch `post_install` print, on stderr, a short notice that says the fingerprint is off
  for Custodio's dialogs and names `sudo custodio fingerprint enable` and `custodio doctor`. The wording is one text,
  the same in the three formats (the test compares the three captured stderr texts). It is printed after the existing work of the script and never changes the script's exit
  status or its calls (the lifecycle tests keep passing). It does not run the command: the package touches no PAM file.
  Upgrade stays silent, and so does a deb reinstall after a non-purge removal (`$2` set; say so in a comment) (conservative: the person decided on install). The notice is not a warning about an override.
- Removal: `prerm`/`postrm`, `%preun`/`%postun`, `pre_remove`/`post_remove` print nothing about
  `/etc/pam.d/polkit-1` and do not name it. The existing "keys stay on disk" notices are unchanged.
- The package gate (`scripts/check-packages.sh`, through `scripts/check_packages.py`) gains three rules, applied to each
  of the three formats: (a) no packaged file is under `/etc/pam.d/` or `/usr/lib/pam.d/` (the existing file-list rule
  already fails on unlisted files; the new rule says so by name); (b) no script of the package (deb control scripts, rpm
  scriptlets, Arch `.INSTALL`, the hook script and the two `.hook` files) contains `/etc/pam.d`; (c) each install script
  (deb postinst, rpm post, Arch `.INSTALL`) contains both `sudo custodio fingerprint enable` and `custodio doctor`.
  Every rule fails the gate with the format label and the offending path or script name; rule (a) prints its own
  message ("PAM directory") that the file-list rule does not, and the test asserts it.
- `scripts/test-check-packages-pam.sh`: fixture packages built with nfpm through `scripts/lib/package-fixtures.sh`
  (extended by the builder as needed): a clean one the gate accepts, and one negative control per rule: a package
  shipping `/usr/lib/pam.d/x` or `/etc/pam.d/x` (rule a), built and checked against a fixture config
  that lists that file (made with `scripts/lib/nfpm_edit.py`), so the file-list rule passes and only rule (a) can fail, one whose script names `/etc/pam.d` (rule b), one whose install
  script lacks the notice (rule c, with each of the two phrases missing in turn). Each runs for the formats the rule
  covers (the three) as independent cases in parallel. This is the gate's own negative control; no other test of the
  gate is planned.
- `scripts/test-package-scripts.sh` gains the check of the notice: the install script of each format, extracted from the
  real fixture package, is run (deb `postinst configure` without `$2`, rpm `post` with `$1=1`, Arch `post_install`) with
  the recording stubs and the stderr is captured; the notice is present, and absent on upgrade (`postinst configure OLD`,
  `$1=2`, `post_upgrade`). The removal scripts of each format are run (`prerm remove`, `postrm remove`, `purge`, `preun` and `postun` with
  `$1=0`, `pre_remove`, `post_remove`) and their output contains neither `pam` nor `fingerprint` (case-insensitive).

Left to other features: the `custodio fingerprint` command (F197, done), `doctor` and the e2e behaviour of the
override (F199, F203), the documents (their own features), the other package gates and the install/lifecycle runs on
real systems (checkpoints). The package format files themselves (`packaging/nfpm.yaml`) already ship no PAM file.

Cost (estimated from the similar existing scripts): `test-check-packages-pam.sh` builds four to six small nfpm packages
(about 1 s each, the builds and the cases in parallel) and runs the gate (about 1 s each): 10–15 s total, runs in parallel
with the other script tests. `test-package-scripts.sh` gains about 12 shell invocations: under 1 s. No cargo test, no e2e
case, no new budget needed; the builder adds the new script to `scripts/run-script-tests.sh` / the `test-scripts` recipe
beside `test-check-packages-deps.sh` and times it.

Environment: nfpm, dpkg-deb, rpm, bsdtar are what the existing package tests already use; nothing new.

## Steps

- [ ] Write `scripts/test-check-packages-pam.sh` first with its fixtures (clean, PAM file, script naming `/etc/pam.d`, script without each phrase); it fails on the current gate.
- [ ] Add the three rules to the gate (`check_packages.py`) and wire the new script into the test recipe; the script passes.
- [ ] Extend `scripts/test-package-scripts.sh` with the notice and removal-silence checks (red first).
- [ ] Add the notice to deb `postinst`, rpm `post` and Arch `post_install` (install only); `test-package-scripts.sh` passes.
- [ ] Run the lifecycle scripts that execute these scripts (`test-deb-lifecycle.sh`, `test-rpm-lifecycle.sh`, `test-arch-lifecycle.sh`, `test-arch-scripts-static.sh`) and fix any that expected silence; run `just quick` and the `verify` scripts.

## Evidence

- No package format ships a file under `/etc/pam.d/` or `/usr/lib/pam.d/` → `scripts/test-check-packages-pam.sh`, cases "shipped PAM file" (each of the two directories, each format, config listing the file) → gate exits non-zero with the "PAM directory" message, the format and the path; the clean package → gate exits 0.
- No package script (deb, rpm, Arch) refers to `/etc/pam.d`; the check enforces it → same script, case "script names /etc/pam.d" per format → gate fails naming the format and the script.
- The package check enforces the notice → same script, cases "no `sudo custodio fingerprint enable`" and "no `custodio doctor`" per format → gate fails naming the format and the missing phrase.
- The real packages pass the new rules → `scripts/test-check-packages.sh` (its good set runs the gate) → passes.
- The install notice says the fingerprint is off and names both commands, for each format (acceptance 5) → `scripts/test-package-scripts.sh`, running the real deb postinst, rpm post and Arch post_install → stderr contains the phrase "fingerprint is off", `sudo custodio fingerprint enable` and `custodio doctor`; on upgrade the notice is absent; exit status and recorded calls are unchanged.
- Removal prints no warning about an existing override → `scripts/test-package-scripts.sh`, pre-removal, removal and purge scripts of each format → output has no `pam` and no `fingerprint`.
- The package does not touch PAM on any script path → rule (b) above on the real packages (in `scripts/test-check-packages.sh`) plus the unchanged lifecycle tests → pass.
- Nothing else broke → `just quick` → green.
