# F199 — End-to-end: the fingerprint command on every target

## Scope

Built here:

- **A `fingerprint-*` case group** of the container suite, run as root on the real `/etc` and `/usr` of each of the five
  targets, after the package is installed. A new guest step `fingerprint` (`e2e/fingerprint-run.sh`, called from
  `e2e/guest.sh` before the `upgrade` step; `case_group` and `phase_runs` in `e2e/select.sh` learn the group) runs the real
  `custodio fingerprint` of the installed package. It does not touch the daemon, keys or the TPM, so it does not depend on
  the TPM mode. It runs in the container targets only, not in the VM (`e2e/vm/cases.list` is not changed; the VM group is a
  later feature).
- **The ids.** In `e2e/cases.list` (every target owes them; none may be skipped, which the `verify` checks):
  `fingerprint-enable-file` (exact content, mode 0644, `root:root`), `fingerprint-pam-password` (a PAM client of
  `polkit-1` authenticates a test user by password through the include; a wrong password is refused),
  `fingerprint-enable-twice` (second `enable` succeeds and changes nothing), `fingerprint-refuse-foreign`,
  `fingerprint-refuse-no-vendor`, `fingerprint-refuse-no-module` (each exits non-zero and changes nothing),
  `fingerprint-disable-restores` (the state of `/etc/pam.d` is byte for byte the one before `enable`).
  Family cases go to the target's own `cases.list` (the Debian family: `debian13/cases.list` and `ubuntu2604/cases.list`
  exist; `fedora44` and `alma10` get a new one; `arch` has none): `fingerprint-pam-auth-update` on debian13 and ubuntu2604
  (`pam-auth-update --enable fprintd` and `--disable fprintd` leave the override byte-identical),
  `fingerprint-selinux-label` and `fingerprint-authselect` on fedora44 and alma10 (label equal to the policy's default for
  `/etc/pam.d`; `authselect apply-changes` leaves the override byte-identical). The builder may split an id in two where one
  judgement needs it.
- **The container images.** The five Containerfiles add `fprintd`, the family's PAM module (`libpam-fprintd`, `fprintd-pam`,
  Arch's `fprintd`) and a PAM client. The client may be anything from the distribution's own archives or the Python already in
  the image (for example `ctypes` on `libpam`); no download from elsewhere. The images already write a pam_permit
  `/etc/pam.d/polkit-1` for the test agent: that file is a foreign file. The group sets it aside, works on the real
  layout (no `/etc/pam.d/polkit-1`), and puts it back (content, mode, owner, label) at the end and from an exit trap, so the
  later steps still have their agent. The step creates a test user with a password and removes it.
- **The judge.** `e2e/fingerprint.py` (a judge the run uses) takes the observation files the guest step writes (manifests of
  `/etc/pam.d` and of the files the command may not touch: path, type, mode, owner, label, hash; each command's exit status and
  output; the PAM client's results) and decides each case. `scripts/test-e2e-fingerprint.sh` runs it on fixture
  observations: one accepted set, and one rejected set per rule (wrong content, mode, owner, a changed manifest after a refusal,
  after the second `enable`, after `disable`, a PAM client that accepts a wrong password, a label different from the default, an
  override altered by `pam-auth-update`/`authselect`). That is the only test of the judge. The guest script itself, the Containerfiles
  and the wiring are proven by the runs.
- **Left to other features:** the `custodio fingerprint` code and its fixture-root tests (F197, done); the packages and the
  install notice (F198, done); `doctor` (F203; acceptance 17's last sentence); the Ubuntu VM group; the documents.
  F197's `apply_owner` and `apply_label` (excluded from mutation testing, the comment names F199) are proven here: owner
  and label on the real file system.

Environment, checked in the dev container: `podman` is present (`/usr/bin/podman`), no image is cached locally, so the first
run of each target pulls and builds its image (network needed; the loop's e2e runs already do this). `/sys/fs/selinux` does not
exist here (the kernel is Ubuntu's, no SELinux; the same limit as F131 and F147 found). So in a fedora44 or alma10 container on
this host SELinux is **not enforcing**, and the label cannot be exercised on it. The case `fingerprint-selinux-label` is
therefore written to decide from the observed state: where `/sys/fs/selinux/enforce` reads 1 it requires the label of the
written file to equal `matchpathcon -n /etc/pam.d/polkit-1` (and `restorecon -n` to report nothing to change); where it does not
exist or reads 0 it reports the case as run, requires that no label step failed, and prints "SELinux not enforcing here". The
judge's fixtures cover both branches (the enforcing one with a wrong label as negative control). The enforcing branch is proven
on a real SELinux host by a person's run of the same command (`docs/manual-acceptance.md` section 11, fedora44, already lists a
fingerprint-free SELinux run; the builder adds one line for this case there if the file's format allows, else records it in
PROGRESS.md for the evaluator). No deviation is needed: the requirement says "where SELinux is enforcing", and the group does
what it says on each system; what the dev container cannot show is stated here, not hidden.

Not decided here, left to the builder's first runs (each recorded in a finding `docs/findings/F199.md` if it changes the plan):
package names and availability per family (Alma 10's `fprintd-pam`, Arch's `fprintd` for the module); where each family's
`pam_fprintd.so` lives (the command already searches `{usr/,}lib{,64}/security` and `lib*/*/security`); whether `authselect
apply-changes` has a profile to apply in the Fedora and Alma images (the builder may select one in the case and restores
the files of `/etc/authselect` and `/etc/pam.d` it changes, or in the Containerfile). If `authselect` cannot run in the
image at all, the builder shows it with a command and the finding, amends this contract to the narrowest replacement, and
records a deviation as CLAUDE.md says. Which observation proves that `pam_fprintd` was reached through the override (for
example fprintd's D-Bus activation or its journal line, absent before and after `disable`): it must fail if `polkit-1` ignored
the override.

Cost (estimated; the builder measures and records it in PROGRESS.md). The judge test: a Python run on a dozen small
fixtures, under 2 s, parallel with the other script tests. The group in a container: `enable`/`disable` take milliseconds
except the reader probe (up to 1.5 s, bounded by the command); each PAM client run goes through `pam_fprintd` and may start
`fprintd` by D-Bus activation (about 1 to 5 s the first time); `pam-auth-update` and `authselect` about 1 to 3 s. The group is
inherently sequential (all cases share one real `/etc/pam.d`), 20–40 s per target and run, in the guest of each target,
and the five targets run at once (`e2e/run.sh`). It is the cheapest level that can show owner, label, a PAM client and the
two tools; fixture-root tests (F197) already prove the decisions. Image builds add the packages (a few seconds of install,
cached after the first). The e2e budgets in `budgets.tsv` (debian13 800 s, ubuntu2604 530 s, fedora44 570 s, alma10 540 s,
arch 480 s) are tight against their last loop runs; if the measured full-run time with the group does not fit, the builder
asks for a bigger budget in BLOCKED.md and does not trim the group. On debian13 a full `just e2e` runs the swtpm and none
modes and so the group twice; that is accepted (under a minute) rather than special-cased.

## Evidence

- `enable` writes the exact file, mode 0644, `root:root` (acceptance 17) → `just e2e-cases <target> 'fingerprint-*'`, case
  `fingerprint-enable-file`, judged by `e2e/fingerprint.py` from the real file → passes on all five targets; the judge rejects
  a wrong content, mode or owner → `scripts/test-e2e-fingerprint.sh`.
- A PAM client of service `polkit-1` authenticates the test user by password through the include, `pam_fprintd` falling
  through for lack of a reader → case `fingerprint-pam-password`: the right password is accepted, a wrong one is refused
  (a client that accepts anything would fail it), and `pam_fprintd` was reached through the override (the observation fixed
  by the builder), absent again after `disable`; the judge's control: a client that accepts the wrong password is rejected.
- `enable` again changes nothing and succeeds → `fingerprint-enable-twice`: exit 0, manifest of `/etc/pam.d` (content, mode,
  owner, label, mtime of the file) identical to before the second call; control: a changed manifest is rejected.
- A foreign file, a missing vendor file and a missing module are each refused with nothing changed → `fingerprint-refuse-foreign`
  (the image's pam_permit file, and no other file touched), `fingerprint-refuse-no-vendor` (`/usr/lib/pam.d/polkit-1` moved
  aside), `fingerprint-refuse-no-module` (`pam_fprintd.so` moved aside): non-zero exit, the message names the cause,
  and the manifests of `/etc/pam.d` and of the moved-aside paths are unchanged; the system files are put back and the exit trap
  restores them if the case fails. Control: a refusal that left a file behind is rejected.
- `disable` restores `/etc/pam.d` byte for byte → `fingerprint-disable-restores`: the manifest (every file: path, type, mode,
  owner, label, hash) equals the one taken before `enable`, with no `polkit-1`; the test agent's file is back afterwards with
  the same bytes, mode, owner and label as before the group. Control: a manifest with one extra or changed file is rejected.
- On Debian and Ubuntu, `pam-auth-update --enable fprintd` and `--disable fprintd` leave the override byte-identical
  (acceptance 17) → `fingerprint-pam-auth-update` on debian13 and ubuntu2604: hash, mode, owner of `/etc/pam.d/polkit-1`
  equal after each call, `common-auth` changed by `--enable` (so the tool really ran) and back after `--disable`; control: an
  altered override is rejected.
- On Fedora and Alma the written file's SELinux label equals the policy's default for `/etc/pam.d` where SELinux is enforcing
  → `fingerprint-selinux-label` on fedora44 and alma10: the branch described under Scope; in this dev container the
  not-enforcing branch runs and is reported as run; the enforcing branch is judged on fixtures (a wrong label is rejected) and
  by a person's run on a SELinux host (Scope). This is the one piece the dev container cannot show.
- On Fedora and Alma `authselect apply-changes` leaves the override byte-identical (acceptance 17) → `fingerprint-authselect`:
  the command ran and succeeded (its exit status and a changed or re-applied authselect-managed file prove it), the override
  is identical; control as above.
- The group runs on every target and none of its cases is skipped → the `verify` line
  `! grep -qs '^fingerprint-' e2e/targets/{fedora44,alma10,arch}/skip.list` and each `just e2e-cases <target> 'fingerprint-*'`
  (the accounting of `check-cases.sh` requires each selected id exactly once, run); the debian13 and ubuntu2604 runs are in
  the `verify` too.
- The judge's own rules → `scripts/test-e2e-fingerprint.sh` (accepted set passes; one negative control per rule fails with
  the rule named) → passes in under 2 s.
- The later steps still work with the group in place (the agent's file is restored; the select wiring knows the group) →
  `scripts/test-e2e-select.sh`, `scripts/test-e2e-skips.sh`, `scripts/test-e2e-selftests.sh` and `just quick` → green; the
  full-suite effect is read by the loop against `budgets.tsv` (Scope, Cost).
