# F20 — Composed mechanisms in C_GetMechanismList, C_GetMechanismInfo, C_SignInit and single-part C_Sign

## Scope
Wires `custodio_pkcs11::composed` (F19) into the module for the single-part path. Changes are in
`module.rs` (logic, no pointers), `ffi.rs` (argument checks, list and info), their unit tests, and
the cryptoki integration test in `crates/custodio-pkcs11/tests/cryptoki`.

- `Mechanism` gains a composed variant holding a `Composed`. `Mechanism::new` accepts the six
  composed `CKM_*` values with no parameter; any parameter (non-null `pParameter` or non-zero
  `ulParameterLen`) is `CKR_MECHANISM_PARAM_INVALID`, decided in `C_SignInit` before any service
  call. `sign_init` rejects a mechanism whose key type does not fit the token with
  `CKR_KEY_TYPE_INCONSISTENT` (as for the raw ones). Neither failure reaches the service or polkit.
- `mechanisms(token)` returns the raw M0 mechanisms plus, for an RSA token, the three
  `CKM_SHA*_RSA_PKCS` and, for a P-256 token, the three `CKM_ECDSA_SHA*`. `C_GetMechanismInfo`
  answers for exactly those; composed ones get the same key-size bounds and flags as their raw
  counterpart (`CKF_SIGN`, plus `CKF_EC_F_P | CKF_EC_NAMEDCURVE` for ECDSA).
- `Session` state for sign holds the checked mechanism. `Module::sign` for a composed mechanism:
  length query or buffer smaller than `signature_len()` returns `Length`/`TooSmall` before any
  hashing, service call or polkit, and keeps the operation; with a large enough buffer it ends the
  operation, hashes `data` in the module with `DigestHasher` (streamed in chunks, no copy of the
  whole message beyond what the client already holds), calls `sign_input`, and sends only that,
  with the raw mechanism (`CKM_RSA_PKCS`/`CKM_ECDSA`), to the backend. Any other failure ends the
  operation, as in M0.
- Hashing runs after the `Mutex<State>` guard is dropped, like the backend call today, so a large
  message never stalls other sessions. Structurally: the guard lives in a block that returns only
  owned values (key id, checked mechanism), and hashing is a free function `hash_message(&Composed,
  &[u8]) -> Vec<u8>` with no access to `Module` or the guard, so it cannot run under the lock.
- New dev-dependency of `custodio-pkcs11`: `libloading` (for `composed_retry`, which loads
  `C_GetFunctionList` from the built module). The `Cargo.lock` change and a `cargo deny` pass are
  expected; the licence must already be allowed, otherwise the builder writes `BLOCKED.md`.
- The key-size bounds and flags of `C_GetMechanismInfo` move into a pure function in `module.rs`
  (`mechanism_info(&Token, mechanism) -> Option<(bits, flags)>`), so both token types are unit
  tested there; `ffi.rs` only writes the result. `fake.rs` (shared with the fuzz target and
  `ffi/tests.rs`, one P-256 slot) is not changed; the recording backend is a new type in
  `module/tests.rs`, next to the existing `Fake`.
- The data-size limit is the client's memory only; the service's 1024-byte input limit applies to
  the digest/`DigestInfo`, which is always smaller.

Left for other features: `C_SignUpdate`/`C_SignFinal` (F21; they stay `unsupported::*`),
`C_Login` (F22+), audit/journal, fork/thread tests of multi-part operations, e2e with
`pkcs11-tool`. The raw-mechanism code paths and their tests are not changed. One exception, stated
openly: the `basic` child scenario asserts `mechs == vec![ECDSA]` for the P-256 token, which
cannot stay true once composed mechanisms are listed. That list assertion (only) is loosened to
`contains`; the exact lists are asserted by the new scenario below. Its sign calls, the expected
signatures and `f.asked() == 3` stay as they are, and the composed signing goes in new scenarios
so M0 counts do not move.

The feature is about five steps; no split needed.

## Steps
- [ ] 0. Add an RSA DER certificate fixture for the unit tests: extract it from the existing
      `tests/fixtures/rsa2048.p12` with `openssl pkcs12 -nokeys` and convert it to DER
      (`gen.sh` is not run; it would make new keys). Add the new recording backend type.
- [ ] 1. `Mechanism` composed variant, parameter check in `Mechanism::new`/`C_SignInit`, `fits`, and
      `mechanisms()` per key type, with unit tests in `module/tests.rs` written first.
- [ ] 2. `mechanism_info` in `module.rs` and `C_GetMechanismInfo` using it, with unit tests for
      both token types and a P-256 test through the `extern "C"` function in `ffi/tests.rs`.
- [ ] 3. `Module::sign` for composed mechanisms: hash, `sign_input`, raw `SignParams`, length
      query and too-small buffer before hashing and without ending the operation. Unit tests with a
      recording backend.
- [ ] 4. Integration: a recording of the service's input, the `composed` scenarios in
      `tests/cryptoki` (listing, mismatch, parameter, sign and verify, retry, large message).
- [ ] 5. Run `just check` and `just test-integration`; append the `PROGRESS.md` entry; commit.

## Evidence
Unit tests are in `custodio-pkcs11` (`cargo test -p custodio-pkcs11 --lib`) with a fake `Backend`
that records `(id, SignParams, data)` of every call. Integration tests are `just test-integration`.

- RSA token has no ECDSA mechanism, P-256 token has no RSA mechanism, composed ones listed →
  `module::tests::mechanism_lists_fit_the_key`: asserts the exact sets (sorted, literal `CKM_*`
  values from `cryptoki_sys`): RSA = `RSA_PKCS`, `RSA_PKCS_PSS`, `SHA256/384/512_RSA_PKCS`;
  P-256 = `ECDSA`, `ECDSA_SHA256/384/512` → equal. Same through the built module in the
  integration scenario `mechanisms` (`C_GetMechanismList` via `cryptoki`, for the `rsa` and `ec`
  slots), asserted exactly, also as a set equality so an extra or missing entry fails.
- `C_GetMechanismInfo` describes only the fitting ones → `module::tests::mechanism_info_fits_the_key`
  calls `mechanism_info` for every one of the six composed values on both tokens: `Some` with
  bits 2048 (RSA) or 256 (P-256) and flags `CKF_SIGN` (plus `CKF_EC_F_P | CKF_EC_NAMEDCURVE` for
  ECDSA) on the fitting token, `None` on the other; also `CKM_SHA224_RSA_PKCS`,
  `CKM_SHA1_RSA_PKCS`, `CKM_ECDSA_SHA1` → `None`. `ffi::tests::composed_mechanism_info` calls the
  `extern "C"` `C_GetMechanismInfo` on the P-256 slot: `CKR_OK` and ECDSA flags for the three
  `CKM_ECDSA_SHA*`, `CKR_MECHANISM_INVALID` for the three RSA ones. The integration scenario
  `mechanisms` repeats it through `cryptoki`'s `get_mechanism_info` on both slots (`sign()` set,
  `verify()` not set; the other key type's mechanisms give an error).
- Parameter on a composed mechanism fails, no polkit → unit test
  `module::tests::composed_with_parameter_is_refused` (`Mechanism::new` with a parameter) and
  `ffi::tests::composed_sign_init_parameter` (the `extern "C"` `C_SignInit` on the P-256 slot, with
  non-null `pParameter` of length 0, null with length 1, and a PSS-params struct) →
  `CKR_MECHANISM_PARAM_INVALID`. The module test checks that the recording backend has 0 calls.
  `ffi::tests` runs on the unchanged `fake.rs`, which cannot record calls; it does not need to,
  because the refusal is decided in `Mechanism::new` before any backend call exists on that path
  (the module test proves that), and the ffi test only asserts the return code. Both tests then
  call `C_SignInit` with the no-parameter mechanism and assert it succeeds (the refused init did
  not leave an operation active). `cryptoki` cannot attach a parameter to these mechanisms, so the parameter
  case is covered by `ffi::tests::composed_sign_init_parameter` with a hand-built `CK_MECHANISM`; the
  scenario `composed_refusals` also asserts `f.asked() == 0`.
- Key and mechanism mismatch fails, no polkit → unit test `composed_mismatch_is_refused`: each of
  the three RSA composed mechanisms on the P-256 token and each ECDSA one on the RSA token →
  `sign_init` returns `CKR_KEY_TYPE_INCONSISTENT`; backend 0 calls. Integration scenario
  `composed_refusals` does the same six pairs through `cryptoki` `session.sign(...)` (error
  `KeyTypeInconsistent`), then asserts `f.asked() == 0` in the parent (fails if polkit was asked).
- Hash in the module, service gets digest or DigestInfo only → unit tests
  `composed_sign_sends_digest_or_digestinfo` for all six mechanisms, message `"abc"`: the recorded
  call has `SignParams.mechanism == CKM_RSA_PKCS` (RSA) or `CKM_ECDSA` (ECDSA), `hash == 0`,
  `salt_len == 0`, and `data` equal to literal hex expected values (RFC 8017 prefix + FIPS 180
  "abc" digest for RSA; the bare 32/48/64-byte digest for ECDSA), not computed by `sha2` in the
  test; the lengths are exactly 51, 67 and 83 for RSA SHA-256/384/512 and 32, 48 and 64 for ECDSA.
- Acceptance 4, the input the service receives, through the built module →
  integration scenario `composed_sign`, whose parent starts the bus with a monitor: a second
  connection to the private bus calls `org.freedesktop.DBus.Monitoring.BecomeMonitor` and records
  every `Sign` method call to `com.rfirma.Custodio1` (the real wire message the real service
  received; the service is not replaced). For each of the six mechanisms the child signs a message
  of known content; the parent decodes the recorded body `(id, mechanism, hash, salt_len, data)` and
  asserts: `mechanism` is `CKM_RSA_PKCS` or `CKM_ECDSA`; `data` equals the digest or DigestInfo,
  where the expected value is computed in the parent with independent code (`sha2` plus the
  RFC prefix, or the `rsa` crate's `Pkcs1v15Sign::new::<ShaN>()` prefix); and the message is not
  present anywhere in the raw bytes of the recorded message (`windows` search of a 16-byte
  distinctive marker repeated through the message). If `BecomeMonitor` fails on the private
  `--session` bus the test fails hard (no skip, no fallback). It also fails if the monitor records
  zero `Sign` calls, so a broken monitor cannot pass vacuously. The 6 recorded calls are matched to
  the mechanisms in order (the child signs in a fixed order and the parent checks that each body's
  `mechanism` and `data` belong to the same entry), so a digest swapped between two mechanisms
  fails. The scenario ends with exactly 6
  recorded `Sign` calls and `f.asked() == 6`; its large-message part is the separate scenario
  `composed_large` below.
- Signature verifies over the original message → same scenario: the child prints each signature;
  the parent verifies with an independent verifier that hashes the message itself:
  `rsa::pkcs1v15::VerifyingKey<ShaN>::verify(message, sig)` against the `rsa` test certificate's
  public key and `p256::ecdsa::VerifyingKey::verify_prehash` over the verifier's own digest for
  ECDSA, for SHA-256/384/512 (so truncation is exercised through the whole path) → all six `Ok`;
  the same signature over a different message → `Err`. Because `verify_prehash` truncates with the
  same code as the service's `sign_prehash`, the SHA-384/512 ECDSA signatures are also verified
  over the parent's own digest cut by hand to its leftmost 32 bytes (FIPS 186) → `Ok`, and over the
  rightmost 32 bytes → `Err`. The public keys come from the DER certificates the module lists,
  not from the private store.
- Data size limited only by client memory → integration scenario `composed_large`: the child signs
  a 64 MiB message (far over the service's 1024-byte `MAX_SIGN_DATA_LEN`) with
  `CKM_SHA256_RSA_PKCS` and then `CKM_ECDSA_SHA384`; both succeed and verify as above, the monitor
  records exactly 2 `Sign` calls, each body under 1 KiB, and `f.asked() == 2`. The child builds the
  message as a 16-byte marker repeated to 64 MiB (length is a constant shared by both sides);
  the parent rebuilds the same bytes for verification, so nothing is passed through stdout. The
  marker search of acceptance 4 also runs on these two recorded bodies. Unit test
  `module::tests::composed_sign_big_message` calls `Module::sign` with a zero-filled slice of 16 MiB
  (`1 MiB` under `cfg!(miri)`, so `just miri` finishes without `#[ignore]`) and checks the recorded
  `data` equals the digest of the same bytes hashed in one shot by the test, a known-answer for
  the zero-filled size → equal (fails if the module truncates or caps the data). A unit test
  `composed_backend_runs_outside_the_state_lock` is deterministic: the recording backend's `sign`
  calls `open_session` and `slot_list` on the same `Module` from inside the call → both return
  (would deadlock if the guard were held across the backend call; the test runs the call on a
  thread with a bounded `recv_timeout` so a deadlock is a failure, not a hang). That the hash
  itself runs outside the lock is shown only by the structure described in Scope (guard block
  returns owned values; `hash_message` has no access to the state), checked in review; a timing
  test for it would be best-effort and is not claimed as proof.
- Length query and too-small buffer: length, `CKR_BUFFER_TOO_SMALL`, no polkit, operation stays →
  unit test `composed_length_query_and_small_buffer`: for RSA (256) and ECDSA (64), a `None`
  capacity returns `Length(n)`; a capacity of `n - 1` and of 0 returns `TooSmall(n)`; after each,
  the backend has 0 calls; then a large enough capacity returns the signature with exactly 1
  backend call, and a further `sign` without init returns `CKR_OPERATION_NOT_INITIALIZED`
  (operation ended). The backend recording shows 0 calls for the query and the small buffers. Integration scenario `composed_retry`: the child calls `C_Sign` through the raw `cryptoki_sys`
  function list (the function list obtained from the loaded module, e.g. through `C_GetFunctionList` on the
  same library the child loads) with a NULL buffer, then a 1-byte buffer, then a buffer of the returned length, for
  one RSA and one ECDSA composed mechanism; it asserts, per call: NULL buffer → `CKR_OK`
  with `*pulSignatureLen` = 256 (RSA) or 64 (ECDSA); 1-byte buffer → `CKR_BUFFER_TOO_SMALL` with
  the same length written back; buffer of that length → `CKR_OK`, `*pulSignatureLen` unchanged and
  a signature the parent verifies. There is no new `C_SignInit` between the three calls. The child
  uses `Session::handle()` of cryptoki 0.12.1 for the session. The parent asserts
  `f.asked() == 2` in total for the two mechanisms (fails if polkit was asked on the query or the
  small buffer, or twice on a retry), exactly 2 recorded `Sign` calls, and that both signatures
  verify over the message as above.
- Any other failure ends the operation → unit test `composed_failure_ends_the_operation`: backend
  returns `Denied`, `Invalid` and `Unavailable` in turn → `CKR_FUNCTION_FAILED`,
  `CKR_DATA_INVALID`, `CKR_DEVICE_ERROR`; after each, `sign` returns
  `CKR_OPERATION_NOT_INITIALIZED` and a new `sign_init` is accepted. A wrong-sized signature from
  the backend → `CKR_FUNCTION_FAILED` and ended. Integration scenario `composed_denied` (polkit
  refuses): composed `session.sign` fails with `FunctionFailed` and returns no signature bytes (the
  parent asserts the output buffer is untouched), the next attempt asks polkit
  again (`f.asked() == 2`) and, after the failure, a `C_Sign` without init fails
  `OperationNotInitialized`.
- Raw mechanisms unchanged → `cargo test -p custodio-pkcs11 --lib` and
  `cargo test -p custodio-pkcs11 --test cryptoki`: every existing test in `module/tests.rs`,
  `ffi/tests.rs` and the `tests/cryptoki` scenarios passes, with `git diff` on those files showing
  only added tests, apart from the single loosened mechanism-list assertion in `basic` named in
  Scope (a reviewer can check with `git diff -- crates/custodio-pkcs11/tests/cryptoki/child.rs`).
  `lists_certificates_and_signs_through_the_service` still asserts `f.asked() == 3`. `cargo test
  -p custodiod` passes, with no edits under `crates/custodiod/src` or `crates/custodiod/tests`
  (`git diff --stat` on that path is empty).
- No new `unsafe` beyond the FFI argument handling → `git diff` of `module.rs` contains no
  `unsafe`; each new `unsafe` in `ffi.rs` has a `// SAFETY:` comment. No `#[allow]` without a
