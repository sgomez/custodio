# F183 — The Firefox snap registration, stale-copy refresh, and the VM group set up by the command

## Scope
Extends `custodio register` (F182, `custodio-cli/src/register_native.rs`; the builder may split the snap half into a new
module of `custodio-cli`, which then joins the `mutants` recipe's `custodio-cli` file list in the justfile) with the
snap half of SPEC Design 3 and 4, and sets up the VM snap group with it. F182's rules for native profiles do not
change; the snap profile is the one `register_discover::discover` already returns with `snap: true`
(`~/snap/firefox/common/.mozilla/firefox/`, lock state included). Behaviours:
- **The copy.** The fixed path is `~/snap/firefox/common/libcustodio_pkcs11.so` (the path F179's harness already uses),
  mode 0755. It is placed when the snap has a profile (the discovery result) and registered at that path in each snap
  profile with the same `modutil` routine F182 uses (recognition by library, never a second entry). "Installed" and
  "has a profile" are what discovery says; a snap without a profile, or no snap, gets no copy and no error. An snap
  profile entry that points to the installed path (not the copy) is left as it is, as F182 pins for a Custodio library at
  another existing path. The registered path is the host path of the copy, as the F172/F179 finding shows it worked.
- **Writing.** The copy is written to a temporary file in the same directory and `rename(2)`d over the target; the
  temporary file is removed on failure, and one left by a killed run is removed by the next run. A symlink at the copy
  path is replaced as a link (never followed). An interruption leaves the old copy or the new one.
- **Refresh.** On every run (registration and refresh-only), a copy that exists and whose bytes differ from the module
  being registered (the installed module, or `--module`) is replaced at the same path. Equal bytes: not touched (mtime
  and inode unchanged). No copy: none is created by a refresh, by refresh-only mode, or by registration when the snap has
  no profile. A held snap profile does not stop a refresh (the rename leaves the running browser its old mapping) but
  does stop its registration (named, "close the browser", non-zero, as F182).
- **A copy that cannot be replaced** (unwritable directory, a directory at the path, the temporary file cannot be
  created) makes the command exit non-zero with a line on stderr naming the copy's path and the reason; the old copy stays
  as it was. A missing module file stays F182's one error (nothing changes); refresh-only with no installed module
  changes nothing and exits zero with a journal line saying so (the conservative reading: an uninstalled package leaves
  inert copies, SPEC Design 3).
- **Removal** (`--remove`) also deletes the copy (absent copy: nothing, idempotent) and the snap profile's Custodio entries
  (every Custodio-named library, as F182). Conservative pin: a held snap profile keeps both its entry and its copy, is
  named, and makes the exit non-zero; the copy is deleted only when no entry of any snap profile remains pointing to it.
- **Refresh-only mode.** A new option of the subcommand (name the builder's, in the man page and usage text), which
  does only the copy refresh: no discovery of native profiles, no `modutil` (it works where `modutil` is absent), no lock
  checks. Same root/sudo refusal as the rest. Its outcome (refreshed, up to date, no copy, or failure with the reason)
  goes to the user's journal. How is the builder's within this limit: an entry reaches the journal through the journald
  native socket (as `custodiod`'s `JournalSink` does) or the unit's stderr, but the test must see the entry the
  command sends, so the socket path is injectable and the entry carries a fixed `SYSLOG_IDENTIFIER`, a priority (error for a
  failure, info otherwise) and the copy path. A journal that cannot be reached never changes the exit status and its
  failure is reported on stderr. The per-user units that call this mode, and the `modutil` dependency, are F184.
- **Left for other features.** The systemd user units and the packaging (F184, which proves acceptance 12's trigger part);
  the README and `docs/install.md` (F185, F186); the real VM run (the last feature: this feature changes the VM scripts
  and judges them with `scripts/test-e2e-vm-snap.sh`, but runs no VM); native-profile behaviour (F182).
  Acceptance 12's command part (stale copy refreshed, never silent) is proven here; acceptance 10 as a whole, which F182
  proved only for native profiles, is proven by `register_acceptance.rs`. The root refusal and held-profile skip of
  acceptance 10 are proven in detail by F182; here they are checked once more, on the whole-flow home through the real
  binary, because the acceptance states them as one scenario.
- **The VM group.** `e2e/vm/snap-user.sh`'s `place` phase runs `custodio register` as the user instead of `install` of
  the module (the test client `snap-client.py` is still copied by hand: it is the harness's, not the product's). The
  command needs a snap profile to act on, and a first `snap run --shell firefox` creates none, so the phase first makes
  one (a `profiles.ini` and a `certutil -N` database under the snap's profile root, or a headless first start of the
  snap, whichever the builder shows to work without the store UI; the choice is recorded in the commit). The guest also
  needs `modutil`/`certutil` (`libnss3-tools`): until F184 declares the dependency in the package, the harness installs it
  in the guest's setup and says so in a comment. The phase fails the run if the command fails or its report does not say
  the profile was registered. The register output is kept in the evidence directory and judged by `e2e/vm/snap.py`
  (an existing case's judge or a fact in `snap-record`; no new case, so `cases.list` and its accounting are untouched).
  The real guest run is not done here (nothing in this environment can run it; it is the last feature's), so the
  judge is proven on fixtures with negative controls and the harness shell by `shellcheck` and the script test.
- **Environment** (checked now): `modutil` and `certutil` are in the dev container (F172, F182); the fixture rig of
  F182 (`tests/fixture/mod.rs`: fixture home, `modutil`-made profiles, stub programs, snapshot, command runner) is
  reused by both new test files. No privilege beyond F182's is needed; the unwritable-directory case is made by mode 0555
  on a directory in the container (uid 1000, not root), and the journal case by a datagram socket in a temp directory.
- **Costs.** `register_snap`: about 15 integration cases over fixture homes with real `modutil` (30–60 ms per call,
  3–10 calls per case), estimated 8–12 s CPU in total, parallel with each other and with the other integration tests
  (like `register_native`). `register_acceptance`: 2–3 tests running the real binary on one whole-flow home, about 2–4 s
  each, parallel. No e2e case, no new VM case. `scripts/test-e2e-vm-snap.sh` gains a few fixture judgements, well under
  1 s each; it runs in parallel with the other script tests as now and under the `script * 120` s budget. Waits (a
  held profile, a datagram receive) are on a pipe or a socket with a timeout, never a fixed `sleep`. `just mutants-diff
  F183` covers the new code only: F182's diff took one command with 64 mutants; this one is estimated at 40–80 mutants,
  each paying the nested `cargo build` if the test files still use it; the builder measures it in step 6 and, if it
  cannot fit 30 minutes, says so in PROGRESS.md and asks for the split in BLOCKED.md rather than weakening the list.
- Six steps; no split needed.

## Evidence
- Copy placed at the fixed path, registered → `register_snap::a_snap_profile_gets_the_copy_and_one_entry`: a fixture home
  with a snap profile → `~/snap/firefox/common/libcustodio_pkcs11.so` exists with the bytes of the module and mode 0755,
  `modutil -list` of the snap profile shows exactly one Custodio module whose library is that path, the report line names
  "Firefox (snap)" and the profile as registered. Control: the same home with no snap directory, and one with
  `~/snap/firefox/` but no profile → no copy, no error, exit zero, the home byte-identical.
- Written atomically → `register_snap::the_copy_is_written_by_rename` : a stub reading the directory is not possible, so
  the test observes the two effects: while the copy is replaced by a run whose temporary-file creation fails (a
  pre-existing directory at the temporary name, or a read-only directory) the old copy is byte-identical and no temporary
  file remains, and a temporary file left by a killed run (planted) is removed by the next run; plus a successful
  replace gives the target a new inode with the new bytes (rename, not in-place write; the old inode is still readable
  with its old bytes through a file handle opened before the run).
- Stale copy replaced on every run, at the same path → `register_snap::a_stale_copy_is_replaced_in_place`: copy bytes
  differ from the module → after the run equal to it, same path, report "refreshed", entry unchanged; a second run
  leaves inode and mtime as they were (up to date). Control: the copy with equal bytes is not rewritten. Also a stale copy
  is replaced when the snap profile is held (registration skipped and named, refresh done).
- A refresh never creates a copy → `register_snap::a_refresh_never_creates_a_copy`: refresh-only mode on a home with a
  snap profile and no copy, and on a home with a registered native profile → no file created anywhere (file lists and
  hashes equal), exit zero, the journal line says "no copy". Control: registration on the same home creates it.
- A copy it cannot replace exits non-zero naming it → `register_snap::an_unreplaceable_copy_fails_naming_it`: a stale
  copy in a read-only (0555) directory, and separately a directory at the copy path → non-zero, stderr names the copy
  path and a reason, the old copy as it was, the native profiles of the same home still processed; in refresh-only mode
  the same, and the journal line has the error priority and the path. Control: a writable directory works.
- Removal deletes the copy → `register_snap::removal_deletes_the_copy_and_the_entry`: after `--remove` no copy, no
  Custodio entry in the snap profile, a second removal is byte-identical, a foreign module entry of the snap profile is
  line-for-line as it was; a held snap profile keeps entry and copy, is named, exit non-zero.
- Refresh-only does only the refresh → `register_snap::refresh_only_touches_nothing_but_the_copy`: stub `modutil` on
  `PATH` records a marker (absent after the run), and `modutil` absent from `PATH` still works; native profiles'
  `pkcs11.txt` and the snap profile byte-identical; the copy is replaced; root and `SUDO_UID` are refused as for the
  rest (the real binary under `unshare -Ur`, the home byte-identical).
- Outcome in the user's journal → `register_snap::refresh_only_logs_its_outcome_to_the_journal`: the journal socket
  injected as a datagram socket in a temp directory; the datagram carries the fixed identifier, priority and the copy
  path for each of: refreshed, up to date, no copy, failure (with the reason), no installed module. Control: an
  unreachable socket leaves the exit status as the refresh decided and prints the reason on stderr.
- Command line → unit tests beside `parse_register_args` for the new option (alone, with `--module`, with `--remove`
  rejected as a combination, repeated, unknown), and `tests/exit.rs`-style exit code 2 for a usage error with the real
  binary.
- Acceptance 10 as a whole → `register_acceptance::acceptance_10_on_one_home`: a home with a legacy and an XDG Firefox
  profile, a hand-registered entry under another name in one of them, a foreign module entry in each, and the Firefox snap
  with a profile; the real binary with `--module` at the built module → every profile has exactly one Custodio module in
  NSS's `modutil -list` (hand entry kept under its name), snap profile pointing to the copy; a second run leaves a hash
  of the whole home equal; `--remove` leaves no Custodio entry in any profile, no copy, every other entry line for line
  as before the first run; a locked native profile (a live-pid `lock`) → skipped, named in stdout/stderr, exit non-zero,
  the others done; root (`unshare -Ur`) and `SUDO_UID` refused, home byte-identical. Negative control inside the test:
  a home where one profile's entry is deleted by hand makes the "exactly one in each profile" check fail (the check
  function is exercised on that state and must report it).
- VM group uses the command → `scripts/test-e2e-vm-snap.sh`: fixtures of the register output and the copy (registered
  line present and the copy equal to the installed module: accepted; command failed, "skipped" report, a copy that
  differs from the module, a missing report: each rejected with the fact named) → the script exits zero; the harness
  shell scripts pass `shellcheck`. Not proven here, by the last feature's VM run: the real guest placing the copy with
  the command and the snap loading it.
- Whole feature → `just quick`, `cargo test -p custodio-cli --test register_snap --locked`, `cargo test -p custodio-cli
  --test register_acceptance --locked`, `scripts/test-e2e-vm-snap.sh`, `just mutants-diff F183` (every mutant of the new
  code caught or unviable) → green.
