# F185 — README, threat model and SECURITY.md

## Scope
Three documents and two script tests; no Rust change.

- **`README.md`** (rewritten for users; its "Development" section may move to `docs/` or stay, but is then covered by the
  same rules). It covers every item of SPEC Design 8's README list, each in its own words: what Custodio is; what it
  protects against and its limits; the three storage kinds and what each protects against (`tpm` cannot be copied even
  by root; `encrypted-tpm` and `encrypted-host` are decrypted in the service's memory to sign); that import falls back
  to the encrypted kinds without asking (`docs/decisions.md`, 2026 "import still falls back") and that `custodio list`
  shows each key's kind; the full-disk encryption warning (the existing section stays true: it already matches F180);
  registering browsers with `custodio register`, and removing the registration with `custodio register --remove`
  before uninstalling the package, never through Firefox's "Browse" dialog (SPEC Design 3: the snap is denied
  `file_mmap`); and the limits: the snap route is not a supported snapd interface, only the Firefox snap is supported
  (not Chromium, Thunderbird or Firefox Flatpak), Mozilla's own Firefox on Fedora and RHEL/Alma needs the manual route
  of `docs/install.md`, lost keys need the original `.p12`, TLS client authentication shows several dialogs per page.
  The "Not ready for use yet" paragraph is removed (this is the release). It links the threat model and `SECURITY.md`.
  Facts (kind names, command names and options) come from the code and `docs/api.md`, not from memory.
- **One threat-model document** (`docs/threat-model.md`; path is the builder's but it is fixed once linked), for the
  product as released, consolidated from M0–M6 (`docs/milestones/M*/SPEC.md` "Threat model", M6's `SPEC.md` section,
  `docs/findings/`, `docs/reports/firefox-snap.md`): who is protected from whom; in scope; out of scope; not guaranteed;
  the Firefox snap socket and its reliance on an undocumented snapd rule (what rule, what breaks if snapd changes it, how
  that shows: the registered copy sees no slot); the registration command (writes only the user's own profiles and snap
  directory, refuses root); and the full-disk encryption advice. It does not repeat the milestone specs by reference
  alone: a reader needs no milestone file. Later milestone SPECs stay where they are.
- **`SECURITY.md`** links the threat model, and its scope adds the snap sockets (a peer the label check should refuse, a
  call beyond list/sign, a socket replaced by the snap) and the registration command (writes outside the user's
  profiles/snap directory, edits a held profile, leaves a half-written copy).
- **Scripts**, added to `just test-scripts` (justfile) and so to `script-tests`: `scripts/test-docs-readme.sh` and
  `scripts/test-docs-threat-model.sh`. Shared helpers (fenced-block extraction, link check) may go in a `scripts/lib/`
  file; a shared helper is not a third test.
- **Not here.** Prose is judged by a person (SPEC acceptance 20), and no test greps wording, headings or citations
  (CLAUDE.md). Release notes and `docs/install.md` are other features; `docs/install.md`'s and the release notes' own
  command runs are theirs (SPEC acceptance 16 is split across them). The real-browser behaviour of `register` is F183's
  and F182's tests and the VM checkpoint; the full-disk warning's logic is F180's. The existing `test-docs-install.sh`
  keeps checking that the README links `docs/install.md`; the README keeps that link.

**What "run as written" means.** The README and the threat model show commands in fenced blocks. A block is *run*
when its info string says `console` (the convention of `docs/api.md`); every `$ ` command line in it is executed by the
test exactly as printed, in one shell per block, and the lines after it are compared with what the real command prints
where the document shows output. `custodio import` asks for its password on `/dev/tty`, so the test drives it through a
pseudo-terminal (the builder picks the mechanism). The commands run against the real `custodio` CLI built from the tree:
`list`/`import`/`delete` against `docs_api_server` on a private bus with the scripted polkit (as `test-docs-api.sh`,
F98), `register`/`register --remove` on a temporary `HOME` laid out with a Firefox profile, a snap profile and a stub
`modutil` first on `PATH` (as F182's/F183's tests do), then the effect is checked (the registered entry is there, then gone).
A command that cannot run in a test (a package-manager install, `sudo`, `just setup`) is not shown in a `console`
block; it goes in a `bash` block, and the test fails on any block with no recognised info string, so nothing is skipped
silently. A `bash` block's commands are never run, so the documents keep them to what no test can exercise, and the test
prints the count of such blocks. Commands the document says a person types in a browser (Firefox's "Browse") are
prose, not blocks.

**Links.** Every relative link in each document (`[text](path)`, with or without `#anchor`) resolves to an existing file
in the repository, and a `#anchor` to a heading of that file (GitHub's slug rule). The README's links to the threat model and
`SECURITY.md`, and `SECURITY.md`'s link to the threat model, must be present and resolve (a link check of a link that
was never written proves nothing, so each test requires its required links by target path). External `https://` links
are not fetched (no network in the test).

**Measured/expected costs.** Each script builds `custodio-cli` and `docs_api_server` (`cargo build --quiet --locked`
under `timeout`; warm about 1–2 s, cold CLI debug build measured 9 s with dependencies cached in F184; the example
server is shared with `test-docs-api.sh`, and cargo's lock serialises the builds), starts one private bus (about 1 s)
and runs about 6 short commands: estimated 5–15 s warm each, plus the negative controls (each a fixture copy of the document, about 1 s,
run in parallel with each other where they do not share the bus, and with nothing that needs a bus in
`test-docs-threat-model.sh`, which runs no service: its commands are the few `console` examples such as `journalctl`-free
`custodio` ones, or none; it then must still pass the link check and the block-kind rule). Both are plain script tests,
in parallel with the other script tests in `test-scripts`; waits are on conditions (the bus socket appearing), never
`sleep`. Both fit the `script * 120` budget; if the cold build does not, the builder asks in BLOCKED.md. No e2e case,
no VM run, no package build: `just e2e`, the package gates and the VM suite are the checkpoints'.

**Environment.** Needs `busctl`/`dbus-daemon` (already used by `test-docs-api.sh`), `unshare` and `python3` (stub `modutil`
and the pseudo-terminal driver may be python or `script(1)`; the builder runs the smallest command that shows which works
here and records it in PROGRESS.md). `modutil` itself is not needed: a stub records its arguments, as F182's tests do; the
real NSS check is F182's real-service test. No network, no root, no container engine.

*The module path.* `custodio register` with no `--module` uses the fixed `INSTALLED_MODULE =
/usr/lib/custodio/libcustodio_pkcs11.so` (`register_native.rs:23`), absent here (no root). The README shows the command
without `--module`, as a user types it, so the test gives it a module at that path inside a mount namespace. Commands run
in this container (uid 1000):
`unshare -rm sh -c 'mount -t overlay overlay -o lowerdir=<stage>:/usr/lib,upperdir=<up>,workdir=<wk> /usr/lib && ls /usr/lib/custodio'`
printed `libcustodio_pkcs11.so` (rc 0; `<stage>/custodio/libcustodio_pkcs11.so` is an empty file). A plain bind mount over
`/usr/lib/custodio` fails (the mount point does not exist), hence the overlay. `register` refuses euid 0, which `unshare -r`
gives, so the test drops back to the user inside the namespace: `... && unshare --user --map-user=1000 --map-group=1000 sh -c 'id -u; ls /usr/lib/custodio'`
printed `1000` and the file, so the unchanged command runs as a non-root user and finds the module. The mounts live only in
that namespace; nothing on the host changes. The test uses the real binary and the unchanged README command, with no test-only
override. If `unshare` cannot do this on a host (checked at the start of the script), the script fails with that reason
rather than skipping.

*The NSS config.* `NSS_CONFIG = /etc/crypto-policies/back-ends/nss.config` (`register_discover.rs:65`) is absent here, and an
overlay over `/etc` fails (`mount: /etc: wrong fs type`: `/etc` has submounts), so it cannot be provided. The test therefore
uses the host's state, which it records: absent (this container and Debian) means native profiles are registered; if a host
has the file (Fedora-like), native profiles are skipped. The README's `register` output block is compared line by line only
for the snap profile line and the summary the command prints independent of that file; lines for native profiles are compared
only when the file is absent. The fixtures make the effect check (snap copy and `-add`) on the snap profile, which does not
depend on that file, so it holds on both.

*`list`/`import`.* `DbusImporter::system()` connects to the system bus, so the test sets `DBUS_SYSTEM_BUS_ADDRESS` to the
private bus outside the block (the block is typed exactly as printed, with no address in it). `import` reads the
password on `/dev/tty`: the README's block names a file, and the test places a fixture `.p12` at that path (a throw-away
file made with `openssl`, the one `test-docs-api.sh` uses if it has one) whose password is the one the pseudo-terminal
driver types. The full-disk warning that `list`/`import` print (F180) comes from the host (`custodio` checks the host's
disks), so it depends on the environment: the test compares **stdout only**, and with the warning on stderr not compared.
If the README's output block shows the warning, it is in a separate block kind not compared (the builder confirms
where F180 prints it and says so in PROGRESS.md; if it is on stdout, the test pins the host status through the same
switch F180's tests use).

*Threat-model script.* It likely has no `console` block. With none, it builds no CLI, starts no bus and runs no namespace;
it checks only links and block kinds (cost about 1 s). If it does have `console` blocks, it uses the same helper.

## Evidence
- README covers the storage kinds, fallback, `custodio list` kind, FDE warning, register/remove, never "Browse", limits →
  **a person**, SPEC acceptance 20 (no test greps the wording). What a test does prove: the commands and kind names the README
  shows exist → the `console` blocks run (below), and the kind names in `custodio list`'s printed output are the ones the
  README shows (a `console` block with the output) → `test-docs-readme.sh` passes.
- Every command the README shows runs as written → `scripts/test-docs-readme.sh` runs each `console` block on the real CLI
  → exit 0 and the printed output matches the document. Negative controls: a copy of the README with a command altered
  (`custodio lst`) fails; with an output line altered fails.
- `custodio register` and `register --remove` as the README shows them have their effect → same script: after the
  `register` block the stub `modutil` log shows an `-add` for the installed module path in the fixture profile and the snap copy
  exists; after the `--remove` block the entry is gone and the copy is removed. Control: a README whose remove command is
  `register --refresh-only` fails this check.
- Every relative link of the README resolves; the README links the threat model and `SECURITY.md` → `test-docs-readme.sh`
  → pass. Control (required links only; the checker is shared and its controls are in the shared-helper item below): a README with the threat-model
  link removed fails.

  command it shows runs as written → `scripts/test-docs-threat-model.sh` → pass. Controls: a `SECURITY.md` copy without the threat-model link fails; if it has `console` blocks, one whose command exits non-zero fails.
- Threat-model content (in scope, out of scope, not guaranteed, the snap socket and its undocumented snapd rule, FDE advice) and
