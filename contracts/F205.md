# F205 — Completions for bash, zsh and fish, with key ids, shipped by every package format

## Scope
Builds: the hidden command `custodio __key-ids` that `docs/findings/F191.md` decided (it does not exist yet; F191 only
decided it); the three completion files `packaging/completions/custodio.bash`, `_custodio` and `custodio.fish`; their
entries in `packaging/nfpm.yaml`; the two zsh presence exceptions in `packaging/parity-exceptions.txt`; the package
check's expectation of the three files; the docs lines on `compinit`. The decision entry for the zsh directory is already
in `docs/decisions/packaging.md` (F191); F205 writes none. Left out: the package gates on real packages (`just package`,
lifecycle, install tests) and `just e2e`: they run at the checkpoint features; the three files in the real packages are
proven there, here only on fixture packages. Package lint (lintian, rpmlint, namcap) is a checkpoint too.
The verify has no `mutants-diff`, so none is planned. Six steps: about five, each one session.

Environment (run in the dev container on 2026-11-16): `zsh --version` → 5.9; `fish --version` → 4.0.2;
`/usr/share/bash-completion/bash_completion` exists; `shellcheck`, `nfpm`, `dbus-daemon` are on the path. So the real shells run
here (F191 measured the rest of the container's behaviour). The completion test needs the real `custodio` binary; custodio-it has no
`CARGO_BIN_EXE` for another package, so the builder chooses how the test gets the binary (for example building `custodio-cli`
once), without a second `cargo` lock fight inside the run, and says so in PROGRESS.md.

Behaviour fixed by F191 and not reopened: key ids come from `custodio __key-ids` (calls `ListKeys` only; stdout one id per line,
sorted, only ids in the grammar of `docs/api.md`; on any failure stdout and stderr empty, exit 1; 2 s call timeout inside `custodio`,
none in the files). Files call `custodio __key-ids 2>/dev/null` and treat each line as data (bash: `read -r` + `[[ == "$cur"* ]]`,
never `compgen -W`; zsh: `compadd -- ${(f)...}`; fish: `-a '(…)'`). `__key-ids` is hidden: not in `COMMANDS`, the help, the man page
or any completion. Acceptance 12 bounds for the whole completion from the real shell: service absent ≤ 1 s; running with 200 keys ≤ 2 s;
service hung ≤ 4 s offering nothing. `import --id` names a new key, so it does not complete ids.

Costs (estimates from `list.rs`/`doctor_acceptance`, which use the same rig): `completions.rs` ≈ 15 s wall: one rig, 200 keys seeded
once (if importing 200 keys through the service takes more than 10 s the builder seeds the store directly), then the three shells run
in parallel as separate `#[test]`s (cargo runs them in parallel with the other tests of that binary); the hung case waits for the
timeout (≈ 2 s) on a condition, no `sleep`. `scripts/test-check-packages-completions.sh` ≈ 20 s: it builds fixture packages as
`test-check-packages-pam.sh` does (one case per command, all run in parallel); it runs in `test-scripts` in parallel with the other
script tests, under the 120 s default of `budgets.tsv`. No e2e case: nothing here depends on the distribution beyond what F191
measured and the checkpoint proves.

## Evidence
- Every command and option complete, `fingerprint` and `doctor` included → `completions.rs`, one test per shell: from the real shell, the commands offered at the first word equal the names in `custodio_cli::help::COMMANDS` and, per command, the options offered equal its `options` (and `--help`/`-h`); `__key-ids` is never offered → equal sets in all three shells. A command or option missing from a file, or a new one added to `COMMANDS` and not to a file, fails it. This is also the "a test fails when a command or option of the help is missing from a completion file" requirement; negative control: the same comparison on a copy of each file with one option line removed fails (one per shell, in the same test file).
- Key ids for `list`, `delete` and any other command taking one → `completions.rs`: every command whose `args` has `<key id>` in `COMMANDS` (today `list`, `delete`) offers, in each real shell, exactly the ids of the keys in the running service that start with the typed prefix; `import --id` offers none → equal sets.
- Ids come from the service through `custodio`, as data → `completions.rs`: a stand-in `custodio` first on `PATH` that prints lines such as `$(touch MARK)`, backquotes, `;`, spaces and `*` is run through each shell's completion: the marker file does not exist and no hostile text is executed or globbed. Together with the unit test that `__key-ids` drops lines outside the grammar.
- No polkit request, nothing written → `completions.rs`/rig test of `__key-ids` and one completion against the rig: the fake polkit's call count is 0, the bus monitor sees `ListKeys` and no other method of the service, the state directory is byte-identical before and after → all hold; negative control: the same assertion does see the count rise after an `import` on that rig (the counting is live).
- Nothing printed, prompt return, service absent → `completions.rs`, each shell: with no bus name owner the completion offers nothing, writes nothing on stdout/stderr of the shell and returns within 1 s (asserted on a condition, not a sleep); `__key-ids` itself: stdout empty, stderr empty, exit 1 (rig test, absent and bus socket missing).
- Hung service → rig test (a peer that owns the name and never replies) of `custodio __key-ids`: exit 1, no output, within the 2 s timeout plus a margin; `completions.rs`, each shell: offers nothing within 4 s. 200 keys: all 200 ids offered within 2 s in each shell.
- Files pass the shells' own checks → `shellcheck packaging/completions/custodio.bash`, `zsh -n packaging/completions/_custodio`, `fish --no-execute packaging/completions/custodio.fish` (in `verify`) → exit 0.
- nfpm installs the files where each shell loads them → `scripts/test-check-packages-completions.sh`: the gate accepts a clean fixture set of the real `packaging/nfpm.yaml` and the three listings hold: bash and fish at `/usr/share/bash-completion/completions/custodio` and `/usr/share/fish/vendor_completions.d/custodio.fish` in all three formats, zsh at `/usr/share/zsh/vendor-completions/_custodio` in the .deb and `/usr/share/zsh/site-functions/_custodio` in the .rpm and Arch package (mode 0644, root:root).
- The package check fails when a format lacks a file at its location → the same script, negative controls built from the real config: each of the three files dropped from each format (nine cases) and the .deb's zsh file placed in `site-functions` each fails with a line naming the format and the path; the clean fixture passes; `scripts/test-check-packages.sh` still passes.
- Difference between formats recorded as the parity rules require → `scripts/test-check-parity.sh` and the gate on the fixture set with the committed `packaging/parity-exceptions.txt`: passes with the two zsh exceptions; the existing rule "a difference not in the exceptions fails" is shown for the zsh path by removing its exception from a copy of the file in the completions script (one case) → fails.
- Acceptance 12, package part and the shell part → the two lines above and the three completion tests; the files in the real packages are proven at the checkpoint.
- Docs name `compinit` and the locations → the docs are not grepped; the step is done by reading the install documentation against `docs/findings/F191.md` (conclusion 4); `just quick` stays green with the docs tests that already run.
