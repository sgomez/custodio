# F168 — Checkpoint and last feature: the VM target, its cases, CI and the documentation

## Scope
Almost nothing new is built. This feature runs every suite of the milestone on the work of F150–F167 and fixes whatever fails, at its
cause, under the M4 rules: no `#[ignore]`, no lowered threshold, no `#[allow]` without a justification, no recipe turned into a no-op,
no guard loosened, no case changed except where the case is wrong, no skip added without a stated and evidenced reason, no
`budgets.tsv` edit. The `verify` is
`just check && just api-contract && just fuzz-smoke && just e2e && just package-gates && just coverage-gate && just e2e-vm full && just e2e-vm lacking`;
the loop runs it whole, a builder session never does. The only new things are (a) the **gap table** below, which this contract owes
the SPEC (acceptance 12), and (b) the small checker that reads it (step 2).

**What the checkpoint proves, and where**
- `just check`: lint, every unit and integration test, the system gates and all script tests, with each host self-test of the VM
  harness (`test-vm-image.sh`, `test-vm-launch.sh`, `test-vm-modes.sh`, `test-vm-credread.sh`, `test-vm-host-check.sh`,
  `test-e2e-vm-cases.sh`, `test-e2e-vm-host.sh`, `test-e2e-vm-kinds.sh`, `test-e2e-vm-silent.sh`, `test-ci-e2e-vm.sh`, and the VM
  sections of `test-e2e-sign/noplain/pcr/tpmclear/upgradekinds.sh`). They carry acceptance 1's refusal of a bad image, 5's
  told-apart credentials, 13 (`libtss2-rc0t64`), 15 (the workflow triggers) and 16 (systemd 257 floor, `ubuntu2404` gone, install
  docs). Whatever is red is fixed here.
- `just api-contract`; `just fuzz-smoke` (its default list must name every fuzz target that exists: today the ten of
  `crates/*/fuzz/fuzz_targets`; a target the list lacks is added to it).
- `just e2e` with `E2E_TPM` unset: now five targets (alma10, arch, debian13, fedora44, ubuntu2604; `ubuntu2404` is gone, F156) with
  `swtpm`, and debian13 also with `none`: six records. Every case id owed is accounted exactly once per record. The
  `fallback-tpmbound-*` and `upgrade-kinds-tpmbound` cases are reported **skipped** in every one (acceptance 14;
  `check-cases.sh` refuses them reported run outside a VM). The record directory `target/e2e/` still holds `ubuntu2404.*` files from
  M4; they are removed before the counting step.
- `just package-gates` (acceptance 13, 16), `just coverage-gate` (coverage and the CRAP gate hold over the code F155 and F167 changed).
- `just e2e-vm full` and `just e2e-vm lacking` on the verified Ubuntu 26.04 minimal image: acceptance 1 to 12 (table in Evidence).
  The VM has no `E2E_TPM` and no container; its record is `target/e2e/vm.<mode>.record`.
- Not proven here (a person's, outside the loop): acceptance 17 (done and recorded by F166, `docs/findings/F166.md`) and the observation
  of acceptance 15 on the milestone's real release pull request.

**Gap table.** SPEC acceptance 12 requires that each gap of the M4 deviation (`docs/milestones/M4/SPEC_DEVIATIONS.md`, F134) maps in this
contract to VM cases that ran in the record. The cases below exist in `e2e/vm/cases.list`. Each must be reported `run` (never skipped)
in `target/e2e/vm.lacking.log`, the mode in which RSA 2048 (and P-256 if the F152 route allows it) is `encrypted-tpm`, and the stored
credential of every `encrypted-tpm` key they make was read by the harness reader (`reader: key ...` lines, F157/F161). `full` is the
control: the same cases run there with kind `tpm`. The table is machine-read by step 2; its format is `gap | cases`, one row per line.

```gap-table
F134 signing under encrypted-tpm, end to end | sign-kind-matches-mode sign-rsa-pkcs sign-rsa-composed sign-ec-ecdsa sign-ec-composed
F134 RSA-PSS with a real TPM-sealed credential, every hash and salt length | sign-rsa-pss-sha256 sign-rsa-pss-sha384 sign-rsa-pss-sha512
F135 no plaintext key in the state directory for encrypted-tpm | noplain-rsa noplain-ec noplain-no-key-file
F137 encrypted-tpm keys sign after a PCR change, a service restart and a guest power cycle | pcr-extended-signs pcr-restarted-signs pcr-signs-every-key
F138 the tpmbound fallback cases run, import and list say weaker and why | fallback-tpmbound-import fallback-tpmbound-cli-list tpm-kind-import-rsa tpm-kind-api-list tpm-kind-cli-list tpm-kind-journal
F140 after a TPM clear, signing fails with an entry, the key stays listed and deletable | tpm-clear-sign-fails tpm-clear-keys-listed tpm-clear-delete
F141 an upgrade keeps encrypted-tpm keys, owners, certificates and kinds | upgrade-kinds-before upgrade-kinds-kept upgrade-kinds-signs upgrade-kinds-tpmbound
```

Container-to-VM forms (already recorded, not redone here): the mapping tables of `contracts/F162.md` (module path, state directory) and
`contracts/F163.md` ("restart `swtpm`" is a guest power cycle with the state kept; "clear the TPM" is `tpm2_clear` from the guest, route
A; upgrade by `apt-get install --no-install-recommends` of N+1).

**Environment, run before step 3** (results go in `PROGRESS.md`). Checked while writing this contract:
`just vm-host-check` exit 0 (OK kvm-device, qemu-system-x86_64, kvm-accel, ovmf-code, ovmf-vars, swtpm, swtpm-profile, seed-tool, gpgv,
keyring); `podman info` exit 0; `swtpm --version` 0.7.1 in the dev container (the container targets), 0.10.2 under `/opt/swtpm` for the
VM. The VM needs network in the guest (apt) and the image cache of `just vm-image`. If KVM, podman or the network is gone, or an image cannot
be pulled, that is a `BLOCKED.md` question, not a reason to skip a target, a mode or a case; software emulation is never used. If podman has
lost its pause process, `timeout 120 podman system migrate` is the known remedy (F132).

**New test and its cost.** One: `scripts/test-vm-gap-map.sh` (host self-test, joins `just test-scripts`, runs in parallel with the other script
tests, estimated 1–2 s from `test-e2e-vm-cases.sh`, well under the `script *` budget of 120 s), over `e2e/vm/gap-map.sh`. Nothing else is
added: no new case id, no e2e case, no container target.

**Time and budgets.** Measured or estimated per piece (earlier logs and PROGRESS.md):
- `just check`: ~10–15 min cold (M4 F146); skipped on an unchanged tree through `target/check-ok` (`CHECK_FORCE=1` forces it).
- `just e2e`: six records at once, wall = the slowest: `target/e2e/timings.tsv` has debian13 swtpm 683 s, debian13 none 480 s, alma10 437 s,
  fedora44 403 s, arch 387 s, ubuntu2604 369 s, against `budgets.tsv` 800, (none: no own row), 540, 570, 480, 530. Debian13 has ~15% room;
  F150–F167 added no container case, so no growth is expected, and the builder compares each measured time with its row. A target over its
  row is a `BLOCKED.md` request (a person sets budgets), after the rest of the steps are done; no case is removed or skipped to fit.
- `just package-gates`, `just api-contract`, `just fuzz-smoke`: minutes each; the builder records them.
- `just coverage-gate`: not measured in any log I could find (estimate 10–25 min: the integration tests run under `cargo llvm-cov`). It is
  run as its two recipes, `just coverage` then `just crap`, one per command, `timeout 1700`; if `coverage` alone passes 25 min the builder
  says so in `PROGRESS.md` and asks for the time limit it needs in `BLOCKED.md`.
- `just e2e-vm <mode>` (new rows `vm full`, `vm lacking` for `budgets.tsv`; none exist, and the builder never edits `budgets.tsv`).
  Estimate from the partial real runs recorded in F161–F163: image check 19 s (cached), boot 13 s, tools/install ~10 s, setup 11 s, kinds
  and fallback and silent ~60 s, sign 30 s, noplain 22 s, pcr 28 s plus cycle 12 s, tpm-clear 54 s, upgrade 33 s, teardown: about **4–6 min
  per mode**, ~10 min for the two, run one after the other in the `verify` (no concurrency is claimed between them). The builder measures
  both in step 5, and if no row exists asks for roughly 1.3× the worse mode in `BLOCKED.md` after finishing the rest.
- Limits: a command runs at most 30 min and a session 45 min. Each step below is one command or a few short ones; the two VM modes, the
  container `just e2e` and the coverage halves each get a command of their own with `timeout 1700`. No step runs the whole `verify`. A
  failure fixed in this feature may take more than one session; steps stay ticked only when their evidence passed on the final tree.

## Steps
- [x] Baseline, host side: run `just check` (a red script test is run alone first to see its cause), `just api-contract`, `just fuzz-smoke`.
      Fix each failure at its cause, one commit per fix. Check that the `fuzz-smoke` default list equals `cargo fuzz list` of both fuzz crates.
- [x] Gap-table checker, test first: write `scripts/test-vm-gap-map.sh` (fixtures: a good table; a gap row missing; a case not in the VM
      list; a mapped case on `e2e/vm/skip.list`; a mapped case reported `skip` or missing or twice in a fixture log; `lacking` log without a `reader: key`
      line; negative controls shown to fail), then `e2e/vm/gap-map.sh` (reads the fenced `gap-table` block of `contracts/F168.md`, checks it against `e2e/vm/cases.list`,
      `skip.list` and, given logs, against the `E2E-CASE run <id>` lines). Add the test to `just test-scripts`; run it alone.
- [ ] Container end-to-end: environment checks above; `timeout 1700 just e2e` once (six records at once); fix every failing case, TPM set-up
      or accounting error at its cause; note the six pass results, case counts and wall times in `PROGRESS.md` against `budgets.tsv`.
- [x] `timeout 1700 just package-gates`, then `just coverage` and `just crap` (each its own command); fix every finding. A package-lint list
      entry only with a reason and only for a finding that is not a defect.
- [x] VM, one mode per command: `timeout 1700 just e2e-vm full`, then `timeout 1700 just e2e-vm lacking` (the host needs the `just vm-image` cache).
      Fix each failure at its cause, never by loosening a guard. Note each wall time and its steps in `PROGRESS.md`.
- [x] Gap evidence: run `e2e/vm/gap-map.sh` on `target/e2e/vm.lacking.log` and `vm.full.log`, and read both records for Design 1's items. Fix a missing
      mapping at its cause (a case that did not run is investigated, not removed from the table). Write the result in `PROGRESS.md`.
- [ ] Final: after the last fix, rerun what ran before it (one per command), from a `target/e2e/` cleared of old records, re-count the Evidence
      records, run `just quick` once. Write `BLOCKED.md` for budget rows only after every other step is ticked, with the measured times.

## Evidence
Acceptance numbers are those of `SPEC.md`. "VM log" is `target/e2e/vm.<mode>.log`, "record" `target/e2e/vm.<mode>.record`.
- Every suite green on the final tree → the `verify` run by the loop → exit 0; the builder's per-step runs of steps 1 and 3–5 exit 0.
- Host self-tests of the VM harness, with their negative controls (acceptance 1 refusal of a bad image, 5 told-apart credentials, 12
  accounting, 13, 15, 16) → `just check`, which runs `test-scripts` incl. the files listed in Scope → exit 0. Each already has its
  controls, written by F157–F167; a control that stopped failing would turn the script red.
- Gap table is well formed and consistent → `scripts/test-vm-gap-map.sh` → exit 0; its controls (missing gap row, unknown case, mapped case on the skip
  list, a case reported `skip` or twice or absent in a fixture log, no `reader: key` line) → each makes `e2e/vm/gap-map.sh` fail.
- Acceptance 12, each gap maps to VM cases that ran → `e2e/vm/gap-map.sh target/e2e/vm.lacking.log` (and `vm.full.log` as control with the same cases) → exit 0;
  every case of every row is `E2E-CASE run` exactly once, and the lacking log has `reader: key` lines for the `encrypted-tpm` keys while the full log has none.
- Acceptance 12, every case reported once → each VM log ends with `check-cases: 38 cases accounted for` (38 = the ids of `e2e/vm/cases.list`) and
  `e2e-vm[<mode>]: passed`. `vm-silent-*` are reported skipped in `full` only (listed with a reason in `e2e/vm/skip.list`) and run in `lacking`; every other id runs
  in both modes.
- Acceptance 1 → in both VM logs `vm-tpmrm0-exists` and `vm-has-tpm2-full` are `run`; each record has `has_tpm2=yes (exit 0)` and an `image_serial` that is not
  `unknown`; the image check ran against Ubuntu's signature (`step_image` present).
- Design 1 "Record" → each record holds `target=vm`, `tpm=<mode>`, `image_serial`, `kernel`, `systemd`, `package_version`, `swtpm_version`, `has_tpm2`, and a
  `step_*` line with seconds for image, boot, copy, install, tools, setup, every case group (cycle, pcr, tpmclear, upgrade, …) and teardown; none is `unknown`:
