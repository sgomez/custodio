# F191 — Research: shell completion locations per package format and fast key ids without polkit

## Scope
Research only. Output: `docs/findings/F191.md` (headed `## F191`, within the 5000-token limit, rules at
the top of `docs/findings.md`: conclusion first, **verified**/**inferred**, evidence as the command and
the lines that prove it) and one index line in `docs/findings.md`
(`- [F191](findings/F191.md) — topic: the conclusion`). If the finding shows that formats must differ,
the same commit adds a dated entry to `docs/decisions/packaging.md` (its rules) naming the exception
that F205 will put in `packaging/parity-exceptions.txt`. No product code, no test, nothing in `e2e/`,
no change to `packaging/`, other contracts or `features.json`. F205 implements the `Decision: ` line
(completion files, nfpm entries, parity exception, the `custodio` call for key ids, the test and its
bound); the completion test and the package check are proven there. The dev container lacks bash-completion,
zsh and fish (F204's step), so a shell is run inside the target containers, not here.

What the finding must settle (SPEC Design 3 "Completions", open question 4, acceptance 12):
- **Locations.** For bash, zsh and fish on each of `debian13`, `ubuntu2604`, `fedora44`, `alma10`, `arch`:
  the directory each shell loads from with no configuration, given the target's own packages
  (bash-completion's `pkg-config --variable=completionsdir` or its `BASH_COMPLETION_USER_DIR`/search
  path code; zsh's default `fpath` from `zsh -c 'print -l $fpath'`, which candidates among
  `/usr/share/zsh/vendor-completions` and `/usr/share/zsh/site-functions` it contains on each
  target; fish's `$__fish_vendor_completionsdirs`). Candidates to confirm or reject:
  `/usr/share/bash-completion/completions`, `/usr/share/zsh/vendor-completions`,
  `/usr/share/zsh/site-functions`, `/usr/share/fish/vendor_completions.d`. File names each loader
  needs (`custodio`, `_custodio` with `#compdef`, `custodio.fish`). Also what each shell needs
  installed for completion to work at all (bash-completion, `compinit` run by the default zsh
  configuration or not) and so what "no configuration" can honestly mean per target; where a target
  needs the person's `compinit`, the finding says so and F205's docs must too.
- **Packages.** Whether nfpm (the version pinned in `mise.toml`) installs the same `dst` for the .deb,
  .rpm and Arch package from one `contents` list in `packaging/nfpm.yaml`, or needs per-format entries
  (`overrides`, per-format `contents`); which directories the packages must own or may leave to
  `bash-completion`/`zsh`/`fish` packages (rpm lists no directories, deb/Arch list parents: F37). Whether a
  format difference results, and then the exact entry for `packaging/parity-exceptions.txt` and the
  parity rule it falls under (read `scripts/check-parity.sh`). If every format can ship the same paths,
  the finding says so and that no exception is needed. Which of the five targets use which
  package format is taken from `e2e/targets/*/Containerfile` and `docs/decisions/packaging.md`.
- **Key ids.** How completion obtains the person's key ids through `custodio`: the form of the command
  (a hidden or documented subcommand or option of `custodio list`, output one id per line, nothing else),
  that it calls only `ListKeys` (read `docs/api.md`: no polkit, read-only, read from the record), that it
  opens no agent and writes nothing (read the CLI's `list` path and `custodio-client`, including whether
  it writes to the journal, a file or the terminal), and what it prints and returns when the service is
  absent or the bus is missing, when the bus name is not activatable, and when the call hangs. The
  finding chooses a timeout (where it lives: in `custodio`, in the completion file, or both) and why.
  Ids and anything else read from the service reach the shell as data, never as shell code: the
  finding says how each of the three completions keeps an id that contains shell or terminal
  metacharacters inert (ids are produced by the service; state what an id may contain and cite the code).
- **Cost and bound.** Measured: the wall time of `custodio list`, or the smallest equivalent, against a
  running service (the integration tests' peer or service on a private bus, whichever the dev container
  can start; the first step finds out), against an absent service (no socket) and against a service
  that is activatable but slow; with 1 key and with the largest realistic number (say 200, if the test
  harness can create them; otherwise the call's cost per key is measured and the larger case is
  **inferred**). From the numbers the finding sets the time bound acceptance 12 may assert on the absent
  service case (a figure with margin for a loaded CI machine, and the margin's reason) and the one for
  the running case.
- The finding ends with one line `Decision: ` that F205 can implement without more research: the three
  destination paths per format, the parity exception or its absence, the key id command and its output
  contract, the timeout, and the bound.

## Steps
- [ ] Environment: run the smallest commands that show `podman` can start `debian13`, `ubuntu2604`,
      `fedora44`, `alma10` and `arch` images (images `debian:13`, `ubuntu:26.04`, `fedora:44`,
      `almalinux:10`, `archlinux` are present or pull) and install bash-completion, zsh and fish
      from the distribution there; note any target that cannot, and mark its rows **inferred** from
      the distribution's package file list instead.
- [ ] Locations: in the five containers (one `podman run` per target, all five started at once) run the
      commands above for the three shells and record the directories each loads and the packages that own them.
- [ ] nfpm and parity: read `packaging/nfpm.yaml`, `scripts/check-parity.sh`,
      `packaging/parity-exceptions.txt` and the pinned nfpm's per-format `contents` rules; decide whether a
      difference between formats is forced and, if so, write the decisions entry.
- [ ] Key ids: read the CLI `list` path, `custodio-client` and `docs/api.md`; measure the running,
      absent and slow-service cases of the cost and choose the output contract, the timeout and the bound.
- [ ] Write `docs/findings/F191.md` with the `Decision: ` line and its index line; run `just quick`.
