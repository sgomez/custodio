# F38 — Package linters with justified exception lists

## Scope
Built here:
- `just package-lint`: `scripts/package-lint.sh [DIR [LISTDIR]]` (default `target/packages`, `packaging/lint`) runs
  lintian on the one `.deb`, rpmlint on the one `.rpm` and namcap on the one `.pkg.tar.zst`. It then prints every
  finding as `LINTER | TAG | SUBJECT` and fails if any finding is not covered by that linter's exception list, or if
  any exception is unused. All severities count (lintian error, warning, info, pedantic and experimental; rpmlint
  errors and warnings; every namcap line), so "any finding" is literal. The recipe is added to `package-gates`
  (after `package`), so `check-slow` includes it; it is not part of `just check` (it needs built packages).
- Fail-closed inputs, as in F37: `DIR` missing or without exactly one package of the linter's format, a linter that
  cannot be run at all, or a linter that exits with a status that is neither "clean" nor "findings" (crash, bad
  usage) is a failure with a message naming the problem. Output that parses to zero findings while the linter
  reported a finding exit status is also a failure (the parser must not hide findings).
- Exception lists, committed in `packaging/lint/lintian.txt`, `rpmlint.txt`, `namcap.txt`. Line format
  `TAG | SUBJECT-GLOB | REASON`; `#` comments and blank lines are ignored. The gate rejects an entry with an empty
  reason, an unparsable line, and a stale entry (matches no finding in this run). An entry applies only to the
  linter whose file holds it. Subject globs are anchored (`fnmatch` on the whole subject). Findings are fixed in
  the packaging where possible; an entry is only for something that cannot be fixed (for example a rule that
  conflicts with the one-file-list design), and the reason says why. The lists are expected to be short.
- Where each linter runs: `scripts/package-lint.sh` uses the host linter if it is installed **and** its version
  equals the pin in `packaging/lint/pins.txt`; otherwise it runs it in a container of the target distribution
  (Debian 13 for lintian, Fedora 44 for rpmlint, Arch for namcap) with `podman` or `docker`. Stock distribution
  images do not hold the linters, so the container is a per-linter image built from `packaging/lint/<linter>.Containerfile`
  (with network, once, tagged by the hash of its Containerfile) on a base pinned by digest in `pins.txt`, with the
  linter installed at the exact version pinned in `pins.txt`. Each exact version must stay installable, so the
  Containerfiles point the package manager at a dated, immutable source recorded in `pins.txt`: namcap (Arch) uses
  a dated Arch Linux Archive snapshot (`archive.archlinux.org/repos/YYYY/MM/DD/`) as the only pacman mirror, and
  the exact namcap version is installed from it; lintian (Debian 13) uses a `snapshot.debian.org` timestamp as the
  apt source; rpmlint (Fedora 44) uses the pinned koji build (`dnf --repofrompath` or a direct koji RPM checked by
  sha256), because the updates repo keeps only the newest build. Step 1 confirms each of these works; if one
  cannot be pinned, why is recorded in `docs/findings.md` and the pin falls back to the best available identity
  (version plus a hash of the package file). The image build checks the installed version equals the pin and
  fails otherwise. When the pinned version cannot be installed (snapshot gone, build removed), the gate fails with a
  message that names the pin and the linter; it never falls back to a different version. The run uses
  `--network none`, the package directory mounted read-only and a non-root `--user`. With neither a usable host
  linter nor a container runtime it fails (never skips). The version-mismatch rule is also why a CI runner with a
  different lintian does not silently apply different rules.
- Dev image: `harness/Containerfile` installs lintian and rpmlint (apt, exact versions pinned in `pins.txt`, kept in
  step) and namcap. namcap is not packaged for Debian, so the builder researches (subagent) the least bad way to
  have it in the image: a pinned upstream release built from source with its `pyalpm`/libalpm dependency, checked by
  hash. If that cannot be made to work in Debian 13, namcap is run in the Arch container always and the reason is
  recorded in `docs/findings.md`; the dev container then needs a container runtime for namcap, and if that is not
  possible in the dev container, `BLOCKED.md` asks the person.
- Open question from F36 / SPEC ("Arch and `/usr/libexec`"): the run on the real packages must show that
  `/usr/lib/custodio/custodiod` draws no namcap and no rpmlint finding about its path or about the package layout.
  The result (the exact findings before any fix, and after) goes to `docs/findings.md`. If a finding on that path
  cannot be fixed or justified honestly, the builder writes `BLOCKED.md` with the options instead of listing it.
- CI: ubuntu-24.04's apt cannot install Debian 13's lintian or Fedora's rpmlint, so in CI all three linters run in
  the containers through the runner's docker (`PACKAGE_LINT_FORCE_CONTAINER=1` is set in the step). The `package`
  job gets one more named step `just package-lint` after the parity and glibc steps; its log shows the "ran" lines.
- Flags and hidden findings: lintian runs with `--no-user-config`-equivalent isolation (`--no-cfg`, `--profile
  debian/main` pinned, `--display-info --display-experimental --pedantic --show-overrides`); its "ran" line
  includes the version of the profile actually used (the `lintian-profiles`/vendor data version), and
  `docs/findings.md` records that no tag is disabled by that profile (checked from the profile files and from a
  run with a tag count). rpmlint 2.x loads its packaged defaults and `/etc/xdg/rpmlint/*.toml` (Fedora ships
  filters in `fedora.toml`), and `-c FILE` adds to those rather than replacing them. Step 1 confirms this and
  records it; the gate then guarantees that no `Filters` apply apart from the committed lists, by building the
  rpmlint image with `/etc/xdg/rpmlint` emptied (or the option the research finds), and passing the committed
  empty config for the user layer; the "ran" line prints the list of config files rpmlint loaded. namcap runs
  with `-i`. Exit statuses are not trusted: rpmlint exits 0 on warnings, lintian
  fails only on errors by default, namcap mostly exits 0. Instead every output line is parsed; a line that is not
  a recognised finding, a recognised summary or a known banner is a failure, and rpmlint's summary counts must
  equal the number of parsed findings. Overrides are findings: lintian `O:` lines fail, and the gate fails if the
  .deb contains `usr/share/lintian/overrides/*` (so a package cannot bypass the committed lists).
- Exception matching: TAG is compared exactly (no glob); SUBJECT-GLOB is anchored `fnmatch`; a SUBJECT-GLOB that
  is only `*` is rejected.
- Self-tests `scripts/test-package-lint.sh`, added to `package-gate-test` (so they run in `just check`). They use
  stub linters on `PATH` (and a stub `podman`/`docker`) that print canned output in the real tools' formats, copied
  from real runs recorded in the test's fixtures, plus fixture packages from `scripts/lib/package-fixtures.sh`. The
  real linters are exercised by `just package-lint` itself.

Left for other features: lifecycle script content (F43, F44), installing on real targets (e2e), parity and glibc
gates (F37), dependency checks (F36). The feature fits in about six steps; no split is needed.

## Evidence
- Runs lintian on the .deb, rpmlint on the .rpm, namcap on the Arch package → `scripts/test-package-lint.sh`:
  stubs record their arguments; each is called once with the path of its own package and no other → asserted
  arguments. `just package-lint` on the real packages → exit 0, and its output shows a "ran" line per linter with
  the tool version.
- Part of `just package-gates` → `just --dry-run package-gates` lists `package-lint`; `just --dry-run check-slow`
  lists `package-gates`; `grep` of `.github/workflows/ci.yml` shows the named step in the `package` job after
  `just package`; actionlint and zizmor pass within `just check`.
- Any finding fails → test: a stub for each linter prints one finding not in its list → non-zero exit, output names
  linter, tag and subject; all three clean → exit 0. Also one test per severity line, each failing on
  its own: lintian `E:` `W:` `I:` `P:` `X:` `O:`, rpmlint `E:` `W:`, namcap `E:` `W:` `I:`. A stub that exits 0 but
  prints a finding fails; a stub printing an unrecognised line format fails; an rpmlint summary whose counts
  differ from the parsed findings fails.
- Flags are applied → test: the stubs record their arguments; the asserted set includes the lintian display/pedantic/
  no-config flags, rpmlint's committed empty config and namcap `-i`.
- Overrides cannot bypass the lists → test: a fixture .deb containing `usr/share/lintian/overrides/custodio` fails
  the gate; `O:` output fails.
- Findings listed with a reason pass → test: the same finding listed (`TAG | SUBJECT | reason`) → exit 0.
- Entry without a reason fails; unparsable line fails; stale entry (no matching finding) fails → tests, each
  non-zero with a message naming the file and line.
- Lists are per linter → test: a lintian finding listed only in `rpmlint.txt` still fails; a finding whose tag
  matches but whose subject does not match the glob still fails; a `*` tag entry covers nothing; a SUBJECT-GLOB
  of only `*` is rejected; the glob is anchored (a prefix match does not
  hide it).
- Committed lists justified → a test over the committed files runs the same parser (no empty reason, no unparsable
  line); `just package-lint` on the real packages passes with no stale entry. The test also runs the committed lists through
  the gate's matcher and asserts that no entry matches the subject `/usr/lib/custodio/custodiod` (nor
  `usr/lib/custodio/custodiod`), whatever globs are used.
- Findings fixed in the packaging rather than listed → the builder's list of raw findings (step 2, in
  `docs/findings.md`) shows each finding as fixed or listed; the committed lists contain only the latter, and the
  review can compare. Test: `grep` that no committed list holds a non-comment line without a reason field.
- Fail closed → tests: `DIR` missing, no package of a format, two packages of a format, linter stub exiting with a
  crash status (2 or 127), stub exiting "findings" with output that parses to nothing, no host linter and no
  runtime → each non-zero with a message naming the problem; none passes silently.
- Installed in the dev image, pinned → `harness/Containerfile` installs lintian and rpmlint with versions equal to
  `packaging/lint/pins.txt` (a test greps that the versions agree); `just package-lint` run in the dev container
  uses them (the "ran" lines say `host`). namcap, branch 1 (built from source): the Containerfile checks the
  sha256 of the namcap and pyalpm sources and the version grep covers it; branch 2 (container only):
  `docs/findings.md` records why and the namcap "ran" line says `container`. The builder states the branch in
  PROGRESS.md.
- Linter versions in containers equal the pins → the image build fails when the installed version differs from
  `pins.txt` (checked for all three: lintian, rpmlint, and namcap from the dated ALA snapshot; a test greps that
  each Containerfile has the version assertion and takes its pin and snapshot date/timestamp from `pins.txt`),
  and the "ran" line prints the version, which `just package-lint` compares with the pin. Test: a stub container
  linter (stub `podman`/`docker` running a stub linter) reports a version different from the pin → the gate fails
  with a message naming linter, found version and pin, for each of the three linters; reporting the pin → passes.
- Pins stay installable → `pins.txt` holds the snapshot/koji source for each linter; a test greps that no
  Containerfile installs an unversioned linter or a rolling mirror (no `apt-get install lintian` without `=version`,
  no default pacman mirrorlist). The error path is tested: a stub container whose build exits non-zero because the
  pin is not installable → the gate fails with a message naming the pin and does not run any other version.
- rpmlint reports what the distro config filters → `docs/findings.md` records a run (and
  `reports/package-lint-container.txt` shows it) where a tag that the stock Fedora `fedora.toml` filters is
  reported by the gate's rpmlint, e.g. by running the gate's rpmlint image on a small fixture rpm that triggers a
  tag listed in Fedora's filters; the same fixture run with the stock config is shown to hide it. The test over
  the committed image checks `/etc/xdg/rpmlint` holds no `.toml` filters.
- lintian profile hides nothing → `docs/findings.md` records the profile and vendor data versions, and that a
  profile check shows no tag disabled; the "ran" line prints the profile version.
- On a host lacking a linter the recipe uses a container of the target distribution → test: `PATH` without the
  linter and with a stub `podman` that records its arguments → called with the image built from the pinned base, the package
  directory mounted read-only, `--network none` and a non-root `--user`; the same with only `docker`; a host linter whose version differs
  from the pin is not used (container chosen). The real container path is exercised by
  `PACKAGE_LINT_FORCE_CONTAINER=1 just package-lint` → exit 0 with three "ran ... container" lines; the output is
  saved to `reports/package-lint-container.txt` (committed) for the review. In CI the same runs in the job.
- Path `/usr/lib/custodio/custodiod` accepted by namcap and rpmlint, or reported → `docs/findings.md` records the
  raw namcap and rpmlint output on the real packages before any exception is applied, and none of the findings has
  that path as subject; the matcher test above shows no list entry covers it; otherwise `BLOCKED.md` exists with the options and the feature is not claimed.
- Verify command → `just check && just package && just package-lint` → exit 0.
