# F19 — Composed-mechanism core: hashing, DigestInfo and mechanism mapping

## Scope
Pure Rust in `custodio-pkcs11`, one new module `composed` (file `src/composed.rs`, no `unsafe`, no
FFI, no D-Bus, no session state). It builds:

- `Composed`: the six mechanisms (`CKM_SHA256/384/512_RSA_PKCS`, `CKM_ECDSA_SHA256/384/512`) with
  `from_ckm(u64) -> Option<Composed>`, `ckm()`, `hash()` (SHA-256/384/512), `key_type()` (RSA or
  P-256) and `raw()` (the raw service mechanism: `CKM_RSA_PKCS` or `CKM_ECDSA`).
- `DigestHasher`: an incremental hasher (`new(hash)`, `update`, `finalize`) that is `Clone`, so a
  later multi-part path can clone it, finalize the clone, and keep the original after
  `CKR_BUFFER_TOO_SMALL`.
- `digest_info(hash, digest)`: the RFC 8017 section 9.2 `DigestInfo` for SHA-256/384/512 (fixed
  prefix plus digest; a digest of the wrong length is an error).
- `sign_input(composed, hasher)`: the bytes handed to the service. This is the `DigestInfo` for
  RSA and the bare digest for ECDSA, with no truncation (decided below).

Left for other features: wiring into `C_SignInit`/`C_Sign`/`C_SignUpdate`/`C_SignFinal`,
`C_GetMechanismList`/`Info`, session state, polkit, audit, the D-Bus interface, fuzz and e2e.
The existing module code and its tests stay unchanged.

Truncation decision: the module passes the full SHA-384/512 digest and the service truncates
(it already does; see step 2). Reasons: the service owns the P-256 curve and the module stays a
thin mapper; no D-Bus change is needed. The choice is recorded in `docs/decisions.md` in step 2.
If the step-2 test shows the service does not already produce the standard result, the builder
changes `custodiod/src/sign.rs` so it does, and keeps the 1024-byte input limit.

The feature is about five steps; no split needed.

## Steps
- [ ] 1. Add `Composed` and its mapping (mechanism → hash, key type, raw mechanism), with unit
      tests that fail on any swapped or missing row. Rejects raw mechanisms and unknown values.
- [ ] 2. Add `DigestHasher` (Clone) and `digest_info` with RFC 8017 known-answer tests. Add the
      service test for SHA-384/512 digests on P-256 in `custodiod`, change `sign.rs` only if the
      test fails (the existing `custodiod` sign tests must then stay unchanged), and record the
      truncation decision in `docs/decisions.md` (format at the top of that file).
- [ ] 3. Add `sign_input` joining hasher, `DigestInfo` and mechanism.
- [ ] 4. Add the cross-verification tests for all six mechanisms (RSA 2048 and P-256 test keys,
      signing through `sign_input` and `custodiod::sign::sign`, verifying over the original
      message with an independent verifier).
- [ ] 5. Run `just check` and the Evidence; append the `PROGRESS.md` entry; commit.

## Evidence
All tests are in `custodio-pkcs11` unless noted; run with `cargo test -p custodio-pkcs11 composed`.

- Six composed mechanisms map to hash → `composed::tests::mapping_table`: asserts all six rows of
  (CKM value, hash, key type, raw mechanism) literally, not derived from the code under test →
  each row equals the PKCS#11 value in `cryptoki-sys` and the table in SPEC.md section 1.
- RSA ones need an RSA key, ECDSA ones need P-256 → same test, `key_type()` column → fails if a
  row is swapped.
- Raw/unknown mechanisms are not composed → `composed::tests::rejects_non_composed`, listing the
  constants by their `cryptoki_sys` names: `CKM_RSA_PKCS`, `CKM_ECDSA`, `CKM_RSA_PKCS_PSS`,
  `CKM_SHA256`, `CKM_SHA_1_RSA_PKCS`, `CKM_ECDSA_SHA1`, the neighbours `CKM_SHA224_RSA_PKCS` and
  `CKM_ECDSA_SHA224` (SHA-224 is out of scope in SPEC), and 0 → `from_ckm` returns `None` for each.
- Hashing is correct → `composed::tests::hash_known_answers`: SHA-256/384/512 of `""`, `"abc"` and
  a multi-block message against the FIPS 180 / NIST vectors written as hex literals → equal.
- Incremental and clone → `composed::tests::incremental_equals_one_shot` (chunk sizes 1, 7, and the
  whole message give the same digest) and `composed::tests::clone_keeps_state`: update with "ab",
  clone, finalize the clone, update the original with "c", finalize → the clone digest is that of
  "ab", the original digest is that of "abc" (fails if a clone shares or consumes state).
- DigestInfo byte for byte → `composed::tests::digest_info_prefix_rfc8017`: for each of
  SHA-256/384/512, `digest_info(h, d)` equals the literal RFC 8017 section 9.2 prefix
  (`3031300d060960864801650304020105000420`, `3041300d060960864801650304020205000430`,
  `3051300d060960864801650304020305000440`) followed by `d`, and also equals a DER encoding of the
  `DigestInfo` built in the test, independent of the literals: a `der` 0.8.3 `Sequence` of
  `spki` 0.8.1 `AlgorithmIdentifierOwned` (OID from `const-oid` 0.10.2
  `db::rfc5912::ID_SHA_256/384/512`, parameters `NULL`) and a `der::asn1::OctetString` of `d`,
  encoded with `der::Encode::to_der` → equal. (`pkcs1` 0.8.0-rc.5 has no `DigestInfo` type.)
  These three crates are dev-dependencies at the versions already in `Cargo.lock`.
- Wrong digest length → `composed::tests::digest_info_rejects_bad_length`: 0, 31 and 33 bytes for
  SHA-256, 32 for SHA-384 → error.
- Service input per mechanism → `composed::tests::sign_input_shape`: for RSA mechanisms the output
  is the `DigestInfo` of the message hash; for ECDSA it is exactly the bare digest, 32/48/64
  bytes, never truncated and never the message → equal to expected hex literals for "abc" (the RFC
  prefix plus the FIPS 180 "abc" digest), not computed with `sha2` in the test.
- Truncation choice does not change the signature, SHA-384/512 on P-256 → test in `custodiod`
  (`sign::tests::ecdsa_long_digest_standard_result`): signs the full 48- and 64-byte digests with
  `Mechanism::Ecdsa`, and checks the signature verifies over the original message with
  `p256` verify_prehash on the digest truncated to its leftmost 32 bytes, and also with an
  `openssl` CLI check when the binary exists → verifies. In the same test, `verify_prehash`
  over the rightmost 32 bytes of the 48- and 64-byte digests must return `Err`, so the test tells
  left from right truncation. Also `cargo test -p custodiod sign` → the existing sign tests pass
  unchanged.
- Cross-verification, all six → `composed::tests::cross_verify_{rsa,ecdsa}`: for each mechanism
  and a test key (RSA 2048, P-256), a signature made by `custodiod::sign::sign` on `sign_input`
  verifies over the original message with a verifier that hashes the message itself, so it does
  not use our `DigestInfo` code: `rsa::pkcs1v15::VerifyingKey<ShaN>::verify(message, sig)` for RSA
  and `p256::ecdsa::VerifyingKey::verify_prehash` over the verifier's own hash for ECDSA. Because
  `verify_prehash` truncates with the same `bits2field` code as `sign_prehash` in `custodiod`, the
  SHA-384/512 cases also verify over the verifier's own digest cut by hand to its leftmost 32 bytes. Also: the same signature does not verify over a different message, and an
  RSA signature made with another hash's `DigestInfo` does not verify (fails if the verifier
  accepts anything).
- Same cross-check with OpenSSL → `composed::tests::cross_verify_openssl`: `openssl dgst
  -sha{256,384,512} -verify` for RSA (DER-wrapped ECDSA signature for P-256 after converting
  `r||s` to DER) on the same signatures; if `openssl` is not on PATH it prints a skip
  line; if it is on PATH and verification fails, the test fails (no skip on failure). It is a second
  independent check of the truncation.
- No FFI, pure code → `grep -n 'unsafe\|extern' crates/custodio-pkcs11/src/composed.rs` → no
  output; the module is also free of `zbus` and `cryptoki_sys` function calls (constants only).
- Hash secrecy rules → the hasher has no `Debug` that prints state (derives none or prints a
  placeholder); `composed::tests::debug_does_not_leak` formats it after `update(b"secret-data")`
  and asserts the output contains neither the data nor digest hex.
- Dependencies stay allowed → `just check` (includes `cargo deny`) → passes; `deny.toml` denies duplicate
  versions, so the new `sha2` dependency and the `rsa`/`p256` dev-dependencies use exactly the
  versions `custodiod` pins (`sha2 = "0.11.1"`, `rsa = "=0.10.0-rc.19"`, `p256 = "0.14.0"`), as do
  `der`/`spki`/`const-oid`; no new `skip` entry in `deny.toml`; no OpenSSL crate (the CLI is only
  invoked as a process).
- Whole feature → `just check` → exits 0, including clippy pedantic and no new `#[allow]`
  without a justifying comment.
- Truncation decision recorded → `grep -n -i 'truncation' docs/decisions.md` → shows an entry dated
  today with Decision, Why and Rejected bullets.
