# F160 — The VM case list and the VM run: just e2e-vm, install without recommends, the shipped unit and the record

## Scope
Built:
- `e2e/vm/cases.list`: the case list of the VM target. It holds (a) the cases of the groups `sign-*`, `noplain-*`, `pcr-*`,
  `fallback-*`, `tpm-clear-*` and `upgrade-kinds-*` that can exist in a VM, under the ids the container scripts already report
  (the VM reuses the case scripts); (b) the VM-only cases below. The shared setup (install, service, users, key import) has no
  case id of its own: it is a step of the run and a failed step fails the run. A container case of those six groups that is not
  in the VM list (for example `fallback-host-*`, which exist only in mode `none`) is named, with a reason, in a data file
  `e2e/vm/omitted.list` (`case: reason`), so that nothing leaves the VM list unseen. `tpm-kind-*` and the other VM-only cases that
  later features add (F161 and after) are added to the list by those features, not here.
- `e2e/vm/skip.list`: the cases a VM run may report skipped, with the reason (same format and lint as `skip.list` of a target).
  F160 puts into it only what cannot run in a VM by nature; it does not park a case whose VM form belongs to F161–F163.
- The accounting in `e2e/check-cases.sh` for a VM run (the caller says it is one; how is the builder's choice). It is the same
  accounting: every case of the list reported exactly once, run or skipped, a skipped case on the skip list, an unknown, missing
  or duplicated case failing the run, and with a selection (`e2e-vm-cases`) exactly the selected cases. The existing per-mode
  rules (`sign-*`, `noplain-*`, `journal-kind-*` and `upgrade-kinds-before|kept|signs` never skipped; `pcr-*`, `tpm-clear-*`
  not skipped when the VM has a TPM, which it always has) apply to both VM modes, `full` and `lacking`. The one change:
  `fallback-tpmbound-*` and `upgrade-kinds-tpmbound` reported run are accepted in a VM run and still refused in a container run
  (any `CHECK_TPM_MODE`). In a VM run they are refused when reported skipped (acceptance 4 and 10 need them to run in the VM),
  so no `skip.list` entry can park them and a skipped run cannot pass the checkpoint accounting; this rule is F160's, not left to
  F161/F163. The VM has no `none` mode, and `tpmfail-*` are not in the list. A container run is accounted exactly as
  before: `scripts/test-e2e-skips.sh` passes unchanged (no control of it is edited or removed).
- The host driver of one VM run (a new script under `e2e/vm/`; its name is the builder's) and the recipes in `justfile`:
  `just e2e-vm mode` (`full` or `lacking`, anything else, empty or missing refused before a package is built or a VM
  started) and `just e2e-vm-cases mode +names` (names and globs like `e2e-cases`, resolved against `e2e/vm/cases.list` only;
  a name that matches no case refuses the run before anything starts). Both depend on `e2e-packages` as `e2e` does. The driver:
  1. gets the image from `e2e/vm/image.sh` (F158; a failing `image.sh` stops the run before any VM exists);
  2. starts the VM with `e2e/vm/vm.sh start MODE` (F159) and stops it on every exit (a trap), whatever happens;
  3. copies into the guest, byte for byte, the package N and N+1 (`.deb`), the `e2e` scripts and the same few files the
     container mounts for the cases (`docs/audit.md`, `scripts/check-no-plaintext.sh`, `scripts/check_no_plaintext.py`,
     `crates/custodiod/src/app_id_source.rs`, the harness's credential reader of F157), at the paths the case scripts expect;
  4. installs the package N with apt and **`--no-install-recommends`** (`apt-get update` first: the image has empty lists), and
     only then reads `systemd-analyze has-tpm2` for the record and for the VM-only case below. This order is the point: F151 found
     that `tpm2-tools` brings the `libtss2` libraries `has-tpm2` needs, so installing the test tools first would hide a package
     that lacks `libtss2-rc0t64` (F154);
  5. installs the test tools in the guest only (polkit test agent and what the cases need as the Debian 13 target's
     `Containerfile` lists: `tpm2-tools`, `openssl`, `opensc`/`p11-kit`/`pkcs11-provider`, `libnss3-tools`, `python3-gi` and so on,
     also without recommends), after which the package is still the one installed in step 4 and no test tool is a dependency of it;
  6. runs the shared setup and the selected cases with the existing guest scripts, and accounts for them with
     `check-cases.sh` on the guest's `E2E-CASE` lines. The guest side must not call `tpm_setup`/`tpm_teardown`, must not start an
     `swtpm`, filter or drop-in, and leaves the unit as shipped. The builder decides whether that is a VM mode of `guest.sh` or a
     guest driver of its own; either way no container run changes (`scripts/test-e2e-host.sh` and the other existing e2e host
     self-tests pass unchanged). How the VM mode maps to the expectations the case scripts read from `E2E_TPM` (`full` expects what
     `swtpm` expects, `lacking` what `lacking` expects) is written in the driver's header and is what the driver passes to the guest command as `E2E_TPM`. A group whose script needs a VM form (restart
     of `swtpm`, clearing the TPM, upgrade kinds: F161–F163) is wired to its existing script here; that it passes in a VM is proven
     by F161–F163 and the checkpoint, not claimed here.
  The driver changes nothing on the host: the test tools and packages are installed by guest commands only; the host sees
  read-only `dpkg-deb -f`.
  7. writes the record and the per-step times, whether the run passed or not.
- The VM-only cases, judged in the guest by a script whose judging functions the host self-test also runs on fixtures:
  `/dev/tpmrm0` exists; `systemd-analyze has-tpm2` reports full support (exit 0, output `yes`) right after the package install and
  before any test tool; the install used no recommends (apt's recorded command line holds the flag; the `Recommends` of the packages the
  install pulled in are not installed, since the `.deb` itself declares none); the installed unit is the shipped one (no drop-in under `/etc`, `/run`, `/usr/lib`
  `custodio.service.d`, the unit file's checksum equal to the package's, no `CUSTODIOD_TEST_SWTPM_TCTI` in the unit, its drop-ins
  or the running service's environment); the service reaches the TPM through `/dev/tpmrm0` (no TCTI override, and the running
  service has the device open or its configured TCTI is the device; the builder proves which signal is reliable in the probe
  step and the case uses it).
- The run record, printed and saved under `target/e2e/` as `vm.<mode>.record` (log `vm.<mode>.log`, steps `vm.<mode>.phases.tsv`,
  so the container files and `phases.tsv` that `run.sh` rewrites are untouched). `key=value` lines: `target`, `tpm` (the mode),
  `image_serial`, `kernel` (guest `uname -r`), `systemd` (guest), `package_version`, `swtpm_version` (the host executable the
  launcher used), `has_tpm2` (the guest's output and exit code), and one line per step with its seconds (image, boot, copy,
  install, tools, setup (always present), each case group, teardown). A field the run could not read is written as `unknown`, never left out.
- The guest side in its VM mode is tested by a section "guest" of `scripts/test-e2e-vm-host.sh` (helper under `scripts/lib/`):
  it runs the real guest script with `systemctl`, `apt-get`, `swtpm` and `systemd-analyze` stubbed on `PATH` to log, the tpm-lib
  functions overridden to log, and the unit and drop-in directories pointed at a temporary tree. It costs under 1 s, in parallel
  with the other sections.
- Two self-tests, both added to `just test-scripts` (`verify` runs them by name; `just quick` does not run `test-scripts`): `scripts/test-e2e-vm-cases.sh` and `scripts/test-e2e-vm-host.sh` (a helper under `scripts/lib/` if one
  file would pass the 5000-token limit). A negative control is a copy of the script under test with one behaviour removed,
  shown to differ with `cmp`; the same check run on the copy must fail.

Not built (and where): the real run of `just e2e-vm full|lacking` and its numbers are at the checkpoint (F168); the kind, sign,
PCR, TPM-clear and upgrade cases passing in a VM (F161–F163); the silent-fallback case and the credential reader's use (F161);
the CI workflow and runner KVM (F164); image, launcher and modes (F158, F159, only called). The VM target's row in `budgets.tsv`
is a person's: this feature does not edit it, and the first real run asks for it in `BLOCKED.md` if the loop finds none.

Environment: the dev container has `/dev/kvm`, QEMU, `swtpm` 0.10.2 under `/opt/swtpm` and the verified image cache (F158,
F159: `just vm-host-check` exit 0), so nothing new is needed on the host. The guest needs network for `apt-get` at the real run.
Step 5 measures, once and by hand, what the self-tests cannot. Measured: the serial channel copies 15 KB/s (10 minutes for N and N+1); the guest has a route out. The files
travel on a read-only payload drive (F159 amendment); the serial channel carries commands and results only.

Cost (estimates): `test-e2e-vm-cases.sh` 1–3 s (no VM); `test-e2e-vm-host.sh` 4–8 s (about 20 driver runs against a stub `vm.sh`, started together, waits on conditions);
both run under the `script *` budget (120 s). The step 5 probe: one `full` boot (13 s), the copy and the install, a few minutes once, by hand.
Every step fits one session.

## Evidence
- Payload → `test-e2e-vm-host.sh` "good": `vm start` carries `VM_PAYLOAD`, a tar of both packages, the e2e tree and the mounted files (read back
  by the test); no `vm put`; the guest extracts it from the payload drive. Control: a driver copy using `vm put` for a package fails.
- The VM has its own list, with the groups and the VM-only cases → `test-e2e-vm-cases.sh` "list": `e2e/vm/cases.list` lints (one id
  per line, no duplicate), holds at least one case of each of the six groups and each VM-only case, and every id of the six
  groups found in `e2e/cases.list` and `e2e/targets/debian13/cases.list` is either in the VM list or in `e2e/vm/omitted.list`
  with a reason, never both, and every omitted id exists in a container list. Controls: a copy of the VM list without one id of a
  group (not omitted) fails; a copy with an id no script reports fails.
- The list matches the case scripts → `test-e2e-vm-cases.sh` "scripts": every id of the VM list is reported by a case script or
  generated by one the test can run in its listing mode (by a method that reads the scripts' reporting calls, not their
  comments), and every id a VM-only case script reports is in the list. Controls: a copy of a script that stops reporting one
  id, and a copy that reports an extra one, each fail.
- Accounting, VM run → `test-e2e-vm-cases.sh` "accounting": over a synthetic guest output for the real VM list, in both modes, a
  complete run passes; one case missing, one unknown, one reported twice, a skipped case not on the skip list, a skipped
  `sign-*`/`noplain-*`/`pcr-*`/`tpm-clear-*` case, and a skipped `upgrade-kinds-kept` in a VM run, a selection run that reports a case not selected each fail with the message
  naming the case. Each is the same check as the container's on the same input, and the message equals the container's. The comparison runs for `CHECK_TPM_MODE` unset and for each mode, and with the VM flag
  absent the output is byte-identical to before, so the flag cannot change the default path.
- tpmbound cases → the same test: `fallback-tpmbound-import`, `fallback-tpmbound-cli-list` and `upgrade-kinds-tpmbound`
  reported run pass in a VM run (both modes), and the same input accounted as a container run (each `CHECK_TPM_MODE` of
  `swtpm`, `none`, `lacking` and unset) fails naming the case; reported skipped fail in a VM run even if a (fixture) skip list names them, naming the case.
  Controls: a copy of `check-cases.sh` that accepts them run in a container run fails this test; a copy that accepts them skipped
  in a VM run fails it too.
- The container accounting is unchanged → `scripts/test-e2e-skips.sh` exits 0 with no edit to its existing controls (`git diff`
  on the script shows additions only, if any), and `scripts/test-e2e-host.sh` exits 0.
- Recipes → `test-e2e-vm-host.sh` "recipes" (run on a copy of the justfile whose `e2e-packages` is stubbed to log, so no package is built;
  the mode check runs before the dependencies, in a first dependency recipe or a just-level `assert`, not in the body): `just --dry-run e2e-vm full` and `... lacking` show `e2e-packages` before the
  driver and the mode passed; `e2e-vm partial`, `FULL`, an empty mode and no mode exit non-zero with the allowed values named and
  no package build, image, or VM started (the stub logs show no call); `e2e-vm-cases full 'sign-*'` passes the selection, and a name
  that matches no VM case refuses before anything starts. Control: a recipe copy without the check starts the stub and fails.
- Steps and order → `test-e2e-vm-host.sh` "good" against the stub VM: the stub's call log shows, in this order, the image,
  `start MODE`, the copies (N, N+1, scripts), `apt-get update`, the package install, the has-tpm2 read, the tools install, the setup
  and cases, the record, `stop`; the mode reached `start` as given, and the guest command carries `E2E_TPM` mapped as the header says (`full` → the swtpm
  expectation, `lacking` → `lacking`), checked in both modes. Controls: a driver copy that installs the tools before the
  package fails the "has-tpm2 read before the tools" check; a copy passing `lacking` for `full` (and one dropping `E2E_TPM`) fails the mapping check.
- Guest side in VM mode → "guest" in `test-e2e-vm-host.sh`: with the logging stubs, one run of the guest in VM mode shows no
  `tpm_setup`/`tpm_teardown` call, no `swtpm` start, no file written under any `custodio.service.d` (the tree is identical before and
  after) and the unit file byte-identical; and the log shows the shipped-unit, no-TCTI and `/dev/tpmrm0` judges running after the
  shared setup and after the cases, not only before them. Controls: a copy of the guest script that calls `tpm_setup` (so it writes the
  `CUSTODIOD_TEST_SWTPM_TCTI` drop-in) fails both checks; a copy that runs the judges only before the setup fails the order check.
- Install without recommends → "good": the install command line the stub received has `apt-get`, `install` and
  `--no-install-recommends` on the package file, and so does the tools install; the package is installed by apt, not `dpkg -i`.
  Controls: a driver copy without the flag; a copy using `dpkg -i`; a stub transcript where the guest reports a Recommends
  package installed by the run → the VM-only "no recommends" case fails.
- VM-only cases → "vm-only" with fixtures of what the guest shows: each passes on the good fixture, and fails, naming the cause, on:
  no `/dev/tpmrm0`; `has-tpm2` output `partial` or exit 16 (the libtss2 gap) or `no`; apt's command line without the flag, or a
  `Recommends` package installed; a drop-in file present; the unit's checksum different from the packaged one; `CUSTODIOD_TEST_SWTPM_TCTI`
  in the unit, in a drop-in or in the service's environment; the service's TPM access through a socket instead of the device.
  Each failing fixture is a negative control of its own case. The judgement is also proven in a real guest by step 5 (recorded)
  and at the checkpoint.
- Record → "good": the saved `target/e2e/vm.<mode>.record` and the printed record both hold `target`, `tpm` equal to the mode,
  `image_serial` equal to the stub image's serial, `kernel`, `systemd`, `package_version` (equal to the fake `.deb`'s), `swtpm_version`
  (equal to the stub swtpm's `--version`), `has_tpm2` with output and exit code, and a seconds value for each step the stub log
  shows ran; both modes write their own file when run at once. A step that did not run is not given a time. Controls: a driver
  copy that drops `image_serial`; one that drops the step times; one that reports another mode than asked, each fails.
- Failure paths, each with the stub → `test-e2e-vm-host.sh`: `image.sh` failing, `vm.sh start` failing, a missing package, a missing
  N+1, `apt-get install` failing, `has-tpm2` not `yes`, a guest reporting a case twice, a case missing, an unknown case, a VM-only
  case failing, and `SIGINT`/`SIGTERM` during the run: each exits non-zero with a message naming the cause, calls `stop` exactly once
  when a VM was started (never when none was), leaves no temporary file (`TMPDIR` pointed at an empty directory), and still
  saves a record naming the steps that ran when a VM was started; a failing `image.sh` or `start` starts no later step. Controls:
  a driver copy without the stop trap leaves the stub VM running; a copy that ignores the accounting result exits 0 on a
  missing case; both fail the test.
- Test tools are guest-only → `test-e2e-vm-host.sh`: the driver itself runs `dpkg-deb -f` on the `.deb` it is given and refuses one whose
  `Depends`/`Recommends` name a test tool (the self-test feeds it the fake); the tools install appears in the stub log only as a guest command, the package
  file's `Depends`/`Recommends` fields (read with `dpkg-deb -f` from the fake `.deb` the test builds) name none of them, and
  nothing is installed on the host: the stub `PATH` puts logging `apt-get`, `dpkg` and `apt` ahead of any real one, and the log
  has no call from the driver itself (only `dpkg-deb -f`, read-only). Controls: a driver copy that runs `apt-get install` locally
  fails the host check; a fake `.deb` that depends on `tpm2-tools` fails the check.
- The shipped unit, no drop-in, no TCTI variable, the TPM through `/dev/tpmrm0`, `/dev/tpmrm0` exists, `has-tpm2` full after the
  install, no recommends, in a real guest → step 5 by hand (recorded in PROGRESS) and the checkpoint F168; the run record fields in a
  real guest, the numbers and the time budget row → the checkpoint F168 (and a person's `budgets.tsv`).
- Overall → `just quick`, then the `verify` scripts, exit 0.
