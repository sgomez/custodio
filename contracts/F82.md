# F82 — Journal entries name the flatpak app-id

## Scope
Wires F81's `AppIdSource` into the service and adds the app-id to the sign, import, delete and replace
certificate entries (F70–F79 entries, F74 model, `docs/audit.md`). F80 (validation, `AppId`, `AppIdOutcome`) and F81
(the reader, its bounds, the fake source) are not re-proven; this feature proves the wiring, the fields, the
no-effect rule and the documentation.

- **Pinned process reaches the source.** Today `CallerCredentials::credentials` returns only `Caller` and drops the
  `ProcessFD` after the `Pid:` check (`credentials.rs`). The builder changes the credentials result so the caller's
  pidfd (owned, dup'd or kept) is available to the operations. The `Caller` that polkit and the entry use (uid, pid,
  the polkit subject) is unchanged. A reply that fails today (no `ProcessFD`, not a pidfd of `ProcessID`) keeps
  failing as today (`AuthorizationUnavailable`, no polkit); this is not an app-id case.
- **When the source is asked.** Only for a call that has credentials and reaches the point where an entry is
  submitted with a caller (the same calls as today: after the argument and ownership refusals, so refusals still leave
  no entry and make no source call). The lookup happens in the same place for all four operations (one shared helper,
  not four copies) and is bounded by F81's deadline; it never refuses and never changes a reply. An entry without a
  caller (missing sender / failed credentials) has no pidfd: it carries the `undetermined` case, and the source is
  not asked. The service holds the source as a replaceable value like the sink (`Custodio` constructor keeps its
  signature or gains a builder method; production `main` wires `CgroupAppIdSource::new()`; "no source configured" in
  tests behaves as today). Whether the lookup runs before or after polkit is the builder's choice, within: the
  polkit subject, action, details and the number of asks do not depend on it, and a lookup in flight holds no per-key
  lock longer than F81's bound.
- **Entry fields.** Every entry of the four operations has the app-id state in documented fields, the builder names
  them (suggested `CUSTODIO_APP_ID_STATE` with three values, and `CUSTODIO_APP_ID` only for the first):
  an app-id was read → the validated id; no app-id (not sandboxed) → state says so, no id field; could not be
  determined → state says so, no id field. A source-less/no-caller entry is `undetermined`. The field is present on
  every entry (so a query for "not sandboxed" and "undetermined" both work), the compatibility rule of
  `docs/audit.md` holds (existing fields unchanged), and `MESSAGE` text is either unchanged or gains only typed
  values. Only an `AppId` value (F80's type, no public constructor) can be put into an entry; the entry model takes
  no `&str` for it, so a non-validated string cannot reach it. A hostile value never appears anywhere in an entry
  (message, any field).
- **No effect on outcome.** The app-id never changes the outcome, the reply, the polkit subject/details/action, the
  store changes, the order of the operations (F73–F79), or fail-closed behaviour. A sink failure is
  `AuditUnavailable` with every app-id case as without one.
- **Docs.** `docs/audit.md`: the new fields and values in the Fields table; the three cases; a query by app-id that
  runs (`journalctl _SYSTEMD_UNIT=custodio.service _UID=… CUSTODIO_APP_ID=…`) and one per case; the statements that
  the app-id is not authenticated (a process outside flatpak can forge a scope name; it is a record, not an
  authorization) and that for a flatpak caller `CUSTODIO_PID` is the pid of `xdg-dbus-proxy`, not the app's;
  that the source is the caller's cgroup scope (F67 decision (c), not `/.flatpak-info`) and that "none" is a
  best-effort finding, not proof of no sandbox. `docs/api.md` is changed only if an error or behaviour text there
  mentions entries.
- **Left for other features.** Real flatpak/cgroup behaviour in a container with the packaged unit (F95, F100
  e2e), journal catalog text and package checks (F90/F100), the `custodio` CLI. If the real reader cannot see the
  user's cgroups in the unit sandbox, that is F95's to prove; here the real source is only wired and unit-tested via
  F81's tests.
- **Size.** About five steps; no split.

Environment: nothing beyond the dev container. Tests use the private `dbus-daemon`, the polkit double of
`tests/audit/bus.rs`, `MemorySink`/`FailingSink`, F81's `FakeAppIdSource`, and a fake source that records the uid and
whether it was asked. For a pidfd on a real bus connection the private bus gives a real `ProcessFD` of the test process.
No new tool, network or privilege.

## Steps
- [ ] Failing tests first: a new `crates/custodiod/tests/app_id_audit.rs` (+ submodules under the file-size gate)
      and unit tests for the entry fields, one per Evidence row.
- [ ] Entry model: the app-id state on the four entry kinds (`Entry`, `OperationEntry`), the wire fields, the message
      unchanged or typed-only; only `AppId` is accepted; existing entry tests adapted, never weakened.
- [ ] Credentials: make the pinned pidfd available next to `Caller` without changing what polkit and entries see
      of the caller; add the source to `Custodio` and `main`, and the shared lookup helper.
- [ ] Use the helper in sign, import, delete and replace so every submitted entry carries the case; the
      three-cases tests and the equal-outcome tests pass.
- [ ] `docs/audit.md` (fields, values, queries, not authenticated, proxy pid) with doc tests; `just quick`, then
      `just mutants-diff F82` until clean; append `PROGRESS.md`.

## Evidence
All integration rows in `tests/app_id_audit.rs` unless stated; "entry" is the recording sink's entry decoded to its
wire fields.
- Three cases, every operation → `app_id_cases_for_every_operation`: for each of sign, import, delete, replace
  (successful approved call) and each of the fake source's three answers (`reading("org.example.App")`, none,
  undetermined), exactly one entry whose app-id state field has the literal documented value, `CUSTODIO_APP_ID`
  equal to `org.example.App` for the first and absent for the other two. The sign, import, delete and replace
  calls are the existing helpers' calls. Fails if one operation forgets the field or two cases are mapped to one.
- Cases on non-success outcomes → `app_id_on_every_outcome`: the same three answers on `denied`,
  `authorization_unavailable` (polkit), and one failure outcome per operation (signing_failed, wrong_password,
  certificate_mismatch; delete has none beyond the above) carry the field, since the entry is written for every
  outcome.
- Missing caller → `app_id_without_caller_is_undetermined`: a missing sender / failed credentials entry of each
  operation says `undetermined`, has no id field, and the source records zero calls.
- Outcome unchanged → `app_id_never_changes_the_outcome`: for each operation and each of the three answers and for
  "no source configured", the reply, the polkit asks (count, action, subject, details), the store afterwards (files,
  `ListKeys`, a later `Sign` verifying) and the entry apart from the app-id fields are equal to the no-source run.
  Includes Deny, Unavailable and the failing sink (reply `AuditUnavailable`, import not kept, delete restored,
  replace restored) with each answer.
- Refusals still silent → `app_id_not_asked_for_refusals`: invalid id, a missing or foreign id, a pending-delete id
  and a taken import id: no entry, no sink call, no source call, same replies.
- Source gets the pinned process → `source_is_asked_with_the_callers_uid_and_pidfd`: a recording fake sees the
  credentials' uid and a pidfd whose `Pid:` equals the entry's pid, once per call (not per entry field); two callers
  with different uids see their own.
- Source is bounded → `slow_source_delays_by_no_more_than_the_bound`: a source that never returns (released by
  dropping a channel at the end) gives an `undetermined` entry and the normal reply within F81's deadline plus a
  stated margin, with the real `LOOKUP_DEADLINE` or the lookup's documented timeout; a fast source adds no wait. A
  panicking source does not take the call down and gives `undetermined`. Fails if the helper awaits without the
  bound.
- Only a validated id is copied → `entry_model_takes_only_validated_app_ids`: a `compile_fail` doctest that builds an
  entry field from a `&str`/`String`; unit test that the wire value of a read id equals the validated id exactly;
  `hostile_values_never_reach_an_entry`: raw hostile strings (newline, `\x00`, 300 bytes, a `CUSTODIO_UID=0`
  injection, non-UTF-8, `=` characters, a valid id with trailing space) offered through the real `CgroupAppIdSource`
  on a fixture cgroup tree (F81's fixtures) produce `undetermined` or `none` entries and the string appears nowhere
  in the datagram (fields, message), also through the journal sink's datagram for each operation.
- Journal wire → `journal_sink_datagram_names_the_app_id`: over the private bus with the journal sink, one case per
  operation and answer gives a datagram with the documented field names and values, and the existing fields
  (`MESSAGE_ID`, `PRIORITY`, uid, pid, key id, outcome) unchanged.
- Entry secrecy intact → the existing `*_entries_hold_no_secrets` tests (sign, import, delete, replace) still pass
  with a source answering a read id; no new secret appears.
- Docs → `cargo test -p custodiod docs`: fails if `docs/audit.md` lacks any new field or value (checked against the
  code's names), the query by app-id, the "not authenticated" statement, the proxy-pid statement, the source being
  the cgroup scope, or if a documented query does not run against the entries a test produced (the same harness
  the other documented queries use).
- Negative control → one test per kind shows the checks can fail: a deliberately wrong sink-side copy (a test-local
  entry carrying the app-id of a different case) is caught by the three-cases comparison.
- Earlier behaviour intact → F73–F79 audit tests and F81's tests pass unchanged apart from added field expectations
  in `just quick`; `just system-gates` is not rerun here (the unit and the exposure gate are untouched).
- Mutants → `just mutants-diff F82` reports no surviving mutant in the changed code (case mapping, field names,
  the helper's bound, the zero-call rules, the pidfd hand-over).
