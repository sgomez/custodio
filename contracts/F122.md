# F122 — Fuzz targets for stored state and TPM signing input

## Scope
`crates/custodiod/fuzz` gains targets for the readers that parse bytes read back from disk, and for the TPM path's
handling of signing input. `just fuzz-smoke`'s default `expected` list gains the new names.

What the code survey found (the builder re-checks with `grep -rn -i "digestinfo\|digest_info" crates/custodiod/src`):
- `tpm::blob::Blob::parse` (and `from_parts`) reads the stored blob framing: the target `tpm_blob`.
- `creds::header::inspect` reads the credential header back after `Encrypt`: the target `cred_frame`.
- `store::Record::decode` reads the stored record that holds both: the target `record_decode` (stored state; it is
  reachable through the already public `store::Record`).
- The TPM signing path does **not** parse a `DigestInfo`: `tpm::sign::block::pkcs1_block` only frames the payload
  and `prepare_with` only checks lengths. So there is **no `digest_info` target**; the signing input is covered by
  `tpm_sign_input`, which drives `block::prepare_with` (all key kinds and mechanisms, PSS salt fixed, `salt_len` and
  data length taken from the input) and checks the block length and the refusals. If the re-check finds a real
  `DigestInfo` parser, the builder adds `digest_info` instead of arguing.
- Not here: the other existing targets (F-earlier), running the targets for longer than the smoke run, the corpus of
  checkpoints (F90, F100 run `just fuzz-smoke` again).

Environment: the nightly toolchain and `cargo-fuzz` are what `fuzz-build` already uses for the five existing
targets; the builder confirms with `just fuzz-build` at the first step and records the result in `PROGRESS.md`.
Only items already `pub` in `custodiod` are used; if a target needs one more export, it is added narrowly (it is
documented, and it does not need the `fuzzing` feature).

## Steps
- [ ] Re-check for a `DigestInfo` parser in the TPM path; write the result into the `PROGRESS.md` entry.
- [ ] `tpm_blob` target: `Blob::parse` on arbitrary bytes and `Blob::from_parts` on two arbitrary slices. Whatever is
      accepted must re-serialise (`to_bytes`) to bytes that parse again to an equal blob, and `public_area` must
      succeed; nothing may panic.
- [ ] `cred_frame` target: `creds::header::inspect` on arbitrary bytes returns a `Binding` or a `HeaderError`, never a
      panic; for any input shorter than the offsets it reads, it errors.
- [ ] `record_decode` target: `Record::decode` on arbitrary bytes; an accepted record re-encodes and decodes to the
      same owner, id, kind and certificate.
- [ ] `tpm_sign_input` target: `block::prepare_with` over every (kind, mechanism) pair with arbitrary data, salt length
      and hash; an accepted RSA block is 256 bytes, an accepted ECDSA digest is 32 bytes; no panic, no huge allocation
      from an oversized `salt_len`.
- [ ] Register the bins in `crates/custodiod/fuzz/Cargo.toml`, add the names to the default `expected` list of
      `just fuzz-smoke` (and its comment), and mention the targets where the fuzz workspace is documented, if it is.
- [ ] Run the evidence below.

## Evidence
- Targets exist and build → `just fuzz-build` → exit 0, builds `tpm_blob`, `cred_frame`, `record_decode`,
  `tpm_sign_input` besides the old five.
- Targets lint clean → `just lint-fuzz` → exit 0 (clippy `-D warnings` on the fuzz workspace).
- Each target runs without a crash → `just fuzz-smoke` (new default list) → exit 0, and its output has a
  `fuzz-smoke: <target> -runs=…` line for each of `tpm_blob`, `cred_frame`, `record_decode`, `tpm_sign_input`.
- Default list includes the new ones, and the check can fail → `just fuzz-smoke "delete_args replace_cert_args app_id
  dbus_args p12_parse pkcs11_args tpm_blob cred_frame"` → exit 0; and, as a negative control run once and recorded in
  `PROGRESS.md`, the same command with a made-up extra name (`… cred_frame no_such_target`) → exit non-zero with
  `target no_such_target is missing or did not run`.
- Targets exercise real input, not only reject it → a seed per target (a valid blob, a valid credential header of each
  `Binding`, a valid record, one PSS and one PKCS#1 input) is placed in the target's checked-in corpus if the
  workspace keeps one, or else the builder shows once (command and result in `PROGRESS.md`) that a short run reaches
  the accepting branch (`-print_final_stats` / coverage shows more than the first reject).
- `DigestInfo` parsing → the re-check step: no parser exists, so no `digest_info` target; `tpm_sign_input` covers
  `prepare_with` instead → the `PROGRESS.md` entry states the grep and its result.
- Repo stays green → `just quick` → exit 0.
