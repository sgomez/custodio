# F186 — docs/install.md, release notes and the manual acceptance steps

## Scope
Three documents changed or added, three script tests; no Rust change.

- **`docs/install.md`** (the "Firefox" section) shows `custodio register` as the way to register browsers, and
  `custodio register --remove` to run *before* uninstalling the package (and says where in "Removing and purging" that
  belongs). The manual `modutil` route stays as a fallback, with `modutil -add` and the matching `-delete`, and says when it
  is needed: Mozilla's own Firefox on Fedora and RHEL/Alma (which the command skips), and a browser the command does not
  know. The existing claims (install command per target, bus-check messages, paths) stay true and stay checked by
  `scripts/test-docs-install.sh`, which must still pass unchanged in what it checks. Facts (command, options, what the
  command prints and skips) come from `docs/api.md`, the code and the F185 README, not from memory.
- **Release notes** for v0.8.0, unnamed (`docs/decisions.md`, "First public release"), in one file whose path is the
  builder's and is fixed once linked from the README. It covers SPEC Design 8's list: supported systems; what is new since
  M5 (snap sockets, the registration command, the stale-copy refresh units, the full-disk warning, the docs; taken from
  `docs/milestones/M6` and `SPEC.md`); known limits (the same limits as the README, which it may link rather than copy);
  the upgrade note that keys stored before M4 were purged (`docs/milestones/M4/SPEC.md`, "No migration"; `docs/audit.md`
  for the journal entry). The notes' version is `0.8.0`/`v0.8.0` and no codename. The package file names in `install.md`
  say `0.1.0` today and `Cargo.toml` is `0.1.0`: bumping the version is the release step (`just release`), not this
  feature, so no test compares the notes' version with the manifest, and PROGRESS.md says so.
- **`docs/manual-acceptance.md`** gains one section (numbered after the last one, 25 (section 24 is M5's PCR-mask page)) for SPEC acceptance 19: an Ubuntu
  26.04 *desktop* VM with the Firefox snap from the store; install the package; run `custodio register`; a TLS server that
  requires a client certificate; Firefox completes client authentication once with an RSA and once with a P-256 key, with a
  polkit dialog per signature; refusing the dialog fails the handshake; the journal query that shows each signature with the
  Firefox label and Firefox's pid; the snap revision recorded. It ends with a result table in the form of sections 23/25's neighbours (23, 24)
  (step, expected, pass/fail), and states what is an invalid run (for example a label that is not `snap.firefox.*`).
  Who runs it and when is a person's (the milestone sign-off), never the loop.
- **Scripts**, added to `just test-scripts` and so to `script-tests` like their neighbours (justfile lines near
  `test-docs-readme.sh`): `scripts/test-docs-install-register.sh`, `scripts/test-docs-release-notes.sh`,
  `scripts/test-docs-manual-m6.sh`. They reuse `scripts/lib/docs_check.py` (F185: block-kind rule, link check, `console`
  block runner) and the F185 fixtures for `register` (temporary `HOME`, stub `modutil` first on `PATH`, the
  `unshare` overlay that supplies `/usr/lib/custodio/libcustodio_pkcs11.so`); a shared helper is not a fourth test. They
  extend `docs_check.py` or a new `scripts/lib/` file if they need something it lacks (no duplication of its code).
- **Not here.** Prose, and whether the notes agree with `docs/api.md`/`audit.md`/`decisions.md` (acceptance 20), is a
  person's; no test greps wording, headings or citations. The real Firefox snap, polkit dialogs and a real TLS handshake
  in Firefox are acceptance 19 itself: a person's run, plus the VM suite's snap cases at the checkpoint (acceptance 17).
  The README's own commands are F185's. `test-docs-install.sh` is not edited except to keep it green (it is a `verify`
  item and is not weakened).

**What "run as written" means** is F185's rule: a fenced block whose info string is `console` is run command for command in
one shell, and where the document shows output it is compared with what the real command prints (stdout only); a `bash`
block is never run and the script prints how many there are; any other info string, or none, fails. Where a command
cannot run in a test (a package-manager install, `sudo`, `snap`, a VM, a browser), it sits in a `bash` block; the three
scripts print the count of those blocks, and the builder keeps them to what no test can exercise.

- **`test-docs-install-register.sh`.** Runs the `console` blocks of `docs/install.md` that show the registration and its
  removal on the real `custodio` (as F185's README script does): after `register` the stub `modutil` log shows an `-add` for
  the installed module path in the fixture Firefox profile and the snap copy exists; after `register --remove` the entry
  and the copy are gone. The manual fallback shows `modutil -add`/`-delete` with a profile path; as `<profile directory>`
  is a placeholder and `docs_check.py run` would hand it to bash literally, the fallback sits in a `bash` block (never run by that runner) and the script runs it itself, substituting a fixture profile directory for the placeholder (the substitution is
  in the script, the document keeps the placeholder) against the real `/usr/bin/modutil` (installed here; it needs an NSS database in the fixture profile, a closed stdin, and a wait on its exit, never on time) else the stub, and the
  builder records which in PROGRESS.md; the command's *form* (`-dbdir sql:`, `-add`, `-libfile`, the module path) is then
  checked against what `custodio register` itself passes to `modutil` (the stub's recorded arguments), so the fallback and
  the command cannot drift apart. Also: the document's relative links resolve and `#anchor`s match headings; the
  README keeps its link to `install.md` (checked by `test-docs-install.sh`).
- **`test-docs-release-notes.sh`.** (1) The systems the notes name as supported (a list or table under a fixed heading of the notes, which the script reads and the builder fixes) equal the set of
  `e2e/targets/*/` (one per directory; the mapping directory → system name, `debian13` → Debian 13 … `alma10` → RHEL/Alma
  10, is a table in the script that fails on an unknown directory, as `test-docs-install.sh` does) — so adding a target
  without the notes, or naming a system with no target, fails. (2) The README links the notes (required link by target path)
  and every relative link of the notes resolves. (3) Every `console` block of the notes runs as written (the upgrade note
  and any `custodio register` example); the block-kind rule holds. (4) The notes' version string is `0.8.0`/`v0.8.0` and
  `docs/decisions.md` still carries the "v0.8.0, no name" decision (a pin of the fact, not of wording: the script reads the
  decision's version token, not its prose).
- **`test-docs-manual-m6.sh`.** Reads only the new section 25 (`## 25.`) of `manual-acceptance.md`, as `test-docs-manual-m5.sh` does
  for its section 24; it never matches `## 24.`. It runs what can run on the dev container: the `openssl` commands that make the test CA, the RSA 2048
  and P-256 client certificates and `openssl s_server -Verify`/`s_client` (a real client-certificate handshake on loopback, one server per case on `-accept 0` with a wait on its `ACCEPT` line, judged by the verify output of server/client, never by `s_client`'s exit status; both key types, whose type and size/curve are read with `openssl pkey -text`, prime256v1 and RSA 2048; a client with no certificate or the wrong CA is refused), the page's `journalctl` query, checked statically as said below (the query selects exactly the Firefox-labelled
  signature entries and prints the pid; entries of other labels are not selected). No fixture journal can be written in the dev container (no `systemd-journal-remote`, no `/run/systemd/journal`, no python `systemd`), so the query is checked statically: its match is the full value `CUSTODIO_PEER_LABEL=snap.firefox.firefox (enforce)` read from the code's allowed label and `docs/audit.md`, not a `snap.firefox` prefix, and its field names exist in `docs/audit.md`; a person runs the real query in acceptance 19, and the field names the page uses
  against `docs/audit.md`. What only a VM can run (`snap list firefox`, Firefox, the polkit dialog, `multipass`/`virsh`) is
  in `bash` blocks counted and listed by the script, never silently skipped. The result table's rows are checked as a table
  (each has step, expected, result columns; the section ends with the form).

**Costs** (estimated from `test-docs-readme.sh`, 1.9 s with 6 controls, and `test-docs-manual-m5.sh`, ~1.5 s with 19
controls): `test-docs-install-register.sh` builds `custodio-cli` and the example server only if it needs the bus (it does
not: `register` needs none, F182), so ~3–6 s warm, ~12 s cold, controls in parallel; `test-docs-release-notes.sh` ~2 s
(a link check, `e2e/targets` listing, a `register` run if the notes show one); `test-docs-manual-m6.sh` ~3 s (two
`openssl` handshakes on ephemeral loopback ports, waits on the listening socket, never `sleep`; ECDSA key generation and RSA
2048 are well under 1 s). All three are plain script tests that run in parallel with the other script tests in
`test-scripts`; each fits `script * 120`. No e2e case, no VM run, no package build, no network: the checkpoint runs
`just e2e` and the VM suite. The builder measures all three and records the times in PROGRESS.md.

**Environment.** Needs `python3`, `openssl`, `journalctl`, `unshare` (all present: `openssl` and `journalctl` are in
`/usr/bin` here; the unshare overlay and the `1000` mapping were shown to work by F185, whose PROGRESS entry and contract
give the command). `modutil` may be a stub. A missing tool fails naming it, never skips. `journalctl --directory` over a
fixture journal needs `systemd-journal-remote` or `systemd-cat`-free means to write one; the builder's first step runs the
smallest command that shows which way works here (for example `systemd-journal-remote` on a export-format file) and records
it; if no way works in the dev container, the journal query is checked by its field and match names against `docs/audit.md`
and the code and the builder says so in PROGRESS.md (a person runs the real query in acceptance 19). If a non-VM check
that this contract promises turns out impossible, it is amended with the evaluator's approval, not dropped.

  runs the `console` blocks on the real CLI → exit 0, output equal to the document's, `-add` for the installed module path
