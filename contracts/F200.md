# F200 — VM group: the virtual sensor, polkit with the override, a signature by finger and the four fallbacks

## Scope

Built here, all in the Ubuntu 26.04 VM target, **full mode only** (SPEC, end-to-end scope; acceptances 18 and 19):

- **A `vm-fingerprint-*` group** in `e2e/vm/cases.list`, run by a new root script (`e2e/vm/fingerprint.sh`, with a lib and a user-side
  script as `snap.sh`/`silent.sh` have) that `e2e/guest.sh` calls through `phase_runs` (new `vm-fingerprint-*` in `e2e/select.sh`
  `case_group`) and that `e2e/vm/run.sh` times as a step. It is the first VM group that runs a real polkit
  authentication with a real `fprintd`, so it works on its own accounts: a test user with a password, never the harness's `ubuntu`
  account.
- **The ids** (the builder may split one where one judgement needs it; every one must be reported `run` in full mode):
  `vm-fingerprint-stage` (the virtual sensor is up and a finger is enrolled; the versions are recorded),
  `vm-fingerprint-polkit-finger` (enrolled finger approves a `pkexec` or `pkcheck`+`pkttyagent` authentication),
  `vm-fingerprint-polkit-unenrolled` (an unenrolled finger falls back to the password, which approves),
  `vm-fingerprint-polkit-timeout` (no touch for 10 s falls back to the password, which approves),
  `vm-fingerprint-sudo` (password only, no fingerprint prompt),
  `vm-fingerprint-negative` (no touch, no password: stays unapproved),
  `vm-fingerprint-disabled` (after `disable`, polkit no longer offers the finger),
  `vm-fingerprint-sign` (a Custodio signature approved by the finger, verified with `openssl`, with its journal entry), and
  `vm-fingerprint-fallback-module`, `-daemon`, `-reader`, `-finger` (each goes straight to the password).
  Their container twins do not exist (`e2e/cases.list` is not changed). `e2e/vm/skip.list` and `omitted.list` are not given these ids.
- **Staging** (as `docs/findings/acceptance-6-fingerprint.md` and the report's method): `fprintd`, `libpam-fprintd` and `libfprint`
  come from Ubuntu's signed archive with `apt-get` inside the guest (no other source; installed in the guest only, never a
  dependency of the package); the `fprintd.service` drop-in with `FP_VIRTUAL_DEVICE`, `RuntimeDirectory` and `--no-timeout`;
  `custodio fingerprint enable`; enrolling a finger by the virtual socket (`SCAN <id>` and close). The harness's own
  `/etc/pam.d/polkit-1` (pam_permit, written by `run.sh` for the test agent) is a foreign file for `enable`: the group sets it aside,
  works on the real layout, and puts it back, from an exit trap too. Same for the harness's passwordless `sudo` rule: it is out of the
  way only for the `sudo` case, restored by the same trap, and the host's own commands (`vm.sh run`) never depend on it while it is
  away (the builder shows how, e.g. a test user's `sudo -k` run through `su`). Packages added inside the VM and their versions are
  recorded (polkit, fprintd, libfprint, libpam-fprintd: new keys in `vm.full.record`, `unknown` fails the run, as the snap keys).
- **Staging failure is a failure.** If the virtual sensor cannot be staged (no virtual driver in libfprint: the library lacks
  `FP_VIRTUAL_DEVICE`; no socket; enrolment fails), the group fails; no skip path exists for it (acceptance 19). In `lacking`
  mode the group is reported skipped with a reason, as `snap-*` is (the SPEC puts the group in `full`).
- **The judge**: `e2e/vm/fingerprint.py`, takes the evidence files the guest writes (per case: the transcript of the polkit
  agent or `pkexec`, the events of the driver, the sudo transcript, the journal, the signature and certificate/key, the process and
  unit state) and decides each case. `scripts/test-e2e-vm-fingerprint.sh` runs it on fixture evidence: one accepted set and, per rule and per
  case, one broken fact that must be rejected with the rule named (including a finger prompt shown by `sudo`; a negative control
  that was approved; a timeout case that fell back before 10 s or never; a fallback case that offered the finger; a signature that does
  not verify; a journal entry missing or extra; a version unknown; a staging record that says skipped). It also fails if the
  group's case ids differ from `e2e/vm/cases.list` (the same check `scripts/test-e2e-vm-cases.sh` makes for other groups: that script
  learns the group, its count and "skipped is refused in a full run"). Nothing tests the guest scripts against a stub: the run proves them.
- **Left to other features:** the container group (F199, done), `doctor` (F203), documents, the manual acceptance; the release run of
  the whole VM suite and the package gates at the checkpoint.

Environment, to be checked by step 1 with the smallest commands and recorded in `docs/findings/F200.md`: `/dev/kvm` exists in the dev
container (checked here), and VM runs already work (F168). Unknown until run: that the signed archive serves `fprintd`/`libpam-fprintd`
to the guest with `--no-recommends`, and whether `libfprint-2-2` in the image has the virtual driver (`grep -c FP_VIRTUAL_DEVICE` on the
library; the finding of 2026-11-01 says yes). If the archive or the driver is missing the group still fails (acceptance 19); a
deviation is for a person, not decided here. How `sudo`'s PAM stack, polkit's agent (`pkttyagent` in a pty, reusing `e2e/cli-pty.py`
and `e2e/cli-lib.sh` where they fit) and the 10-second timeout (`pam_fprintd.so ... timeout=10`) are driven and observed is for the builder
to decide; the observations must be the ones that would differ if the finger were not tried (the prompt text of the agent or of `sudo`,
fprintd's journal and D-Bus state, the scan being consumed) and not only the final status.

Costs (estimates; the builder measures them and records in PROGRESS.md). The judge test: Python on small fixtures, under 2 s, in
`test-scripts`, parallel with the other script tests; the `test-e2e-vm-cases.sh` additions are a few `cmp`/grep runs, under 1 s. The group in
the guest is inherently sequential (one fprintd, one sensor, one `/etc/pam.d`): apt install of the three packages 15–40 s; the
timeout case 10 s plus a margin; the other polkit/sudo cases 2–5 s each; the daemon, reader and module fallbacks restart fprintd and
restore it, about 5 s each; the signature 5 s. Estimated 100–180 s inside the guest. `just e2e-vm-cases full 'vm-fingerprint-*'`
still pays the VM's image, boot, copy, install and tools steps (about 5 minutes of the 503 s measured in F168), so one run is about
8–10 min and fits a command (limit 30 min) and a session. `budgets.tsv` has vm/full at 580 s, ~15% over 503 s: with this group in the
full suite the full run will not fit; the builder measures the group's step (`vm.full.phases.tsv`) and asks for a bigger budget in
BLOCKED.md; the group is not trimmed and no case waits with a fixed `sleep` (waits are on a condition: the socket, the unit state,
the agent's prompt, the journal line), except the 10-second timeout, which is the thing under test and is awaited on the agent's event
with a bound.
No step runs the whole `verify`: step 6 is the one run of the group (the feature "runs the group alone once"); the loop runs the `verify`.

## Steps

- [ ] Environment and plan: in a VM started by the existing tooling (one command), show the three facts (the packages install
      from the archive with the versions; the library holds `FP_VIRTUAL_DEVICE`; a drop-in socket accepts `SCAN`) and record
      them in `docs/findings/F200.md` (a subagent may read the report and the finding; conclusions only).
- [ ] Write `e2e/vm/fingerprint.py` (judge) and `scripts/test-e2e-vm-fingerprint.sh` with the accepted fixture set and one rejected
      fixture per rule and case; it fails first, then passes; add it to the `test-scripts` recipe and the `shell-scripts-test` list where the
      F179 scripts are.
- [ ] Wiring, no guest logic yet: the ids in `e2e/vm/cases.list`; `case_group`/`phase_runs` in `e2e/select.sh`; the call in
      `e2e/guest.sh`; `run.sh` step time, record keys and the full-only rule (skipped in `lacking`, refused skipped in `full`);
      `scripts/test-e2e-vm-cases.sh` and `scripts/test-e2e-select.sh` learn the group. `scripts/test-e2e-vm-cases.sh` and
      `just e2e-vm-check full 'vm-fingerprint-sign vm-fingerprint-fallback-module vm-fingerprint-fallback-daemon vm-fingerprint-fallback-reader vm-fingerprint-fallback-finger'` pass.
- [ ] Staging and the polkit cases: the set-aside/restore with its exit trap, install, drop-in, `enable`, enrolment, versions in the record,
      the hard failure when staging fails; then `vm-fingerprint-stage`, `-polkit-finger`, `-polkit-unenrolled`, `-polkit-timeout`,
      `-negative`. Run `just e2e-vm-cases full 'vm-fingerprint-*'` (one command) and fix.
- [ ] The `sudo` case (the harness's passwordless rule out of the way and back), `vm-fingerprint-disabled`, `vm-fingerprint-sign`
      (openssl verification, journal entry; no key material in the evidence kept), and the four fallbacks (module removed or
      disabled, daemon stopped and masked, virtual-device drop-in removed, enrolled finger deleted; each restored afterwards).
- [ ] Final: `just quick`, `scripts/test-e2e-vm-fingerprint.sh`, `scripts/test-e2e-vm-cases.sh`, `scripts/test-e2e-select.sh`; run
      `just e2e-vm-cases full 'vm-fingerprint-*'` once (the only full-group run of this feature) and record each step's seconds and the
      versions in PROGRESS.md; then the `verify`'s `just e2e-vm-check` line.

## Evidence

- Staging, and a failure to stage fails (acceptances 18, 19) → case `vm-fingerprint-stage` of `just e2e-vm-cases full 'vm-fingerprint-*'`:
  the library holds the virtual driver, the socket exists while the device is open, `fprintd` lists a device, a finger is
  enrolled, `custodio fingerprint enable` wrote the override; run → passes. The judge rejects an evidence set whose staging
  facts are missing or say skipped, and `scripts/test-e2e-vm-cases.sh` rejects `vm-fingerprint-*` reported `skipped` in a full run
  → `scripts/test-e2e-vm-fingerprint.sh`, `scripts/test-e2e-vm-cases.sh`.
- The enrolled finger approves a polkit authentication → `vm-fingerprint-polkit-finger`: the agent/`pkexec` ran, the finger prompt
  was shown, the scan was sent and the authentication completed with no password typed; judge control: an approval with a typed
  password or without the finger prompt is rejected.
- An unenrolled finger falls back to the password, which approves → `vm-fingerprint-polkit-unenrolled`: the match failed (fprintd's
  state or the agent's message), the password prompt followed, the right password completed it; control: a wrong password does not.
- No touch within 10 seconds falls back to the password, which approves → `vm-fingerprint-polkit-timeout`: the password prompt came after
  the 10-second wait (not at once, not never), then the password completed it; control: a fall-back before 10 s or no
  fall-back is rejected by the judge.
- `sudo` asks for the password only and shows no fingerprint prompt, with the harness's rule out of the way → `vm-fingerprint-sudo`: the
  transcript holds the password prompt, no fingerprint text, and the sudo really authenticated (the rule was not in effect: `sudo -k` then
  the run needs the password); the rule is back afterwards; control: a transcript with a fingerprint prompt, or a run without a password
  prompt, is rejected.
- A negative control (no touch, no password) stays unapproved → `vm-fingerprint-negative`: the authentication did not complete and the
  action was not performed (a file or id the approved case leaves is absent); control: an approved record is rejected.
- After `disable` polkit no longer offers the finger → `vm-fingerprint-disabled`: `/etc/pam.d/polkit-1` is absent (the harness's file
  back or none, as the case sets), a fresh authentication shows the password prompt only and consumes no scan; control: a prompt with the
  finger is rejected.
- A Custodio signature approved by the enrolled finger, verified with openssl, with its journal entry → `vm-fingerprint-sign`: a signature
  by the PKCS#11 module with a key of the test account, with the finger as the only authentication, `openssl` verifies it against the
  key's public part, and the journal holds one `signature made` entry for the key and uid (`custodiod` entries, none extra, none missing);
  controls: a signature that does not verify, a missing or extra journal entry, a password typed.
- Each fallback goes straight to the password → `vm-fingerprint-fallback-module` (module not loadable by PAM), `-daemon` (fprintd
  stopped and unable to start), `-reader` (no device: the virtual-device drop-in removed), `-finger` (the enrolled finger deleted): in each,
  the first prompt is the password, there is no wait of 10 seconds, no finger prompt, and the password approves; the state is restored
  after each; control: a case that offered the finger or waited the timeout is rejected.
- The run records polkit, fprintd, libfprint and libpam-fprintd versions (acceptance 18) → `vm.full.record` of the run has the four keys,
  none `unknown`, and `vm-fingerprint-stage` reports them; control: an `unknown` version is rejected by the judge fixtures.
- The judge's rules and the case list → `scripts/test-e2e-vm-fingerprint.sh` (accepted set passes, each broken fixture fails with the rule named, under 2 s),
  `scripts/test-e2e-vm-cases.sh` (group present, ids reported once, skipped refused in full, accepted in lacking) → pass.
- The group runs in the real VM once → `just e2e-vm-cases full 'vm-fingerprint-*'` → exit 0, every id `run`; `just e2e-vm-check full '<the five names>'` → exit 0
  (all five names match cases of the list). The group's step time goes to PROGRESS.md and the loop reads it against `budgets.tsv` (Scope, Costs).
