# F202 — `custodio doctor`: the command, its exit status and the three fingerprint checks

## Scope

Built here:

- The subcommand `custodio doctor` (parsed by hand like the others, no arguments; an extra argument is a usage error of F193's kind),
  registered in F193's command table with its help (what it does, that it is read-only, the exit status, an example) and in
  `packaging/custodio.1`. It refuses root with a two-line error, as `register` does. It prints one line per check
  (`ok` / `not ok` / `could not check` plus a short state) and, under every unsatisfied check, its fix. It never opens a polkit
  dialog, a password prompt or a browser and needs no root.
- A pure module (`doctor_decide`, no I/O) that takes observed values and returns, for each check, a state, its text and its fix, and the
  exit status. A second module (`doctor_cmd`) observes the real system (reads files, asks `net.reactivated.Fprint` on the system bus)
  and prints. Both join the custodio-cli list of the `mutants` recipe; no function is excluded.
- Check 1 (reader): `fprintd` lists a device → satisfied; no device → not satisfied with the fix; `fprintd` not installed → the missing
  piece, naming the package for the family (`fprintd` + `libpam-fprintd`; `fprintd` + `fprintd-pam`; `fprintd`), the family read as
  `enable` reads it (`family_from_os_release`; unknown family names all three). A bus that does not answer is "could not check" with the reason.
- Check 2 (enrolled finger): the person's enrolled fingers asked with `ListEnrolledFingers`. Fingers listed → satisfied;
  `net.reactivated.Fprint.Error.NoEnrolledPrints` → missing, fix names the desktop's enrolment (or `fprintd-enroll`); any refusal
  (`PermissionDenied` / "Not Authorized: net.reactivated.fprint.device.verify", the ssh case) or other error → "could not check" with
  the error's reason, **never** "missing". No reader or no `fprintd` → this check is "could not check" (nothing to ask), with that reason.
  The call must not raise a polkit prompt: the method is called with no interactive-authorization flag and the fake records that.
- Check 3 (fingerprint active for polkit), reading files only, in this order: (a) Custodio's override (`is_custodios`) — and whether its
  `include` resolves (vendor file exists and is a regular file): a missing vendor file is reported **first**, ahead of every other line
  of the output, as the most urgent problem with its fix, and makes the exit status non-zero; (b) someone else's `/etc/pam.d/polkit-1`
  with an uncommented `auth` line with `pam_fprintd.so` (`first_fprintd_auth_line`); (c) globally, with F197's per-family detection
  (`pam_has_fprintd` on `common-auth`, authselect `with-fingerprint`, `system-auth`/`sudo` on Arch), which says that `sudo` uses the
  finger too; (d) none (not active, fix: `sudo custodio fingerprint enable`). The combination F201 decided on — an override of
  Custodio's or someone else's with an active `pam_fprintd.so` auth line **and** `pam_fprintd` active in `common-auth` — is reported as a
  warning line under check 3 (it asks the finger twice, 20 s with no touch), with F201's fix: `sudo custodio fingerprint disable` when
  the file is Custodio's, else remove the file's `pam_fprintd.so` line or `sudo pam-auth-update --disable fprintd`. The warning does
  not change the exit status. It is decided from the same observed state, only on a system where `common-auth` exists.
- Exit status (SPEC Design 2): 0 unless a broken include; checks 1 to 3 otherwise never count, "could not check" of check 1 or 2 does
  not count either as they are the fingerprint's. The rule is in the pure module as one function and applies to every state of every
  check. Checks 4 to 6 belong to F203, which adds them to the same output and the same rule ("could not check" and not satisfied count
  there); this feature builds the rule with its inputs for them as "not yet observed" so F203 plugs in without changing it. Its own tests
  cover the rule over the three checks plus the broken include; F203 proves the rule with 4 to 6 (`doctor_acceptance.rs`).
- A seam: the existing `fixture-root` feature and `CUSTODIO_FIXTURE_ROOT` / `CUSTODIO_FIXTURE_EUID` (files read under the root, uid
  overridden). No new variable is needed unless the user name for `ListEnrolledFingers` needs one; if it does, it is added to the list
  in `scripts/check-fixture-seams.sh`, `scripts/test-check-fixture-seams.sh` and the `fixture-seams` recipe's loop, and its negative
  control. The bus is reached through `DBUS_SYSTEM_BUS_ADDRESS`, which is not a seam.

Left to other features, not proven here:

- Checks 4 to 6, the whole-command acceptance test (acceptance 6) and the six-check output as a whole: F203. Doctor on every target in
  containers and "leaves /etc and home unchanged" on real systems: F204. Completions: F205. User documents: F207.
- A real fprintd, a real device and a real ssh session: not available in the dev container. The "Not Authorized" refusal is proven
  against a fake on a private bus that returns that exact error name and text (the report's text), as F197's fake does; the ssh
  session itself belongs to a person's run in `docs/manual-acceptance.md`, which F207 owns.

Environment, checked in the dev container (as in F197): `dbus-daemon` and `dbus-run-session` 1.16.2 exist, and
`crates/custodio-cli/tests/fixture/mod.rs` and `tests/fingerprint.rs` already start a private bus with a fake
`net.reactivated.Fprint`; doctor's tests reuse that fake (moved to the fixture module if shared, one place) with added methods
`GetDevices` (zero, one, error), `ListEnrolledFingers` (fingers, `NoEnrolledPrints`, a refusal, a slow answer). The uid is 1000, not root.

Sizing: five steps, no split.

Costs (estimates from `tests/fingerprint.rs` and `fingerprint_decide.rs`; the builder reports measured times in PROGRESS.md):

## Evidence

- Refuses root, two lines, writes nothing → `doctor_reader`: with `CUSTODIO_FIXTURE_EUID=0` the binary exits non-zero, standard error
  has at least two lines and nothing on standard output; the fixture tree is byte-identical afterwards → pass. A non-root run exits as
  the checks dictate (control).
- Read-only, no dialog, no prompt, no browser → `doctor_reader` and `doctor_polkit`: every case compares the fixture tree before and
  after (identical); the fake bus records the calls: only `GetDevices` and `ListEnrolledFingers`, with no interactive-authorization
  flag set, no `Claim`/`VerifyStart`; the process is run with no terminal and an empty `PATH` containing no browser, and finishes
  within a bound → pass. A doctor that claimed the device or asked polkit fails the recorded-calls assertion.
- One line per check with a state, the fix under each unsatisfied one → `doctor_reader`/`doctor_polkit`: each case asserts the state
  word and the fix text of its check; a satisfied check has no fix line → pass.
- Check 1, three states → `doctor_reader`: one device → ok; zero devices → not ok with its fix; no `fprintd` (no service file, no
  bus name) → not ok, names the package for each of Debian-family, Fedora-family, Arch and unknown (all three) os-release; bus not
  answering → could not check with the reason → pass. A check that always says ok fails the zero-device and missing cases.
- Check 2 → `doctor_reader`: fingers listed → ok; `NoEnrolledPrints` → missing, fix; "Not Authorized:
  net.reactivated.fprint.device.verify" → state "could not check", the line holds the reason, and the word "missing" does not appear
  on that line; another error, and a slow answer past the bound → "could not check"; no reader → "could not check" naming it →
  pass. A doctor that maps every error to missing fails the refusal case.
- Check 3 states → `doctor_polkit`, one fixture root each: Custodio's override with its vendor file → active through the override
  (include resolves); Custodio's override with the vendor file missing, and with it not a regular file → broken include, the first
  line of the whole output, with its fix, exit non-zero; someone else's file with an `auth ... pam_fprintd.so` line → active through
  that file; the same file with `pam_fprintd.so` only in a comment or `-auth`/`account` line → not active (control); globally on each of
  Debian (`common-auth`), Fedora (`with-fingerprint`), Arch (`system-auth`, `sudo`) → says `sudo` uses the finger too; no override,
  nothing global → not active with `sudo custodio fingerprint enable`; a vendor-file-less root with no override → not a broken include
  → pass. Each expected line fails if the state is mis-read (e.g. one that treats a missing vendor file as ok).
- The F201 combination → `doctor_polkit`: Custodio's override plus `pam_fprintd` in `common-auth` → warning with
  `sudo custodio fingerprint disable`; someone else's file plus `common-auth` → warning with the two other fixes; each alone → no
  warning; the warning with exit status 0 (it does not count) → pass.
- Exit-status rule for these checks → `doctor_reader`/`doctor_polkit` and unit tests of the function: checks 1, 2, 3 unsatisfied, in any
  mix, "could not check" on 1 or 2, and the combination warning → 0; a broken include with everything else satisfied, and with
  1 to 3 unsatisfied → non-zero. A function that counts check 1 or ignores the include fails. The part of the rule that concerns checks
  4 to 6 is proven by F203 (`doctor_acceptance.rs`), per Scope.
- Help → `tests/help.rs` (existing): `custodio doctor --help` and `custodio --help` print it on standard output, status 0; every
  command and option in the help is in `packaging/custodio.1` and the other way round; an extra argument is a usage error (status 2,
  standard error, says how to get help) → pass. The man page is checked by that parity test, not by wording.
- Fixture seam covered → `scripts/test-check-fixture-seams.sh` (its negative controls) and `just fixture-seams` → pass: the
  release binary has none of the seam's names, a build with the feature does.
- Modules in `mutants` → `just mutants-diff F202` → 0 missed in `doctor_decide` and `doctor_cmd`.
- Whole → `just quick` green.

## Amendments

- Scope, bound on the wait (evaluator note 1): doctor waits at most 1.5 s for each question it asks `fprintd` (`GetDevices`, then `ListEnrolledFingers`), so at most 3 s for both, never D-Bus's own 25 s. The slow-answer case of `doctor_reader` has the fake answer after 3 s and so takes about 1.5 s; the cost row's "2 to 4 s" holds because the tests run in parallel. A question that is not answered in time is "could not check" with that reason.
- Scope, where each question goes: `ListEnrolledFingers` is a method of the device object (`net.reactivated.Fprint.Device`), asked at the first path `GetDevices` returned, with an empty user name (fprintd takes the caller's); no `Claim`.
- Check 1, "not installed" versus "bus not answering" (evaluator note 3): `fprintd` is not installed only when there is **no service file** (`usr/share/dbus-1/system-services/net.reactivated.Fprint.service`) **and** the bus says the name has no owner (`ServiceUnknown`). A name that is there but does not answer in time, an error from it, a name with no owner but a service file, or a bus that cannot be reached are "could not check" with the reason. The tests use these two signals in opposite combinations (no file + slow owner; file + no owner), so a doctor that confuses them fails one.
- Evidence, "no interactive flag" (evaluator note 2): the fake reads `ALLOW_INTERACTIVE_AUTH` from the message header itself and records it; one control case calls the fake with the flag set and asserts it is recorded, so the assertion can fail.
- Evidence, fixtures (evaluator note 5): the root builder and the global forms (Debian `common-auth`, Fedora authselect, Arch `system-auth`/`sudo`) are the ones of `tests/fingerprint.rs`, moved to a shared test module used by both.
