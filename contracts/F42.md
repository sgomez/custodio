# F42 — Install-time check that the system bus provides ProcessFD

## Scope
One POSIX shell check, run by each format before its package changes anything, plus `just test-scripts`.

Built here:
- The check. It asks the running system bus for its own connection credentials
  (`org.freedesktop.DBus.GetConnectionCredentials` on `org.freedesktop.DBus`) and looks for `ProcessFD` in the reply. It tests
  the capability only: never the daemon's name, version or the distribution. Three outcomes:
  - bus answers with `ProcessFD`: exit 0, installation goes on;
  - bus answers without `ProcessFD`: non-zero exit, a message on stderr that names the missing `ProcessFD` support and
    points to `docs/install.md` (on Ubuntu 24.04: switch to `dbus-broker` and reboot);
  - no system bus running (no socket, or connection refused): exit 0 and a notice that the service will refuse to sign
    until a bus with `ProcessFD` runs. This is the proposed answer of the open question "Installing without a running bus".
- It runs in the pre-install hook of each format: deb `preinst` (for `install` and `upgrade`, not for `abort-*`), rpm `%pre`
  (install and upgrade), Arch `pre_install` and `pre_upgrade`. Nothing is unpacked at that point, so a refusal on deb and rpm
  leaves no Custodio file; it must make the package manager itself abort the installation, which is proven with the real tools
  (see Evidence), not assumed from the script's exit status. Arch is different (next paragraph). The hook does only this check; account, daemon-reload and the rest stay with F43/F44.
- One source of the check in the repository. Each format's script embeds it (a pre-install script cannot read packaged
  files), and a gate in `just check` fails if an embedded copy differs from the source.
- The package gates and lint lists that currently assume "no preinst / pre / pre_install" are updated for the new scripts
  (F36 limited the lifecycle files to the post scripts; this is an amendment of that, not a weakening: the gates still
  list every script and its content).
- `just test-scripts` (new recipe, part of `just check`).

Arch warns on the first installation and refuses on every upgrade or reinstall (decided by a person, option 2 of the F42
`BLOCKED.md`; evidence in `docs/findings.md`, "F42 — Does pacman stop an installation ..."). With the real `pacman -U`, libalpm
ignores the exit status of `pre_install`/`pre_upgrade` (it prints "command failed to execute correctly", installs, exits 0),
and a hook shipped in the package is loaded before the package is unpacked, so it cannot guard the package's own first
installation. So on Arch:
- `pre_install` and `pre_upgrade` run the same check and, when the bus lacks `ProcessFD`, print the refusal message loudly on
  stderr; the installation then goes on (the service refuses to sign at runtime anyway, so nothing is exposed). The scripts do
  not claim to abort.
- The package ships an alpm hook (`PreTransaction`, `AbortOnFail`) that runs the same check, so a transaction that upgrades or
  reinstalls an already installed Custodio is aborted with the message when the bus lacks `ProcessFD`. The hook runs the shared
  check (one source, embedded as for the install script; it is a file under `/usr/share/libalpm/hooks/` plus the check it
  runs, which is packaged like any other file and covered by the package gates, parity list and sync gate).
- SPEC.md and the F42 description in `features.json` say the installation fails on a bus without `ProcessFD`; they are not
  edited here (only a person edits them). For Arch the behaviour is the above; the wording difference is reported in
  `PROGRESS.md` for a person to reconcile.

Left for others: the rest of the lifecycle scripts (F43, F44), `docs/install.md` (F51), refusal inside a real Ubuntu 24.04
container with the `.deb` (F45 and later e2e; SPEC step 8), the runtime refusal in `custodiod` (done).

Query-tool note: the one-shot tools cannot know their own unique name, so the check asks for the bus's own credentials
(`org.freedesktop.DBus`) and reads `ProcessFD` only from a successful reply, never from an error text.

Open choice for the builder, decided within these limits: the query tool (`busctl`, `dbus-send` or another tool that is on
every target with a running bus; it must not add a package dependency that the dependency gate does not already allow),
and what happens when a bus socket exists but no query tool does. Decided: `busctl` first, `dbus-send` second; a present socket
with neither tool is refused. That case must not install silently as if the bus were
fine: it must either refuse with a message or use another tool, and the choice is recorded in the code and tested.

## Evidence
- Passes on a bus with `ProcessFD` → `just test-scripts`, case "private dbus-daemon": the container's `dbus-daemon` (1.16)
  is started on a temporary socket and the check, pointed at it, exits 0 with no refusal message. The test first asserts the
  daemon really returns `ProcessFD` (so the case cannot pass by accident).
- Refuses a bus without `ProcessFD` → `just test-scripts`, case "bus without ProcessFD": a bus or stub that answers
  the credentials call with uid and pid but no `ProcessFD`; exit status non-zero, stderr contains `ProcessFD` and
  `docs/install.md` and the Ubuntu 24.04 / `dbus-broker` hint. The same stub with `ProcessFD` added passes (control).
- Names no daemon or distribution → `just test-scripts`, case "capability not name": the stub without `ProcessFD` is
  run while its reported daemon/`/etc/os-release` look like `dbus-broker`/Debian 13, and still refused; the one with it is
  accepted when presented as `dbus-daemon` 1.14 on Ubuntu 24.04. `grep` of the check source finds no `os-release`, `lsb_release`,
  `dbus-broker` or `dbus-daemon` test.
- No bus → install anyway with a notice → `just test-scripts`, cases "socket absent" (the test sets `DBUS_SYSTEM_BUS_ADDRESS` to a
  nonexistent path) and "socket present, nothing listening": exit 0, output contains a notice that the service will refuse to sign until a bus with `ProcessFD` runs, and
  does not contain the refusal message. Default address: a test with `DBUS_SYSTEM_BUS_ADDRESS` unset
  asserts (by tracing which address the tool is given, via the recording stub tool) that the production check uses
  `unix:path=/run/dbus/system_bus_socket`, and that the variable, when set, overrides it.
- A bus that answers wrongly or cannot be queried is not treated as "no bus" → `just test-scripts`, cases "bus returns
  an error" and "socket present but no query tool": the behaviour chosen in Scope (refusal or fallback tool) is asserted,
  and neither exits 0 silently. A further case: the bus returns an error whose message contains the word `ProcessFD`; it must
  not count as capability present (the check reads `ProcessFD` only from a successful reply to the bus's own credentials, not from
  anywhere in the tool's output). The tool choice accounts for what a deb `preinst` can rely on (Essential and Pre-Depends
  packages only): the missing-tool case is a real one, and no new Pre-Depends/Depends is added without passing the dependency gate.
- A refusal really stops the install, in deb and rpm → `just test-scripts` (or a recipe it runs), real-tool cases using the
  real fixture packages from `just package` and the stub bus selected through `DBUS_SYSTEM_BUS_ADDRESS` (the same override the
  production check honours): `dpkg --root <tmp> -i` of the `.deb` (or a container if dpkg refuses to run unprivileged) and
  `rpm -i --root <tmp>` of the `.rpm`. With the bus lacking `ProcessFD`: the tool exits non-zero, its output
  contains the refusal message, and the target root holds no Custodio file (`find` over the root for the package's paths and
  `dpkg -L`/`rpm -q` report it not installed). Controls with the same package: with `ProcessFD` the install
  succeeds and the files exist; with no bus it succeeds and the notice is in the output.
- Arch behaves as decided in Scope → `just test-scripts`, real `pacman -U` of the `.pkg.tar.zst` in the Arch image built from
  `packaging/lint/namcap.Containerfile` or a sibling, with the stub bus selected through `DBUS_SYSTEM_BUS_ADDRESS`. Bus lacking
  `ProcessFD`: (a) first installation exits 0, the package is installed and the output contains the refusal message; (b) a
  second `pacman -U` of the same package (reinstall) and of an N+1 package (upgrade) exits non-zero, prints the message, and
  leaves the installed files and `pacman -Q` version unchanged. Controls: with `ProcessFD` all three succeed; with no bus they
  succeed and print the notice. If the Arch image cannot be built offline the test is skipped only with an explicit message in
  `just test-scripts`, and `verify`'s evaluator run must have executed it.
- Fails before anything changes → `just test-scripts`: the refused run is made with recording stubs for `systemd-sysusers`,
  `systemctl`, `deb-systemd-invoke`, and the log is empty; and `packaging` fixture test: the pre-install script is the
  first thing the hook does and runs before any other command.
- Same check in the three formats → gate in `just check` (sync gate) and its own test: it fails when one embedded copy is
  edited by one byte, and passes on the tree. Fixture-package test: scripts extracted from the real fixture `.deb`
  (`preinst`), `.rpm` (`%pre`) and Arch `.INSTALL` (`pre_install`, `pre_upgrade`) each give refuse / pass / notice on the three
  buses, with deb `install` and `upgrade` args and rpm argument 1 and 2; deb `abort-upgrade` does not run the check.
- POSIX shell → `shellcheck` through `just lint` (the files are found by the shebang list) and the check is run with
  `dash` in `just test-scripts` (not only bash).
- `just test-scripts` exists and is part of `just check` → `just --show test-scripts`, and `grep` of the `check` recipe's
  dependencies; removing the recipe makes `just check` fail.
- Package gates still hold → `just check && just test-scripts && just package && just package-lint` (the `verify` command)
