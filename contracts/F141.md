# F141 — End-to-end cases: upgrade between M4 builds keeps kinds

## Scope
New cases `upgrade-kinds-*` for the second part of SPEC acceptance 5 ("Upgrading from one M4 build to the next keeps keys, owners, certificates and kinds"), against the
real packages in the debian13 container. They ride on the **one** existing upgrade run of `e2e/upgrade.sh` (package N installed over by N+1 with the target's `install.sh`,
id prefix `upgrade`): no second install, no new container, no new step in `guest.sh` (`upgrade-kinds-*` stays in the `upgrade` group of `select.sh`; the pattern is
distinct from `upgrade-oldpath-*`, and the old-path run, which is not "N to N+1", reports none of them). The keys already seeded by that run are the subjects: alice's `rsa1`
and `ec1`, bob's `rsa1` (same id, other owner, replaced certificate) and `bobonly`. What those keys' kind is in each mode is fixed by the mode, and is judged **absolutely**
(not only "after == before"), so a run where every key silently got the same wrong kind fails: `swtpm` and `lacking` → `tpm`, `none` → `encrypted-host`.

Cases (each reported exactly once; the builder may add one):
- `upgrade-kinds-before`: before the install, `ListKeys` as each owner (and `custodio list`) gives every seeded key the kind of the mode, an RSA and a P-256 key among them (alice's
  pair), and the owner of each record is its account.
- `upgrade-kinds-kept`: after the install, `ListKeys` per owner and `custodio list` give the same ids, the same owners, the same kinds and the same certificates (DER, byte-for-byte,
  including bob's replaced one) as before; the kind text of the CLI is unchanged.
- `upgrade-kinds-signs`: the signatures the existing round makes after the upgrade (alice RSA and ECDSA, bob's keys; no extra polkit call is added) leave their journal entries with the
  kind of the mode for the key signed, one per signature, and the listing after the round still gives the same kinds.
- `upgrade-kinds-tpmbound`: the kind `encrypted-tpm`. Reported **skipped in every mode** (the container cannot make that kind: `SPEC_DEVIATIONS.md` F134, `docs/findings/F134.md` last
  section). This feature extends the F134 entry to F141 (own commit with the contract amendment, the evaluator approves it, a person reviews it). Its cover instead is a
  integration test, if none exists: step 2 looks for one that restarts the service object over the same state directory with a key of each of the four kinds (credential double for the
  TPM-bound one) and checks ids, owners, kinds and certificates; if none exists, the builder adds a small one (`kinds_suite` style, a few seconds, parallel like the others) and names it in
  the skip reason. Real `systemd-creds` is not run for it; the builder does not claim the TPM-bound half proven end to end.

Already proven elsewhere and not repeated: keys, owners and certificates survive (`upgrade-state-unchanged`, `upgrade-keys-listed`, `upgrade-signs-with-polkit`, F48/F96, still run by
the verify and must still pass); version/binary/no manual step (the other `upgrade-*` cases); the old-path upgrade (F61); the upgrade from an M3 build (SPEC acceptance 9, other
feature); the same kinds' signing (F134). Package gates and `just e2e` as a whole run at the checkpoint.

**Placement and accounting.** The ids go in `e2e/targets/debian13/cases.list` (the kind depends on the TPM, SPEC end-to-end scope), not in `e2e/cases.list`. `upgrade.sh` runs on every
target, so it must report `upgrade-kinds-*` only where the target lists them (the other targets' accounting must not see an unlisted case); the builder decides how and a host test
proves it. `upgrade-kinds-tpmbound` is in `skip.list`; `check-cases.sh` refuses a skip of the other three in any mode and a run of `upgrade-kinds-tpmbound`.

**Negative controls.** Host (`scripts/test-e2e-upgradekinds.sh`, no container, in the justfile script-test list; judgement functions in `e2e/upgradekinds.py`, python3 `-I`, functions of
files): they accept a good record per mode and reject: a kind different from the mode's before the install, a kind changed by the upgrade (every pair), an id or owner missing/added/changed,
a changed certificate, a CLI row whose kind text differs, a journal entry with another kind or a missing/double one, and a run in which all keys have the same wrong kind (the absolute
check). Also placement/accounting rules above, and that the mutation of `upgrade.sh` leaving the kinds judgement out makes the host test fail (a stub-driven run of the script, as
`test-e2e-upgrade.sh` does). Guest: no separate control beyond the absolute kind and the host rejections; the kind is read from the product's own `ListKeys`.

**Cost.** Host test: under 5 s, parallel with the other script tests. Guest: three or four extra `ListKeys` rounds per owner (no polkit, ~0.3 s each), one `custodio list`, a journal
read; no new signature and no new import. Estimated +3–6 s on the upgrade phase in each mode; `just e2e-cases debian13 'upgrade-*'` stays at about its present time (the builder measures
the phase before and after in PROGRESS.md; the existing upgrade run is the one costing time, since it installs twice-over packages). The new integration test (if added): under 10 s,
parallel. Nothing goes to `e2e/cases.list`. The full debian13 run grows by about 5 s, on top of F135–F140's growth noted in PROGRESS.md; the builder sums it there and asks in BLOCKED.md if
a measured run passes the budget (that run is the checkpoint's).

**Environment.** The verify runs `upgrade-*` in `swtpm` (default) and `E2E_TPM=none`; `lacking` is run by the builder as well, and the contract expects `tpm` there (deviation F134). The
probe is the first guest run itself (`swtpm` does not run in the dev container); the dev container does the host tests and `cargo test`. Size: five steps.

      times (phase before/after) in `PROGRESS.md`.
- [ ] `just quick`; PROGRESS entry with the budget sum and the deviation reference.

## Evidence
- Kinds of the seeded keys are the mode's → `upgrade-kinds-before` (`just e2e-cases debian13 'upgrade-*'` in `swtpm`, `none`, `lacking`) → `tpm`, `encrypted-host`, `tpm` for an RSA and a P-256 key, owners right.
- Upgrade N→N+1 keeps kinds, owners, certificates → `upgrade-kinds-kept` (same runs) → identical ids, owners, kinds, DER certificates, CLI kind text after the install.
- Kinds are not lost on use → `upgrade-kinds-signs` (same runs) → one journal entry per signature after the upgrade with the mode's kind; kinds unchanged after the round.
- TPM-bound kind → `upgrade-kinds-tpmbound` skipped (reason names the deviation) + the restart/reload integration test named in the reason (`cargo test -p custodiod --test <name> --locked`) → four kinds survive over the same state directory.
- Existing upgrade cases still pass → the verify's `upgrade-*` selection in both modes → all `upgrade-*` cases pass.
- A test can fail → `scripts/test-e2e-upgradekinds.sh` (in `just quick`) → good records accepted, each bad record and the omitted-judgement mutant rejected; placement/accounting rules enforced.
