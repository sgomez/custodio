# F22 — C_Login and C_Logout as no-ops

## Scope
Replaces the `unsupported::Login` and `unsupported::Logout` stubs with real functions. The file-size
gate of `scripts/check-files.sh` counts tokens (bytes / 4, max 5000), and `ffi.rs` and
`ffi/tests.rs` are close to it, so new code goes in new files: the two FFI functions in
`src/ffi/login.rs`; unit tests in `src/ffi/tests/login.rs` and `src/module/tests/login.rs`;
integration scenarios in `tests/cryptoki/login.rs` (parent tests) and `tests/cryptoki/login_child.rs`
(child scenarios), the pattern of `multipart*.rs`. Other changes: the function-list entries in
`ffi.rs`, a read-only session check in `module.rs` (no new state: `git diff` of `module.rs` adds no field
to `State` or `Session`), `unsupported.rs` (both stubs removed), and the test harness:
`tests/cryptoki/parent.rs` gains a count of every method call to `BUS_NAME` (today its monitor
records only `Sign`), and the fake backend gains a `list_certificates` counter.

Two existing expectations change because the functions are no longer stubs: the `C_Login` assertion
in `ffi::tests::function_list_is_complete_and_null_checked`, and the assertion in the `unsupported`
child scenario (`tests/cryptoki/child.rs`, run by `everything_else_is_not_supported`) that
`session.login(User, None)` returns `FunctionNotSupported`; login is removed from that list.

Behaviour, all of it stateless:

- `C_Login(session, user, pin, len)`: the session is checked first. Not initialized →
  `CKR_CRYPTOKI_NOT_INITIALIZED`; unknown handle → `CKR_SESSION_HANDLE_INVALID` (this is the
  "PKCS#11 code" for an invalid session, and it wins over the user type). Then by user type:
  `CKU_USER` and `CKU_CONTEXT_SPECIFIC` → `CKR_OK`; `CKU_SO` → `CKR_SESSION_READ_ONLY_EXISTS` (the
  PKCS#11 code for an SO login while only read-only sessions exist, which is every session here;
  the spec's proposed default); any other value → `CKR_USER_TYPE_INVALID`.
- The PIN pointer and length are never read, not even to check for NULL: a NULL, empty, huge or
  dangling pointer with any length gives the same result. No `CKR_ARGUMENTS_BAD`, no copy, no
  field, no log line, no error text containing it. The module does not contact the service or
  polkit.
- `C_Logout(session)`: valid session → `CKR_OK` (also without a previous login, since Firefox calls
  it first); invalid → `CKR_SESSION_HANDLE_INVALID`; not initialized →
  `CKR_CRYPTOKI_NOT_INITIALIZED`.
- Interim rule for the open question, recorded in `docs/decisions.md` (the one step that writes
  it): a repeated `C_Login` returns `CKR_OK` every time (never `CKR_USER_ALREADY_LOGGED_IN`), and
  `C_GetSessionInfo` keeps reporting `CKS_RO_PUBLIC_SESSION` before and after a login or logout.
  Both are the tolerant choice: no client sees a login error, and the reported state
  is never an error. The entry says to settle it by the manual acceptance clients (SPEC open question).
- A login does not touch the sign state: an open `C_SignInit` operation (single or multi-part)
  survives `C_Login`/`C_Logout` unchanged, and no operation starts or ends.
- Token flags, `CKA_ALWAYS_AUTHENTICATE` and mechanism lists are not changed. Tests pin them.

Left for other features: Miri/ASan/fuzz coverage of C_Login: F23; the audit journal, e2e with `pkcs11-tool` or a client that logs in
(`just e2e`), the manual acceptance that settles the open questions. Real PIN semantics are out of
scope for the milestone.

The feature is five steps; no split needed.

## Evidence
- `C_Login` with `CKU_USER` and `CKU_CONTEXT_SPECIFIC` returns `CKR_OK` with NULL, empty and
  arbitrary PIN → ffi unit test `login_accepts_any_pin` (6 combinations, plus length 0 with a
  non-NULL pointer and a non-NULL pointer with length 0) → every call `CKR_OK`.
- The PIN is never read → ffi unit test `login_never_dereferences_the_pin`: a dangling non-NULL
  pointer (address 1) with length 1 000 000, and NULL with length 5 → `CKR_OK` (not
  `CKR_ARGUMENTS_BAD`). The `CKR_OK` result is the proof that no
  `CKR_ARGUMENTS_BAD` check reads or tests the pointer; Miri/ASan runs are F23.
- The PIN is not stored, forwarded or logged → `grep -rniw "pin\|ppin" crates/custodio-pkcs11/src | grep -v tests`
  prints nothing (no match at all; today it is already empty): the `C_Login` parameters are bound
  as `_pin_ptr`/`_pin_len` (`-w` does not match them) and no comment in non-test code uses the
  standalone word (the evaluator runs it); unit test `login_leaves_session_unchanged` takes the session's fields (slot,
  find state, sign state) and `C_GetSessionInfo` before and after a login with PIN
  `b"sentinel-pin-7731"` and asserts they are equal, and that the `Debug` text of the sign state
  contains neither the text nor its byte list `[115, 101, ...]` → equal and absent. No `Debug` derive is added to `State` or `Session`.
- Does not contact the service or polkit → integration `login_does_not_contact_service`: the
  monitor gains a count of every method call to `BUS_NAME` (it runs on its own thread, so the
  parent reads it only after it has stopped changing for 200 ms). Two child scenarios do the same
  setup (list slots, open a session, list objects); `login_baseline` stops there, `login_variants`
  continues with all login variants and a logout. Both children close their connections the same way, so the settled
  counts are comparable. The parent runs both and asserts the settled
  counts are equal, `f.asked() == 0`, and the setup count is above 0 (the counter works). No
  streaming runner and no marker are needed. Unit: `module/tests/login.rs` with the `Fake` backend
  asserts that its `signed` and `list_certificates` counters do not change across login and logout.
- Invalid session handle → ffi unit test `login_invalid_session`: handle never opened, and a
  handle closed after use, for `CKU_USER`, `CKU_CONTEXT_SPECIFIC` and `CKU_SO` →
  `CKR_SESSION_HANDLE_INVALID` each; before `C_Initialize` → `CKR_CRYPTOKI_NOT_INITIALIZED`.
  Same two cases for `C_Logout`.
- `CKU_SO` fails → `login_security_officer_fails`, valid session, with and without PIN →
  `CKR_SESSION_READ_ONLY_EXISTS`; an unknown user type (3, `CK_ULONG::MAX`) →
  `CKR_USER_TYPE_INVALID`. Failure leaves `C_GetSessionInfo` and the sign state unchanged.
- Repeated login → `login_twice_and_after_logout` (user, user, context-specific, logout, user,
  logout, logout) → `CKR_OK` for every call, never `CKR_USER_ALREADY_LOGGED_IN`.
- Session state per the interim rule → `session_state_does_not_change_with_login`: after each step
  of the same sequence `C_GetSessionInfo` reports `CKS_RO_PUBLIC_SESSION` and flags
  `CKF_SERIAL_SESSION` → equal to the value before any login. This test is the proof of the state; the M0
  session-info test only checks `CKR_OK` and is not counted as evidence.
- Rule recorded → `docs/decisions.md` has an entry titled for the repeated-login/session-state
  rule, with Decision, Why, Rejected bullets, mentioning the SO result; checked by the evaluator
  by reading it. `git diff` shows no other edit to decisions.md.
- `C_Logout` returns `CKR_OK` → `logout_is_ok` (without a previous login, after a login, twice in a
  row) → `CKR_OK`; integration `login_logout_cryptoki` calls `Session::login(UserType::User, None)`
  and `Session::logout()` through the `cryptoki` crate → `Ok`.
- Context-specific login via the real library → integration child scenario `login_variants` uses
  `cryptoki` only: `UserType::ContextSpecific` and `UserType::User`, each with `None`, an empty
  `AuthPin` and an arbitrary one → all `Ok`. The NULL-pointer-with-length and dangling-pointer
  cases stay in the unit tests, since `cryptoki` cannot build them. `UserType::So` → `Err` with `SessionReadOnlyExists`; invalid handle is covered only by the unit test
  `login_invalid_session` (`cryptoki` hands out no raw handle, and dropping a `Session` closes it);
  the integration scenario does not claim it.
- Token flags unchanged → unit test `token_flags_ignore_login` and integration
  `login_changes_no_flags`: `C_GetTokenInfo` flags and `C_GetAttributeValue` of
  `CKA_ALWAYS_AUTHENTICATE` before and after a login and logout are identical, flags have
  `CKF_LOGIN_REQUIRED` and `CKF_PROTECTED_AUTHENTICATION_PATH` clear, the attribute is
  `CK_FALSE`; the mechanism list is identical too → equal and clear.
- A signature after a login still asks polkit (acceptance 6) → integration
  `sign_after_login_asks_polkit` (both RSA and EC keys, polkit allowing): login `CKU_USER`, sign
  with `CKM_RSA_PKCS`/`CKM_ECDSA`, then `CKU_CONTEXT_SPECIFIC` login between `C_SignInit` and
  `C_Sign`, sign again, composed mechanism once → the signatures verify (existing independent
  verifier) and `f.asked()` equals the number of signatures: a login never replaces a check. A
  mutation that skips polkit after a login makes the count smaller and fails.
- A denial still fails after a login → integration `denied_after_login_still_fails` (polkit
  refusing): login, `C_SignInit`, `C_Sign` → `CKR_FUNCTION_FAILED` (the code the existing `denied`
  scenario asserts), no bytes written to the output buffer (pre-filled with 0xAA), and `asked()`
  increases with every attempt (2 attempts → 2, no cached result from a logout/login in between).
- A login mid-operation changes nothing → unit test `login_keeps_the_open_operation`:
  `C_SignInit`, `C_SignUpdate`, `C_Login`, `C_Logout`, `C_SignUpdate`, `C_SignFinal` all `CKR_OK`,
  and the input the fake backend recorded (`LAST_INPUT`) equals the one from the same sequence
  without the login calls. Integration `login_keeps_the_open_operation` does the same with an RSA
  key → the signature is byte-identical to the one made without the login calls (deterministic).
- Function list → the updated `function_list_is_complete_and_null_checked` asserts `C_Login` and
  `C_Logout` are non-NULL and no longer return `CKR_FUNCTION_NOT_SUPPORTED`; the stubs are gone
  from `unsupported.rs` (`grep -n "Login\|Logout" crates/custodio-pkcs11/src/unsupported.rs` → no
  match). The integration scenario `unsupported` passes with login removed from its list.
- No gate weakened → `just check && just test-integration` → both pass; no `#[ignore]`, no new
  `#[allow]` without a comment, `git diff` shows no deleted test; the only changed
