# F138 — End-to-end cases: the fallback kinds and what the CLI says

## Scope
New cases `fallback-*` for SPEC acceptance 6, first sentence and the CLI sentence: what the key's kind is after import, what `custodio import`
says about it, and that `custodio list` shows it, against the real service, CLI and package in the debian13 container. ("The keys sign as in 2"
is `sign-*` of F134, run in every mode; not repeated here.)

- **`none` (kind `encrypted-host`) is run end to end.** Alice imports an RSA 2048 and a P-256 `.p12` with `custodio import` (the F133 route:
  fixtures from `tpmkind-lib.sh`, own agent dir, both keys deleted at the end). Judged on the real outputs: the import output has exactly one
  `Storage:` line with kind `encrypted-host`, says the key is weaker and the reason "no TPM" (the words of `kind_text` in
  `crates/custodio-cli/src/lib.rs`), and does not say `tpm`/`encrypted-tpm`; `custodio list` shows the kind `encrypted-host` on the row of
  each key. Cases (each reported once; every id matches `fallback-*`): `fallback-host-import-rsa`, `fallback-host-import-ec`,
  `fallback-host-says-weaker-why` (the weaker/why text of both imports, judged apart from the kind line so a missing explanation fails alone),
  `fallback-host-cli-list`. The builder may add one.
- **`encrypted-tpm` ("lacking") cannot be run end to end, by the existing deviation.** `SPEC_DEVIATIONS.md` entry `F134` already names F138's
  `lacking` half: in the container the real `systemd-creds` never seals to a TPM, so with the F131 filter (RSAPSS removed) the keys are `tpm`,
  and with a real lack (`alg=0x1`) the import fails with `CredentialsUnavailable` (`docs/findings/F134.md`, last section). This feature
  touches that entry only to confirm it covers the F138 cases (its heading already says "also F138"; the builder edits it only if the wording
  of the cases needs it, in its own commit with the amendment). Cases `fallback-tpmbound-import` and `fallback-tpmbound-cli-list` exist and are
  reported **skipped in every mode** (`skip.list`, reason names the deviation and what covers the text instead); under `lacking` they are the
  skipped half of the verify. **Not claimed:** nothing here proves the `encrypted-tpm` text or list row end to end. What covers it: `storage_kind`
  in custodio-cli (F123: the text for each kind and reason, `encrypted-tpm` with the TPM-lacks reason), `kinds_suite` (F126, `encrypted-tpm`
  through a credential double) and `no_plaintext` (F127). The person who reviews the deviation judges whether this skipped pair is enough.
  `check-cases.sh` rejects a `fallback-host-*` skip in `none` (those must run there) and a `fallback-tpmbound-*` run is not possible by construction
  (if a mode ever reports one run, the judgement fails because the kind is not `encrypted-tpm`).
- **Modes.** `none`: the four host cases run, the two tpmbound cases skip. `swtpm`: all six skip (the key gets kind `tpm`, which F133 proves).
  `lacking`: all six skip (kind `tpm`, by the deviation). The skip reasons are on the debian13 `skip.list`; the ids are in
  `e2e/targets/debian13/cases.list`, not `e2e/cases.list` (outcome depends on the TPM mode, not the distribution).
- **Not proven here.** The journal naming the kind (SPEC Journal; F133 for `tpm`), failing TPMs (F139), upgrade keeping kinds (F141), package
  gates and the whole `just e2e` (checkpoint).
- **Placement.** A group `fallback` in `select.sh` (`fallback-*` before `tpm-*`... the builder places the pattern so no other group captures it),
  step after `pcr`, own keys deleted at the end, own agent dir, so counts and journal entries read by later steps are unchanged (the builder
  checks that by reading those steps, as F133/F137 did). May reuse `tpmkind-user.sh`/`tpmkind.py` helpers by parameterising the expected kind;
  `tpm-kind-*` judgements must stay as they are (its test still green).
- **Negative controls.** Host test `scripts/test-e2e-fallback.sh` (no container, in the justfile script-test list): the judgement accepts the good
  `encrypted-host` import and list output and rejects: kind `tpm`, kind `encrypted-tpm`, no `Storage:` line, two `Storage:` lines, a host line
  without "weaker", without the reason "no TPM", a list row without the kind or with another kind, a missing key row; `check-cases.sh` accepts
  the tpmbound skips in all modes and the host skips in `swtpm`/`lacking`, rejects a host skip in `none`; ids are in the debian13 list and not in
  `e2e/cases.list`. Also a guest control in the run: in `none` the kind seen by `ListKeys` (`owner-call.py list`) must be `encrypted-host`
  for both keys, so the CLI text is not judged against a mode that gave another kind (a wrong kind fails the run, the run is not vacuous).
- **Cost.** Host test: under 5 s, parallel with other script tests (default budget 60 s). Guest, `none` only: two imports and a list as alice
  (2–4 s each, F133/F134 figures), two deletes, judging in `python3 -I`; estimated 10–15 s of the phase, no new container, no new waits beyond the
  agent's `registered` line; the two imports run as background jobs joined with `wait` if the helper allows, else in sequence (they share one
  agent). `just e2e-cases debian13 'fallback-*'` estimated 40–60 s per mode (F133/F135 whole runs 42–68 s); in `swtpm` and `lacking` the phase
  does nothing but report skips. The full debian13 `none` run grows by ~10–15 s, `swtpm` by ~0; the budget (430 s, measured 360 s, plus
  F135 ~20 s, F136 ~22 s, F137 ~23 s in `swtpm`) is the one at risk: the builder notes the sum in PROGRESS.md and asks for more in BLOCKED.md
  if the measured run passes it. No `budgets.tsv` change expected for this feature.
- Size: five steps, one session each at most.

## Evidence
- With no TPM the kind is `encrypted-host` → `fallback-host-import-rsa`, `fallback-host-import-ec` (`E2E_TPM=none just e2e-cases debian13 'fallback-*'`)
  → the CLI's import output has one `Storage: encrypted-host` line for each key type; `ListKeys` says the same.
- `custodio import` says the key is weaker and why → `fallback-host-says-weaker-why` (same run) → both imports say it is weaker than a TPM key and
  that this machine has no TPM; the control: the judgement fails on a `tpm` output or on text lacking either part (host test).
- `custodio list` shows the kind → `fallback-host-cli-list` (same run) → each key's row shows `encrypted-host`.
- With a lacking TPM the kind is `encrypted-tpm`, the CLI says weaker and why, the list shows it → `fallback-tpmbound-import`,
  `fallback-tpmbound-cli-list` → reported **skipped** in `lacking` (`E2E_TPM=lacking just e2e-cases debian13 'fallback-*'`, 6 skipped, accounted) because of
  the `F134` deviation; the text per kind and reason is proven by `storage_kind` (F123), the kind by `kinds_suite` (F126). Not an end-to-end proof.
- Reported as skipped in a mode they do not apply to → the same `lacking` run and `swtpm`; host test on `check-cases.sh`: tpmbound skips accepted
  everywhere, host skip accepted in `swtpm`/`lacking`, refused in `none`.
- Each judgement can fail → `scripts/test-e2e-fallback.sh` → rejects each bad output listed, accepts the good.
- Keys signing as in 2 → `sign-*` (F134), not repeated.
- State left as found → end of the step → both keys absent from `ListKeys`, later steps' counts unchanged (full run at the checkpoint).
- `just quick` green and the `verify` command → exit 0.
