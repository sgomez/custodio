# F88 — custodio delete with confirmation

## Scope
Adds `custodio delete <id>` next to `import` and `list`, through the documented `DeleteKey`
(`docs/api.md`) and the client crate only (no dependency on `custodiod`; `just deps-check`, F64,
not repeated). Built here:
- `parse_command` dispatches `delete` with exactly one argument, the id; a missing id, an extra
  argument or any option (so also any would-be "yes"/"force" flag) is a usage error, status 2,
  usage text names `delete`. Nothing in the id is checked locally beyond what the API bound
  requires; the service decides (`InvalidArgs`, `NoSuchKey`).
- The confirmation: a prompt on the controlling terminal (`/dev/tty`, as the import password,
  `docs/decisions.md` 2026-10-27; the builder may choose otherwise only with a decision entry),
  naming the id and saying the key cannot be recovered. Only an explicit affirmative answer
  continues (the builder fixes the accepted words and the test pins them); anything else,
  empty input and end of input included, declines. Declining calls nothing on the bus and exits
  non-zero with a fixed message. The prompt is shown before any bus call.
- Without a terminal (no controlling terminal / `/dev/tty` cannot be opened) the command refuses
  with a fixed message and a non-zero status, before any bus call; piped stdin, a file or an
  environment variable never answers the confirmation. There is no option, environment variable
  or configuration that skips it.
- Service side: a trait like `Importer`/`KeyLister`, implemented in `bus.rs` with the single
  `DeleteKey(s)` call on the client constants. Failures reuse F86's `ServiceFailure` (documented
  names, service absent, transport, unknown name) with its fixed messages and `exit_status`
  (1; usage 2). The service's free text never appears. `NoSuchKey` and `PolkitDenied` have their
  own messages already in the table (not re-proven; F86 owns the table); here they are observed
  through `delete`. Success prints a fixed confirmation line and exits 0.
- `packaging/custodio.1` documents `delete`: synopsis, the confirmation and that the key cannot
  be recovered, that there is no flag to skip it, that it needs a terminal, that polkit asks as
  well, exit status.

Not here: `pkttyagent` (F89; without an agent `delete` shows `AuthorizationUnavailable` for now),
the service's delete semantics, ownership and audit (F76), package/install/e2e runs (F90/F100).
Environment: `rustix` with the `pty` feature is already a dependency of `custodio-cli` and its
`tty` tests open a pseudo-terminal in the dev container (`openpt`), and `/dev/ptmx` exists;
Python's `pty.openpty()` also works here. The builder's first step shows that a child spawned
with the slave as controlling terminal (new session, `TIOCSCTTY`) can open `/dev/tty`; if it
cannot, that is reported before building on it.

## Evidence
- Usage → unit and binary tests: `delete` alone, `delete a b`, `delete --yes a`, `delete -y a`,
  `delete --force a` give status 2, usage on stderr, nothing on stdout, no prompt, no bus call;
  `import` and `list` usage tests stay green → pass.
- Calls only the documented method → bus-monitor test: after a confirmed delete exactly one call,
  `DeleteKey`, to `BUS_NAME`/`OBJECT_PATH`/interface from the client constants, with the id as its
  only argument → pass.
- Confirmation asked, with the warning, before the service → pty test of the real binary: the
  terminal output contains the id and the not-recoverable wording before any answer is sent, and
  the bus monitor (method calls to `BUS_NAME` only) shows none at that moment (checked before the answer is written) → pass.
- Confirm → pty test: answer sent, fake polkit records exactly one call under
  `com.rfirma.custodio.delete-certificate` after the answer, status 0, key absent from the
  service's list afterwards and its files gone, success line shown → pass.
- Decline → pty tests (answer `n`, and end of input/hangup; empty line and near-miss words are
  unit-only, next to the test that pins the accepted words): status non-zero, fixed decline message, bus monitor shows zero calls and the
  fake polkit zero calls, the key is still listed → pass. A unit test proves the same on
  `run_delete` with a recording service, so the mutant "ignore the answer" fails.
- polkit denial → pty test with the fake polkit denying: after confirming, status non-zero, the
  `PolkitDenied` message, the key still listed and its files present → pass. Each polkit answer is shown to
  be asked again on a second delete (no cache) only by F76; not repeated.
- Missing id → pty test confirming a delete of an id that does not exist: the `NoSuchKey` message, non-zero, fake polkit
  zero calls → pass.
- No terminal → binary test with no controlling terminal (new session, stdin/stdout/stderr not
  terminals, with `yes`-like input piped on stdin): fixed refusal message, non-zero, zero bus
  calls, the key is still listed. A variant with a terminal on stdin only is not needed. → pass.
- No bypass → the usage tests above, plus a test that setting plausible environment variables
  (e.g. `CUSTODIO_YES=1`, `YES=1`, `FORCE=1`) does not remove the prompt (the bus is untouched
  until the pty answer) → pass.
- Errors from the documented names → the table is F86's (`failure/tests.rs`); here one bus test
  with the credentials double failing (`AuthorizationUnavailable`, the one test of this mapping;
  the polkit-unavailable variant above is dropped) and the service absent (no name owner → "cannot talk to the service", status 1, not 2)
  show that delete reaches that mapping and prints no service free text → pass.
- No secrets or internals in output → the failure tests assert that no service free text and no
  certificate bytes appear → pass.
- Man page documents it → a test run by `just test` (`tests/man.rs` style) reads
  `packaging/custodio.1` and checks: `custodio delete` in SYNOPSIS; the confirmation and the
  not-recoverable wording; that there is no option to skip it; that it needs a terminal; that
  polkit asks too; the exit status; it fails if any is removed → pass.
- `just quick` → exit 0.
