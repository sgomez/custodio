# F67 — Research: how custodiod can read the caller's flatpak app-id

## Scope
Built: a section `## F67` in `docs/findings.md` and, only if it decides (d), a pending entry `## F67` in
`SPEC_DEVIATIONS.md` (the file does not exist yet; the builder creates it with the format header that
CLAUDE.md refers to). No Rust, no unit, no policy change: `data/custodio.service` stays as it is, and nothing
is shipped. The open question is settled by trying the candidates, not by argument.

Not here: parsing, reading or journalling the app-id (F-features that depend on this one: the `app_id`
parser, the hostile-input reader, the journal field), and the "Detection through the flatpak proxy" open
question (acceptance 15 and its own feature). The section only reports whether the *process the bus names*
for a flatpak (`xdg-dbus-proxy`) would be in the source it picks, from `xdg-dbus-proxy`/flatpak sources.

What the section must try, each under the real `custodio.service` (ProtectProc=invisible, ProcSubset=pid,
PrivateUsers=yes, empty capability set) on a supported target (one of the install targets under
`e2e/targets/`, not the refusal-only ubuntu2404), in the e2e container, with a caller of another uid:
- (a) loosening the unit: the smallest loosening that makes `/proc/<pid>/root` (or `/.flatpak-info` of the
  caller) readable, shown to work or fail, and rejected because it fails the exposure gate (`just
  unit-hardening` score or the SPEC's no-loosening rule) and exposes every process.
- (b) a separate privileged reader: what it would need (capability, interface), why it is not built in M3.
- (c) at least these sources, each tried as `custodio` under the unit against a caller in a scope named
  `app-flatpak-<id>-<n>.scope` (a transient scope made with `systemd-run --scope`/`--unit`, since real flatpak
  may be absent; say so): the caller's cgroup through the pinned ProcessFD (pidfd `fdinfo`, `PIDFD_GET_INFO`
  cgroup id, and what resolving it needs), and systemd's `GetUnitByPIDFD` / `GetUnitByPID` over D-Bus (with
  the bus policy the unit and `data/com.rfirma.Custodio1.conf` allow, and polkit if it asks). Any other source
  the builder finds that needs no /proc access of another uid may be added. Each result is recorded, working or not.
- (d) the deviation: only chosen if every (c) source failed, with the failure shown.

Environment: needs a systemd container able to run the real unit (the e2e container). Smallest command run
in this session: `podman run --rm --pid=private docker.io/library/debian:trixie true` → exit 0 (rootless
podman 5.x, `--pid=private` works now; F45's earlier failure no longer applies). Booting a systemd guest was
not tried here; step 1 does it. If no target can boot the unit in this dev container, the builder records
the exact failing command in the section, tries the same unit properties with `systemd-run` in the
dev container itself, and, if that cannot reproduce the unit either, writes `BLOCKED.md` (a person's run on the
host) rather than deciding from reading alone.

## Steps
- [ ] Bring up a supported target's systemd container with the packaged `custodio.service` (use the e2e
      machinery, e.g. `e2e/run.sh` helpers or the Containerfile of one target), and record under `## F67`
      the target, the engine, the unit's checksum equal to `data/custodio.service`, and the baseline: as
      `custodio` under the unit, reading another uid's `/proc/<pid>/root` and `/proc/<pid>/cgroup` fails
      (commands and errors). Use a subagent for `xdg-dbus-proxy`, flatpak and systemd man-page reading.
- [ ] Try (a) and (b): the loosening experiment with its result and the exposure-gate consequence; the
      privileged-reader analysis. Commands and output.
- [ ] Try the (c) sources listed in Scope, as `custodio` under the unit, against a caller of another uid in a
      forged `app-flatpak-<id>-<n>.scope` and one outside such a scope; record what each returns, errors, and
      the kernel and systemd versions. Read flatpak/`xdg-dbus-proxy` sources for which process sits in that scope.
- [ ] Decide. For (c): the exact source, its format (the string shape, escaping of `-` and `\x2d` in the
      scope name, how the id is recovered), the bounds a reader needs (maximum length, call timeout,
      how it confirms the same process afterwards), and how the three cases (read, none, undetermined) are told
      apart. For (d): create `SPEC_DEVIATIONS.md` if absent and add the pending `## F67` entry amending
      acceptances 9 and 15, with the finding it relies on.
- [ ] End the section with the line `Decision: (c)` or `Decision: (d)` at column 0; run the feature's `verify`.
