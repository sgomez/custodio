# F121 — Purge pre-M4 keys before answering any call

## Scope
`custodiod` removes every key of the earlier (M3) format at start-up, one journal entry per key, and takes the bus name
only after that. F116 already recognises the earlier format without reading it (`KeyStore::legacy`, `legacy_all`,
`LegacyEntry`, `StoreError::Legacy`); this feature adds the removal, the entry, the ordering and the documentation.

- **Who purges.** The service, not the package scripts: that is what makes it hold for every package format and for a
  service started without an upgrade (SPEC §6). The package scripts are not touched.
- **Removal follows the store's rules.** Each file of a legacy entry is removed under the area lock, through the checked
  open (plain file of the service uid, no symlink followed or removed, content not parsed), and the directory is synced.
  Anything that breaks a rule (a symlink, a foreign owner, a wrong type, an unreadable area) is refused, not repaired:
  the purge fails, nothing past it is touched, the service exits non-zero and does not take the bus name. Files of the
  new format are never removed. A second start finds nothing and writes nothing.
- **The journal entry.** One entry per purged key (not per file: a key and its `-cert` file are one entry), carrying the
  owner, the id and the outcome `purged`; message id, fields, priority and message shape are the builder's, under the
  compatibility rule. It is submitted before the key's files are removed, as delete does, so a crash can repeat an entry
  on the next start but never lose one. If the entry cannot be written the key is not removed and the purge fails as
  above (conservative). `docs/audit.md` documents the identifier, the operation, the fields, the outcome and its priority,
  the message shape, and a query for it; the `data/custodio.catalog` text follows if it lists operations.
- **Ordering.** The sequence "open store, purge, serve, take the name" lives in one library function that `main` calls,
  so a test can drive it with a private bus, a fake polkit and a controllable journal sink. The function lives in a
  new file under `src/` that joins the `mutants` list (not in `lib.rs`). `main` keeps no serve or request-name path of
  its own (its current `serve`/`build_service` are removed or moved into that function), so the binary cannot serve
  without purging. The name is requested only after the purge returned, and no object is served and no bus connection
  for the service is opened before that either.
- **Orphan certificate.** An orphan legacy `a-cert` next to a new-format key `a` is grouped as id `a`; the purge removes
  only the legacy file `a-cert`, never `a`. The entry then names an id that is still live; this is accepted and
  documented in `docs/audit.md`.
- **Left to other features / checkpoints.** The upgrade from a real M3 package, per package format, with a real
  `journalctl` read (SPEC acceptance 9) runs at the checkpoints (F90/F100 and the package features there); here the entries
  are read from the in-memory sink and the datagram `JournalSink`, as the audit tests do. The CLI's wording (F123).
  Removal of the package's state directory is M2's behaviour and unchanged.
- **Size.** About five steps; no split. New non-test files under `src/` join the `mutants` recipe's `--file` list.

Environment: needs `dbus-daemon` (present, `/usr/bin/dbus-daemon`) and the fake-polkit rig that `storage_choice` and
`main_tests` already use; no TPM is needed, since the fixture is plain old-format files and the service is started with
`NoTpm` and in-memory credentials. No new tool.

## Steps
- [ ] Tests first and the fixture: an M3-format state fixture builder for the `purge` target (owners, ids with and without
      `-cert`, an orphan `-cert`, plus new-format keys alongside), and unit tests for the removal on the store (rules,
      symlink, foreign owner, idempotence, new-format files untouched). Then the store's removal of a legacy entry.
- [ ] The purge entry: type, wire form, `docs/audit.md` (identifier, fields, outcome, priority, message shape, query) and
      the catalog text, with the docs-versus-code check the audit tests already do for the other entries.
- [ ] The purge routine: for each legacy entry, entry first, then removal; refuses on any rule break or an entry that
      cannot be written; returns the purged list.
- [ ] The start-up function (purge, then serve, then request the name), `main` calling only it (own serve path removed,
      `main_tests::wiring` run over a legacy fixture); the `purge` integration
      target over a private bus: empty state, absent from `ListKeys`, entries, re-import of the same ids, no call
      answered during the purge, second start.
- [ ] Add the new files to the `mutants` list; `just mutants-diff F121` and `just quick` green; hand off.

## Evidence
- Earlier-format key files are deleted at start → `purge::state_is_empty_after_start` → the owner areas of an M3
  fixture (several owners, a key with its `-cert`, a key without one, an orphan `-cert`) hold no legacy file after the
  service has taken the name; the directory listing is exactly what is expected.
- Gone from the API → `purge::purged_keys_are_not_listed` → a new-format key placed alongside is still listed over the bus,
  and `Sign` on a purged id answers the documented "no such key" error.
- One journal entry per purged key (owner, id, purged) → `purge::one_entry_per_key` → the in-memory sink holds exactly
  one entry per fixture key (a key and its `-cert` are one), each with the right owner, id and outcome, none for the
  new-format key; the same entries seen through the `JournalSink` datagram carry the documented fields and priority.
- Entry carries no key material → `purge::entries_hold_no_key_bytes` → the fixture's key and certificate bytes (planted
  as recognisable sentinels) appear in no field, message or Debug of any entry.
- Documented in `docs/audit.md` → the audit docs-versus-code tests (unit, `audit::docs_tests`) → every purge field,
  value and message shape appears in the document and the code, both ways, the catalog text exists (`data/custodio.catalog`
  lists operations), and the purge query passes the existing query checks (`query_uses_trusted_fields`,
  `every_query_uses_only_what_the_code_emits`); the edited-copy control (one purge line removed or invented) fails.
- The same ids import again → `purge::same_ids_import_again` → after the purge an `ImportP12` over the bus of each purged
  id by the same owner succeeds, `ListKeys` shows it with its kind, and `Sign` with the fake polkit approving works.
- No call answered, name not taken, until the purge is complete → `purge::no_call_before_purge_complete` → the journal
  sink blocks on the first entry; while it blocks, `GetNameOwner`/`NameHasOwner` for the service name says it has no owner
  and a `ListKeys`, `Sign` and `ImportP12` call fails with the bus's "no owner / service unknown" error; `ListNames` on the private bus shows no connection besides the
  test's own and the fake polkit, so nothing is served under a unique name either; once released the name is taken and
  the same calls are answered.
- The binary purges → `main_tests::wiring` (legacy fixture variant) → starting through `main`'s path leaves the legacy
  file gone and the name taken; with the purge call removed from the start-up function the test fails.
- Refuse rather than repair → `purge::refuses_and_does_not_start` → with a symlink named like a legacy key in an area, a
  failing sink, start-up returns an error and the name is never taken. Symlink row: the symlink and its target are
  untouched (this is refused already when the legacy files are listed). Failing-sink row: every file of the first legacy
  entry is still on disk and no removal happened (the proof that the entry is written before the removal). Rows are
  literal. The foreign-owner case cannot be made in this integration target (uid 1000, private `file_uid`); it is
  proven by the store unit test, using the `file_uid` override as `remove_refuses_a_symlink_and_a_foreign_owner` does.
- Second start purges nothing → `purge::second_start_purges_nothing` → starting again over the same state writes no
  entry and removes nothing; a state with no legacy file at all (service started without an upgrade) likewise writes no
  entry and still serves.
- No symlink followed → covered by the row above, and by the store unit test of removal over a symlinked area and a
  symlinked key file.
- Test can fail / no weakened gate → `just mutants-diff F121` → 0 missed in the new and changed files of the `mutants`
  list.
- The rest of the build is intact → `just quick` → green.
