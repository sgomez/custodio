# F144 — End-to-end cases: journal queries for kinds, purge and load failures

## Scope
New cases `journal-kind-*` for SPEC acceptance 11 ("`docs/audit.md` ... its queries work"), limited to the queries that F120/F121 added to `docs/audit.md`. The cases run the
queries **as the document gives them**, extracted from the fenced blocks of `docs/audit.md` (the extractor of `e2e/jo.py` `extract_queries` is the model; the builder reuses it or
a small sibling, so a changed query in the document changes the test), against the **real journal** of the packaged service in the debian13 guest, and compare what each
returns with the entries the case itself caused (a cursor taken before, the exact set after). "Exactly the expected entries" means: no entry missing, no stray one, and a
forged entry (same `MESSAGE_ID` and `CUSTODIO_*` fields written by another process, as `e2e/jo-forge.py` does) is not returned, because the documented queries name the unit and
the service user.

The queries covered (the three groups of the description):
- **the kind** — "By storage kind" (`CUSTODIO_OPERATION=import CUSTODIO_STORAGE_KIND=<kind>`). The document shows the `encrypted-host` form; the case runs it with each of the three
  kind values in place (the document says the value is one of the three). Expected: the kind of the mode (`tpm` in `swtpm` and `lacking`, `encrypted-host` in `none`) returns
  exactly the case's imports, the other kinds return none of them. `encrypted-tpm` cannot be made in the container (`SPEC_DEVIATIONS.md` F134), so it is judged only to return none
  of the case's entries; no claim is made that it returns an entry.
- **the purge entries** — `CUSTODIO_OPERATION=purge` and "By the owner of a purged key" (`CUSTODIO_OWNER_UID`). Entries are caused by an old-format key file placed in the state
  directory (as root, owner and mode as the store demands) for two users, followed by a restart of the service; they must be of the earlier format that the service really purges.
  Step 1 finds the cheapest source of that format (the fixture of `crates/custodiod/tests/purge/`, or a file written by the M3 tool the F142 run already builds); the real M3 package
  upgrade is **not** repeated (that is F142 `upgrade-m3-*`, which already judges one purge entry per key after a real upgrade). Expected: the operation query returns exactly one
  entry per placed key, the owner query exactly those of that owner, and none of them carries a caller.
- **the failed loads** — "A signature that failed because the key is lost, and one that failed for a reason that may pass" (`CUSTODIO_CAUSE=key_lost`, `CUSTODIO_CAUSE=temporarily_unavailable`
  with `CUSTODIO_OPERATION=sign`). The cheapest real injection that makes the service report each cause on a real `Sign` (polkit approved) is the builder's choice, within limits:
  it runs through the packaged service (no test-only switch in the product), it is undone at the end, the state and the counts later steps read are as found (keys deleted), and each
  cause is seen in the entry of an actual call. Candidates for step 1 to try, cheapest first: a stored blob of a key damaged as root and restored (`key_lost`); the credential service
  socket stopped (`temporarily_unavailable` for `encrypted-host`); in `swtpm`/`lacking` the second swtpm and its clear as F140 does (`tpmclear.py`, `tpmclear-run.sh`) only if the
  cheaper ones cannot give the cause. A cause that no cheaper injection gives in a mode is judged in the mode where it can be given and reported skipped in the others
  (`skip.list`, reason), never by a unit test standing in. Expected: each query returns exactly the failed signatures caused, with the outcome `signing_failed`; the entries
  carry the key's kind; a signature that succeeded or was denied is not returned.
- **Import-failure queries** ("By cause", `credentials_unavailable`, and `CUSTODIO_OUTCOME=storage_failure`) are produced and judged by F139 `tpmfail-*`, which already ties the
  entry to the cause; they are **not repeated** here unless the injection of the failed-load group makes the entry for free (the stopped credential socket does: one extra failed
  import in the same step, judged by the same query run; the builder may take it, it is not required).
- **Not repeated:** that each field and value is documented and set by the code (F120 `kind_audit`, F121 `purge`, with `docs_tests`); the other queries of the document
  (F94 `journal-ops-queries`); the text of the messages; secrets in entries (F120 and `tpmclear`/`tpmfail` judge them; this feature still passes the same secret check over the entries
  it reads, cheaply, since it already has them).
- **Proven at the checkpoint:** `just e2e` as a whole and the package gates.

**No cause available anywhere.** If step 1 finds no injection that gives a cause in any mode, it amends the contract (evaluator approves) or writes `BLOCKED.md`; a case skipped in every
mode is never acceptable. If a cause can be given only in `none` (e.g. the credential socket stopped with `encrypted-host`), the `E2E_TPM=none` run is mandatory evidence (the verify
runs only the default `swtpm`) and its result goes in `PROGRESS.md`.

**Extractor.** The sibling of `jo.extract_queries` replaces only the values it must: the kind in the kind query and the uid in `CUSTODIO_OWNER_UID=`/`CUSTODIO_UID=` (`jo.py` replaces only
`CUSTODIO_UID=1000`); every other token stays exactly as the document has it, which the host test checks.

**Modes.** Cases that need a TPM to be judged (`swtpm`, `lacking`: kind `tpm`) and cases that need none (`none`: kind `encrypted-host`) are listed in
`e2e/targets/debian13/cases.list` (the outcome depends on the TPM or the key kind, not on the distribution: SPEC end-to-end scope), not in `e2e/cases.list`. The kind-import and
purge cases run in every mode (the expected kind is derived from the mode, and a wrong kind fails the case, so the run is not vacuous). A case whose injection exists only in some
modes is reported skipped in the others through `skip.list` with a reason, and `check-cases.sh` refuses a skip in a mode that has the injection (as for `pcr-*`, `tpm-slots-*`).
Group `journalkind` in `select.sh`, pattern `journal-kind-*` placed before `journal-ops-*`/`journal-entries` are not captured (it must not collide with them; the host select test
checks it), a step in `guest.sh` after `tpmslots` and before the upgrade, leaving the service active, the state, the keys and the journal counts as the later steps read them (its keys
deleted; its purge entries are the ones the later `journal` count steps must not see: the builder checks every later step that counts entries or keys, and says which in `PROGRESS.md`).

**Cases** (each reported exactly once; the builder may split or merge the failure cases by what the injection gives, within these names): `journal-kind-import`,
`journal-kind-purge`, `journal-kind-owner`, `journal-kind-key-lost`, `journal-kind-temporarily-unavailable`. A further `journal-kind-forged` (a forged entry is not returned by any
of the queries above) may be a part of the first three rather than its own case.

**Negative controls.** The proof that the comparison can fail is the host test below. Guest checks: a forged entry with the kind, the purge fields and the cause fields (written with `systemd-cat`/`logger` by root and by alice, as `jo-forge.py` does) is
present in the journal while the queries run, and is not returned; and, in the window the queries run over, a successful and a denied sign of the same key, which no cause query may return. Host (`scripts/test-e2e-journalkind.sh`, no container, in the justfile script-test list; python3
`-I`, judgement functions in a file of `e2e/`, as `e2e/tpmslots.py`): accepts a good record and rejects a missing entry, a stray entry, a forged entry returned, a wrong kind, a
purge count that is not one per key, an owner query that returns another owner's entry, a failed-load query that returns a signature that succeeded, an extractor that finds no
query for a heading the case needs (a changed document fails the extraction, not silently), and `check-cases.sh` accepts the skips of `skip.list` and refuses one in a mode that has the
injection; the ids are in the debian13 list and not in `e2e/cases.list`.

**Cost.** Host test: under 5 s, parallel with the other script tests (budget 60 s). Guest per mode: one import per kind round (two keys, ~5 s each, the two in parallel jobs where the
store allows it; F143 measured ~5 s per import), the old-format placement and one service restart (~3 s, the purge runs at start), two failed signatures (~5 s each, parallel with
the others where independent), one delete session at the end (~5–7 s, one session for all the keys), journal reads and 8–10 `journalctl` queries (<1 s each, run as parallel jobs, each
a few hundred ms). Estimated 25–35 s of phase in `swtpm`/`lacking`, ~25 s in `none`, no new container and no new guest boot; `just e2e-cases debian13 'journal-kind-*'` about 55–75 s per mode
(F140: 55–57 s; F143: 74–77 s with a 50 s phase). The full debian13 `swtpm` run grows by ~30 s on top of F135–F143 against 430 s in `budgets.tsv` (360 s measured before those): **this may
not fit**. The builder sums it in `PROGRESS.md` (the real full-run measure is the checkpoint's) and asks for more in `BLOCKED.md` if a measured run passes the budget. If the
second-swtpm route for `key_lost` is needed it adds ~30 s (F140 phase); that is the reason it is the last resort, and the builder says so if it is taken.

**Environment.** `journalctl`, `systemd-cat`, `busctl`, `pkcs11-tool`, `openssl`, `python3` are in the debian13 guest (F94, F139, F140, F143 used them); `swtpm` and the guest do not run in
the dev container (F136), so the probe of step 1 is the guest run itself. No new tool and no network.

Size: five steps, one session each at most.

      injection gives `key_lost` and which `temporarily_unavailable` in each mode, with what the entry holds; that each documented query form returns the case's entries and not a forged one.
      Commands and results in `docs/findings/F144.md` (short); amend this contract (evaluator approves) if a finding changes a case or a skip.
- [x] Tests first, host side: failing `scripts/test-e2e-journalkind.sh` (placement, accounting rules, judgements on good and bad records as listed), added to the justfile script-test list;
      then the judgement file in `e2e/` (python3 `-I`, functions of files) with its self-test until the host test passes.
- [x] Guest side: group `journalkind` in `select.sh`, `journalkind-run.sh`/`-user.sh`/`-cases.sh` (own keys and ids, the imports, the placement and restart, the injections, the queries from the
      document, the forged-entry control, the cases), step in `guest.sh`, ids in the debian13 `cases.list`, skips in `skip.list`, the `check-cases.sh` rule and header text; texts that became wrong updated.
- [x] Run `just e2e-cases debian13 'journal-kind-*'` in `swtpm`, then `E2E_TPM=lacking`, then `E2E_TPM=none` (skips accounted); note times, the entries counted per query, and the effect on
      later steps (key and journal counts they read) in `PROGRESS.md`.
- [x] Run `just quick`; sum the budget effect in `PROGRESS.md`.

## Evidence
- The kind query finds the imports of the kind → `journal-kind-import` (`just e2e-cases debian13 'journal-kind-*'` in `swtpm`, `E2E_TPM=lacking`, `E2E_TPM=none`) → the documented
  `CUSTODIO_OPERATION=import CUSTODIO_STORAGE_KIND=<kind>` query, taken from `docs/audit.md`, returns exactly the case's imports for the kind of the mode (`tpm` / `encrypted-host`)
  and none for the other kinds, a forged entry with that kind is not returned, and the entries hold no secret.
- The purge queries find the purge entries → `journal-kind-purge`, `journal-kind-owner` (same runs) → after the old-format files are placed and the service restarted, the operation
  query returns one entry per placed key (outcome `purged`, no caller), the owner query exactly those of that uid, a forged purge entry is not returned; the old-format files are gone. Re-importing the same ids is left to F121 and F142.
- The failed-load queries find the failed signatures → `journal-kind-key-lost`, `journal-kind-temporarily-unavailable` (same runs, or skipped where `skip.list` says, with the reason)
  → each cause query returns exactly the signatures that failed for it (outcome `signing_failed`, the kind of the key), and not a successful or a denied one; the injection is undone and
  the key signs again where the injection is reversible.
- The comparison can fail, accounting is right → `scripts/test-e2e-journalkind.sh` (in the justfile script-test list; run by the builder directly, it is not in `just quick`) → good
  record accepted; every bad record listed above rejected; skips accepted in the modes without the injection and refused in the others; ids placed in the debian13 list only.
- Skipped where it does not apply → `E2E_TPM=none just e2e-cases debian13 'journal-kind-*'` (and `lacking` if a case is skipped there) → exit 0, "N cases accounted for", the skipped
  ones with the reason from `skip.list`.

## Amendments
- The probe (step 1) found every injection works in every mode, so no case is skipped anywhere and `skip.list` gets no `journal-kind-*` line: `key_lost` is a record of the key damaged
  (last byte flipped, original put back) in swtpm, lacking and none; `temporarily_unavailable` is the service's TPM pointed at a path that does not exist (`tf_point`, swtpm and lacking) or the
  credential service socket stopped (none). `check-cases.sh` refuses a skip of any `journal-kind-*` case in any mode (as for `sign-*`, `noplain-*`), with a matching host-test case, and the
  host test checks the debian13 skip list has no such line (this replaces "reported skipped in a mode they do not apply to" and the skip-list rule for the failed-load cases).
- Evaluator notes applied: the kind query's cursor is checked against the entries before it (the host test rejects a result holding one); the owner query runs once per uid and each user's
  entries are excluded from the other's result (host test); the purge runs on the packaged service's start-up path (files placed, service restarted, `purged` entries, files gone: a guest check);
  the secret check is not evidence for this feature; the cost is summed in `PROGRESS.md`.
