# F158 — Download and verify the Ubuntu 26.04 minimal cloud image

## Scope
Built:
- `e2e/vm/image.sh` and the recipe `just vm-image` (with a comment line like the neighbouring recipes). The script fetches
  the Ubuntu 26.04 minimal cloud image (amd64 `.img`), `SHA256SUMS` and `SHA256SUMS.gpg` from the place `docs/findings/F151.md`
  names (`cloud-images.ubuntu.com/minimal/releases/resolute/`), checks the signature with `gpgv` against the Ubuntu cloud image
  keyring (default `/usr/share/keyrings/ubuntu-cloudimage-keyring.gpg`, the one `scripts/vm-host-check.sh` requires) and then
  the image against the line of the signed sums, and only then moves the image (with the signed sums it was checked against)
  into the cache. Downloads go to a private temporary directory that is removed on every exit, so a refusal leaves nothing
  in the cache, not even a partial file. Base URL, keyring and cache directory are overridable by environment variables
  (names are the builder's) so the self-test can point them at local fixtures; the defaults are the real ones.
- The cache is outside the repository (a per-user cache directory); the script refuses a cache directory inside the
  repository tree, so an image cannot be committed by accident.
- A cached image is verified again on every use: the cached signed sums are checked with `gpgv`, then the image against them.
  If that fails the script exits non-zero, says which check failed and removes the failing files from the cache; it does not
  silently download a replacement. A cache that passes is used without a download.
- On success it prints, on stdout, the image path, the serial and the SHA-256 in a form a later script can read (F159 uses the
  path; the run record of F160+ uses serial and checksum). Diagnostics go to stderr.
- The pinning choice (SPEC "Image pinning"): the builder chooses between one dated serial and the newest release verified by
  signature, within these limits: the serial is recorded either way; whichever is chosen, the three files come from one
  `release-<serial>` directory (F151: `release/` is an alias that can move between two downloads, so it is not mixed with a
  serial). The choice and why go into `docs/decisions.md` (rules at its top; it must stay under the size limit `just quick` checks).
- `scripts/test-vm-image.sh`, added to `just test-scripts`: offline, on local fixtures (a throwaway test key in a temporary
  `GNUPGHOME`, a small fake image, signed sums, `file://` URLs).

Not built: booting the image, overlays, the seed (F159); anything that reads the printed record into a run record (F160).
Nothing proven at a checkpoint.

Environment (checked this session): `gpgv`, `gpg` and `curl` are in the dev container; `curl -sI .../resolute/release/SHA256SUMS`
answers `HTTP/1.1 200 OK`; F151 downloaded the 421900800-byte image in 18 s and verified it with the same `gpgv`/`sha256sum`
commands. `/tmp` has 16 GB free. The keyring path is the one F150's `just vm-host-check` already requires.

Cost:
- `scripts/test-vm-image.sh`: one `gpg --quick-generate-key` (about 1 s), then about ten runs of the script on a few-kilobyte
  fixture; estimated 3–6 s, no network, no VM, no container. The independent refusal cases use separate cache directories and
  run at once (`wait`), no `sleep`. A script test running in parallel with the others under the `script *` budget (120 s); no
  new budget needed.
- `just vm-image` (in the `verify`): the first run downloads about 422 MB (about 20 s measured by F151) plus the SHA-256 of 422 MB
  (about 1–2 s); later runs reuse the cache and only verify (about 2 s). It needs network on the first run only. It is not
  an e2e case and not in `just quick`. Every step fits one session; no split.

## Evidence
- Fetches the image, `SHA256SUMS` and `SHA256SUMS.gpg`, verifies, places the image in the cache → `scripts/test-vm-image.sh`
  "good": on the fixtures the script exits 0, the cache holds the image whose bytes equal the fixture (`cmp`) → pass. With the
  real network → `just vm-image` (in `verify`) → exit 0, the printed path exists and its `sha256sum` equals the printed checksum.
- Prints the serial and the checksum → test "good": stdout has the fixture's serial and the SHA-256 computed independently with
  `sha256sum` on the fixture → both equal; `just vm-image` prints a serial of eight digits and 64 hex characters.
- Verifies the signature with `gpgv` against the keyring, and only then trusts the checksum → controls, each run against a fresh
  empty cache, each must exit non-zero, name its own reason on stderr, and leave the cache directory with no file in it (`find`
  lists nothing, partial downloads included):
  - bad signature: `SHA256SUMS` changed by one character after signing (shown to differ with `cmp`), checksum line still matching the image;
  - signature by another key: sums and image consistent, signed by a second key not in the keyring;
  - wrong checksum: sums correctly signed but listing another hash for the image (so only the checksum check can catch it);
  - missing sums: `SHA256SUMS` absent, and as a separate control `SHA256SUMS.gpg` absent;
  - sums with no line for the image name (signed, valid) → refused, as a variant of the wrong-checksum control.
  The four reasons differ from one another in the output (a script that fails with one generic message fails here).
- The image is placed only after verification → in the same controls the image fixture is present and downloadable, yet no file
  reaches the cache; and the "good" case run with the keyring replaced by the second key's keyring also refuses (a script that
  skipped `gpgv`, or took the checksum from an unsigned source, would pass the bad-signature and other-key cases and fail here).
- A cached image is verified again before use → test: after a good run, (a) the cached image with one byte changed (`cmp` shows
  it differs) → non-zero, names the checksum, the image is removed from the cache; (b) the cached signed sums changed → non-zero,
  names the signature; (c) an untouched cache with the base URL pointed at a nonexistent path → exit 0 and the same serial and
  checksum printed (the cache is used and verified without a download).
  After (a) and (b) the cache holds no usable image.
- Cached outside the repository, never committed → test: with `HOME`/`XDG_CACHE_HOME` pointed at a temporary directory, the default
  cache path printed is under it and not under the repository root; a cache directory inside the repository root is refused
  and nothing is created there; `git status --porcelain` is empty after the run.
- Real image → `just vm-image` twice in the `verify`: the second run finishes without downloading (checked by running it with the
  base URL pointed at a nonexistent path in the builder's own check, recorded in PROGRESS) and prints the same serial and checksum.
- Pinning choice recorded with why → entry in `docs/decisions.md` (accepted by the evaluator on reading it; a document is not
  grepped), `just quick` (size limit) → green; the behaviour it describes is the one the tests above and `just vm-image` show:
  the serial printed is the `release-<serial>` directory the three files came from (test: the fixture has two serial
  directories with different images; the printed serial and checksum belong to the directory the script's rule selects).
- A test that can fail → each control above is first shown to differ from the good fixture (`cmp` or a changed hash); and the
  test run once against a copy of `image.sh` with the `gpgv` call removed (sed-patched copy in a temp directory, asserted to
  differ from the original) must fail the bad-signature and other-key controls.
