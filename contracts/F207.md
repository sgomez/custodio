# F207 — Documents: fingerprint, the lock screen, the Firefox restart, doctor, the Ubuntu 26.04 guide and docs/install.md

## Scope
Builds the user documents of SPEC Design 5 and the two script tests that run their commands (acceptance 16), on what exists:
`custodio fingerprint` (F197), `custodio doctor` (F202, F203), the completions (F205), the service's import/delete note (F201), and
the shared helper `scripts/lib/docs_check.py` with `scripts/lib/docs-register-fixture.sh` that `test-docs-readme.sh` and
`test-docs-install-register.sh` already use (console blocks run as written, block kinds, links). New files, names the builder may change if the
README links them: `docs/fingerprint.md` (turn on and off, what changes, fallback, the limits of the threat model's "Not guaranteed", refusals,
other systems with package names and what was or was not run, the GNOME lock screen on Ubuntu, the Firefox restart); `docs/doctor.md` (every check,
its states and fixes); `docs/guide-ubuntu-2604.md` (the end-to-end guide). `docs/install.md` gains the fingerprint command, doctor and
completions (the completions section exists from F205: the builder adds the fingerprint and doctor parts and links, and does not repeat what is
there). The README links the three documents; `test-docs-readme.sh` and the other install scripts keep passing.

Left to other features: `docs/threat-model.md`, SECURITY.md, `docs/api.md`, `docs/audit.md`, the 0.9.0 release notes and the manual steps
(F208). Prose is checked by a person (acceptance 20, 22), never by grepping wording. Nothing here proves the real Ubuntu VM or a real reader
(F209 and acceptance 22). The Debian 13 and Alma 10 "not run in a VM" statements are written from `docs/findings/F199.md` and
`docs/findings/F201.md`; the builder reads them, does not re-research.

Environment (run in the dev container, 2026-11-16): `unshare -rm true` works; `dpkg`, `apt-get`, `sudo`, `openssl`, `modutil`, `nfpm`,
`dbus-daemon` are present; `gsettings`, `pkexec`, `fprintd`, `firefox` are absent. So commands of those tools cannot run as themselves here.
The way each is met (the builder decides the code, the requirement is fixed): a tool absent in the container is put first on `PATH` as a
named wrapper in the script's fixture directory that accepts exactly the arguments the document shows and otherwise exits non-zero (`sudo`
runs the rest as the fixture's root: `CUSTODIO_FIXTURE_EUID=0` on the real CLI built with the `fixture-root` feature, as `just fixture-seams` builds it;
`gsettings` and `pkexec` record the call, which the test compares with the document's command; `apt-get install ./x.deb` and `dpkg -r`/`-P` run the real
`dpkg` into a fixture root the way `scripts/test-deb-lifecycle-real.sh` does, with `scripts/lib/bus-fixtures.sh` and `lifecycle-fixtures.sh`).
Steps that are only a person at a screen (exporting the `.p12` from Firefox's certificate manager, enrolling a finger in GNOME Settings,
pressing Tab, signing in to a site) are prose or `text` blocks and are listed in the script's output as "a person's"; every `console`
block, without exception, is run. The guide shows the `.p12` export as prose and then imports a `.p12` that the script supplies from the
fixtures (`openssl pkcs12`), so the import command is the real one.

Sizing: seven steps (step 1 is split in two so that the rigs and the scripts each fit a session); no further split.

Costs (estimates from `test-docs-readme.sh` and `test-deb-lifecycle-real.sh`, which use the same rigs; the builder measures and writes the
numbers in PROGRESS.md):

| Test | Time | How it runs |
|---|---|---|
| `scripts/test-docs-fingerprint.sh` (the console blocks of `docs/fingerprint.md` and `docs/doctor.md` on fixture roots and a fake fprintd and service on a private bus; about 8 negative-control copies) | about 30 s | a script test, parallel with the other script tests in `test-scripts`; the blocks of one document run in order, the controls and the two documents run at once |
| `scripts/test-docs-guide.sh` (the guide's blocks in one fixture system: real dpkg install and removal, the real CLI, a private bus; about 8 controls) | about 60 to 90 s, the heaviest of the three because of dpkg | a script test in `test-scripts`; its controls run at once, not one after another; under the 120 s default of `budgets.tsv`; if the measured time passes 100 s the builder asks for a row in BLOCKED.md, it does not split the guide |
| `scripts/test-docs-install.sh`, `-install-register.sh`, `-readme.sh` | unchanged (existing, 10 to 40 s each) | existing |

No e2e case: nothing here depends on the distribution beyond what F199 and F204 run on every target. No unit test, no mutants (`verify` has no
`mutants-diff`). The two scripts are proven by their own run; no test of them against a stub, only the negative controls below, which are
broken copies of the documents.

## Evidence
- Turn the fingerprint on and off; exactly what it changes (one file, every polkit action, not `sudo`, not the login) → `test-docs-fingerprint.sh`:
  the `console` blocks of `docs/fingerprint.md` (`sudo custodio fingerprint enable`, then `disable`) run as written on a fixture root with a fake
  fprintd; the output shown equals what the real CLI prints; the file the document shows equals the bytes `enable` wrote (compared, not
  grepped), `disable` removes it, and the tree of the fixture root is otherwise identical before and after → all hold. Negative controls: a copy
  whose shown file differs by one character, and a copy whose output line is changed, each fail.
- Fallback to the password; "not `sudo`, not the login" → what runs is the same blocks; the claims are prose and a person's (acceptance 20); the
  F199 and F209 runs prove the behaviour on the targets. Stated here so no test greps for them.
- Every limit of "Not guaranteed"; the other systems, what was and was not run → prose, a person's (acceptance 20, step 5 reading); not tested by
  wording. The package names the document gives per system are proven by the refusal blocks below.
- What to do when `enable` refuses (Omarchy's setup, an administrator's file, the global switches) → `test-docs-fingerprint.sh`: one `console`
  block per refusal, marked as failing, run on the fixture it needs (an existing foreign `/etc/pam.d/polkit-1`; Omarchy's file; `pam_fprintd` in
  `common-auth` of the Debian family, `authselect` with fingerprint on the Fedora family, `system-auth` on Arch; not root; no `pam_fprintd.so`
  or no fprintd, with the os-release of each of the five systems so that the package names the document shows for each are the ones the CLI prints) →
  exit non-zero, the two-line message equals the document's, the fixture root unchanged. Negative control: a copy that shows the Debian package
  name under the Fedora heading fails.
- The GNOME lock screen (GDM's own PAM file and the GNOME setting; turn it off with `gsettings`; the untested `gdm` user) → the `gsettings set
  org.gnome.login-screen enable-fingerprint-authentication false` line runs as written through the recording wrapper and the recorded arguments
  equal an argv fixed in the script from SPEC Design 5 (not read from the document, so the check is not circular; a copy with another key name fails); that `enable` prints the lock-screen note on GNOME is run in
  the blocks above; the claims about GDM are prose, a person's (acceptance 20) and the untested `gdm` user is stated as untested.
- The Firefox restart after import and delete → the guide's import and delete blocks (`test-docs-guide.sh`) run as written and show the sentence
  the CLI prints (acceptance 15 proves the CLI; the README test already runs the same sentence); the restart itself is prose.
- Every doctor check, its states and fixes → `test-docs-fingerprint.sh`: `docs/doctor.md` has a section for each of the six checks, and the set of
  check names equals the names `custodio doctor` prints on a fixture (derived from the CLI's output, so a seventh check added to the CLI fails
  the test); its `console` blocks show `custodio doctor` on fixtures that produce each state the document explains (ok, not ok with the fix,
  could not check, a broken include, no profile, `unknown` storage with a reason) and each runs as written with the exit status the document
  states (`fails=yes` where it exits 1). Negative controls: a copy with one check's section removed fails; a copy whose shown fix differs from
  the CLI's fails.

  `docs/doctor.md` and the guide: they hold only `console` and `text` blocks, and a `text` block with a `$ ` line fails. Negative controls: a copy
