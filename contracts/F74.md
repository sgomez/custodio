# F74 — Journal entries name the operation

## Scope
Built, in `custodiod`'s audit module, `docs/audit.md` and `data/custodio.catalog`:
- A new field `CUSTODIO_OPERATION` on every entry, with one value per operation: `sign`, `import`, `delete`,
  `replace_certificate`. The operation is part of the typed entry model (not a free string), so the entry
  still cannot carry text that was not validated. Signing entries gain `CUSTODIO_OPERATION=sign`; every
  other field, value, priority, message text and the signing `MESSAGE_ID` stay as they are
  (compatibility rule of `docs/audit.md`).
- The entry model defines what the later features write for the other three operations (F75 import,
  F77 delete, F79 replace certificate): their outcome values, priorities, message shapes and one
  `MESSAGE_ID` per kind of message (the builder decides whether that is one id per operation or per
  outcome, and documents it; every id is new, 32 lower-case hex digits, distinct from the signing one and
  from each other). The model has no place for the `.p12`, the password, certificate bytes, data or
  signature: an entry is built from typed parts only, as today. The outcome set covers at least the
  outcomes named in F75/F77/F79: stored, denied, authorization unavailable, wrong password, unsupported key,
  storage failure; deleted; replaced, certificate mismatch. Import entries may carry the key type when
  known (F75 names it), as a fixed-name typed value.
- `data/custodio.catalog` gets an entry for every new `MESSAGE_ID`, in the same two forms as today (the
  `en` one first, then the untagged default), each with one `Subject:` and `Defined-By: custodio`.
  `e2e/catalog-text.txt`, `e2e/journal.py` and `scripts/test-e2e-catalog.sh` are adapted so they still
  check the signing explanation against the signing entries, without weakening.
- `docs/audit.md`: the field, its four values, the new outcomes and message ids, the message shapes, and
  one example query per operation (trusted `_SYSTEMD_UNIT`/`_UID` plus `CUSTODIO_OPERATION=<value>`).
  Its documentation tests (`audit/docs_tests.rs`) check every documented query, field, value, id and
  outcome against the code and the catalog, and fail when the code gains a value the page lacks.
- `audit/*.rs` stays under the file-size gate; any new audit file is added to the `--file` list of the
  `mutants` recipe (an extension, not a threshold change).

Not built: writing import, delete or replace-certificate entries, the methods themselves, and failing closed
on audit errors (F75, F76–F79). Signing's own audit behaviour is unchanged. Real journald registration of the
catalog and `journalctl -x` on a booted target are proven by the existing e2e journal cases and the package
gates at the checkpoints (F90, F100), which run the shipped `data/custodio.catalog`; here the catalog is
proven by the documentation tests and the container-free catalog script (`scripts/test-e2e-catalog.sh`, in
`just test-scripts`). A guest run of the `journal-*` cases needs a booted target and is not run here.

Environment: nothing beyond the dev container.

Size: about five steps; no split.

## Steps
- [ ] Failing tests first: operation field on signing entries (wire and `Entry::fields`), the model for the

- [ ] Add the operation to the entry model and `CUSTODIO_OPERATION` to the wire fields; signing entries

- [ ] Add the catalog entries and adapt `e2e/catalog-text.txt`, `e2e/journal.py` and

- [ ] Update `docs/audit.md` (field, values, outcomes, ids, messages, a query per operation) and the module

- [ ] Run `just quick`, then `just mutants-diff F74`; fix surviving mutants with tests; write `PROGRESS.md`.

## Evidence
- Signing entries carry the operation, other fields unchanged → unit test in `audit/tests.rs`: for every
  `Outcome` and with/without caller, `fields()` equals the previous field list plus
  `CUSTODIO_OPERATION=sign`, the same `MESSAGE_ID`, priority and `MESSAGE` as before (literal expected
  values, not recomputed) → passes; an integration test in `tests/audit` signs over the private bus and
  reads `CUSTODIO_OPERATION=sign` from the sink → passes. Negative control: mutating the value or dropping
  the field fails it.
- Operation values are exactly the four documented names → unit test over an exhaustive match of the
  operation type (stops compiling on a new variant): names `sign`, `import`, `delete`, `replace_certificate`,
  all distinct → passes.
- Model for the other operations: outcomes, priorities, messages and ids → unit tests building an entry for
  each operation and each of its outcomes, asserting literal `CUSTODIO_OPERATION`, `CUSTODIO_OUTCOME`,
  `PRIORITY`, `MESSAGE_ID` and `MESSAGE`; every id is 32 lower-case hex, all ids distinct; an outcome is only
  accepted with an operation it belongs to (an invalid pairing does not compile or is not constructible) →
  passes.
- Forbidden content (`.p12`, password, certificate bytes, data, signature) → compile_fail doctests like the
  existing ones (a `Vec<u8>`/`String` cannot be passed for any new part; no `From<&str>`), plus a leak test
  in `tests/audit/leaks.rs` style that builds an entry for each new operation and outcome with a recognisable
  key id and scans the encoded datagram for the marker strings of secrets, which are only ever given to the
  neighbouring API → passes; the scan fails against a deliberately leaking entry (negative control kept in
  the test).
- Catalog has an entry per new id → `docs_tests` `catalog_format`: every `MESSAGE_ID` the code can emit has
  both the `en` and the untagged entry, one `Subject:` and one `Defined-By: custodio` each, the `en` entry
  first for each id, and the catalog has no id the code does not emit → passes.
- Signing explanation still shown → `scripts/test-e2e-catalog.sh` passes with the adapted checks and its
  negative controls; `e2e/catalog-text.txt` is the body of the signing entries only → passes.
- Docs name the field, values, new outcomes, ids → `docs_tests`: the field table contains
  `CUSTODIO_OPERATION` (always present); every operation name, outcome name, priority and `MESSAGE_ID`
  from the code appears in `docs/audit.md`, and each documented value is in the code → passes; removing a
  value from the page fails it.
- A query per operation → `docs_tests`: for each operation there is a `journalctl` line in the page with
  `_SYSTEMD_UNIT=custodio.service`, `_UID=` and `CUSTODIO_OPERATION=<that value>`; every `journalctl` line
  in the page uses only fields/values the code emits (parsed, not grepped for one word) → passes.
- Compatibility rule intact → `docs_tests` `limits_and_compatibility_documented` still passes, and the old
  signing documentation tests pass unchanged.
- Shipped catalog passes the package gates and e2e journal cases → proven at the checkpoints F90/F100 (see
  Scope); locally `just quick` does not run the catalog script (it is in `just test-scripts`), so the evidence runs `scripts/test-e2e-catalog.sh` and `bash e2e/journal-selftest.sh` directly, and `just mutants-diff F74` covers the audit code.

  `bash e2e/journal-selftest.sh` (host) directly. (3) `CUSTODIO_OPERATION` is added to the signing catalog body

  `authorization_unavailable`, `wrong_password`, `unsupported_key`, `storage_failure`; delete `deleted`, `denied`,
  `authorization_unavailable`, `storage_failure`; replace certificate `replaced`, `denied`,
  `authorization_unavailable`, `certificate_mismatch`, `storage_failure`. One `MESSAGE_ID` per operation (3 new).
  (5) `CUSTODIO_KEY_TYPE` (`rsa_2048`, `ecdsa_p256`) is documented as import-only and omitted when unknown, which
  `optional_fields_flagged` covers. (6) docs_tests enumerates operations through `Operation::all()`, which the
  unit test proves exhaustive.
