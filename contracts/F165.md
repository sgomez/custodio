# F165 — Written steps for reading the PCR mask on Debian 13

## Scope
Built:
- A new section in `docs/manual-acceptance.md` (after the M4 result form, section 23; numbered next, headed as M5 acceptance 17,
  the PCR mask on Debian 13), written for a person on Debian 13 with a TPM, hardware or a VM with a virtual TPM. The page says the
  record states which. Steps: (1) `systemd-analyze has-tpm2` reports full support with `libtss2-rc` installed (what "full" looks
  like, and that anything less stops the run); (2) seal a user-scoped credential through the same Varlink call the service makes
  (`io.systemd.Credentials.Encrypt`, scope `user`, no `withKey`, on `/run/systemd/io.systemd.Credentials`, the exact
  `varlinkctl call` command, run as the user the service seals for, plaintext base64 in `data`); (3) read its key identifier and
  PCR mask with `e2e/vm/credread.py` (F157), with the systemd 257 identifiers of `docs/findings/F110.md` / `F153.md` for the
  reading, or the documented equivalent (the header read by hand from F153's offsets) when the repository is not on the machine;
  (4) a credential that is not TPM-bound (host-only, null key, unknown identifier) is an invalid reading: stop and repeat after
  fixing the TPM, never record it as "PCR 7 refuted"; (5) record date, machine, systemd version, hardware or virtual TPM,
  `has-tpm2`, identifier, mask and result in `docs/findings/F166.md` (the file itself is F166's, not built here).
- `scripts/test-docs-manual-m5.sh` (with a helper under `scripts/lib/` only if the size gate needs one), added to
  `just test-scripts`.

Not built: `docs/findings/F166.md` and its index line, and the run on a real machine (F166, by a person). Nothing on the new
page is claimed as run on Debian 13 or on hardware; the page says so (**unverified**), like sections 20 to 22. No change to
`e2e/vm/credread.py`, the service or the VM harness.

Environment (looked up, not yet run): `varlinkctl` is in the dev container (`/usr/bin/varlinkctl`); `scripts/with-swtpm.sh`,
`e2e/vm/mkcreds.sh` and `python3` are what F157's self-test already uses. The builder's first step runs the smallest command
that shows the dev container can do the Varlink call (`varlinkctl call` with the page's arguments against a stub socket, or
`varlinkctl --help` / argument parsing against a throw-away `unix:` listener). If the real daemon socket cannot be had in the
container, the arguments are proven against the service's request (below) and the real call stays a person's step in F166.

Test (`scripts/test-docs-manual-m5.sh`): reads the new section only (never M1-M4 sections), extracts the fenced commands, and
runs them as written, on F157's fixtures made by `e2e/vm/mkcreds.sh` under `scripts/with-swtpm.sh`:
- Results the page states (systemd 257 on Debian 13 defaults to mask `0x80`, F153): user-scoped host+TPM identifier with mask
  `0x80` = **PCR 7 confirmed**; same identifier with mask `0` = **refuted**; host-only, null or unknown identifier = **invalid
  reading, repeat**; any other mask has its own stated outcome (recorded as found, not confirmed). The page reads with
  `credread.py FILE --systemd-version 257` and does not use `--expect-tpm-bound` (it would exit 1 on the confirmed 0x80); if it
  mentions the flag, it says exit 1 with a nonzero mask is not a failure of the run.
- The test applies the page's interpretation to the reader output on `scoped-pcr7` (confirmed), `scoped` with mask 0 (refuted),
  `host-scoped` and `null` (invalid).
- Seal to read, end to end: the page's `varlinkctl call` runs against a one-shot stub socket that records the request and answers
  `{"blob": <base64 of the scoped fixture>}`; the test runs the page's command that turns the reply into the credential file, then
  the page's reader command on it, and checks `host+tpm2-scoped`. The recorded request has method
  `io.systemd.Credentials.Encrypt`, `name`, valid base64 `data`, `scope":"user"`, no `withKey`, and equals the shape of the
  request in `crates/custodiod/src/creds/systemd.rs`. The page says the call runs as the target user, not under `sudo`.
- The documented equivalent (header read by hand): the page's command is run as written on `scoped`, `scoped-pcr7` and
  `host-scoped` and must give the same identifier and mask as `credread.py`. No wording comparison with F153 offsets.
- `has-tpm2`: the page's quoted "full support" lines are compared with the real `systemd-analyze has-tpm2` output format in the
  container (with the swtpm if it reports one); `libtss2-rc` is named.
- The record list on the page names date, machine, systemd version, hardware or virtual, `has-tpm2`, identifier, mask and the
  result with its two values "PCR 7 confirmed" / "refuted"; compared with F166's description in `features.json` (read only).
Negative controls (fixture copies of the page, each must differ from the real one and fail): `has-tpm2` step removed; `libtss2-rc`
dropped; `withKey` added; scope `system`; reader path misspelled; `--systemd-version` changed; confirmed and refuted swapped, or
0x80 called invalid; the "not TPM-bound is invalid" rule removed; the hand-read command broken (wrong offset); the blob-extraction
command broken; the hardware/virtual field removed. Controls run in parallel subshells.

Cost (estimated from `scripts/test-docs-manual-m4.sh`, ~6.5 s wall, and F157's self-test, 2–4 s): ~5 s wall, one swtpm session
for the fixtures run in the background while the text checks and controls run in parallel. A script test: runs in parallel with
the other script tests under the `script *` budget (120 s); no new budget. No VM, no e2e case, no `sleep`; a missing `swtpm`,
`varlinkctl` or `tpm2-tools` fails naming the tool, never skips. Every step fits one session; no split.

Proven at the checkpoint, not here: the page's links in the docs inventory, if any gate there covers it.
