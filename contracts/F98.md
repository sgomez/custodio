# F98 — Complete client documentation

## Scope
Built: the prose of `docs/api.md` for client authors, a test `scripts/test-docs-api.sh` (added to
`test-scripts` in the justfile) that runs the document's busctl examples against the real service, and a
README link. The existing machine-checked items of `docs/api.md` (methods, arguments, bounds, error names,
actions, the line formats `crates/custodiod/tests/api_contract.rs` reads) stay as they are; `just api-contract`
must still pass. Added prose must not use those line formats in a way that confuses that test.

Left for other features: acceptance 14/15 runs by a person or a flatpak (F99); the real-bus, real-polkit
and real-flatpak runs (checkpoints F90/F100). Detection behaviour itself is research already done in
`docs/findings.md` "F68" (its `Detection steps` and the final `Detection:` line); this feature documents it
and does not re-measure it. Hashing-in-the-client and the compatibility rule are stated in the document, and
the compatibility rule points to `docs/audit.md` instead of copying it.

Environment probes (this session, dev container):
- `dbus-daemon --version` → 1.16.2; a private `dbus-daemon --config-file=… --nofork` plus
  `busctl --address=unix:path=… call org.freedesktop.DBus … GetConnectionCredentials s org.freedesktop.DBus`
  → `a{sv} 3 "ProcessID" … "UnixUserID" … "ProcessFD" h 5` (ProcessFD works, so the service can identify the
  caller on a private bus). `busctl` and `openssl` exist; `python3 -c "import dbus"` and `import gi` fail.
- There is no `/run/systemd/journal/socket` and no `/dev/log` in the container, and `custodiod`'s `main` is
  wired to the real polkit and the journal (`crates/custodiod/src/main.rs`), with no hook for a fake.
  So the test cannot start the shipped binary as is. A small test-only server (a Rust example or test binary
  that builds the same `Custodio` service type with a scripted fake authorizer and a journal sink that writes
  the entries to a file or socket) is needed; the builder places it and states why it is not shipped. It must
  not change the behaviour of the shipped `custodiod`, and no `#[allow]` without a comment.
- If a private-bus polkit stand-in as a separate bus peer turns out cheaper than an in-process fake, the
  builder may use it, as long as the service under test is the real `Custodio` code with the real
  `PolkitAuthorizer` or the in-process authorizer, and the fake's answer (approve, deny, unreachable) is
  chosen by the test per call.

Size: five steps; no split proposed.

## Steps
- [ ] Test rig: a test-only server for the private bus that runs the real service type with a fake polkit
      whose answer (approve / deny / unreachable) the script sets per example, and records the actions it
      was asked under; the script starts a private `dbus-daemon`, the server and (for the absent case) can
      run without it. Write `scripts/test-docs-api.sh` first with the example format (below) and the
      negative-control scaffolding, red against today's `docs/api.md`.
- [ ] Example format and runner: each operation's example in the document is a fenced block with a marker
      that names the polkit mode, followed by the busctl command and the exact documented result (output or
      error name). The runner extracts every such block from the document (nothing hard-coded in the script
      apart from the fixtures an example refers to), runs them in document order on one service with state
      carried over (import, list, replace, sign, delete), and compares the result. It fails if the document
      has no example for an operation, or an example that does not run.
- [ ] Write the documentation in `docs/api.md`: (a) detection on the host and from a flatpak with
      `--system-talk-name=com.rfirma.Custodio1`, and what a client sees when the service is absent, not
      activatable, or blocked by the sandbox, following `docs/findings.md` F68 (including that absent and
      blocked are indistinguishable through the proxy); (b) for each method, arguments, bounds and results
      (already present; keep, and add what is missing), plus the polkit action it asks and whether a dialog
      shows; (c) for every error name, when it occurs; (d) ownership (the bus uid, no owner argument, another
      user's id is `NoSuchKey`) and its consequences for a client; (e) what is journalled, the app-id record,
      and a pointer to `docs/audit.md`; (f) the signature takes the digest/data the client prepared: hashing
      stays in the client, the service never hashes `data` except as PSS says; (g) the compatibility rule,
      by reference to `docs/audit.md` "Compatibility rule" and stated for the interface too only as far as
      SPEC.md says; (h) one short busctl example per operation (`ListKeys`, `ImportP12`, `ReplaceCertificate`,
      `Sign`, `DeleteKey`).
- [ ] Comparison rules: results that change between runs (ECDSA/PSS signatures, long DER lists)
      are documented with a named placeholder and checked by a stated rule (length, prefix, or `openssl` verification),
      never a bare wildcard. The `Sign` example signs a digest the client made with `openssl dgst` and the runner
      verifies it over the original data, which shows the service did not hash. One detection example runs on the
      private bus with no server and no activation file: `NameHasOwner` false, name missing from
      `ListActivatableNames`, `StartServiceByName` fails `ServiceUnknown`. D-Bus and systemd error names in the
      detection section are written inline, not as `- error` / `- action` / `- in` / `- out` list lines, so
      `api-contract` does not read them.
- [ ] Make the examples run: fix the examples and the documented results until the runner passes against the
      service; add the negative controls (below); add `scripts/test-docs-api.sh` to `test-scripts` in the
      `justfile`.
- [ ] README links `docs/api.md`. Run `just quick`, `scripts/test-docs-api.sh` and `just api-contract` until
      they pass.

## Amendments
- Step 4 no longer cites "evaluator notes 3-5" (there was no earlier review); the rules stay as written. The test-only server
  needs no journal sink that writes to a file (no evidence reads the journal): it uses the in-memory sink of the real service
  type. The examples read `busctl --system ...` as a person types them on the real bus, and the runner changes only the bus
  selection (a shell function maps `--system` to `--address=` of the private bus). `busctl` prints `Call failed: <message>`
  and not the error name (`docs/findings.md` F91), so an example that fails names the error in its info string and the document
  gives the fixed message of each error; the runner checks the printed message equals the one of that name.
