# F196 — The storage classifier: same answer at every start, or an explained unknown

## Scope

The decision is already taken in `docs/findings/F189.md`: the cause of the `unknown` then `not-encrypted` for `252:0` was
**not reproduced** (inferred, not verified), so only **route 2** is built: `unknown` stays and the service says why. The
"fix the cause" route is closed (nothing to fix is proven); F189's reproduction says a complete chain always gives
`not-encrypted` and every incomplete read gives `unknown`, and `storage_stability.rs` keeps that as a regression guard.
No unit setting is added (F189 decided). F180's rules stay: nothing in F189 showed one wrong. The `doctor` part of
acceptance 14 is F203 and the CLI's use of the reason is not built here.

Built here:

- **Reason in the classifier.** The classifier returns, next to the `StateStorage`, an enumerated reason for each
  `unknown` and none for `encrypted` / `not-encrypted`. One value per cause in F189's table, in the same order of
  precedence as the code: no covering mount or unreadable mount table; filesystem not on the block list or anonymous
  device; sysfs chain missing or incomplete (canonicalize of the node, `dm/`, `dm/uuid` unreadable/empty/unknown prefix,
  `slaves/` unreadable or empty, partition or disk shape wrong, loop or depth limit); layer not classified (md that is
  not all encrypted, other dm uuid, no hardware link or a disk with slaves); members disagree; fscrypt not excluded (the
  check failed or says encrypted); state directory cannot be resolved. The exact names (short, lower-case, stable) are the
  builder's. The existing `classify`/`classify_with` callers (`startup.rs`, tests, `main`) keep working; the verdict of every
  existing input is unchanged.
- **Bus.** A read-only, bus-only addition to the API, found once at start like the verdict: the reason for the current
  `unknown`, an empty/absent value otherwise. It asks no polkit, writes no journal entry, changes nothing, and the snap
  socket does not serve it. Property or method is the builder's choice, within the compatibility rule of `docs/api.md`
  (names only added, none changed); a client that gets `UnknownMethod`/`UnknownProperty` shows nothing. `docs/api.md`
  documents it, with the list of values and what each means for the operator, and `docs/audit.md` if the journal line
  gets the field (optional; if added, the existing `CUSTODIO_STATE_STORAGE` is unchanged). The existing `StateStorage`
  method and its three values are unchanged.
- **Out of scope:** the CLI/doctor text (F203), packaging, unit hardening, the fscrypt/`statx` logic itself.

Environment: no dm device can be created in this container (F189: no `/dev/mapper`, `dmsetup`, loop control; no
`CAP_MKNOD`). So every case runs on fixture sysfs/mountinfo trees (the existing `tests/state_storage/tree.rs`) and the bus
case on the existing private bus of `storage_api.rs`; nothing needs privileges.

Cost: `storage_stability.rs` is about 15 table-driven unit cases on temp dirs, no TPM, no polkit, well under 1 s in total,
parallel with the other test binaries by default (like `state_storage`, measured as a similar suite in `just quick`).
Bus cases extend `storage_api.rs`, each about the cost of the existing ones (private bus, under 2 s, parallel). No e2e case:
the behaviour does not depend on the distribution, and the real-system answer is proven at the checkpoints by the existing
doctor/e2e features. `just mutants-diff F196` runs on the changed lines of `storage.rs`, `dbus.rs` and the audit/startup
glue only; its time is bounded by the changed mutants, and the builder reports the measured time in PROGRESS.md. If it
exceeds `budgets.tsv`, ask for more in BLOCKED.md.

## Evidence
- Route 2 is taken because the cause is only inferred → `docs/findings/F189.md` (already merged); no test greps it → no new
  evidence needed beyond the rows below.
- Same storage, same answer at every start (regression guard, no flip) → `cargo test -p custodiod --test storage_stability`,
  case "complete chain repeated": the same fixture classified many times (and from several threads at once) gives
  `not-encrypted` with no reason every time; the incomplete-chain fixtures give the same `unknown` and the same reason every
  time → pass. Fails if the classifier reads any state that changes between calls.
- The reason is exposed for each unavoidable unknown → `storage_stability`, one case per cause: no covering mount; unreadable
  mountinfo; fs not on block list (tmpfs/overlay/nfs); anonymous `0:N` device; state dir cannot be resolved; `sys/dev/block`
  node missing; `dm/` absent; `dm/uuid` missing; `dm/uuid` empty; `dm/uuid` unknown prefix (`CRYPT-VERITY`, `CRYPT-INTEGRITY`
  must not be encrypted); `slaves/` missing; `slaves/` empty; members disagree (crypt + plain); md with plain members; partition
  whose disk lacks `dev` or has `partition`; disk without `device` link; disk with slaves; a loop in `slaves/`; depth over the
  limit; fscrypt check fails; fscrypt says encrypted → each gives `unknown` and its own reason value, and the values of
  distinct causes group as the contract lists (a mutant that returns the wrong or a constant reason fails).
- `unknown` is never turned into `encrypted` (a test case for each unknown of F180 and F189) → the same cases assert the
  verdict is `Unknown`, not `Encrypted` and not `NotEncrypted`, and a no-reason result only ever accompanies `encrypted` /
  `not-encrypted` → pass.
- F180's rules stay → `cargo test -p custodiod --test state_storage` unchanged and green (no edits to that file's
  expectations); the verdict of the F189 case A fixture is `not-encrypted`, and LUKS1/LUKS2/PLAIN fixtures stay `encrypted`
  with no reason → pass.
- Read-only, bus-only addition → `cargo test -p custodiod --test storage_api`: new cases return the reason of each of the
  three verdicts' service (empty for encrypted and not-encrypted, the value for unknown, over the real bus type), call asks no
  polkit and writes no journal entry and leaves the state unchanged (as the existing `bus_asks_no_polkit` /
  `bus_changes_no_state` do for the new name) → pass; the snap socket does not serve it →
  `cargo test -p custodiod --test snap_socket_surface` (existing surface test, extended by the new name if it lists names).
- Under the compatibility rule, checked by `just api-contract` → `just api-contract` and `scripts/test-docs-api.sh` → pass:
  the documented name, type and value list match the live service, no existing name or value changed; the doc test's
  negative controls still fail on a broken copy.
- Journal field, if added → `start_journals_storage_field` extended: `CUSTODIO_STATE_STORAGE` unchanged, the new field
  present only on unknown; skipped (`[-]`-like) if the builder adds no field.
- The tests detect wrong code → `just mutants-diff F196` → no surviving mutant in the changed lines.
- No regression → `just quick` → green.
