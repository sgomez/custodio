# F23 — Miri, AddressSanitizer and fuzzing for the new FFI entry points

## Scope
Proves, with the tools the repository already has, that the FFI entry points added or changed by
F19–F22 are free of undefined behaviour and cannot be crashed by arbitrary arguments or call
orders. Production code changes only if a tool finds a bug, apart from these planned exceptions:
the `unsafe_code` lint attributes (below), a sign-call counter in `fake.rs`, widening the
visibility of the `SERIAL` lock in `ffi/tests.rs`, and one added line in the justfile `test` recipe.

- **Miri / ASan (unit tests).** `just miri` and `just asan` already run all `--lib` tests of
  `custodio-pkcs11`, which use the fake service. Nothing in them is gated off (no `cfg(miri)`, no
  `#[ignore]`; the builder confirms this and may not add either). What is added: tests in the
  existing files `src/ffi/tests/{composed,multipart,login}.rs` (or a new `src/ffi/tests/sanitizers.rs`,
  to stay under the 5000-token file gate) for the gaps in the Evidence table. Tests that already
  cover a row are cited, not copied.
- **Fuzz target.** `ffi/fuzzing.rs` (`step`, `% 17` ops) gains: `C_SignUpdate`, `C_SignFinal`,
  `C_Login`, `C_Logout`; the composed mechanism types in the `C_SignInit` mechanism choice and in `C_GetMechanismInfo`:
  the three ECDSA ones (`CKM_ECDSA_SHA{256,384,512}`), which the fake supports, and the three RSA
  ones (`CKM_SHA{256,384,512}_RSA_PKCS`), which it must refuse;
  and the `C_Sign` op keeps its sizes. Any order, any sizes: every op is chosen from the script
  bytes with no state kept by the harness. If the file would exceed the token gate, the new ops go
  in `src/ffi/fuzzing/` submodule(s); the `--exclude` of `just crap` is then extended to those
  files only (the same harness-only exclusion that exists for `fuzzing.rs`) and `docs/decisions.md`
  is not touched. `fuzz/Cargo.toml` and `fuzz_targets/pkcs11_args.rs` stay as they are unless a
  second target is wanted (not planned).
- **`forbid(unsafe_code)` outside FFI.** Today the crate has no such attribute (only the doc
  comment in `lib.rs`; `ffi`, `unsupported` hold the `unsafe extern "C"` functions). Add
  `#![deny(unsafe_code)]` to `lib.rs`, `#![allow(unsafe_code)]` (with the comment justifying it) in
  `ffi.rs` and `unsupported.rs` only, and `#![forbid(unsafe_code)]` in `module.rs`, `composed.rs`,
  `token.rs`, `backend.rs` and `fake.rs`. Test modules under `ffi/` inherit the FFI allowance.
- **The fake has no RSA key (decision: option b).** `fake.rs` holds one P-256 key; the existing tests
  assert that `C_GetMechanismInfo` refuses `CKM_SHA{256,384,512}_RSA_PKCS` and that the list has 4
  entries (`CKM_ECDSA` plus the 3 composed ECDSA types). Those assertions stay as they are. All
  "composed" rows below therefore cover the 3 ECDSA composed types, and the RSA composed types are
  checked only as refused. RSA signing is covered by `module` tests that use their own backend.
- **Sign-call counter.** `fake.rs` gains `pub static SIGN_CALLS: AtomicUsize` (`cfg(test)`, like `LAST_INPUT`), incremented by
  `FakeBackend::sign`. Tests read it as a before/after difference under the `SERIAL` lock.
- **Serialising the fuzzing tests.** `fuzzing::run` calls `C_Finalize` at its start and end, so
  `ffi::fuzzing::tests` must not overlap with `ffi::tests`, which holds `SERIAL` (private to
  `ffi::tests` today). `SERIAL` becomes `pub(in crate::ffi)`; every `fuzzing::tests` test takes it
  first (`super::super::tests::SERIAL`), poison-tolerant like `Session::new`, and holds it for the
  whole test, including its reads of `SIGN_CALLS` and `LAST_INPUT`. The pass is checked by running
  the whole lib suite with `--features fuzzing` and default threads, repeated 5 times.
- **Environment.** The pinned nightly `nightly-2026-10-26` with `miri`, `rust-src` and
  `llvm-tools-preview` must be installed (`just setup` does it); earlier sessions could not run
  `just miri` for lack of it. If it cannot be installed (no network), write `BLOCKED.md`.

Left for other features: running the fuzzer for long (CI/nightly campaigns), the audit journal,
e2e. No change to `features.json`, `SPEC.md` or the justfile recipes `miri`, `asan`, `fuzz-build`,
`lint-fuzz`. The feature fits in five steps; no split.

## Steps
- [ ] Install the pinned nightly; run `just miri` and `just asan` on the tree as it is and record
  the baseline (pass/fail, test count) in the session notes; fix any UB or leak they report, test
  first.
- [ ] Add `SIGN_CALLS` to `fake.rs` with `fake::tests::sign_counter_counts` (two `sign` calls move it
  by exactly 2, a `list_certificates` call by 0), and make `SERIAL` reachable from `ffi::fuzzing`.
- [ ] Write the missing unit tests (Evidence rows marked "new"), red/green against the current
  code, and run each by name under Miri and ASan.
- [ ] Extend the fuzz harness: new ops, composed mechanism types, `C_Login` arguments; add the
  `--features fuzzing` unit tests that replay hand-built scripts; `just fuzz-build`,
  `just lint-fuzz` and `just lint` green.
- [ ] Add the `unsafe_code` lint structure; prove it with a throwaway `unsafe` block.
- [ ] Mutation checks (below), then run `just miri && just asan && just fuzz-build && just
  lint-fuzz` and `just check`; append `PROGRESS.md`.

## Evidence
Commands: `MIRI(name)` = `cargo +nightly-2026-10-26 miri test -p custodio-pkcs11 --lib --locked <name>`;
`ASAN(name)` = `RUSTFLAGS="-Zsanitizer=address" cargo +nightly-2026-10-26 test -p custodio-pkcs11 --lib
--locked --target "$(rustc +nightly-2026-10-26 -vV | sed -n 's/^host: //p')" --target-dir target/asan <name>`
(the same flags as `just asan`). Every row that says "under Miri and ASan" is run with both for each
test it names, and passes with exit 0 and "1 passed" (or the count of the filter); the full recipes
run at the end.

- Nothing hides tests from the sanitizers → `grep -rnE 'cfg\(miri\)|cfg_attr\(miri|#\[ignore' crates/custodio-pkcs11/src` → no output.
- Sign-call counter works → `fake::tests::sign_counter_counts`: two `sign` calls raise `SIGN_CALLS` by exactly 2, `list_certificates` by 0 → passes; fails if the counter is not incremented in `sign`.
- `C_GetMechanismList` with the composed mechanisms: length query (NULL list), exact size, too-small, larger buffer → `ffi::tests::list_outputs_respect_the_callers_sizes` (existing, 4-entry list) plus **new** `ffi::tests::mechanism_list_sizes_with_composed`: NULL list gives `CKR_OK` and count 4; a buffer one short gives `CKR_BUFFER_TOO_SMALL` with the count set and the buffer untouched (sentinel bytes intact); a larger buffer writes exactly 4 entries, the sentinel after them intact, and the entries contain `CKM_ECDSA_SHA256/384/512`; the RSA composed types are absent → passes under Miri and ASan.
- `C_GetMechanismInfo` with the composed mechanisms → `ffi::tests::composed::composed_mechanism_info` (existing; fills a `MaybeUninit`, rejects NULL; ECDSA composed types succeed, `CKM_SHA{256,384,512}_RSA_PKCS` give `CKR_MECHANISM_INVALID`) → passes under Miri and ASan.
- `C_SignInit` with composed mechanisms (parameter NULL/non-NULL, NULL mechanism pointer, RSA composed refused) → `ffi::tests::composed::composed_sign_init_parameter` (existing) plus **new** `ffi::tests::composed_sign_init_null_mechanism`: for each of the 3 ECDSA composed types, a NULL mechanism pointer gives `CKR_ARGUMENTS_BAD` and no operation is left active (a following valid `C_SignInit` is `CKR_OK`); and **new** `ffi::tests::composed_rsa_types_refused_by_sign_init`: `C_SignInit` with each RSA composed type returns the same refusal code the module gives today (the builder reads it; expected `CKR_MECHANISM_INVALID`), no operation is left active, and `SIGN_CALLS` did not move → passes under Miri and ASan.
- `C_Sign` with composed mechanisms, length query and too-small buffer, for the 3 ECDSA composed types → **new** `ffi::tests::composed_sign_length_query_and_small_buffer`: per type, `C_Sign` with NULL signature returns `CKR_OK` and length 64 and leaves the operation active (`SIGN_CALLS` unchanged); with a heap `Vec<u8>` of exactly 63 bytes plus guard checks it returns `CKR_BUFFER_TOO_SMALL` with the length set, buffer untouched, operation still active; the retry with a `Vec` of exactly 64 bytes gives `CKR_OK` with the fake's signature (`[7; 64]`) and `SIGN_CALLS` up by exactly 1 → passes under Miri and ASan.
- `C_SignUpdate` / `C_SignFinal`, including NULL part, zero length, huge length, NULL length pointer, length query, too-small buffer → `ffi::tests::multipart::sign_update_and_final_arguments` and `sign_update_rules_through_the_c_functions` (existing) plus **new** `ffi::tests::multipart_final_small_buffer_keeps_operation`: the output buffers are heap `Vec<u8>` of exactly the length passed (so ASan sees any write past `*len`; no 64-byte stack arrays), and the test also checks a canary byte placed in a larger allocation right after the slice. `C_SignFinal` with a 63-byte buffer returns `CKR_BUFFER_TOO_SMALL`, the next `C_SignFinal` with a 64-byte buffer returns `CKR_OK` with the same bytes as a one-shot `C_Sign` of the concatenated parts → passes under Miri and ASan.
- `C_Login` / `C_Logout` including NULL and empty PIN pointers → `ffi::tests::login::login_accepts_any_pin`, `login_never_dereferences_the_pin`, `login_invalid_session`, `login_security_officer_fails`, `logout_is_ok` (existing; cover NULL with length 0 and 4, empty slice pointer, dangling pointer, `CK_ULONG::MAX` length) → pass under Miri and ASan. Miri's checks make the dangling-pointer test fail if the module ever reads the PIN; mutation (c) below shows it.
- Sanity that the sanitizers can fail on these functions → one-off mutations, results recorded in `PROGRESS.md`, not committed: (a) `C_GetMechanismList` writes `count + 1` entries; (b) `C_SignFinal` writes one byte past `*len` (detectable because `multipart_final_small_buffer_keeps_operation` and the sign tests use exact-size heap buffers); (c) `C_Login` reads `*pin`; (d) the fuzz harness reads one byte of the PIN buffer it hands to `C_Login` when that buffer is dangling (see `login_arguments`). Expected: (a)(b) `just miri` and `just asan` each fail; (c) `just miri` fails (ASan may not); (d) `cargo test -p custodio-pkcs11 --features fuzzing --lib fuzzing::login_arguments` fails under Miri (`MIRI(--features fuzzing fuzzing::login_arguments)`). The tree is restored with `git checkout` and `git status` is clean before committing.
- Fuzz tests do not race with the rest → `ffi::fuzzing::tests` tests all take `SERIAL`; `for i in 1 2 3 4 5; do cargo test -p custodio-pkcs11 --features fuzzing --lib --locked || exit 1; done` passes with default test threads; `grep -c 'SERIAL' crates/custodio-pkcs11/src/ffi/fuzzing.rs` is at least the number of fuzzing tests. The `fuzzing::` tests are also run by name under Miri (reduced counts, see below) and ASan with `--features fuzzing`.
- Fuzz target covers the new mechanisms → **new** `ffi::fuzzing::tests::script_reaches_composed_mechanisms` (cfg `feature = "fuzzing"`): a hand-built script calls `C_GetMechanismInfo` on `CKM_ECDSA_SHA256`, then `C_SignInit` with `CKM_ECDSA_SHA256`, `C_SignUpdate` with two parts, `C_SignFinal`; the test asserts `SIGN_CALLS` rose by exactly 1 and `LAST_INPUT` is the raw SHA-256 digest of the concatenated parts (a constant test vector, e.g. SHA-256 of "abc") → `cargo test -p custodio-pkcs11 --features fuzzing --lib fuzzing::script_reaches_composed_mechanisms` passes; fails if the ops are not wired or the composed type is not selectable. A second script with `CKM_SHA256_RSA_PKCS` in `C_SignInit` + `C_SignUpdate` + `C_SignFinal` asserts `SIGN_CALLS` did not move (refused through the fake). The `--features fuzzing` test command is added to the `test` recipe of the justfile (an addition only) so CI runs it.
- Arbitrary multi-part sequences in any order and with any sizes → **new** `ffi::fuzzing::tests::sequences_in_any_order`: for every permutation of {init, update, final, sign} (24) and sizes 0, 1, 129, 4096 (and a NULL part), a script built by the test runs through `fuzzing::run` without panic and leaves the module finalized (`C_Initialize` afterwards returns `CKR_OK`, then `C_Finalize`). For the permutation init, update, final, `SIGN_CALLS` rose by exactly 1; for init, final, update (final first) it did not rise by more than 1; for update, final, init, sign without a prior init it stayed 0 until the sign after init. Plus a deterministic xorshift set of 2000 random scripts of length ≤ 512 → no panic, no abort. Under Miri the counts shrink via `cfg!(miri)` to 24 permutations x sizes {0, 129} and 20 random scripts (a reduced loop count, not a skipped test). Fails if an op is missing, because the counter assertions would not hold.
- Arbitrary `C_Login` arguments → **new** `ffi::fuzzing::tests::login_arguments`: scripts that contain only login and logout ops (no sign op, so `SIGN_CALLS` can only move if the login op reaches the service) with random session, user type (valid and invalid), NULL/non-NULL PIN and lengths up to `CK_ULONG::MAX` run without panic, and `SIGN_CALLS` stays at 0 across the whole test. The harness never allocates a PIN buffer shorter than the length it passes, except when the length is larger than any buffer, in which case the pointer is NULL or dangling; documented in the module comment, because `C_Login` never reads it. Mutation (d) above shows the dangling case is checked by Miri → passes under Miri and ASan.
- The target builds → `just fuzz-build` → exit 0, builds `pkcs11_args`; `just lint-fuzz` → exit 0 (clippy clean, release guard still refuses `fuzzing`).
- The fuzzer actually runs with the new ops → `cd crates/custodio-pkcs11/fuzz && cargo +nightly-2026-10-26 fuzz run pkcs11_args -- -max_total_time=60` → ends without a crash artefact; one-off mutation (b) makes it find a crash within the same 60 s (recorded in `PROGRESS.md`, mutation reverted).
- Lint of the new code → `just lint` → exit 0 (includes the `--features fuzzing` clippy).
- `forbid(unsafe_code)` holds outside FFI → `grep -n 'forbid(unsafe_code)' crates/custodio-pkcs11/src/{module,composed,token,backend,fake}.rs` prints one line per file; `lib.rs` holds `deny(unsafe_code)` (one `grep -n 'deny(unsafe_code)'` line) and still mentions unsafe in its doc comment; `ffi.rs` and `unsupported.rs` hold `allow(unsafe_code)` with a justifying comment; `grep -rln 'unsafe' crates/custodio-pkcs11/src` lists only files under `ffi`, `ffi.rs`, `unsupported.rs`, `lib.rs`. `cargo build -p custodio-pkcs11` passes. Throwaway check: adding `unsafe { }` to `module.rs`, `token.rs` or `module/signing.rs` makes `cargo build` fail with an `unsafe_code` error; removed afterwards. The rest of the workspace keeps its `#![forbid(unsafe_code)]` (`grep -rn forbid crates/*/src/{lib,main}.rs` unchanged apart from the new `deny` in `custodio-pkcs11/src/lib.rs`).
