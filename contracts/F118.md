# F118 — Sign, delete and replace certificate for every storage kind

## Scope
Built in `custodiod`. After F114 (TPM signing), F115 (credentials), F116 (store with kinds) and F117 (choice at import),
the only thing missing in the service is the sign path for a TPM record: `Custodio::sign_record` still answers
`Internal` for it (F116's interim). This feature closes that and proves the three key operations for all three kinds.

- **Sign dispatches on the stored kind.** TPM kind: `tpm::sign::sign` through the service's `TpmAccess` (the one
  `Custodio::with_tpm` already carries; the private key is never in the service). Encrypted kinds: decrypt through the
  credentials access point, sign, drop (as today; the key is `secrecy`/`zeroize` and not kept). Nothing else chooses the
  path: there is no retry of a TPM record through the credential service or the reverse. Mechanism parity, bounds and
  the `SignError` classes are F114's and `sign::sign`'s and are not re-proven here beyond one signature per mechanism
  family and key type.
- **Polkit stays first and uncached** for every kind: the authorization, then (only if granted) the TPM or the
  decryption. Delete and replace keep M3's order and asking per call.
- **Failure classes at sign, all failing closed.** A TPM blob that does not load (cleared TPM, other parent:
  `ParentMismatch`; a damaged private area: `LoadFailed`) and a credential that cannot be decrypted
  (`CredsError::CannotDecrypt`: TPM cleared for a TPM-bound credential, host key changed) are the "key lost" class.
  They get a documented D-Bus error name, **distinct from `Internal` and from the transient class**, under the
  compatibility rule (an existing name keeps its documented meaning; a name documented as "`ImportP12` only" is not
  widened, a new one is added instead). The builder picks the name(s): one for both or one per source, but the person
  must be able to tell "this key can no longer be used" from "try again later". The transient class (TPM absent or
  failing at sign, `Lacks`, `BadResult`, credential service unavailable) also gets a documented name, existing or new;
  `Internal` stays for bugs and store faults. Added to `custodio-client`, `ServiceError` (fixed messages, nothing from
  the input or the response codes), `docs/api.md` (`## Errors` and the `Sign` section), so `just api-contract` stays green.
- **Journal.** Each failed sign leaves exactly one entry through the existing outcome `signing_failed`
  (an authorized sign that failed). The distinct outcome or field naming the cause, and its text in `docs/audit.md`,
  are F120; this feature does not change `audit/`.
- **The key stays.** After any of these failures the record is byte-for-byte unchanged, `ListKeys` still lists the key
  with its certificate, and `DeleteKey` removes it (also when the TPM is absent or cleared and when the credential
  cannot be decrypted: delete never touches the TPM or the credentials). Nothing is deleted or migrated by sign.
- **Delete and replace certificate for every kind.** Delete: unchanged M3 behaviour for the three kinds, plus the
  lost-key case above. Replace: the comparison of the certificate with the key (TPM kind: the blob's public area, no
  TPM call; encrypted kinds: decrypt for the comparison and drop, as today); the stored protected form and the kind do
  not change; a key that can no longer be decrypted cannot be compared, so the replace fails with a documented name
  (existing; the builder uses `Internal` as today unless a documented name fits) and changes nothing.
- **Children and descriptors** (`docs/findings/F117.md`). A `systemd-creds` child must inherit no descriptor of the
  service, so a TPM context open on another thread never reaches it. The service has `forbid(unsafe_code)`, so closing
  descriptors in the child is not done with `pre_exec`; how it is met is a step that researches and decides (see Steps),
  within these limits: no `unsafe` in `custodiod`, no weakening of `forbid(unsafe_code)`, and the child's argv and
  stdin handling stay as F115 fixed them (plaintext never in argv, env or a file).
- **Left to other features.** The kind in the API and list (F119); the cause and the kind in the journal and
  `docs/audit.md` (F120); the purge (F121); the CLI and PKCS#11 wording; end-to-end cases and the install/lifecycle
  tests, proven at the checkpoints (F132/F146) and the e2e features. Mutants of the sign dispatch run in this
  feature's `verify` (`just mutants-diff F118`); the files it changes are already on the `mutants` list, any new
  non-test file joins it.
- **Size.** About five steps; no split proposed. `dbus.rs` is 555 lines: the sign dispatch and the error mapping go in a
  new file under `src/dbus/` (each file under 5000 tokens, the check-files gate).

Environment check (run in the dev container while writing this contract): `cargo test -p custodiod --test creds --locked
cleared_tpm_cannot_decrypt` → `1 passed`. That is the real `systemd-creds` against a TPM-bound credential with a cleared
`swtpm`, through the `Daemon` helper of `tests/creds/env.rs`; `tpm_sign` already clears an `swtpm` under a stored blob
(`rig.tpm.clear()`). `sign_kinds` reuses these helpers and needs nothing else.

## Evidence
All `sign_kinds` rows run the real service on the private bus with fake polkit, the in-memory sink, `swtpm` and, for the
kinds that need it, the real `systemd-creds` (as `creds` does); an injected-failure row uses a double for the access
point it names. Each row runs for RSA 2048 and P-256.

- Sign works for each kind, and verifies with the key's certificate by an implementation independent of the service →
  `sign_kinds::signs_each_kind` → for TPM, encrypted TPM-bound and encrypted host-bound, one signature per mechanism
  family (`CKM_RSA_PKCS`; `CKM_RSA_PKCS_PSS`; `CKM_ECDSA`) verified with `openssl` against the stored certificate's key.
  The record read back has the kind asked for (a TPM record holds a blob and no credential; the encrypted ones a
  credential and no blob). A TPM key signs inside the TPM and an encrypted key is decrypted for each signature and
  dropped: for the TPM kind the TPM is opened once per signature and `decrypt` is never called; for the encrypted kinds
  `decrypt` is called once per signature (the next one decrypts again) and the TPM is never opened (counting access
  points). Negative control: a key signed by the wrong certificate's key fails the
  same check.
- Every signature calls polkit, no cached authorization → `sign_kinds::polkit_every_signature` → for each kind three
  signs in a row make three polkit calls (the fake counts them); with polkit flipped to deny between two signs the
  second fails `PolkitDenied`, and on that denial the TPM `open` count and the credentials `decrypt` count do not move.
- A TPM blob that does not load, a credential that cannot be decrypted → `sign_kinds::lost_keys::{tpm_cleared_under_tpm_key,
  tpm_cleared_under_tpm_bound_credential, host_key_changed, damaged_blob}` → the cleared `swtpm`
  case uses the real `swtpm` cleared with `clear()` after the import (`tpm_cleared_under_tpm_bound_credential` with the
  real `systemd-creds`); the call fails with the documented "key lost" name (the exact string, read from the
  `custodio-client` constant) and not `Internal`; `host_key_changed` uses the credential double and `damaged_blob` a blob with its private
  area damaged. Control first: before the clear, the same call signs.
- The transient class is told apart from the lost class → `sign_kinds::transient::{tpm_absent, tpm_faulted,
  tpm_lacks_the_mechanism, credentials_down}` → each fails with its documented name, which is not the "key lost" name
  and not `Internal`; after the access point is healed the same key signs again (nothing was deleted or marked).
- No fallback → in every row of the two tests above, one assertion per row: a failed TPM sign makes no `decrypt` call, a
  failed credential sign makes no TPM `open` call, and neither makes an `encrypt` call; the record file is
  byte-identical before and after (including after a failure with the TPM-bound credential).
- One journal entry per failed sign → in each row above, the sink holds exactly one entry for the call, operation
  `sign`, outcome `signing_failed`, the key id and the caller; a successful sign leaves exactly one `signed`; a denied
  one exactly one `denied`. No key, blob or credential bytes in the entry.
- The key stays listed and can be deleted → `sign_kinds::lost_keys_stay_listed_and_deletable` → after each lost-key
  and transient failure, `ListKeys` still returns the key with its certificate, and `DeleteKey` succeeds with the TPM
  absent or cleared and the credential undecryptable; the owner area then holds no file for the key and a later import
  of the same id (healed access points) succeeds.
- Delete works for every kind → `sign_kinds::delete_each_kind` → after a sign, `DeleteKey` removes the record and the
  certificate for TPM, TPM-bound and host-bound; `Sign` then fails `NoSuchKey`; the TPM `open` count and the credentials
  counts do not move during delete.
- Replace certificate works for every kind → `sign_kinds::replace_each_kind` → a second certificate for the same key
  replaces the first; `ListKeys` shows it; the kind and the protected form (blob or credential bytes) are unchanged; a
  sign afterwards verifies against the new certificate; a certificate for another key fails `CertificateMismatch` and
  changes nothing; for the TPM kind the TPM `open` count does not move during the replace. For a credential that cannot
  be decrypted the replace fails closed and the stored certificate is unchanged (`sign_kinds::replace_lost_key`).
- The `systemd-creds` child inherits no descriptor of the service → `sign_kinds::creds_child_inherits_no_descriptor` →
  the test process holds a descriptor without close-on-exec; the real `SystemdCreds::run` path starts a substitute
  program that prints its `/proc/self/fd`; nothing above 2 is reported. Negative control: a plain `Command` in the same
  harness reports the descriptor every time, so the test fails without the fix. As a symptom check,
  `sign_kinds::concurrent_kinds` signs a TPM key and a TPM-bound key at once on the private bus and both succeed.
- Errors documented → `just api-contract` (in `just quick`) → green; it fails when a new name is in the client but not in
  `docs/api.md` or the live service. Not asserted by grepping wording.
- The sign mapping is tight → `just mutants-diff F118` → 0 missed (a mutant that maps a lost key to the transient name,
  or falls back to the other kind, is killed by the rows above).

- Shipped launcher under the hardened unit (Steps, descriptor step) → the launcher is `/usr/bin/bash`
  (`creds::systemd::LAUNCHER`). In the dev container: `test -x /usr/bin/bash && readlink -f /usr/bin/bash` →
  `/usr/bin/bash`; `systemd-analyze syscall-filter @default | grep -w execve` → `    execve` and
  `systemd-analyze syscall-filter @system-service | grep -w @default` → `    @default` (the unit allows
  `@system-service`); `systemd-analyze syscall-filter @privileged @resources | grep -cw execve` → `0` (the unit denies
  those groups, so `execve` stays allowed). `ProtectSystem=strict` keeps `/usr` executable and `/proc/self/fd` is in
  `ProcSubset=pid`. The full proof under the real unit is at the checkpoints (F132/F146).
- A missing launcher at run time fails closed as the transient name, not `Internal`, and not as a signature →
  `sign_kinds::transient::missing_launcher` → the real `systemd-creds` signs (control), then its launcher is a path that
  does not exist: `Sign` fails `TemporarilyUnavailable`, the record is unchanged, one `signing_failed` entry; with the
  launcher back it signs again.
