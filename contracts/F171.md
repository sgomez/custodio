# F171 — Research: the Firefox snap in the M5 VM image

## Scope
Research only. It writes `docs/findings/F171.md` (headed `## F171`, under 5000 tokens, conclusion
first, each claim marked **verified** or **inferred**, ends with `Decision: ` lines), its index line
in `docs/findings.md`, and `BLOCKED.md` only if the snap's base is older than the module supports.
No product code, no change to `SPEC.md`, `e2e/vm/` or `docs/decisions.md` (recording the snap-cache
choice there is left to the VM snap feature, which reads the `Decision:` lines). Probes are scratch
scripts outside the repository, not committed; the finding quotes commands and the lines of output.

It settles SPEC Design 6 "Check first" and the open questions "Which labels of the Firefox snap to
accept" and "The Firefox snap's base" (the "Profile locations" question for the snap is answered
here for the snap only; native browsers are F172's).

Environment, probed in this session:
- `scripts/vm-host-check.sh` reports swtpm, seed tool, gpgv and keyring OK, and the verified image is
  already in `~/.cache/custodio/vm-image/` (`ubuntu-26.04-minimal-cloudimg-amd64.img`, 422 MB), so
  `e2e/vm/vm.sh start full` can boot it (`/dev/kvm` as F150 requires).
- `curl https://api.snapcraft.io/v2/snaps/info/firefox` answers from the dev container, with the
  `stable` channel at revision 9181, base `core26`, version 160.0-1, 312 MB. This is the store's
  answer today, not the installed snap: the finding uses it only to compare with what the VM
  installs (the SPEC says 154 / `gnome-46-2404` / core24 on the earlier lab VM, which is old).
- Not yet shown: that the guest reaches the store through the VM's user networking. Step 1 shows it
  before anything else; if it cannot, the finding says so and the contract's later steps are marked
  `- [-]` with the reason, and `BLOCKED.md` asks how the run gets snaps (a person's decision).

Cost: no new test, suite, e2e case or script in the repository, nothing in `e2e/*/cases.list`, and
nothing touches `budgets.tsv`. The probes boot the VM (about 1 to 2 minutes, F168 measured 503 s for a
whole `full` run) and install the snap: the download is hundreds of MB over the serial-console `run`
channel's one command, so every install and `snap` command uses `vm.sh run DIR -t <seconds>` with a
`timeout` (no more than 1500 s per command), output filtered with `tail`/`grep` (the channel is 15 KB/s,
F160). The finding records the measured install time and size; if the snap plus content snaps do not
fit in one command's 30 minutes, the install is split per snap (`snap install` per content snap).
The loop's `verify` is a few greps, under a second. Package gates, install and lifecycle tests,
`just e2e`: not run, and nothing here is proven only by them.

The feature fits in five steps; no split.

## Steps
- [ ] Boot the image in mode `full` and measure what it ships: `snap --version` / `command -v snapd`,
      `dpkg -l snapd apparmor`, `systemctl is-active snapd.socket`, `/sys/module/apparmor/parameters/enabled`,
      `aa-status` or `/sys/kernel/security/apparmor/profiles` count, `cat /proc/self/attr/current`,
      `dbus-daemon --version`, `ldd --version`, free disk space, and that the guest reaches the store.
      If snapd or AppArmor is missing, find how the run installs it from the archive (`apt-get install`
      of which packages, and whether AppArmor needs a kernel parameter or only a package) and measure
      that install, size and time.
- [ ] Install the Firefox snap from `stable`: record time, bytes downloaded, the snaps pulled
      (`snap list --all`: firefox, its content snaps, base, snapd), the revision of each, and
      `snap info firefox` (channel, base, version). Then the caching question: where snapd keeps the
      downloaded `.snap` and `.assert` files (`/var/lib/snapd/snaps`, `/var/lib/snapd/assertions`), and
      whether a run can reuse them by revision: `snap download` / `snap ack` + `snap install <file>`
      verified by assertions (`snap known`, `snap download` writes `.assert`), tried on a second boot
      with the files placed through the payload drive; and what stops silent refresh
      (`snap refresh --hold`, `snap set system refresh.hold`, or `snap refresh --time`; whichever
      works, with the command and its output).
- [ ] The snap's shape: from `/snap/firefox/current/meta/snap.yaml` and `snap info`, its base, apps
      (name, command, whether a daemon), hooks (`meta/hooks/`, and any hook declared in `snap.yaml`),
      and plugs; glibc of the base (the loaded `libc.so.6` under `snap run --shell firefox`, and the
      base's `ldd --version`) and whether it is at least what the module needs (the module's glibc
      floor is looked up in the repo: `docs/` and the packaging/targets' lowest glibc, stated with the
      file read). Cross-check the content snaps' own bases.
- [ ] The labels and profiles: the AppArmor profile name of every app and hook
      (`/var/lib/snapd/apparmor/profiles/snap.firefox.*`, `aa-status`), and what `/proc/self/attr/current`
      (and `SO_PEERSEC` on a socket, via a short `python3 -I` script) reports from inside
      `snap run --shell firefox`, from a hook-style shell (`snap run --shell firefox --hook configure`
      if it works), and from a helper app; which of them could load the module and reach the socket
      directory, so the finding can say whether accepting any label of the snap is needed or only
      `snap.firefox.firefox`. Record the exact label form (`snap.firefox.firefox (enforce)`) as bytes.
      Where its profiles live (`~/snap/firefox/common/.mozilla/firefox/`, XDG or not), by running
      the snap once and listing.
- [ ] Write the finding: a versions table (snap revision, base, snapd, AppArmor, dbus-daemon, glibc,
      kernel), the conclusion first, the `Decision: ` lines (snapd source, caching or not, which labels
      the socket accepts, the base); add its line to `docs/findings.md`; write `BLOCKED.md` only if
      the base is older than the module supports (otherwise say in PROGRESS.md that it was skipped);
      append `PROGRESS.md`; stop the VM; run `just quick`; commit `docs(F171): ...`.

## Evidence
- snapd shipped / AppArmor enabled at boot → the step-1 commands and output lines in the finding, with
  the image name and kernel → a stated yes/no for each, **verified**; if no, the `apt-get` command that
  installs it, with its size and time, **verified**. It would fail if the output lines do not match the
  statement.
- Download size and time of the Firefox snap with its content snaps → the install command, the
  `snap list --all` lines with revisions, bytes (`ls -l /var/lib/snapd/snaps`) and elapsed seconds → a
  table in the finding; the numbers come from the run, not from the store query.
- Caching by revision, verified by signed assertions, never refreshed silently → the `snap download` /
  `snap ack` / `snap install <file>` (or the route that worked) on a second boot from files placed
  through the payload drive, with the output showing the revision installed from the file and the
  assertion check; the hold command and `snap refresh --time` (or `snap get system refresh.hold`) output →
  a `Decision:` line saying cache or not, with the measured time saved; where the cache does not work,
  it says so and the decision is not to cache.
- Apps, hooks and their AppArmor labels → `snap info`, `meta/snap.yaml`, `ls meta/hooks`, the profile
  file names and the `/proc/self/attr/current` values read from inside the confinement, per app/hook
  (**verified**; a hook that cannot be started is stated **inferred** from its profile) → a table and a
  `Decision:` line naming the accepted labels (any app or hook, or only `snap.firefox.firefox`), with
  the reason from the table (for example whether a helper or hook profile can load the module).
- Base and glibc → `snap info firefox`, `meta/snap.yaml` `base:` line, and `ldd --version` /
  `libc.so.6` under `snap run --shell firefox` → versions in the finding; a `Decision:` line says the
  base supports the module (glibc not below the floor read from the repo) or `BLOCKED.md` asks the
  question. The comparison with the store query (9181 / core26) and with the SPEC's 154 / core24 states
  which one the run installs.
- Profiles location → the directory listing after one run of the snap → stated in the finding with the
  path, **verified**.
- Versions recorded → the table above (snap revision, base, snapd, AppArmor, dbus-daemon versions) →
  each with the command that printed it.
- Verify keywords and structure (`## F171`, the ten words, a **verified**/**inferred** mark, a
  `Decision: ` line, the index line) → the loop's `verify` command → exit 0.
- Index line in `docs/findings.md` and the file under 5000 tokens → `just quick`
  (`scripts/check-files.sh`) → green.
