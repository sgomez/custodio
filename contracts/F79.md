# F79 — Replace certificate leaves one journal entry and fails closed

## Scope
`ReplaceCertificate` (`Custodio::replace_call` in `src/dbus/replace.rs`, F78 order: bounds → credentials → lookup →
polkit → comparison → store) gains the journal entry. F74 already defines `OperationEntry::replace_certificate`,
`ReplaceOutcome`, the message id, the catalog entry and the `docs/audit.md` table; this feature emits them, adds the
fail-closed restore, and fills the documentation. F78's checks, order and atomic store do not change.

- **When.** Once polkit has been asked, exactly one `replace_certificate` entry is submitted through the existing
  sink (on a worker thread, via `run_on_thread` like `import_call`/`delete_call`) before the reply, with operation,
  the caller's uid and pid, the key id and the outcome: `replaced` (stored), `denied`, `authorization_unavailable`
  (polkit `Unavailable`/`BadSender`), `certificate_mismatch`, `storage_failure`. `storage_failure` covers every
  failure after approval that is not a mismatch: the store cannot replace the certificate, the key cannot be read
  again, the key is of a type the comparison does not support (reply `Internal` as in F78), and a key or certificate
  that vanished between the lookup and the store (the builder maps the reply it already has and states the mapping in
  `docs/audit.md`). Every approved call leaves one entry, so entries equal polkit asks.
  As for sign, import and delete (`docs/decisions.md`): once the arguments are valid, a missing sender or failed
  credentials lookup leaves one `authorization_unavailable` entry without uid and pid, replies
  `AuthorizationUnavailable`, and does not ask polkit. `InvalidArgs` and `NoSuchKey` (a missing id, another uid's id,
  a key F77 made unusable) leave no entry and make no sink call, also with the failing sink (they must not become
  `AuditUnavailable`).
- **Fail closed.** If the entry cannot be submitted, for any outcome, the reply is `AuditUnavailable`. For an
  approved replace the old certificate is back: `<id>-cert` byte-identical to before, `ListKeys` shows the old one,
  the key file untouched, no temp file left, a later replace with a working sink succeeds with its own one entry.
  The mechanism is the builder's (store, submit, restore the bytes read before the store; or stage and rename after
  the entry), within these limits: nothing is cached across calls, the restore is atomic like the replace (F78
  store operation), and the restore and the submit happen under the same per-(owner, id) lock as the replace, so a
  second replace or a delete of that id sees the old certificate or the new one only after its entry is submitted.
  If the restore itself fails, the reply is still `AuditUnavailable` (as import's rollback) and `docs/audit.md`
  ("Not guaranteed") says that case can leave the new certificate; the same section states that a `ListKeys` during
  the pending entry may see either certificate. These are documented residuals, not silent ones.
- **No new refusals.** No entry for `denied`/mismatch/store failure changes any F78 reply; only the sink failure adds
  `AuditUnavailable`.
- **Content.** Never certificate bytes (old or new), key bytes, data or signature: the entry model cannot hold them
  (F74); this feature proves it end to end.
- **Docs.** `docs/audit.md` replace section (outcomes as built including the `storage_failure` mapping, the order,
  the restore, the residual cases, a query per outcome that works) and `docs/api.md` `ReplaceCertificate`
  (`AuditUnavailable` applies; order; remove "does not write a journal entry"). Documentation tests extended for each
  statement added.
- **Left for other features.** Entry model, catalog and docs table (F74); the replace method, its checks and atomic
  store (F78); the app-id field (F80+); e2e journal cases with a real agent and the packaged catalog (F90/F100).
  Size: about five steps; no split.

Environment: nothing beyond the dev container. Tests use the private `dbus-daemon`, the async polkit double of
`tests/audit/bus.rs` (with `hold`), the `MemorySink`/failing/gate sinks as in `tests/delete_audit.rs`, and the
fixtures F78 added (`cert-*.der`, including `cert-p256-other-recert.der`). Tests needing an unwritable store skip as
root. No new tool, network or privilege.

## Evidence
All rows in `tests/replace_audit.rs` unless stated; "entry" is what the recording sink got, decoded to its wire
fields; the store is read from disk and through `ListKeys`/`Sign`.
- Exactly one entry per outcome → `replace_entry_per_outcome`: approved with a matching certificate → one entry
  operation `replace_certificate`, outcome `replaced`, the caller's uid and pid, the key id; Deny → `denied`;
  Unavailable and `BadSender` → `authorization_unavailable`; a certificate for another key → `certificate_mismatch`;
  a store that cannot replace (area made unwritable after the lookup, and `<id>-cert` made a directory; skipped as
  root) → `storage_failure`. Each: `len() == 1`, literal field values, polkit asked once, and the reply as in F78
  (`Internal` for storage failure). This is the single proof of result → outcome and reply. For `denied`,
  `authorization_unavailable`, `certificate_mismatch` and `storage_failure` the certificate is byte-identical.
- Unsupported key type or unreadable key after approval → unit test in `dbus/tests/replace_call.rs` (or
  `dbus/replace/tests.rs`) with a key that `certificate_matches_key` returns `None` for: one `storage_failure`
  entry, reply `Internal`.
- Missing sender / failed credentials → `replace_without_caller_leaves_unavailable_entry`: one
  `authorization_unavailable` entry with no uid and pid, `AuthorizationUnavailable`, polkit not asked, certificate
  unchanged.
- Refusals leave no entry → `replace_refusals_leave_no_entry`: bad id, oversized / unparsable / trailing-byte
  certificate, a missing id, another uid's id, a key made unusable by a pending delete: sink attempts 0 and polkit
  asks 0, also with the failing sink, and the reply is the F78 one.
- Failing sink restores → `replace_failing_sink_keeps_the_old_certificate`: an approved replace with the failing sink
  replies `AuditUnavailable`; `<id>` and `<id>-cert` byte-identical to the snapshot; the area holds no extra file;
  `ListKeys` shows the old certificate; `Sign` gives a valid signature; no `replaced` entry is recorded; a later
  replace with a working sink succeeds, `ListKeys` shows the new certificate and its one entry is `replaced`. Also
  for the sink failing on `denied`, `authorization_unavailable`, `certificate_mismatch` and `storage_failure`: reply
  `AuditUnavailable` (not the F78 error), nothing changed. Fails if the new certificate is kept after a failed
  submission.
- Restore fails → `replace_restore_failure_still_reports_audit_unavailable` (skipped as root): the sink fails and the
  store is made to refuse the restore (the builder names the means in the test); the reply is `AuditUnavailable`,
  never success, and no entry is recorded as submitted.
- Serialization → `replace_entry_is_submitted_under_the_key_lock` with a gate sink holding the submission of an
  approved replace: a second replace and a delete of the same id do not reach polkit (ask count stays 1) until the
  gate is released; after release the first succeeds with its entry, then the second runs with its own ask and
  entry. With the failing sink released the same way, the second sees the old certificate (its comparison and its
  entry are made against the restored store) and polkit asks equal entries submitted. A replace of another id or
  another owner is not blocked. At least 20 rounds of two same-uid replaces: entries equal polkit asks, exactly one
  `replaced` entry per success, the final certificate is one of the two submitted, never a mix.
- Delete interplay → `replace_and_delete_each_leave_one_entry`: a replace and a delete of one id, polkit holding both
  until both asked, at least 20 rounds: one `delete` entry `deleted` always; the replace is either `replaced` (one
  entry) or `NoSuchKey` with no entry and no ask; entries equal asks; no certificate remains without its key.
- Content → `replace_entries_hold_no_secrets`: the whole datagram/fields of every replace entry (success, denied,
  mismatch, storage failure, failing sink) contain neither the new nor the old certificate (raw, hex, base64, and
  its DER subject or serial strings), no key bytes, with a negative control that plants such a string and is caught
  (as in `delete_audit.rs`).
- Journal path → `journal_sink_datagram_for_replace` (style of `journal_sink_datagram_for_delete`): a replace over the
  private bus with the journal sink gives a datagram with `CUSTODIO_OPERATION=replace_certificate`, the catalog
  `MESSAGE_ID` `336e0b53720a735afb179ebc7f779ed6`, uid, pid, key id and outcome; one case per outcome checks the
  outcome field value and the `PRIORITY` of the table.
- Docs → `docs/audit.md` and `docs/api.md` statements checked by `cargo test -p custodiod docs` and `just
  api-contract`: fails if the replace order, the outcome mapping (including `storage_failure`), `AuditUnavailable`,
  the restore and its residual cases, or any documented replace query is missing or no longer runs against the code.
- F78 behaviour intact (bounds, order, polkit once and action, atomic store, two uids, sign after replace, delete
  interplay) → F78's tests, adapted only to the entry counts, pass in `just quick`; `tests/owners.rs` counts
  stay consistent.
- Mutants → `just mutants-diff F79` reports no surviving mutant in the changed code (outcome mapping, order of
  entry and restore, restore on every outcome, lock use, entry without caller).
