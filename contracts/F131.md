# F131 — End-to-end runs with a TPM, without one, and with a lacking TPM

## Scope
The e2e harness (`e2e/run.sh`, `e2e/guest.sh`, the five-plus target directories, the `just e2e` and `just e2e-cases`
recipes, CI) learns the variable `E2E_TPM` and gives every target container a software TPM by the route F108 chose
(`docs/findings/F108.md`, route 2: `swtpm` on a unix socket under `/tmp`, state under `/var/tmp`, a drop-in in
`/run/systemd/system/custodio.service.d/` that sets `CUSTODIOD_TEST_SWTPM_TCTI` and `BindReadOnlyPaths=`; `/dev/vtpmx` route 1
needs a host change and is not used). The F108 finding fixes the route; the builder takes the details from it and from
`docs/decisions.md` (2026-11-03, the test-only socket variable).

- `E2E_TPM` is `swtpm` (default, also when unset), `none` or `lacking`; any other value is refused by `e2e/run.sh` before
  anything is started, with a message naming the allowed values. `swtpm`: the service sees a working TPM. `none`: the
  drop-in's TCTI points at a socket that is absent (the service sees "no TPM"). `lacking`: the TCTI points at a
  `TpmFilter` (F107) socket in front of the `swtpm`, with the capability F107 says a key type needs removed (as F108
  did with `RSAPSS`). `TpmFilter` is only a library today; the step that needs a command line adds one as an example of
  `custodio-it` (arguments: upstream socket, listen socket, lacking identifiers) that the container mounts, built by the
  recipe like the other e2e inputs. The binary must run in the target (same-glibc concern: the dev container's glibc is
  older than or equal to every target's, else the step uses a static or older-built binary and records why).
- The five-plus Containerfiles install `swtpm`, `swtpm-tools` (or the distribution's equivalent) and `tpm2-tools`. Where a
  target confines `swtpm` (AppArmor on ubuntu, SELinux on fedora/alma, per F108's "what may differ") the setup uses the
  path the policy allows; each target's difference is checked by running it, and any that cannot be solved is a
  `SPEC_DEVIATIONS.md` entry backed by a finding, not a skipped target.
- `just e2e` (target `all`) runs every target twice, with `swtpm` and with `none`, so every M0–M3 case runs both ways;
  `just e2e TARGET` and `just e2e-cases` run the one mode given by `E2E_TPM` (default `swtpm`). `lacking` is accepted by
  both and runs the selected cases (a `lacking` run of all cases is not part of `just e2e`; M4's own `lacking` cases
  belong to the later e2e cases of M4).
- The record `target/e2e/<target>.record` has a line `tpm=<mode>`, and the mode is part of the record's file name so the
  two modes of a target do not overwrite each other (`<target>.<mode>.record` or equivalent; the builder decides, the
  tests pin it). The log is per mode as well.
- The drop-in exists only in the containers, only for the TPM setup, and the guest checks before and after the cases that
  the **installed** unit has none of it: `DropInPaths` empty without the TPM setup, the package's file list (`dpkg -L`,
  `rpm -ql`, `pacman -Ql`) names no `custodio.service.d`, and `systemctl cat` shows only the packaged file. The check is
  one step of the guest run on every target and mode, accounted like a case.
- CI: the repository has no e2e job yet (`.github/workflows/ci.yml` has commits, lint, test, coverage, nightly, mutants,
  package, ci). This feature adds the e2e jobs, one per target × mode (`swtpm`, `none`) that run `just e2e-packages`-based
  `just e2e` of the target with `E2E_TPM` set, and wires them into the `ci` aggregate job. If the GitHub runner cannot run
  a privileged systemd container, the job says so and the step records the reason; it is not left out silently.
- Not here: the M4 cases that need a TPM (`tpm-*`, `lacking-*`, PCR extension, clear, upgrade of kinds): later e2e
  features. Not here either: package, install and lifecycle gates and the full `just e2e` run, which belong to F90/F100
  (checkpoints); `verify` runs only `e2e-cases debian13 pkcs11-tool-approve-rsa` in the three modes.

Environment: F108 ran `swtpm 0.7.1`, `swtpm_setup`, `tpm2-tools 5.7` and the rootless podman in the dev container (debian13
target). Before step 2 the builder re-runs `podman info` and the one-line F108 setup in the debian13 container (`swtpm_setup`,
`swtpm socket`, `tpm2_getcap algorithms`) and writes the result into `docs/findings/F131.md`; a target whose container
cannot do this on this host is reported there with the exact failing command, and handled as above. Size: six steps; if the
per-target confinement work (SELinux on fedora44/alma10) turns out large, the builder proposes the split rather than
leaving a target out.

## Evidence
- `E2E_TPM` values and default → `scripts/test-e2e-host.sh` (new cases) → unset and `swtpm` give the same run; `none` and
  `lacking` reach the guest as such; `bogus`, empty-but-set and upper case are refused with exit 1 and nothing is started
  (the stub engine's log is empty). Control: a copy of `run.sh` that ignores the variable fails the test.
- `just e2e` runs both modes → host test with the stub engine and two targets → each target's guest is invoked once with
  `swtpm` and once with `none`, never with `lacking`; a failing mode does not stop the other and the exit is non-zero.
  `e2e` and `e2e-cases` honour the variable → the recipe text/`just --dry-run` shows `E2E_TPM` reaches `run.sh`.
- The record names the mode → the same host test → `<target>` record for each mode exists, holds `tpm=swtpm` or
  `tpm=none`, and the two do not overwrite one another; a record without the line fails the run (as a missing
  `bus-daemon` does today).
- Every target has the tools → `scripts/test-e2e-targets.sh` (new check) → each Containerfile's install command lists
  `swtpm` and `tpm2-tools` (or the target's name for them); control: a Containerfile without them is flagged.
- A TPM, none, lacking really differ → the guest's TPM setup step (run by the `verify`) → in `swtpm` mode
  `tpm2_getcap algorithms` through the drop-in's TCTI inside the unit succeeds and `none` fails with the "Cannot connect to
  swtpm TPM socket" message; in `lacking` mode `tpm2_testparms` of the lacking scheme fails with `TPM_RC_SCHEME` while a
  scheme the TPM has succeeds. The step fails the run if the observed state is not the requested mode.
- The drop-in is only in the containers → guest step "no test drop-in in the installed unit" (every target and mode) and
  its selftest → `DropInPaths` empty, no `custodio.service.d` in the package list, only the packaged unit file in
  `systemctl cat`, both before the TPM setup and after its cleanup; the selftest plants a drop-in and the check fails.
  `docs/findings/F108.md` already shows the debian13 numbers; this re-checks them in the final harness.
- Every case runs both ways → `verify`: `just e2e-cases debian13 pkcs11-tool-approve-rsa` with `swtpm`, with
  `E2E_TPM=none` and with `E2E_TPM=lacking`, each passes with the case accounting satisfied and the record naming its
  mode. (The other targets and the whole case list run at the checkpoints.)
- CI runs both modes → a host test (`scripts/test-ci-e2e.sh` or an addition to an existing workflow test) parses
  `.github/workflows/ci.yml` → there is an e2e job per target for `swtpm` and for `none`, each runs `just` with
  `E2E_TPM` set to its mode, and the `ci` job needs them; control: a copy without the `none` jobs fails. `actionlint` and
  `zizmor` pass in `just quick`/lint.
- Gate stays green → `just quick` → passes.
