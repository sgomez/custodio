# F163 — VM cases: encrypted-tpm keys survive a PCR change, restarts, a TPM clear and an upgrade

## Scope
Built (acceptance 8, 9 and 10; Design 1 "Cases"). The ids are already in `e2e/vm/cases.list` (F160): `pcr-extended-signs`, `pcr-restarted-signs`,
`pcr-signs-every-key`, `tpm-clear-sign-fails`, `tpm-clear-keys-listed`, `tpm-clear-delete`, `upgrade-kinds-before`, `-kept`, `-signs`, `-tpmbound`.
Here the three runners become VM-aware (`E2E_VM=1`; `full` = guest `E2E_TPM=swtpm`, `lacking`), as F161/F162 did for theirs. The kind table of a VM run is
`full` → `tpm`/`tpm` and `lacking` → `encrypted-tpm`/`encrypted-tpm` (RSA 2048 and P-256); the container tables are unchanged and used when `E2E_VM` is unset.
In `lacking`, after each import and before the key is used or deleted, root runs the reader (`vm_read_credential`, `e2e/vm/cred-lib.sh`, F161) on every
`encrypted-tpm` key the group makes; a failing reader fails the run; in `full` it is not called. No case of the three groups is skipped in either VM mode
(`check-cases.sh` with `CHECK_VM` refuses it, as for sign/noplain), and `upgrade-kinds-tpmbound` runs in both.

**Mapping container → VM** (the spec asks the contract to record it; the builder completes the "decided" rows in step 1 and amends this table):
- *Restart of the service*: `systemctl restart custodio` in the guest, as in the container (new MainPID, active, bus `Ping`).
- *Restart of `swtpm` with the state kept* → **guest power cycle with the swtpm state directory kept** (`vm.sh cycle`, proven by `scripts/test-vm-launch.sh`;
  F151 finding: the TPM's persistent state survives it). `vm.sh` is a host tool and the guest run is one `systemd-run` command that a power cycle kills, so the
  host driver (`e2e/vm/run.sh`) splits the guest run around the cycle: the keys are imported, PCRs extended, the service restarted and every key signed before;
  the host cycles; then, in a second guest invocation of the same run, the same keys are listed with the same kind and sign again. The cases are reported once
  across both invocations (accounting merges them), the keys are deleted at the end, and setup is not repeated after the cycle. Nothing in the guest stops or
  starts `swtpm`, and no test TCTI or drop-in exists (SPEC Design 1).
- *PCR tools*: `tpm2-tools` in the guest through `/dev/tpmrm0` (the kernel's resource manager) instead of the service's private socket. PCRs 7 and 0 (not 11) are
  extended. The first half reads PCRs 0 and 7 before the extension (the "first reading") and stores them in the run's state file, which the driver carries to the second
  invocation. After the power cycle the PCRs must **equal the first reading** (OVMF measurements are deterministic, `docs/findings/F163.md`, `full` and `lacking`);
  a reading that is neither the first reading nor the extended values is rejected too. The boot id must have changed.
- *TPM clear* (acceptance 9): **route A** (settled by the probe): `tpm2_clear` from the guest on `/dev/tpmrm0` with the empty lockout auth, in both modes; no host action,
  no second TPM, no drop-in. The M4 isolation by a second `swtpm` behind the test TCTI is not available in a VM, so the VM clears the TPM of the run; the later steps
  (`tpmslots`, `upgrade`) start from a cleared TPM and a fresh primary, which the case proves works by re-importing a key after the clear (as M4's `tpm-clear-delete`).
  Evidence that the clear happened: the owner-hierarchy primary of a fixed template (read with `tpm2_readpublic`) has another name afterwards (as M4).
- *Upgrade*: package N is the `.deb` the run installs and N+1 is the same tree with a raised patch number (`target/packages-next`, both already in the VM
  payload), so N already depends on `libtss2-rc0t64`. Upgrade is by the distribution's tool in the guest, as the VM install is. Seeds are the four keys of
  `upgrade-accts.sh` (alice ec1, rsa1; bob bobonly, rsa1).

Not built (where): the container behaviour of the three groups is M4's and is proven by the existing container sections of the three self-tests,
`test-e2e-skips.sh` and `test-e2e-vm-cases.sh`; real full runs of `just e2e-vm full|lacking` and their budget rows are F168; sign, noplain (F162), tpm-kind,
fallback, silent (F161) are not touched. Whether RSA-PSS etc. sign in a real guest is F162's.

Environment: `/dev/kvm`, swtpm, the guest boot, tool install, `lacking` profile and `vm.sh cycle` are proven by F160–F162 (real guests passed on 2026-11-08, e.g.
`just e2e-vm-cases lacking 'sign-*' 'noplain-*'` 1m34s). What is not yet proven is `tpm2_clear` and PCR extension through `/dev/tpmrm0` in the guest and the PCR
values after a cycle: step 1 runs the smallest command that shows them and records the result in `docs/findings/F163.md`. If route A fails and B also cannot be
made to work, the builder writes BLOCKED.md.

Cost: each of the three self-tests gains a VM section (fixtures and stub `su`/`journalctl`/reader, judge runs at once with `&`/`wait`, as F161/F162): estimated
+2–4 s each on top of today's (pcr ~3 s, tpmclear ~4 s, upgradekinds ~10 s from the container sections; the builder measures), parallel with the other script
tests under the `script *` budget (120 s); `test-e2e-upgradekinds.sh` stays far under it. No new e2e case id and no new container case: the ten ids exist and run
only in the VM list (`e2e/vm/cases.list`) and, as before, in `e2e/targets/debian13/cases.list`. Real-guest cost (probes, not `verify`; paid at F168): pcr about one
boot (~15 s) for the cycle plus ~1 min of cases; tpm-clear ~30 s; upgrade ~1–2 min (apt upgrade included); the probe runs are one command each (< 10 min), the
two modes at once in one command only if `run.sh` isolates concurrent runs, else one command per mode. Each step fits one session.

## Evidence
- Acceptance 8, every `encrypted-tpm` key signs after PCR 7 and another PCR are extended and the service is restarted → `scripts/test-e2e-pcr.sh` VM sections: `pcr-run.sh` first half with `E2E_VM=1` on fixtures in `lacking` and `full` → exit 0, `pcr-extended-signs` reported run; controls: PCRs unchanged by the "extension", the service pid unchanged, a signature that does not verify, a signing refusal, a missing key, fewer than two keys, each fail the run.
- Same, again after a guest power cycle with the swtpm state kept → same test, second half on fixtures and the driver section with a stub `vm.sh`: the cycle is called once between the halves, the keys of the first half are the ones signing in the second (same ids, same kind), the boot id changed, the PCRs equal the first reading → `pcr-restarted-signs`, `pcr-signs-every-key` run; controls: no cycle, boot id unchanged, extended PCRs still in place, a key missing or a kind changed after, PCRs after the cycle that are neither the extended values nor the first reading, a half that fails, a cycle that fails (VM stopped, run fails) are each rejected; a copy of the driver that never cycles fails the same fixtures.
- The keys are `encrypted-tpm` in `lacking` and `tpm` in `full` (kind table), and the reader proves it → pcr, tpm-clear and upgrade-kinds self-tests: accepted for the right mode; `tpm` in `lacking`, `encrypted-tpm` in `full`, `encrypted-host`, one key missing each rejected; stub reader exit 0 passes, non-zero fails the run with its reason, not called in `full`; a control copy of a runner without the reader call is marked a failure by the test.
- Acceptance 9, after the clear signing fails with the documented error and a journal entry → `scripts/test-e2e-tpmclear.sh` VM sections: fixtures with the signatures before, the primary's name changed, D-Bus `KeyLost` with the documented text and `CKR_DEVICE_ERROR` through the module on every attempt, one `sign`/`signing_failed`/`key_lost` journal entry per Sign call with key, kind, uid and no secret → `tpm-clear-sign-fails` run; controls: a sign that succeeds after the clear, the primary's name unchanged (nothing was cleared), a missing journal entry, an entry of another operation or with a secret, another error text each fail.
- The key is still listed and can be deleted → same test: ids and kinds in `ListKeys` and `custodio list` as before, records still in the state directory, the deletes succeed and one `delete` entry per key, the re-import after the clear has the mode's kind, signs and is deleted → `tpm-clear-keys-listed`, `tpm-clear-delete` run; controls: a key missing from the list, a changed state directory, a failing delete, a re-import that does not sign each fail.
- The decided clear route is the one used (route A: no second TPM, host state replacement or drop-in is created in a VM run) → same test, driver/stub section; a VM run that sets a test TCTI or a drop-in fails it.
- Acceptance 10, N → N+1 keeps each `encrypted-tpm` key, owner, certificate and kind, and the key signs → `scripts/test-e2e-upgradekinds.sh` VM sections: fixtures of the four seeded keys before, after and in the round, in `lacking` (`encrypted-tpm`) and `full` (`tpm`) → `upgrade-kinds-before`, `-kept`, `-signs` run; controls: a kind changed, an owner changed, a certificate changed, a key lost, a signing round that fails or whose journal kind differs each fail.
- `upgrade-kinds-tpmbound` runs in a VM and is not skipped; in a container it stays skipped; the credential still passes the reader after the upgrade → same test: with `E2E_VM=1` the case is reported run in both modes, in `lacking` the stub reader is called on each key after the upgrade and a failing reader fails the case; without `E2E_VM` it is reported skipped with the M4 reason; `check-cases.sh` with `CHECK_VM` refuses it skipped even if the skip list names it → expected as stated.
- N already depends on `libtss2-rc0t64`; N and N+1 are built from this tree → the VM payload test (`scripts/test-e2e-upgradekinds.sh` driver section) checks that the two `.deb`s are different versions with the same dependency list containing `libtss2-rc0t64`; control: a payload with an N lacking it fails.
- None of the three groups is skipped in a VM run; the container accounting is unchanged → accounting loops in the three self-tests: container `swtpm none lacking` as before, and `CHECK_VM=1` for `full`, `lacking`: all run accepted, one skipped refused, all skipped refused even with a skip list naming them; `scripts/test-e2e-skips.sh` and `scripts/test-e2e-vm-cases.sh` still pass.
- Container cases behave as in M4 → the unchanged container sections of the three self-tests pass.
- Everything compiles and lints → `just quick` → green.
