# F76 — Delete a key

## Scope
A new method `DeleteKey(id: s)` on `com.rfirma.Custodio1` (`Custodio::delete_call`, same shape as `sign_call` and
`import_call`) removes one of the caller's keys together with its certificate (`<id>` and `<id>-cert` in the
owner's area).

- **Order.** (1) `id` is checked against the documented bound (`InvalidArgs`; the existing key-id rule); (2) the
  caller is identified (no sender or failed credentials → `AuthorizationUnavailable`, no polkit); (3) the key is
  looked up among the caller's keys only (`NoSuchKey`, no polkit, for a missing id and for another uid's id,
  indistinguishable); (4) polkit is asked once per call under `DELETE_ACTION_ID`
  (`com.rfirma.custodio.delete-certificate`, already shipped) with `AllowUserInteraction` (`PolkitDenied`, or
  `AuthorizationUnavailable` for unavailable/`BadSender`); (5) the files are removed. Denial or unavailability leave
  key and certificate in place. Nothing is cached.
- **Removal.** The key file goes first, then the certificate, so a partial failure never leaves a key without its
  certificate (as `rollback_import`). A key that vanished between the lookup and the removal (two concurrent
  deletes) makes the loser fail `NoSuchKey`: the builder gives `KeyStore` a removal that tells "missing" from
  "removed" (the existing `remove` treats missing as success and is used by the import rollback; do not change that
  behaviour). A failure to remove is `Internal`; if the key file could not be removed, key and certificate both
  remain.
- **Signature in progress.** `sign_call` reads the key before polkit, so a sign already past its lookup completes
  with the key it holds, and a sign that looks up after the delete fails `NoSuchKey`. Nothing else is acceptable
  (no `Internal`, no partial signature).
- **After a delete.** Absent from `ListKeys`, `Sign` fails `NoSuchKey`, neither file is left in the state
  directory, and the id can be imported again (the own-id check also looks at `<id>-cert`).
- **Docs.** `docs/api.md` gets a `### Method DeleteKey` section (in `id: s`, no out, bounds, the order above); the
  error list names `DeleteKey` for `PolkitDenied`, `NoSuchKey` and `Internal` as needed. `just api-contract` checks it
  against the live introspection, so the method, its argument and its bounds line must match.
- **Left for other features.** The journal entry for delete and the unusable-then-submit-then-remove ordering with
  restore (F77: this feature writes no entry and calls no sink; `DeleteOutcome` stays unused here); the CLI
  `custodio delete` and its confirmation (later CLI feature); the PKCS#11 module showing no token (later
  feature, it only reads `ListKeys`); the e2e cases with a real agent (F90/F100). Size: about five steps; no split.

Environment: nothing beyond the dev container. The tests use the private `dbus-daemon` and polkit double of
`tests/audit/bus.rs` (async, with `hold` and `on_request`) and the name→uid credentials fake of `tests/owners.rs`,
as F72/F73 do. No new tool, network or privilege. Tests that need an unwritable store skip as root, as before.

## Evidence
All rows in `crates/custodiod/tests/delete.rs` unless stated; stores are inspected on disk and through
`ListKeys`/`Sign` over the private bus; polkit asks are read from the double (`asked()` with action and flags).
- Bound on the id → `delete_rejects_bad_ids`: empty, 60 bytes, a non-`[A-Za-z0-9_-]` byte, an id ending in `-cert`
  each give `InvalidArgs`, `asked()` empty, the store unchanged; a valid 59-byte id passes the check (reaches
  `NoSuchKey`). Fails if the bound is off by one or checked after polkit.
- Missing or foreign id, no polkit → `delete_missing_equals_foreign`: uid 1000 owns `k`; uid 1001 deletes `k` and
  deletes `absent`; uid 1000 deletes `absent`. All three fail with the same error name and message `NoSuchKey`,
  `asked()` empty, 1000's key and certificate still on disk and listed. Also with polkit answering Yes, Deny and
  Unavailable (the answer must not change the result).
- Credentials → `delete_without_credentials_is_unavailable`: no sender / failing lookup / no `ProcessFD`
  gives `AuthorizationUnavailable`, no polkit, key kept.
- polkit once, right action → `delete_asks_polkit_once_with_interaction`: an approved delete shows exactly one ask,
  action `com.rfirma.custodio.delete-certificate`, flags `AllowUserInteraction`, subject the caller's
  connection; two deletes (second `NoSuchKey`) show one ask in total, so nothing is cached; delete after an
  earlier approval of sign asks again.
- Denial or unavailability keep the key → `delete_denied_and_unavailable_keep_the_key`: polkit Deny →
  `PolkitDenied`; Unavailable and `BadSender` → `AuthorizationUnavailable`; each leaves `<id>` and `<id>-cert`
  byte-identical on disk, listed, and signing still works.
- After a delete → `delete_removes_everything`: approve; the reply is empty; `ListKeys` no longer has the id and
  still has the owner's other keys; `Sign` gives `NoSuchKey` and asks no polkit; `read_dir` of the owner's area
  shows neither `<id>` nor `<id>-cert` (nor a temp file) and the other key's files are untouched; the same id is
  imported again (approve) and signs, with a new certificate. Fails if the certificate is left or the id stays taken.
- Two uids → `delete_leaves_other_uids_alone`: 1000 and 1001 each import `my-key`; 1001 deletes `my-key`; 1000's
  key still lists, signs and is on disk, 1001's is gone. Also pairs 0/1000 as in `owners.rs`.
- Partial failure → `delete_store_failures`: an area made unwritable by the polkit double while it answers (after
  the lookup): reply `Internal`, key and certificate both still present (skipped as root). A certificate
  that cannot be removed after the key went (certificate entry made undeletable or replaced by a directory):
  reply `Internal`, the key is gone (`Sign` → `NoSuchKey`), and the test pins what `ListKeys`
  and a re-import do (documented in `docs/api.md` or the code, whichever the builder chooses).
- Concurrent deletes → `concurrent_deletes_one_wins`: two clients of the same uid delete the same id with the async
  polkit double holding both until both asked (`asked().len() == 2`), repeated for at least 20 rounds: exactly
  one reply is success and the other is `NoSuchKey`; the files are gone. Fails if both succeed.
- Signature in progress → `sign_during_delete_completes_or_fails_no_such_key`: a sign is held in polkit (after its
  lookup); a delete is approved and finishes; the sign is released. The sign's result is a valid signature (verified
  with the key's public key) or `NoSuchKey`, never another error; a sign started after the delete returns is
  `NoSuchKey`. A repeat with the delete held while a sign passes through. Fails on `Internal` or a bad signature.
- Documented → `just api-contract`: `DeleteKey` with `in id: s`, no out, a bounds line, matches the live
  introspection both ways; the `delete-certificate` action stays in the policy. `docs/api.md` states the order, that
  no entry is written yet is NOT stated (F77 owns it), and the key and certificate removal.
- Unit tests in `store/tests.rs` and `dbus/tests.rs` → the store rows of Steps; the pre-polkit refusals never call
  the authorizer (a counting authorizer, literal expected counts), the error mapping of each outcome is a literal table.
- No journal entry yet → `delete_leaves_no_entry_yet` is NOT written (F77 changes it); instead the existing
  `MemorySink` counts in `owners.rs` and `audit` tests stay unchanged and green in `just quick`.
- Existing behaviour intact (import, sign, list, owners) → the adapted existing tests pass in `just quick`.
- Mutants → `just mutants-diff F76` reports no surviving mutant in the changed code (order of checks, removal
  order, missing-vs-removed, error mapping, action constant).
