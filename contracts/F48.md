# F48 — End-to-end upgrade cases on every target

## Scope
Built here:
- The upgrade case of SPEC design section 2 ("Upgrade") and section 4 ("Lifecycle cases"), run by the shared guest on each of the five
  targets: debian13, ubuntu2604, fedora44, alma10, arch. No new target directory; `just e2e` (all) runs it everywhere, and
  `just e2e <t>` runs it for one target.
- A package N+1: "built from the same tree with only the version raised" (the proposal of SPEC open questions, "Version and release
  numbers", and `docs/decisions.md` 2026-10-30: `just package version=...` already builds an N+1; no `Cargo.toml` edit). `just package`
  empties `target/packages`, so the `e2e` recipe must produce N+1 without removing N, in a place that is not `target/packages`. The N+1 package is in
  the same three formats, and has the same binary and file list as N (see Evidence). Its version compares greater than N by the target's own
  tool, inside the guest (see Evidence); the host does not compare versions, because the dev container has no `vercmp` or `rpmdev-vercmp`. It is mounted read-only into the container next to N,
  never copied into the image, and installed by the target's own `install.sh` (the same file that installed N): `dpkg -i`, `apt-get install`, `dnf install`,
  `pacman -U --needed`. The host (`e2e/run.sh`) chooses N and N+1 apart (the existing `find` for `package.pattern` must not
  be able to pick N+1 as N, or the reverse).
- The case runs inside the one guest run, AFTER the existing cases and `journal-check.sh` (so the audit counts of F45/F59 are not disturbed), starting from the state that run
  left: keys imported with N by `import.py`, service running. It is reported as `E2E-CASE` lines registered in `e2e/cases.list`
  (so a run that skips one without a `skip.list` entry fails, as for every case). No target needs a `skip.list` entry for it; none is
  added.
- A comparison helper that a self-test exercises with fixtures (like `journal-selftest.sh` for the journal checker), run by the guest before it relies on the helper.
- `scripts/test-e2e-host.sh` learns the second mount and the case ids.

Left for other features: upgrade from the cargo-deb .deb (F60); removal, purge, reinstall (F49); the refusal on Ubuntu 24.04 (F50); a signature
waiting for polkit during an upgrade (no feature in this milestone's list; not here); the bus check and the Arch hook order, the maintainer-script
stubs and real pacman/dpkg/rpm tests (F43, F44, F58 already prove them in package-level tests; this feature proves the whole thing on
the real distributions with the real service); the not-running-before variant (D-Bus activation after an upgrade), which the description
does not ask for.

Environment checked while writing this contract (dev container): `command -v vercmp rpmdev-vercmp` finds nothing, so no version comparison is
done on the host. `dpkg --compare-versions 0.1.0-1 lt 0.1.1-1` exits 0 and `rpm --eval '%{lua: print(rpm.vercmp("0.1.0-1","0.1.1-1"))}'` prints `-1` here; the
builder confirms the rpm form (and Arch's `vercmp`, which ships with pacman) in the Fedora, Alma and Arch images in the version-check step. `podman info` shows `rootless: true`, `cgroupManager: cgroupfs`; `command -v nfpm podman` finds
`/usr/local/bin/nfpm` and `/usr/bin/podman`; F46 and F47 ran `just e2e` on all five targets in this container. So the real runs are possible here, and the contract requires them. The workspace version is 0.1.0.

Size: about six steps; no split needed.

## Steps
- [ ] Write the failing tests first. (a) `scripts/test-e2e-host.sh`: with the stub engine, the run mounts N and N+1 as two different read-only files, neither in the image, `cases.list` contains the new ids, a stub run that omits one fails the accounting. (b) a self-test of the
      comparison helper (its own script, run by the guest and by `just test-scripts`) with fixtures: unchanged tree passes; each of changed byte, changed mode, changed uid/gid, an added file, a removed file, a changed
      directory mode, a changed listing of keys, and a service whose `/proc/<pid>/exe` is unchanged / deleted / not the installed file, is rejected with its own message. Run it red.
- [ ] Build N+1 in the `e2e` recipe (or a script it calls) without wiping N, and make `run.sh` find and mount both. On the host, check only what needs no version tool: N+1's version string differs from N's, and the sha256 of `custodiod` and the sorted file lists of the two packages (per format) are equal.
- [ ] Write the comparison helper and the upgrade case in the guest: snapshot before; check, with the target's own comparison (`dpkg --compare-versions N gt N1` negated: N1 must be `gt` N; rpm's `rpm.vercmp` via `rpm --eval` on Fedora/Alma, checked to work in both images; `vercmp` on Arch), that N+1 is strictly greater than N, failing the case before installing; install N+1 with the target's `install.sh`; compare after (see Evidence); report the case lines.
- [ ] Run `just e2e <t>` for each target until the case passes. A failure is a defect of the case, of a shared script that is wrong for one distribution (small fix, the others stay green), or a real defect of the package (a bug found: fix it in the package with its own test, or write `BLOCKED.md` if it is a decision). Never weaken the check, and never skip: no skip entry for this case.
- [ ] Update docs that list the e2e cases (README or harness text, if they list them) and `docs/findings.md` with one short entry only if the run showed something non-obvious (for example how the executable identity is read per distribution).
- [ ] Real run, required: `just e2e` (all five). Paste exit status, the new `E2E-CASE` lines per target, the pre- and post-upgrade versions and the executable identities (device:inode, pid) per target into `PROGRESS.md`; run `verify`. If it cannot run, write a finding and `BLOCKED.md`; do not fall back to the stub test.

## Evidence
- The package N+1 differs from N only by the version, and is installed by the target's tool, not by copying → `scripts/test-e2e-host.sh` (stub engine) → N+1 is a second read-only mount distinct from N's; no `COPY`/`ADD` of a package in any Containerfile (the existing check); N+1 is installed through `install.sh` (the guest's log line names the file), and the host check rejects an N+1 whose `custodiod` hash or file list differs from N's (control with fixtures in the stub test).
- N+1 is strictly greater than N, by the target's own tool → real run, per target, and the comparison helper's self-test → the guest runs the comparison before installing N+1 and the case fails if it is not greater; self-test controls (with the comparison stubbed by fixtures of the same form on the dev container's `dpkg --compare-versions`): N+1 equal to N and N+1 lower than N each fail the case without installing. Real-run log line shows the compared versions and tool per target.
- The upgrade really happened → REQUIRED real run, per target → the installed package version queried with the target's own database (`dpkg-query`, `rpm -q`, `pacman -Q`) equals N before and N+1 after, and N ≠ N+1. This fails if `--needed` or `dpkg -i` turned the install into a no-op; the downgrade case is excluded by the previous bullet, not by this one.
- Key files byte-identical, same owner and modes → real run → before and after the install, the case lists every file and directory under the state directory (resolved through the `/var/lib/custodio` link to `/var/lib/private/custodio`; at least the two imported keys' files must be present, and the count is asserted > 0) with `sha256sum` (or `cmp` against a copy) plus `stat` uid, gid and mode; the two lists are equal. The custodio account's uid and gid are equal too. Negative controls in the self-test: one flipped byte, one changed mode, one changed owner, one file added, one removed, a changed directory mode each make the helper fail.
- The same keys are listed → real run → the token/key listing taken through the PKCS#11 module as the user before and after is identical and names `rsa1` and `ec1` (not empty); self-test control: a listing without one key fails.
- They sign with polkit asked → real run → after the upgrade, as the user in a logind session with the test agent, one approved RSA and one approved ECDSA signature succeed, each verifies against the public key, and the agent's request counter rose by exactly one per signature; with the agent set to deny, a signature fails and the counter still rises by one (polkit is asked each time, nothing cached from before the upgrade). Fails if the signature needs no polkit call or the old authorization is reused.
- The service that was running before runs the new binary afterwards, by identity, not only state → real run → before: `custodio.service` is active with `MainPID` p1 and the identity of `/proc/p1/exe` (device and inode) is that of `/usr/lib/custodio/custodiod`. After: it is active, `MainPID` p2 ≠ p1 (it restarted), and `stat -L /proc/p2/exe` has the device and inode of the file now at `/usr/lib/custodio/custodiod` and that path is not reported `(deleted)`; the old p1 no longer exists, or its exe reads `(deleted)`. The identity is by inode and not by a hash, because N+1 has the same binary content as N; the case says so. Self-test controls: an unchanged pid, an exe link ending in `(deleted)`, and an exe whose inode is not the installed file's each fail. Also asserted: p2 is still the `MainPID` after a short settle (a few seconds), so the service did not keep restarting; no claim on the exact number of restarts.
- No manual step was needed → real run → between the start of the install and the end of the case the guest runs nothing but the target's `install.sh` for N+1 (no `systemctl restart custodio`, `daemon-reload`, `reload dbus` or `start custodio` in the case's code between the snapshots; asserted by a static grep of the case's section in the guest script, delimited by explicit `# BEGIN upgrade-case` / `# END upgrade-case` markers; the check fails if either marker is missing or the section is empty, so it cannot silently match nothing, and fails if such a command is present; the self-test feeds it a section containing `systemctl restart custodio` and expects failure) and the install exits 0 with no prompt (the tool runs non-interactively, as in `install.sh`). Fails if the new binary is running only because the test restarted it.
- The case is accounted on every target → REQUIRED real `just e2e` → exit 0, "e2e: passed: alma10 arch debian13 fedora44 ubuntu2604", every id of the new cases in `cases.list` appears as run (not skipped) in `target/e2e/<t>.log` for all five targets.
- Shellcheck and syntax → `just check` and `bash -n e2e/*.sh` → pass; `verify`'s greps for `upgrade` and `sha256sum`/`cmp ` in `e2e` hold, but are not the proof: the real run is.
