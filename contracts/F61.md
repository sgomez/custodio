# F61 — The service binary where each distribution wants it

## Scope
Built here:
- The service binary at `/usr/libexec/custodio/custodiod` in the .deb and the .rpm and at `/usr/lib/custodio/custodiod` in the Arch package.
  The pkcs11 module and everything else stay where they are. The difference is listed in `packaging/parity-exceptions.txt`, one entry per path, no wider: the libexec path (deb, rpm; presence) and the Arch path (arch; presence),
  plus entries for the `/usr/libexec/custodio` and `/usr/lib/custodio` directories only if `check_parity.py` lists directories and the gate needs them. Each has a reason
  (the Arch reason names Arch having no `/usr/libexec`). `check_parity.py` compares presence, kind, mode, owner, group and target, not content, so the per-format unit text needs none. The rpm-only
  directory entries, the file lists the gates keep (`scripts/package_expected.py`, `check_packages.py`, the lint lists in `packaging/lint/`,
  the fixtures of the gate tests) and the e2e scripts that name the daemon path follow the new paths. The gates must still reject a package
  whose daemon is at the other format's path.
- `ExecStart` of the unit follows each path **from one source unit file**: the repository keeps one unit source, and the per-format unit is
  derived from it at package time (the builder picks the mechanism). The gates that read `data/custodio.service` directly (`security-score`,
  `unit-hardening`, `unit-verify`) keep working on what the repository holds. The package gate checks, per format, that the ExecStart of the
  unit inside the package is the path of that same package's daemon, executable, mode 0755.
- `docs/decisions.md`: the 2026-10-30 entry "Package version scheme and the service under /usr/lib/custodio" is replaced (not left beside a
  contradicting entry) by one that keeps the version scheme and the `Exec=/bin/false` activation file, and records the new paths, why (on
  Fedora `/usr/lib/custodio` is `lib_t`, so systemd leaves the service in `init_t` and the key files get `init_var_lib_t`, seen in F54 and F55;
  from `/usr/libexec` (`bin_t`) it runs in `unconfined_service_t`, as SPEC expects) and what was rejected. Text mentioning the old path in
  other docs (`docs/install.md`, `docs/manual-acceptance.md`, `SECURITY.md`, README) is brought in line where it names the daemon path.
- Upgrade from a package with the old path (`/usr/lib/custodio/custodiod` on deb/rpm, i.e. the current M2 packages): the state directory and
  keys are untouched, the old file is gone, the service that was running is restarted once from the new path. Packages with the old path
  are built for the tests from the current tree's `nfpm.yaml` with the daemon path (and the unit's ExecStart) overridden (a fixture), not from a pinned old commit; the same fixture is the `PKG_FROM`
  of a new e2e upgrade case (below), because the F48 case upgrades N to N+1 from one tree and both will have the new path;
  the M1 cargo-deb package (F60) keeps its own path, `/usr/libexec/custodiod`, and F60's case is only adapted if the new path makes it fail.
- Relabeling: on an installation upgraded from the old path, key files written under `init_t` (`init_var_lib_t`) get the default label
  (`var_lib_t`) back. This also holds when the .rpm is layered with rpm-ostree, where no scriptlet touches `/var` at deploy time and
  `%post` runs in a build root. A step researches the mechanism (candidates: a label-only `systemd-tmpfiles` `Z` line with `-` for mode and owner;
  a restorecon in `%post`/`postinst`/the Arch hook; both) and decides within these limits: it changes only the SELinux label, never owner, mode,
  content or the directory's existence; it is a no-op without SELinux, without the tool, or in a chroot; failure never fails the install; it never
  reads or lists key files into output; it does not run `restorecon` on anything outside the state directory. The finding (tool source or a
  command run, with its result) goes into `docs/findings.md`, and the choice into `docs/decisions.md` only if a later session could undo it unknowing.
- The three packages pass the package gates, lintian, rpmlint and namcap with the lists in `packaging/lint/` (an entry whose path moved
  is updated, with the reason kept; no new entry without a reason).

Left to others: the SELinux policy module (out of scope in SPEC); the M1 package path; any change to the pkcs11 module path.

Environment (checked while writing this contract, dev container): `command -v podman` prints `/usr/bin/podman` (podman 5.4.2), and F46–F48 ran `just e2e` here, so the e2e run is the loop's, not a person's. `nfpm` is at `/usr/local/bin/nfpm`, `lintian` and `systemd-tmpfiles` are on PATH.
`rpmlint`/`namcap` run in the containers of `packaging/lint/` via `just package-lint`. SELinux is not available in the dev container or the
e2e containers (SPEC "Limits"), so the labels cannot be shown there; they are shown on the lab VMs `fedora44` and `bazzite` (libvirt, SELinux enforcing),
the same way as F54 and F55, by a person's run (see Evidence). Size: about five steps, no split.
