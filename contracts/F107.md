# F107 — Research: mechanism parity on the TPM and the capabilities each key type needs

## Scope
Built:
- A section `## F107` in `docs/findings.md` that settles the SPEC open questions "Mechanism parity
  on the TPM" and "A TPM that lacks a capability only for some mechanisms", for a person to approve
  in F111. Every claim is backed by a command and its output on `swtpm` (or a source read), marked
  verified or inferred as the rest of the file does. It covers:
  - Each mechanism the service offers, run both ways. (a) `TPM2_Sign` only: `CKM_RSA_PKCS` with a
    caller-supplied payload (what happens when it is not a `DigestInfo`) and with a `DigestInfo`
    per hash (SHA-1, SHA-256, SHA-384, SHA-512; SHA-1 is run because `CKM_RSA_PKCS` signs any payload today, and is served or `lacks` under (a)); `CKM_RSA_PKCS_PSS` with
    each supported hash and salt length; `CKM_ECDSA` on P-256 with SHA-256, SHA-384 and SHA-512
    digests and the service's truncation (`docs/decisions.md`). Each cell is served, or `lacks`
    with the TPM's response code. (b) Padding built in the service and only the raw RSA private
    operation in the TPM (`TPM2_RSA_Decrypt` with the null scheme on a key with the `decrypt`
    attribute): the same mechanisms, and whether the result equals the (a) result or the software
    result.
  - Every signature produced is checked with an independent verifier (the `openssl` CLI as an external command, never the crate, or the `rsa`/`p256` crates as dev dependencies), with the salt length the verifier is told to expect, so
    "verifies" is not assumed.
  - The PSS salt length the TPM produces per hash on this `swtpm` (libtpms version recorded), and
    for each hash whether it equals the hash length (the TLS 1.3 requirement in SPEC section 4).
  - Which hashes a P-256 key needs from the TPM (SHA-256 only, or also SHA-384/512 depending on
    how the truncated digest is handed to `TPM2_Sign`), shown by running it.
  - The `decrypt` attribute weighed against the SPEC threat model (what root or another
    TPM-access holder can do with a key that can decrypt, versus sign-only), and what a
    key with both `sign` and `decrypt` allows in the TPM (the TPM rejects `sign|decrypt` for
    restricted keys only; the finding records what `swtpm` does).
  - Once, the list of TPM capabilities each key type (exactly RSA 2048 and ECC P-256, the only kinds M4 ships; RSA 3072/4096 and P-384 are out of scope and not probed) needs: algorithms, curves, schemes, hashes, key sizes, and, for (b), the
    `decrypt` attribute and null scheme. This is the list the service will query
    (`TPM2_GetCapability` of algorithms, ECC curves, and `TPM2_TestParms` where it is the
    cheaper exact check); the finding says which call answers which item and shows the output on
    `swtpm`.
  - How the tests simulate a TPM that lacks one of them. The installed `swtpm` is 0.7.1 with
    libtpms 0.9.2 (checked: `swtpm socket --print-capabilities` lists no `profile` feature, and
    `swtpm_setup` has no profile or algorithm option), so a profile that disables an algorithm is
    probably not available. The step decides, within these limits: first confirm or refute that
    with a command; then either use a profile if it works, or a documented replacement that
    answers the capability queries and the sign/decrypt calls with the TPM's real
    "unsupported" response codes (for example a byte-level proxy on `swtpm`'s command socket in `custodio-it` that parses the command code and parameters and returns the `TPM_RC_*` the real one would; no `unsafe` anywhere in this feature). The finding
    shows the replacement making a query or a `TPM2_TestParms` fail for one algorithm and succeed
    on the unfiltered `swtpm`, and says what it cannot simulate. It does not build the replacement
    as shipped test infrastructure unless that is the narrowest way to show it works; if it does,
    it lives in `custodio-it` and F108 onward reuses it.
  - A recommendation on the partial-lack question (a key type whose TPM lacks one mechanism:
    TPM and lose it, or encrypted and keep it), consistent with "a mechanism is never silently
    dropped or changed for a TPM key", and flagging any departure from SPEC for the person in F111.
  - It ends with a line `Decision: (a)` or `Decision: (b)`.
- The probe `crates/custodio-it/examples/tpm-probe.rs` gains `mechanisms [--tcti <tcti>]`, which
  runs every mechanism of the (a) and (b) lists above and prints one `key: value` line each (the
  mechanism, hash, salt length requested, outcome served/`lacks` with the response code, the salt
  length found by verifying, and verified yes/no), so a person can repeat it on a hardware TPM.
  It creates only transient keys and flushes them; it never calls `EvictControl`, sets an auth
  value or clears. Without `--tcti` it uses the environment TCTI. It exits 0 when it ran every
  case and printed an outcome for each (a `lacks` is a result, not a failure), 1 when the TPM
  cannot be reached or the TPM served a signature that no candidate salt or expected parameter makes verify (so a broken probe cannot pass the `verify`), 2 on usage error.

Left to other features: the TPM module, import and the real capability query (F108 onward); the
hardware-TPM run and the person's approval, and recording the approved choice in
`docs/decisions.md` (F111). The parent key is F106's (reuse its primary template). Nothing
here changes `SPEC.md` or ships the capability list in code.

Environment (checked this session, dev container): `swtpm` 0.7.1 and `libtpms0` 0.9.2 are
installed; `swtpm socket --tpm2 --print-capabilities` lists `rsa-keysize-1024/2048/3072` and no
profile feature; `swtpm_setup` offers `--ecc` and no algorithm or profile option. The F105
fixture and `just with-swtpm` work (F104, F105, F106 pass). swtpm serves one client at a time.
Not yet shown: which of the mechanisms the 0.9.2 libtpms serves through `tss-esapi`
8.0.0-alpha.4 (`sign`, `rsa_decrypt`); step 1 checks it. If libtpms 0.9.2 lacks something this
feature needs (for example a SHA-512 digest for P-256), that is a finding about
`swtpm`, recorded with its response code, and the finding says it must be repeated on a hardware
TPM in F111.

## Steps
- [ ] Probe skeleton for `mechanisms [--tcti]`: argument parsing next to `parent`, usage error
      (exit 2) on a bad subcommand, TCTI from the environment by default, a failing run first
      (a test or a documented run with a bad TCTI exits non-zero), then the transient RSA and
      P-256 keys it needs and the independent verification helper; prints the key lines for one
      case (`CKM_ECDSA` P-256 SHA-256) to prove the loop end to end.
- [ ] Way (a) in the probe: `CKM_RSA_PKCS` payload and `DigestInfo` per hash, `CKM_RSA_PKCS_PSS`
      per hash and per salt length (hash length, largest, zero, one other), `CKM_ECDSA` with
      SHA-256/384/512 digests and the truncation; prints outcome, response code, found salt, and
      whether the signature verifies. Includes the negative controls: two payloads that are not a parseable `DigestInfo` (the 36-byte MD5+SHA-1 concatenation of TLS 1.0/1.1, and a `DigestInfo` with a hash OID the parser does not know), and a salt length the TPM does not produce.
- [ ] Way (b) in the probe: key with `decrypt`, padding built in the probe for the same
      mechanisms, raw RSA private operation by the TPM, results verified; prints the same lines.
      Then the capability queries (`GetCapability` algorithms and curves, `TestParms`) printed as
      the list each key type needs.
- [ ] `decrypt` experiments: attributes of a sign|decrypt key, what a decrypt-capable key lets another caller do, shown by a command.
- [ ] Simulating a lack: check `swtpm`/libtpms for a profile or algorithm switch (commands and
      output); if none works, build or specify the documented replacement within the limits in
      Scope and show it failing one capability while the plain `swtpm` succeeds. 
- [ ] Write `## F107` in `docs/findings.md` (all topics in Scope; the words `CKM_RSA_PKCS`,
      `CKM_RSA_PKCS_PSS`, `CKM_ECDSA`, `DigestInfo`, `salt`, `decrypt`, `SHA-384`, `SHA-512`,
      `lacks`, `profile` appear), with the probe output pasted, the capability list, the recommendation, one sentence that the composed mechanisms (`CKM_SHA*_RSA_PKCS`, `CKM_ECDSA_SHA*`) reduce to the base cases, and the line `Decision: (a)` or `Decision: (b)`; `just quick`; the whole
      `verify`; commit.

## Evidence
- Every mechanism run both ways → `tpm-probe mechanisms` output pasted into `## F107`, one line
  per mechanism/hash/salt per way → the table in the finding has a cell (served or `lacks` with a
  response code) for each combination in the feature description, each "served" cell marked
  verified by the independent verifier.
- `CKM_RSA_PKCS` with a payload that is not a `DigestInfo` → probe case under (a) → `lacks` (or
  the TPM's error), while under (b) it is served and verifies (negative control showing the two
  ways differ, and that (a) really parses).
- PSS salt per hash → probe lines `salt_found` per hash, determined by verifying with each
  candidate salt length → finding gives the length per hash on this `swtpm` and says whether it
  equals the hash length; a deliberately wrong expected salt makes the verifier report
  "not verified" (negative control).
- P-256 hashes needed from the TPM → probe lines for SHA-256, SHA-384, SHA-512 digests with the
  truncation, under (a) → the finding states which hashes the TPM must support and shows the
  result of each; the truncated value equals the leftmost 32 bytes (checked against the
  verifier).
- `decrypt` against the threat model → experiment output (the key's attributes, a raw
  decrypt of data by a different caller using the same handle/blob) and a paragraph citing the
  SPEC threat model sections → the finding says what the attribute adds (decryption of chosen
  ciphertext, signing of arbitrary padding) and why it does or does not matter here.
- Capability list → the probe's capability section and the finding's single list → every
  item (algorithm, curve, scheme, hash, size) per key type appears once, with the call that
  answers it and its `swtpm` output.
- Simulating a lack → command output showing whether the installed `swtpm` supports a `profile`
  (expected: no; the output is pasted) and the replacement's run → a query/`TestParms` for one
  chosen capability fails with the TPM's response code via the replacement and passes on plain
  `swtpm`; the finding names what it cannot simulate.
- Partial-lack recommendation → read by the evaluator → the finding recommends one option, says
  why with reference to SPEC section 4 ("never silently dropped or changed"), and flags any
  departure from SPEC.
- Decision line → the verify's regex `^Decision: [(](a|b)[)]` → passes; the choice is consistent
  with the measured results (if (a) loses a mechanism the SPEC requires, the finding says so and
  how that is handled).
- Probe `mechanisms` works and is read-only → `just with-swtpm cargo run -q --locked -p
  custodio-it --example tpm-probe -- mechanisms` → exit 0; with `--tcti swtpm:path=/nonexistent`
  → non-zero exit with a message; `tpm2_getcap handles-persistent` and the NV listing before and
  after a run on a fresh `swtpm` are identical (pasted in the finding); an unknown subcommand
  → exit 2.
