# F108 — Research: how swtpm reaches the end-to-end containers

## Scope
Built: a section `## F108` in `docs/findings.md` that settles the SPEC open question "How `swtpm`
reaches the end-to-end containers". Every claim is backed by a command and its output, run in the
debian13 target container (`e2e/targets/debian13/Containerfile`, `--privileged --cgroupns=host`
like `e2e/run.sh`) under the dev container's rootless podman, and marked verified or inferred as
the rest of the file does. It covers two routes:
- **Route 1, vTPM proxy.** `swtpm chardev --vtpm-proxy` on `/dev/vtpmx` (host module
  `tpm_vtpm_proxy`), which would give the container a real `/dev/tpmrm0`. The step runs the
  smallest commands that show whether it can work here: `/dev/vtpmx` in the dev container and in
  the container, `/proc/modules` and `/proc/misc` for `tpm_vtpm_proxy`, whether the dev container
  user can load a module or create the device, and `swtpm chardev --vtpm-proxy` itself. Checked in
  this session (dev container): `/dev/vtpmx` and `/dev/tpm*` do not exist, `/lib/modules/$(uname -r)`
  does not exist, `/proc/config.gz` is unreadable, `sudo -n` gives no root, and the host's `tpm`,
  `tpm_crb` and `tpm_tis` modules are loaded but `tpm_vtpm_proxy` is not. If the run confirms that
  route 1 needs a host change (module loaded, `/dev/vtpmx` passed into the dev container), the
  finding says exactly which change, and the builder writes `BLOCKED.md` for a person (question and
  options) after the research is done, as the description requires. It still reports route 2 fully.
- **Route 2, socket and drop-in.** `swtpm` runs in (or is reachable from) the container and the
  service reaches it by a TCTI string through a test-only systemd drop-in, never in the shipped
  unit or packages. The step decides within limits: how the service's TCTI is set (environment in the
  drop-in, or another way the service's code allows, which the finding reads from the TPM module
  F104/F106 left, `tss-esapi` accepting `swtpm:path=`), where the socket lives (inside the container
  versus a bind mount from the dev container, given the unit's sandbox, `PrivateTmp`, `ProtectSystem`),
  and what the unit's sandbox lets through. It does not need the real service TPM code; a unit's
  sandbox is shown with the shipped `custodio.service` plus a drop-in running `systemd-run`-style
  or `systemctl show -p Environment` and a process in the unit's namespace reading the socket.

For the chosen route the finding states, each with a command run (or marked inferred):
- how a case gets **a TPM**, **no TPM**, and **a TPM lacking a capability** (the F107 filter,
  `custodio_it::tpm_filter::TpmFilter`, in front of `swtpm`'s socket; reused, not rebuilt);
- how `tpm2-tools` in the container reach the same TPM (TCTI string or device, `TPM2TOOLS_TCTI`,
  and the one-client-at-a-time limit of `swtpm` from F105), shown by `tpm2_getcap` and a
  `tpm2_pcrread` in the container against the same instance the service uses;
- how a case **extends a PCR**, **restarts `swtpm`** (state persisted, `swtpm_ioctl -i` plus
  startup as in F106) and **clears it** (`tpm2_clear`), with the PCR value before and after;
- how a run **proves the shipped unit carries no test drop-in**: the package's file list and
  `systemctl cat custodio.service` (or `systemctl show -p DropInPaths`) on a container with the
  package installed and without the test drop-in show none; with the drop-in installed the command
  shows it (negative control); the finding says where the drop-in lives (a path the packages never
  own, removed by the run) and what check F109 onward (the `e2e` setup) should run.
It ends with a line `Decision: ` naming the route (or "route 1 needs a host change, see BLOCKED.md").
The words `vtpm`, `/dev/tpmrm0`, `drop-in`, `TCTI`, `tpm2-tools` and `debian13` appear.

Left to other features: the shipped TPM module and capability query, the real TPM cases (F109
onward), the `e2e` wiring that implements the chosen route, and the per-target device questions of
F109 (`tss` group, `PrivateDevices`, `DeviceAllow`). This feature changes no recipe, unit, script or
Rust code, and not `SPEC.md`. The other targets (ubuntu, fedora, alma, arch) are not run; the
finding says whether the route is expected to differ by target (inferred) for F109 to check.
Nothing here is proven only at a checkpoint.

Environment, checked this session: `podman` is installed and rootless with the `vfs` driver
(`podman info`), no image is cached, and the network reaches `deb.debian.org`, so the debian13
image builds (`podman build -f e2e/targets/debian13/Containerfile`, notes in `docs/findings.md`
"Nested podman in the dev container"). `swtpm` 0.7.1 is installed. `just with-swtpm` works (F104).
If the nested container cannot run systemd with a privileged flag here, the finding records the
failing command and what was used instead (the earlier e2e logs in `target/e2e/` show it ran).

## Steps
- [ ] Build or reuse the debian13 image under rootless podman, start it as `e2e/run.sh` does,
      and record `systemctl is-system-running`; add `swtpm`, `swtpm-tools` and `tpm2-tools` from
      Debian in the container (finding records the package names; a new package list line in the
      Containerfile is not made here).
- [ ] Route 1: run the vtpm commands in the dev container and in the container (device, module,
      `swtpm chardev --vtpm-proxy`); record exact output and whether it works. If it does not,
      record the smallest host change.
- [ ] Route 2: in the container, start `swtpm` on a socket, point a unit at it with a drop-in
      (using the shipped `custodio.service` text from `data/` or the installed package, or a
      stand-in unit with the same sandbox lines if the package cannot be installed in this
      session; say which), and show a process in that unit's sandbox talking TPM with
      `tpm2-tools`/`tss-esapi` over the TCTI.
- [ ] For the chosen route: TPM / no TPM / lacking capability (filter) setups, `tpm2-tools` in
      the container reaching the same TPM, PCR extend, `swtpm` restart (PCR persists), clear, and
      the drop-in absence check with its negative control; record each command and output.
- [ ] Write `## F108` in `docs/findings.md` with all of the above, the words listed in Scope, and
      the `Decision: ` line; `just quick`; the whole `verify`; commit. If route 1 is the only
      working one and needs a host change, also write `BLOCKED.md` (question, options) and commit.
