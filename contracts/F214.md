# F214 — Decrypted keys stay out of swap and core dumps

## Scope
Builds (SPEC Design 4, acceptance 24, GitHub issue #53): custodiod protects itself at start (core limit 0, then non-dumpable),
so a crash leaves no core and no crash report with its memory, whatever the unit says and whatever the core handler;
`LimitCORE=0` and `MemorySwapMax=0` (the only swap protection) in `data/custodio.service`, the one source every format's unit is
derived from (`scripts/derive-units.sh`); `scripts/check-unit-hardening.sh` requires each exactly once; a container case group
`memory-*` on debian13 and a VM group `vm-memory-*` (Ubuntu 26.04, full mode) under the default handler and under
systemd-coredump; the hibernation and swap text of `docs/threat-model.md`, `docs/api.md` ("Storage kinds") and
`docs/release-notes-v0.9.0.md`.

Fixed here, not reopened:
- First thing in `run()` (the body `main` calls), before `KeyStore::open`: `rustix::process::setrlimit(Resource::Core, Rlimit { current: Some(0),
  maximum: Some(0) })`, then `rustix::process::set_dumpable_behavior(DumpableBehavior::NotDumpable)`. rustix 1.1.6 with the
  `process` feature is already a custodiod dependency and has both, so `#![forbid(unsafe_code)]` stays on `main.rs` and `lib.rs`;
  no new crate, no `libc`/`nix`. If either fails custodiod prints the error and exits 1. Lowering a limit needs no capability;
  `setrlimit`/`prlimit64` and `prctl` are in `@system-service` and not in `~@privileged @resources`. custodiod never changes its
  credentials after start, so nothing resets the flag (see the kernel note below).
- Why this holds under any handler, read for this contract (Linux and systemd `main`, apport `main`, fetched 2026-11-21):
  - Kernel, the flag. `kernel/sys.c` `PR_SET_DUMPABLE` accepts only `TASK_DUMPABLE_OFF` or `TASK_DUMPABLE_OWNER`;
    `fs/coredump.c` `vfs_coredump()` returns early when `coredump_skip()` finds `cprm->dumpable == TASK_DUMPABLE_OFF`, before any
    file or pipe helper is set up. So no handler, apport or systemd-coredump, receives the memory of a non-dumpable process, and
    `fs.suid_dumpable=2` (set by both handlers) does not apply: `kernel/cred.c` `commit_creds()` writes `suid_dumpable` into the
    flag only when euid, egid, fsuid, fsgid change or capabilities shrink, which custodiod never does after start.
  - Kernel, the limit. `coredump_pipe()`: "Normally core limits are irrelevant to pipes"; only `limit == 1` aborts, then
    `cprm->limit = RLIM_INFINITY`. The limit stops the kernel's own core file (`coredump_file()`), not a pipe.
  - apport (`data/apport`): `write_user_coredump()` returns on `limit == 0`, but `process_crash_from_kernel_with_proc_pid()`
    still stores stdin as `info["CoreDump"]` in the `.crash` report (capped at 3/4 of RAM): apport ignores the limit for the
    report, and does not refuse a non-dumpable process (`determine_report_owner()` only makes the report root's). It never sees
    custodiod's crash because the kernel skips it (above); the limit alone would not protect against apport.
  - systemd-coredump: `coredump-context.c` takes the limit from `%c` (or `pid_getrlimit(…, RLIMIT_CORE, …)`), the crashed
    process's own; `coredump-submit.c` `save_external_coredump()`: `if (context->rlimit < page_size())` logs "Resource limits
    disable core dumping for process …" and creates no file. It is the second layer if the flag were ever reset.
  - So `/proc/self/coredump_filter` is not needed: with the flag off no dump exists to filter. Consequence for the cases: a crash
    of custodiod is never handed to a handler, so systemd records `Result=signal` (killed), not `core-dump`, and no handler
    writes a journal entry for it.
- Ubuntu 26.04's default handler, found from the archive (not yet from the image): the `server`, `server-cloud-minimal` and
  `cloud-image` (via `Task-Seeds: server`) seeds at ubuntu-archive-team.ubuntu.com/seeds/ubuntu.resolute/ list `apport`, none
  lists `systemd-coredump`; `apport` 2.34.0-0ubuntu2 depends on `apport-core-dump-handler | systemd-coredump`, so the default is
  `apport-core-dump-handler` (`apport.service`), and apport's `start_apport()` sets `kernel.core_pattern` to
  `|/usr/share/apport/apport -p%p -s%s -c%c -d%d -P%P -u%u -g%g -F%F -- %E` and `fs.suid_dumpable=2`. The VM group records
  what the image actually has; whatever it is, it is the "default handler" of the cases.
- apport ignores executables that belong to no package, so the default-handler control crashes a packaged binary (e.g.
  coreutils' `sleep`). A control that leaves no report means the handler is not storing, and the case fails.
- Out of scope: `MADV_DONTDUMP`, `mlock`, `memfd_secret`, `coredump_filter` (the flag, the limit and `MemorySwapMax=0` cover the
  whole process, libraries' copies included); root reading the running service's memory; making hibernation safe (documented:
  encrypted swap and hibernation image).
- Every format ships the same unit: `check_packages.py` already requires each format's unit to come from
  `target/units/<format>/custodio.service`, derived from `data/custodio.service`; the static check of the source is enough.
  The real packages' unit is proven at F213 (`just package-gates`).

Environment:
- Non-dumpable keeps what custodiod reads of itself readable (`/proc/self/fdinfo/<pidfd>` for the peer check,
  `/proc/self/mountinfo`, `/proc/self/cgroup`). Run on the host (kernel 7.0.0): a Python process that called
  `prctl(PR_SET_DUMPABLE, 0)` read all three and listed `/proc/self/fd` and `/proc/self/fdinfo`; `/proc/self/status` became
  uid 0. The containers share the host kernel; the VM's kernel is proven by its `sign-*` cases at F213. If a sign or snap case
  fails there with the peer check refused, that is this feature's defect, fixed here.
- Containers share the host's `kernel.core_pattern` (host: `core`, `fs.suid_dumpable = 0`), so no container can run apport or
  systemd-coredump as the handler: crashes are proven only in the VM, which has its own kernel. The VM group first records
  `kernel.core_pattern`, `fs.suid_dumpable` and the default handler's package and version, and runs the default-handler cases;
  then installs `systemd-coredump` from the signed archive if absent (as F200 installs fprintd), makes it the handler (its
  sysctl file applied, apport stopped for the rest of the run), and records the same. If a handler cannot be made the one
  `kernel.core_pattern` names, its stage case fails and its cases fail with it, never skip (as acceptance 19).
- `memory.swap.max` needs the cgroup v2 memory controller, which a nested container may not delegate: read only in the VM.

## Evidence
- The unit sets `MemorySwapMax=0` and `LimitCORE=0`, each once (Design 4) → `scripts/test-check-unit-hardening.sh` → the
  shipped unit passes `check-unit-hardening.sh`; a copy without `MemorySwapMax=0` and a copy with `LimitCORE=infinity` each fail
  it. `just unit-verify` and `just security-ceiling` pass (the settings parse, exposure not above 0.7).
- custodiod lowers its own core limit and is non-dumpable → unit test `core_limit_and_dumpable` → after the
  call `getrlimit(Core)` is 0/0 and the flag reads `NotDumpable` (fails if either call is removed). Fail-closed is a review point, not a test:
  neither syscall can be made to fail in a test (lowering a limit and clearing the flag do not fail without seccomp). The
  function returns the error of either call, and the call is `harden()?` on the first line of `run()` in
  `crates/custodiod/src/main.rs`, before `KeyStore::open`; `main` already prints the error and exits 1 when `run()` returns
  `Err`. The reviewer checks the result is propagated, not discarded; `just mutants-diff F214` → no
  surviving mutant. That it runs before any key is read is a review point (first line of `run()`, before `KeyStore::open`).
- The running unit has both settings (acc. 24) → `memory-unit-settings` (debian13): `systemctl show custodio -p MemorySwapMax
  -p LimitCORE` prints `MemorySwapMax=0` and `LimitCORE=0` → pass.
- The running process's own core limit is 0 → `memory-core-limit`: `/proc/<MainPID>/limits` "Max core file size" is 0 soft and
  hard → pass. (That it holds without the unit is proven by the `*-override` VM cases and the unit test.)
- The running process is not dumpable → `memory-not-dumpable`: the service's `/proc/<MainPID>/status` Uid is not 0 and its
  `/proc/<MainPID>` entries are owned by uid 0; in the same case a control process run as a non-root uid has its entries owned by
  that uid (the check can tell the two apart) → pass; the control reading 0 fails the case.
- The kernel applies the swap limit (acc. 24) → `vm-memory-swap-max`: `memory.swap.max` of the service's cgroup is `0` → pass.
- "A crash" below means: SIGSEGV to the MainPID; wait for the unit to be failed; systemd's `Result` is `signal` (the kernel
  produced no dump; `core-dump` fails the case); the handler's store gains nothing for custodiod; then `reset-failed`, and the
  next bus call starts the service again (`ListKeys` answers). The store: apport, no new `/var/crash/*.crash` with a `CoreDump`
  field and nothing new in `/var/lib/apport/coredump/`; systemd-coredump, nothing new in `/var/lib/systemd/coredump/` and no
  `coredumpctl` entry with a stored core for the pid.
- Default handler is staged and recorded, never skipped → `vm-memory-default-stage`: `kernel.core_pattern` (expected apport's
  pipe), `fs.suid_dumpable`, the handler's package and version in the record; a pattern that pipes to no handler fails → pass. If the image ships apport disabled (`/etc/default/apport` `enabled=0`), the stage records it and fails; it does not enable apport.
- Default handler, shipped unit (acc. 24) → `vm-memory-default-crash`: a crash → pass.
- Default handler, unit overridden (acc. 24) → `vm-memory-default-crash-override`: a drop-in under
  `/run/systemd/system/custodio.service.d/` sets `LimitCORE=infinity`, daemon-reload, restart; `systemctl show` gives
  `LimitCORE=infinity` while `/proc/<MainPID>/limits` reads 0; a crash → pass. The drop-in is removed and the service restarted.
- The default-handler checks can fail → `vm-memory-default-control`: a transient unit (`systemd-run -p LimitCORE=infinity`) of a
  packaged binary, SIGSEGV the same way: `Result=core-dump`, and a `.crash` with a `CoreDump` field (or a core in
  `/var/lib/apport/coredump/`) appears for it → pass; none means the handler is not storing and the group proves nothing, so the
  case fails. The report is removed afterwards.
- systemd-coredump is staged and recorded, never skipped → `vm-memory-coredump-stage`: after the default-handler cases,
  `kernel.core_pattern` pipes to `systemd-coredump`; versions and `fs.suid_dumpable` in the record → pass; otherwise it and the
  group's later cases fail.
- systemd-coredump, shipped unit and overridden unit (acc. 24, issue #53) → `vm-memory-coredump-crash` and
  `vm-memory-coredump-crash-override` (the same drop-in cycle) → a crash each → pass.
- The systemd-coredump checks can fail → `vm-memory-coredump-control`: the same transient process: `Result=core-dump` and a core
  under `/var/lib/systemd/coredump/` for it → pass, else the case fails; the file is removed.
- The lacking mode reports the group skipped with the reason in `e2e/vm/skip.list` (the behaviour does not depend on the TPM
  mode).
- Documents: hibernation, encrypted swap, what the flag, the limit and the settings cover → `scripts/test-docs-threat-model.sh`,
