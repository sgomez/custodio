# F130 — Resource test: more calls than TPM object slots

## Scope
The integration target `tpm_resources` in `custodiod` (`crates/custodiod/tests/tpm_resources.rs`, reusing the
`storage_choice`/`sign_kinds`/`tpm_import` rigs through `#[path]`, as `tpm_lifecycle` does): the real service on the
private bus with fake polkit approving, a real `swtpm`, the in-memory journal. Everything goes through the bus
(`ImportKey`, `Sign`), not through `custodiod::tpm` directly.

- The slot count is read from the `swtpm` itself (`tpm2_getcap properties-fixed`, the transient-object capability the
  TPM reports) and is asserted to be small and positive. The number of calls is derived from it (a multiple of it plus
  a margin), not a literal, so a TPM with more slots makes the test run more calls.
- Two runs of calls, each longer than the slot count: signatures (kind `tpm`, RSA 2048 and P-256) and imports (kind
  `tpm`, both key types, each import a new key id).
- "Including after calls that fail midway": calls in which a TPM command fails or the connection drops, via the
  `tpm_filter` (`custodio_it`) in front of the `swtpm`, on commands that come after an object was loaded or created
  (for sign: `Load`, `Sign`/`RSA_Decrypt` as the signing path uses; for import: `Import`, and the flush that follows
  `CreatePrimary` as `tpm_import/flush.rs` does). Each failure is followed by calls that succeed, and the failures are
  more numerous than the slots in total, so a leak per failure would exhaust the TPM.
- Not here: the per-call flush of every object and session at the library level, and 30 direct signs / 10 direct
  imports (F114, F113: `tpm_sign::many_signatures_in_a_row`, `tpm_import::many_imports_in_a_row`,
  `tpm_import::nothing_loaded`); `encrypted-tpm` (no TPM objects per call except the credential, F118/F129); a cleared
  TPM (F129). No mutants (`verify` has none). Package gates and e2e are at the checkpoints.

Environment check: `swtpm 0.7.1` and `tpm2_getcap` under `/usr/bin` (the `tpm_sign` target already reads
`properties-fixed` from this `swtpm`; its F113 finding records three transient objects at a time and no resource
manager). Size: four steps, no split.

## Steps
- [ ] Tests first: `tpm_resources.rs` with the cases below and the slot-count helper (failing until wired).
- [ ] Wire the rig: service + `swtpm` + optional fault filter in front of the TPM the service uses; helper that
      imports, signs, verifies, and checks nothing is loaded.
- [ ] Long runs (signs, imports) and the failing-midway runs, each followed by successful calls.
- [ ] Negative controls, then `just quick` and the evidence command.

## Evidence
- Slot count comes from the TPM → `tpm_resources::slot_count_is_reported` → the value parsed from `tpm2_getcap
  properties-fixed` on the `swtpm` is at least 1 and below a bound that keeps the test short (the parse requires the
  capability's name and value lines; a getcap output without them fails the test). Control: the parser, given a text
  with the line removed, errors instead of returning a default.
- More signatures than slots → `tpm_resources::signatures_exceed_slots` → for both key types, `slots * 3 + margin`
  consecutive `Sign` calls through the bus all succeed and each verifies with the key's certificate by an independent
  implementation (`openssl`); the count of calls asserted greater than the slot count; after the run the TPM holds no
  transient object, loaded session or saved session. Negative control: with a fault filter that lets `FlushContext` fail
  silently for one call (or a deliberately leaking client loading `slots` objects on the same `swtpm`), the next call
  fails — showing the run would detect a leak of one object per call.
- More imports than slots → `tpm_resources::imports_exceed_slots` → for both key types, more `ImportKey` calls than
  the slot count, each a new id, all succeed and return kind `tpm`; `ListKeys` shows them all; the TPM then holds
  nothing; and a sign with the last imported key of each type succeeds and verifies.
- Failing midway, signatures → `tpm_resources::failed_signatures_leave_no_slot_used` → for each of the failing
  commands named under Scope and for both fault actions (error response, connection dropped mid reply), a `Sign` fails
  with an error (not a success), repeated so the failures alone number more than the slots; after each batch the TPM
  holds nothing and the next more-than-slots run of signatures succeeds and verifies. The test asserts that the filter's
  record shows the faulted command reached (so a fault that never fires fails the test) and that the `Sign` before the
  faults and after them both succeed.
- Failing midway, imports → `tpm_resources::failed_imports_leave_no_slot_used` → same shape for `ImportKey`: failures
  at `Import` and at the flush-adjacent command named under Scope, more failures than slots, each import returns an
  error and stores no key file (the key count in `ListKeys` and on disk is unchanged); then more-than-slots successful
  imports and a verified sign with one of them; the TPM holds nothing.
- Interleaving → `tpm_resources::mixed_calls_in_a_row` → one sequence alternating import, sign, failed sign, failed
  import, delete of an imported key, for more than `slots * 3` rounds, ends with all expected calls succeeded, the
  TPM holding nothing, and `ListKeys` equal to the keys the sequence expects to remain.
- Documentation of the guarantee holds → no test on wording; the guarantee is the three tests above (SPEC §Resource
  test).
