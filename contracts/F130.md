# F130 — Resource test: more calls than TPM object slots

## Scope
The integration target `tpm_resources` in `custodiod` (`crates/custodiod/tests/tpm_resources.rs`, reusing the
`storage_choice`/`sign_kinds`/`tpm_import` rigs through `#[path]`, as `tpm_lifecycle` does): the real service on the
private bus with fake polkit approving, a real `swtpm`, the in-memory journal. Everything goes through the bus
(`ImportKey`, `Sign`), not through `custodiod::tpm` directly.

- The slot count is read from the `swtpm` itself (`tpm2_getcap properties-fixed`, the transient-object capability the
  TPM reports) and is asserted to be small and positive. The number of calls is derived from it (a multiple of it plus
  a margin), not a literal, so a TPM with more slots makes the test run more calls.
- Two runs of calls, each longer than the slot count: signatures (kind `tpm`, RSA 2048 and P-256) and imports (kind
  `tpm`, both key types, each import a new key id).
- "Including after calls that fail midway", in two classes, using the `tpm_filter` (`custodio_it`) in front of the
  `swtpm`. The filter never forwards a faulted command, and this `swtpm` has no resource manager (F113 finding;
  `tpm_sign/blobs.rs`, `tpm_import/flush.rs`):
  - Error responses the code flushes after: `Respond(0x101)` (not a lack-like code, which would make the service fall
    back to another kind) on `Load` and `Sign` (sign path; `RSA_Decrypt` too if the path uses it) and on
    `CreatePrimary` and `Import` (import path). The service must leave nothing loaded, even with failures repeated
    more times than there are slots.
  - Connection drops (`DropMidReply`) on the same commands and `Respond(0x101)` on `FlushContext`: the service cannot
    flush, so the stand-in for the kernel resource manager (`tpm2_flushcontext -t`, as `blobs.rs` does) runs after each
    one; the call must still fail with an error and the next calls must succeed.
  Each failure is followed by calls that succeed.
- Not here: the per-call flush of every object and session at the library level, and 30 direct signs / 10 direct
  imports (F114, F113: `tpm_sign::many_signatures_in_a_row`, `tpm_import::many_imports_in_a_row`,
  `tpm_import::nothing_loaded`); `encrypted-tpm` (no TPM objects per call except the credential, F118/F129); a cleared
  TPM (F129). No mutants (`verify` has none). Package gates and e2e are at the checkpoints.

Environment check: `swtpm 0.7.1` and `tpm2_getcap` under `/usr/bin` (the `tpm_sign` target already reads
`properties-fixed` from this `swtpm`; its F113 finding records three transient objects at a time and no resource
manager). Size: four steps, no split.

## Steps
- [x] Tests first: `tpm_resources.rs` with the cases below and the slot-count helper (failing until wired).
- [x] Wire the rig: service + `swtpm` + optional fault filter in front of the TPM the service uses; helper that
      imports, signs, verifies, and checks nothing is loaded.
- [x] Long runs (signs, imports) and the failing-midway runs, each followed by successful calls.
- [x] Negative controls, then `just quick` and the evidence command.

## Evidence
- Slot count comes from the TPM → `tpm_resources::slot_count_is_reported` → the value parsed from `tpm2_getcap
  properties-fixed` on the `swtpm` is at least 1 and below a bound that keeps the test short (the parse requires the
  capability's name and value lines; a getcap output without them fails the test). Control: the parser, given a text
  with the line removed, errors instead of returning a default.
- More signatures than slots → `tpm_resources::signatures_exceed_slots` → for both key types, `slots * 3 + margin`
  consecutive `Sign` calls through the bus all succeed and each verifies with the key's certificate by an independent
  implementation (`openssl`); the count of calls asserted greater than the slot count; after the run the TPM holds no
  transient object, loaded session or saved session. Negative control: a leaking client that loads `slots` objects on the same `swtpm`
  (`tpm2_createprimary`) makes the next `Sign` fail, so the run would detect a leak.
- More imports than slots → `tpm_resources::imports_exceed_slots` → for both key types, more `ImportKey` calls than
  the slot count, each a new id, all succeed and return kind `tpm`; `ListKeys` shows them all; the TPM then holds
  nothing; and a sign with the last imported key of each type succeeds and verifies.
- Failing midway, signatures → `tpm_resources::failed_signatures_leave_no_slot_used` → for each (command,
  `Respond(0x101)`) pair of the first class, a `Sign` fails with an error, repeated more times than the slots, then
  the TPM holds nothing and a run of more-than-slots signatures succeeds and verifies. For each drop/flush-failure pair
  of the second class, the call errors, the stand-in flush runs, and the next more-than-slots run succeeds. The filter's
  record shows each faulted command was reached (a fault that never fires fails the test), and a `Sign` before and
  after the faults succeeds.
- Failing midway, imports → `tpm_resources::failed_imports_leave_no_slot_used` → same shape for `ImportKey` with
  `CreatePrimary` and `Import` faults (class one: repeated more than slots, nothing loaded) and drops (class two);
  each failed import returns an error and stores no key (`ListKeys` and the files on disk unchanged); then
  more-than-slots successful imports and a verified sign with one of them.

## Builder notes (from the evaluator's approval)
- Pair each faulted command with the key type that sends it (`Sign` for P-256, `RSA_Decrypt` for RSA); a fault that
  cannot fire for a key type is not listed for it.
- In class two, assert that handles are left behind after a `FlushContext` fault before the stand-in flush runs.
- A failed flush must reach the bus as an error; if it does not, amend the contract rather than relax the assert.
- Class two needs one run longer than the slot count after the last fault, not after every pair.
