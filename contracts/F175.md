# F175 — Per-connection peer check and peer-to-peer D-Bus with ListKeys for the peer's own uid

## Scope
Builds, for the `firefox` snap socket F173 already passes to custodiod: (1) the per-connection peer
check, (2) a peer-to-peer zbus server on each accepted connection that exports the interface at the
bus name's object path with `ListKeys` only, (3) `ListKeys` filtered by the peer's uid, (4) the
test-only credential source and the gate that keeps it out of shipped files. Left for others:
`Sign` on the socket, polkit, journal fields (F176); `ImportP12`/`DeleteKey`/`ReplaceCertificate`
being unknown, introspection of exactly `ListKeys` and `Sign`, and limits and timeouts (later
features: acceptance 3 and 7). Here the socket interface holds `ListKeys` alone. Acceptance 2 (accept
and refuse cases) and 5 are proven here; acceptance 15's test-label half is proven here (its exposure
half is F173).

Fixed by earlier work, not re-decided: `docs/findings/F170.md` Decisions: `PrivateUsers=identity`;
the service takes the uid from `SO_PEERCRED` only and treats 65534 as unknown (refused before any
polkit call); the p2p server is `ANONYMOUS` only, with no `.user_id()`, so no uid the peer claims is
ever compared; an `EXTERNAL` client is rejected. The label verdict is `custodiod::peer_label::check`
(F174). The handshake choice is recorded in `docs/decisions.md` (step 1), as the feature requires,
with a one-line pointer to F170.

Check on accept, once per connection, before any bytes are read: read `SO_PEERCRED`, `SO_PEERPIDFD`
and `SO_PEERSEC`. Refuse (close, journal a line naming the reason, never the label bytes or key
material) unless all three are readable, the label passes F174, and the uid is neither 65534 nor
unreadable. Root is not special: root with a bad label is refused; root with a good label is
accepted as uid 0. The pidfd is kept with the connection for F176.

Test-only source: a Cargo feature (the existing `test-seam`, or a sibling the builder names)
that lets a test supply the label, and the uid/pidfd outcome, per socket instead of the kernel's.
It is a dev-dependency feature only and has the existing `compile_error!` in release builds. Real
kernel reading is also tested with no seam: in the dev container a real peer connects, the uid and
pidfd are read for real and the label is whatever `SO_PEERSEC` really gives (unreadable here), which
must be refused. The overflow uid cannot be produced unprivileged (a peer's uid is always the
caller's own kuid; checked: `unshare -U -r` works but changes only how a uid is shown inside), so
overflow, unreadable uid, root and a missing pidfd are proven through the seam's injected
credentials into the same decision function the accept path calls, and the real-socket test proves
the accept path calls it.

Environment checked: user `dev` (uid 1000), `unshare -U -r` available, no privilege available.

Cost of the new tests:
- `crates/custodiod/tests/snap_socket_peer.rs`: in-process, one private bus-less p2p connection per
  case over `UnixStream::pair`/tempdir sockets; about 15 cases, under 3 s total, parallel with other
  integration tests. Waits are on the connection (reply or end-of-file), no fixed `sleep`.
- Unit tests of the decision function: milliseconds.
- `scripts/check-test-label.sh` (in `just quick`, added to the recipe) ~0.2 s of greps;
  `scripts/test-check-test-label.sh` ~2 s of fixture copies, run by `verify` and added to
  `test-scripts` (parallel with the other script tests; within the 120 s `script *` budget).
  `quick` is not slowed beyond the 0.2 s.
- No e2e case: the real-confinement label is case 17 (VM), a later feature.
- `just mutants-diff F175`: the new code is small; estimated like F173's 58 mutants, a few minutes.

About five steps; fits one to two sessions; no split.

## Steps
- [ ] Failing tests first: `crates/custodiod/tests/snap_socket_peer.rs` (cases under Evidence) and
      `scripts/test-check-test-label.sh` with its fixtures.
- [ ] Peer credentials: read the three values once per accepted connection; the decision function
      (credentials in, accept with uid and pidfd, or a refusal reason out) with the seam source for
      tests; refuse as Scope says. Record in `docs/decisions.md` the handshake (ANONYMOUS-only p2p
      server, no claimed uid ever used), following that file's rules.
- [ ] Serving: replace "accept and close" for an accepted peer with a p2p zbus server on the
      connection exporting the interface at the same name and path with `ListKeys`, which returns the
      keys of the peer's kernel uid only, via the existing store listing. A failed handshake or
      refusal of one connection never ends the service or affects the bus.
- [ ] `scripts/check-test-label.sh` in `just quick`: counts the test-only source's enabling in `data/`
      and `packaging/` and fails on any; the seam stays a dev-dependency feature only.
- [ ] At the end run `just quick`, the evidence commands, and `just mutants-diff F175`.

## Evidence
- Accepted peer lists only its own keys (acceptance 2) → `snap_socket_peer::own_keys_only` → two
  uids' keys in the store; a peer with the Firefox enforce label and uid A gets exactly A's; a second
  peer with uid B gets exactly B's, and neither sees the other's.
- `ListKeys` is served at the same name and path → `snap_socket_peer::interface_and_path` → a
  p2p client calls `ListKeys` on `BUS_NAME`/`OBJECT_PATH` and gets the reply.
- Refused labels (acceptance 2) → `snap_socket_peer::refused_labels` → one case each for unconfined,
  another snap's label, a non-snap label, Firefox in complain mode, stacked `//&unconfined`, a child
  profile and an SELinux context: the connection is closed with no method answered (a `ListKeys` call
  fails, nothing returned); the control, the exact enforce label, is accepted in the same harness.
- Missing pidfd or label (acceptance 2) → `snap_socket_peer::missing_pidfd`, `::missing_label` →
  refused although the other two values are valid; accepted when all three are supplied.
- Root with a bad label is refused, root with the good label accepted → `snap_socket_peer::root`.
- Overflow and unreadable uid (acceptance 5) → `snap_socket_peer::overflow_uid` (65534 and
  70000 reported as unmapped) and `::unreadable_uid` → closed connection, no key of any uid returned;
  control: a real uid with the good label is accepted.
- Real kernel path without the seam → `snap_socket_peer::real_peer_without_label` → a real
  `UnixStream` peer of this process: uid and pidfd readable, label unreadable → refused; proves the
  accept path reads the kernel and refuses on a failed `SO_PEERSEC`.
- Never trusts a claimed uid (F170 decision) → `snap_socket_peer::claimed_uid_ignored` → a
  client that announces another uid in the handshake (`EXTERNAL` with uid B) is rejected, and an
  `ANONYMOUS` client still gets its kernel uid's keys, not B's.
- Refusal text leaks nothing → `snap_socket_peer::refusal_journal` → the journalled line names the
  reason and holds neither label bytes nor any key id.
- The service survives bad peers → `snap_socket_peer::bad_peer_then_good` → after a refused peer
  and a peer that sends garbage, an accepted peer still lists.
- Handshake mechanism recorded → the step's commit and `docs/decisions.md` entry (read by a person;
  not tested by wording, per CLAUDE.md).
- Test-label source never ships (acceptance 15) → `scripts/check-test-label.sh` in `just quick` →
  passes on the tree: zero enabling occurrences in `data/` and `packaging/`, and the feature only a
  dev-dependency.
- Gate can fail → `scripts/test-check-test-label.sh` → passes on a copy of the shipped files; each
  fixture fails with a message naming the fault: the feature turned on in a unit file, in
  `packaging/nfpm.yaml` or a packaging script, in a `data/` file, and as a normal (non-dev)
  dependency feature or default feature in `Cargo.toml`.
- Mutants → `just mutants-diff F175` → no surviving mutant in the check, decision function or
  `ListKeys` filtering.
