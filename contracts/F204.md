# F204 — End-to-end: doctor on every target

## Scope

Built here:

- **A `doctor-*` case group** of the container suite. A new guest step `doctor` (`e2e/doctor-run.sh` as root, and `e2e/doctor-user.sh`
  as a regular account in a login session, `su -l`, as `cli-run.sh`/`cli-user.sh` do) runs the real `custodio doctor` of the installed
  package on each of the five targets, after the package is installed and the service runs. `case_group` and `phase_runs` in
  `e2e/select.sh` learn the group; `e2e/guest.sh` calls the step right after `fingerprint` and before `upgrade`; the lists in
  `scripts/test-e2e-select.sh` and any group list the self-tests read are extended. Containers only (the VM group is F200's, not touched).
  It does not depend on the TPM mode (check 6 reports whatever the service says in the mode of the run).
- **The ids**, in `e2e/cases.list` (every target owes them; none may be skipped): `doctor-six-checks`, `doctor-no-reader`,
  `doctor-override-active`, `doctor-broken-include`, `doctor-no-firefox-profile`, `doctor-journal`, `doctor-state-storage`,
  `doctor-exit-status`, `doctor-never-prompts`, `doctor-root-refused`, `doctor-changes-nothing`. The builder may split or merge ids
  where one judgement needs it; the evidence below must stay covered. No per-target list: nothing here depends on the distribution
  except what the judge reads from the real system (see Evidence).
- **The judge** `e2e/doctor.py` (run by the step) takes the observation files the guest writes (each run's stdout, stderr, exit status,
  manifests, the independent observations below) and decides each case. `scripts/test-e2e-doctor.sh` runs it on fixture observations:
  one accepted set and one rejected set per rule. That is its only test; the guest scripts and wiring are proven by the runs.
- **Left to other features:** the doctor code and its fixture tests (F202, F203, done: all six checks in each state, the exit rules,
  fuzzing of journald's configuration); the real sensor, enrolled finger and `sudo` (F200's VM group; the container has no reader);
  Firefox registered in a profile, a snap copy and p11-kit (F203's fixture tests and the `register` cases; here only the "no profile"
  state is staged, because no Firefox is in the images); the documents.

Environment (checked by the earlier groups): the containers are privileged systemd containers (`podman`), with `fprintd` and its PAM
module installed by F199 and no sensor; the Custodio service runs in them; `/sys/fs/selinux` is not enforcing on this host, which does
not matter here (doctor reads no label). Not shown by the dev container and not needed: a reader, a desktop session.

**Exit 0 cannot be reached in a container, and the contract says so.** The state directory of the containers is on overlay, where
the service reports `StateStorage=unknown` (reason `not-block-filesystem`; `docs/findings/F180.md` line 55, `F189.md` line 54: no dm
device in this container), and doctor prints `not ok` for check 6 on `unknown` (`doctor_later.rs`, `storage`). So on every target every
run of the group exits 1. Stubbing the service's bus name to answer `encrypted` is not planned: it would replace the real service in
`doctor-state-storage`, whose point is the real one. **The exit-0 branch is left to F203's fixture tests (`doctor_decide.rs`
`exit_status`, all combinations) and F200's VM group**; the second step re-checks with a run that check 6 is `not ok` in
the container, and if it is not (a target with an encrypted state directory) the 0 branch is judged for real too. What stops a doctor
that always exits 1 from passing: the exit evidence below is not read from the exit code alone but from **pairs of runs that differ
in one thing** and from the printed lines. The exit status is 1 in the baseline, so the pairs compare the *lines*: the check that
changed must change its word (`ok`, `not ok`, `could not check` are what the binary prints) and carry its fix, while every other
line is identical, and the exit code must match what the lines dictate (1 if any `not ok`/`could not check` among checks 4 to 6 or
the broken-include line; 0 otherwise). A doctor that counts checks 1 to 3, or ignores the broken include, or exits 1 regardless, is
caught where the lines say "nothing counts" and the exit is 1 (judge rule: exit 1 needs a counting line; in the baseline that line is
check 6 `not ok`, so the judge also requires the counting line to be named in the run's record), and by the broken-include pair,
whose lines show the include line `not ok` first (see below).

What the group sees per target is otherwise **decided by the first run** (recorded in `docs/findings/F204.md` if it changes a case):
whether fprintd answers on the bus of the container and what checks 1 and 2 then say (`ok`, `not ok` or `could not check`, never
an error or a prompt); the journal's effective storage in the image. The judge decides from independent observations of the same
system, not from constants per target: check 5 against `/var/log/journal` and the journald configuration as the guest reads them;
check 6 against the `StateStorage` and `StateStorageReason` properties read from the service by the guest with `busctl`
(`docs/api.md`). If a state cannot be staged on a target, the builder amends the case to the narrowest one that still runs there; a
case is never skipped.

**Staging** (by `doctor-run.sh`, restored by one exit trap, in this order of risk): the override (`custodio fingerprint enable`/
`disable`); the vendor file that the override's `include` line actually names (read from the override, resolved as F199's
`fingerprint-run.sh` does per family, renamed in its own directory and put back); the journald drop-in
`/etc/systemd/journald.conf.d/50-persistent.conf` where the journal case needs one (only when the image's journal is not persistent
and `journald.conf.d` can be written; then journald is restarted, and again on restore); `custodio.service` is stopped for the
"could not check" case and started again. `doctor-changes-nothing` excludes **exactly** these paths: the override file, the file the
include names, and that one drop-in file (and `journald.conf.d` itself only if the group created it, with the listing before and
after checked to be equal once restored); nothing above them.

Cost (estimated from F199/F203; the builder measures and records it in PROGRESS.md). Judge test: a Python run on about 25 small
fixtures, under 2 s, in parallel with the other script tests. The group: one `doctor` run costs up to about 1.5 s per question to
fprintd and the service (six checks, most answer at once), about 15 runs, so 15 to 40 s per target, sequential (it shares the real
`/etc/pam.d` with the override cases), in the guest of each target; the five targets run at once. The e2e budgets (debian13 800 s,
ubuntu2604 530 s, fedora44 570 s, alma10 540 s, arch 480 s) are tight against the last loop runs; if the measured full run with the
group does not fit, the builder asks for a bigger budget in BLOCKED.md and does not trim the group. On debian13 a full `just e2e` runs
the swtpm and none modes and so the group twice; accepted.

## Evidence

- Doctor prints one line per check for this container, each with a state and, where not `ok`, a fix, and without an error →
  `doctor-six-checks` (regular user, login session): exactly the six checks (checks 1 to 3 as the binary names them, then `module in
  Firefox`, `persistent journal`, `state directory storage`), each line starts with `ok`, `not ok` or `could not check`, every line
  other than `ok` has a `fix:` line under it, stderr empty, no panic or backtrace text; judge controls: a missing check, a line
  without one of the three words, a missing fix and non-empty stderr are each rejected → `scripts/test-e2e-doctor.sh`.
- What is missing is reported, not turned into an error (checks 1 to 3; the container has no sensor) → `doctor-no-reader`: check 1 is
  `not ok` with the package fix or `could not check` with its reason; check 2 is never `not ok` unless check 1 saw a reader (an
  unanswerable fprintd is `could not check`); and checks 1 to 3 do not count towards the exit status: the pair "doctor as is" and
  "the same run with the override enabled" (check 3 changes word) has the same exit status, and the judge requires, for each exit 1,
  a counting line among checks 4 to 6 or the include line; control: check 2 `not ok` with no reader is rejected, and exit 1 with
  every counting line `ok` is rejected.
- Check 3 sees Custodio's override on the real `/etc/pam.d` → `doctor-override-active`: before `custodio fingerprint enable` check 3 is
  not `ok` with Custodio's override; after it check 3 is `ok` and says `active through Custodio's override`, its include resolves
  (the file it names exists); after `disable` it is back to the first line; checks 4 to 6 lines are identical across the three runs;
  control: a run that says "active through Custodio's override" without the override file is rejected.
- A broken include is the most urgent problem and counts → `doctor-broken-include`: run doctor twice with the override enabled, once
  with its include intact and once with the file that the override's `include` line names moved aside (read from the override, not a
  fixed path). In the second run the line for check 3 is `not ok`, says the include is `missing`, names that file and has the fix
  (reinstall polkit or `custodio fingerprint disable`), it is the first line that is `not ok`, and the other lines are identical to
  the first run's; the judge requires the include line to be named among the counting lines in the exit record, so a doctor that
  ignores the broken include (check 3 `ok`) is rejected even though both exits are 1; file and override are put back by the exit trap.
  Control: a second run with check 3 `ok` and the include missing is rejected; exit 0 with a broken include is rejected.
- No Firefox profile is reported as such, not as a Custodio failure → `doctor-no-firefox-profile` (the account has no profile; the
  images have no Firefox): the `module in Firefox` line is `ok` and says `no browser profile was found`, it has no fix, and it is not
  among the counting lines (the pair "no profile" and the same account with an unreadable `~/.mozilla` that is a file, where the
  line becomes `could not check`, shows that the line would count if it were not `ok`; the second run restores the home exactly);
  control: `not ok` or `could not check` for an account that has no profile is rejected.
- The persistent journal (check 5) is read without root and agrees with the system → `doctor-journal`: the state equals what the guest
  observes independently (`/var/log/journal` present and journald's effective `Storage=`): `ok` ("the journal is persistent") only
  when the directory exists and storage is not volatile or none; `not ok` states the cause and has a fix naming the documented steps
  (`mkdir -p /var/log/journal`, the drop-in); a second run with the drop-in staged (or the directory, whichever the image lacks)
  flips the line to the other word and only that line; control: `ok` with no directory is rejected.
- The storage of the state directory (check 6) is what the service reports → `doctor-state-storage`: with the real service running, the
  line equals the `StateStorage` read by the guest: `encrypted` → `ok`, `not-encrypted` → `not ok` with the full-disk-encryption fix,
  `unknown` → `not ok` and the reason doctor prints (the text after `reason `) equals `StateStorageReason` read by the guest (in the
  containers: `not-block-filesystem`, the only part of the line that varies); with the service stopped by the case (started again by
  the exit trap) the line is `could not check` with its fix; control: `ok` where the service says `unknown`, and a printed reason
  that differs from the property, are each rejected.
- Exit status as its checks dictate → `doctor-exit-status`, over every run of the group, by the judge's rule: the exit is 1 exactly when
  the include line or a line of checks 4 to 6 is `not ok`/`could not check`, and 0 otherwise, using the printed words. In the
  containers the 0 branch does not occur (see Scope); it is proven by F203's fixture tests, and a doctor that always exits 1 is
  caught by the pairs above (broken include ignored, checks 1 to 3 counted, no-profile counted, check 6 `could not check` vs `not
  ok` both 1 but with different lines). Control (judge fixtures): exit 0 with a `not ok` check 6 and exit 1 with all counting lines
  `ok` are each rejected.
- Never a prompt, never root → `doctor-never-prompts`: run with no terminal (stdin from `/dev/null`), no agent in the session, and a time limit; it
  finishes inside the limit, with no new polkit authorization request in the journal and no new Custodio signature entry; the account has no
  sudo rights; control: a run that hit the limit is rejected.
- Refuses root like `register` → `doctor-root-refused`: exit 2 as root, no check lines, `/etc` unchanged; control: exit 0 as root is
  rejected.
- Leaves `/etc` and the user's home unchanged (acceptance 17) → `doctor-changes-nothing`: manifests (path, type, mode, owner, hash,
  mtime) of the whole `/etc` (minus exactly the staged paths of Scope, listed in the script) and of the account's home
  (including that no `~/.mozilla`, `~/.config` or cache file appears) taken before the first and after the last run of the user step are
  identical, and a manifest of `/etc/pam.d` is identical around every single run, including the runs with the override enabled and
  broken; control: a manifest with one changed or added file is rejected.
- The group runs on every target and none of its cases is skipped → the `verify` lines `just e2e-cases <target> 'doctor-*'` for the
  five targets (the accounting of `check-cases.sh` requires each selected id exactly once, run).
- The judge's own rules → `scripts/test-e2e-doctor.sh` (accepted set passes; one negative control per rule fails with the rule named)
  → passes in under 2 s.
- The later steps still work with the group in place → `scripts/test-e2e-select.sh`, `scripts/test-e2e-skips.sh`,
  `scripts/test-e2e-selftests.sh` and `just quick` → green; the full-suite effect is read by the loop against `budgets.tsv`.
