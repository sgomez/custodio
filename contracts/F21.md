# F21 — Multi-part C_SignUpdate and C_SignFinal for composed mechanisms

## Scope
Replaces the `unsupported::SignUpdate`/`SignFinal` stubs with real functions for the six composed
mechanisms. Changes are in `module.rs` (logic, no pointers), `ffi.rs` (argument checks,
`C_SignUpdate`, `C_SignFinal` in the function list), `unsupported.rs` (the two stubs are removed),
their unit tests, and the cryptoki integration tests in `crates/custodio-pkcs11/tests/cryptoki`.

- The sign state of a `Session` gains a multi-part hash state: a `DigestHasher` (F19), created
  by the first `C_SignUpdate` after `C_SignInit` with a composed mechanism and owned by the
  session. Nothing else is kept: no thread, connection or lock past a call. Its `Debug` is the
  placeholder one of `DigestHasher`.
- `Module::sign_update(session, part)`: with a raw mechanism it ends the operation and returns
  **`CKR_OPERATION_NOT_INITIALIZED`** (raw mechanisms are single-part only; this is what SoftHSMv2
  returns, see `docs/findings.md`, and a person confirmed it). A later
  `C_Sign`/`C_SignUpdate`/`C_SignFinal` without a new init gives `CKR_OPERATION_NOT_INITIALIZED`. `sign_final` with a raw mechanism (no update before it, also
  the NULL-buffer length query) behaves the same: same code, operation ended, no backend call,
  no polkit. No init → `CKR_OPERATION_NOT_INITIALIZED`.
  Unknown session → `CKR_SESSION_HANDLE_INVALID`. An empty part (`len 0`, null pointer allowed)
  is valid and changes nothing.
- Hashing a part runs outside the `Mutex<State>` guard, as F20 does for `C_Sign`: the guard block
  takes the hasher out of the session (leaving a "busy" marker) and returns owned values; the
  part is hashed by a free function with no access to `Module`; the hasher is put back under a
  second short lock (dropped silently if the session was closed meanwhile). Different sessions never
  wait for it. What a second call on the same session does meanwhile is the "Busy session" rule.
- `Module::sign_final(session, capacity)`: same outcomes as `sign` — `None` capacity →
  `Length(n)`, capacity `< n` → `TooSmall(n)`, both before any hashing, service call or polkit,
  and keeping the hash state byte for byte. A large enough buffer ends the operation (state taken
  under the lock, so two threads cannot sign twice), builds `sign_input` from the hasher, and calls
  the backend once with the raw mechanism (`CKM_RSA_PKCS`/`CKM_ECDSA`) and only that input. Any
  other failure (`Denied`, `Invalid`, `Unavailable`, wrong signature size) ends the operation with
  the same codes as `sign`. `C_SignFinal` without any `C_SignUpdate` signs the hash of the empty
  message (PKCS#11 allows it).
- `Module::sign` on a session that has had a `C_SignUpdate` returns `CKR_OPERATION_ACTIVE` and
  **ends the operation** (SPEC: any failure but a small buffer ends it, also the length-query form,
  which here is an error, not a successful query). Afterwards `sign_update`/`sign_final`/`sign`
  give `CKR_OPERATION_NOT_INITIALIZED`, with no backend call. A `C_Sign` length query *before* the
  first update is a normal query and changes nothing; updates are accepted after it.
- Busy session: while a part is in flight, a second `sign_update`, `sign_final` or `sign` on the
  same session ends the operation: it sets an "aborted" mark, returns `CKR_OPERATION_ACTIVE`; a
  further such call while the mark is set returns `CKR_OPERATION_NOT_INITIALIZED`. `sign_init`
  while busy returns `CKR_OPERATION_ACTIVE` and changes nothing (as with any open operation).
  The first call, finding the mark, drops its hasher and returns `CKR_OK` (its part was valid);
  it puts the hasher back only if the session's operation is still the one it started, so it can
  never overwrite an operation begun after the abort (each operation carries a counter value).
  After the abort, and once the first call has returned, `sign_final` gives
  `CKR_OPERATION_NOT_INITIALIZED` and a new `sign_init` is accepted.
- Argument errors: `CKR_ARGUMENTS_BAD` raised by `ffi.rs` before `Module` is reached (null part
  with non-zero length, null `pulSignatureLen`) leaves the operation as it was, exactly like
  `C_Sign` today. Asserted for both functions.
- `C_SignInit` while an operation (single or multi-part) is open stays `CKR_OPERATION_ACTIVE` and
  keeps the operation, as today.
- The result of a multi-part signature is byte-identical to `C_Sign` of the concatenation for RSA
  PKCS#1 v1.5 (deterministic); for ECDSA only verification is required.
- Raw mechanisms keep working exactly as in M0/F20; their code paths and tests are not changed.

Left for other features: `C_Login` (F22+), audit/journal, fuzz target for multi-part sequences,
`pkcs11-tool`/OpenSSL e2e. The fork test and thread test additions are in this feature (below).

The feature is about six steps; no split needed.

## Evidence
Unit tests: `cargo test -p custodio-pkcs11 --lib`, with the recording backend from F20
(`(id, SignParams, data)` of every call). Integration: `just test-integration`.

- Any number of updates, then final, signs the hash of all parts → unit test
  `multipart_sends_digest_of_concatenation`: for all six mechanisms, the parts `"a"`, `""`, `"bc"`
  (empty part in the middle) and, in a second run, 1000 one-byte parts and a 3-part split at a
  non-block boundary of a 200-byte message → exactly 1 backend call whose `data` equals the literal
  expected hex (RFC 8017 prefix + FIPS 180 "abc" digest for RSA; bare digest for ECDSA) for "abc",
  and for the 200-byte message equals the data recorded by a single-part `sign` of the same
  message on a second module → equal. Zero updates (`sign_final` only) → data equals the digest of
  the empty message (literal known answer e3b0c442… for SHA-256). Fails if a part is dropped,
  repeated or the hash is reset between updates.
- Hash state belongs to the session → unit test `multipart_state_is_per_session`: two sessions on
  the same token, interleaved updates with different messages, finals in reverse order → each
  recorded input is the digest of its own message. A session closed in the middle: `sign_final`
  → `CKR_SESSION_HANDLE_INVALID`, and a new session's final gives `CKR_OPERATION_NOT_INITIALIZED`.
- No thread, connection or lock past a call → unit test `multipart_leaves_the_lock_free`: after
  `sign_update` returns, `open_session`, `slot_list` and `sign_init` on another session run on a
  thread with `recv_timeout` (a hang is a failure). Integration: the existing `tasks`-style
  count of `/proc/self/task` is repeated around `C_SignUpdate` and also around `C_SignFinal` (before, after, 2 s later equal
  each time; the final is the call that uses the bus) in the scenario `multipart_tasks`. The same three points also
  compare the number of entries in `/proc/self/fd` (the listing's own descriptor is excluded by
  reading it once before the first count and subtracting it consistently): equal around
  `C_SignUpdate` and around `C_SignFinal`, so a bus connection kept open after `C_SignFinal`
  fails the test. `multipart_leaves_the_lock_free` also asserts that `sign_update` makes 0
  backend calls (recording backend), so only `sign_final` touches the service. Hashing outside the lock → unit test
  `multipart_update_busy` (each of update, final, sign in a fresh run): hashing is `hash_part(&mut DigestHasher, &[u8])` with no access to
  `Module`, and while a part is in flight the session is marked busy. The test builds that state
  directly (test-only constructor of the marker) → a second `sign_update`/`sign_final`/`sign` gives
  `CKR_OPERATION_ACTIVE`, other sessions still work; when the first call completes its result is
  `CKR_OK`, its hasher is dropped, and `sign_final` gives `CKR_OPERATION_NOT_INITIALIZED` with 0
  backend calls. Also: while busy, a second aborting call, then `sign_init` → `CKR_OPERATION_ACTIVE`;
  after the first call returns, `sign_init` is accepted, a new update starts, and the first call's
  late return does not overwrite it (the final signs only the new parts). The test finishes
  "the first call" through the same put-back function the real `sign_update` uses (it takes the
  operation counter and the hasher), not through a test copy, so the rule that a late return never
  overwrites a newer operation is tested on the production code. `sign_init` while busy
  and not aborted → `CKR_OPERATION_ACTIVE`, operation kept. That the hash runs outside the lock is shown
  by this structure and checked in review, not by a timing test. Review checks that the guard block returns owned values.
- Length query or too-small buffer in `C_SignFinal`: no polkit, hash state kept, retry asks once
  and signs once → unit test `multipart_final_length_and_small_buffer`: RSA (256) and ECDSA (64):
  `None` → `Length(n)`; `n - 1` and `0` → `TooSmall(n)`; backend 0 calls after each; then a
  buffer of `n` → exactly 1 backend call whose `data` equals the known answer of the whole
  message (fails if the state was lost or reset by the query: the digest would differ), then
  `sign_final` again → `CKR_OPERATION_NOT_INITIALIZED`, backend still 1 call. Also an `update`
  between the small-buffer failure and the retry extends the same message (digest of all parts).
  Integration scenario `multipart_retry` (raw `cryptoki_sys` function list as in
  `composed_retry`; `C_SignInit`, two `C_SignUpdate`, then `C_SignFinal` with NULL buffer,
  1-byte buffer, exact buffer, for one RSA and one ECDSA mechanism): NULL → `CKR_OK` with 256/64;
  1 byte → `CKR_BUFFER_TOO_SMALL` with the same length written back; exact → `CKR_OK`. The parent
  asserts `f.asked() == 2` in total, exactly 2 `Sign` calls on the bus monitor (F20 fixture; the
  monitor must record at least one call or the test fails), and that both signatures verify over
  the original message with the independent verifiers of F20.
- Any other failure ends the operation → unit test `multipart_failure_ends_the_operation`: backend
  `Denied`, `Invalid`, `Unavailable` in turn, and a wrong-length signature → `CKR_FUNCTION_FAILED`,
  `CKR_DATA_INVALID`, `CKR_DEVICE_ERROR`, `CKR_FUNCTION_FAILED`; after each, `sign_update`,
  `sign_final` and `sign` → `CKR_OPERATION_NOT_INITIALIZED` and a new `sign_init` is accepted and
  starts from an empty hash (a following final over new parts equals the digest of the new parts
  only). Integration `multipart_denied` (polkit refuses): `C_SignFinal` fails
  `CKR_FUNCTION_FAILED`, the output buffer is untouched and `*pulSignatureLen` keeps its input value (as in the
  F20 `composed_denied` check);
  an immediate `C_SignFinal` gives `CKR_OPERATION_NOT_INITIALIZED`; a second full attempt (new
  `C_SignInit`, update, final, polkit still refusing) returns `CKR_FUNCTION_FAILED` again and asks
  polkit again (`f.asked() == 2`). Then the fixture switches to allow and a third full attempt
  returns `CKR_OK` with a signature that verifies over its message (`f.asked() == 3`).
- `C_SignUpdate` with a raw mechanism fails and ends the operation → unit test
  `multipart_raw_mechanism_ends`: for `CKM_RSA_PKCS`, `CKM_RSA_PKCS_PSS` (RSA token) and `CKM_ECDSA`
  (P-256), both orders: `sign_update` and, in a separate run, `sign_final` (NULL-buffer length query
  and full buffer, with no update before) → `CKR_OPERATION_NOT_INITIALIZED`; afterwards `sign`,
  `sign_update`, `sign_final` → `CKR_OPERATION_NOT_INITIALIZED`; a new `sign_init` + single-part
  `sign` with the raw mechanism succeeds with 1 backend call; the failed calls made 0. Integration
  `multipart_raw` uses the raw `CK_FUNCTION_LIST` as in `composed_retry`: same codes,
  `f.asked() == 0` after the refusals, then one raw `C_Sign` works (`f.asked() == 1`).
- `C_Sign` after `C_SignUpdate` is rejected as PKCS#11 says → unit test
  `multipart_sign_after_update_is_rejected`: `sign` with a large buffer after one update →
  `CKR_OPERATION_ACTIVE`, 0 backend calls; then `sign_final`, `sign_update`, `sign` →
  `CKR_OPERATION_NOT_INITIALIZED`. Again with the length-query form (`None`) → the same. The
  builder records the SoftHSMv2 behaviour in `docs/findings.md` (the code `CKR_OPERATION_ACTIVE`
  and the ending of the operation are this project's conservative choices). Unit test
  `multipart_sign_query_before_update`: `sign(None)` → `Length`, then two updates and `sign_final`
  → the digest of the parts (1 backend call). Unit test `multipart_sign_init_while_open`:
  `sign_init` before and after the first update → `CKR_OPERATION_ACTIVE`, and the final still signs

  `CKR_OPERATION_ACTIVE`, `C_SignFinal` → `CKR_OPERATION_NOT_INITIALIZED`, `f.asked() == 0`.
- Single-part and multi-part signatures verify and RSA ones are byte-identical (acceptance 2) →
  integration scenario `multipart_equivalence`, whose child signs one message (known marker
  pattern, 100 000 bytes) with every one of the six mechanisms twice: once `C_Sign`, once with
  `C_SignUpdate` in uneven parts (sizes 1, 0, 4095, 4096, the rest) plus `C_SignFinal`, and
  prints both. The parent verifies all 12 signatures with the independent verifiers of F20
  (`rsa` crate `VerifyingKey<ShaN>`; `p256` over its own digest, including the truncation checks

  A separate scenario `multipart_large` signs 64 MiB in 1 MiB parts with `CKM_SHA256_RSA_PKCS`

- Threads: other threads cannot corrupt or finish it → scenario `multipart_threads`: the parent
  opens a multi-part operation on session A (one update). Eight worker threads, each with its own

  ninth thread calls `C_SignInit` on A's handle through the raw function list in a loop →
  always `CKR_OPERATION_ACTIVE`. The ninth thread counts its calls and is stopped by a flag and
  joined (together with the workers) before the main thread calls `C_SignUpdate`/`C_SignFinal` on
