# F93 — End-to-end replace certificate and delete cases

## Scope
Built: the `replace-*` and `delete-*` cases of `e2e/cases.list`, run by the e2e guest as an ordinary account (alice, her own
session and test agent, agent approving) against the shipped service, the CLI, the PKCS#11 module (`pkcs11-tool`) and OpenSSL.
They prove acceptance 5 and acceptance 6 of SPEC.md. The pattern is F92's (`e2e/ops-*.sh`: root side, alice's session, a
judgement library with a self-test) and F91's (`owner-call.py` for the calls the CLI lacks: replace, sign, import; the error
name is read from the D-Bus reply, finding "F91").

Parts:
- Step groups `replace` and `delete` in `e2e/select.sh` (`case_group`, `phase_runs`), so `just e2e-cases debian13 'replace-*' 'delete-*'`
  runs the setup and these steps only, and `just e2e` runs them too. They run after `ops-polkit` and before `upgrade`; they leave no key
  behind, so `TOTAL`, the journal window and the starting state of upgrade/lifecycle are as before (the builder shows this, as F91/F92 did).
  The builder may put both groups in one guest step if that is simpler, as long as selecting one of them reaches only what it needs.
- The exact case ids (the builder fixes them; each is named `replace-*` or `delete-*` and each Evidence line below is one or more of them).
- Container-free tests of every new shell-level helper and judgement (selection, accounting, a judgement fed bad evidence), like F91's
  and F92's (`scripts/test-e2e-*.sh`, run by `just quick`).
- Fixtures made in the guest with OpenSSL: a key with two certificates (the second one has a different subject, so the old and new
  certificates differ in bytes and in `custodio list`), a `.p12` with the first, and a second, unrelated key and its certificate for the mismatch.

Not built, owned elsewhere: service, CLI or module behaviour (F78, F85, F87, F88 and their tests); polkit asked once, denied or
unavailable for replace and delete (F92); ownership of another uid's id (F91); journal content of these calls (F94); the checkpoints
F90/F100. Proven at the checkpoint only: the cases on the other five targets (`just e2e`, F100). The CLI has no replace command, so
replace is called over D-Bus; delete is made with the CLI (`custodio delete`, on a pseudo-terminal as `e2e/delete.py` does).
The feature is about five steps; no split.

Environment (run in this session): `podman run --rm --privileged --cgroupns=host alpine echo ok` → `ok`; the local `custodio-e2e-*`
images exist. `pkcs11-tool`, `openssl`, the test agent and `owner-call.py` are already used by the setup and the F91/F92 steps.

## Steps
- [ ] Failing container-free tests first: `select.sh` maps `replace-*` and `delete-*` to their groups; `phase_runs` is true only when a
      case of the group is selected; the accounting reports every case exactly once. Add the ids to `e2e/cases.list`.
- [ ] Helpers and their self-test: the snapshot of what a key shows (state directory listing as `snapshot_state`, `custodio list`, the
      certificate bytes the module exposes per token), and the judgements (certificate shown equals the expected DER; the module shows
      no token for an id; exact error name; state equal; a signature verifies against a given certificate's public key), each with
      bad-evidence cases in a self-test that must fail.
- [ ] Guest side, replace: alice imports a key with certificate 1. Replace with certificate 2 (same key) over D-Bus, approving; judge
      the list, the module and a new signature. Then replace with a certificate of the unrelated key; judge the error and that nothing changed.
- [ ] Guest side, delete: alice imports a key, signs once (shows it worked), deletes with `custodio delete` (confirming, agent approving);
      judge list, module, sign, the state directory and re-import. The step deletes whatever it imported at the end.
- [ ] Negative controls (run, shown red, reverted): (a) the judgement of "module shows the new certificate" fed the old certificate;
      (b) the mismatch case replaced by a same-key certificate, so its error check goes red; (c) the delete case skipping the delete, so
      the absent-from-list and file-gone checks go red. Then `just quick` and `just e2e-cases debian13 'replace-*' 'delete-*'` until both pass.

## Evidence
- The cases are in `e2e/cases.list`, reported exactly once each, and the selection reaches only their steps → `scripts/test-e2e-select.sh`
  and the accounting tests (via `just quick`) → pass; a case missing from the guest output fails.
- Same-key certificate replaces the old one → case `replace-same-key` → the replace call returns `ok`; the agent logged exactly one
  `replace-certificate` line; the certificate shown before is certificate 1 and after is certificate 2 (compared as bytes/hash, and
  the two differ), so a no-op replace fails.
- `custodio list` shows the new one → case `replace-list-shows-new` → the `custodio list` output after the replace carries certificate 2's
  subject (and not certificate 1's) for the id, with the id and key type unchanged.
- The PKCS#11 module shows the new one → case `replace-module-shows-new` → `pkcs11-tool --module … --token-label ID --type cert --read-object`
  gives exactly certificate 2's DER (sha256 equal to the fixture), not certificate 1's.
- A signature afterwards verifies with the new certificate → case `replace-sign-verifies` → a signature made with `pkcs11-tool` (agent
  approving, one request) verifies with `openssl dgst -verify` against the public key of the certificate read back from the module
  (certificate 2); the same signature against an unrelated key's public key does not verify (negative control inside the case).
- A certificate for a different key fails with the documented error and changes nothing → case `replace-different-key` → the call gives
  exactly `com.rfirma.Custodio1.Error.CertificateMismatch` (the name in `docs/api.md`), and the snapshot (state directory, list, module
  certificate bytes) taken before equals the one after, so the key still shows certificate 2 and still signs.
- After `custodio delete` the key is absent from list → case `delete-list-absent` → the CLI exits 0 (one polkit request, confirmation
  given), and `custodio list` no longer has the id, while another key of alice's, imported before, is still listed.
- The module shows no token for it → case `delete-module-no-token` → `pkcs11-tool --list-token-slots` and `--token-label ID` find no token
  for the id, while the token of the other key is still there.
- Sign fails with "no such key" → case `delete-sign-no-such-key` → a Sign call over D-Bus gives exactly
  `com.rfirma.Custodio1.Error.NoSuchKey`; it had succeeded before the delete (same call, same id), so the case would fail if the key never existed.
- Its file is gone from the state directory → case `delete-state-file-gone` → the state snapshot after the delete lacks the entries the import
  added (the listing after equals the one taken before the import), and the key's files were present in the snapshot before the delete.
- The id can be imported again → case `delete-reimport` → `custodio import` (or ImportP12) of the same `.p12` under the same id succeeds, the
  id is listed and signs again, and the step ends by deleting it so the state directory equals the one at the start of the step.
- Negative controls → (a) old certificate fed to the module judgement, (b) a same-key certificate in the mismatch case, (c) delete skipped
  → each shown red once, then reverted.
- Whole feature → `just quick && just e2e-cases debian13 'replace-*' 'delete-*'` → exit 0, the accounting lists the `replace-*` and
  `delete-*` cases and no other.
