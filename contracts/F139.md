# F139 — End-to-end cases: injected TPM and credential failures

## Scope
New cases `tpmfail-*` for SPEC acceptance 7, against the real packaged service, CLI and journal in the debian13 container: with a TPM that is present
but fails in an injected way, `custodio import` fails with the documented error, stores nothing, leaves one journal entry, and no key ends up in a
weaker kind. The injection is by the one test seam the shipped binary has (`CUSTODIOD_TEST_SWTPM_TCTI` in the e2e drop-in of `tpm-lib.sh`, `docs/decisions.md`
"the test-only TPM socket variable") and by stopping the credential service. Nothing shipped changes. The per-reason matrix on a private bus (every listed reason,
every other failure, fake polkit) is F117's `storage_choice` and the causes' names are F120's `kind_audit`; this feature proves the same rule once end to end
with the packaged binary, and does not repeat the matrix.

Injections (the builder may add `owner hierarchy has an authValue` → `tpm_owner` if it costs under 5 s; the three below are required). Each is a case id
`tpmfail-<name>`, judged on the same five facts, which are the case's whole outcome:

1. **`tpmfail-device-unopenable`** — the drop-in names a socket path that exists and refuses the connection (a stale socket file with no listener). Expected:
   D-Bus error `TpmFailed`, journal cause `tpm_device` or `tpm_error` (the builder reads which in `crates/custodiod/src/tpm/open.rs` and `docs/audit.md` and
   fixes the one the code gives, it is not left open in the judgement). Must differ from "no TPM" (a missing path), which imports as `encrypted-host`.
2. **`tpmfail-tpm-error`** — a TPM that answers the connection and then fails: a real TPM error response or a connection that breaks in the capability query
   (builder's choice of stub, e.g. a small listener or a filter in front of `swtpm`; no change to `custodio-it` unless it is the cheapest way). Expected: `TpmFailed`,
   journal cause `tpm_error`.
3. **`tpmfail-credentials-down`** — the credential service stopped so the service cannot reach it (stopping `systemd-creds.socket`, runtime masking if that is
   not enough; the first step finds the smallest that makes the Varlink call fail and puts the command and result in `docs/findings/F139.md`; nothing
   under `/usr` or `/lib` is edited). Two sub-settings, one case each, because the container cannot tell them apart in one:
   - `tpmfail-credentials-down-tpm-lacking`: the TPM is present and lacks RSA (filter `alg=0x1`, as in `docs/findings/F134.md`), so the choice is `encrypted-tpm`, which
     needs the credential service. Expected: `CredentialsUnavailable`, cause `credentials_unavailable`. **Limit, stated plainly:** `docs/findings/F134.md` (last
     section) shows the same error comes with the credential service up, because the container's `systemd-creds` never seals to a TPM; so this case alone cannot
     show that the stopped service is the cause. It proves the rule on the real path (no fall-through to `encrypted-host` or `tpm`), the distinction is the next case.
   - `tpmfail-credentials-down-host`: no TPM (missing socket path) so the choice is `encrypted-host`, which also needs the credential service. **Control in the same
     case:** with the service up the same import succeeds with kind `encrypted-host` (the F138 route), with it stopped it fails with `CredentialsUnavailable`
     / `credentials_unavailable`, with it started again it succeeds; so the stopped service is shown to be the cause. This sub-setting has no TPM present; it is
     the cheapest honest control and is covered by SPEC's "credential service unavailable" being independent of the TPM. The person reviewing may judge it; no deviation is
     needed because nothing in SPEC's sentence is unmet by the pair together.

The five facts judged for each injection, from real outputs (the CLI's stderr/exit status, `ListKeys` via `owner-call.py list`, a listing of the state
directory as root, `journalctl`):
- (a) the import exits non-zero and the CLI output names the documented error (not a stack trace, not a success line); the D-Bus error name is read with
  `owner-call.py` (or the CLI's own text if it prints it) and is the one expected above;
- (b) nothing is stored: the state directory (the key records and any temporary file) is identical before and after, and the id is absent from `ListKeys`;
- (c) exactly one journal entry of operation `import` for the attempt (since a cursor taken just before), outcome `storage_failure`, the expected `CUSTODIO_CAUSE`,
  no kind field naming a stored kind, and no secret (the password, the fixture's key bytes) in it;
- (d) no weaker kind: neither the CLI output nor `ListKeys` nor the journal says `encrypted-host` or `encrypted-tpm` for the failed attempt, and a later import
  of the same id with the TPM restored succeeds with kind `tpm` (so the id was not consumed);
- (e) the service keeps answering: after the injection is removed (drop-in restored to the mode's TPM, credential socket started) the service is active and
  `Ping`s, which is also the restore the next scenario starts from.

- **Modes.** The cases replace the drop-in themselves, so what they need from the mode is a TPM to restore to and a package with the drop-in mechanism.
  `swtpm`: all cases run (this is the mode of the `verify`). `none` and `lacking`: all cases are reported skipped (`skip.list`, reasons: no TPM to
  fail / the filter of `lacking` is not what the cases use, the same cases run in `swtpm`). `check-cases.sh` refuses a `tpmfail-*` skip in `swtpm`. Ids are in
  `e2e/targets/debian13/cases.list` (the outcome depends on the TPM, not the distribution; SPEC end-to-end scope), not in `e2e/cases.list`.
- **Placement.** A group `tpmfail` in `select.sh` (before `fallback-*`? the builder places the pattern so no other group captures it), step in `guest.sh` after
  `fallback` and before the upgrade, with its own agent dir and key ids; alice's keys are never stored (each attempt fails) except the control imports and the restore imports of fact (d), which are
  all deleted; the TPM drop-in, the credential socket and the service are restored at the end of the step even if a case fails (a trap), so later steps see
  the mode's TPM and a running credential service. The builder reads the later steps' journal counts and key counts, as F133/F137/F138 did, and notes the result.
- **Not proven here.** Every listed reason's matrix and mutation coverage of the choice (F117), the cause names for each failure (F120), the kind text for
  `encrypted-tpm` end to end (F134 deviation; `storage_kind` in custodio-cli), signing after a cleared TPM (F140 or its neighbour), package gates and `just e2e` (checkpoint).
- **Negative controls.** Host test `scripts/test-e2e-tpmfail.sh` (no container, in the justfile script-test list): the judgement functions (python3 `-I`, as functions of
  files, in `e2e/tpmfail.py`) accept a good record of each injection and reject: exit status 0, a success line in the output, a stored file after the attempt, an id in
  `ListKeys`, zero or two journal entries, a wrong cause, a `Storage:` line with `encrypted-host`/`encrypted-tpm`, a secret in the entry, a missing control (the
  host sub-setting with no success before or after). `check-cases.sh` accepts the skips in `none` and `lacking`, refuses one in `swtpm`; the ids are in the debian13
  list and not in `e2e/cases.list`. A guest control in the run: before the first injection an import with the mode's TPM succeeds with kind `tpm` and is deleted, so the
  failures are not judged against a broken rig.
- **Cost.** Host test: under 5 s, parallel with the other script tests (budget 60 s). Guest, `swtpm` only: each scenario is a drop-in rewrite, `daemon-reload`, a
  service restart (ready = new MainPID, `is-active`, bus `Ping`; no fixed sleep) and one failing import (2–4 s, F133/F134 figures), plus the control imports; the
  scenarios share one service and one drop-in, so they run in sequence by necessity, while the stubs (stale socket, the failing listener, the second filter) are prepared
  once at the start in parallel with `&`/`wait`. Estimate 25–40 s of the phase, no new container. `just e2e-cases debian13 'tpmfail-*'` estimated 55–75 s in `swtpm`
  (F135–F137 runs of this kind: 48–71 s), about 20 s in `none`/`lacking` (skips only). The full debian13 `swtpm` run grows by ~30 s on top of F135 (~20 s), F136 (~22 s)
  and F137 (~23 s) against a budget of 430 s measured at 360 s: **this may not fit**; the builder sums it in `PROGRESS.md` and asks for more in `BLOCKED.md` if a measured
  run passes the budget (that run is the checkpoint's, not this feature's). No `budgets.tsv` change is requested now.
- **Sockets under the sandbox.** The stale socket and the failing listener sit under a path that the rewritten drop-in's `BindReadOnlyPaths=` exposes (as `$TPM_DIR`), else the unit
  sees "missing" (`encrypted-host`) instead of "refused"; facts (a) and (d) catch a mistake. Step 1 records whether stopping `systemd-creds.socket` leaves the socket file (refused) or not (missing).
- **Environment check (done before building, by step 1).** That the credential socket can be stopped and a stale socket path refuses a connection inside the
  container are the first step's smallest commands, with their result in `docs/findings/F139.md`. If the credential socket cannot be stopped in the container, the
  `credentials-down` cases fall to the unit-level proof (F117 `storage_choice`) through a `SPEC_DEVIATIONS.md` entry, with an amended contract, before anything else is built.
- Size: five steps, one session each at most.

## Evidence
- Device present but unopenable fails closed → `tpmfail-device-unopenable` (`just e2e-cases debian13 'tpmfail-*'`) → import exits non-zero with `TpmFailed`, state directory unchanged,
  id absent from `ListKeys`, one `import` entry with `storage_failure` and the cause read from the code, no `encrypted-*` kind anywhere, later import with the TPM restored gives `tpm`.
- A TPM error fails closed → `tpmfail-tpm-error` (same run) → the same five facts with cause `tpm_error`.
- Credential service down fails closed → `tpmfail-credentials-down-tpm-lacking` and `tpmfail-credentials-down-host` (same run) → `CredentialsUnavailable`, nothing stored, one entry with
  `credentials_unavailable`, no other kind; in the host case the import succeeds with the service up before and after, so the stopped service is the cause. The TPM-present
  case alone does not show the cause (F134 finding); the pair does.
- Documented error, nothing stored, one journal entry, no weaker kind → the five facts (a)–(d) in every case above; the journal entry holds no secret → fact (c).
- The rig is not broken and the service recovers → the guest control import with kind `tpm` at the start and fact (e) after each scenario; the trap restores the drop-in, the
  credential socket and the service at the end (the step's last check: `ListKeys` empty of its keys, the unit's TPM equals the mode's per `tpm_observe`).
- Reported as skipped in a mode they do not apply to → `E2E_TPM=none just e2e-cases debian13 'tpmfail-*'` and `E2E_TPM=lacking ...` → all skipped, "accounted for"; host test on
  `check-cases.sh`: skips accepted in `none`/`lacking`, refused in `swtpm`.
- Each judgement can fail → `scripts/test-e2e-tpmfail.sh` → rejects each bad record listed, accepts the good ones.
- Per-reason matrix, mutation coverage of the choice, cause names → F117, F120, not repeated.
- State left as found → end of the step → later steps' key and journal counts unchanged (full run at the checkpoint).
- `just quick` green and the `verify` command → exit 0.
