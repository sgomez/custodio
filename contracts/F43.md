# F43 — Lifecycle scripts of the .deb: install, upgrade, remove, purge

## Scope
The four maintainer scripts of the `.deb` (`preinst`, `postinst`, `prerm`, `postrm`, wired in `packaging/nfpm.yaml`) and the
tests that run them. SPEC design section 2 is the source of the behaviour; Debian's conventions (what `dh_installsysusers` and
`dh_installsystemd` do, not their text) decide the details SPEC leaves open.

Built here:
- Account: dpkg unpacks the bus policy before `postinst` runs, and `dbus-daemon` may load it by itself (inotify), so the account
  is created in `preinst` (`install` and `upgrade`, after the F42 bus check), from sysusers content embedded in the script
  (a pre-unpack script cannot read packaged files), with a sync gate against `data/sysusers.d/custodio.conf` like F42's. If the
  account cannot be created, `preinst` fails non-zero with a message on stderr (no `|| true`); nothing is unpacked then.
- Dependency: dpkg guarantees `Depends` only for `postinst`, and a `preinst install` can run before `systemd` is unpacked when
  both go in one transaction (debootstrap, image builds). So the package that provides `systemd-sysusers` on Debian 13 and
  Ubuntu 26.04 (`systemd`, unless the builder finds it elsewhere) moves to `Pre-Depends` of the deb in `packaging/nfpm.yaml`
  (rpm and Arch lists unchanged). The alternative (a `useradd` fallback) is rejected: it would be a second account definition
  to keep in sync. Recorded in `docs/decisions.md`.
- `postinst`: on `configure`, `daemon-reload`, then reload the bus, then update the journal catalog; the reloads tolerate
  failure (no live systemd in a chroot, F36 decision). The unit
  is never enabled and never started. On upgrade (`configure` with an old version), the service is restarted once, after the
  daemon reload and bus reload, and only if it was running before the upgrade.
- `preinst`: keeps the F42 bus check unchanged (and its sync gate) and, on `upgrade`, records whether the service is running so
  `postinst` can restart it only then. How it is recorded is the builder's choice, with no state under the state directory.
- `prerm`: on `remove` (also the removal half of `purge`), stop the service. On `upgrade` it does not stop it (the restart
  happens once, in `postinst`). Failed-upgrade and deconfigure calls are handled per Debian policy and never touch data.
- `postrm`: on `remove` and `purge`, daemon-reload, reload the bus (the policy file is gone), keep the state directory and the
  account, and print a notice saying where the keys are, and that deleting them by hand destroys them for good. Same behaviour
  for `purge` (SPEC decision), and also for `abort-*`/`disappear` calls without any data change.
- Upgrade from the last cargo-deb `.deb` (only script: the M1 postinst, no preinst/prerm/postrm) is a normal upgrade: the new
  scripts must work when invoked with that package's version as the old version and when the old package's own `prerm`/`postrm`
  do not exist.
- `just test-scripts` gains a test that runs each script on a temporary root with stubbed `systemctl`, `systemd-sysusers`,
  `journalctl` and bus tools, records the calls, and asserts the calls and a populated state directory unchanged.
- The package gates, fixture tests and lint lists that assume "only preinst and postinst" are updated to list the four scripts
  and their content (an amendment of F36/F42, not a weakening).

Not here: rpm scriptlets (F44), the Arch script (F58), the e2e upgrade on real distributions (F45 and
later), `docs/install.md` (F51), any change to the bus policy, polkit action or unit hardening. If the notice text needs a
doc pointer, it names the state directory and the manual command only.

Size: about seven small steps; no split needed.

## Evidence
- Install creates the account from the sysusers file before the bus policy is loaded → real `dpkg -i` in the test root with
  the mechanism named in the test header: a `systemd-sysusers` stub that, when called, records whether
  `/etc/dbus-1/system.d/com.rfirma.Custodio1.conf` already exists in the root (and adds the account to the root's
  `/etc/passwd`) → the record says "absent" and the account is in `/etc/passwd` after unpack. The check is valid only because
  the mutant "account creation moved to `postinst`" makes the record say "present" and fails it; the test runs that mutant.
  Plus the script-level install case logs `systemd-sysusers` before any bus reload. The embedded sysusers content equals
  `data/sysusers.d/custodio.conf` (sync gate; a mutated copy fails).
- Install does daemon-reload, reloads the bus, updates the journal catalog → same case → log contains `systemctl daemon-reload`,
  the bus reload and `journalctl --update-catalog`, each exactly once.
- Install never enables or starts the unit → same case → no `enable`, `start`, `restart`, `preset` call to `systemctl`, `deb-systemd-helper` or
  `deb-systemd-invoke` (all three are stubbed and logged; the last two are not essential, so the scripts should not need them) in
  the log; mutant adding `enable` fails.
- Install never touches the state directory → same case with a populated state directory (and with none present: still not
  created) → tree listing with content hash, owner, mode, mtime of the state directory is identical before and after; no
  command in the log has a path under it as argument.
- Upgrade keeps state directory and account → `upgrade` case (`preinst upgrade`, `postinst configure OLD`) → state tree
  byte-identical with same owner, modes; no `userdel`/`sysusers` removal call; uid of `custodio` unchanged in the stub passwd.
- Upgrade restarts once, after new files and bus policy, only if running → two upgrade cases (stub `is-active` reports active /
  inactive) → active: exactly one `restart custodio.service` (or equivalent) after daemon-reload and bus reload; inactive: no
  restart, no start (the stub models `is-active` and `try-restart` with state, so a correct `try-restart` implementation passes); a mutant that restarts unconditionally or before the bus reload fails.
  Third case: `postinst configure OLD` without the marker `preinst upgrade` would have written (upgrade from the cargo-deb
  package, or a `preinst` that failed half-way), with the stub reporting active → no restart, no start, exit 0.
- Upgrade does not stop the service in `prerm` → `prerm upgrade NEW` case → no `stop` call.
- Every action path the header lists is run → one stub case each for `prerm failed-upgrade`, `prerm deconfigure`,
  `postrm abort-install`, `postrm abort-upgrade`, `postrm failed-upgrade`, `postrm disappear` (and `prerm remove` / `postrm
  remove|purge` above), each with its expected call list written in the header (for example `deconfigure`: no stop; `abort-*`:
  no state or account change and no `enable`/`start`) → the log equals the expected list, exit 0, state tree identical.
- Remove stops the service, keeps state and account, prints the notice → `remove` case → log has the stop; state tree
  identical; no account-removal call; the notice is on the stream the header names (stdout or stderr; the test captures them
  separately and asserts it appears on that one) and names the state directory path and the "deleting them by hand destroys
  them" message; mutant deleting the directory fails.
- Purge behaves as remove → `purge` case (`prerm remove`, `postrm remove`, `postrm purge`) → same assertions as remove,
  state tree identical, notice printed; no `rm`, `chown`, `chmod`, `cp`, `cat` call on the state path in the log.
- No script deletes, chowns, chmods, reads, copies or prints anything under the state directory → static gate in
  `test-scripts` greps the four scripts for the state path (`/var/lib/custodio`, `StateDirectory`) and allows only the notice
  text and an allowlist that names each permitted line (file and exact text) with a reason, not a pattern; plus the runtime logs above (stubs for `rm chown chmod cp cat` fail the test when called with
  that path).
- Scripts do not widen bus policy, polkit action or unit hardening → grep gate: the scripts never write, sed, cp or install
  onto the bus policy, polkit action or unit paths; the existing unit-hardening, bus-policy and polkit gates in `check` still pass.
- The state checks reach the real tree → stub cases run inside the root (user namespace or chroot, as `bf_in_root` does) or the
  scripts honour a root variable; a control test with a deliberately bad script (`rm -rf /var/lib/custodio`, or a redirection
  into it) must make the tree comparison fail, proving the check sees the path the scripts use.
- Upgrade from the last cargo-deb .deb is a normal upgrade → real `dpkg -i` of a fixture old package (only M1 postinst) then of
  the built `.deb`, populated state directory → dpkg exits 0, state tree identical, new files present, scripts ran without
  error although the old package had no prerm/postrm; also the script-level case with an old-version argument.
- Real remove and purge with dpkg → `dpkg -r`, `dpkg -P` on the built `.deb` → exit 0, packaged files gone, state directory
  and account still there, tree identical, notice printed, and the service is not left running afterwards (checked via the
  stub's state after `postrm`, covering reactivation between stop and reload where the stub can model it).
- Scripts behave on hostile or odd inputs → cases with stubs failing (`systemctl` non-zero, no systemd running as in a chroot)
  → scripts still exit 0 on the paths where Debian tolerates it (as the M1 `|| true`); a `systemd-sysusers` stub that exits
  non-zero makes `preinst` exit non-zero with a stderr message, and putting `|| true` back (mutant) fails the test; only the
  reloads in `postinst`/`postrm` tolerate failure. `preinst install` with no `systemd-sysusers` on `PATH` is a separate case:
  with `Pre-Depends` this cannot happen under dpkg, so the script exits non-zero with a clear stderr message naming the
  missing tool (it must not silently skip account creation), and the case asserts that and that nothing was created.
- Package contents and lint → `just package && just package-lint` → the `.deb` contains all four scripts in the control
  archive with mode 0755, `check-packages` lists them, lintian shows no new finding outside the list with reasons.
- Whole feature → `just check && just test-scripts && just package && just package-lint` → all pass.
- Dependency checks (F42 stays correct) → `test-bus-check*.sh`, `check-bus-check-sync.sh` → still pass unchanged.
- Sync gate placement → the check that the embedded sysusers content equals `data/sysusers.d/custodio.conf` runs from `check`
  (next to `check-bus-check-sync`); a test with a mutated copy must fail it.
- Upgrade over the M1 account → script-level case where the stub passwd already has `custodio` → `preinst upgrade` exits 0, uid
  unchanged, no second creation error.
- `systemd-sysusers` available when `preinst` runs → built `.deb` control file (`dpkg-deb -f` in `package-lint` or
  `check-packages`) → `Pre-Depends` contains `systemd` and `Depends` still holds the other entries; a fixture with `systemd`
  only in `Depends` fails the check; `docs/decisions.md` records the choice and the rejected fallback.
- Test hygiene → the account-before-unpack assertion is one concrete mechanism named in the test header; the state-path grep
  allowlist lives in the test file with a reason per entry; the test header states what the stubs cannot cover (a real systemd),
  left to F45.
