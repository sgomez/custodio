# F129 — PCR, restart and TPM-clear checks

## Scope
The integration target `tpm_lifecycle` in `custodiod` (`crates/custodiod/tests/tpm_lifecycle.rs`, reusing the
`sign_kinds`/`storage_choice`/`kinds_suite` rigs through `#[path]`: private bus, fake polkit approving, real `swtpm`,
the journal sink). One service imports four keys through the bus: kind `tpm` (RSA 2048 and P-256) and kind
`encrypted-tpm` (RSA 2048 and P-256; credentials made by the **real** `systemd-creds` bound to the `swtpm`, as
`sign_kinds/real.rs` does, not the in-memory fake). Then, in one story:

1. Every key signs (baseline, verified with its certificate by an independent implementation).
2. PCR 7 and other PCRs (the builder picks at least 0, 2, 4 and 7, and one in the 16–23 range) are extended in
   `swtpm`; every key still signs.
3. `swtpm` is restarted (state kept, PCRs reset to their start values) and the service is stopped and started again on the
   same state directory (a new service object and bus name owner); the keys are still listed with the same ids, kinds
   and certificates, and every key still signs.
4. The TPM is cleared; signing with each key fails with the documented error (`KeyLost`, `docs/api.md`) and leaves a
   journal entry with the documented outcome (`key_lost`, `docs/audit.md`); the keys are still listed; each is deleted.

Left for other features: single-failure rows for a cleared TPM, a changed host key, a damaged blob and the other
transient failures (F118 `sign_kinds`, F120 `kind_audit`); duplication (F128); the kind `encrypted-host`, which has no
TPM and so no PCR or clear (F126, F118); the real `fwupd`/`dbx` run and the upgrade from one M4 build to the next
(checkpoints); `systemd-creds` under the real unit (F147). No mutants (`verify` has none).

Environment check (dev container): `systemd-creds --version` → `systemd 257 (257.13-1~deb13u1)`; `swtpm`, `tpm2-tools`
under `/usr/bin`. `custodio_it::swtpm::Swtpm` already has `extend_pcr`, `restart` (same state, TCTI string unchanged)
and `clear`; `sign_kinds` already runs real `systemd-creds` on `swtpm`. If the service cannot be restarted on an existing
state directory with the current `Svc`, a start-on-existing-state variant is part of step 2.
Size: five steps, no split.

## Steps
- [ ] Tests first: `tpm_lifecycle.rs` with the cases below and the helper that builds the four-key store (failing until wired).
- [ ] Wire the setup: one `swtpm`, real `systemd-creds`, four imports; a way to stop the service and start a new one on the
      same state directory, sink and polkit, keeping the key files.
- [ ] PCR and restart cases (baseline, extend, restart `swtpm` and service, sign, list).
- [ ] TPM-clear cases (sign fails with the documented error and entry, list unchanged, files untouched, delete).
- [ ] Negative controls, then `just quick` and the evidence command.

## Evidence
- Four keys of two kinds are imported → `tpm_lifecycle::imports_four_keys` → the import results and `ListKeys` show
  exactly four ids, kinds `tpm` ×2 and `encrypted-tpm` ×2, RSA and P-256 in each; the state has exactly four key files;
  baseline: every key signs and the signature verifies with its certificate (independent `openssl`). A
  store of three, or an `encrypted-tpm` key made by the fake creds, fails the test (the test checks the credential header
  is that of a real `systemd-creds` TPM credential, with an empty PCR mask).
- Extending PCRs changes nothing → `tpm_lifecycle::signs_after_pcr_extension` → `tpm2_pcrread` shows each extended PCR
  (including 7) different from its value before; then every key signs and verifies with its certificate, with one polkit
  request per signature. Negative control: a credential made by the real `systemd-creds` with `--tpm2-pcrs=7` before the
  extension is rejected for decryption after it, so the test's PCR change is one that would break a PCR-bound key.
- Restart keeps every key → `tpm_lifecycle::signs_after_restarts` → after `Swtpm::restart` the PCRs read as their reset
  values (not the extended ones), after the service is stopped and started again on the same state directory the new
  service (different bus name owner / fresh counters) lists the same four ids, kinds and certificates, and every key signs
  and verifies, calling polkit once per signature (no authorization carried over from before the restart). Negative control:
  the same sequence with the state directory of the service replaced by an empty one lists nothing and fails
  `NoSuchKey` on signing, so "still signs" is not satisfied by an unrelated store.
- Clear: sign fails, documented → `tpm_lifecycle::cleared_tpm_sign_fails_documented` → after `Swtpm::clear`, for each of
  the four keys, `Sign` returns the D-Bus error `com.rfirma.Custodio1.Error.KeyLost` with the message documented in
  `docs/api.md`, taken from the document by the test (not retyped); there is exactly one new journal entry per attempt,
  with outcome `key_lost`, the key's kind and owner, and the documented fields of `docs/audit.md`, and none of the key
  bytes, password or credential bytes. Control: the same four signs, in the same order, immediately before the clear
  succeed with no `key_lost` entry.
- Clear: still listed, unchanged → `tpm_lifecycle::cleared_keys_stay_listed` → `ListKeys` after the failed signs, and
  after a further service restart, returns the same ids, kinds and certificates as before the clear; the key files are
  byte-identical to those before the clear; no key was deleted, re-stored or turned into another kind (no fallback).
- Clear: can be deleted → `tpm_lifecycle::cleared_keys_can_be_deleted` → `DeleteKey` succeeds for each of the four keys,
  `ListKeys` is empty, the key files are gone, each delete leaves its journal entry; a sign on a deleted id fails
  `NoSuchKey`, not `KeyLost`, so the earlier `KeyLost` came from the stored key.
