# F136 — End-to-end cases: TPM keys cannot be duplicated

## Scope
New cases `tpm-dup-*` for SPEC acceptance 4, run against the real service in the debian13 container. For each key the service stored
with kind `tpm` (an RSA 2048 and a P-256 `.p12` imported by alice), as root with `tpm2-tools` on the **stored record** found in the
service's real state directory (`/var/lib/private/custodio/<uid>/<id>`, as F135's finding says):
the public area shows an empty `authPolicy`; `tpm2_duplicate` on the loaded key fails; the blob does not load in a second, independent
`swtpm`. What the guest has to do is the builder's: take the public and private areas out of the record (layout in
`crates/custodiod/src/store/record.rs`: header, id, certificate, then the parent name and `Blob`), recreate the parent on the service's
swtpm with the template of `SRK_ATTRS` (`docs/findings/F113.md`), check that the parent's name equals the one stored in the record (so the
load is under the right parent, not an accident), and load.

- **Already proven elsewhere, not repeated.** The same three properties on blobs the service stores, through the bus with `swtpm` and
  a fake polkit, are F128's (`cargo test -p custodiod --test tpm_duplicate`, part of `just quick`), including the exact `TPM_RC_POLICY_FAIL`
  and `integrity` errors and the duplicable control key. Here only the real daemon, real storage and the real installed package are
  added; the error codes are asserted as F128 does (policy failure for the duplicate, integrity for the second TPM), not re-derived.
  The no-PCR dependency (F137), signing (F134), kinds (F133) and the manual hardware run (acceptance 13) are not here. Reboot, upgrade and
  package gates are proven at the checkpoint.
- **Modes.** `swtpm`: both keys are `tpm`; the cases run. `lacking`: both keys are `tpm` too (the F131 filter, deviation in
  `SPEC_DEVIATIONS.md` F134; no change needed for this feature, it adds no `encrypted-tpm` claim), so the cases run; the guest talks to the real
  swtpm directly (the filter's upstream socket, or the filter's, builder's choice). `none`: no key is `tpm`; the cases are reported skipped
  (`skip.list` with a reason, as the `tpm-kind-*` cases). The case reads `ListKeys` for its keys and expects the mode's kind exactly: a `tpm`
  key under `swtpm`/`lacking` (a wrong kind fails, the run is not vacuous). `encrypted-tpm` keys have no TPM blob, so the check is not defined for
  them; "for each TPM key" is each key of kind `tpm` in the state directory, and the guest enumerates the records it finds with kind tag `tpm`
  and fails if it finds fewer than the two it imported.
- **Cases** (each reported exactly once; the builder may add one; every id matches `tpm-dup-*`): `tpm-dup-authpolicy-empty` (for each key the
  public area, read with `tpm2_readpublic` on the loaded key, has no `authorization policy`; tpm2-tools leaves the line out when empty, so the
  judgement also checks that the output is a key's output: name and attributes present), `tpm-dup-duplicate-fails` (`tpm2_duplicate` under a
  policy session on `TPM2_CC_Duplicate` fails for each key), `tpm-dup-other-tpm` (`tpm2_load` of the same public and private areas under the
  second swtpm's parent fails with an integrity error, for each key).
- **Placement.** Ids in `e2e/targets/debian13/cases.list` (their outcome depends on the TPM), not in `e2e/cases.list`; skip entries for
  `none` in `e2e/targets/debian13/skip.list`; `check-cases.sh` rejects a `tpm-dup-*` skip in `swtpm` and in `lacking` (the F133/F134 pattern).
  `select.sh` gets a group `tpmdup`, run after the `noplain` step with keys of its own, deleted at the end, so counts and state seen by other
  steps are unchanged. The judging code is python3 `-I` functions of files, with a self-test, like `noplain.py`.
- **Negative controls.**
  - Guest (same cases, no extra case): on the first TPM a key made by `tpm2_create` **with** a duplicate-allowing policy/attributes (as F128's
    `made_key(duplicable)`) is duplicated by the same invocation the cases use, so a failure of the stored keys is the key's and not the
    invocation's; and the stored blob **does** load under the service's own parent on the first swtpm (the "second TPM refuses" result is not
    a broken load command). Both must hold or the case fails.
  - Host (`scripts/test-e2e-tpmdup.sh`, no container, in the justfile script-test list): the judgements reject evidence with a non-empty
    `authorization policy`, a `tpm2_duplicate` that succeeded, a second-TPM load that succeeded or that failed for another reason than integrity
    (a bad path, a wrong parent template), a parent name that differs from the stored one, a record that is not kind `tpm`, and fewer than
    two TPM records; they accept the matching good evidence. The record extraction is tested on a record written by the real code path
    (built with the `Record` encoder through a small `custodiod` test helper or on the fixtures F128/F135 use; the builder decides) so the
    guest's reading of the layout cannot drift from `record.rs`.
- **Environment.** `tpm2-tools`, `swtpm` and `swtpm_setup` are in the debian13 image (`Containerfile`) and the service's swtpm already runs in
  all modes (`docs/findings/F131.md`). Step 1 shows with one run that root in the guest can read the record file and open the service's swtpm
  socket with `tpm2-tools`, and that a **second swtpm** (own state directory under `/var/tmp`, own socket under `/tmp`, as `tpm-lib.sh` does for the
  first) starts. It must be stopped before the guest's `tpm_teardown`, whose wait is on "no swtpm process" (`tpm_swtpm_stop`). If it cannot run
  there, the case is rewritten before anything else is built (a person's run or a deviation, with the command and its result in the finding).
- **Cost.** Host test `scripts/test-e2e-tpmdup.sh`: under 5 s, runs in parallel with the other script tests (default budget 60 s). Guest:
  two imports as alice (2–4 s each, as F134/F135), a second swtpm start (`swtpm_setup` ~1–2 s), per key a `createprimary` and a load or duplicate (tpm2-tools
  calls ~0.1–0.3 s each, about 30 calls), estimated 8–15 s per mode on top of shared setup, no new container. The two keys, and the three checks
  per key, run at once (background jobs joined with `wait`, own context files); the parent creation on the second swtpm runs while the
  imports run. Waits are on the sockets and the agent's `registered` line, never a fixed `sleep`. Each `just e2e-cases debian13 'tpm-dup-*'`
  is estimated 1–2 min (F135's whole run was 42–61 s); the verify's single run is `swtpm`, the `lacking` and `none` runs are the builder's separate
  commands. The full debian13 `swtpm` run (budget 430 s, measured 360 s, plus F135's ~20 s) grows by another ~10–15 s; if the measured full run
  passes the budget the builder asks in BLOCKED.md. No `budgets.tsv` change expected.
- Size: five steps, one session each at most.

## Evidence
- Empty `authPolicy` of each stored TPM key → `tpm-dup-authpolicy-empty` (`just e2e-cases debian13 'tpm-dup-*'` in `swtpm`, and `E2E_TPM=lacking`) →
  `tpm2_readpublic` on the key loaded from the real state-directory record shows no `authorization policy` for the RSA and the P-256 key; the
  case log names the kind found and the parent name equal to the stored one.
- `tpm2_duplicate` on the loaded key fails → `tpm-dup-duplicate-fails` (same runs) → non-zero exit with the policy-failure response for both keys.
- The invocation can succeed, so the failure is the key's → guest control in the same cases → the same `tpm2_duplicate` on a duplicable key made on
  that swtpm exits 0; if it does not, the case fails.
- The blob does not load in a second swtpm → `tpm-dup-other-tpm` (same runs) → `tpm2_load` under the second swtpm's parent fails with an
  integrity error for both keys; control: the same load on the first swtpm under its parent succeeds, and the second swtpm is a different TPM
  (different parent name).
- Each judgement can fail → `scripts/test-e2e-tpmdup.sh` (host) → rejects each bad evidence listed above and accepts the good; record reading
  agrees with a record produced by the real encoder.
- For each TPM key, not two chosen ones → the guest enumerates the `tpm` records in the state directory → fails with fewer than the two imported;
  the host test covers the count.
- Skipped where it does not apply → `E2E_TPM=none just e2e-cases debian13 'tpm-dup-*'` → 3 cases reported skipped and accounted for with the
  `skip.list` reasons; host test: `check-cases.sh` accepts the `none` skip and rejects a `tpm-dup-*` skip in `swtpm` and in `lacking`; ids are in the
  debian13 list and not in `e2e/cases.list`.
- State left as found, nothing left running → the cases' deletes and the second swtpm's stop → both keys absent from `ListKeys`; no extra `swtpm`
  process after the step (the guest's own teardown already waits for it); later steps in the same run still pass (full run at the checkpoint).
- Properties on the service's stored blobs through the bus → F128 (`tpm_duplicate`), not repeated; acceptance 13 on hardware → F-manual, not here.
- `just quick` green and the `verify` command → exit 0.
