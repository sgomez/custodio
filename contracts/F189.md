# F189 — Research: why the storage classifier answers unknown, then not-encrypted, for device 252:0

## Scope
Research only. Output: `docs/findings/F189.md` (headed `## F189`, within the 5000-token limit, rules of
`docs/findings/F180.md` and the top of `docs/findings.md`) and one index line in `docs/findings.md`
(`- [F189](findings/F189.md) — ...`). No product code, no test, no `contracts` change elsewhere.
F196 builds whatever the `Decision:` says; this feature does not.

What the finding must settle: why `crates/custodiod/src/storage.rs` gives `unknown` at one start and
`not-encrypted` at a later one for an LVM volume (`252:0`) on an unencrypted partition. The code paths
that can return `unknown` for that chain, and so the candidate causes to confirm or rule out one by one:
- `mounted_device`: the mount of the state directory absent from `/proc/self/mountinfo`, or a
  different mount (for example the DynamicUser bind or a tmpfs) taking the longest prefix.
- `walk_node` on the `dm` node: `dm/uuid` empty or unreadable, or a prefix other than `LVM-`.
- `members`: `slaves/` empty or incomplete at that moment (no member gives `None` → `unknown`), or
  members that disagree.
- The partition → disk step: the disk's `device` link or `dev` file absent, or `slaves` non-empty.
- The `statx` fscrypt check failing.
- The unit's sandbox (`ProcSubset`, `ProtectKernelTunables`, `PrivateDevices`) hiding a file at start
  that is readable later; and ordering (`After=` in `data/custodio.service`) against udev/LVM
  activation.

Environment (checked while writing this contract): the dev container is uid 1000, no passwordless
`sudo`, no `/dev/mapper`, no `dmsetup`; `losetup` exists. `/sys/dev/block/252:0` exists, with
`dm/uuid` `LVM-...` and `slaves` = `nvme0n1p2`. So a live LVM volume can be *read* here but not
*created*. The builder's first step runs the smallest command that shows whether a dm device can be
created (`dmsetup`, or `sudo -n`); if it cannot, the reproduction is on a fixture sysfs/mountinfo tree
fed to `classify` (an existing way to run the real code, see `crates/custodiod/tests/state_storage*`),
with the real `252:0` entries copied as the reference shape, and every claim about the *start-time*
state is marked **inferred** unless a source (kernel `drivers/md/dm-sysfs.c`/`dm-ioctl.c`, lvm2/udev rules
`69-dm-lvm.rules`, systemd's unit/udev ordering) or a command run shows it. The research may use
subagents for kernel, lvm2 and systemd sources and returns conclusions.

Routes for `Decision:` (one line, starting `Decision: `): (1) fix so that the same storage gets the
same answer at every start, and whether a unit setting is needed and why it does not weaken the unit
(`systemd-analyze security` score or the specific directive named); or (2) keep `unknown` and say what
reason the service can expose (a short enumerated reason per unknown cause, read-only, bus only, under
the API compatibility rule). If neither is possible, the builder writes `BLOCKED.md` (SPEC open
question), commits and stops. Any F180 rule shown wrong is corrected in `docs/findings/F180.md` and
its index line, and F189 says so; otherwise F189 says F180's rules stand.

Cost: no test or suite is added; `just quick` (which runs `scripts/check-files.sh`) is the only run, at
its usual cost. Nothing goes in `e2e/`. Acceptance 14 (service and `doctor` parts) is proven by F196 and
F203, not here.

## Steps
- [ ] Run the smallest command showing whether the container can create a dm/LVM device; record the
      result; read the real `252:0` sysfs entries (`dm/uuid`, `slaves`, partition and disk links) and
      `/proc/self/mountinfo`.
- [ ] Trace every `unknown` return of `storage.rs` for an LVM-on-partition chain and list which could
      differ between two starts; reproduce each candidate on a fixture tree through `classify` (a
      scratch run, no committed test) and note which give `unknown` and which `not-encrypted`.
- [ ] Research outside material with subagents (when sysfs `slaves`/`dm/uuid` appear relative to
      `dm` creation and udev; LVM activation ordering; sandbox directives effect on `/sys` and
      `/proc` reads at start) and decide which candidate is the cause, marking each statement
      **verified** or **inferred**.
- [ ] Write `docs/findings/F189.md` (`## F189`, conclusion first, evidence, the `Decision: ` line,
      F180 corrections or "F180 rules stand") and add the `docs/findings.md` index line; add a
      unit-setting statement if the decision needs one.
- [ ] Run `just quick`; run the feature's `verify`; if neither route is possible write `BLOCKED.md`
      instead.
