# F159 — VM launcher with its TPM modes: QEMU with KVM, OVMF, tpm-crb and swtpm, full and lacking

## Scope
Built:
- `e2e/vm/vm.sh`: boots the image `e2e/vm/image.sh` (F158) verified, as a fresh qcow2 overlay, under QEMU with KVM, OVMF code
  plus a per-run copy of the vars file, and a `tpm-crb` device backed by an `swtpm` on the host. Boot command line, seed and
  channel follow `docs/findings/F151.md` (serial console on a unix socket, `cloud-localds` NoCloud seed, user networking
  with no port forward). The `swtpm` state directory is created fresh for each run, is never one the caller supplies, and is
  reused by every power cycle of that run. Operations: start (with the mode), wait for boot, run a command (output and exit
  code), copy a file in and out, power cycle (QEMU restarted, same `swtpm` state, same vars copy), shut down. It installs
  nothing in the guest and changes nothing in the product: the seed holds the account and password of F151 only, no unit
  drop-in, no `CUSTODIOD_*` variable. The calling interface (arguments, or a command per operation) is the builder's choice,
  documented in the script header, because F160 and later features call it.
- Refusal without a usable `/dev/kvm` (missing, or not openable read-write, or QEMU not offering the `kvm` accelerator), with
  nothing started and no fallback to software emulation of any kind (no option, variable or default selects it).
- Cleanup of QEMU, `swtpm` and every temporary file (overlay, vars copy, seed, sockets, logs) on every exit: success, failed
  command, boot timeout, QEMU or `swtpm` failing to start, `SIGINT`/`SIGTERM`. `swtpm` is started only right before QEMU,
  after every check that can refuse (F151: an `swtpm` without a QEMU stays idle and the tool sandbox cannot kill it). Two
  launches at once do not collide (per-run directories; socket paths are short enough for the 108-byte limit, or the launcher
  refuses clearly before starting anything).
- Modes. `full` and `lacking` are the only values; anything else, empty or missing is refused before anything starts.
  `lacking` uses F152's route 2: an `swtpm` 0.10.2 custom profile whose `Commands` are the default list minus `0x159`
  (`TPM2_RSA_Decrypt`), the profile file kept in the repository under `e2e/vm/`. It never uses `ecc-min-size=384`, never
  `rsa-min-size=3072` and never removes `0x15d` or any algorithm: P-256 stays available and keeps kind `tpm` (RSA only; F161 may
  ask for more). Both modes run the same `swtpm` executable, the same seed and the same QEMU arguments; `full` has no profile, so
  the difference between modes is the profile and nothing else. `lacking` refuses to start (before anything starts) when that
  `swtpm` cannot take a profile (version below 0.10 or no `--profile`) or the profile file is missing or empty.
- Dev container: the dev container has `swtpm` 0.7.1 (no `--profile`) and `/dev/kvm` is present (`ls -l /dev/kvm` →
  `crw-rw----+ ... 10, 232`; `curl -sI https://deb.debian.org/debian/pool/main/s/swtpm/swtpm_0.10.2-2_amd64.deb` →
  `HTTP/2 200`, both checked this session). So F152's route needs a tool the container lacks: step 1 adds the four `.deb` files
  of F152 (sha256 pinned there) to `harness/Containerfile`, in the last layer so earlier cached layers stay valid, and
  `scripts/vm-host-check.sh` learns to report an `swtpm` that can take a profile. The builder chooses between installing over
  0.7.1 and a separate prefix the launcher uses; it prefers the separate prefix unless it runs the existing `swtpm` users
  (`scripts/test-with-swtpm.sh` and whatever else `grep -rn swtpm justfile scripts` shows) with 0.10.2 and they pass, and
  records the choice in `docs/decisions.md` only if a later session could undo it unknowingly. The last step writes `BLOCKED.md`
  for the rebuild, as F150 did. Nothing here needs the rebuild to pass `verify` (the self-tests use stubs).
- `scripts/test-vm-launch.sh` and `scripts/test-vm-modes.sh`, both in `just test-scripts`. Their stubs: `qemu-system-x86_64`
  records its arguments and the pid, answers `-accel help`, and serves a fake guest on the `-serial unix:` socket (a small
  Python script, run with `-I`, that logs in and runs the typed lines in a local shell with the sentinel protocol, so the
  launcher's real driving code runs); on `poweroff` or `SIGTERM` it exits. `swtpm` stub records its arguments, version,
  pid and state-directory contents, writes a marker file into the state directory, and exits when its peer goes. Real
  `qemu-img`, `cloud-localds` and `bsdtar` (both in the container) make and read the overlay and the seed.
  A negative control is a copy of the launcher with the one behaviour removed (shown to differ from the original with `cmp`);
  the same check run on the copy must fail.

Not built: the real boot, the real `swtpm` profile in a guest and the real channel in a guest run at the checkpoint (F151
and F152 are the evidence that the command lines work); the case list, install of the package and the run record (F160);
the case that reads credentials (F161+); the CI job and the KVM setup of the runner (F164); image download (F158, only
called). No software emulation, ever.

Cost (estimates from `scripts/test-vm-image.sh`, 1–2 s, and `scripts/test-vm-host-check.sh`, a few seconds; none measured yet):
- `scripts/test-vm-launch.sh`: about 15 launcher runs on stubs, each under 1 s because the fake guest answers at once and
  waits are on a condition (socket present, login seen), never `sleep`. Independent runs (good, refusals, failures, signals,
  controls) are started together and checked after `wait`. Estimated 5–10 s, no network, no VM, parallel with the other script
  tests under the `script *` budget (120 s); no new budget.
- `scripts/test-vm-modes.sh`: about 12 short runs, estimated 3–6 s, same rules.
- A real boot (about 30 s to the login prompt per F151) is not in `verify`; step 6 does it once by hand and records it.
- The Containerfile gain is a one-off image build (four downloads, about 3 MB), not a per-run cost.
- Every step fits one session; the feature is about five steps, no split.

## Evidence
- Boots the verified image as an overlay, never touching it → `test-vm-launch.sh` "good": the overlay's `qemu-img info` names
  the image as its backing file, the image's `sha256sum` is the same before and after the run, and the launcher fails (nothing
  started) when `image.sh` is pointed at a failing script. Negative control: copy using the image itself as the disk → fails.
- KVM, OVMF, per-run vars → "good" command line: acceleration is `kvm` with `-cpu host`, no `tcg` anywhere in it; OVMF code is
  `readonly` pflash and vars a second pflash; the vars file is a different file in two runs, equal to the template at start
  (`cmp`), the template unchanged after a run in which the stub modified the copy. Controls: copy without `kvm`; copy using
  the template directly.
- `tpm-crb` backed by `swtpm` → "good": the QEMU arguments hold `-device tpm-crb`, an `emulator` tpmdev whose socket is the
  one the `swtpm` stub was told to listen on, and the `swtpm` is `--tpm2`. Control: copy with `tpm-tis` fails.
- `swtpm` state fresh for each run and kept across a power cycle → the stub writes a marker into its state directory: after
  a power cycle the second `swtpm` gets the same directory and sees the marker; a second run gets a different, empty
  directory; a state directory supplied by the caller (non-empty) is refused. Controls: copy that makes a new directory per
  power cycle fails the first check; copy that reuses the previous run's directory fails the second.
- Seed → "good": the seed image read back with `bsdtar` has volume id `cidata`, `user-data` starting `#cloud-config` with the
  F151 account and password, SSH password login off, and `meta-data` with an instance id and a hostname; it holds no
  `CUSTODIOD_` text and no systemd unit; the QEMU arguments have no `hostfwd` and no other network device than user
  networking. Control: copy that omits the password fails.
- Drives the guest → fake guest: a command's stdout and exit code come back (0, 3, and 127 for a missing command); multi-line
  output and output containing the text `__RC=` keep their exact bytes; a command that hangs ends at the caller's timeout with
  a non-zero exit; copy in and out of a file holding all 256 byte values, no final newline, and 3 MB of random data is
  byte-exact (`cmp`); wait for boot succeeds when the login appears and fails at its timeout when the fake guest never shows
  one, within the timeout plus one second (no fixed sleep); power cycle leaves a guest that answers again and a QEMU with a
  new pid; shutdown ends QEMU and `swtpm`. Controls: copy that drops the exit code; copy that strips the last byte on copy.
  The real guest is proven at the checkpoint.
- Refuses without a usable KVM → missing device, a device path that cannot be opened read-write (a directory), and a QEMU stub
  whose `-accel help` lacks `kvm`: each exits non-zero, the message names KVM, neither stub was started (no pid file, no
  argument log), no temporary file remains, and setting `QEMU_ACCEL=tcg`, `ACCEL=tcg` or a `--accel` argument changes nothing.
  Control: copy without the check starts the stubs and the test fails.
- Cleans up whatever the outcome → after each of: normal shutdown; a failing command; boot timeout; the QEMU stub exiting at
  once; the `swtpm` stub refusing to start; `SIGINT` and `SIGTERM` during boot; the recorded stub pids are gone and the
  temporary directory (`TMPDIR` pointed at an empty test directory) is empty again. In the `swtpm`-fails case no QEMU was
  started, and in the QEMU-fails case the `swtpm` that was started is gone. Control: copy without the trap leaves stubs and
  files behind.
- Two launches at once and long paths → `test-vm-launch.sh`: two launches in parallel get different directories and sockets and
  both succeed; with `TMPDIR` of over 100 characters the launcher works or refuses before starting anything with a message
  naming the path length.
- Modes accepted and refused → `test-vm-modes.sh`: `full` and `lacking` start; `partial`, `FULL`, an empty string, `full
  lacking`, `--mode` and no mode at all each exit non-zero before either stub starts, leave nothing, and name the allowed
  values. Control: copy that treats a missing mode as `full` fails.
- `full` adds nothing → the recorded `swtpm` arguments of `full` have no `--profile` and no profile file is created; the
  QEMU and `swtpm` arguments, with the per-run paths replaced by fixed words, equal an exact list written in the test.
  Control: copy that always passes the profile fails.
- `lacking` arguments → the `swtpm` stub gets `--profile` with a file; its `Commands` equal F152's default list
  (`0x11f-0x122,0x124-0x12e,0x130-0x140,0x142-0x159,0x15b-0x15e,0x160-0x165,0x167-0x174,0x176-0x178,0x17a-0x193,0x197,0x199-0x19c`)
  minus `0x159` exactly (both differences computed by the test as sets); `Algorithms` still hold `rsa` and `ecc-nist-p256`;
  no `ecc-min-size=384`, no `rsa-min-size=3072`; `0x15d` is present. The normalized QEMU and `swtpm` arguments of the two modes
  differ only by the profile argument, the seed `user-data` of the two modes is byte-identical, and both used the same `swtpm`
  executable (so the TPM changes for every guest process, never the service alone). Controls: copy whose profile also
  drops `0x15d`; copy whose profile keeps `0x159`; copy using another `swtpm` in `lacking` only.
- `lacking` cannot start without its route → an `swtpm` stub of 0.7.1 (`--version`), one without `--profile` in its help,
  a missing profile file and an empty one: each exits non-zero before any stub starts with a message naming the `swtpm` version
  or the profile; `full` with the 0.7.1 stub still starts. Control: copy without the version check starts `lacking` on 0.7.1.
- Container tooling → `scripts/test-vm-host-check.sh` (extended; it runs in `just test-scripts`, which `verify` does **not** call, so the
  evaluator runs it as listed evidence): an `swtpm` stub without `--profile` gives a MISSING line and exit 1, one with it gives OK;
  control as the script's other cases. The Containerfile lists the four packages with the pinned sha256 values of F152 (checked by
  the builder against `docs/findings/F152.md`); the protection is that the Containerfile runs `sha256sum -c` on those four values
  before it unpacks them, so a wrong hash fails the rebuild. The rebuild itself is the person's (`BLOCKED.md`).
- Real boot → step 6 only, recorded in PROGRESS; the checkpoint (F160 onwards) is where `full` and `lacking` run for real.
