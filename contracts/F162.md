# F162 — VM cases: every mechanism signs with encrypted-tpm keys, RSA-PSS included, and no plaintext key

## Scope
Built (acceptance 6 and 7; Design 1 "Cases"):
- **`sign-*` in a VM.** The eight ids are already in `e2e/vm/cases.list` (F160). Here `sign-run.sh` / `sign.py` become mode-aware for a VM run
  (`E2E_VM=1`; `full` = guest `E2E_TPM=swtpm`): in `lacking` both keys (RSA 2048 and P-256; F161 moved P-256 to `encrypted-tpm` too) get
  `encrypted-tpm`; in `full` both get `tpm`. `sign-kind-matches-mode` expects `encrypted-tpm` for RSA in `lacking` and `tpm` in `full`
  (and the same for P-256 as above); the container `KINDS` table (incl. its `lacking` = `tpm`) is unchanged and used when `E2E_VM` is unset.
  Every mechanism the module offers per type is signed as in M4 (RSA-PKCS, SHAn-RSA-PKCS, `CKM_RSA_PKCS_PSS` with sha256/384/512 and the salt
  lengths 0, hash length and maximum, the over-maximum refusal, ECDSA, composed ECDSA) and each signature is verified by `openssl`
  against the certificate the module served. In `lacking`, after the imports and before the deletes, root runs the reader
  (`vm_read_credential`, `e2e/vm/cred-lib.sh`, F161) on both keys, so "every signature is from an `encrypted-tpm` key" is shown by the stored credential and not only by the label; a
  failing reader fails the run. No sign case is skipped in either VM mode.
- **`noplain-*` in a VM.** Same ids (`noplain-rsa`, `noplain-ec`, `noplain-no-key-file`). `noplain-run.sh` / `noplain.py` get the same
  VM-aware kind table (`lacking` → `encrypted-tpm`/`encrypted-tpm`, `full` → `tpm`/`tpm`; container table unchanged). After each import
  `scripts/check-no-plaintext.sh` (unchanged, from `/e2e-noplain`, which the payload already carries) scans the guest's real state
  directory with that key's `.p12` and password; `noplain-no-key-file` judges the same directory. In `lacking` the reader runs on both stored
  credentials too (so the scan is not vacuous: the key is stored as an `encrypted-tpm` record). The planted-key control copy stays. No skip.
- **Mapping** (container → VM; recorded here as the spec asks): the module path is the installed package's PKCS#11 module in the guest
  (builder finds it; a `MODULE` the VM run passes in); the state directory is `/var/lib/custodio` as the real unit sees it (readlink, as now);
  `/e2e`, `/e2e-noplain` come from the payload drive (F160); alice's session and agent are the same `su -l alice` under the guest's logind;
  nothing needs a restart of `swtpm` or a clear (those are F163). No case script of these two groups needs any other VM form; if the builder finds one, it
  adds it to this table in an amendment.
- **Self-tests.** `scripts/test-e2e-sign.sh` and `scripts/test-e2e-noplain.sh` (both in `verify`) gain the VM expectations with negative
  controls (below); their container checks stay.

Not built (where): pcr, tpm-clear, upgrade-kinds (F163); the real full runs and budget rows (F168); the host container run of the sign
and noplain cases is unchanged (M4), proven by the existing container sections of the two self-tests and `test-e2e-skips.sh`.
RSA-PSS with a TPM-sealed credential in a real guest is proven by the builder probe (step 4, not evidence) and at F168.

Environment: `/dev/kvm`, swtpm and both VM modes were proven in real guests by F160/F161 (`just e2e-vm-cases lacking ...` passed on 2026-11-08, 1m41s
for three groups). No new environment need.

Cost: the two self-tests are about 2 s and 1 s today; the VM sections add judges on fixtures run at once (`&`/`wait`), estimated +2–3 s each,
parallel with the other script tests under the `script *` budget (120 s). No new e2e case: the 11 ids exist and run only in the VM list.
Real-guest cost (paid at F168, not by `verify`): the sign step is about the container's (~40 requests, signatures of a case at once) plus 2 reader calls (<1 s);
noplain about the container's. Each step fits a session; the probe is one command (<10 min).
