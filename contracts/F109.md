# F109 — Research: how the service reaches the TPM under its unit

## Scope
Built: a section `## F109` in `docs/findings.md` that settles the SPEC open question "How the
service reaches the TPM under its unit". Every claim is backed by a command and its output, run in
the target's own e2e container (`e2e/targets/<t>/Containerfile`, started as `e2e/run.sh` does,
rootless podman with `vfs` in the dev container, as F108 did), and marked verified or inferred as
the rest of the file does. The six targets are debian13, ubuntu2404, ubuntu2604, fedora44, alma10
and arch. Only the resource manager node `/dev/tpmrm0` is considered; `/dev/tpm0` is never opened
or granted, and the finding says no candidate names it.

Per target the finding reports:
- **`tss` group and owner.** Whether the `tss` group exists in the image, with which package
  (`tpm2-tss` or the target's name for it, installed in the container for the question; no
  Containerfile change here), and what the package's udev rules (`tpm-udev.rules`, read from the
  installed file) give `/dev/tpmrm0` as owner, group and mode.
- **The candidate units**, each the shipped `data/custodio.service` text plus the smallest change:
  (A) the shipped unit as it is (`PrivateDevices=yes`, no TPM node); (B) `PrivateDevices=yes` plus
  `BindPaths=`/`BindReadOnlyPaths=` of the node; (C) `PrivateDevices=no` with `DevicePolicy=closed`,
  `DeviceAllow=/dev/tpmrm0 rw` and the group; (D) any variant the research shows is needed (for
  example `SupplementaryGroups=tss`, or `PrivateUsers=no`, or `PrivateDevices=yes` with
  `DeviceAllow=` and `BindPaths=` together). Which exist is decided by the step within these
  limits: no candidate may name `/dev/tpm0`, drop `NoNewPrivileges`, `CapabilityBoundingSet=`
  empty, `ProtectSystem`, `RestrictAddressFamilies` or `SystemCallFilter`, and no unit file in
  `data/` is edited by this feature.
- **What `PrivateDevices=yes` hides and what `DeviceAllow=`/`BindPaths=` do with it**, shown by a
  process in each candidate's sandbox listing `/dev` and opening the node.
- **Group access under `PrivateUsers=yes`** with the static `custodio` user (the sysusers entry
  of `data/sysusers.d`, which `DynamicUser=yes` in the shipped unit reuses; the finding states
  which of the two the unit really runs as): whether a supplementary group outside the user
  namespace's mapping still lets the process open a node owned `root:tss 0660`, and what `id`
  and `ls -ln` show inside the sandbox.
- **The exposure score** of every candidate: `systemd-analyze security --offline=yes
  --threshold=10 <unit>` (the threshold of `just security-score`, read from the justfile, not
  assumed) with that target's own `systemd-analyze` and its version, plus the score on the dev
  container's systemd 257 that `just system-gates` uses, and the lines that cost points.

**What the containers can show.** F108 decided route 2 (`swtpm` on a unix socket): the e2e
containers have no real `/dev/tpmrm0` (the dev container has no `/dev/tpm*` and no `/dev/vtpmx`;
re-run `ls /dev/tpm* /dev/vtpmx` and record it). Probed by the contract author in this session:
`podman run --rm --privileged docker.io/library/debian:trixie sh -c 'mknod /dev/tpmrm0 c 10 224'`
fails `Operation not permitted` (rootless, uid_map `0 1000 1`), and a node passed with
`--device /dev/null:/dev/tpmrm0` appears as `crw-rw-rw- 65534 65534` where `chgrp` and `chmod`
fail. The first step re-runs both probes and pastes the output. So a character device owned
`root:tss 0660` cannot exist here, and the stand-in is split in two:
- (a) a character device passed with `--device` (e.g. `/dev/null` as `/dev/tpmrm0`), used only for
  the `PrivateDevices`/`DeviceAllow`/`BindPaths`/`DevicePolicy=closed` checks;
- (b) a regular file created inside the container as `root:tss 0660`, used for the supplementary
  group check under `PrivateUsers=yes` as `custodio`.
That the kernel checks a device inode's mode and group as it does a regular file's is *inferred*.
**Every candidate runs as a real unit file** started by the container's own systemd (PID 1, booted
as `e2e/run.sh` does), the shipped `custodio.service` text with only `ExecStart=` swapped for a
probe script (and the candidate's directives); no hand-built `unshare`/`nsenter` sandbox. For
each candidate the finding pastes `systemctl show -p
PrivateDevices,PrivateUsers,DevicePolicy,DeviceAllow,SupplementaryGroups,User`. If a unit fails to
start in the nested container the error is recorded, not dropped. Running with `--cgroupns=host`
rootless may not enforce the cgroup device filter; the control "a node not in `DeviceAllow=` fails
under `DevicePolicy=closed`" shows it, and if it does not fail the finding says enforcement could
not be shown here and moves it to F147.
What a stand-in cannot show goes in a subsection "Left to the hardware acceptance (F147)", each as
a command F147 runs: that `udev` creates the real `tpmrm0` (misc 10:224, driver `tpm_crb`/`tpm_tis`)
with the rules' owner; that the device filter accepts `DeviceAllow=/dev/tpmrm0` for the real node;
group access to the real node under `PrivateUsers=yes`; and `tpm2_getcap` through it under the
chosen unit.

It ends with a line `Decision: ` and the exact unit directives (as they would appear in
`custodio.service`) plus, if needed, the drop-in or sysusers/tmpfiles line for the group; if
targets differ, which directive handles which. If no candidate meets the threshold on the dev
container's score, the builder writes `BLOCKED.md` for a person (question, options, scores) and
the threshold stays 10. The words `tss`, `/dev/tpmrm0`, `PrivateDevices`, `PrivateUsers`,
`DeviceAllow`, `exposure` and the six target names appear.

Left to other features: the shipped TPM module, applying the decision to `data/custodio.service`,
`sysusers.d`, the packages and the polkit/SELinux policy, the real TPM e2e cases, and the real
hardware (F147). This feature changes no recipe, unit, script, Containerfile or Rust code and not
`SPEC.md`; it adds only the section (and `BLOCKED.md` if needed). Package gates, `just e2e` and
lifecycle tests run at the checkpoints and are not run here; `just system-gates` (in `verify`)
must stay green because the unit is untouched.

Environment, checked this session: `podman` is rootless with the `vfs` driver; no `/dev/tpm*` in
the dev container; systemd 257 in the dev container; the dev container reaches
archive.ubuntu.com, repo.almalinux.org, geo.mirror.pkgbuild.com, mirrors.fedoraproject.org and
Docker Hub (HTTP 200/302/401), so all six images can be built. Building six images is slow; the
step builds one at a time with `timeout` and logs to a file it tails.

## Steps
- [ ] Re-run the environment checks and the two stand-in probes (`ls /dev/tpm* /dev/vtpmx`, `mknod`, `--device`, `podman info`, the threshold in
      `justfile`, the score of the shipped unit in the dev container) and record them.
- [ ] On debian13, the reference target: build the image, start it, install the `tpm2-tss`
      package, report the `tss` group and the udev rules, create the stand-in node, define the
      candidate units as real unit files under the container's systemd (with the `systemctl show`
      output), and show what each does to the node (`/dev` listing, open attempt) and
      under `PrivateUsers=yes` with the `custodio` user and `tss` as supplementary group.
- [ ] Repeat on ubuntu2404, ubuntu2604, fedora44, alma10 and arch with the same script (kept
      outside the repository or in a scratch path; not committed), recording per target the
      group, the owner and mode from the rules, the behaviours that differ, and the exposure
      scores with that target's `systemd-analyze` version.
- [ ] Decide: pick the candidate that meets the threshold with the least exposure and works on
      every target; if none does, write `BLOCKED.md`. Write the "Left to the hardware
      acceptance (F147)" subsection.
- [ ] Write `## F109` in `docs/findings.md` with all of the above, the listed words and the
      `Decision: ` line; `just quick`; the whole `verify` (includes `just system-gates`); commit.

## Evidence
- `tss` group exists (or not) and who owns `/dev/tpmrm0`, on each of six targets → `getent group
  tss` and the installed udev rules file line, per target → output pasted, one block per target;
  a target where the group is absent says so and how the unit then gets access.
- Only `/dev/tpmrm0` considered → every candidate's directives and the Decision line contain no
  `/dev/tpm0` (`grep -c '/dev/tpm0\b'` over the unit-text code blocks, not the prose, prints 0) → shown.
- `PrivateDevices=yes` hides the node → in unit A, a process lists `/dev` and `open()` of the
  stand-in (a) fails `ENOENT`; the same stand-in is visible and opens in unit C (negative control for
  the test) → output pasted.
- What `DeviceAllow=`/`BindPaths=` do → in B and C, `ls -l`/open result and, for C, the
  `DevicePolicy=closed` effect on another node (`/dev/null` is allowed by default? the finding
  reports it, and a node not listed fails) → output pasted.
- Group access under `PrivateUsers=yes` with the `custodio` user → inside the sandbox `id` and
  `ls -ln` of file (b) (unmapped gid shown), and an open for read/write as `custodio` with
  `SupplementaryGroups=tss`: succeeds; without it fails `EACCES` (negative control) → output pasted, per target.
- Exposure of each candidate vs the threshold → `systemd-analyze security --offline=yes
  --threshold=10 <candidate>` per candidate per target, exit status and score → table in the
  section; the chosen candidate's score on the dev container's systemd 257 is ≤ the threshold of
  `just security-score` (a bare unit still fails it, as that recipe checks) → `just
  system-gates` passing with the unit unchanged is only the regression check.
- No candidate meets the threshold → `BLOCKED.md` exists and the Decision line says "see
  BLOCKED.md"; otherwise `BLOCKED.md` does not exist and `git diff` shows the threshold untouched
  (`grep -n 'security-score threshold' justfile` still prints `"10"`) → shown.
- What containers cannot show → a subsection "Left to the hardware acceptance (F147)" with
  commands, and the stand-in's creation command and its output (or why it failed) → read by the
  evaluator.
- The words and the exact directives → the feature's `verify` (the twelve words, `^Decision: `,
  `just system-gates`) → passes; `just quick` green.
