# F150 — KVM for the VM target: research, VM tools in the dev container, and the vm-host-check recipe

## Scope
Built:
- `docs/findings/F150.md` (`## F150`) and its line in `docs/findings.md`: the KVM question of SPEC "Open questions".
- The dev container installs the VM target's tools (`harness/Containerfile`); `harness/run.sh` exposes `/dev/kvm` as the finding decides.
- `just vm-host-check` (`scripts/vm-host-check.sh`) and its self-test `scripts/test-vm-host-check.sh`, added to `just test-scripts`.
- `BLOCKED.md` asking for the rebuild of the dev container, after the Containerfile and `run.sh` change is committed.

Not built (left to other features): the cloud image download and verification, the seed and boot (F151 settles
the seed tool; this feature installs `cloud-image-utils` and the check accepts it, or the ISO tool F151 names
only if F151 changes it), the VM case list, and the CI job for the VM (the finding only names what a job must do).
No software-emulation measurement (a person's choice), and the builder never switches to it.

Environment, measured in this session (`ls -l /dev/kvm; id; command -v qemu-system-x86_64 cloud-localds gpgv swtpm; ls /usr/share/OVMF`):
`/dev/kvm` does not exist in the current dev container (`ls /dev` lists only console, core, fd, full, mqueue, null,
ptmx, pts, random, shm, std*, tty, urandom, zero); user `dev` (uid 1000, no extra groups); only `swtpm` is installed
(`/usr/bin/swtpm`); no qemu, no `/usr/share/OVMF`, no `cloud-localds`, no `gpgv` on the PATH. So `just vm-host-check`
fails here today, by design, until the person rebuilds the container on a host that has KVM.
The host is outside what a session can inspect (`harness/run.sh` is run by a person, from a Mac per its header, with
rootless podman): the finding reports what this container can see and marks host facts and the GitHub runner
**inferred** (from the cited documentation or source) unless a command in the finding shows them. The first
`vm-host-check` on the rebuilt container is the person's check that the exposure worked. If the finding concludes
the host cannot offer `/dev/kvm` (for example the engine runs in a VM without nested virtualisation), the builder
writes `BLOCKED.md` with the options and stops; the person decides. Nothing here edits the host.

Research is delegated to a subagent (GitHub runner documentation, podman `--device` and rootless group semantics,
udev rules for `/dev/kvm`); the finding states the conclusion with the evidence lines, not dumps.

Test cost: `scripts/test-vm-host-check.sh` is a script test with stubbed paths, no VM, no network, no container;
estimated 2–5 s (about 10 invocations of a bash script, similar to `scripts/test-bus-check-sync.sh`), well under the
`script *` budget of 120 s; it runs in parallel with the other script tests inside `test-scripts`. No e2e case, no
unit test, no new long suite. `just vm-host-check` itself runs in under a second. The Containerfile gain is a
one-off image build, not a per-run cost.

      `podman info` of the nested engine if useful) and read the sources for the host side and the runner (subagent);
      write `docs/findings/F150.md` with the conclusion first, each fact marked **verified** or **inferred**, the
      runner's `/dev/kvm` udev rule and the `runner` user, the `ubuntu-26.04` image, what `harness/run.sh` needs
      (`--device /dev/kvm`, and the group or `--group-add keep-groups`/`--annotation` step the finding proves for rootless
      podman with `--userns=keep-id`), and a last line `Decision: ` for the dev container and for CI. Index it in `docs/findings.md`.
- [ ] If the finding says a host change is needed or the host cannot offer KVM: note it for `BLOCKED.md` (written in the last step).
- [ ] Write `scripts/test-vm-host-check.sh` first (failing), then `scripts/vm-host-check.sh` and the `vm-host-check` recipe;
      the script takes its paths from overridable variables so the test can stub them. Add the self-test to `test-scripts`.
- [ ] Install in `harness/Containerfile`, from the distribution, each with a comment saying why: `qemu-system-x86`,
      `qemu-utils`, `ovmf`, `cloud-image-utils`, `ubuntu-keyring` (and `gpgv` if not already present); change `harness/run.sh`
      to expose `/dev/kvm` as the finding decided, without failing when the host has no such device if the finding decides so.
- [ ] Run `just quick` and the evidence below; commit the work; write `BLOCKED.md` asking a person to rebuild the dev
      container (and to make the host change if the finding says so), commit it, and stop. The feature passes on the rebuilt container.
