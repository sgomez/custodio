# F197 — `custodio fingerprint enable` and `disable`: decisions, refusals, the command and the check that no fixture seam ships

## Scope

Built here:

- A pure module of custodio-cli (`fingerprint_decide`, no I/O: it takes an observed state and returns a decision or a
  value). It holds: the exact bytes `enable` writes (the five lines of SPEC Design 1 plus comment lines that say
  Custodio wrote the file and how to undo it); "is this file Custodio's" (exactly those bytes); detection of fingerprint
  active globally from file contents per family (Debian family: `pam_fprintd` in `common-auth`; Fedora family:
  authselect's `with-fingerprint` feature; Arch: `pam_fprintd` in `system-auth` or `sudo`; the report's "Detection");
  and `decide_enable` / `decide_disable` from an observed state. Each refusal has its two-line message (line 1 what
  is wrong, line 2 the next step, through the error module of F193) and the package names per family
  (`libpam-fprintd` and `fprintd`; `fprintd-pam` and `fprintd`; `fprintd`). The decisions: not root, foreign file
  (administrator's, Omarchy-style, Custodio's with a changed byte, a symlink or other non-regular file), no vendor
  file (missing or not regular), no `pam_fprintd.so`, no `fprintd`, already enabled (success, nothing to write),
  fingerprint already global (refusal, non-zero, says the override would be redundant, next step: turn the global
  switch off and run `enable` again), no reader (write, with a warning naming `custodio doctor`), nothing to disable
  (success), disable of a foreign file (refusal). The family comes from an observed `os-release` (`ID`, `ID_LIKE`);
  for an unknown family the conservative option holds (every family's global form is checked, and the package names of
  all three families are given). Fingerprint modules of other lines (comments, `-auth`, `include` lines) are decided
  by the parser, which the fuzz target covers.
- The fuzz target `pam_file` (`crates/custodio-cli/fuzz`) for the PAM and authselect parsers, in `fuzz-smoke`'s default
  `expected` list. The decision module and the command's module join the custodio-cli list of the `mutants` recipe.
- The subcommand, in its own module, which gathers the observed state from the real system and applies the decision:
  refuses unless root; probes `pam_fprintd.so`, `fprintd` and its devices (no device is a warning, never a refusal; the
  question is asked of `net.reactivated.Fprint` without a polkit prompt, and an unanswered question is read as "no
  reader" with the warning, never as a refusal); writes `/etc/pam.d/polkit-1` atomically (the whole file or no file; a
  temporary file in the same directory, flushed, then renamed, removed on failure), mode 0644, owner `root:root`,
  with the SELinux label the policy gives a new file there where SELinux is enforcing (how the label is obtained and
  applied is the builder's choice within: the policy's default for the path, never a fixed type, and a failure to
  label removes the file again and refuses); a second `enable` changes nothing; `disable` removes only Custodio's file;
  prints what changed and how to undo it, and the lock-screen note when it applies, without changing any setting.
  Help (entries in the command table of F193) and the man page text.
- A seam that points the command at a fixture root (a cargo feature of custodio-cli, named for what it is, plus
  whatever it reads), never in what ships. `just fixture-seams` builds the release binary the way the packages build
  it and fails if it has the seam; `scripts/check-fixture-seams.sh <binary-or-tree>` is the check, with
  `scripts/test-check-fixture-seams.sh` as its negative control (like `scripts/check-test-label.sh`: it also fails if
  a shipped file under `data/` or `packaging/` or a non-dev dependency / default feature names the seam). The test
  script is added to `just test-scripts` and `shell-scripts-test`, as `test-check-test-label.sh` is.

Left to other features, not proven here:

- Owner `root:root` and the SELinux label of the written file need real root and real SELinux. The dev container runs as
  uid 1000 with no `/sys/fs/selinux` (checked: `id -u` is 1000, no `getenforce`, `restorecon`). They are proven on the
  real `/etc` by F199 only (every target; the label on fedora44 and alma10); no test here claims them. The chown call
  and the label-applying call are two small functions of the command module (`apply_owner`, `apply_label`, or the
  builder's names), each only a system call plus the policy lookup. They are excluded from the `mutants` run by name in
  the recipe (with a comment naming F199 as where they are proven), and nothing else is. The label step's failure
  path (a failure after the temporary file exists) is not excluded: the seam injects it (below).
- A PAM client authenticating through the override, `pam-auth-update` and `authselect` leaving it alone: F199. The
  virtual sensor and the fallbacks: F200. `doctor`'s use of the same detection: F202 (it calls the module's detection
  and gets its tests there). Package scripts not touching PAM: F198. The user documents: F207.

Environment, checked in the dev container: `which dbus-daemon dbus-run-session` gives `/usr/bin/dbus-daemon` and
`/usr/bin/dbus-run-session` (version 1.16.2), and `crates/custodio-cli/tests/fixture/mod.rs` already starts a private
`dbus-daemon` for the register tests, so a private bus needs nothing new. The fake `net.reactivated.Fprint` is a small
zbus server inside `tests/fingerprint.rs` (zbus is already a dependency; an extra dev-dependency is the builder's call
within what `cargo deny` allows). The command reaches the system bus through the standard `DBUS_SYSTEM_BUS_ADDRESS`
variable, which is not a seam.

The seam (a cargo feature of custodio-cli, never default, never in packages). With it the command reads
`CUSTODIO_FIXTURE_ROOT` (every path it reads or writes is under that root), `CUSTODIO_FIXTURE_EUID` (overrides the
effective uid; absent means the real `geteuid`) and `CUSTODIO_FIXTURE_FAIL` (`rename` or `label`: fail at that point,
after the temporary file has been written). Without the feature none of these names is in the binary.

Sizing: about six steps; nothing needs a split. The fixture seam is built together with the command because `fingerprint.rs`
needs it.

Costs (estimates from similar tests in this crate; the builder reports measured times in PROGRESS.md):

| Test | Time | How it runs |
|---|---|---|
| `tests/fingerprint_decide.rs` (every state of the decision table, parser cases, one-byte-changed over every byte of the file) | under 1 s | own test binary, tests parallel |
| unit tests in the new modules | under 1 s | parallel, lib test binary |
| `tests/fingerprint.rs` (about 35 cases, each runs the binary on its own temporary fixture root; three start a private `dbus-daemon`, about 0.2 s each, own socket) | 3 to 6 s | own test binary, tests parallel, no shared state |
| `pam_file` in `fuzz-smoke` | 2000 runs, about 1 s plus one more target build | the recipe's own loop |
| `scripts/test-check-fixture-seams.sh` | under 5 s (fixture binaries are small files, no build) | with the other script tests, parallel |
| `just fixture-seams` | one release build of `custodio-cli`; a few minutes cold, seconds if the package build left `target/release` warm | one command, in `verify` only |
| `just mutants-diff F197` | two new modules plus the command: expect 60 to 120 mutants, 3 jobs, 8 to 15 minutes | one command; if it would pass 30 minutes the builder splits it with `--file` and says so |

No e2e case here (F199 has them). Nothing is slower than `budgets.tsv`'s script row.

## Evidence

- The five lines are exactly SPEC's, and comments do not change what a reader sees → `fingerprint_decide`: the written bytes
  split into non-comment lines equal the five lines of Design 1 in order; an Omarchy-style reader (the first non-comment
  `auth` line containing `pam_fprintd.so`) finds the line `auth     [success=done default=ignore] pam_fprintd.so max-tries=1 timeout=10`
  and no comment line matches it → pass; a variant with `pam_fprintd.so` in a comment must not be read as active (control).
- Whose file it is → `fingerprint_decide`: the exact bytes are Custodio's; each of: one byte changed (every position),
  a byte appended, a byte removed, CRLF, no final newline, an Omarchy-style file, an administrator's file, empty file
  are not → pass.
- Global detection per family → `fingerprint_decide`: Debian `common-auth` with and without an active `pam_fprintd`
  (commented, `-auth`, `sufficient`, `[success=...]` forms); authselect with and without `with-fingerprint` (a feature
  whose name merely contains it does not count); Arch `system-auth` and `sudo` each alone; a Debian-family system with
  fingerprint only in `sudo` is not global there; unknown family checks all forms → each expected active / inactive.
- Every decision of `enable` and `disable` (not root, foreign file, symlink / non-regular, no vendor file, vendor not
  regular, no module, no `fprintd`, already enabled, global active, no reader, nothing to disable, disable foreign,
  success), each with its message (two lines, the package names per family, `custodio doctor` in the warning, the
  next step) and the exit class (refusal non-zero, already enabled, nothing to disable and warning succeed) →
  `fingerprint_decide`, a table with one row per state → pass. Acceptances 2, 3, 4 as decisions.
- The module does no I/O → its functions take observed values only; `fingerprint_decide` calls them without a file system
  in every case (the file has no temporary directory) → pass.
- Fuzz of the PAM and authselect parsers → `just fuzz-build && just lint-fuzz && just fuzz-smoke` → `pam_file` is built
  and runs; `just fuzz-smoke "<list without pam_file>"` shows the expected list is what requires it (the existing
  negative control of the recipe).
- Mutants → `just mutants-diff F197` → 0 missed in the decision and command modules (both are in the recipe's list); only the two named owner / label system-call functions are excluded, with a comment naming F199.
- Acceptance 1 (the file, mode, re-run) → `fingerprint.rs`: `enable` on a fixture root with vendor file, module and
  fprintd (fake bus with one device) writes bytes equal to the module's file, mode 0644 even under umask 077, nothing
  else changed in the root (a before/after tree comparison); the second `enable` exits 0 with the tree byte-identical
  and says nothing was changed → pass. Owner `root:root` and label: F199 only.
- The device probe, three outcomes → `fingerprint.rs`, each on its own private bus (`DBUS_SYSTEM_BUS_ADDRESS`):
  (a) the fake `net.reactivated.Fprint` lists one device → file written, no reader warning;
  (b) it lists zero devices → file written, exit 0, the warning naming `custodio doctor` and the password fallback;
  (c) no name owner on the bus, a bus address that does not exist, and a fake that answers after the probe's limit →
  the same as (b), never a refusal. A probe that always says "no reader" fails (a); one that always says "reader"
  fails (b) and (c); one that treats no answer as a refusal fails (c). The fake records its calls: only the device
  listing was asked, so no polkit prompt is raised → pass. Mutants on the probe are killed by these cases.
- What it prints → `fingerprint.rs`: the output of `enable` says every polkit dialog accepts the finger, a wrong finger
  or 10 s without a touch falls back to the password, `sudo` and the login are unchanged, and the command that undoes
  it; no setting changed in the fixture root → pass.
- The lock-screen note → decided from two observed inputs read under the root: the GNOME login-screen schema is present
  (`usr/share/glib-2.0/schemas/org.gnome.login-screen.gschema.xml`) with no file in `etc/dconf/db/*.d/` setting
  `enable-fingerprint-authentication=false`; and the family is not Fedora or Alma (authselect locks it off, from
  os-release). `fingerprint_decide` has the rule over those values (shown or not for: schema absent; present and key
  unset; present and set false; Fedora family). `fingerprint.rs` has two cases: schema present, key unset → note shown
  and the dconf files byte-identical after; a dconf file with the key false → note not shown → pass.
- Atomic write → `fingerprint.rs`: with `CUSTODIO_FIXTURE_FAIL=rename` and with `=label`, the seam fails the step after
  the temporary file was written and flushed; `enable` exits non-zero, there is no `etc/pam.d/polkit-1`, no leftover
  temporary file, and the tree is byte-identical. An unwritable `etc/pam.d` is a third case (non-zero, two-line
  message, nothing created). Removing the cleanup of the temporary file fails the two seam cases → pass.
- Not root → `fingerprint.rs`: one case sets no `CUSTODIO_FIXTURE_EUID`, so the real `geteuid` decides; it first
  asserts the test's own uid is not 0 (in the dev container it is 1000; if run as root the case fails with a message
  that the suite must run unprivileged), then expects non-zero, the two-line message, tree byte-identical. Every other
  case sets `CUSTODIO_FIXTURE_EUID=0`. Replacing the real check with "always root" fails this case. The decision for
  a non-root euid is also a row of `fingerprint_decide`. F199 does not test this refusal → pass.
- Acceptance 2, every other refusal → `fingerprint.rs` (euid 0 by the seam): Omarchy-style file, administrator's file,
  Custodio's with one byte changed (one case; every position is proven in `fingerprint_decide`), a symlink (to a
  Custodio file and to nothing), no vendor file, no module, no `fprintd`: each exits non-zero, prints two lines with
  the next step, and the root tree is byte-identical. The module lookup runs on three layouts, each with the module
  absent (refused) and present only there (accepted): `usr/lib/x86_64-linux-gnu/security` (multiarch),
  `usr/lib64/security`, `usr/lib/security`; a single hard-coded path fails at least four of the six cases → pass.
- Acceptance 3 → `fingerprint.rs`: every global form (Debian `common-auth`, Fedora authselect feature, Arch
  `system-auth`, Arch `sudo`) exits non-zero, says the override would be redundant and names the next step, changes
  nothing → pass.
- Acceptance 4 → `fingerprint.rs`: `disable` removes Custodio's file and the rest of the tree is byte-identical; with no
  file it exits 0 with the tree unchanged and says so; with a foreign file it refuses, names who might own it and how
  to look, and the file is byte-identical → pass.
- Help and man page → `cargo test -p custodio-cli --test help --locked`: `fingerprint`, `enable` and `disable` are in
  the table, the help (standard output, status 0) and the man page, both ways → pass.
- The seam never ships → `scripts/test-check-fixture-seams.sh`: a fixture binary / tree with the seam is flagged, a clean
  one passes (one negative control per rule: a binary containing the seam, a shipped file naming it, a default feature
  enabling it) → pass; `just fixture-seams` on the real release build → pass. A positive run of the check on a build
  made with the feature (inside the test script only if a build is not needed; otherwise by the builder once, noted in
  PROGRESS.md) shows the check sees the real seam, not only the fixture's text.
- `just quick` → green (includes `fingerprint_decide`'s siblings, clippy, file size, the test-label check).
