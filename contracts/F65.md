# F65 — Give each failure its own D-Bus error name

## Scope
Built:
- One service error type in `custodiod` (name and file are the builder's). Each variant maps to one D-Bus
  error name under `com.rfirma.Custodio1` (for example `com.rfirma.Custodio1.Error.<Name>`; the exact
  spelling is chosen once and recorded where SPEC.md's "chosen once, documented" rule needs it). At least
  these variants: invalid arguments; no such key; key id already taken; polkit denied; authorization
  unavailable; wrong password or unreadable `.p12`; unsupported key type; certificate does not match the key;
  audit unavailable; internal or storage failure. Names are distinct and only ever added to.
- Every existing failure path of `ListKeys`, `ListCertificates`, `ImportP12` and `Sign` returns the matching
  name instead of `org.freedesktop.DBus.Error.*`. This includes the path in `dbus.rs` that today turns every
  `ImportError` into `Failed`, the `StoreError` mapping, `SignError`, `RequestError`, credentials/polkit
  failures and audit failures. If the builder finds an existing failure that fits no listed variant, it adds
  a variant rather than falling back to a generic name.
- Message texts are fixed strings for people: they are not built from key ids, paths, the password, `.p12`
  bytes, parser errors (`ImportError::Parse(String)`, `UnsupportedKey(String)`, `io::Error`, `PathBuf`) or the
  rejected input.
- `custodio-client` holds the error names as plain `&str` constants (no dependency, no zbus; the crate stays
  as F64 left it). `custodiod` takes its names from there (single definition).
- `custodio-pkcs11` maps the names to `BackendError`/CKR codes (`backend.rs::map_error`); `custodio-cli` maps
  them to its messages (`bus.rs`) and no longer prints the service's message text as the only signal.
  The CKR value for each case that exists today is unchanged (record the current value per case in the first
  step, before touching the mapping).

Not built: `DeleteKey`, replace-certificate or any new method (later features); the client documentation and
the published list of names beyond a doc comment on the client constants (later documentation features);
anything that only the checkpoints prove (F90, F100).
Where the CLI's output is re-checked end to end is out of scope; here the CLI is proven by its own tests.
Note: if the error type lives in a new file, add it to the `--file` list of the `mutants` recipe so
`mutants-diff F65` covers it (that is a recipe extension, not a threshold change).

Environment: nothing beyond the dev container is needed; the dbus tests of `custodiod` already run a private bus.

Size: about five steps; no split proposed.

## Steps
- [ ] Record the baseline per service failure, not per `map_error` input: for each failure that Sign or
      ListCertificates can return to the module today, the fdo name it arrives as (from `dbus.rs`) and the
      CKR value it ends as (`backend.rs::map_error` + `module/signing.rs` sign_with). Expected table, to be
      checked against the code and written to `PROGRESS.md`: polkit unavailable, no sender, credentials
      failure → `AccessDenied` → `Denied` → `CKR_FUNCTION_FAILED`; polkit denied → same; no such key, audit
      unavailable, bad key, signing failure, store failure → `Failed` → `Unavailable` → `CKR_DEVICE_ERROR`;
      every invalid-argument case → `InvalidArgs` → `Invalid` → `CKR_DATA_INVALID`. Only the denied case is
      pinned by an existing test today (cryptoki); the rest are pinned by the new table test. Add the failing
      tests for the error type: variant → name table, distinctness, and the message check below.
- [ ] Add the name constants to `custodio-client`, and the service error type in `custodiod` with its
      D-Bus name mapping and fixed messages.
- [ ] Route `ListKeys`, `ListCertificates`, `ImportP12` and `Sign` through the new type, with a D-Bus test per
      failure (over the private bus, reading the error name from the reply).
- [ ] Map the names in `custodio-pkcs11` (to the `BackendError` of the step 1 table, so CKR codes stay equal;
      not by what looks natural) and in `custodio-cli` (to messages), each with unit tests. Extend the
      `pkcs11` run of the `mutants` recipe with `--file crates/custodio-pkcs11/src/backend.rs` (and the error
      type's file for `custodiod`); this adds coverage, no threshold changes.
- [ ] Run `just quick`, then `just mutants-diff F65` and fix surviving mutants with tests (not by narrowing
      the run); write the `PROGRESS.md` entry.

## Evidence
- Variants map to distinct names in the project namespace, with at least the ten listed cases → unit test in
  `custodiod` (table of every variant → expected name string, asserting the set has no duplicates, every name
  starts with `com.rfirma.Custodio1.` and none is in `org.freedesktop.DBus.Error.`) → passes; a negative
  control changes one name to a duplicate and the test fails.
- The client crate holds the names, once → `cargo test -p custodio-client` (names are the expected literals) and
  `grep -rn` showing the literal name strings appear only in `custodio-client` outside tests; `cargo tree -p
  custodio-client` has no dependency → expected output.
- Every failure of ListKeys/ListCertificates returns its name → dbus test in `custodiod` with a store that
  fails (unreadable or bad-permission store) → reply error name is the internal/storage name, not an fdo name.
- ImportP12 failures → dbus tests, one per case: bad id / oversize input / oversize password → invalid
  arguments; id already present → key id taken; wrong password and garbage bytes → wrong password or
  unreadable `.p12`; a non-RSA-2048/P-256 key → unsupported key type; certificate not matching the key →
  certificate mismatch; store write failure → internal/storage. (Each asserts the exact name.) Also a
  `p12` with no private key / multiple keys → the variant the builder picks (invalid arguments or unreadable
  `.p12`), asserted by name; the pick is recorded in the error type's doc comment so F66 lists it the same.
- Sign failures → dbus tests, one per case: bad id, bad mechanism, bad hash, bad salt, oversized data → invalid
  arguments; unknown key → no such key; polkit denies → polkit denied; polkit unavailable, no sender and
  credentials failure → authorization unavailable; audit sink failing → audit unavailable; key file bad /
  signing failure → internal/storage; mechanism mismatch → invalid arguments. Each asserts the exact name.
  No successful call is changed (existing success tests stay green).
- Messages are fixed and leak nothing → test in `custodiod` that triggers every failure above with
  recognizable sentinels in the key id, the password, the `.p12` bytes and the store directory path (and a
  parser error that carries text), and asserts that no reply message contains any sentinel, the store path,
  any `/` path fragment, or the id/password; plus a test that each variant's message is a `'static` fixed
  string equal for two different inputs of the same variant → passes; negative control: a variant built to
  include its input fails the sentinel test.
- The PKCS#11 module maps each name, and CKR values per service failure are unchanged → table unit test in
  `custodio-pkcs11` over `map_error`, one row per new name (all ten, plus an unknown name and a non-method
  error), asserting the exact `BackendError` from the step 1 table: authorization unavailable → `Denied`;
  polkit denied → `Denied`; no such key, audit unavailable, internal/storage, key id taken, wrong
  password, unsupported key type, certificate mismatch, unknown name, non-method error → `Unavailable`;
  invalid arguments → `Invalid`. A second assertion in the same test file maps `BackendError` to CKR through
  `sign_with` (`Denied` → `CKR_FUNCTION_FAILED`, `Unavailable` → `CKR_DEVICE_ERROR`, `Invalid` →
  `CKR_DATA_INVALID`) so the end value is pinned. Negative control: mapping authorization unavailable to
  `Unavailable` makes the test fail. As a one-off, `cargo test -p custodio-it --test cryptoki` stays green with
  no edited expectation; it only re-checks the denied case and is not the proof for the other codes. →
  `cargo test -p custodio-pkcs11` (in `just quick`) green.
- The CLI shows a message per name → unit test in `custodio-cli` over the error-to-message function for every
  name plus an unknown name and a transport error (exact message strings asserted, and none is the service's
  free text), and the existing `custodio-it` `cli.rs` import-failure tests still pass → `cargo test -p
  custodio-cli`, `cargo test -p custodio-it --test cli` → green.
- Tests catch wrong mapping → `just mutants-diff F65` → no surviving mutants in the changed lines of the
  error type, `dbus.rs` and (after the recipe extension) `backend.rs`. The CLI's `bus.rs` and the client
  constants are outside the mutants run; their exact-string unit tests are the proof there.
- `just quick` → exit 0.
