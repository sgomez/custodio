# F58 — Lifecycle scripts of the Arch package

## Scope
The Arch install script (`packaging/arch/pre_install`, `pre_upgrade`, `post_install`, `post_upgrade` and the new `pre_remove` and
`post_remove`, wired in `packaging/nfpm.yaml`), possibly one more pacman hook shipped by the package, and the tests that run them.
SPEC design section 2 is the source of the behaviour. `contracts/F43.md` (deb) and `contracts/F44.md` (rpm) are the model: the same
decisions, expressed with pacman's conventions. systemd's own pacman hooks are the reference for what is NOT repeated: what the
hooks already do on the target system is not duplicated by the scripts. Behaviour is copied, not text.

Built here:
- Research (subagent; record in `docs/findings.md`, with the file or command that proves each line): which hooks the `systemd`
  (and `dbus`, if any) package of Arch installs, their `When`, `Trigger` (paths, operations) and names, hence their order
  (pacman runs hooks of one phase in file-name order, and runs the install script of a package BEFORE the PostTransaction hooks).
  For each of the four decisions below it says whether a hook already does it for the paths this package ships (unit, sysusers file,
  catalog, bus policy), when, and whether it fires on install, upgrade and removal.
- Account: created before the bus policy is unpacked, from the sysusers content embedded as in F43/F44, under the same sync gate
  against `data/sysusers.d/custodio.conf`, in `pre_install` and `pre_upgrade` after the F42 check. Reason to be proven by the
  research: systemd's sysusers hook runs PostTransaction, after unpacking, so it is too late for the bus. If the research showed
  otherwise, the builder amends this step (evaluator approval) instead of silently dropping it. The tool missing or failing makes
  the script fail with a message on stderr and no `|| true`; the test states what pacman does with that status (the F42 findings say
  it installs anyway) and the contract does not claim more than that. No `useradd` fallback; one account definition. The
  `systemd-sysusers custodio.conf || true` in `post_install`/`post_upgrade` goes away if the research shows it duplicates the hook.
- Failed bus check on a first install: pacman goes on installing, so the account must still be created before the policy is
  unpacked. `pre_install` and `pre_upgrade` therefore run the check, keep its status, create the account, and only then exit with the
  check's status (and print its message as today). Only the embedded `custodio_bus_check` function stays byte-identical to
  `packaging/bus-check.sh`; the tail of the scripts may change.
- Reloads and catalog: daemon-reload, then bus reload, then catalog update, each once and tolerating failure (no live systemd). The
  scripts run only the ones no hook does at the right time; the research decides, and a step records in `docs/decisions.md`
  which hook covers which call and which the script does (a later session could undo it without knowing why). The bus reload has
  no systemd hook and stays in the script unless the research finds one.
- Never enable, never start, no preset.
- Restart on upgrade: once, after the new files, the daemon reload and the bus reload, and only if the service was running before.
  The old package's scripts do not run on a pacman upgrade, so this holds on the first upgrade from today's F42-era package too: no
  outcome of "does not restart while running" is acceptable (only an amendment backed by the research can change that). Constraint from the pacman order: `post_upgrade` runs before PostTransaction hooks, so a restart there can precede a hook's
  daemon-reload. The step decides how (a daemon-reload in `post_upgrade` before the restart, or a restart in a PostTransaction hook of
  this package ordered after systemd's hooks, or another mechanism), within these limits: it passes the order evidence below
  with a real pacman upgrade; "was running" is read without any state under the state directory; no restart on first install; the
  choice is recorded in `docs/decisions.md`. If it needs a new hook file, it is added to `nfpm.yaml`, to the parity and lint lists,
  and the F42 PreTransaction hook stays unchanged.
- Removal: `pre_remove` stops the service on removal and does nothing on upgrade (pacman runs `pre_remove` only for a real removal,
  and the test states it); `post_remove` reloads the bus (policy gone) and systemd where no hook does, keeps the state directory
  and the account, and prints the notice of F43/F44 byte for byte (`packaging/deb/postrm`, `packaging/rpm/postun`), on stderr with stdout empty. No other script touches the state directory or the account.
- No script touches the state directory, and none widens the bus policy, polkit action or unit hardening.
- `just test-scripts`: stubbed test of `post_install`, `post_upgrade`, `pre_remove`, `post_remove` (and the `pre_*` account part) on a
  temporary root, like `test-deb-lifecycle.sh` and `test-rpm-lifecycle.sh`; static test with the state-path allowlist; real-pacman
  test in the Arch image of the F42 test (needs a container engine; `CUSTODIO_SKIP_ARCH_INSTALL=1` skips it with a message, as in F42).
- Package gates, fixture tests and lint lists that assume "Arch has only the four F42 files and no pre/post remove" are updated by
  inverting, not deleting, the assertions. The namcap list is updated only with a reason per entry.

Not here: deb scripts (F43), rpm scriptlets (F44), e2e on real Arch (F45 and later), `docs/install.md` (F51), any change to the bus
policy, polkit action or unit hardening, and the F42 check text (stays byte-identical to `packaging/bus-check.sh`).

Size: about seven steps; no split needed.

## Steps
- [ ] Read SPEC section 2, `packaging/arch/*`, `contracts/F42.md`, `F43.md`, `F44.md`, their `docs/decisions.md` entries and the
      F43/F44 test headers; research the Arch hooks (see Scope) and write the findings. Decide in the header of
      `scripts/test-arch-lifecycle.sh` the exact stubbed calls per script and action (install, upgrade, remove) and which are left
      to hooks. Record the choices a later session could undo (hook vs script per call, restart mechanism, notice stream) in
      `docs/decisions.md`.
- [ ] Write the failing `scripts/test-arch-lifecycle.sh` (temporary root, logging stubs, populated state directory with a hidden file,
      a symlink and a 0600 key file; the stubs model `is-active`/`restart` with state) and the install case; add it to `test-scripts`.
- [ ] Failing static test (state-path allowlist with a reason per entry, no enable/start, no writes to policy/action/unit paths) and
      the sysusers sync gate for the Arch scripts, wired into `check` and `test-scripts`.
- [ ] `pre_install`/`pre_upgrade`: F42 check unchanged, then the account. `post_install`/`post_upgrade`: reloads, catalog and the
      restart as decided, never enable or start.
- [ ] `pre_remove`/`post_remove` and, if decided, the extra hook; wire everything in `packaging/nfpm.yaml`.
- [ ] Update the package gates, fixture tests, parity and lint lists (namcap) for the new files; `check-bus-check-sync` still passes.
- [ ] Real-pacman proof in the Arch image: install, upgrade between two builds of this tree (version override), remove; then run
      `verify` and every item of the evidence.

## Evidence
(Research notes, settled in the first step (hook research) before any test is written: how the real run makes calls of the systemd hooks visible, since they may call
`/usr/bin/systemctl` by absolute path and skip in a chroot or when systemd is not booted, otherwise the duplication counts see zero
hook calls; whether Arch's `dbus` package ships its own reload hook; and the grep gates must not ban `set-property` outright if a
restart-marker hook turns out to be the mechanism.)
- Hook research is real → `docs/findings.md` F58 section → lists each hook with its name, `When`, trigger and the command that showed
  it (file read from the pinned Arch image or archive); a test or check that the per-call decision table in `docs/decisions.md`
  names every call of the evidence below. Reviewer can re-run the quoted command.
- Install creates the account from the sysusers file before the bus policy exists → real `pacman -U` in the Arch image with the
  account check done in `pre_install`'s time (a `systemd-sysusers` wrapper recording whether
  `/etc/dbus-1/system.d/com.rfirma.Custodio1.conf` or its packaged path already exists) → "absent"; the account is in `/etc/passwd`
  afterwards. A mutant moving creation to `post_install` makes the record say "present" and fails the test, which runs the mutant.
  Stub case: `pre_install` logs `systemd-sysusers` before any other effect after the bus check.
- Embedded sysusers content equals `data/sysusers.d/custodio.conf` → sync gate run from `check` and `test-scripts`; a mutated copy
  in the `pre_install` or `pre_upgrade` fails it.
- Account failure is loud → stub `systemd-sysusers` exiting non-zero, and the tool missing → script exits non-zero with a stderr
  message naming the tool and nothing created; a mutant with `|| true` fails; the real-pacman case records what pacman does with
  that status (installs anyway, per F42 findings; recorded for `pre_upgrade` too) and that the message shows.
- Failed bus check on a first install still creates the account first → stub case and real `pacman -U` with a bus lacking
  ProcessFD → the sysusers wrapper (log each call with its caller; assert on the one from `pre_install`, naming the packaged policy
  path `/usr/share/dbus-1/system.d/com.rfirma.Custodio1.conf`) records "absent", the account exists afterwards, the F42 message still
  shows, and the script's exit status is the check's (non-zero); a mutant that exits right after the check fails.
- Install does daemon-reload, reloads the bus, updates the catalog, without duplicating hooks → stub case on the four scripts plus the
  real-pacman run (with the real systemd hooks present in the image) → across scripts and hooks, `daemon-reload`, the bus reload and
  `journalctl --update-catalog` each happen at least once and after the files are unpacked, and the calls a hook does are NOT also in
  the scripts (log of a real run, counted: each exactly once; a script that repeats a hook's call fails). The bus reload comes after
  the daemon reload.
- Install never enables or starts → stub case and real run → no `enable`, `start`, `restart`, `preset` to `systemctl`; mutant adding
  `enable` fails; the unit is inactive and disabled after the real install.
- Install never touches the state directory → stub case with a populated state directory and with none (not created) → tree listing
  with content hash, owner, mode, mtime identical; no command in the log has a path under it; real run likewise.
- Upgrade keeps state and account → stub `upgrade` case (`pre_upgrade`, `post_upgrade`) and real upgrade between two builds →
  state tree identical; no account removal call; uid of `custodio` unchanged; a stub passwd that already has the account (M1 or
  earlier install) → `pre_upgrade` exits 0, no second creation error.
- Upgrade restarts once, after the new files, the daemon reload and the bus reload, only if running → stub cases with `is-active`
  active/inactive, and real pacman upgrade in the image with a stub `systemctl` that logs calls with a sequence number across
  scripts and hooks → active: exactly one restart, with a higher sequence number than the daemon-reload and the bus reload and
  after unpacking; inactive: none, no start; first install: none; a mutant restarting unconditionally or before the daemon-reload fails.
  Stub case for a truly missing marker (if the mechanism uses one) with the stub active, written down as a tested outcome: no start, exit 0,
  and the first upgrade from today's F42-era package behaves exactly as the lines above: active gives one restart in the stated
  order, inactive none and no start, exit 0.
- Upgrade does not stop the service → `pre_remove` is not run on a real upgrade (log of the real run), and the stub case `pre_remove`
  with upgrade semantics (as pacman never calls it) is not claimed; no `stop` in the real upgrade log.
- Removal stops the service, keeps state and account, prints the notice → stub `remove` case and real `pacman -R` → stop in the log;
  state tree identical; packaged files gone; account still in `/etc/passwd`; no `userdel`, no `rm`/`chown`/`chmod`/`cp`/`cat` on the
  state path; the notice is on stderr with stdout empty (captured separately) and its three lines are byte-identical to the deb `postrm` and rpm `postun` notice
  (one comparison; a mutant changing one word fails); mutant deleting the directory fails; the bus reload and the daemon reload happen after the policy is gone and
  are not duplicated with the hook; the service is not left running (stub state after `post_remove`).
- Purge-like removal (`pacman -Rns`) behaves as remove → real `-Rns` → same assertions (pacman has no purge; the notice still prints
  and state stays; the test states it).
- No script deletes, chowns, chmods, reads, copies or prints anything under the state directory → static gate over all Arch scripts
  and hook files for `/var/lib/custodio`/`StateDirectory`, allowlist of exact lines with a reason; plus runtime stubs failing when
  called with that path; control test with a deliberately bad script (`rm -rf /var/lib/custodio`) must fail the tree comparison.
- Scripts and hooks do not widen bus policy, polkit action or unit hardening → grep gate: no write, sed, cp, install, tee onto those
  paths in any Arch script or hook; the existing unit-hardening, bus-policy and polkit gates in `check` still pass.
- F42 check and PreTransaction hook kept → `check-bus-check-sync.sh`, `test-bus-check*.sh`, `test-install-real.sh` pass unchanged; the
  hook file `custodio-bus-check.hook` content is unchanged and the package still lists it.
- Failures tolerated only where intended → stubs with `systemctl` failing and no systemd running → `post_*` exit 0 (reloads tolerate
  failure); only the account step in `pre_*` fails loud.
- Every stub case runs against the real tree → the scripts run in a root (user namespace or chroot, or via a root variable); the
  control test above proves it; the header states what the stubs cannot cover (a real running systemd), left to F45.
- Package contents and lint → `just package && just package-lint` → the Arch `.INSTALL` of the built package defines `pre_install`,
  `post_install`, `pre_upgrade`, `post_upgrade`, `pre_remove`, `post_remove` (checked by extracting it with `bsdtar`); any new hook file
  is in the package with mode 0644; `check-parity` agrees with the deb and rpm on shared paths (or the exception list gives a reason);
  namcap shows no new finding outside the list with reasons.
- Gate tests updated, not weakened → `test-package-scripts.sh` and related fixtures now assert the six functions (at least `test-package-scripts.sh` lines for the fourteen-file count and the function list) (the old "no
  remove scripts" assertion inverted); the number of assertions does not drop (diff reviewed in the evaluator pass).
- Whole feature → `just check && just test-scripts && just package && just package-lint` → all pass.
