# F30 — Research the M1 open questions that do not need the manual clients

## Scope
Documentation only: `docs/findings.md` gains one section, `## M1 open questions: login type, caller
detail, refused calls` (the heading contains `M1`, as `verify` requires), with three subsections. No
code, test, unit, SPEC or features.json change; code that follows from the answers is not part of
this feature, so the section ends with "Follow-ups" (a list for later features, not done here).
Open questions of SPEC.md answered: Security officer login, More caller detail, Calls refused before
authorization. Not answered here (need the manual clients): repeated login, LibreOffice PIN prompt,
LibreOffice ECDSA, rFirma build, volatile journals.

Every claim carries **verified** (read in source, docs, a release note, or run here; say which, with the
version or branch and date) or **inferred**, as the rest of the file does. Outside material is read by
subagents that return conclusions with file and line pointers; I check the pointers that carry a
conclusion. Experiments run here are described with the command and the observed result.

Subsections:
1. **`CKU_SO`.** Open question: does any client *ever* send `C_Login(CKU_SO)`, and from which option
   or code path. No answer is assumed before the source is read. Method, per tree, with the commit or
   tag and the date read recorded in the section header (as the file's header does for the other
   trees):
   - **NSS** at `NSS_3_110_RTM`: grep the whole tree for `CKU_SO`; list every call site (file, function;
     expected to include `PK11_InitPin` in `lib/pk11wrap/pk11auth.c`, to be confirmed) with the callers
     that reach it (for example `PK11_NeedUserInit` users, Firefox's "set primary password" flow,
     `modutil -changepw`, `certutil -W`), each traced to its entry point.
   - **LibreOffice** and **Firefox** (the NSS consumers): which of those NSS paths they call. Then read
     our token flags in `crates/custodio-pkcs11` (`CKF_USER_PIN_INITIALIZED`, `CKF_LOGIN_REQUIRED`,
     `CKF_PROTECTED_AUTHENTICATION_PATH`) and state whether they keep both clients off the
     `CKU_SO` path (`PK11_NeedUserInit` is false when the flag is set; check that reading).
   - **pkcs11-provider** and **OpenSC** (`pkcs11-tool`, plus `pkcs11-spy`): grep each tree for `CKU_SO`
     and name the option or code path behind every hit; for `pkcs11-tool` at least `--login-type so`,
     `--init-pin`, `--so-pin`, `--change-pin --login-type so`, and any other hit the grep shows.
   - **rFirma**: the source we can read; if unavailable, say "not read" and mark inferred.
   - What our module returns today for `CKU_SO` (read `C_Login` in `crates/custodio-pkcs11`) and a
     recommendation (fail with `CKR_USER_TYPE_INVALID` or equivalent, or succeed), with the effect on
     each client path found.
2. **Caller detail.** What `GetConnectionCredentials` returns on the daemon each target actually ships
   by default, at the shipped version: Debian and Ubuntu default to dbus-daemon, Fedora, RHEL/Alma
   and Arch to dbus-broker. Per-target table: release, default daemon, version, kernel, and for each
   key (`UnixUserID`, `ProcessID`, `ProcessFD`, `LinuxSecurityLabel`, `UnixGroupIDs`,
   `AdtAuditSessionData`) present/absent at that version, from the daemons' NEWS or source at the
   tag. Versions come from the Repology API, dated, as section 3 of the file does (reuse and cite
   section 3's table where the date is the same). A key such as `ProcessFD` counts as present only if
   it is present in the shipped version. Then, for each candidate (pidfd, security label,
   exe/cmdline/cgroup via `/proc/<pid>`), whether the service can use it under `ProtectProc=invisible`
   + `ProcSubset=pid` (read `data/custodio.service`; systemd.exec docs for what those hide; whether a
   pidfd lets `/proc/self/fdinfo` or `pidfd_getpid`-style reads work without `/proc/<pid>` access;
   whether `CAP_SYS_PTRACE`/`hidepid` would be needed). State the kernel minimum each pidfd path
   needs (`SO_PEERPIDFD` 6.5+, `pidfd_open` 5.3+, `PIDFD_GET_INFO` and the rest as found) against
   each target's kernel. Options that need loosening the unit are listed and rejected. The exposure
   gate (SPEC.md:301, "without loosening the exposure gate") is shown untouched; see Evidence.
   Recommendation: what to add to the entry, and what to drop.
3. **Refused calls and journald rate limit.** journald's per-service limits (`RateLimitIntervalSec`,
   `RateLimitBurst`, per-unit scope, `LogRateLimit*` unit overrides, how a dropped burst is reported:
   the "Suppressed N messages" entry) from journald.conf(5), systemd.exec(5), and `docs/audit.md`
   (stay consistent). The burst is not a fixed 10000: journald.conf(5) scales `RateLimitBurst=` by
   the free space of the journal's filesystem. Read and record that scaling (the multiplier steps
   and the free-space thresholds, from the man page for the systemd version used, and the source if
   the page is vague), and compute the budget for this machine's journal filesystem and for a
   typical small one; the "default budget" in the comparison uses those numbers, not 10000. Measure on
   this machine, if `systemd-run` and journald are usable (else mark not measured): a transient unit
   with a low `LogRateLimitBurst=` (a unit override is per unit, which is the scope the measurement
   shows) logging N entries via `logger`/`systemd-cat`, then count entries kept and the suppression
   notice. Record the full `systemd-run` command line and `systemctl --version`. State what a
   flood of refused calls (unauthenticated local processes, no polkit dialog) would do to
   authorized-call entries given that budget and the service's own request rate. Compare the three
   options (no entry, per-call entry, aggregate) and recommend one, with what an aggregate would
   carry (count, time window, uid) and whether it needs its own rate or timer.
