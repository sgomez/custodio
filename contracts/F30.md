# F30 — Research the M1 open questions that do not need the manual clients

## Scope
Documentation only: `docs/findings.md` gains one section, `## M1 open questions: login type, caller
detail, refused calls` (the heading contains `M1`, as `verify` requires), with three subsections. No
code, test, unit, SPEC or features.json change; code that follows from the answers is not part of
this feature, so the section ends with "Follow-ups" (a list for later features, not done here).
Open questions of SPEC.md answered: Security officer login, More caller detail, Calls refused before
authorization. Not answered here (need the manual clients): repeated login, LibreOffice PIN prompt,
LibreOffice ECDSA, rFirma build, volatile journals.

Every claim carries **verified** (read in source, docs, a release note, or run here; say which, with the
version or branch and date) or **inferred**, as the rest of the file does. Outside material is read by
subagents that return conclusions with file and line pointers; I check the pointers that carry a
conclusion. Experiments run here are described with the command and the observed result.

Subsections:
1. **`CKU_SO`.** For each of rFirma (the repo/source we can read; if unavailable, say "not read"
   and mark inferred), LibreOffice/NSS (`pk11auth`/`PK11_Authenticate`/`PK11_CheckUserPassword` paths, which
   only use `CKU_USER`), pkcs11-provider, and `pkcs11-tool` (`--login-type so` exists): does it ever send
   `C_Login(CKU_SO)`, and under what option. Also what our module returns today for `CKU_SO`
   (read `crates/custodio-pkcs11`) and a recommendation (fail with `CKR_USER_TYPE_INVALID` or
   equivalent, or succeed), with the effect on each client.
2. **Caller detail.** What `GetConnectionCredentials` returns on dbus-daemon 1.16 and dbus-broker 37 for
   the supported targets (Debian 13, Ubuntu 25.10+, Fedora 41+, RHEL/Alma 10, Arch): keys
   (`UnixUserID`, `ProcessID`, `ProcessFD`, `LinuxSecurityLabel`, `UnixGroupIDs`, `AdtAuditSessionData`),
   which are present per daemon and since which version. Then, for each candidate (pidfd, security
   label, exe/cmdline/cgroup via `/proc/<pid>`), whether the service can use it under
   `ProtectProc=invisible` + `ProcSubset=pid` (read `data/custodio.service`; systemd.exec docs for
   what those two settings hide; whether a pidfd lets `/proc/self/fdinfo` or `pidfd_getpid`/`SO_PEERPIDFD`-style
   reads work without `/proc/<pid>` access; whether `CAP_SYS_PTRACE`/`hidepid` would be needed). Keep
   to what is possible without loosening the unit; state which options need loosening and are rejected.
   Recommendation: what to add to the entry, and what to drop.
3. **Refused calls and journald rate limit.** journald's per-service limits (`RateLimitIntervalSec`,
   `RateLimitBurst` defaults 10000 msgs per 30 s, per-unit scope, `LogRateLimit*` unit overrides,
   and how a dropped burst is reported: the "Suppressed N messages" entry) from the journald.conf and
   systemd.exec man pages, and `docs/audit.md` (which already mentions it; stay consistent). Measure
   on this machine, if `systemd-run` and journald are usable (else mark not measured): a throwaway
   transient unit logging N entries via `logger`/`systemd-cat` with a low `LogRateLimitBurst`, then
   count entries kept and the suppression notice; and state what a flood of refused calls
   (unauthenticated local processes, no polkit dialog) would do to authorized-call entries given
   the default budget and the service's own request rate. Compare the three options (no entry,
   per-call entry, aggregate) and recommend one, with what an aggregate would carry (count, time
   window, uid) and whether it needs its own rate or timer.
