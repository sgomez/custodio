# F184 — Packaging: modutil dependency, the per-user refresh trigger, and the snap-base gate

## Scope
Three packaging pieces, each with a script gate. Built in this order; no Rust change is expected (the refresh-only
mode is `custodio register --refresh-only`, F183, and its journal entry is F183's).

1. **modutil dependency.** `packaging/nfpm.yaml` gains `modutil`'s package as a run-time dependency of each format under
   its name: `libnss3-tools` (deb), `nss-tools` (rpm), `nss` (Arch). The names are the F172 Decision (all verified there);
   they go into the table of `scripts/package_expected.py` that `check-packages` already reads, so the package gate
   (`scripts/check-packages.sh`) sees them too. `scripts/check-register-deps.sh` compares that table with
   `packaging/nfpm.yaml` for the three formats, fails naming the format and package when one is missing, misspelled,
   given under another format's name or left out of one format, and fails when the nfpm file declares one the table lacks.
   `scripts/test-check-register-deps.sh` runs it on fixture nfpm files (no nfpm run, no package build).
2. **Per-user refresh trigger.** The package ships, in every format, systemd user units that run
   `custodio register --refresh-only` (a) at login and (b) when the installed module changes, and enables them for every
   user, so no user has to run anything (SPEC Design 4, "decided"). The units' file names, and whether a path unit plus a
   service or a service plus a path unit's `PathChanged`/`PathModified`, are the builder's. "Enabled for every user" must
   take effect from the installed files alone: a symlink in `/usr/lib/systemd/user/default.target.wants/` (or the
   `paths.target.wants/` of the path unit's target) shipped in all three formats. A preset file alone is not enough (it
   enables nothing for existing users without a `systemctl --global preset` step) and a maintainer-script step that can
   fail an install, or one needing `systemctl --user` at install time, is not allowed.
   Hardening: the unit sets only directives the test can exercise. Running the `ExecStart` arguments outside systemd
   ignores `ProtectHome=`, `ProtectSystem=`, `ReadWritePaths=` and `PrivateNetwork=`, so the test proves them statically:
   if the unit has `ProtectHome=` (other than `no`), `ProtectSystem=` (other than `no`) or `TemporaryFileSystem=`, it must
   have a `ReadWritePaths=` (or `BindPaths=`) that covers `%h/snap/firefox/common`; a negative control removes that line
   and must fail. `NoNewPrivileges=` and `PrivateNetwork=` need nothing writable and are checked only to be well-formed by
   `verify`. Anything else that restricts what the command can reach is left out.
   The unit's output reaches the user's journal through stderr (the command's own journal datagram goes to
   `/run/systemd/journal/socket` of the user's system); the unit's comment says so.
   `scripts/package_expected.py` lists every new file with its mode (and symlinks if used), so `check-packages`,
   `check-parity` and the lints see them; `packaging/parity-exceptions.txt` gets no new line (the files are in all
   three). The lint lists (`packaging/lint/*.txt`) change only for a finding the new files cause, each with a reason; the
   linters run at the checkpoint, not here, so a list entry needs the finding's source (a run of the linter on the
   built package) or is not added.
   `scripts/test-user-refresh-units.sh` checks the units from the source tree (and, that the link targets exist):
   `systemd-analyze verify` on them, that the login trigger and the change trigger exist, that they are enabled for every
   user, that the hardening is writable where needed, and that the service's `ExecStart` runs `/usr/bin/custodio` (the
   static check is the binary path only; the argument list is proven once, by the run below). Acceptance 12 ("the units pass `systemd-analyze verify` and run the refresh mode") ends here.
   **Probe of `systemd-analyze verify` in the dev container** (run in this session): `systemd-analyze --user verify X.service`
   exits 1 with "Failed to lookup RuntimeDirectory path" unless `XDG_RUNTIME_DIR` is a temporary directory of mode 0700;
   with `XDG_RUNTIME_DIR=$(mktemp -d)` (chmod 700) it works, but a unit with `Bogus=1` under `[Service]` still exits **0**
   and prints `Unknown key 'Bogus' in section [Service], ignoring.` on stderr. So the test runs
   `XDG_RUNTIME_DIR=<temp 0700> systemd-analyze --user verify <units>`, captures stderr and stdout, and fails when the exit
   code is non-zero **or any output at all appears**. The "bad directive" control is a unit with `Bogus=1` and must fail
   through that output rule (a control that only checks the exit code would pass, so the control also asserts the exit code
   was 0, proving the output rule is what caught it).
   **Second probe (the binary is absent):** `/usr/bin/custodio` does not exist in the dev container, so
   `systemd-analyze --user verify` on the shipped service exits 1 with `Command /usr/bin/custodio is not executable: No such
   file or directory`, even though the unit is right. `--root=<dir>` does not help: with `--user` it fails with "Failed to
   initialize unit search paths ... Invalid argument" (systemd 257). What works (run by the evaluator): copy the unit into a
   temp dir and replace `/usr/bin/custodio` in `ExecStart` with an executable stub in that dir; verify then exits 0 with no
   output, also with `ProtectSystem=strict` and `ReadWritePaths=%h/...`; a path unit with `PathChanged=` on the missing
   module also verifies with no output. So the test runs `verify` on **copies** in a temp dir in which only the binary path
   is replaced by the stub, and for each copy it checks that the copy differs from the shipped unit in that one token only
   (the shipped text with every `/usr/bin/custodio` replaced by the stub path equals the copy, and the shipped file's other
   lines are untouched), so the substitution cannot hide anything else. Units without that token are copied as they are
   and compared byte for byte. The `Bogus=1` control is built on such a copy too.
   Proven at the checkpoint, not here: the units inside the built `.deb`, `.rpm` and Arch package (`just package-gates`), a
   real login and a real module replacement on a VM. The part of acceptance 12 about the command, stale copies and the
   journal entry is F183's.
3. **Snap-base gate.** `packaging/snap-bases.txt` records the base of the Firefox snap's stable channel and its glibc, in
   the format of `packaging/glibc-ceiling.txt` (header, `base = NAME | GLIBC | SOURCE` lines, the sources being
   F171's measurements: `docs/findings/F171.md`, `meta/snap.yaml`, `ldd --version` inside `snap run --shell firefox`),
   plus the shared libraries the base provides that the module may need, each with its source. F171 recorded core26,
   glibc 2.43, rev 9181. `scripts/check-snap-base.sh` (the recipe `just snap-base-fit`, added to `package-gates`) reads
   the shipped `libcustodio_pkcs11.so` from the `.deb` in `target/packages` or from an ELF path given to it (the module is
   the same file in all three packages; `check-parity` proves it, not this feature) and fails when it needs a `GLIBC_x.y` above the base's glibc or a
   `NEEDED` library the base file does not list, naming the symbol or library and the base. Which libraries the base is
   known to provide is a research step: if a download of the core26 snap or a table of its files is possible in the dev
   container, the list comes from it; if not, the list is limited to what F171's in-snap runs showed (**verified**) and the
   rest is **inferred**, so the gate is conservative: a library the file does not list fails it.
   `scripts/test-snap-base-fit.sh` builds fixture ELF files with `gcc` (as `test-glibc-ceiling.sh` does) and proves the
   gate passes on one that fits the recorded base and fails on one above it by symbol version (acceptance 13) and on one
   with a needed library the base lacks; it runs `check-snap-base.sh` on a fixture package directory, not the real one.
   The gate on the real module is proven at the checkpoint (`just package-gates`) and by `verify` only through the
   fixture test; the step that adds the recipe also runs the script by hand against the freshly rebuilt release module (no step runs
   `just package`; that is the checkpoint's).
   The glibc ceiling gate (`packaging/glibc-ceiling.txt`) stays as it is; this gate is a second, independent one.

Left for other features: the README text (F185), `docs/install.md` (F186), the VM snap run (F187), the
changelog for the release, any change to the registration command.

**Costs.** `test-check-register-deps.sh`: pure shell and python on small fixture files, under 5 s. `test-user-refresh-units.sh`:
`systemd-analyze verify` on three or four unit files plus negative controls, each under a second, about 5 s, **plus
the build of `custodio-cli`**: `target/debug/custodio-cli` does not exist in a fresh tree and `test-scripts` gives no
ordering guarantee, so the script builds it itself (`cargo build -p custodio-cli --locked`, with `timeout`). A warm
tree makes that about 1 s; a cold one is a full debug build of the crate and its dependencies (the builder measures it
and states it in PROGRESS.md; it is the one long cost of this feature). Cargo's build-directory lock serialises it
against other cargo runs in `test-scripts`; it runs concurrently with the other script tests. If the cold build does not
fit `script * 120` in `budgets.tsv`, the builder asks for a bigger budget in BLOCKED.md. `test-snap-base-fit.sh`:
three or four `gcc` links of small ELF files and `readelf` calls, about 5 s (`test-glibc-ceiling.sh` is the same shape).
The register-deps and user-units tests join `test-scripts`; the snap-base one joins `package-gate-test` (it uses `gcc`
and the fixture library `scripts/lib/package-fixtures.sh` like the glibc test); they run in parallel with the others.
No unit test, no e2e case, no VM, no package build is added. The `snap-base-fit` recipe adds one `readelf` pass over one
file to `package-gates`: well under 1 s.

## Evidence
- modutil is a run-time dependency of every format under its name (F172) → `scripts/check-register-deps.sh` on the real
  `packaging/nfpm.yaml` → exit 0; and `scripts/test-check-packages-deps.sh` → passes with the new names in the fixture packages.
- `check-register-deps` compares with `nfpm.yaml`, with negative controls → `scripts/test-check-register-deps.sh` → passes;
  controls: dependency missing in one format (three cases, one per format), wrong name (`nss-tools` in the deb),
  a name that belongs to another format, a name present only in a comment or in another section than that format's
  `depends` (no pass), a name with a version it should not have if the table has none; each fails with the format and
  the package named.
- The package ships user units, enabled for every user, that run the refresh-only mode at login and when the installed
  module changes → `scripts/test-user-refresh-units.sh` → passes: `systemd-analyze verify` (user mode, temp `XDG_RUNTIME_DIR`, any output fails) is clean on each stub-binary copy of a unit, and each copy differs from the shipped unit only in the binary path, the enablement is a symlink in a `*.wants/` directory of `/usr/lib/systemd/user/` whose target exists, a login
  trigger and a change trigger exist (the path watched is `INSTALLED_MODULE`, the same constant the command uses; the
  test compares with the string of `register_native.rs`), the hardening check above holds, the `ExecStart`
  line's binary is `/usr/bin/custodio`. Negative controls as in Steps; each exits non-zero with its cause.
- The service runs the refresh mode (acceptance 12, trigger part) → same script: it takes the `ExecStart` line of the
  service, replaces the binary `/usr/bin/custodio` with `target/debug/custodio-cli`, and, because
  `/usr/lib/custodio/libcustodio_pkcs11.so` (`INSTALLED_MODULE`) does not exist in the container, adds
  `--module <fixture module>`; the test asserts that, with those two changes undone, the argument list is exactly
  `register --refresh-only` (so nothing else in the line is altered). It runs with a temp `HOME` holding a stale copy in
  `snap/firefox/common/...`, and the copy is replaced by the fixture. `/run/systemd/journal/socket` does not exist in the
  container (probed), so the journal outcome is read from the command's stderr/stdout (what F183 prints when the journal is
  unreachable plus its normal outcome line); this is stated, not a skip. The hardening directives are proven by the static
  check above, since this run is outside systemd. If the run cannot work for a reason found while building, the builder
  amends this line with the evaluator's approval; no silent skip.
- `scripts/package_expected.py` lists the new files → `scripts/test-check-packages.sh` and `scripts/test-check-parity.sh`
  → pass on fixture packages that carry them; a fixture without one of the new files fails the gate naming it
  (one negative control).
- The snap base and its glibc are recorded with sources (F171) → `scripts/test-snap-base-fit.sh` reads
  `packaging/snap-bases.txt` and fails when a `base` line lacks glibc or a source (negative control on a fixture file); the
  file's values equal F171's (core26, 2.43) — checked by the script against `docs/findings/F171.md`'s own table line (the cell reads `2.43-2ubuntu2.4 (...)`: the script parses the leading `MAJOR.MINOR` out of it and compares that with the recorded glibc, never the whole cell), so the
  two cannot drift (a code-versus-data check, not a prose grep: the line is data the finding records).
- The gate fails on a module whose ELF requirements exceed the base (acceptance 13) → `scripts/test-snap-base-fit.sh`:
  fixture ELF needing `GLIBC_` the recorded glibc plus one minor → gate exits non-zero naming the symbol and the base; a
  fixture needing a `NEEDED` library the base lacks → non-zero naming the library; a fixture that fits → exit 0.
  The fixtures are real `gcc` output; the "above" one is a real `.symver` reference to a version number above the file's
  recorded glibc, or the recorded glibc in a fixture file is set below the host's (as `test-glibc-ceiling.sh` does).
- The gate passes on the shipped module → the step rebuilds the module with
  `cargo build --release -p custodio-pkcs11 --locked` and always runs `scripts/check-snap-base.sh` on the fresh
  `target/release/libcustodio_pkcs11.so` (the gate takes an ELF path too): exit 0. The `.deb` in `target/packages` is not
  used, as it may predate this commit's module. Proven on the built packages at the checkpoint (`just package-gates`).
- `just snap-base-fit` is in `just package-gates` → `just --dry-run package-gates` lists `snap-base-fit` (a command, not a
  grep of the file) and `just snap-base-fit` runs the script.
- `just quick` green, and `scripts/test-shell-scripts.sh` lists the new scripts as linted.
