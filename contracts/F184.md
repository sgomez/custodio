# F184 — Packaging: modutil dependency, the per-user refresh trigger, and the snap-base gate

## Scope
Three packaging pieces, each with a script gate. Built in this order; no Rust change is expected (the refresh-only
mode is `custodio register --refresh-only`, F183, and its journal entry is F183's).

1. **modutil dependency.** `packaging/nfpm.yaml` gains `modutil`'s package as a run-time dependency of each format under
   its name: `libnss3-tools` (deb), `nss-tools` (rpm), `nss` (Arch). The names are the F172 Decision (all verified there);
   they go into the table of `scripts/package_expected.py` that `check-packages` already reads, so the package gate
   (`scripts/check-packages.sh`) sees them too. `scripts/check-register-deps.sh` compares that table with
   `packaging/nfpm.yaml` for the three formats, fails naming the format and package when one is missing, misspelled,
   given under another format's name or left out of one format, and fails when the nfpm file declares one the table lacks.
   `scripts/test-check-register-deps.sh` runs it on fixture nfpm files (no nfpm run, no package build).
2. **Per-user refresh trigger.** The package ships, in every format, systemd user units that run
   `custodio register --refresh-only` (a) at login and (b) when the installed module changes, and enables them for every
   user, so no user has to run anything (SPEC Design 4, "decided"). The units' file names, whether a path unit plus a
   service or a service plus a path unit's `PathChanged`/`PathModified`, and the way "enabled for every user" is done
   (symlinks in the package's `*.wants/` directory, or a preset) are the builder's; the way must work in all three
   formats without a maintainer-script step that can fail an install, and must not depend on `systemctl --user` being
   reachable at install time. The unit hardens what a user unit can (no network, no new privileges, a read-only
   filesystem apart from the user's `~/snap/firefox/common` that the command writes) only so far as the command still
   works: the test proves the command runs under the unit's own `ExecStart` line. The unit's output reaches the
   user's journal (stderr, the command's own journal datagram, or both; the builder says which in the unit's comment).
   `scripts/package_expected.py` lists every new file with its mode (and symlinks if used), so `check-packages`,
   `check-parity` and the lints see them; `packaging/parity-exceptions.txt` gets no new line (the files are in all
   three). The lint lists (`packaging/lint/*.txt`) change only for a finding the new files cause, each with a reason; the
   linters run at the checkpoint, not here, so a list entry needs the finding's source (a run of the linter on the
   built package) or is not added.
   `scripts/test-user-refresh-units.sh` checks the units from the source tree (and, if the files are installed by
   symlink, that the link targets exist): `systemd-analyze verify` on them, that the login trigger and the change trigger
   exist, that they are enabled for every user, and that the service's `ExecStart` is the refresh-only mode of
   `/usr/bin/custodio`. Acceptance 12 ("the units pass `systemd-analyze verify` and run the refresh mode") ends here.
   Proven at the checkpoint, not here: the units inside the built `.deb`, `.rpm` and Arch package (`just package-gates`), a
   real login and a real module replacement on a VM. The part of acceptance 12 about the command, stale copies and the
   journal entry is F183's.
3. **Snap-base gate.** `packaging/snap-bases.txt` records the base of the Firefox snap's stable channel and its glibc, in
   the format of `packaging/glibc-ceiling.txt` (header, `base = NAME | GLIBC | SOURCE` lines, the sources being
   F171's measurements: `docs/findings/F171.md`, `meta/snap.yaml`, `ldd --version` inside `snap run --shell firefox`),
   plus the shared libraries the base provides that the module may need, each with its source. F171 recorded core26,
   glibc 2.43, rev 9181. `scripts/check-snap-base.sh` (the recipe `just snap-base-fit`, added to `package-gates`) reads
   the shipped `libcustodio_pkcs11.so` from the `.deb` in `target/packages` (the module is the same file in all three
   packages; `check-parity` proves it, not this feature) and fails when it needs a `GLIBC_x.y` above the base's glibc or a
   `NEEDED` library the base file does not list, naming the symbol or library and the base. Which libraries the base is
   known to provide is a research step: if a download of the core26 snap or a table of its files is possible in the dev
   container, the list comes from it; if not, the list is limited to what F171's in-snap runs showed (**verified**) and the
   rest is **inferred**, so the gate is conservative: a library the file does not list fails it.
   `scripts/test-snap-base-fit.sh` builds fixture ELF files with `gcc` (as `test-glibc-ceiling.sh` does) and proves the
   gate passes on one that fits the recorded base and fails on one above it by symbol version (acceptance 13) and on one
   with a needed library the base lacks; it runs `check-snap-base.sh` on a fixture package directory, not the real one.
   The gate on the real module is proven at the checkpoint (`just package-gates`) and by `verify` only through the
   fixture test; the step that adds the recipe also runs the script by hand against a package built in step 5 of
   this session if `target/packages` has one (a `just package` run is not part of any step: it is the checkpoint's).
   The glibc ceiling gate (`packaging/glibc-ceiling.txt`) stays as it is; this gate is a second, independent one.

Left for other features: the README text (F185), `docs/install.md` (F186), the VM snap run (F187), the
changelog for the release, any change to the registration command.

**Costs.** `test-check-register-deps.sh`: pure shell and python on small fixture files, under 5 s. `test-user-refresh-units.sh`:
`systemd-analyze verify` on three or four unit files plus negative controls, each a separate file, run one after another
only because each is under a second; about 5 s in total. `test-snap-base-fit.sh`: three or four `gcc` links of small
ELF files and `readelf` calls, about 5 s (`test-glibc-ceiling.sh` is the same shape). All three are script tests
that join `test-scripts` (the register-deps one and the user-units one) and `package-gate-test` (the snap-base one, which
uses `gcc` and the fixture library `scripts/lib/package-fixtures.sh` like the glibc test), so they run in parallel with the
others; all fit the `script * 120` budget. No unit test, no e2e case, no VM, no package build is added. The `snap-base-fit`
recipe adds one `readelf` pass over one file to `package-gates`: well under 1 s.

## Evidence
- modutil is a run-time dependency of every format under its name (F172) → `scripts/check-register-deps.sh` on the real
  `packaging/nfpm.yaml` → exit 0; and `scripts/test-check-packages-deps.sh` → passes with the new names in the fixture packages.
- `check-register-deps` compares with `nfpm.yaml`, with negative controls → `scripts/test-check-register-deps.sh` → passes;
  controls: dependency missing in one format (three cases, one per format), wrong name (`nss-tools` in the deb),
  a name that belongs to another format, a name present only in a comment or in another section than that format's
  `depends` (no pass), a name with a version it should not have if the table has none; each fails with the format and
  the package named.
- The package ships user units, enabled for every user, that run the refresh-only mode at login and when the installed
  module changes → `scripts/test-user-refresh-units.sh` → passes: `systemd-analyze verify` is clean on each unit, a login
  trigger and a change trigger exist (the path watched is `INSTALLED_MODULE`, the same constant the command uses; the
  test compares with the string of `register_native.rs`), the enablement is in the package file list, the `ExecStart`
  line runs `/usr/bin/custodio register --refresh-only`. Negative controls as in Steps; each exits non-zero with its cause.
- The service runs the refresh mode (acceptance 12, trigger part) → same script, which also runs the `ExecStart`'s
  arguments with the built `target/debug/custodio` (path substituted, a temp `HOME`, an injected journal socket if the
  command allows one, else the command's stderr) against a stale fixture copy in the temp home, and the copy is replaced.
  If the builder cannot run it without a bus or a home, the test says what it skipped and why, and this line is
  replaced by an amendment the evaluator approves; no silent skip.
- `scripts/package_expected.py` lists the new files → `scripts/test-check-packages.sh` and `scripts/test-check-parity.sh`
  → pass on fixture packages that carry them; a fixture without one of the new files fails the gate naming it
  (one negative control).
- The snap base and its glibc are recorded with sources (F171) → `scripts/test-snap-base-fit.sh` reads
  `packaging/snap-bases.txt` and fails when a `base` line lacks glibc or a source (negative control on a fixture file); the
  file's values equal F171's (core26, 2.43) — checked by the script against `docs/findings/F171.md`'s own table line, so the
  two cannot drift (a code-versus-data check, not a prose grep: the line is data the finding records).
- The gate fails on a module whose ELF requirements exceed the base (acceptance 13) → `scripts/test-snap-base-fit.sh`:
  fixture ELF needing `GLIBC_` the recorded glibc plus one minor → gate exits non-zero naming the symbol and the base; a
  fixture needing a `NEEDED` library the base lacks → non-zero naming the library; a fixture that fits → exit 0.
  The fixtures are real `gcc` output; the "above" one is a real `.symver` reference to a version number above the file's
  recorded glibc, or the recorded glibc in a fixture file is set below the host's (as `test-glibc-ceiling.sh` does).
- The gate passes on the shipped module → `scripts/check-snap-base.sh` on `target/packages` when a package build exists in
  the tree, else `readelf` of `target/release/libcustodio_pkcs11.so` through the gate's python entry (the gate takes an ELF
  path too): exit 0. Proven on the built packages at the checkpoint (`just package-gates`).
- `just snap-base-fit` is in `just package-gates` → `just --dry-run package-gates` lists `snap-base-fit` (a command, not a
  grep of the file) and `just snap-base-fit` runs the script.
- `just quick` green, and `scripts/test-shell-scripts.sh` lists the new scripts as linted.
