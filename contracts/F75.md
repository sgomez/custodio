# F75 — Import leaves one journal entry and fails closed

## Scope
`ImportP12` (`Custodio::import_call`, F73 order: arguments → credentials → own-id check → polkit → decode →
store) gains the journal entry. F74 already defines `OperationEntry::import`, `ImportOutcome`, `AuditKeyType`,
the message id, the catalog entry and `docs/audit.md`; this feature only emits them.

- **When.** Once polkit has been asked, the outcome is known and exactly one import entry is submitted through the
  existing sink, before the reply. Outcomes: `stored`, `denied`, `authorization_unavailable` (polkit `Unavailable`
  or `BadSender`), `wrong_password` (every decoder failure that gives `WrongPasswordOrBadP12`), `unsupported_key`
  (`UnsupportedKeyType`; the builder maps every `ImportError` variant explicitly, including the ones with no
  outcome of their own such as `CertificateMismatch`, to the nearest outcome and says which in the code),
  `storage_failure` (any store error after decoding, including the lost race below). Each entry has the caller's
  uid and pid, the key id, and the key type only when decoding got far enough to know it (`stored`,
  `storage_failure`). Exception, as for sign (`docs/decisions.md`, `docs/audit.md`): a missing sender or a failed
  credentials lookup, once the arguments are valid, leaves one `authorization_unavailable` entry without uid, pid
  and key type, and the call returns `AuthorizationUnavailable` (no polkit, no decoder). The import mapping is
  literal: `Parse`, `NoPrivateKey`, `MultipleKeys`, `NoCertificate` → `wrong_password`; `UnsupportedKey` and
  `CertificateMismatch` → `unsupported_key`; `Store(_)` and `TooLarge` → `storage_failure`; the reply errors keep
  their F73 names (`WrongPasswordOrBadP12`, `UnsupportedKeyType`, `CertificateMismatch`, `KeyIdTaken` for
  `AlreadyExists`, `InvalidArgs` for `TooLarge`, `Internal` otherwise).
- **No entry before authorization (M1's behaviour).** Bad arguments and `KeyIdTaken` from the own-id check return their M1/F73 errors, ask no polkit, call no
  sink and leave no entry (`KeyIdTaken` is a refusal of the caller's own id, like sign's `NoSuchKey`). The builder checks that `docs/audit.md` states this for import (it says it for
  arguments and for sign) and corrects the wording only if it is missing or wrong.
- **Fail closed.** If the sink fails, the call returns `AuditUnavailable` ("audit unavailable") for every outcome.
  For `stored` the key and its certificate are removed again, so the store is as before the call (the store has no
  removal today; the builder adds the narrowest one, used only for this rollback). The key file goes before the
  certificate, so a partial rollback never leaves a key without a certificate. If the removal itself fails the call
  still returns `AuditUnavailable`; the key is not reported as imported. Nothing reports a stored key as done unless
  its entry was submitted.
- **Concurrency.** The loser of two concurrent imports of the same id by the same owner reaches the store after
  polkit, gets the store's `AlreadyExists` and keeps the error `KeyIdTaken`; it leaves one `storage_failure` entry
  (conservative: it passed authorization, so it leaves exactly one entry; no new outcome value). The winner leaves
  one `stored` entry. If the winner's entry fails and its key is rolled back, the loser may also win the id later;
  at no time are there two keys or two `stored` entries.
- **Content.** Never the `.p12` or the password: the entry model already cannot hold them (F74); this feature
  proves it end to end.
- Left for other features: delete and replace certificate entries (F76+, F78+); the entry model, catalog and docs
  (F74, done); polkit order and decoder seam (F73, done); the e2e journal cases with a real agent (F90/F100). Size:
  about five steps; no split.

Environment: nothing beyond the dev container. D-Bus tests use the private `dbus-daemon` of `tests/audit/bus.rs`
and the `MemorySink`/`FailingSink` already in use; no new tool, network or privilege.

## Evidence
All rows are in `tests/import_audit.rs` unless stated; "entry" means what `MemorySink` recorded, decoded with the
journal field accessors, compared to literal expected values.
- Exactly one entry for each outcome, naming operation, uid, pid, key id, key type and outcome →
  `import_entry_per_outcome`: table of six cases (approve → `stored` with `rsa_2048`, and with `ecdsa_p256`;
  polkit deny → `denied`; polkit unavailable and polkit `BadSender` → `authorization_unavailable` with uid/pid;
  a failed credentials lookup and a missing sender → `authorization_unavailable` without uid, pid or key type;
  wrong password → `wrong_password`; an RSA 1024 or other unsupported key `.p12` → `unsupported_key`; a store
  that cannot write → `storage_failure` with the type; the area is made unwritable (mode 0500) by the polkit double
  while it answers, i.e. after the own-id check, which must still succeed). Each asserts `sink.operation_entries().len() == 1` and `sink.entries()` empty,
  `CUSTODIO_OPERATION=import`, the real uid/pid of the test client, the id, `CUSTODIO_OUTCOME`, and the key type
  present exactly for `stored`/`storage_failure` and absent otherwise, and the reply error name. Fails if any
  field, count or outcome mapping is off. Every `ImportError` variant is mapped → unit test in `dbus/tests.rs`
  over all variants comparing with the literal table in Scope (not recomputed from the code).
- Never the `.p12` or the password → `import_entries_hold_no_secrets`: imports with a recognisable password and a
  `.p12` (and its base64/hex), for every outcome above, then scans every recorded entry's fields and `MESSAGE`
  for the password and for byte/base64/hex fragments of the `.p12` and of the certificate; a negative control
  runs the same scan on a deliberately leaking string and must find it → passes.
- Fail closed, stored → `failing_sink_rolls_the_import_back`: approve, `FailingSink`; reply error is
  `AuditUnavailable` with text "audit unavailable"; the store lists nothing for the owner (neither key nor
  `-cert`), the id can be imported again with a working sink and then leaves one `stored` entry, and signing with
  the id before that re-import fails `NoSuchKey`. Fails if the key is kept, or if the sink result is ignored.
- Fail closed, other outcomes → `failing_sink_fails_every_outcome`: for denied, unavailable, wrong password,
  unsupported key and storage failure, the reply is `AuditUnavailable` and the store is unchanged (listing equal
  before and after).
- Rollback is exact → the store unit test above (also: a symlink or foreign-owner file is refused as `get` does), plus `rollback_failure_still_reports_audit_unavailable`: the
  removal is made to fail (the area made unwritable after the put by a sink that does so while recording); the
  reply is still `AuditUnavailable`, never success.
- Refusals before authorization keep M1's behaviour → `import_refusals_leave_no_entry`: bad id, oversized `.p12`,
  oversized password, and an id the caller already has: each gives its F73 error,
  `polkit.asked()` and the decoder counter unchanged (0), and `sink.operation_entries()` and `sink.entries()` empty, also with the
  `FailingSink` (the error is not `AuditUnavailable`, proving the sink is not called). Fails if an entry is
  written earlier.
- Two concurrent imports of the same id by the same owner → `concurrent_imports_leave_one_key_one_success`: two
  clients of the same uid import the same id at once (the async polkit double holds both calls until both
  have asked, so both are past the own-id check and polkit before either stores; no blocking barrier inside the
  synchronous decoder, which would stall the bus executor); repeat in a loop of at least 20 rounds. After each round: `polkit.asked().len() == 2` (both really ran concurrently), the store lists exactly
  one key and one certificate for the id, exactly one `stored` entry in `operation_entries()`, the other call fails `KeyIdTaken` and
  leaves exactly one `storage_failure` entry, total 2 entries. Fails if both succeed, both fail, or an entry is
  missing or doubled.
- Integration tests with the in-memory and failing sinks cover every outcome and the forbidden content → the rows
  above; every `ImportOutcome::all()` value is reached by at least one test (asserted by collecting the outcomes
  seen in `import_entry_per_outcome` and comparing with `ImportOutcome::all()`).
- Existing behaviour intact (sign entries, F73 order, owners) → the adapted existing tests pass in `just quick`.
- Mutants → `just mutants-diff F75` reports no surviving mutant in the changed code (outcome mapping, rollback,
  order of record and reply, store removal).
