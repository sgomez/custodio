# F104 — TPM tools in the dev container and CI, and the with-swtpm recipe

## Scope
Built:
- `harness/Containerfile` and every CI job that builds or tests the workspace (all jobs of
  `.github/workflows/ci.yml` and `mutants.yml` that run cargo, directly or through `just`) install,
  from the distribution, `swtpm`, `swtpm-tools`, `tpm2-tools` and `libtss2-dev`, plus whatever
  extra distribution package the swtpm TCTI needs to work (if `tpm2-tools` does not pull it in).
  Each install has a comment saying why (`tss-esapi` builds against the TSS2 headers; tests and
  tools use a software TPM).
- `just with-swtpm *cmd`: fresh `swtpm` in socket mode with its state in a new temporary
  directory, `TPM2_Startup`, `TPM2TOOLS_TCTI` exported, runs the command, always stops `swtpm`
  and removes the state, exits with the command's status, and fails with a clear message when
  `swtpm` or `tpm2-tools` is missing.
- A script test for the recipe and a check that the CI and container installs stay in step.

Left to other features: the `tss-esapi` dependency and any TPM code or tests that use the recipe.

Environment (checked in this session, dev container before the rebuild): `command -v swtpm
swtpm_setup tpm2_getcap` prints nothing for all three and `pkg-config --exists tss2-esys` fails.
So the real recipe cannot run until the container is rebuilt. This is the step the feature
description assigns to a person. Until then the builder proves only what does not need the tools:
the missing-tool failures (with a stripped `PATH`) and the install-sync check. The last step
writes `BLOCKED.md` asking for the rebuild. The `verify` command and the evidence marked
"rebuilt container" run on the rebuilt container, where the feature passes. No installing
packages into the running container by hand, no deviation needed.

Proven at the checkpoints, not here: that CI jobs go green with the packages (a push to CI); the
package gates.

## Evidence
- Containerfile installs the four packages, with a comment → sync check script test → passes;
  negative control: with one package name removed from a temporary copy, the check fails and
  names the missing package.
- Every CI job that builds or tests the workspace installs them, with a comment → same sync
  check, which scans every job of `ci.yml` and `mutants.yml` that runs cargo or `just` (a
  short, commented list of jobs exempt because they never compile) → passes; negative control:
  a temporary copy of a workflow with a cargo job lacking the install fails the check.
- TSS2 development files present → `pkg-config --exists tss2-esys` → exit 0 (rebuilt container).
- Recipe runs a command against a fresh started TPM → `just with-swtpm tpm2_getcap algorithms`
  and `just with-swtpm tpm2_createprimary -C o -c /dev/null` → both exit 0 (rebuilt container;
  the second also proves `TPM2_Startup` ran and `TPM2TOOLS_TCTI` is exported).
- Exit status is the command's → `! just with-swtpm false` and in the script test
  `with-swtpm sh -c 'exit 7'` → status 7 (rebuilt container).
- State is new each run → script test creates and persists an object in one run
  (`tpm2_evictcontrol`) and checks `tpm2_getcap handles-persistent` is empty in the next
  (rebuilt container).
- swtpm stopped and temporary state removed whatever the outcome → script test records the
  state directory (printed by the command from the environment/`TPM2TOOLS_TCTI`) and the swtpm
  process id, then after a succeeding run, a failing run and a run whose recipe gets SIGTERM
  mid-command checks the directory is gone and the process is not running (rebuilt container).
- Clear failure when tools are missing → script test runs the recipe with a `PATH` that hides
  `swtpm` (then `tpm2-tools`) → nonzero status, stderr names the missing tool, and the command
  is not run (runs now and after the rebuild).
- Lints → `just quick` → passes (shellcheck covers the new scripts).
