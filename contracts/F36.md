# F36 — Build the .deb, .rpm and Arch package with nfpm from one file list

## Scope
Replace `cargo deb` with nfpm. `just package` builds the release binaries and then one `.deb`, one `.rpm`
and one `.pkg.tar.zst` (x86_64) in `target/packages`, from a single nfpm configuration.

Built here:
- `packaging/nfpm.yaml`: the one file list (source, destination, mode, owner of every installed file;
  everything under `/usr`, nothing in `/etc` or `/var`) and the common metadata. Per-format
  `overrides:` hold only metadata, dependency names and `polkit >= 124` where the format can say it.
- The service moves to `/usr/lib/custodio/custodiod` in all three formats (open question "Arch and
  `/usr/libexec`", option (a)). Only `ExecStart` in `data/custodio.service` changes. The D-Bus activation file
  `data/com.rfirma.Custodio1.service` needs **no** change: it keeps `Exec=/bin/false` and
  `SystemdService=custodio.service` on purpose, so `dbus-daemon` can only start the service through the
  hardened unit, never the binary directly. This departs from the literal feature text, which says the
  activation file is "updated": it contains no `/usr/libexec` (`grep -q libexec
  data/com.rfirma.Custodio1.service` fails today), so there is no path to change. That is recorded in `docs/decisions.md` (a later session might
  "fix" the `/bin/false`). One unit, one activation file.
- Lifecycle script files, one set per format, with names that differ per format and no `.sh` suffix:
  - deb: `packaging/deb/postinst` only (no preinst, prerm, postrm). It keeps the M1 guard
    `[ "$1" = configure ]` around the three actions.
  - rpm: `packaging/rpm/post` only (nfpm `postinstall`, rendered as `%post`; no pre, preun, postun).
  - Arch: `packaging/arch/post_install` and `packaging/arch/post_upgrade` (nfpm `postinstall` and
    `postupgrade`, rendered as the functions `post_install` and `post_upgrade` of `.INSTALL`; M1's postinst also
    ran on upgrade, so both exist). No other function.
  All four source files start with `#!/bin/sh` (including the two Arch fragments, which nfpm wraps inside the
  `post_install()`/`post_upgrade()` functions of `.INSTALL`), so the shebang-based `shell_scripts` finds them.
  Until F43/F44 each does only what `data/debian/postinst` does: `systemd-sysusers custodio.conf`,
  `systemctl daemon-reload`, `systemctl reload dbus`, each with `|| true`.
- The build gate run by `just package` on the real packages, split so no tracked file passes the 5000-token
  cap of `scripts/check-files.sh`: `scripts/check-packages.sh` (tool presence check, extraction of each package
  into a temp dir with `dpkg-deb`, `rpm`, `bsdtar`, `readelf`, then one call to the helper) and
  `scripts/check_packages.py` (run as `python3 -I`; parsing of `packaging/nfpm.yaml`, the checks) with its
  data tables (explicit file list with modes, dependency table, soname table) in
  `scripts/package_expected.py`. If any file still nears the cap, the tables move to a JSON file read by the helper.
  Missing-tool behaviour is the same for the split: the shell part checks every tool with `command -v` before
  anything else, and the helper turns a `FileNotFoundError` from a subprocess into a message naming the tool.
- `scripts/test-check-packages.sh` (file list part) and `scripts/test-check-packages-deps.sh` (dependencies,
  NEEDED, scripts, missing tool, versions) share `scripts/lib/package-fixtures.sh`; `scripts/test-package-scripts.sh`
  and `scripts/test-shell-scripts.sh` test the lifecycle scripts and `shell_scripts`. Recipes, all part of `check`:
  `package-gate-test` (runs the first three) and `shell-scripts-test` (the third). Each recipe is added to `check`
  in the step that completes the files it needs (see Steps), so `check` is green after every step. `check` stays fast and does
  not need `target/packages` nor a release build: the tests build their own small fixture packages with nfpm
  (a throwaway `nfpm` config in a temp dir, derived from the real `packaging/nfpm.yaml` by a small python edit per
  case, using a copied system ELF for the binaries, and the real
  `packaging/` scripts and unit file). `just package` runs `scripts/check-packages.sh` against the real
  packages; it does not run the fixture tests.
- Version scheme (below) and `docs/decisions.md` entries.
- Supply chain: nfpm and the checking tools installed in the dev image, CI and (nfpm) pinned in `mise.toml`.
  `cargo-deb`, `[package.metadata.deb]`, `data/debian` and every `cargo deb` use leave the repository,
  mise.toml, the dev image and CI. `target/debian` references move to `target/packages` (`e2e/run.sh`,
  `docs/manual-acceptance.md`, the `justfile` comments).
- `shell_scripts` in the justfile covers the maintainer scripts whatever their file names.

Version scheme (decision recorded in `docs/decisions.md`): source of truth is `[workspace.package] version`
in `Cargo.toml`, `X.Y.Z` or `X.Y.Z-pre`. The packaging revision is always `1` in all three formats (Debian
revision `-1`, RPM release `1`, Arch pkgrel `1`): the tree is the source, so there is no packaging-only rebuild
to number; bumping the workspace version is the only way to get a new package. A pre-release is passed to
nfpm as `version` plus `prerelease`, so each format uses its own pre-release sorting and not a plain `-`:
`0.2.0-rc.1` becomes deb `0.2.0~rc.1-1`, rpm version `0.2.0~rc.1` release `1`, Arch pkgver `0.2.0_rc.1`
pkgrel `1` (Arch forbids `-` in pkgver). Step 1 confirms with nfpm what it renders; if nfpm renders differently,
the scheme recorded is what nfpm renders, provided a pre-release sorts below its release in deb and rpm and
the Arch pkgver has no `-`. `just package version=X.Y.Z[-pre]` overrides the version without touching
`Cargo.toml` or `Cargo.lock`.

Left for other features: the parity check, glibc ceiling and package linters (other M2 gates), real lifecycle
behaviour (F43, F44), the e2e contents (it only needs the new path). Dependency lists name the libraries the
binaries link, read from `readelf -d`; no automatic computation.

Larger than five steps (eleven, each small); a split is not needed.
