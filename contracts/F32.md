# F32 — Written manual acceptance steps

## Scope
Documentation only: one new file, `docs/manual-acceptance.md`, for SPEC.md acceptance 11, 12 and 13. No
code, test, unit, SPEC or features.json change. Nobody runs the steps in this feature; the person who
approves the milestone does (feature F33). The feature is small (four steps), so no split is needed.

Facts the steps use are taken from the repository, not from memory: the `custodio import [--id ID]
FILE.p12` command and its tty password prompt (`crates/custodio-cli/src/lib.rs`, `e2e/import.py`), the
shipped `custodio.module` (p11-kit file, module path `/usr/lib/custodio/libcustodio_pkcs11.so`), the
`.deb` built by `just package` (`target/debian`), the queries in `docs/audit.md` "Queries", and
`docs/findings.md` section 4 (the two M0 workarounds). A command is written only if it was checked
here (`--help`, a man page, a file in the repo); otherwise the step says "adjust to your NSS/LibreOffice
version" and is marked unverified. Names that cannot be checked here (the LibreOffice menu path, the
rFirma menu path) are given as described, with the marker **unverified**.

Left for other features: running the steps (F33), automated checks (F28, F29, F31), Firefox, other
distributions, fixing anything the run finds.

Contents, in this order:
1. **Prerequisites and test material.** Graphical Debian 13 or Ubuntu 26.04 session with a polkit
   agent (the dialog must appear); one account for the person and one admin account for the journal;
   test CA, an RSA 2048 and a P-256 key, each with a certificate that LibreOffice and rFirma accept,
   made as `.p12` with `openssl` commands that are written out in full, using the same `pkcs12 -export`
   options as `e2e/guest.sh:32`, certificates signed by the test CA (not self-signed) with
   `keyUsage=digitalSignature,nonRepudiation`; packages `opensc` (`pkcs11-tool`) and `libnss3-tools`
   (`modutil`, `certutil`); trusting the test CA (`certutil -A -d sql:<dir> -t "C,," -i ca.crt`) in
   the NSS database LibreOffice uses, and for rFirma by the way it needs (unverified); versions to record (OS,
   polkit, LibreOffice, rFirma build, `.deb`).
2. **Install the `.deb`**, check the service and the polkit action are there.
3. **Import** both keys with `custodio import --id rsa2048` / `--id p256`;
   `pkcs11-tool --module /usr/lib/custodio/libcustodio_pkcs11.so --list-objects` shows both.
4. **rFirma build** without the two workarounds: states which two (fallback from `CKM_SHA256_RSA_PKCS`
   to raw `CKM_RSA_PKCS` over a `DigestInfo`; skipping `C_Login` when `CKF_LOGIN_REQUIRED` is unset),
   that the maintainers must provide the build (SPEC open question "Which rFirma build"), and how to
   confirm the build lacks them. The person records whether it is a release or a build with the
   workarounds reverted, and its version or commit.
5. **rFirma run**, per key: certificate listed; sign, polkit dialog seen; sign again, dialog again;
   sign and cancel, signature fails. Pass/fail table with a result column.
6. **LibreOffice run**: register the module in the NSS database LibreOffice uses (path found by the
   person, e.g. the profile's `cert9.db` or the shared `~/.pki/nssdb`; `modutil -add` command with
   `-dbdir sql:<dir>`; `modutil -list` check), per key sign an ODF document (dialog seen), save, close,
   reopen, signature shown valid; also cancel once per key.
7. **Journal comparison**: the query, with `--since`/`--until` around the run, from `docs/audit.md` run as administrator after steps 5 and 6,
   a table of steps taken (time, client, key, approved/cancelled) against entries found (uid, pid,
   key, outcome), the pid compared with `pgrep` taken during the run, and the rule: one entry per
   signature and per cancellation, none extra, none missing.
8. **What to record** for the open questions, one block each, with exact observations to write down:
   PIN dialog in LibreOffice (whether any PIN/password dialog appeared, when, text); LibreOffice with
   ECDSA (signed or not, error text, validity after reopening, and the fallback: a software NSS token
   with the same key, to tell a Custodio fault from a LibreOffice one); repeated login and session
   state (whether any client called `C_Login` twice, whether it prompted or failed, from a
   `pkcs11-spy` trace if used). This run only records what clients do with today's behaviour; trying
   `CKR_USER_ALREADY_LOGGED_IN` needs another build and is out of scope; plus the rFirma build and `CKU_SO` if seen.
9. **Result form**: the table the person fills in, one row per acceptance 11, 12, 13, pass/fail/
   not run, and where to report.

## Evidence
- File exists and names the required terms → feature `verify` command → exit 0 (fails if the file is
  empty or lacks rFirma, LibreOffice, `RSA 2048`, `P-256`, `journalctl`, `polkit`).
- Installing the `.deb` → `grep -c 'dpkg -i\|apt install' docs/manual-acceptance.md` ≥ 1, and the
  `.deb` path/name matches what `just package` writes (`ls target/debian` if built, else the `justfile`
  recipe) → section 2 names it.
- Importing an RSA 2048 and a P-256 key → `grep -F 'custodio import' docs/manual-acceptance.md`
  matches two commands with `--id`; the flags equal `USAGE` in `crates/custodio-cli/src/lib.rs`.
- Test key material commands are valid → run the written `openssl` commands in a temp dir here; both
  `.p12` files are produced, `openssl pkcs12 -info` reads them, `openssl verify -CAfile ca.crt` on both
  certificates exits 0, `openssl x509 -text` shows the key usage, and the `pkcs12 -export` options
  equal `e2e/guest.sh:32` (diff) → all as stated.
- `custodio import` accepts those files → the export options match the ones `e2e/guest.sh` already
  imports (diff above); the import itself is run by the person and marked unverified here.
- CA trusted for "valid" → `grep -F 'certutil -A'` in the file, with `-t "C,,"`, before the LibreOffice
  signing step.
- Packages and module flag → `grep` finds `opensc`, `libnss3-tools`, and `pkcs11-tool` with `--module`.
- Journal time window → `grep -E -- '--since' ` and `--until` in section 7.
- rFirma without the two M0 workarounds → `grep -n 'findings.md' docs/manual-acceptance.md` points to
  section 4 and the text names both workarounds (`CKM_RSA_PKCS`/`DigestInfo` and `C_Login`/
  `CKF_LOGIN_REQUIRED`) → manual review by the evaluator against `docs/findings.md` lines 107–131.
- Registering the module in the NSS database LibreOffice uses → the file has a `modutil -add` command
  with `-libfile /usr/lib/custodio/libcustodio_pkcs11.so`, the path equals the one in
  `data/custodio.module`, and a `modutil -list` check → `grep` for both strings, diff of the path.
- Signing and cancelling in rFirma and in LibreOffice with each key → the results table has one row
  for each of the 2 clients × 2 keys × {certificate listed, approve, approve again (rFirma), cancel} and each row has an
  expected result column (dialog shown / dialog again / signature fails) → count rows by review.
- Reopening the ODF document to check the signature → the LibreOffice section has a close, reopen and
  "signature valid" step per key → review; `grep -i reopen`.
- Journal query → the query text in the file is character-for-character one from `docs/audit.md`
  → `grep -F` of the first query line of the audit doc in the manual file; includes `_SYSTEMD_UNIT`
  and `_UID`, so it fails if copied without the trusted fields.
- Comparing entries against steps → the section has a table with columns uid, pid, key, outcome and
  the rule "one entry per signature and per cancellation" → review.
- Open question PIN dialog in LibreOffice → `grep -nE '^#+ .*PIN dialog'` finds a heading under
  "What to record", followed by a fill-in field (blank line to complete) → review.
- Open question LibreOffice with ECDSA → an item that names ECDSA and the software NSS token fallback
  → `grep -nE '^#+ .*ECDSA'`, with a fill-in field.
- Open question repeated login and session state → an item that names `C_Login` repeated and
  `CKR_USER_ALREADY_LOGGED_IN` and `C_GetSessionInfo` → `grep -nE '^#+ .*[Rr]epeated login'` finds the heading, the text names the other two terms, with a
  fill-in field; it states that only current behaviour is recorded.
- Nothing unverified is presented as verified → every command not run here carries the word
  "unverified"; the evaluator lists the commands in the file and checks each is either run in the
  PROGRESS.md entry or marked.
- No gate weakened, nothing else changed → `git diff --stat` for the feature touches only
  `docs/manual-acceptance.md`, `contracts/F32.md`, `PROGRESS.md`; `just check` → exit 0.
