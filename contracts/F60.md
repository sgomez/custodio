# F60 — End-to-end upgrade from the last cargo-deb .deb on Debian 13

## Scope
Built here:
- A script (called by the `e2e` recipe, like `scripts/package-next.sh`) that produces the old package: the `.deb` that `cargo deb` built from the
  last M1 commit, into a directory that is neither `target/packages` nor `target/packages-next`. The source is read with `git archive` of a
  pinned commit (the tag `v0.3.0`, commit `0f48354`, or the last M1 commit if the builder shows it is a better pin; the pin is a full commit id in the
  script) into a fresh empty directory, with its own `CARGO_TARGET_DIR`, so the working tree and its `target/` are not touched. `cargo-deb` 3.8.0 (the version
  M1's `mise.toml` pinned) is installed by the script into a private `--root` directory with `cargo install --locked`; it is not added to `mise.toml`,
  `mise.lock`, `harness/Containerfile` or `.github`, and no recipe outside `e2e` needs it. The packages are built with the M1 commands
  (`cargo build --release --locked ...`, `cargo deb --locked --no-build -p custodiod`) and a fixed `SOURCE_DATE_EPOCH` (the pinned commit's time).
  The result is cached by the pin, so a second `just e2e` does not rebuild it.
- On `debian13` only (the other targets never had a cargo-deb package): the F48 upgrade case, reused (the same cases, helper and checks, parameterised
  by the old and the new package, not copied), starting from the old `.deb` instead of N, and ending at the first nfpm `.deb`. It is a separate guest run on a fresh
  container (the F48 run leaves N+1 installed). The old package is mounted read-only like N, never copied into the image, and installed with
  `debian13`'s own `install.sh` (`dpkg -i`).
- Ids for the new cases are registered in `e2e/cases.list` for debian13 only (the accounting of F45/F59 applies; no `skip.list` entry), so a run that skips one fails.
- `scripts/test-e2e-host.sh` learns the third mount and the ids; the self-test of F48's helper learns the parameterisation.

Version fact (checked here): the old `.deb` is `Version: 0.1.0-1` (built in the dev container with cargo-deb 3.8.0 from `v0.3.0`; its `Depends` are
`dbus, libc6 (>= 2.34), p11-kit, polkitd, systemd`), and the nfpm package N is also `0.1.0-1`, which dpkg treats as a reinstall, not an upgrade. So the "first nfpm .deb"
installed over the old one is the package N+1 of F48 (the same tree, version raised, `0.1.1-1`), which the guest proves strictly greater than the old one with
`dpkg --compare-versions` before installing. If the builder finds a better way to get a greater first nfpm package, it states it in the amendment; the case must never install an equal or lower version.

Environment checked while writing this contract (dev container): `cargo install --locked --root /tmp/cdeb-root cargo-deb@3.8.0` succeeds in 14 s (network to crates.io works) and prints
`cargo-deb 3.8.0`; `git archive v0.3.0` into an empty directory, `cargo build --release --locked -p custodiod -p custodio-cli -p custodio-pkcs11` (rust 1.99.1, as M1's
`rust-toolchain.toml`) and `cargo deb --locked --no-build -p custodiod` produce `custodio_0.1.0-1_amd64.deb` in 21 s. `cargo deb` is not on the dev container's PATH (it is not in `mise.toml`). Podman, nfpm and the five-target
run were confirmed by F46–F48.

Facts the old package changes for the shared case, which the builder must handle rather than assume: its daemon is not at `/usr/lib/custodio/custodiod` (M1 put the service
in `/usr/libexec`); it has no `preinst`/`prerm`/`postrm` and an M1 `postinst`; it may differ in state-directory handling. The executable-identity check of F48 therefore reads the
installed path from the unit's `ExecStart` before the upgrade for the old process and the new path after, instead of a constant.

Left for other features: all five targets' nfpm-to-nfpm upgrade (F48, done); removal, purge, reinstall (F49); Ubuntu 24.04 refusal (F50); cargo-deb on any other target (none exists).

Size: about five steps; no split needed.

## Steps
- [ ] Tests first: `scripts/test-e2e-host.sh` (stub engine) checks that on debian13 the old package is a third read-only mount distinct from N and N+1, none in the image, and that no other target gets it; that the new case ids are in `cases.list`
      for debian13 and an omitted id fails the accounting; fixtures for the old-package script (a `cargo` / `cargo-deb` stub) check the pin is a commit id, the build runs outside the working tree, and nothing is written to `mise.toml`, `mise.lock`, `harness/Containerfile` or `.github`. The F48 helper self-test gets controls for the parameterisation
      (old process path differs from the new; an old exe path reused after the upgrade is rejected). Run them red.
- [ ] Write the old-package script and wire it into the `e2e` recipe and `run.sh` (the third mount, debian13 only). Check on a real run of the script that the output is `custodio_0.1.0-1_amd64.deb`, built by cargo-deb, and that two builds in different empty directories, each bypassing the cache keyed by the pin, give the same sha256 (reproducible). If absolute paths leak into the binaries, fix it with a fixed build path or `--remap-path-prefix`; the check stays.
- [ ] Make `cases.list`/`check-cases.sh` target-aware for the new ids (expected only on debian13; the stub test shows another target does not fail for lacking them and fails if it reports one), then parameterise the F48 case (packages in, the path of the executable read from the unit, and the key-import step, in case M1's CLI/service import interface differs from N's) and add the debian13 run from the old package: the ids, the pre-install greater-than check against the old version, the install, the comparison.
- [ ] Run `just e2e debian13` until it passes (a defect of the case, or a real defect of the nfpm package for upgrades from the cargo-deb one: fix it with its own test, or write `BLOCKED.md` if it is a decision). Never weaken a check or skip. Then `just e2e` (all five) must still pass.
- [ ] Docs: the README/harness text that lists the e2e cases, and `docs/findings.md` only for something non-obvious the run showed (for example the `Version` collision above). Real run required: paste exit status, the case lines, versions and executable identities into `PROGRESS.md`; run `verify`.

## Evidence
- The old package is the one `cargo deb` built from the last M1 commit, produced reproducibly → the old-package script, run for real, and its stub test → the file is `custodio_0.1.0-1_amd64.deb` whose `dpkg-deb -f` shows the M1 `Depends`
  and its contents show the M1 layout (service in `/usr/libexec`, no `preinst`); two builds from different empty directories have equal sha256; the stub test fails for a pin that is not a full commit id and for a build that runs in the working tree.
- cargo-deb is not put back → `verify`'s `! grep -rqsE 'cargo[- ]deb' mise.toml harness/Containerfile .github`, plus the stub test's check that `mise.toml`, `mise.lock`, the Containerfile and `.github` are unchanged by the script → pass; and `grep -rqi 'cargo.deb\|cargo-deb' e2e` holds because the script and cases name it (this grep is not the proof; the real run is).
- On debian13, `just e2e` also runs the upgrade case from the old .deb to the first nfpm .deb → REQUIRED real `just e2e debian13`, then `just e2e` → exit 0, "e2e: passed: alma10 arch debian13 fedora44 ubuntu2604"; every new id appears as run (not skipped) in `target/e2e/debian13.log`; the other four logs have none of them; `scripts/test-e2e-host.sh` fails if a stub run omits one.
- It is a real upgrade, not a reinstall or a downgrade → real run → `dpkg-query -W -f '${Version}'` is `0.1.0-1` before and `0.1.1-1` after, taken from the installed database, and the guest's `dpkg --compare-versions` check ran before the install; self-test controls (equal and lower version) fail the case without installing.
- Same behaviour as F48's case, by the same helper → real run → key files byte-identical with the same owner and modes (sha256, uid, gid, mode, count > 0); same keys listed (`rsa1`, `ec1`); one approved RSA and one approved ECDSA signature after the upgrade verify, the agent's counter rose by one per signature, and a denied signature fails with the counter still rising (polkit asked each time). F48's helper self-test controls (changed byte, mode, owner, added/removed file, listing without a key) cover the helper; this feature shows them on the old → new run.
- The service running before runs the new binary afterwards, by identity → real run → before: active, `MainPID` p1, `/proc/p1/exe` is the file named by the old unit's `ExecStart`; after: active, `MainPID` p2 ≠ p1, `stat -L /proc/p2/exe` has the device and inode of the file now named by the new unit's `ExecStart`, not `(deleted)`; settled for a few seconds. Controls: unchanged pid, `(deleted)` exe, an exe that is not the installed file each fail (self-test).
- No manual step → real run + static grep → between the start of the install and the end of the case nothing runs but `install.sh` (the `# BEGIN/END upgrade-case` markers and the grep for `systemctl restart/start/daemon-reload/reload` and `pkill` of F48 cover this section too; the grep fails when the section is missing or empty); the install exits 0 without a prompt.
- Shellcheck and syntax → `just check` and `bash -n e2e/*.sh` → pass.
