# F128 — Duplication check for TPM keys

## Scope
The integration target `tpm_duplicate` in `custodiod` (`crates/custodiod/tests/tpm_duplicate.rs`, reusing the F126/F127
rigs through `#[path]`). It imports through the service (the F117 flow, fake polkit approving, real `swtpm`), reads
**the blob the service stored** (the `Record` in the store, or the bytes of the state file parsed with `Blob::parse`;
not the value `import_pkcs8` returns, which F113 already checks), and uses `tpm2-tools` on it, for both key types
(RSA 2048, P-256) and for every TPM key the service stores: also a second key and a key replaced by delete and re-import under the same id, in the same store, so the
check is over the store and not over one lucky key.

Proven here, per stored key: (1) `tpm2_readpublic` shows an empty `authPolicy`; (2) `tpm2_duplicate` on the loaded key
fails with a policy/authorization error, not an argument error; (3) the blob does not load in a second, independent
`swtpm` (own state, own owner seed).

Not here: F113's `tpm_import` proves the same properties on the blob `import_pkcs8` returns (and the other attributes);
this feature adds that they hold for what the service stores. Encrypted kinds hold no TPM blob and are out of scope.
The e2e/manual duplication check on a real state directory runs at the checkpoint features. No mutants (`verify` has none).

Environment check (dev container): `which tpm2_readpublic tpm2_duplicate tpm2_load tpm2_startauthsession
tpm2_policycommandcode swtpm` → all under `/usr/bin`; `tpm2_duplicate --version` → `5.7`. F113's
`blob_does_not_load_elsewhere_and_cannot_be_duplicated` already drives these with two `Rig`s (two `swtpm`).
Size: four steps, no split.

## Evidence
- The test checks the service's stored blobs, not the import return value → `tpm_duplicate::checks_every_stored_key` →
  for both key types, the public key in the stored public area equals the one in that entry's certificate, and the number of
  `tpm` records checked equals exactly the number the test put in the store (RSA, P-256, a second key, a re-imported key: four);
  a store with no TPM key, or with an extra or stale record, fails. The bytes loaded are the stored `public_bytes()` and
  `private_bytes()` unchanged.
- Empty `authPolicy` → `tpm_duplicate::stored_auth_policy_is_empty` → `tpm2_readpublic` on the loaded stored key prints an
  empty `authorization policy` for every stored key. Negative control: a key created by the test with a non-empty policy
  (`tpm2_create -L`) read the same way is seen as non-empty, so the parse of the output can fail.
- `tpm2_duplicate` fails → `tpm_duplicate::stored_key_cannot_be_duplicated` → for every stored key, `tpm2_duplicate` (policy
  session on `TPM2_CC_Duplicate`, as in `tpm_import`) exits non-zero with one response code the builder fixes for that invocation and asserts exactly
  (the policy-failure code for the policy session; F113 asserts `TPM_RC_AUTH_TYPE` 0x124 without one), so an argument or load error cannot pass. Negative control: the same command on a test-created key whose policy is the `PolicyCommandCode(Duplicate)`
  digest, with `fixedTPM`/`fixedParent` clear, succeeds and writes the duplicate, so the command line is able to pass.
- Does not load in a second swtpm → `tpm_duplicate::stored_blob_does_not_load_in_another_tpm` → on a second, independent `swtpm` (a new `Rig` with its own state directory, never a copy of the first's state;
  fresh seed, the same SRK-template parent made there) `tpm2_load` of every stored blob fails with an integrity error.
  Control: on the first `swtpm` the same command loads the same blob.
