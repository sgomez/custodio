# F28 — End-to-end: composed mechanisms, multi-part client and C_Login

## Scope
Extends the `just e2e` suite (Debian 13 systemd container, the `.deb`, real polkit, the test agent
in `e2e/agent.py`). Covers SPEC acceptance 1 (six composed mechanisms through `pkcs11-tool`), 2
(only the part about a multi-part client: OpenSSL with pkcs11-provider; the C_Sign vs
C_SignUpdate/C_SignFinal comparison in one test is F21/F26 integration territory and is not added
here), 6 (`--login` with a PIN still asks polkit) and 10 (M0 checks unchanged).

Built:
- `e2e/Containerfile`: add the Debian package `pkcs11-provider` (`opensc`, which ships
  `pkcs11-tool` and `pkcs11-spy.so`, and `openssl` are already there).
- `e2e/guest.sh`: export the certificates' public keys (`rsa.pub`, `ec.pub`, from the existing
  `rsa.crt`/`ec.crt` via `openssl x509 -pubkey -noout`) into `$work`. The export is inserted
  **before** the existing `chmod 644 "$work"/*` (line 36), so alice can read the files; the
  private-key removal and the import loop stay as they are.
- A new `e2e/composed.sh`, sourced by `user.sh` after the existing checks (so the M0 lines of `user.sh`
  stay untouched: the only edit there is that one `source` line before the final
  `echo "user.sh: passed"`; the token limit is not the reason, `user.sh` is far below it). It uses the
  helpers `fail`, `requests` and `expect_requests` of `user.sh`.
- No change to the module, the service, the justfile or `features.json`.

Parts of SPEC acceptance 6 that e2e cannot show (NULL or empty PIN, `C_Logout`, "login does not
contact the service") are covered by existing tests, which F28 does not change:
`crates/custodio-pkcs11/src/ffi/tests/login.rs` (`login_accepts_any_pin`, `login_never_dereferences_the_pin`,
`logout_is_ok`, `login_twice_and_after_logout`) and `crates/custodio-pkcs11/tests/cryptoki/login.rs`
(`login_does_not_contact_service`, `login_logout_cryptoki`, `sign_after_login_asks_polkit`,
`denied_after_login_still_fails`).

Left to others: running the suite for real (F31; the dev container cannot run `just e2e`), the
journal checks of acceptance 7-9, manual clients. `verify` only lints and greps for the case names.

## Steps
- [ ] Containerfile: install `pkcs11-provider`; guest.sh: write `rsa.pub` and `ec.pub` before the chmod.
- [ ] composed.sh part 1: a `p11sign_composed key mechanism` helper, a `verify_openssl` helper
      (`openssl dgst -<hash> -verify <pub> -signature` for RSA; for ECDSA sign with
      `--signature-format openssl` so the output is DER), and the loop over `SHA256-RSA-PKCS`,
      `SHA384-RSA-PKCS`, `SHA512-RSA-PKCS` on token `rsa1`.
- [ ] composed.sh part 2: the same loop for `ECDSA-SHA256`, `ECDSA-SHA384`, `ECDSA-SHA512` on `ec1`,
      and a deny case per family.
- [ ] composed.sh part 3: OpenSSL + pkcs11-provider signing of `rsa1` and `ec1` by `pkcs11:` URI. The
      module is passed with `export PKCS11_PROVIDER_MODULE=<spy.so>` and `-provider pkcs11 -provider default`
      (no config file, so no section can be left inactive). `<spy.so>` is OpenSC's `pkcs11-spy.so`,
      located at runtime (`/usr/lib/x86_64-linux-gnu/pkcs11-spy.so` on Debian trixie, else `find /usr/lib`);
      if it is not found the run calls `fail`, it never falls back to `$MODULE`. `PKCS11SPY=$MODULE` and
      `PKCS11SPY_OUTPUT=$WORK/spy.log` make the spy forward to the real module. Spy-log checks as in
      Evidence, applied to both the `rsa1` and the `ec1` signature; a denial case (with `rm -f` of
      the output file before it runs).
- [ ] composed.sh part 4: `pkcs11-tool --login --pin 1234` before signing: approve signs and
      verifies, deny fails, each asks the agent exactly once; and the required
      `--login --login-type context-specific --pin 1234` approve case (SPEC names `CKU_CONTEXT_SPECIFIC`).
      All four login cases (USER approve, USER deny, second `--login`, context-specific approve) run
      through the spy (`--module <spy.so>`, `PKCS11SPY=$MODULE`, `spy.log` removed before each) and
      check the log for `C_Login` as in Evidence. If `pkcs11-tool` never calls
      `C_Login(CKU_CONTEXT_SPECIFIC)`, the case fails and PROGRESS.md says so; it must not pass silently.
- [ ] Wire it in: source from `user.sh`, `git add e2e/composed.sh` (shellcheck only sees tracked files,
      `git ls-files '*.sh'`), start the file with `# shellcheck shell=bash` and give variables that come from
      `user.sh` (`WORK`, `MODULE`, `sig`, `E2E_DIR`) a `# shellcheck source=user.sh` link or narrow SC2154
      disables with a justifying comment, no blanket disable; run `just lint` (shellcheck, typos, check-files) and the
      `verify` command; confirm the M0 parts of `user.sh`/`guest.sh` are untouched (`git diff`).

## Evidence
Every case reads `before=$(requests)` right before it runs and checks the counter afterwards
against `before + 1` exactly (not ≥), for approve and deny cases alike.

- Acceptance 1, three RSA mechanisms → `composed.sh` loop over `SHA256-RSA-PKCS SHA384-RSA-PKCS
  SHA512-RSA-PKCS` with `pkcs11-tool --sign --mechanism <m>` on `rsa1`, agent in `approve` mode →
  each signature is 256 bytes, the counter is `before + 1`, and `openssl dgst -sha{256,384,512}
  -verify rsa.pub -signature` over the original `data.bin` prints `Verified OK`. The case also verifies
  with a different digest and requires that to fail, so the hash is really checked.
- Acceptance 1, three ECDSA mechanisms → same loop for `ECDSA-SHA256 ECDSA-SHA384 ECDSA-SHA512` on
  `ec1` with `--signature-format openssl` → `$sig` non-empty, counter `before + 1`, verify over
  `data.bin` with `ec.pub` and the matching digest passes; the cross-digest verify fails.
- Approval is required → in each family, one composed signature with the agent in `deny` mode →
  `pkcs11-tool` exits non-zero, `$sig` is absent or empty, counter exactly `before + 1`.
- Acceptance 2, multi-part client → with `PKCS11_PROVIDER_MODULE` set to the spy and the spy forwarding to
  `$MODULE`, `openssl dgst -sha256 -provider pkcs11 -provider default -sign 'pkcs11:token=rsa1;object=rsa1;type=private'`
  and the same for `ec1`, agent in `approve` mode → exit 0, counter `before + 1`, then `openssl dgst
  -sha256 -verify rsa.pub` (and `ec.pub`) over `data.bin` passes. `spy.log` is removed before each
  signature. Spy-log checks, for **both** the `rsa1` and the `ec1` signature: the log is non-empty and
  contains `C_Initialize` (a provider that never loaded the module cannot pass); it contains
  `C_SignInit`, at least one `C_SignUpdate`, at least one `C_SignFinal` (OpenSSL may send a size
  query with a NULL buffer first, which PKCS#11 allows, so the count is not fixed; only the last
  `C_SignFinal` must return `CKR_OK` with a signature), and no whole-word `C_Sign` (`grep -w`). The
  polkit check stays exact: the counter is `before + 1`. Each failed check fails the test.
- Acceptance 2, several updates → an `rsa1` signature of a file of more than 1 MiB from `/dev/urandom`,
  signed and verified the same way: `C_SignUpdate` appears at least 2 times, at least one `C_SignFinal`
  (same rule), counter `before + 1`.
- Acceptance 2, denial through the provider → `rm -f` of the output file, then agent in `deny` mode →
  `openssl dgst -sign` fails, the output file is absent or empty, counter `before + 1`.
- Acceptance 6 → `pkcs11-tool --login --pin 1234 --sign --mechanism SHA256-RSA-PKCS` (and one with
  `ECDSA-SHA256`) in `approve` mode → signature verifies and counter `before + 1`; in `deny` mode the same
  command fails, no output, counter `before + 1`, so the login authorized nothing. A second `--login`
  signature asks again (counter `+1` more).
- Acceptance 6, context-specific login → `pkcs11-tool --login --login-type context-specific --pin 1234
  --sign --mechanism SHA256-RSA-PKCS` in `approve` mode → the signature verifies with `rsa.pub` and the
  counter is `before + 1`.
- Acceptance 6, `C_Login` really called → the four login cases (USER approve, USER deny, second
  `--login`, context-specific approve) run with `--module <spy.so>` and `PKCS11SPY=$MODULE`, `spy.log`
  removed before each. In every case `spy.log` must show `C_Login` with user type `CKU_USER` (1) in the
  USER cases and `CKU_CONTEXT_SPECIFIC` (2) in the context-specific case, `C_Login` returning
  `CKR_OK`, and `C_SignInit` and `C_Sign` after it (in line order). A run where `pkcs11-tool` skips
  `C_Login`, or moves it elsewhere, fails; if it never calls the context-specific login, the case
  fails and PROGRESS.md records it. The spy is located as for the provider cases and never falls back
  to `$MODULE`.
- Acceptance 6, parts e2e cannot show → the existing tests listed under Scope still pass in `just test`
  (NULL/empty PIN, `C_Logout`, no service contact).
- Acceptance 10 → `git diff` of `e2e/user.sh` and `e2e/guest.sh` shows only added lines (one `source`
  line and the public-key export); the M0 assertions and their request counters are not edited. The new
  cases run after them and use the relative counter, so the M0 absolute counts are unaffected.
- Suite is well formed → `just lint` (shellcheck on `e2e/*.sh`, typos, check-files) → exit 0, and
  `bash -n e2e/*.sh` → exit 0.
- Suite contains the cases → the feature's `verify` command → exit 0. The `pkcs11-provider` name alone
  could match only the Containerfile, so also `grep -qF pkcs11-provider e2e/composed.sh` must succeed
  (the case exists, e.g. in its heading and its `-provider pkcs11` section). Each of the six mechanism
  names and `--login` appears only in `composed.sh`, so removing one of them from the suite makes
  `verify` fail.
- Caveat → the dev container cannot run `just e2e`. Before writing the cases, confirm against
  `pkcs11-tool --help` that `--signature-format`, `--login-type` and `--pin` exist with the spelling
  used, and against the pkcs11-provider man page (`man pkcs11-provider`, or its README on the web
  via a subagent) the name `PKCS11_PROVIDER_MODULE` and the URI attributes, and from pkcs11-provider's source or docs
  whether it forwards the `EVP_DigestSignFinal` size query to the token (this decides nothing in the
  checks, which tolerate both, but is recorded). Also record the exact `C_Login` line format in the
  spy log that the greps rely on. PROGRESS.md records what was
  confirmed and what could not be exercised, so F31 knows what was never run.
