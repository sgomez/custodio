# F28 — End-to-end: composed mechanisms, multi-part client and C_Login

## Scope
Extends the `just e2e` suite (Debian 13 systemd container, the `.deb`, real polkit, the test agent
in `e2e/agent.py`). Covers SPEC acceptance 1 (six composed mechanisms through `pkcs11-tool`), 2
(only the part about a multi-part client: OpenSSL with pkcs11-provider; the C_Sign vs
C_SignUpdate/C_SignFinal comparison in one test is F21/F26 integration territory and is not added
here), 6 (`--login` with a PIN still asks polkit) and 10 (M0 checks unchanged).

Built:
- `e2e/Containerfile`: add the Debian package `pkcs11-provider` (and keep `openssl`).
- `e2e/guest.sh`: export the certificates' public keys (`rsa.pub`, `ec.pub`, from the existing
  `rsa.crt`/`ec.crt` via `openssl x509 -pubkey`) into `$WORK`; they are already `chmod 644`. The
  private-key removal and the existing import loop stay as they are.
- A new `e2e/composed.sh`, sourced by `user.sh` after the existing checks (so that file stays under
  the 5000-token limit of `scripts/check-files.sh`, and the existing lines of `user.sh` are not
  edited except for that one `source` line before the final `echo "user.sh: passed"`). It uses the
  helpers and `expect_requests` of `user.sh`.
- No change to the module, the service, the justfile or `features.json`.

Left to others: running the suite for real (F31; the dev container cannot run `just e2e`), the
journal checks of acceptance 7-9, manual clients. `verify` only lints and greps for the case names.

## Steps
- [ ] Containerfile: install `pkcs11-provider`; guest.sh: write `rsa.pub` and `ec.pub` next to the certs.
- [ ] composed.sh part 1: a `p11sign_composed key mechanism` helper, a `verify_openssl` helper
      (`openssl dgst -<hash> -verify <pub> -signature` for RSA; for ECDSA convert the raw r||s that
      `pkcs11-tool` writes to DER with `--signature-format openssl`, then the same verify), and the
      loop over the three RSA mechanisms `SHA256-RSA-PKCS`, `SHA384-RSA-PKCS`, `SHA512-RSA-PKCS` on token `rsa1`.
- [ ] composed.sh part 2: the same loop for `ECDSA-SHA256`, `ECDSA-SHA384`, `ECDSA-SHA512` on `ec1`,
      and a deny case per family (a denied composed signature fails, leaves no output, and the agent was asked).
- [ ] composed.sh part 3: OpenSSL + pkcs11-provider signing (RSA and EC key by `pkcs11:` URI) with a
      generated OpenSSL config, `PKCS11_PROVIDER_DEBUG` log proving `C_SignUpdate` and `C_SignFinal`
      were called (through OpenSC's `pkcs11-spy.so`, see Evidence), signature verified by OpenSSL with the
      certificate's public key, and a denial case.
- [ ] composed.sh part 4: `pkcs11-tool --login --pin <arbitrary>` before signing: approve signs and
      verifies, deny fails, and each asks the agent exactly once.
- [ ] composed.sh part 5 (optional, cheap): one approve case with `--login --login-type context-specific --pin 1234`.
- [ ] Wire it in: source from `user.sh`, `git add e2e/composed.sh` (shellcheck only sees tracked files,
      `git ls-files '*.sh'`), start the file with `# shellcheck shell=bash` and give variables that come from
      `user.sh` (`WORK`, `MODULE`, `sig`, `E2E_DIR`) a `# shellcheck source=user.sh` link or narrow SC2154
      disables with a justifying comment, no blanket disable; run `just lint` (shellcheck, typos, check-files) and the
      `verify` command; confirm the M0 parts of `user.sh`/`guest.sh` are untouched (`git diff`).

## Evidence
- Acceptance 1, three RSA mechanisms → `composed.sh` loop over `SHA256-RSA-PKCS SHA384-RSA-PKCS
  SHA512-RSA-PKCS` with `pkcs11-tool --sign --mechanism <m>` on `rsa1`, agent in `approve` mode →
  each signature is 256 bytes, the agent got exactly one request per signature (`expect_requests`
  counter), and `openssl dgst -sha{256,384,512} -verify rsa.pub -signature` over the original
  `data.bin` prints `Verified OK`. A signature made with the wrong hash fails this verify, so the
  hash size is really checked: the case also runs a verify with a different digest and requires failure.
- Acceptance 1, three ECDSA mechanisms → same loop for `ECDSA-SHA256 ECDSA-SHA384 ECDSA-SHA512` on
  `ec1` with `--signature-format openssl` → `$sig` exists and is non-empty, then verify over `data.bin` with `ec.pub` and the matching
  digest passes (`Verified OK`); the cross-digest verify fails.
- Approval is required → in each family, one composed signature with the agent in `deny` mode →
  `pkcs11-tool` exits non-zero, `$sig` is absent or empty, and the request counter went up by one.
- Acceptance 2 (multi-part client) → OpenSSL with `-provider pkcs11 -provider default` and a config
  setting `pkcs11-module-path` to `$MODULE`, `openssl dgst -sha256 -sign 'pkcs11:token=rsa1;object=rsa1;type=private'`
  (and `ec1` with `-sha256`), agent in `approve` mode → exit 0, then `openssl dgst -sha256 -verify
  rsa.pub` (and `ec.pub`) over `data.bin` passes. the provider's
  `pkcs11-module-path` points at OpenSC's `pkcs11-spy.so` with `PKCS11SPY=$MODULE` and
  `PKCS11SPY_OUTPUT=$WORK/spy.log` (the spy logs every `C_*` call, independent of the provider's debug
  format; `opensc` is already in the image); the log is removed before each signature so counts belong to
  one run. For the 32-byte file the log contains `C_SignInit`, exactly one `C_SignFinal`, at least one
  `C_SignUpdate`, and no whole-word `C_Sign` call (`grep -w`). For a file of more than 1 MiB from
  `/dev/urandom`, signed and verified the same way, `C_SignUpdate` appears at least 2 times and
  `C_SignFinal` exactly once. Each fails the test otherwise, proving the multi-part path was taken.
  Exactly one agent request per signature.
- Acceptance 2, denial through the provider → agent in `deny` mode → `openssl dgst -sign` fails, no
  output file content, request counter increased by one.
- Acceptance 6 → `pkcs11-tool --login --pin 1234 --sign --mechanism SHA256-RSA-PKCS` (and one with
  `ECDSA-SHA256`) in `approve` mode → signature verifies and the counter rose by exactly one; in
  `deny` mode, a run that also uses `--login --pin 1234` and signs in the same process → fails, no
  output, and the counter rose by one, so the login did not authorize anything. A second `--login` signature asks again.
- Acceptance 10 → `git diff` of `e2e/user.sh` and `e2e/guest.sh` shows only added lines (one `source`
  line and the public-key export); the M0 assertions and their request counters are not edited. Since
  the new cases run after them and the counter is relative (read `requests` before use), the M0
  absolute counts (`expect_requests 1..6`) are unaffected.
- Suite is well formed → `just lint` (shellcheck on `e2e/*.sh`, typos, check-files) → exit 0, and
  `bash -n e2e/*.sh` → exit 0.
- Suite contains the cases → the feature's `verify` command → exit 0 (each of
  `SHA256-RSA-PKCS SHA384-RSA-PKCS SHA512-RSA-PKCS ECDSA-SHA256 ECDSA-SHA384 ECDSA-SHA512
  pkcs11-provider --login` found under `e2e`); removing any one name from the suite makes it fail.
- Caveat → the dev container cannot run `just e2e`; the pkcs11-provider options and the pkcs11-tool
  flags are checked by `--help`/man pages and `openssl` manually where possible, and F31 runs the real thing.
