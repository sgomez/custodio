# F212 — `custodio setup`: the setup commands grouped under one command

## Scope
Builds: `custodio setup browsers enable [--module <path>] | disable | refresh [--module <path>]` and
`custodio setup fingerprint enable | disable` (SPEC Design 3, acceptance 23), with the effects, refusals, output and exit statuses
that `register` (`[--module]`, `--remove`, `--refresh-only`) and `fingerprint` have before this feature; only command names change.
A nested level in the command table, so the help, the parser, the man page parity and the completions see every level of `setup`.
`custodio register` and `custodio fingerprint` become unknown commands, with no alias (no stable release, no frozen API). Every
message, the polkit file header, enable's undo hint, doctor's `Fix:` lines, the install notice of the three package formats,
`packaging/custodio.1`, the three completion files, `data/systemd-user/custodio-refresh.service`, the container and VM end-to-end
scripts, every test and the documents listed in features.json use the new names.

Fixed here, not reopened:
- `--module <path>` is an option of `setup browsers enable` and `refresh` (refresh copies from it to the snap's copy), not of
  `disable`, which removes the entries of every Custodio module file. `disable --module …` is a usage error. The tests that ran
  `register --remove --module <absent>` ("removal does not need the file") run `setup browsers disable`; the parser test of
  `--module X --remove` becomes the usage-error case.
- `JOURNAL_IDENTIFIER` stays `custodio-register`: it is a journal identifier, not a command name. Only the journal `MESSAGE` prefix
  names the new command.
- The polkit file header names `custodio setup fingerprint enable`/`disable`, with no compatibility with the pre-release header: a
  host that ran a pre-release `fingerprint enable` removes that file by hand.
- Historical records unchanged: `CHANGELOG.md`, `docs/release-notes-v0.8.0.md`, `docs/milestones/**`, `docs/findings/**`,
  `PROGRESS.md`'s earlier entries, `docs/decisions.md`, `IDEA.md`, contracts F193–F209.
- `docs/manual-acceptance.md` changes in every section that names `register` or `fingerprint` as a command, M6's included.
- The `justfile` line `DOC=docs/release-notes-v0.8.0.md scripts/test-docs-release-notes.sh` is removed: those notes describe the
  0.8.0 binary, whose `custodio register` the current binary no longer has; only the current release's notes (the script's default,
  0.9.0) are run.
- `docs/release-notes-v0.9.0.md` says that `register` became `setup browsers` and that `fingerprint` moved under `setup`.

Proven at the checkpoint F213, not here: `just check` as a whole, `just e2e` (the `fingerprint-*`, `doctor-*` and snap cases on the new
argv), `just package-gates` (real packages' install notice), coverage, CRAP and both VM modes. Acceptances 1–22 stay proven by the
tests that prove them today, re-pointed at the new argv.

Sizing: nine steps, over the five of the guideline. The split from the checkpoint is already made (F213), and the seams of the
large renames are taken now: packaging (5), e2e (6), document prose with its check (7), document runners (8). If step 3 still runs
past a session, the builder splits it at its seam (texts vs re-pointed tests) and notes it in PROGRESS.md.
`scripts/test-arch-lifecycle.sh` is updated in step 5 to the new names but not run here: it runs at F213 with the package gates.

Environment: probe `zsh --version; fish --version; shellcheck --version` in the dev container. Result in this session: all three
are present (`/usr/bin/zsh`, `/usr/bin/fish`, `/usr/local/bin/shellcheck`; F205 measured zsh 5.9, fish 4.0.2). If any is missing
when building, `BLOCKED.md`. The `justfile` change (the 0.8.0 notes line removed) has no test of its own: `just check` at F213
fails if it stays, so it is proven there.

  cases of Scope, no other assertion removed or loosened (review point) → pass.

  `custodio setup browsers disable --help`; plus one `setup.rs` run only for what the parser cannot show: status 2, stdout empty,
  fixture tree unchanged → pass. The error text is proven only by the parser unit test, not again by the binary run.
- `setup fingerprint enable`/`disable` = acceptances 1–4 → `tests/fingerprint.rs`, `fingerprint_decide.rs` and the fprint fixture
  tests on the new argv (same review point) → pass; `fingerprint_decide` unit tests: the file's PAM lines equal the pre-feature output (a

  lines differ and name the new commands, and `is_custodios` accepts what `enable` writes → pass.
