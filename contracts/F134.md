# F134 — End-to-end cases: every mechanism signs under each kind

## Scope
New cases `sign-*` for SPEC acceptance 2 and the signing half of 6: each key type signs through the PKCS#11 module with every
mechanism the module offers for it, and every signature verifies with the key's certificate using `openssl`. The cases run in
all three modes (`swtpm`, `none`, `lacking`), because in each mode the keys get a different kind and must sign the same way.

- **Mechanisms (from `crates/custodio-pkcs11/src/module/mechanism.rs` and `docs/api.md`).** RSA 2048: `RSA-PKCS` over a
  `DigestInfo` the test builds for SHA-256, SHA-384 and SHA-512, and over payloads that are not a `DigestInfo` (36 bytes of
  MD5||SHA-1, the TLS 1.2 form, and arbitrary bytes of a length that is neither 36 nor a DigestInfo length (51/67/83) and at most 245), because SPEC section 4 says "caller-supplied payload" and the TPM path
  must not parse or reject them (`docs/decisions.md`, "the service pads"); `RSA-PKCS-PSS` with SHA-256, SHA-384 and SHA-512 (MGF1 of the
  same hash) at each salt length in a set; `SHA256/384/512-RSA-PKCS` (composed). P-256: `ECDSA` over a SHA-256, a SHA-384 and a
  SHA-512 digest (the service truncates, `docs/decisions.md`) and `ECDSA-SHA256/384/512` (composed). The module offers no
  composed PSS mechanism, so none is tested.
- **PSS salt lengths.** The set per hash is 0, the hash length, and the largest the key admits (222/206/190 for a 2048-bit key
  with SHA-256/384/512, from F107), and a salt one byte above the largest must be refused with no signature. The first step
  checks these numbers against the running service with a short finding (`docs/findings/F134.md`) and may change the set only to
  what that finding proves; it also records whether `pkcs11-tool` passes `--salt-len` through, whether the over-maximum refusal reaches polkit (so the
  expected request count is exact), and the kinds the keys get in each of the three modes (so the `lacking` expectation is
  proven by a run, not by citation). "Each supported salt length" is
  therefore these values, not every integer.
- **Kind per mode.** The cases are meaningful only if the keys have the kind the mode is meant to give them, so one case,
  `sign-kind-matches-mode`, reads `ListKeys` for the test's own keys and expects: `swtpm`: RSA `tpm`, EC `tpm`; `none`: both
  `encrypted-host`; `lacking` (the filter removes RSAPSS): RSA `tpm`, EC `tpm` (amended: no key needs RSAPSS, `docs/findings/F134.md`). Exact
  values, never a substring. This is the only place the kind is judged here; the import kind under `swtpm` is F133's.
- **Verification of non-`DigestInfo` payloads** uses `openssl pkeyutl -verifyrecover` with the certificate's key: the recovered
  bytes equal the payload, and a control shows other bytes do not match (the pattern of `e2e/upgrade-user.sh`).
- **Verification** uses `openssl` against the public key of the certificate the module serves (read through the module with
  `pkcs11-tool`, then `openssl x509 -pubkey`), not the `.p12` on disk. PSS is verified with explicit `rsa_pss_saltlen` and
  `rsa_mgf1_md` options, so a signature made with another salt or hash fails. A control verifies the same signature against
  another hash or salt and expects failure.
- **Own keys.** As in F133 the cases import their own RSA 2048 and P-256 `.p12` (fixture checked with `openssl` for size and
  curve), as alice with the test agent approving, in a separate agent state directory, and delete them at the end, so the state,
  the request counts and the audit counts of the other steps are unchanged. The step runs after `tpm-kind` and before the
  upgrade; `select.sh` gets a group for `sign-*` (today they would fall to `user`).
- **Case ids**, each reported exactly once: `sign-kind-matches-mode`, `sign-rsa-pkcs`, `sign-rsa-pss-sha256`,
  `sign-rsa-pss-sha384`, `sign-rsa-pss-sha512`, `sign-rsa-composed`, `sign-ec-ecdsa`, `sign-ec-composed`. The builder may add
  one; every id matches `sign-*`.
- **Skips.** None applies to a mode: every case is `run` in `swtpm`, `none` and `lacking`. `skip.list` gets no `sign-*` entry and
  the accounting (`check-cases.sh`) must reject a `sign-*` reported skipped in any mode. (Description: "report as skipped in a
  mode they do not apply to" holds vacuously; stated here so the evaluator sees it is deliberate.)
- **Placement.** The ids go in `e2e/targets/debian13/cases.list`, not `e2e/cases.list` (SPEC end-to-end scope: the outcome depends
  on the TPM and the kind). The existing `composed-*`, `pkcs11-tool-*` cases (M1, every target, shared keys, `swtpm` and `none`)
  stay as they are; they do not run under `lacking`, which is why composed mechanisms are proven again here on own keys.
- **Not here.** Polkit refusal and one request per signature are F92/F97/M1 cases; here the agent only approves, and each
  signature must reach it once (checked by the request count of the case's own agent, which is the "every signature calls polkit"
  guard at no cost). No-plaintext (F135), non-duplication (F136), PCR/restart (later), failing TPMs (later).
- **Environment.** `swtpm 0.7.1`, the `lacking` filter and `pkcs11-tool` work in the debian13 container (`docs/findings/F131.md`:
  all three modes ran there). The builder confirms by running the first case in `lacking` before writing the rest.
- **Cost.** Host-side self-tests (judging functions on good and bad evidence, placement, the accounting rejecting a skip): under
  5 s, parallel with the other script tests (script default budget 60 s). In the container: about 20 signatures on RSA and 7 on
  EC; each is one `pkcs11-tool` process, about 0.5–1 s (the TPM RSA path pads in the service and does one raw operation). The
  signatures are independent, so the guest runs them at once (`xargs -P` or background jobs joined with `wait`), not one after
  another, and verifies them at once; the agent is awaited on its `registered` line, no fixed `sleep`. Estimate: 15–30 s per
  mode on top of the shared setup (about 2–3 min per `just e2e-cases` run, the debian13 `swtpm` full run is 360 s against a
  budget of 430 s). The `verify` runs `just e2e-cases` three times (one per mode, 3–4 min each, in separate commands). No new
  container, no budget change expected; if the measured full debian13 `swtpm` run passes 430 s the builder asks in BLOCKED.md.
- Proven at the checkpoint, not here: the full `just e2e` run and the package gates.
- `sign-kind-matches-mode` is a precondition guard: it reads `ListKeys` only, and the fallback kinds' CLI text and
  journal are F138's. The host test (b) is a regression guard on "no `sign-*` in `skip.list`" (`check-cases.sh` already rejects
  an unlisted skip); no new mode branch is added to it. Negative control (3) is run once in a throwaway copy and noted in
  `PROGRESS.md`, not added to any suite.
- Size: five steps; if the guest step runs over a session, split it at the signatures and the verification, one session each.

## Evidence
- Each key type signs with every mechanism, verified by `openssl` against the certificate's key → `sign-rsa-pkcs`,
  `sign-rsa-composed`, `sign-ec-ecdsa`, `sign-ec-composed` (`just e2e-cases debian13 'sign-*'` in each mode) → for each
  mechanism and hash, a signature of the right size (256 bytes RSA, 64 bytes raw EC r||s) that `openssl` verifies with the
  hash that mechanism used, and that fails when verified with another hash; each signature reached the case's agent exactly once, counted per signature (by the agent log), with an exact
  expected total per case fixed by the finding, so a missing call cannot hide behind a double one. `sign-rsa-pkcs` also signs
  a 36-byte MD5||SHA-1 payload and an arbitrary payload in every mode, and `openssl pkeyutl -verifyrecover` returns exactly
  that payload (other bytes do not match).
- PSS with each supported hash and salt length → `sign-rsa-pss-sha256`, `-sha384`, `-sha512` → at salt 0, hash length and the
  maximum, `openssl` verifies with that hash, MGF1 of the same hash and that exact `rsa_pss_saltlen`, and fails with a different
  salt length; the salt maximum plus one gives a failing `pkcs11-tool` run and an empty output file.
- Same results under the three kinds → the same cases in `swtpm` (`tpm`/`tpm`), `E2E_TPM=none` (`encrypted-host`) and
  `E2E_TPM=lacking` (RSA `tpm`, EC `tpm`) → every case `run` in each mode; no case differs between modes.
- The keys have the kind the mode intends (so the run is not vacuous) → `sign-kind-matches-mode` → the exact `ListKeys` kinds
  above for the two keys; and the host test feeds the judgement a `swtpm` list under `none`, an `encrypted-tpm` RSA under
  `swtpm`, and `encrypted-tpm` for EC or RSA under `lacking`, expecting rejection.
- Run in all three modes, none skipped → `scripts/test-e2e-sign.sh` (host, new) and the three `verify` commands → the ids are in the
  debian13 list and not in `e2e/cases.list`; a `sign-*` reported skipped is rejected by the accounting under each mode; each
  `just e2e-cases` exit 0 with eight cases `run`.
- State left as found → the same cases → both keys are deleted (`ListKeys` lacks them) and the later steps (request and audit
  counts, upgrade) still pass in the same run (the F133 argument; the full run is proven at the checkpoint).
- Negative controls, each must fail: (1) host test: the verify judgement on a recovered payload that differs, on a signature made with a different salt length, a
  different hash, a truncated signature and an empty output; (2) host test: a fixture swapped for a 3072-bit RSA key or a P-384
  key is rejected by the fixture check; (3) one run of `sign-rsa-pss-sha256` in a throwaway copy where the case asks for salt
  length 32 but verifies with 20 fails, then the copy is discarded.
- `just quick` green and the `verify` command → exit 0.

## Amendments
- Found by running (`docs/findings/F134.md`): (1) `pkcs11-tool` cannot sign with RSA-PKCS-PSS through this module (no public key object), so the PSS signatures, and the over-long RSA-PKCS
  payload whose first error `pkcs11-tool` hides, are made by `e2e/p11-pss.py`, a `ctypes` client of the module (C_SignInit with `CK_RSA_PKCS_PSS_PARAMS`, one C_Sign); every other mechanism uses `pkcs11-tool`.
  (2) Under `lacking` (RSAPSS removed) RSA is `tpm`, not `encrypted-tpm`: RSAPSS is not a capability any key needs; removing RSA instead makes the import fail with `CredentialsUnavailable`
  (`encrypted-tpm` needs a TPM-sealed `systemd-creds`, absent in the container; the fallback kinds are F138's). `sign-kind-matches-mode` expects `tpm`/`tpm` under `lacking`, fixed by a run.
  (3) The refusals (salt maximum plus one, a 246-byte payload) give `CKR_DATA_INVALID` in every mode and reach the agent; each case's request count is the exact total of its group.
  (4) Negative control (3) is dropped as the evaluator allowed: the host control on a different salt length already proves it.
