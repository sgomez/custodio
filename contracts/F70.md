# F70 — Per-owner state format in the key store

## Scope
Built, all in `crates/custodiod/src/store.rs` (and its `store/tests.rs`) plus the smallest change to callers
so the workspace compiles and the existing tests stay green:
- A new on-disk layout in which every key is stored under its owner uid, so a lookup by `(owner, id)` can only
  reach that owner's keys. The layout, file names and the way the owner is recorded are the builder's choice,
  but the owner must be both recorded with the key and used to separate keys by construction (a key of owner A
  is never found by opening a path that was derived from owner B). Ids stay under the existing `valid_key_id`
  rule; the owner is a `u32` and is never taken from an id or a string argument.
- `put`, `get` and `list` take the owner explicitly. `list(owner)` returns only that owner's ids.
- The existing rules, extended to the new layout (every directory level the store creates, not only the root):
  exact modes `0700` dirs / `0600` files, owner checks against the service uid, no symlinks (at every level),
  refuse rather than repair (no chmod/chown/removal of anything unexpected, apart from the existing cleanup of
  the store's own `.tmp-*` files), atomic no-overwrite writes, and exactly one key from concurrent inserts of
  the same `(owner, id)`.
- There is no migration code and no reader for the old flat layout. What the new store does when it finds an
  old-layout file in its directory is decided in step 1 within one limit: it never reads such a file as a key
  of any owner (if it refuses, the error is a generic unexpected entry, not a detector for earlier state) and never deletes or rewrites it (refuse rather than repair).
- Callers: `dbus.rs`, `import.rs`, `main.rs` and the integration tests under `crates/custodio-it` get the owner argument.
  The service takes the owner from the caller's bus uid obtained through the existing `CallerCredentials`
  (never from a method argument; no new D-Bus argument). Where a call site has no uid yet, it uses that trait
  and a failure becomes the existing "authorization unavailable" error. The certificate keeps being a second
  entry of the same owner.
Left for other features: the full owner scoping and credentials-failure behaviour of list, sign and import as
tested through D-Bus with two uids (F72), import order (F73), delete and replace certificate (later features),
upgrade e2e cases (F71). The "M3 to M3 upgrade keeps keys" requirement is proven at F90/F100 and F71.

Environment: nothing beyond the dev container. Concurrent-insert and ownership tests need no privilege: a
foreign owner is simulated with the existing `open_as`-style seam (an explicit expected uid), as today's tests do.

Size: about five steps; no split proposed.

## Evidence
All are tests in `crates/custodiod/src/store/tests.rs` unless stated.
- Owner recorded with the key, in a new format → test: after `put(owner, id, k)`, the bytes are on disk in a
  place that depends on the owner, and `get(owner, id)` returns `k` while `get(other, id)` is `NotFound`;
  a second test reopens the store (new `KeyStore::open`) and still finds the key under the same owner.
  Fails if the owner is ignored or not persisted.
- Owners kept apart, lookup never reads another owner's keys → test with owners A and B: `list(A)` shows only
  A's ids, `list(B)` only B's, `get(B, a_only_id)` is `NotFound`, including when B has no area yet; `get` and `list` for an owner without an area create nothing on disk (only `put` creates the area).
  A negative control: a key planted by hand in B's area with A's id is not returned for A.
- Ids unique per owner; two owners may each store `my-key` → test: both `put` succeed, each `get` returns its
  own bytes (different contents), a second `put(A, "my-key")` is `AlreadyExists` and leaves A's bytes intact.
- No argument can set or change the owner → API test: the owner is a separate typed `u32` parameter. Ids made
  only of digits or with a numeric prefix (`0`, `1000`, `1000-key`) stay valid under `valid_key_id`, and the
  existing `InvalidId` cases (`/`, `.`, `..`, empty, too long) stay rejected (regression check only). A
  separation test with crafted pairs that would collide if the layout joined uid and id into one name (owner 1
  with `00-x` and owner 10 with `0-x`; an id equal to another owner's uid) shows `get` and `list` never cross
  owners.
- The service passes the caller's bus uid as owner → required tests in `crates/custodiod/src/dbus/tests.rs`,
  with the existing fake credentials (uid 11, which is not the service euid; the rig keeps a handle to the
  store so the test can read it directly). Each fails if the service used `geteuid()`, `0` or a constant:
  - `import_p12` stores the key and its certificate under owner 11: `store.get(11, id)` and
    `store.get(11, cert_id(id))` return them and `store.get(<service euid>, id)` is `NotFound`. This also
    proves the certificate is a second entry of the same owner.
  - `list_keys` and `list_certificates` read owner 11's area: an entry put directly under 11 is listed, an
    entry put directly under another uid is not.
  - sign uses owner 11's area: a key put directly under 11 signs; the same id put only under another uid
    fails as not found.
  The two-uid D-Bus proof with several callers is F72.
- Exact modes → tests for the root dir, the per-owner dir and key files: created `0700`/`0600` even under a
  restrictive umask (reusing the umask child pattern); an existing root or owner dir with a loose mode is
  rejected with `BadPermissions` (root dir at `open`; owner dir on `get`, `list` and `put` for that owner) and its mode is unchanged afterwards; a loose key file is rejected on `get`.
- Owner checks → tests: root dir, owner dir and key file owned by a uid other than the expected service uid
  give `BadOwner` (for the owner dir and key file via the explicit-uid seam).
- No symlinks → tests: a symlinked root, a symlinked owner dir and a symlinked key file each give
  `BadFileType` (or the existing equivalent) and the link target is never read or written; a non-directory in
  the place of an owner dir and a FIFO as a key do not hang and are refused.
- Refuse rather than repair → test: after each refusal above, the entry is still there with the same mode and
  content; an old-layout flat file in the root (including one named like a valid id equal to an owner's uid, e.g. `1000`, so root entries and owner dirs cannot be confused) is neither returned by `get`/`list` for any owner nor modified or
  removed, and the outcome chosen in step 1 is asserted.
- Atomic writes, never overwrite silently, no leftovers → tests: `put` on an existing `(owner, id)` is
  `AlreadyExists` with bytes unchanged and no `.tmp-*` file left; `open` removes stale `.tmp-*` files of the
  store in the root and in an owner area; `list` skips temp files.
- Two concurrent inserts of the same `(owner, id)` leave exactly one key → test: N threads (at least 8)
  released by a barrier all call `put(owner, id, own bytes)`; exactly one returns `Ok`, the rest
  `AlreadyExists`, `list(owner)` has one entry, `get` returns the winner's bytes, no temp files remain;
  run on a fresh store whose owner area does not exist yet (covers the race creating it), repeated a few times. The test notes which primitive it covers: `put` must rely only on filesystem atomicity
  (`link`, `O_EXCL` or `renameat2` NOREPLACE) and hold no in-process lock, otherwise threads prove nothing about the disk. Concurrent inserts of the same id by two different owners both
  succeed (separate test).
- No migration code and no reader for earlier state → review of the diff: no function reads the flat layout
  as keys; the old-layout test above is the executable proof.
