# F180 — The encrypted state directory: classification, API and the CLI warning

## Scope
Builds Design 7 of SPEC.md, in this order of dependence:
1. **Finding.** `docs/findings/F180.md` (index line in `docs/findings.md`, in the form its rules fix, written
   before the code) settles, each **verified** by a command run in the dev container or by a source read, with
   versions: (a) how the service finds the block-device chain under its state directory with the access the
   unit already has (`PrivateDevices=`, `ProtectSystem=strict`, DynamicUser `StateDirectory=`) and no external
   tool: the mount table, `/sys/dev/block`, `slaves/`, `dm/uuid`; whether each of these is readable under the
   unit's sandbox, by a source read (systemd's documentation or source, with version) of what each of
   `DynamicUser=yes`, `PrivateDevices=yes`, `PrivateUsers=identity`, `ProtectProc=invisible`, `ProcSubset=pid`,
   `ProtectKernelTunables=yes` and `ProtectSystem=strict` in `data/custodio.service` does to `/sys/dev/block`,
   `/sys/devices/**/dm/uuid` and `/proc/self/mountinfo` (where a path is not readable the verdict is
   *unknown*, with the reason, and the contract is amended before building on it); how the state directory
   is reached under DynamicUser: `/var/lib/private/custodio` bind-mounted at `/var/lib/custodio` (its own
   case in the finding and in `state_storage`, alongside the symlink case: the mount entry's root and
   mount point differ from the path, and the classifier resolves it to the backing filesystem); (b) how dm-crypt is recognised (dm uuid prefix
   `CRYPT-`); (c) one verdict per case: plain partition, LUKS, LVM on LUKS, LUKS on LVM, dm-integrity under or
   over crypt, RAID (md) with and without crypt, btrfs over several devices, ZFS, fscrypt, NFS/CIFS/FUSE,
   overlay, tmpfs, bind mounts and a state directory reached by symlink. Default from SPEC: anything not
   proven dm-crypt is *unknown*; *not encrypted* only for a chain fully read that ends at physical devices
   with no dm-crypt in it. This closes the SPEC open question "Classifying the state directory".
   If a case cannot be shown by a command here (ZFS, fscrypt), the finding says so as **inferred** and the
   verdict stays *unknown*.
2. **Classifier** in custodiod, pure over a root path (so a fixture tree stands in for `/sys` and the mount
   table), returning encrypted / not encrypted / unknown. Never unknown-as-encrypted; every read error, loop,
   missing file or unexpected shape is *unknown*.
3. **Start-up journal entry** with the result (field named and documented in `docs/audit.md` under its
   compatibility rule).
4. **Bus API addition**, read-only, bus only (a property or a method; the builder chooses and documents it in
   `docs/api.md`, with the Compatibility rule). It is not served on the socket: F177's socket surface (exactly
   `ListKeys` and `Sign`, no properties) still holds. It asks no polkit and changes nothing.
   `just api-contract` and `scripts/test-docs-api.sh` check it against `docs/api.md`.
5. **CLI**: `custodio import` and `custodio list` read the value over the bus and print the warning (whoever
   takes the machine can use the keys, though not copy a `tpm` key; points to the README) for *not encrypted*
   and *unknown*; nothing for *encrypted*. Never blocks, never changes stdout of the data nor the exit status.
   If the service predates the addition (call fails / unknown name), no warning and no error. The README gains
   the full-disk-encryption section the warning points to, and the man page mentions the warning.

Not here: a real LUKS device and the real polkit; the classifier is proven on fixtures. The real unit is
not run by F180's `verify` (no VM there), so no VM case is added: the production wiring is proven in the dev
container by the entry-point test below, and the sandbox's readability by the finding's source read (step 1).
Re-running Design 7 in the VM is not claimed by any checkpoint. The man page and README prose are checked by
a person (SPEC Design 8), not by wording. One doc-against-code check is made: the README anchor the warning
names exists in `README.md` (`storage_warning.rs`).

Production entry point: the builder exposes one function used by `main` (`classify_state_dir(state_dir_env)`
or similar) that takes only the value of `STATE_DIRECTORY` and reads the real `/`, `/sys` and
`/proc/self/mountinfo`; `main` calls it and nothing else for classification. Step 1 runs the probe in the dev
container for two paths on different storage (the `/work` mount, ext4 on an NVMe partition with no dm, so
*not encrypted*, and a tmpfs such as `/dev/shm`, *unknown*), by the same method the classifier will use, and
records the command and the verdicts in the finding as a record of the dev container only. No test asserts
those recorded verdicts: CI runs `just test` on a GitHub runner with other storage. The test
`state_storage.rs::entry_point_real_root` is portable and calls the entry point with only `STATE_DIRECTORY`
set, for `/dev/shm` and for `CARGO_MANIFEST_DIR`. It asserts: `/dev/shm` is *unknown* when its mount entry is
tmpfs (skipped with a printed note if the machine mounts something else there); `CARGO_MANIFEST_DIR` is not
*unknown* when its mount entry is a block device (otherwise skipped with a note); and each entry-point result
equals the pure classifier run over root `/` for that same path, so a startup that classifies `/` or a fixed
path fails wherever the two paths differ. `entry_point_unset_state_directory_is_unknown` covers the unset case.

Environment: reading `/sys/dev/block` and `/proc/self/mountinfo` works in the dev container (it has `dm-0`,
`dm-1` in `/sys/block`); the step 1 finding runs the smallest commands to show what is readable. No new tool.

Start and bus share one value: the service computes the result once at start and keeps it; the bus reads that
stored value and never calls the classifier again (`bus_returns_*` use a stub that counts calls and fails if
called more than once, and `start_journals_storage_field` and `bus_returns_*` assert the same injected value).

Cost of the new tests:
- `crates/custodiod/tests/state_storage.rs`: one temp fixture tree per case (about 20 cases, one per case of
  the finding, plus unreadable/looping chain negative controls); pure filesystem, under 1 s total, parallel.
- `crates/custodiod/tests/storage_api.rs`: in-process service on a private `dbus-daemon` with the scripted
  polkit as in `api_kind.rs` (about 50 ms a case, about 5 cases, under 3 s), parallel; includes the socket
  not serving it.
- `crates/custodio-cli/tests/storage_warning.rs`: fake service client as in `storage_kind.rs`; milliseconds,
  about 8 cases, parallel.
- `api_contract` and `test-docs-api.sh` additions: tens of ms; within the `script *` 120 s budget.
- `just mutants-diff F180`: the diff is the classifier and the warning; estimated 5 to 10 minutes, one
  command.
- `entry_point_real_root` and `entry_point_unset_state_directory_is_unknown`: read a few real sysfs files,
  milliseconds, parallel.
- No e2e case, no VM case, no script test of its own.
Fits in six steps; no split.

## Evidence
- Finding settles the open question, each case verified or marked inferred → `grep -qF '(findings/F180.md)' docs/findings.md` and `just quick` (file-size check) → pass.
- Chain found without external tool, per case: plain partition → *not encrypted*; LUKS (dm uuid `CRYPT-`) → *encrypted* → `state_storage` cases `plain_partition_is_not_encrypted`, `luks_is_encrypted` → pass.
- LVM on LUKS → *encrypted*; LUKS on LVM → *encrypted*; LVM without crypt → *not encrypted* → `state_storage` named cases → pass.
- dm-integrity, RAID (with and without crypt beneath/above), btrfs over several devices, ZFS, fscrypt, NFS/CIFS/FUSE, overlay, tmpfs → one `state_storage` case each, named after the case (`integrity_is_unknown`, `raid_is_unknown`, `raid_over_crypt_…`, `btrfs_multi_device_…`, `zfs_is_unknown`, `fscrypt_is_unknown`, `network_fs_is_unknown`, `overlay_is_unknown`, `tmpfs_is_unknown`), each asserting exactly the verdict `docs/findings/F180.md` states for that case → pass.
- Never unknown as encrypted, one named test per control: unreadable `dm/uuid` → `unreadable_uuid_is_unknown`; missing `slaves` → `missing_slaves_is_unknown`; cyclic slaves graph → `cycle_is_unknown`; mount entry that does not match → `unmatched_mount_is_unknown`; `CRYPT-` uuid on a device not in the chain → `crypt_off_chain_is_ignored`; negative control, the same fixture as `luks_is_encrypted` with one link made unreadable flips *encrypted* to *unknown* → `unreadable_link_flips_encrypted_to_unknown` → pass.
- State directory resolved through a symlink (`state_dir_symlink`), through the DynamicUser bind mount `/var/lib/private` → `/var/lib/custodio` (`state_dir_private_bind_mount`), and to the longest-prefix mount entry with mount escapes (`longest_prefix_mount`) → pass.
- Production wiring: given only `STATE_DIRECTORY`, the real `/` is used and the verdict is that of the state directory, not of `/` → `entry_point_real_root` (portable: `/dev/shm` unknown, `CARGO_MANIFEST_DIR` not unknown when block-backed, both equal to the pure classifier over `/`) and `entry_point_unset_state_directory_is_unknown` → pass. Readability under the unit's sandbox → the finding's source read of each setting (a person reviews it; no test can run the unit here).
- Result journalled at start → `storage_api.rs::start_journals_storage_field`: starts the service as `main_tests.rs` does, with `JournalSink::new(<file>)` and a stub classifier injected through the same seam `start` receives, once per result (encrypted, not encrypted, unknown); the test reads the datagram captured in the file and asserts the documented field has the injected value. A start that never journals, or journals a fixed value, fails it. The field is documented in `docs/audit.md` (checked by the existing audit doc check) → pass.
- Bus API addition returns the result, read-only, no polkit call, no state change; the three values round-trip (same injected stub) → `storage_api` cases `bus_returns_encrypted`, `bus_returns_not_encrypted`, `bus_returns_unknown`, `bus_asks_no_polkit`, `bus_changes_no_state` → pass; not available on a socket peer → `socket_does_not_serve_storage` plus `just api-contract` (socket introspection exactly `ListKeys`, `Sign`) → pass.
- Documented and checked → `just api-contract && scripts/test-docs-api.sh` → pass; negative control: the `api_contract` fixture with the doc entry removed or its signature changed fails.
- Warning printed for *not encrypted* and *unknown*, not for *encrypted*; names the README; exit status and the data output identical with and without it; old service without the addition → no warning, no error → `storage_warning.rs` cases for both commands → pass.
- Warning points to something real → `storage_warning.rs::warning_anchor_exists_in_readme`: the README anchor the warning prints exists as a heading in `README.md` → pass; fails if the anchor is renamed.
- Man page mentions the warning (acceptance 14) → checked by a person (SPEC Design 8: prose is not tested by wording); no automated check.
- Tests catch wrong code → `just mutants-diff F180` → no surviving mutant outside the allow-listed ones.
