# F142 — End-to-end cases: upgrade from an M3 build purges its keys

## Scope
SPEC acceptance 9 against real packages: a package built from the tag `v0.5.0` (M3, state format without record magic, files `<uid>/<id>` and `<uid>/<id>-cert`) is installed in a fresh
container, keys are imported with it, this tree's package N is installed over it with the target's own `install.sh`, and the result is judged. Cases `upgrade-m3-*`, in
**`e2e/cases.list`** (every target: the package scripts, the package manager's upgrade and the service restart depend on the distribution; the purge itself is TPM-independent, so the
cases run in every mode and are never skipped for a mode).

**Measured now (the environment probe).** `git archive v0.5.0` into an empty directory, `cargo fetch --locked --offline` there: exit 0 (all crates of the tag are in the local cache, no
network needed). `cargo build --release --locked --offline -p custodiod -p custodio-cli -p custodio-pkcs11` of that tree with its own `CARGO_TARGET_DIR`: 21 s cold. `nfpm` is installed.
`podman` is present in the dev container, but `swtpm` guests do not run here (as for F141): the first guest run is the probe of the guest side; the dev container does the host tests.

Cases (each reported exactly once):
- `upgrade-m3-state-purged`: the old-format files exist before the upgrade (the pair of files per key, at least one pair per seeded key: otherwise the case fails, so a seed that
  imported nothing cannot pass), and after it none of them exists; no file under the state directory is of the old format (no file named like a key id or `<id>-cert` without the
  current record format; the judgement is on the file names and on the absence of the old files' sha256, not a grep of docs).
- `upgrade-m3-list-empty`: after the upgrade `ListKeys` as alice and as bob and `custodio list` in each of their sessions show none of the keys (empty), not an error.
- `upgrade-m3-journal-purge`: the journal entries with operation `purge` since the install (`docs/audit.md` fields, read with `journalctl` by field; no source-reading) are exactly one
  per key: the multiset of (owner uid, key id) equals the seeded set, with the same id under two owners counted twice and no entry duplicated or missing; none carries a caller. How
  `docs/audit.md`'s published queries find them is F144's, not repeated.
- `upgrade-m3-reimport`: the same ids (the ones purged, under the same owners) import again with the current `custodio import` and real polkit approval, and are listed afterwards under
  their owners; this also proves the old files do not block them.

Seed: two accounts, four keys, built with the M3 build's own CLI: alice's `rsa1` and `ec1`, bob's `rsa1` (same id, other owner) and `bobonly`. The builder reuses `upgrade-accts.sh seed`
(it already does this for the old-path run) if it works against the M3 CLI, and otherwise writes a small seed of its own; the number and owners above are fixed.

Left to other features and not repeated: that no call is answered before the purge is complete, a second start purging nothing, refusal on a symlink, entries without key bytes (F121,
integration target `purge`); the audit queries (F144); keys, owners, certificates and kinds kept between two M4 builds (F48/F96/F141); the old-path upgrade (F61). Package gates and
`just e2e` as a whole run at the checkpoint.

**Packages.** A new script `scripts/package-m3.sh`, called by `just e2e-packages` (and so by `e2e` and `e2e-cases`), builds the M3 packages into `target/packages-m3`: the tree of the tag
(read with `git archive`, never the working tree, never checked out over it), built with the tag's own recipe and a version lower than N's and N+1's in all three formats by the target's
own comparison (the builder picks it; N is 0.1.0 and the M3 tree is also 0.1.0, so the version must be lowered, e.g. a pre-release or a smaller patch; `e2e/upgrade-lib.sh`'s
`upgrade_gate` refuses an equal or lower target, which is the control in the guest). It does not touch `target/packages`, `-next` or `-oldpath`. The build is kept between runs and reused when
the tag's commit and the script are unchanged (a stamp file), so a warm `e2e-packages` adds about 1 s and a cold one about 40 s (21 s measured for the compile, plus archive, nfpm and the
tag's own package check). The tag missing (a shallow clone) fails with a message, never skips silently. All three formats are built, so every target with a package pattern has an M3
package; a target without one (a refusal-only target installs nothing) lists the cases in its `skip.list` with that reason.

**Guest run.** The M3 run is its own guest run on a fresh container (a mode of `guest.sh` next to `oldpath`; run.sh mounts `/pkg-m3` and makes the run only when an `upgrade-m3-*` case is
selected, or always without a selection). It installs the M3 package, sets up the TPM of the mode as the other runs do, seeds, takes the state snapshot, installs N over it with the target's
`install.sh` (nothing else is run by hand), waits on a condition for the service to be up with a new main pid (no fixed sleep beyond what `upgrade.sh` already does), and judges. The
cases are reported by that run (`select.sh` group `other-mode`, as `upgrade-oldpath-*`). The accounting of the main run for a target must not see them as its own.

**Cost.** Host test `scripts/test-e2e-m3.sh` (judgement functions in `e2e/upgradem3.py`, python3 `-I`; script stubbed, no container, no network): under 5 s, in the justfile
script-test list, parallel with the others. Guest: one extra container run per target and mode, estimated 60–90 s (boot ~10 s, install of M3 and TPM setup ~20 s, four imports ~15 s, the
upgrade ~15 s, judgements ~5 s); it runs concurrently with the other target-mode runs under `E2E_JOBS`. Not an e2e case beyond this: the judgements are python functions tested on the host.
`just e2e-cases debian13 'upgrade-m3-*'` is that run plus the shared setup of the main run (~40 s), unless run.sh can skip the main run for a selection that needs none (the builder
decides; if it is a small change it does it, with a host test, else it measures and notes the cost). The full `just e2e` grows by six target-modes of ~75 s each in parallel, so about +75–150 s
of wall clock depending on `E2E_JOBS`, plus the build above. The builder records the measured times in PROGRESS.md and asks for a bigger budget in BLOCKED.md if `budgets.tsv` is passed.
Size: five steps; no split proposed.

## Steps
- [ ] Tests first, host side: failing `scripts/test-e2e-m3.sh` (judgements of `e2e/upgradem3.py` on good and bad records, the build script's stamp and failure paths with stubbed
      tools, the accounting rules: the ids in `e2e/cases.list`, group `other-mode`, never skipped in a mode, skipped only with the refusal-only reason); add it to the justfile script-test
      list; then `e2e/upgradem3.py` until it passes.
- [ ] `scripts/package-m3.sh` and its wiring in `e2e-packages`: build the three formats from `v0.5.0` into `target/packages-m3` with a lower version; run it once for real; check the
      three files exist, the version is lower than N's by the format's tool, the packaged daemon is the tag's (not this tree's); time the cold and the warm run.
- [ ] Guest side: `/pkg-m3` mount and the M3 run in `run.sh`, mode `m3` in `guest.sh`, `e2e/upgrade-m3.sh` (seed with the M3 build, snapshot, install N, judge, re-import), the ids in `e2e/cases.list`
      and the `check-cases.sh` rules; the self-tests of the upgrade scripts and the host tests of run.sh/guest.sh still pass.
- [ ] Run `just e2e-cases debian13 'upgrade-m3-*'` and the same for `fedora44` in `swtpm`, then both with `E2E_TPM=none` (the verify's runs; the four may run at once as separate commands
      only if they fit the engine, else one after another), and one other target (alma10 or arch) in `swtpm` as a check of the other formats; fix what the first real run shows; note times
      in `PROGRESS.md`.
- [ ] `just quick`; `PROGRESS.md` entry with the measured times against `budgets.tsv`.

## Evidence
- A script builds M3 packages from `v0.5.0` into `target/packages-m3`, and `just e2e-packages` builds them → `scripts/test-e2e-m3.sh` (stubbed: stamp reuse, missing tag fails, `target/packages*` of N, N+1 and old path untouched) and the real run of step 2 (`just e2e-packages`; `ls target/packages-m3`) → deb, rpm and Arch package of a lower version than N, built from the tag's tree.
- The M3 build is installed on the targets with an M3 package, keys are imported → the guest's seed in `upgrade-m3-state-purged` (fails if fewer than one old-format pair per key before the upgrade) → four keys, two owners, old files present before; `just e2e-cases debian13 'upgrade-m3-*'` and `fedora44` in `swtpm` and `none`.
- After the upgrade the state directory has no file of the old format → `upgrade-m3-state-purged` (same runs) → none of the old paths or hashes remains.
- `list` shows none of those keys → `upgrade-m3-list-empty` (same runs) → API and CLI listings of both accounts are empty.
- The journal has one purge entry per key → `upgrade-m3-journal-purge` (same runs) → exactly the four (owner, id) pairs, once each.
- The same ids import again → `upgrade-m3-reimport` (same runs) → the four imports succeed with polkit approval and are listed under their owners.
- Cases are listed in `e2e/cases.list` and accounted once → `check-cases.sh` accounting in every run and `scripts/test-e2e-m3.sh` → reported once, never skipped in a mode, not seen by the main run.
- A test can fail → `scripts/test-e2e-m3.sh` (in `just quick`) → good records accepted; rejected: an old file left, a file of the old format under another name, a listed purged key, a missing, extra or duplicated purge entry, a wrong owner on an entry, a seed with no old files, a reimport that failed; a stubbed `upgrade-m3.sh` with the judgement left out fails.
