# SPEC deviations

Requirements of SPEC.md that nothing this project ships can meet, and what is built instead. A
builder adds an entry with the contract amendment; the evaluator approves both; a person reviews
every entry before `just milestone close`: updates SPEC.md and sets `accepted`, or sets `rejected`
with what to build instead.

Format:

```
## <feature id> — <requirement, in a few words>
- SPEC: section and the sentence that cannot hold.
- Proof: the finding in docs/findings/<id>.md (source or command run).
- Instead: what is built, and its evidence in the contract.
- Status: <pending when added; accepted or rejected by a person>
```

## F110 — encrypted-key fallback bound to the TPM and never to a PCR, on systemd 255 and 257
- SPEC: section 5, "It is bound to the TPM when there is one and to the host key otherwise, and **never to any PCR**, explicitly, whatever the default of the systemd version installed", with a service that is not root.
- Proof: `docs/findings/F110.md`. debian13 and alma10 (systemd 257): the unprivileged call is only the Varlink daemon's `auto` key, whose PCR mask is the daemon's own command-line default, PCR 7 (creds.c v257:1032-1033, 1219-1224; read from source, *inferred* because no kernel TPM can be reached from a container), so with a usable TPM the credential is PCR-bound and the caller cannot change it. ubuntu2404 (255): no `--user`, no Varlink; as uid 992 `--with-key=host` fails `Failed to determine local credential host secret: Permission denied`, `--with-key=tpm2 --tpm2-pcrs=` works against swtpm (TPM alone, no uid binding).
- Instead: on debian13 and alma10 the service reads the stored PCR mask back from each new credential and refuses a nonzero one, so the fallback is unavailable on those machines when a TPM is present (host+uid-bound without a TPM); on ubuntu2404 the service runs `systemd-creds encrypt --with-key=tpm2 --tpm2-pcrs=` itself (TPM alone), and there is no encrypted fallback on a machine without a TPM. Evidence: the tests of the storage feature (F120) and the real-hardware run (F147), which reads the mask of a Varlink credential on a machine with a TPM and can drop the 257 part.
- Status: pending

## F134 — signing under "encrypted, TPM-bound" in the end-to-end runs (also F135, F137, F138)
- SPEC: Acceptance 6, "with a TPM lacking a needed capability, 'encrypted, TPM-bound'. [...] the keys sign as in 2", among the automated acceptances run by `just e2e` with `swtpm`.
- Proof: `docs/findings/F134.md`, last section. The proof is for debian13, the target the SPEC scope gives these cases (not claimed for the others: ubuntu2404 on systemd 255 seals with the CLI and `--tpm2-device`, F110 says that works as the service user; fedora44 and ubuntu2604 run newer systemd). In the debian13 container, the root `systemd-creds` daemon, the only route of the service on the 257 targets, never seals to a TPM (`System lacks TPM2 support or running in a container`), because systemd detects the container by its PID namespace, has no override in 257, and the Varlink `Encrypt` takes no key choice. With a real lack (filter `alg=0x1`) the import fails with `CredentialsUnavailable`. On the 257 targets the kind cannot exist outside a container either (F110 above).
- Instead: under `E2E_TPM=lacking` the F131 filter (RSAPSS removed) stays, both keys are `tpm`, and `sign-kind-matches-mode` expects exactly that. The `lacking` run therefore adds no kind coverage over `swtpm`: it only repeats the same signing with a filtered TPM. Signing under `encrypted-tpm` is covered by two integration tests, neither a full end-to-end proof: (a) every mechanism and every PSS hash and salt length (0, hash length, maximum) with controls, under `encrypted-tpm`: `kinds_suite::sign_every_mechanism_verifies` (F126), with a credential double over a filtered `swtpm`; (b) a credential sealed by the real `systemd-creds` to `swtpm`: the `sign_kinds` failure rows (`crates/custodiod/tests/sign_kinds/failures.rs`), RSA-PKCS and ECDSA verified. Gap, stated plainly: PSS is never verified with a real TPM-sealed credential. F138's `lacking` half meets the same limit: `fallback-tpmbound-import` and `fallback-tpmbound-cli-list` are reported skipped in every mode (`check-cases.sh` refuses them reported run), and what they would prove is covered by `crates/custodio-cli/tests/storage_kind.rs`, `import_encrypted_tpm` (the kind `encrypted-tpm`, the words "weaker" and the TPM-lacks-a-capability reason in the import output) and the same file's `list_shows_each_kind` (the `encrypted-tpm` row of `custodio list`), with `kinds_suite` (F126) producing the kind; not an end-to-end proof. The `fallback-host-*` cases do run end to end in mode `none`. F135 (acceptance 3, no plaintext key in the state directory) meets it too: `lacking` gives `tpm`/`tpm`, so `encrypted-tpm` is not run end to end by `noplain-*`. Instead of an end-to-end run, F127's test `crates/custodiod/tests/no_plaintext/service.rs` (the `encrypted-tpm` cell, lines 66-71) runs `check-no-plaintext.sh` over the service's state directory after an import; stated plainly, that cell uses `MemoryCreds::tpm()`, an in-memory stand-in for the credential store, behind a filtered `swtpm`, not a credential sealed by the real `systemd-creds`. An automated run of the kind would need a VM target, which this milestone does not have. F137 (acceptance 5, first part: keys sign after a PCR extension and restarts of `swtpm` and the service) meets it for the `encrypted-tpm` half only: `pcr-*` runs `tpm` keys (the real daemon, module, polkit, `systemctl restart`); `encrypted-tpm` keys surviving the same PCR extension and both restarts are covered by F129 (`tpm_lifecycle`) with a credential double, not by the real `systemd-creds`; no `encrypted-tpm` claim is made by `pcr-*`. The PSS gap above is unchanged. Status of the choice: the person's confirmation of option C of the earlier BLOCKED.md is recorded only in the builder's commit 9cd5dc7; the reviewing person should confirm it.
- Status: pending
